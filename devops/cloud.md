# DevOps · 云平台基础（面试题库）

本文件考察候选人在云平台工程落地上的真实能力：服务模型选型（IaaS/PaaS/SaaS/FaaS）、计算/存储/网络等基础服务选型、高可用与容灾架构、成本优化（FinOps）、身份与密钥安全、CDN 与边缘、Serverless、混合云与迁移、监控与事件驱动，以及从零设计一套云上高可用系统的综合能力。题目全部为场景化提问、不考八股文——重点看候选人能否给出量化依据、说清取舍、引用线上事故与排障过程、主动覆盖边界条件，难度从实践基础渐进到架构级设计。

### Q1. 一个小团队要做"最省钱"的云选型，怎么定 IaaS/PaaS/SaaS/FaaS？

**问题：** 你是一家 10 人创业公司的架构负责人，预算有限、没有专职运维，需要把"业务应用、用户认证、报表服务、监控告警"全部上云。你会怎么在这四种服务模型里做取舍？选择的判断维度是什么？

**期望加分项：**
- 说清四种模型的本质差异：交付粒度（基础设施/运行时/应用/函数）与责任边界，能对应 AWS（EC2/RDS/SaaS/ Lambda）或阿里云（ECS/RDS/云市场/Function Compute）举例
- 明确判断维度：团队运维能力、业务变更频率、成本结构（固定成本 vs 按调用量付费）、合规与可移植性，而不是"越高级越好"
- 给出混合选型结论：核心业务用 PaaS（RDS/PaaS 容器），认证/报表这类可替代能力买 SaaS，无明确峰值规律、量小且延迟不敏感的部分用 FaaS
- 会算账：例举一台 ECS 月成本与同等能力 PaaS 的差价、FaaS 在低 QPS 下的冷启动与费用拐点（如日均调用 <1 万次时 Lambda 常驻无意义）
- 指出陷阱：团队没运维能力却硬上 IaaS + 自建中间件，隐性人力成本远高于云账单

**减分项：**
- 只背"PaaS 不用管服务器"这类概念，说不出选择依据和量化对比
- 一刀切"全用 Serverless 最省钱"或"全部 IaaS 最灵活"，忽略业务形态与团队能力
- 不考虑责任边界与合规（敏感数据能不能放 SaaS）
- 无成本模型概念，不会估算人力成本 vs 云账单
- 忽略厂商锁定与迁移成本对选型的影响

**解答：**

选型不是"哪个模型高级"，而是"把运维复杂度交给谁最划算"。责任边界图是最有效的工具：IaaS 自己管 OS 以上全部，PaaS 管到运行时，SaaS 只管数据，FaaS 连扩缩容都不管。判断维度按优先级：一是团队运维能力——10 人团队没人专职 DBA，数据库必须用托管 RDS，自建 MySQL 的主从、备份、故障切换足够拖垮整个团队；二是变更频率与流量特征——主业务迭代快、流量有高峰，用托管容器平台或弹性伸缩的 ECS；三是成本结构——固定月费对比按量付费。我给这类团队的典型组合：应用层用 PaaS（阿里云 SAE/容器服务或 AWS ECS，免运维底层 K8s），数据库用 RDS（多 AZ + 自动备份），认证/告警/工单这类通用能力直接买 SaaS（Auth0、云监控告警），只有确证"日均调用量低、无明显峰值"的边缘功能（如图片缩略、定时任务）才用 FaaS。量化上要算总拥有成本：一台 4C8G 的 ECS 约 300 元/月，加上自建 MySQL 的 DBA 人力折合可能比 RDS 贵 3 倍；而 FaaS 在低调用量时近乎零成本，但一旦 QPS 上千且要求低延迟，常驻实例的费用与冷启动问题就会暴露。记住一句话：选模型就是选"你要为哪些运维责任买单"，省下的责任迟早以事故或人力还回来。

**延伸考点：** 什么业务特征下 FaaS 的成本优势会反转？同一套代码如何在 IaaS 与 FaaS 之间迁移，成本分别由谁承担？

### Q2. 业务流量有规律波动，VM、容器、Serverless、裸金属怎么选？

**问题：** 你们平台有四种负载：①核心交易 API（延迟敏感、流量稳定但有秒杀峰值）；②批量离线任务（每天固定时段跑 2 小时）；③对外提供裸机性能的数据库性能压测服务；④内部低频管理后台。请为每种负载选定计算形态，并说明弹性与成本的权衡。

**期望加分项：**
- 一一对应给出结论：交易 API 用容器或 VM + 弹性伸缩（秒杀时扩容、平时缩容），离线任务用 Serverless（按运行时长付费，闲置零成本），压测服务用裸金属（高性能计算、网络延迟低、性能可预期），低频后台用 FaaS 或低配实例
- 说清弹性的本质差异：VM 分钟级扩容（需镜像预热/启动脚本），容器秒级，FaaS 毫秒级但受冷启动约束，裸金属几乎无弹性（需提前备货）
- 会讲成本模型：裸金属是固定成本高、单位性能便宜；FaaS 是按量付费、但长耗时任务成本失控；VM 预留实例与按量价格差 40%-60%
- 提到秒杀场景的配套：容器 + HPA 前要预留配额/库存、镜像预热、数据库连接数上限等连带瓶颈
- 能指出 Serverless 不适合的边界：长时运行（>15 分钟）、需要 GPU、强连接维持（WebSocket 长连接）

**减分项：**
- 所有负载一律"上容器"，不做形态匹配
- 分不清容器与 VM 的扩容速度差异和资源隔离边界
- 不知道裸金属的价值场景，只会说"裸金属贵"
- 忽略 FaaS 冷启动对延迟敏感业务的影响
- 不谈弹性之后的连带瓶颈（数据库、连接数、配额）

**解答：**

计算形态本质是在"弹性粒度、启动速度、成本结构、性能确定性"四个维度上做选择。交易 API 对延迟敏感、峰值是秒杀型，用容器（K8s HPA 或 AWS ECS）+ 弹性伸缩最合适：平时 10 个副本、秒杀时 30 秒内扩到 50 个，但要提前配好镜像预热、节点池扩容时间和数据库连接池上限，否则扩容的是计算、卡死在数据库。批量离线任务每天固定跑 2 小时，典型用 Serverless：AWS Lambda（最长 15 分钟，拆分任务）或阿里云函数计算 + 定时触发，闲置时间零成本，2 小时费用约等于一台低配 ECS 的 1/10。压测服务要模拟真实用户、对 CPU 性能与网络延迟要求可预期，用裸金属（AWS EC2 Bare Metal / 阿里云 EBM）：没有虚拟化损耗、性能曲线稳定，压测数据才可信，代价是几乎无弹性，要按峰值需求备机。低频管理后台直接 FaaS 或 1 核 1G 低配实例，月成本几十元。核心权衡是：VM 用预留实例能省 40%-60% 且弹性中等，适合流量有规律波动的核心业务；FaaS 按调用量计费适合"闲置时间长、偶发触发"的任务，但冷启动（首调 200ms-1s）会伤害对延迟敏感的服务，且累计运行时长越长单位成本越贵——把 7×24 常驻的流量硬塞进 FaaS 是常见的成本失控点。

**延伸考点：** 秒杀场景下容器扩容快但数据库是瓶颈，你会怎么设计限流与削峰？Lambda 与容器在突发流量下的冷启动差异如何量化？

### Q3. 文件系统应用要上云，对象存储和文件存储怎么选？

**问题：** 你们系统里有三类数据：①用户上传的图片和视频；②多台应用服务器需要共享读写的配置文件与临时目录；③需要按业务目录结构长期归档的报表。请分别选择存储方案，并说明对象存储与文件存储在一致性、协议、计费上的关键差异。

**期望加分项：**
- 分类明确：图片视频用对象存储（OSS/S3），共享读写目录用文件存储（NAS/EFS），报表归档用对象存储 + 生命周期策略
- 说清本质区别：对象存储走 HTTP(S) API、无文件系统语义（无目录树、无随机写，最小对象 1KB 起按容量计费），文件存储走 NFS/SMB 协议、支持 POSIX 语义与并发挂载
- 讲一致性：对象存储是"读后写一致"（写成功后立刻可读，但列表/跨桶复制有最终一致窗口），文件存储提供强一致
- 会提生命周期管理：OSS/S3 标准 → 低频 → 归档（Glacier/OSS IA）分层的 cost 节约，如 30 天转低频、90 天转归档能省 60%+ 存储费
- 指出常见坑：应用直接拿文件系统语义写对象存储（追加写、目录重命名）会踩性能/语义坑；NAS 跨地域复制与快照成本
- 提到图片处理配套（OSS 的图片处理/缩略图、CDN 分发加速）

**减分项：**
- 把对象存储当"无限大的文件系统"用，忽略无随机写/追加写语义
- 说不清强一致与最终一致的场景差异
- 没有生命周期/存储分级意识，所有数据一律标准存储
- 忽略协议差异（NFS vs HTTP API）对应用改造成本的影响
- 不知道 NAS 与对象存储在计费（按容量 vs 按容量+请求次数）上的区别

**解答：**

三类数据分开答。用户上传的图片视频用对象存储：OSS/S3 按 HTTP API 读写，天然配合 CDN 分发和图片处理服务（OSS 自带的缩放/水印，上传后自动触发处理函数），成本低（标准存储约 0.12 元/GB/月，还随量递减）。多台应用服务器要共享读写配置与临时目录，用文件存储 NAS/EFS：走 NFS 协议挂载到 ECS 上，多台机器同一路径并发读写、权限统一管理，应用代码几乎零改动；对象存储做不了这个，因为它的语义是"整体 PUT/GET 对象"，不支持并发追加写和 POSIX 权限。长期归档的报表走对象存储加生命周期：标准存储放 30 天、低频放 60 天、之后转归档存储（OSS 归档/AWS Glacier），归档单价约为标准的 1/5，但要记住取回有延迟（分钟到小时级）且要收费，所以热数据千万别直接进归档。关键差异要能讲清：一致性上，对象存储写成功后"读自己写的对象"保证一致（read-after-write），但跨桶复制、目录列表存在最终一致窗口；文件存储是强一致。协议上，对象存储无目录树概念，看似有"目录"其实是前缀；随机写和追加写要么不支持、要么性能极差，数据库数据文件、日志追加这类负载放对象存储是典型误用。计费上，对象存储按容量 + 请求次数（GET/PUT 各计费），高频小文件访问费用会意外飙升，这是很多人踩过的账单坑。

**延伸考点：** 日志这类"持续追加、高并发写入"的数据，放对象存储为什么不行？你会怎么设计日志的上传与归档链路？

### Q4. 生产环境突然被扫到 SSH 暴力破解，网络层面怎么防御？

**问题：** 你负责一个新上云的 VPC，里面有 Web 服务器和数据库，运维同事反映"公网 SSH 一直被暴力破解，安全组加了一堆 IP 白名单还是被绕过"。请完整设计这套云网络的隔离方案，并讲清安全组与 NACL 的分工与差异。

**期望加分项：**
- 给出完整分层设计：VPC + 子网划分（公网子网放 Web/负载均衡，内网子网放应用与数据库，数据库子网禁止公网访问）、路由表、安全组、NACL 各司其职
- 讲清安全组与 NACL 的本质差异：安全组是实例级有状态防火墙（回包自动放行，默认全拒，只支持 allow），NACL 是子网级无状态（入站出站都要显式配，支持 allow/deny 和优先级），安全组适合按角色配，NACL 适合做子网级的"保险丝"
- 给出 SSH 防护实践：SSH 端口改高位 + 密钥登录 + 安全组只对堡垒机 IP 开放，堡垒机（跳板机）统一入口
- 提专线/VPN 方案：管理面走 VPN/专线内网接入，公网完全不放行 22 端口
- 指出"被绕过"的可能原因：安全组规则配错了方向（只加了入站没加出站）、用了 0.0.0.0/0 兜底、NACL 与安全组叠加判断
- 提审计：VPC Flow Logs/阿里云流日志排查真实访问来源

**减分项：**
- 分不清安全组与 NACL 的"有状态/无状态"差异
- 只会在安全组里堆 IP 白名单，不理解攻击面在"公网直接暴露管理端口"
- 不设计网络分层，数据库与 Web 同网段同安全组
- 不知道出站规则与回包的关系（有状态 vs 无状态）
- 没有堡垒机/管理面隔离意识

**解答：**

先纠正方向：安全组加白名单防不住暴力破解，因为公网 IP 是动态的、攻击源会不断换；正确思路是"让管理端口根本不在公网暴露"。网络设计分三层：第一层 VPC 与子网，按职责划分——公网子网只放负载均衡（ALB/SLB）和 Web 服务器，应用服务器放内网子网，数据库放独立内网子网且路由不允许出公网；第二层安全组做实例级白名单，Web 安全组只放 80/443 入站，应用安全组只允许来自 Web 安全组（用安全组 ID 而非 IP 引用），数据库安全组只允许应用安全组访问 3306/5432——安全组之间互相引用是 AWS/阿里云都支持的最佳实践；第三层 NACL 做子网级兜底，比如数据库子网 NACL 显式 deny 所有外部网段入站，即使安全组配错也有最后一道闸。SSH 管理统一走堡垒机：公网只开堡垒机 IP 的 22 或高位端口，堡垒机再做登录审计，内网服务器只允许堡垒机的安全组访问，甚至可以加 VPN/专线让管理流量完全走内网。安全组与 NACL 的核心差异必须说清：安全组有状态——你放行入站后，回包自动放行，只管入站方向即可；NACL 无状态——入站和出站都要显式写规则，支持 deny 且按编号优先级匹配。所以安全组适合表达"谁可以访问我"，NACL 适合表达"这个网段不该碰什么"。最后用流日志（VPC Flow Logs）确认没有遗漏的暴露端口，持续观察异常来源。

**延伸考点：** 安全组引用安全组在跨账号/跨 VPC 场景下还成立吗？NACL 的 deny 规则适合防御什么类型的攻击？

### Q5. 线上出现"部分用户请求报 502/504"，负载均衡层怎么排查与设计？

**问题：** 你们用云负载均衡（ALB/SLB）接入三个应用实例，某天大促时出现"部分用户请求 502、部分请求 504、还有请求串会话"的投诉。请从负载均衡的监听、健康检查、会话保持角度完整排查，并说明何时应该引入 API 网关。

**期望加分项：**
- 排查路径清晰：先看监听器后端响应码分布（502=后端不可达/无健康实例，504=后端处理超时），再查健康检查判定（路径选对没有、阈值/间隔、实例 CPU 打满导致健康检查也超时）
- 讲健康检查设计：用专门的 `/healthz` 轻量接口而非主页；调小间隔加快摘除、调大不健康阈值避免抖动；后端实例在扩容/发布时延迟注册
- 说会话保持的坑：大促扩容后会话哈希集中在少数实例、某实例故障导致会话丢失——会话保持不等于无状态，回答"什么时候必须关掉会话保持"
- 对比 LB 与 API 网关：网关负责协议转换、限流、鉴权、灰度路由，LB 只做四/七层转发；流量入口复杂化（多后端协议、多团队）时才值得引入
- 给出量化手段：看负载均衡的并发连接数、后端队列深度、超时时间配置（ALB idle timeout 60s）

**减分项：**
- 502/504 分不清，直接"重启后端"
- 健康检查路径用首页，不知道探针要独立轻量
- 回答"会话保持开着就没事"，不理解无状态化才是正解
- 分不清 LB 与网关的职责边界，什么流量都往网关塞
- 没有使用负载均衡指标（指标看板、日志）排障的意识

**解答：**

502 与 504 含义不同：502 Bad Gateway 通常是负载均衡无法连上任何健康的后端（健康检查全挂、后端宕机、或后端端口不通）；504 Gateway Timeout 是后端有响应但超时（应用慢、线程池打满、慢 SQL）。排查顺序：先看负载均衡控制台的目标组/后端服务器健康状态——大促时最常见的是健康检查挂了一批实例：健康检查路径用了首页，首页在大促时响应慢或返回 5xx，导致健康检查连续失败把实例误摘除，于是 502；而 504 通常是应用线程池或数据库连接池打满，负载均衡转发后等待超时。健康检查要专门设计：路径用 `/healthz`（不查数据库、不加鉴权、返回即 200），间隔设 5s、不健康阈值 3 次快速摘除，健康阈值 2 次防抖动；后端扩缩容时开启优雅注销（deregistration delay）让存量连接走完。会话保持的问题要讲透：SLB/ALB 的 cookie 粘滞在大促扩容后会失衡（新实例分不到流量、旧实例被打爆），且实例故障时会话直接丢——所以"粘滞会话"是过渡手段，正解是应用无状态化（session 外置到 Redis/数据库），这也是云架构里反复出现的主题。LB 与 API 网关的区别：LB 解决"流量转发到后端"，网关解决"流量在入口的统一治理"——限流、鉴权、API 版本路由、协议转换（HTTP→gRPC）；只有多团队、多协议、需要统一入口治理时才值得引入网关，否则一套 LB + 应用内鉴权就够了，过度设计网关是常见错误。排查工具上，ALB 的访问日志 + 后端指标（P99 延迟、线程池）联动，能快速定位是 LB 层还是应用层。

**延伸考点：** 健康检查挂了但实际访问正常的实例，和实际访问异常但健康检查正常的实例，分别是什么原因？如何设计探测使其覆盖真实路径？

### Q6. 数据库 CPU 打满、主从延迟告警不断，自建还是托管 RDS？

**问题：** 你们原来在 ECS 上自建 MySQL 单机，最近业务翻倍，出现 CPU 打满、磁盘告警、半夜备份影响线上查询，你被要求"把数据库挪到云上"。请对比托管 RDS 与自建 MySQL 的取舍，并给出一个完整的迁移与高可用方案。

**期望加分项：**
- 说清托管 RDS 的价值：自动备份（PITR 时间点恢复）、多 AZ 主备自动切换、只读副本、内核级性能优化（如阿里云 RDS MySQL 的 binlog 优化），运维人力释放
- 讲取舍：RDS 价格高于自建（实例+存储+IOPS 计费），且受实例规格上限约束，超大规模（数百 TB、超高 QPS）或特殊内核定制时仍要自建
- 多可用区方案：主备跨 AZ，RDS 主备切换 RTO 秒级，只读副本（read replica）分担读流量，注意副本延迟与一致性读
- 迁移路径：DTS（阿里云数据传输服务）/DMS 全量+增量同步，先校验数据一致性，再改读写流量（改连接串 + 灰度），最后停写切换
- 备份恢复：RDS 自动备份默认保留 7 天，开启 binlog 才能做 PITR；恢复演练要真做过一次
- 指出坑：切换只读副本后连接串变更、主备切换瞬间连接中断、超大事务导致副本延迟飚升

**减分项：**
- 只说"RDS 省事"，说不出自动备份/多 AZ/副本这些具体能力差异
- 自建派与托管派一刀切，没有按规模/人力/成本权衡
- 迁移只谈"导出导入"，不知道增量同步与一致性校验
- 忽略备份保留期与 PITR 的配置细节
- 不知道主备切换对应用连接池的影响

**解答：**

对比的框架是"把哪些运维责任外包出去"。自建 MySQL 要自己管：安装、主从复制、故障切换（通常要搭 MHA/Orchestrator 或 Pacemaker）、备份与恢复演练、版本升级、内核调优——这些在一个没有专职 DBA 的团队里是持续的人力和事故风险。托管 RDS 把这些打包：自动备份默认保留 7 天并可开 binlog 支持 PITR 到任意秒，多 AZ 部署下主备自动切换 RTO 秒级、RPO 接近 0，只读副本几十分钟就能拉起一个分担读流量，还有云厂商内核优化（比如阿里云 RDS 的 buffer pool 预热、并行查询），读多写少的业务用"1 主 + 2 只读副本 + 应用读写分离"能解决 80% 的性能问题。代价是钱：RDS 按规格+存储+IOPS 计费，同配置通常比自建贵 20%-50%，且单实例有规格上限，超大规模或需要深度定制内核的场景（比如金融级两地三中心、亿级 QPS）仍要自建。迁移要用工具而非手工：用 DTS/DMS 建任务做全量迁移 + 增量同步，同步期间跑一致性校验（行数+校验和），确认追平后停写窗口内切换应用连接串，灰度放量后观察主从延迟再彻底切流量。容易踩的坑：切换后连接串变更要提前改好连接池；主备切换瞬间已有连接会断开，应用要有重连机制；大事务（批量更新几十万行）会让只读副本延迟飙到分钟级，写多读少的业务要评估副本延迟对一致读的影响。备份一定要演练过"恢复"而不是只确认"备份成功了"——很多事故是备份在、恢复不了。

**延伸考点：** RDS 主备切换时应用连接会断，如何在应用层做到无感？只读副本的延迟如何监控与告警？

### Q7. 单可用区宕机 40 分钟，老板要"再也不能发生"，高可用架构怎么设计？

**问题：** 你们的应用和数据库都部署在同一可用区，一次机房故障导致全部服务宕机 40 分钟。老板要求"提高可用性，给出方案和预算"。请设计一个多可用区高可用架构，并说明可用性指标（SLA）怎么算、怎么权衡成本。

**期望加分项：**
- 定义可用性目标：把 SLA 从 99.9%（年宕机 8.8h）提升到 99.99%（年宕机 52min），量化设计目标
- 分层冗余设计：负载均衡（跨 AZ 多节点）→ 应用多 AZ 多实例（无状态 + 弹性伸缩）→ 数据库多 AZ（RDS 主备跨 AZ / Aurora 自动容错）→ 对象存储（本身跨 AZ 冗余）
- 讲设计模式：无状态化（会话外置）、冗余（N+1）、解耦（消息队列削峰填谷）、优雅降级（缓存兜底）
- 说清 RTO/RPO：多 AZ 切换 RTO 分钟级内、RPO 秒级；同城容灾（双 AZ）vs 异地（跨地域）的成本差距
- 提到故障演练：混沌工程/可用区故障演练（AWS 的 AZ 故障注入、阿里云的容灾演练），确保切换流程真的可用
- 算账：多 AZ 的额外成本约 +50%-100%，用业务损失对比投入

**减分项：**
- 只加机器，不解决无状态与数据层冗余
- 说不出 SLA 与成本的量化关系
- 数据库仍是单点（单 AZ 自建主库）
- 不做故障演练，切换流程停留在文档
- 忽略"多 AZ 也要测试"，没有验证过 AZ 故障时的真实表现

**解答：**

先立目标：原 SLA 99.9% 对应年宕机 8.76 小时，这次的 40 分钟是"单点故障全部命中"；要提升到 99.99%（年 52 分钟），设计必须消除单点。核心是三层冗余：接入层用跨多 AZ 的负载均衡（SLB/ALB 本身就是多 AZ 冗余的）；应用层多 AZ 各部署 2+ 实例，配弹性伸缩，实例必须无状态（session 放 Redis、文件放对象存储），这样任一 AZ 挂掉，流量被负载均衡调度到存活 AZ，RTO 分钟级；数据层最容易被忽略——数据库必须跨 AZ：用 RDS 多 AZ 部署（主备不同 AZ，切换秒级）或 Aurora/云原生数据库（存储跨 AZ 3 副本自动容错）；缓存、消息队列也要跨 AZ。设计模式上，"冗余、无状态、解耦"三件套：无状态化让"哪台机器死都无所谓"，消息队列把突发流量削峰、避免雪崩，降级策略保证依赖故障时核心链路可用（比如推荐服务挂了返回兜底缓存）。可用性计算要会：99.99% 的月 SLA 对应每月 4.3 分钟，多 AZ 设计是"自动切换"，关键是切换流程要演练过——用混沌工程定期做 AZ 故障演练（AWS 的 AZ 级故障注入、阿里云容灾演练），验证负载均衡切换、数据库主备切换、DNS 变更是否真的按预期发生，很多团队"设计了高可用"却在演练时发现切换流程里有手工步骤、权限缺失、依赖启动顺序错误。成本权衡：多 AZ 一般让计算成本 +50%（每 AZ 至少 1 副本）、数据库翻倍（主备两份），是否再加异地容灾（成本再 +100%）取决于 RPO/RTO 要求与业务损失评估——先做同城多 AZ，用业务止损金额对比年度新增云成本。

**延伸考点：** 多 AZ 与多地域的成本和 RTO 差异是多少？"双活"与"主备"在流量调度上的本质区别是什么？

### Q8. 月度账单比预算高 30%，FinOps 怎么落地？

**问题：** 你接手一个月的云账单审计，发现比预算超支 30%：有闲置 ECS、存储只增不减、某测试环境的资源规格被越提越高。请设计一套成本优化与治理方案（FinOps），说明从哪里下手收益最大、怎么防止回弹。

**期望加分项：**
- 先讲清成本构成：计算（通常占 50%+，按规格/时长）、存储、网络流量（出口流量计费最容易超支）、数据库、托管服务，用账单按服务/项目/标签拆分定位 TOP 项
- 给出量化抓手：①闲置与低利用率实例——用云监控 CPU 曲线，连续 7 天 CPU<5% 的实例降配或停机；②预留实例/节省计划——稳定负载按 1-3 年预留省 40%-60%；③存储生命周期——标准转低频转归档；④规格降配——用真实监控数据而非"拍脑袋"定规格
- 讲治理机制：成本标签（tag）强制覆盖所有资源、按团队/项目分账、预算告警（超 80% 告警）、容器/弹性伸缩消除"规格拍脑袋"
- 提 Spot 实例/竞价实例的场景：无状态、可中断的任务（离线计算、CI、大数据）用竞价实例省 50%-90%
- 防止回弹：把成本优化嵌入发布流程（新资源必须打标签、必须有规格依据），月度成本复盘会
- 指出典型坑：出口流量费、快照/镜像冗余、日志存储、未绑定的弹性 IP

**减分项：**
- 只会"关掉几台机器"，没有系统性的分账与度量
- 不知道预留实例/节省计划这类结构性优惠
- 忽略标签与分账，改造成本无法量化、没人对账单负责
- 不看实际使用率就降配/关停，导致线上故障
- 没有防回弹机制，优化完下个月又涨回去

**解答：**

FinOps 第一步是"看得清"：在账单里按服务、按标签（业务线/环境/负责人）拆分，把成本归属到团队，同时把成本数据接入监控大盘，让"成本"和"资源利用率"放在一起看。第二步按收益排序动手：①结构性优惠最稳——把稳定运行 7×24 的核心实例买成预留实例或节省计划（AWS 3 年全预付约省 50%+，阿里云包年包月类似），这一步对账单的直接削减最大；②打闲置——用云监控拉出连续 7 天 CPU 利用率 <5% 的实例清单，逐个确认后停机/降配，测试环境晚上定时关机（阿里云可以配"节省停机"模式，按磁盘收费几乎不花钱）；③降配要基于数据——很多实例 4C16G 实际 CPU 常年 10%，降一半规格用户无感知，但要用监控曲线做依据并保留弹性伸缩兜底；④存储走生命周期——日志、备份、旧快照用生命周期规则自动转低频/归档，快照保留策略从"每天全量"改为"日增量+周全量+保留 30 天"；⑤可中断任务上竞价实例——离线计算、CI 构建、大数据批处理用 Spot 实例（便宜 50%-90%），前提是任务可重跑、断点续跑，这也是对"无状态"能力的考验。防回弹机制是 FinOps 的核心：所有新建资源强制打成本标签，未打标签的资源由平台自动回收或告警；预算阈值告警（消耗达预算 80% 时通知，100% 时告警）；月度成本复盘把"单位成本/请求"作为效率指标——成本优化不是一次性的，是嵌入发布与日常流程的持续治理。最容易忽略的账单项：公网出方向流量费（几台机器一天拖几 TB 数据就几千块）、未释放的弹性 IP、冗余快照与镜像、日志服务存储量。

**延伸考点：** 容器化之后"实例规格"消失了，如何继续做成本分账与优化？Spot 实例被回收时应用如何优雅处理？

### Q9. 运维误删生产资源，IAM 权限怎么治理才能既安全又不影响效率？

**问题：** 最近一位刚入职的运维同学在控制台误删了一个生产 Redis 实例，排查发现他拥有管理员权限。老板要求"收紧权限，但不能让开发每次提权限都要等一天"。请设计一套云 IAM 权限治理方案。

**期望加分项：**
- 讲清 IAM 三要素：用户（人）、角色（授予给服务/跨账号）、策略（权限声明），以及"策略生效 = 身份 + 资源 + 操作 + 条件"
- 最小权限落地：按角色分策略（运维/开发/审计/财务），生产与测试环境用资源标签或资源前缀隔离，删除类高危操作（Delete*/Terminate*）默认拒绝、走审批
- 用角色而非长期密钥：应用进程用实例角色（AWS Instance Profile/阿里云 RAM 角色）自动获取临时凭证，杜绝把 AccessKey 写进配置
- 条件上下文（Condition）精细化：限定来源 IP、限定 VPC、MFA 要求、限定资源标签（只能删 tag=env:test 的资源）
- 权限变更流程：自助申请 + 门禁审批（如自建/云上 IaC 的权限申请流程），默认只读，临时提权带时间窗口自动回收
- 审计闭环：CloudTrail/操作审计日志开启，误删后能定位"谁在什么时候干了什么"

**减分项：**
- 只会说"最小权限"四个字，给不出具体的策略设计
- 把 AccessKey 放在应用代码/配置里，没有角色/临时凭证意识
- 删库类高危操作与普通操作同权限，没有分级审批
- 不区分人身份与服务身份，管理面一锅烩
- 没有审计与告警，权限给出去就不管了

**解答：**

核心原则：默认只读、按角色授权、高危操作单独管控、用角色代替密钥。设计上分三步。第一，身份与角色分离：人用 IAM 用户，服务用实例角色——ECS/EC2 启动时绑定 RAM 角色/Instance Profile，应用运行时自动获取临时凭证（STS），这样代码里永远不需要 AccessKey；这是很多公司安全事故的根源（密钥硬编码在配置里被扒走）。第二，策略按最小权限+条件收敛：运维角色只给生产资源的管理权但排除删除类操作——对 `Delete*`/`Terminate*`/`Release*` 这类高危操作默认 deny，需要时走临时提权（比如 30 分钟窗口自动回收）；更精细的用法是用 Condition 限定——只有来自办公网 IP 的请求才允许执行变更、删除必须带 MFA、只能操作 `tag:env=test` 标签的资源，这样"误删"即使发生也只会发生在测试环境。开发日常要用的权限走自助申请：默认只读 + 对测试环境资源的读写，生产变更权限通过审批流（工单系统 + 事后审计）发放。第三，审计闭环：开启操作审计（AWS CloudTrail/阿里云操作审计），把 API 调用日志接入日志平台，配置"DeleteBucket/DeleteInstance/RemoveRole"等高危操作的实时告警——误删事件后 10 分钟内定位到人和操作来源，同时把审计作为权限治理的反馈（谁被拒绝太多次、谁的权限长期未使用）。权限治理的平衡点是效率：不要"一刀切全只读"让业务瘫痪，而是"默认低权限 + 自助申请 + 自动回收 + 审计兜底"，把人为事故转成系统约束。再补一条：定期做权限盘点（未使用的角色、90 天未登录账号、跨账号权限），用 IaC 管理权限变更，让权限像代码一样可评审可回滚。

**延伸考点：** 跨账号访问（如 CI 从开发账号部署到生产账号）怎么用角色与信任策略实现？临时凭证（STS）的有效期与刷新机制怎么设计？

### Q10. 磁盘加密、传输加密、应用改造，KMS 密钥管理怎么做才不失控？

**问题：** 你们收到合规要求"所有存储与传输必须加密、密钥必须可管理可轮换"。目前 ECS 上数据盘未加密、数据库连接是明文、应用里有若干写死的加密常量。请设计一套以 KMS 为核心的密钥管理方案。

**期望加分项：**
- 讲清 KMS 的定位：云上的统一密钥托管（主密钥 CMK/用户主密钥），存储加密（EBS/OSS/RDS 的 KMS 加密）、信封加密（Envelope Encryption：数据密钥 DEK 加密数据、CMK 加密 DEK）
- 落地路径：①存储层——ECS 数据盘、OSS、RDS 全部开启 KMS 加密（新建资源默认加密，可做"默认加密策略"）；②传输层——全链路 TLS/SSL（LB 终结 + 回源加密）；③应用层——敏感配置用 KMS 加密存储，应用通过 SDK 解密（AWS Secrets Manager/阿里云 KMS 的凭据管理）
- 讲信封加密解决性能与密钥分发：大数据量加密用 DEK 而非 CMK 直接加密，CMK 只做 DEK 的加解密，成本与速度都可控
- 密钥轮换：CMK 自动轮换（年轮换），应用侧密钥用版本管理；轮换对应用透明，坏处是"轮换会破坏旧数据"是错误认知
- 权限与审计：KMS 策略独立管控（谁可以用哪些 key、哪个 key 只能给哪个服务用）、对 Decrypt 调用做审计告警
- 指出坑：密钥丢失=数据永久不可恢复（KMS 删除 key 有 7-30 天宽限期，别手滑）；跨账号/跨地域的密钥分发限制

**减分项：**
- 只会说"开启加密"，说不清加密的是数据还是密钥、加密谁管
- 不懂信封加密，不知道 KMS 为什么不直接加密大数据块
- 把密钥轮换与数据解密混为一谈，说不清轮换不影响已加密数据
- 忽略 KMS 权限独立治理与审计
- 没有"密钥丢失不可恢复"的边界意识

**解答：**

密钥管理方案要分三层落地。第一层存储加密：ECS 数据盘、OSS、RDS 全部用云厂商 KMS 主密钥（CMK）加密——这是"默认开启"级别的配置，新建资源统一打"加密"标签，甚至可以设置账号级默认加密策略，防止有人新开资源忘开加密；这一步覆盖的是"磁盘被拖走、快照外泄"的场景。第二层传输加密：入口 LB 终结 TLS，回源到后端走内网 + 双向证书或内网加密，数据库连接开启 SSL（RDS/MySQL 的 SSL 参数组），全链路不留明文。第三层应用层：敏感配置（数据库密码、第三方密钥、支付证书）不落配置文件，存到 KMS 凭据管理（AWS Secrets Manager / 阿里云 KMS 凭据）——应用启动时用 SDK 读取并解密，代码里连明文都不出现。关键技术是信封加密：KMS 不直接加密业务数据（大数据块用 CMK 加密又慢又贵），而是先生成一个数据密钥 DEK（明文用于本地对称加密数据、密文版存起来），用 CMK 加密 DEK；需要解密时用 CMK 解开 DEK 再解数据。这样 CMK 的调用量极少、性能与成本都可控，OSS/EBS 的加密内部就是这个机制。密钥轮换要讲清：CMK 自动轮换（默认一年）生成新密钥版本，但"轮换只影响新数据的加密"，旧数据仍用旧版本可解密——所以轮换是安全的、对应用透明的；真正危险的是删除密钥——删除后数据永久无法解密，所以 KMS 删除主密钥都有宽限期（7-30 天）且要二次确认，这是运维手滑最容易造成"数据永久丢失"的按钮。最后是治理：KMS 的策略独立管理——哪些角色可以用哪个 key、哪个服务能用哪个 key，对 `Decrypt` 调用记审计日志，密钥的使用频率异常（比如半夜批量解密）触发告警，防止"加密了但密钥被人偷用"。

**延伸考点：** 应用侧的对称密钥如果由自己管理（非 KMS），轮换与分发怎么做才能不停机？KMS 跨地域复制（如两地三中心）与跨账号授权如何配置？

### Q11. 首屏图片加载慢、境外用户访问超时，CDN 怎么救？

**问题：** 你们 App 首屏有大量图片和视频，国内用户反馈"高峰期加载慢"，海外用户直接打不开。目前所有请求都打到源站。请设计一套 CDN + 边缘计算方案，并讲清缓存命中、回源、动态加速的原理。

**期望加分项：**
- 讲清 CDN 原理：边缘节点就近缓存静态资源，命中则不再回源；缓存 key（URL）、TTL 与缓存策略（Cache-Control/Expires、CDN 侧规则）、回源与刷新预热
- 分场景落地：图片/视频/JS/CSS 走静态加速（CDN），App API 走动态加速（TCP 优化、传输协议优化、边缘节点回源），海外用全球节点/海外加速
- 给量化指标：命中率目标是 90%+，命中率低时先查缓存 key 是否被带参 URL 破坏、TTL 是否太短、是否被强制刷新
- 讲缓存穿透与一致性：发布时用"刷新+预热"，带版本号的文件名（指纹化）让更新即新 URL；敏感数据不进 CDN 或签私有鉴权 URL
- 提边缘计算：边缘函数（Edge Function/CloudFront Functions）做 A/B 分流、请求改写、鉴权、图片实时处理，减少回源
- 指出坑：回源带宽费、跨域/HTTPS 证书配置、动态接口误设长 TTL 导致数据陈旧

**减分项：**
- 只会说"加了 CDN 就快了"，说不出命中率、回源、TTL 这些核心机制
- 静态与动态流量不区分，动态 API 也套长缓存导致数据陈旧
- 发布后用户还看到旧版本，不知道刷新与版本指纹的关系
- 海外场景只说"开全球节点"，不讲证书、合规（数据出境）、回源链路
- 没有指标（命中率/回源率/延迟）驱动的意识

**解答：**

CDN 的核心是"就近缓存 + 回源兜底"：用户请求被调度到最近的边缘节点，节点按 URL 查缓存，命中直接返回，未命中才回源站取并缓存。设计上先分类流量：静态资源（图片、视频、JS/CSS、字体）走静态加速，配置缓存规则——图片这类几乎不变的资源 TTL 设长（7-30 天），HTML/接口这类易变的设短或走动态加速；API 走动态加速（阿里云 DCDN / AWS CloudFront 的动态路径），本质是优化边缘到源站的传输链路（TCP 优化、连接复用、就近回源），而不是缓存响应。海外访问打不开通常是公网跨国链路抖动，用 CDN 的海外节点就近接入即可，注意数据出境合规（域名/节点区域选择）。落地后的关键指标是命中率：目标 90%+，低于这个值优先排查三类原因——①缓存 key 被参数污染（URL 带 `?timestamp=` 这类随机参数导致每个请求都是新 URL），要配"忽略指定参数"；②TTL 太短或源站响应头没带 Cache-Control；③回源超时或源站不稳定导致缓存失效。发布一致性是高频事故点：版本号进文件名（`app.1.2.3.js`）是正解——新版本自然生成新 URL、旧缓存自动过期，发布时对新资源做"预热"（主动把热点资源推到边缘），而不是依赖清缓存；纯静态 HTML 变更时用"刷新"配合指纹化。边缘计算的场景：在边缘节点上做鉴权（私有视频的签名 URL 校验）、请求改写、A/B 分流、图片实时裁剪（阿里云 CDN 图片处理 / CloudFront Functions），把本该回源的计算下沉到边缘，延迟和回源成本同时下降。最后要防的坑：缓存了不该缓存的动态数据（用户订单、未登录页面）、回源带宽突然飙升（监控回源流量，热点资源及时预热）、HTTPS 证书与回源协议不一致导致的混合内容报错。

**延伸考点：** CDN 回源失败（源站故障）时如何设计"降级缓存"让老版本继续服务？私有内容（付费视频）怎么用签名 URL 保证只有授权用户能访问？

### Q12. 单体应用要改造成 Serverless，哪些能迁、哪些不能迁？

**问题：** 你们的旧单体应用（Java Spring Boot）有 20 个 REST 接口、3 个定时任务、1 个 WebSocket 推送服务、几十个依赖本地文件的批处理模块。CTO 想"全部 Serverless 化"，请给出评估结论与分阶段改造路径，并说清 Serverless 的约束。

**期望加分项：**
- 先给约束清单再下结论：FaaS 的硬约束——执行时长上限（AWS Lambda 15 分钟/阿里云 FC 类似）、冷启动延迟（200ms-1s）、无状态（本地磁盘与内存不保证持久）、连接数管理（数据库连接池在函数实例间不共享）
- 分类评估：无状态 REST 接口可迁（小函数、按量付费），定时任务迁定时触发器，WebSocket 长连接不迁（或迁到托管网关 + 函数处理消息），批处理看时长（>15 分钟要拆分或换容器）
- 讲改造要点：数据库连接复用（用连接代理/RDS Proxy 或按实例池设计）、启动时间优化（Java 换 GraalVM 原生镜像或迁 Go/Node）、依赖外置（本地文件迁对象存储）
- 讲迁移对比：成本模型变化（闲置零成本 vs 常驻费用）、弹性能力（自动扩到千并发 vs 手动/配额上限）、运维简化
- 指出迁移收益与代价的量化：QPS 低时省 60%+ 成本，但冷启动与无状态约束带来的重构工作量
- 提醒渐进路径：先迁 1-2 个接口验证，别"大爆炸"式重写

**减分项：**
- 无脑"全部迁"，不评估时长/状态/连接约束
- 不知道冷启动对延迟敏感接口的影响
- 把本地文件、内存 Session 直接搬进函数
- 数据库连接池在函数里"每次调用建连接"导致连接耗尽
- 没有渐进迁移与回退方案

**解答：**

先亮约束，再谈迁移。FaaS 的硬边界有四条：执行时长（Lambda 最长 15 分钟）、冷启动（并发突增或闲置后首调 200ms-1s）、无状态（本地临时盘不可靠、进程可能随时被回收）、资源共享困难（函数实例之间不能共享数据库连接池和本地文件）。对照你们单体：20 个 REST 接口绝大多数是无状态 HTTP 处理，适合迁——按业务拆分函数，API 网关（AWS API Gateway/阿里云 API 网关）做路由和限流，QPS 低时费用几乎为零；3 个定时任务用定时触发器（CloudWatch Events/cron 触发）天然合适；WebSocket 推送不建议直接迁——长连接不适合函数模型，正确做法是 WebSocket 网关保持长连接、消息处理走函数（连接管理与业务解耦）；批处理模块看时长，超过 15 分钟的要么拆成任务分片（SQS/SWF 分片并发执行），要么用容器（ECS Fargate）而不是硬迁函数。改造的三个关键点：①数据库连接——函数实例并发时会各自建连接，要么用 RDS Proxy/连接复用组件，要么接受连接池上限并按实例数控制并发；②启动时间——Java 的 JVM 冷启动是灾难，迁函数时优先考虑 Go/Node，或 Java 用 GraalVM 原生镜像把冷启动压到几百毫秒；③依赖外置——本地文件、Session、临时目录全部换对象存储和外部缓存。迁移收益要量化：闲置时段零成本、突发自动扩容到千级并发（不用预置机器）、免运维；代价是重构工作量与冷启动对延迟的伤害。落地建议：先迁 1-2 个低频接口跑通监控、成本、发布流程，验证函数超时、连接、权限都没问题再扩展，保留旧单体作为回退——Serverless 化是工程改造不是重写，任何"三个月全量重写"的计划都该警惕。

**延伸考点：** 函数并发数上限（默认 1000）到了会发生什么，如何做并发控制与限流？幂等性在函数重试（at-least-once 语义）下如何保证？

**减分项：**
- 说不清共享责任模型的分界在哪一层
- 等保方案只列名词（防火墙/WAF/堡垒机），说不清对应哪个控制项
- 忽略"运营类"控制项（巡检、演练、漏洞管理、制度）
- 不知道日志留存时长与审计要求的关系
- 把合规当一次性采购，没有持续运营意识

**延伸考点：** 等保要求"日志留存 180 天"，云上日志量巨大时存储成本怎么控制？勒索病毒（Ransomware）场景下，云上备份与不可变存储（immutable backup）怎么设计？

### Q14. 数据主权 + 多云容灾，混合云/多云策略怎么设计？

**问题：** 公司有存量自建机房（核心交易数据被要求本地存储），新业务想用公有云弹性，同时老板担心"被一家云厂商绑定"。请设计一套混合云/多云架构，覆盖数据同步、容灾、避免厂商锁定三个诉求。

**期望加分项：**
- 先分清三种模式的适用性：混合云（本地+公有云）解决存量与数据主权；多云（两朵公有云）解决容灾与议价；厂商锁定是"架构与数据可移植性"问题而非"用了几家云"
- 混合云落地：本地机房与云上 VPC 用专线/Direct Connect 打通，数据同步（数据库 DTS 双向同步、对象存储跨地域/跨云同步），弹性溢出（本地资源不足时把新流量弹性到云上）
- 数据主权场景：敏感数据留本地，云上只跑加工与报表（数据不出域的处理方案、脱敏/沙箱）

- 防厂商锁定：Kubernetes 统一容器层（标准 API）、对象存储用 S3 兼容协议（MinIO/阿里云 OSS 兼容）、Terraform 管理 IaC（跨云一致）、避免深度绑定服务（专有数据库引擎、专有消息协议）
- 指出坑：多云不等于双活（一致性、延迟、成本都翻倍）、云间同步带宽费、跨云身份与审计割裂

**减分项：**
- 把"多云"理解成"多买几朵云"就完事，没有架构设计
- 双活拍脑袋，不谈数据一致性与分布式事务复杂度
- 不区分存量与增量，混合云的"为什么"说不清
- 防锁定只谈 K8s，不谈数据层（数据库、对象存储）的锁定
- 忽略云间同步的成本与延迟

**解答：**

三个诉求要分开设计。混合云的核心驱动是存量与数据主权：自建机房是既成投资，核心交易数据有监管要求必须本地，那就本地机房 + 专线（阿里云高速通道/AWS Direct Connect）连公有云 VPC，数据双向同步（数据库用 DTS 双向同步、对象存储用跨云同步工具），平时本地为主、高峰期把可弹性部分（Web 层、离线计算）溢出到公有云——混合云的收益是"存量不浪费 + 弹性照拿"。数据主权场景，敏感库留在本地，云上只部署加工任务，用脱敏/沙箱方式让云上任务"不落地明文"或只处理脱敏副本。多云容灾要克制：生产在云 A，云 B 只做容灾（数据库异步复制到云 B、应用镜像与 IaC 就绪、灾备切换预案），RTO 小时级、RPO 分钟级；不要一开始就做"双活"——两个云同时写同一份数据的一致性复杂度（分布式事务、冲突解决）与云间延迟会让成本和事故概率都翻倍，双活是成熟期才考虑的形态。防厂商锁定的正确姿势：锁定发生在"架构与数据"，而不是"用了几家云"。落地手段分三层——容器层用 Kubernetes（标准 API，跨云一致）；存储层用 S3 兼容协议（阿里云 OSS 原生兼容 S3 API，或自建 MinIO 做统一抽象）；基础设施层用 Terraform 管理（写一次，换 provider 适配另一家）；避免深度绑定：别用云厂商独有的数据库引擎（如专有 NoSQL）、独有的消息协议、独有的 Serverless 运行时（FaaS 是绑定最深的）。数据层锁定最贵：迁移几 TB 对象存储的出口流量费、数据库重新迁移的停机窗口，都要在设计期预判。最后提醒成本：云间同步流量按量计费、双份存储、双份监控告警——多云从来不是省钱方案，是买"可用性与谈判筹码"的保险。

**延伸考点：** 数据库跨云同步的延迟与一致性如何保障（主从复制还是消息补偿）？K8s 跨云统一调度与"多云就绪"（未发生故障时用不用）的成本对比怎么算？

### Q15. 上千台老服务器要迁上云，Rehost 还是 Refactor？

**问题：** 你们有 500 台物理机/VM 上的旧系统（多年未升级的 Java 应用 + 老 MySQL + 定时批处理），老板要求"一年内迁上云，停机窗口越短越好"。请给出迁移评估方法、策略选择（Rehost/Replatform/Refactor）与执行计划。

**期望加分项：**
- 迁移策略分四类并给出适用场景：Rehost（整体搬迁，用迁移工具/镜像导入，最快）、Replatform（换托管服务，如自建 MySQL→RDS）、Refactor（重构为云原生）、Retire（下架）；一年窗口内主流是 Rehost + Replatform 混合
- 评估先行：迁移评估工具（AWS Application Discovery Service / 阿里云迁移评估）、依赖分析（应用间调用、端口、存储、定时任务依赖）、容量规划（按峰值评估规格与弹性）
- Rehost 实操：阿里云用"服务器迁移中心/迁云工具"（镜像导入）、AWS 用 Application Migration Service（Agent 持续复制，切换时秒级 cutover）；数据库用 DTS 全量+增量
- 停机窗口控制：先迁移非核心系统跑通流程，再逐个核心系统"演练迁移 + 灰度切换"，核心库用增量同步把停机压到分钟级
- 迁后优化节奏：先"搬上去"再"优化"（半年内逐步做 Replatform：RDS、对象存储、弹性伸缩、FinOps）
- 指出坑：老系统 CPU 架构不兼容（x86 vs ARM 迁移成本）、老 OS 版本不再受云厂商支持、批处理依赖本地盘、硬编码 IP/配置文件

**减分项：**
- 一上来就"重构为微服务"，忽略风险与窗口
- 不评估直接搬，搬到一半发现依赖冲突
- 只谈工具不谈停机窗口与回退方案
- 忽略 OS/架构兼容性、硬编码配置这些迁移前排查项
- 迁完就撒手，不做性能与成本验证

**解答：**

一年窗口 + 最小停机，"先搬后优化"是唯一现实路径。迁移策略四选一：Rehost（换台"云里的机器"，最省事）、Replatform（顺手换托管服务）、Refactor（重构，最贵最险）、Retire（顺手关掉没人用的）。一年内主策略是 Rehost + Replatform 混合，Refactor 只留给真正需要弹性/伸缩的核心模块，其余一律不碰。执行分三步：第一步评估——用迁移评估工具扫描 500 台机器的规格、应用栈、依赖关系（哪些应用互调、依赖哪台机器、批处理依赖哪些本地盘和共享目录），输出"依赖地图"，同时盘点"僵尸系统"（半年没人用的直接 Retire 还能省配额）；第二步分批迁移——按依赖顺序：先迁无依赖的边缘系统（报表、管理后台）跑通工具链与流程，再迁有依赖的核心链路，数据库用 DTS 全量+增量同步，应用用迁云工具（阿里云服务器迁移中心/AWS Application Migration Service）做持续复制，切换当天"停写→追平增量→切 DNS/连接串"，停机窗口可以从天级压到分钟级；第三步迁后验证与优化——每个系统迁完都要跑性能对比（P99 延迟、错误率）和回退预案（保留旧环境 1 个月），稳定后半年内逐步做 Replatform：自建 MySQL 换 RDS、文件换对象存储、批处理换定时任务平台，成本与稳定性继续改善。常见坑要提前排：老应用是 32 位或特殊 CPU 架构（新机型不一定支持）、老 OS（CentOS 6 之类）云厂商已不提供基础镜像（要自备镜像）、应用硬编码 IP 和绝对路径（迁移前扫配置）、批处理强依赖"本地凌晨 2 点执行"（换环境后时区与调度要重配）。最后，迁移计划里必须有"回退"而不是只写"切换"——每次切换都预演一次回退，这是大促系统迁移的标准纪律。

**延伸考点：** 迁云工具（Agent 持续复制）与"打包镜像导入"两种 Rehost 方式的停机窗口差异？核心数据库迁移时，如何保证切换瞬间的数据一致性校验？

### Q16. 秒杀消息丢了几千条，托管 MQ 怎么保障消息不丢不重？

**问题：** 你们用自建 Kafka 做订单异步处理，某次大促后发现消费端少处理了几千条订单，排查发现是磁盘打满导致 broker 崩溃、又恰好没有合理配置副本。老板要求"换云上托管 MQ 并保证不丢消息"。请给出方案与消息可靠性设计。

**期望加分项：**
- 说清托管 MQ 的价值：阿里云 RocketMQ/RabbitMQ（云上托管 Kafka 也可）、AWS SQS/SNS 对比自建——免运维（broker 管理、磁盘、分区扩容）、自带高可用与副本策略、弹性
- 消息可靠性的三段论：生产端（发送确认/同步发送、失败重试）、Broker 端（持久化落盘、副本同步 ISR、刷盘策略）、消费端（消费确认 ack、失败重投、幂等消费）
- 消费幂等是核心：at-least-once 语义下"重投"必然发生（网络超时、消费端处理后 ack 丢失），业务侧必须幂等（订单号唯一约束/去重表）
- 选型对比：SQS 适合简单任务队列（最多保留 14 天、可见性超时），RocketMQ/Kafka 适合高吞吐与有序场景；讲"顺序消息"的实现（分区键保证同 key 有序）
- 给排查方法：消息轨迹（trace）、积压指标（消费 lag）监控告警、死信队列（DLQ）捕获处理失败的消息
- 指出坑：消费端批量拉取不 ack 导致重复、生产端不设置发送超时静默失败、broker 磁盘满（托管后仍有配额上限）

**减分项：**
- 只说"用云上 MQ 就不丢了"，说不清三段式可靠性
- 没有幂等设计，认为 at-least-once 可以靠"云平台保证不重"
- 分不清顺序消息与普通消息的实现差异
- 不做消费积压监控，故障靠用户投诉发现
- 不知道死信队列的作用与配置

**解答：**

先明确一个前提：消息不丢是"生产端 + Broker + 消费端"三段共同保证的，托管 MQ 只解决了中间段，两端靠业务代码。生产端：发送要开"发送确认"（同步发送或 async 回调确认），失败按指数退避重试，重试仍失败要落本地或发告警，绝对不能"发出去不管"。Broker 端：托管 RocketMQ/Kafka 自带头节点副本（ISR 同步复制）与持久化，我们只要确认选型时打开同步刷盘（性能换可靠）并设置合理的副本数（≥2），就规避了自建 Kafka"磁盘满、副本为 0 数据全丢"的事故。消费端：消费后必须显式 ack，未 ack 的消息会超时重投（at-least-once），所以重投是必然事件——消费端必须幂等：用订单号/业务唯一键做去重（数据库唯一约束、Redis setnx、去重表），"处理前先查重、处理后记状态"，这是整个链路里最关键的一环。选型上：如果只要"削峰填谷 + 解耦"（订单异步、通知、日志），SQS/云上简单队列就够（可见性超时保证处理中消息不被其他消费者拿到，最长保留 14 天）；如果要顺序消费（支付流水、库存扣减）用分区有序的 RocketMQ/Kafka——同一个 key（如订单号）保证进同一分区、按序消费，但注意"全局有序 = 单分区 = 性能受限"这个权衡。运维层面三件事：①消费积压监控——lag 是核心指标，告警阈值按业务容忍度设（比如滞后 1 万条或 5 分钟）；②死信队列——消费失败 N 次（如 16 次）后进 DLQ，人工/系统补偿处理，防止坏消息阻塞主链路；③消息轨迹/消息查询——出问题能查"这条消息什么时候投递、谁消费的、消费结果"，这是托管 MQ 对比自建的最大优势。大促前还要压测生产→消费全链路吞吐，确认不会在生产端就堆死。

**延伸考点：** 顺序消息 + 消费失败重投，顺序会乱吗？如何保证同一分区内失败重投不阻塞后续消息？事件驱动架构里"消息幂等"与"业务幂等"的边界在哪？

### Q17. 半夜告警刷屏、指标对不上，云监控与自建监控怎么协同？

**问题：** 你们现在 Prometheus + Grafana 自建监控覆盖应用层，但云资源的 CPU/磁盘、负载均衡、RDS 的指标看不到，运维还被"半夜无用告警"折磨。请设计云监控与自建 Prometheus 的分工与集成方案，并给出告警治理方法。

**期望加分项：**
- 分工原则：云监控管"云资源层"（ECS CPU/磁盘/网络、RDS 指标、LB 指标、配额、账单）与云事件（故障通知、实例重启），Prometheus 管"应用层"（QPS、延迟、错误率、队列积压、业务指标），两层用告警组/合成监控打通
- 集成方式：云监控指标通过 API 拉取或云厂商的 Prometheus 兼容端点（阿里云可观测监控 Prometheus 版、AWS CloudWatch 导出器 cloudwatch-exporter），把云指标统一进 Grafana 大盘
- 告警治理方法论：告警要"可执行"——每条告警有 owner、有处置 SOP；去重与抑制（同一实例多个指标异常只发一条）；分级（P0 立即打电话、P3 邮件）；收敛（抖动抑制、静默窗口、依赖关系抑制——上游挂了不重复告警下游）
- 成本与数据保留：云监控指标默认保留周期有限（CloudWatch 详细监控 15 个月按档位收费），长时间序列与自定义业务指标放 Prometheus（本地保留 + 对象存储归档）
- 排障联动：异常事件（如 RDS 主备切换、实例自动重启）用云事件订阅推送到告警平台，与应用告警关联定位因果
- 指出坑：云监控与自建各看各的导致"指标对不上"（采集周期、聚合口径差异）

**减分项：**
- 云上资源指标和应用指标割裂成两套监控，出故障时两头查
- 告警只堆阈值，不设 owner、不收敛、不抑制，刷屏后大家麻木
- 不知道云监控的指标保留期与费用，把长周期指标全塞云监控
- 不订阅云事件（重启、切换、健康检查失败）
- 没有"告警必须可执行"的治理意识

**解答：**

两套监控不是二选一而是分工：云监控（阿里云云监控/AWS CloudWatch）是"资源视角"，覆盖 ECS 的 CPU/磁盘/网络、RDS 的 QPS/连接数/主备状态、负载均衡的后端健康、配额使用率，以及云事件（实例重启、RDS 切换、安全告警）——这些底层数据自建 Prometheus 拿不到或拿不全；Prometheus + Grafana 是"应用视角"，采集 QPS、P99 延迟、错误率、线程池、队列积压这些业务可观测指标。集成做法：用云厂商的 Prometheus 兼容能力（阿里云可观测监控 Prometheus 版可以直接拉云资源指标，AWS 用 cloudwatch-exporter 把 CloudWatch 指标暴露成 Prometheus 格式），或通过 OpenTelemetry/自定义 exporter 拉取 API，最终所有指标进同一个 Grafana——出故障时"资源指标 + 应用指标"在同一张大屏上看因果，这是协同的核心价值。告警治理要立规矩：①每条告警必须可执行——有 owner、有处置手册（SOP），收到告警的人知道"先查什么、怎么止血"；②去重与抑制——同一实例的 CPU/内存/磁盘同时超限只发一条合并告警，上游服务故障自动抑制下游依赖告警（比如依赖的 RDS 切换时，先不发应用的"数据库超时"告警，避免风暴）；③分级与通道——P0（不可用/数据丢失）电话+短信，P1 钉钉/IM 即时，P3 邮件日报，杜绝"全部电话轰炸"；④静默窗口与复盘——发布窗口内的告警自动静默，每周告警复盘把"无效告警"改阈值或删除。指标口径要对齐：云监控是分钟级聚合，Prometheus 是拉取即值，跨系统对比"CPU 平均值"天然有差异，约定统一查询窗口和聚合函数（都是 5 分钟 max 或 avg），避免两边对不上互相扯皮。最后把云事件接进来：RDS 主备切换、ECS 自动重启这类事件订阅推送到告警平台并关联时间线，很多"莫名其妙的服务变慢"其实是底层发生了切换。

**延伸考点：** 多账号/多地域的云监控数据如何统一汇聚（账号聚合、跨地域视图）？告警风暴（Alert Fatigue）在容器弹性伸缩频繁伸缩时如何通过抑制与维护窗口治理？

### Q18. 全站宕机 3 小时才恢复，RPO/RTO 目标怎么定、容灾方案怎么选？

**问题：** 你们上一季度发生一次机房级故障，业务中断 3 小时、恢复后还丢了 20 分钟数据。管理层要求制定容灾目标与方案。请定义 RPO/RTO，设计备份与容灾方案（主备/双活/两地三中心），并给出恢复演练计划。

**期望加分项：**
- 定义清晰：RPO=最多能丢多少数据（时间粒度），RTO=多久恢复业务；给出分级目标示例（核心交易 RPO≤5min/RTO≤30min，非核心 RPO≤24h/RTO≤4h）
- 方案阶梯与成本：备份恢复（RPO=上次备份点，RTO=小时级，最便宜）→ 同城多 AZ 主备（RPO 秒级/RTO 分钟级）→ 异地异步复制（RPO 分钟级/RTO 小时级）→ 双活/两地三中心（RPO≈0/RTO 秒级，最贵）
- 给出选型依据：按业务分级配置而不是"全部双活"；核心库做同城主备+异地备份，核心应用多 AZ，大数据/离线可容忍小时级
- 备份体系：数据库自动备份 + binlog（PITR）、对象存储版本控制与跨地域复制、快照策略；"备份必须可恢复"——定期做恢复演练
- 恢复演练：每季度一次全链路演练（模拟机房故障，计时测 RTO），故障注入工具（混沌工程/容灾演练），演练要含"切换后回切"
- 指出坑：只演练备份没演练切换、回切（failback）比切换更危险、双活的脑裂与冲突解决、演练环境与生产环境差异

**减分项：**
- RPO/RTO 定义说不清或与实际方案对不上
- 一刀切"上两地三中心"，不看成本与业务分级
- 只说"做了备份"，没验证过恢复（RPO 达标 ≠ 能恢复）
- 没有演练节奏与回切设计
- 容灾方案没有和监控、告警、值班打通（故障发生时没人按预案走）

**解答：**

先定义目标再选方案。RPO（Recovery Point Objective）衡量"最多丢多少数据"：上次事件丢 20 分钟数据，说明当时的备份/复制体系 RPO 是 20 分钟+；RTO（Recovery Time Objective）衡量"多久恢复业务"：3 小时就是当时的 RTO。正确做法是按业务分级设目标：核心交易链路 RPO≤5 分钟、RTO≤30 分钟；一般业务 RPO≤1 小时、RTO≤4 小时；离线分析 RPO 24 小时、RTO 一个工作日——分级的目的是让每一分容灾预算花在刀刃上。方案阶梯对应成本：最便宜的是"备份 + 恢复"（RPO=上次备份时刻，RTO 小时级，适合可容忍丢失的数据）；上一层是同城多 AZ 主备（数据库主备同步、应用跨 AZ，RPO 秒级、RTO 分钟级，成本约 +100%）；再上一层是异地复制（跨地域异步复制 + 应用镜像就绪，防地域级灾难，RPO 分钟级、RTO 小时级）；最贵的是双活/两地三中心（RPO≈0、RTO 秒级，但一致性、脑裂与运维复杂度指数级上升）。绝大多数公司"同城多 AZ 主备 + 异地备份 + 每季度演练"就是性价比最优解。落地体系：数据库开自动备份 + binlog（支持 PITR 到任意秒）+ 异地备份；对象存储开版本控制与跨地域复制；ECS 做快照策略（日增量、周全量、保留 N 份）。最关键的一条纪律：备份必须"恢复过才算数"——RPO 达标只是"有数据"，恢复演练验证的是"能起来"。演练设计：每季度一次全链路容灾演练（挑非高峰时段，模拟机房故障，用故障注入/演练开关真实切换流量，计时测 RTO，验证数据完整性，跑一遍业务冒烟，最后回切 failback），重点教训是：回切往往比切换更危险（数据双向同步、会话收敛、DNS 缓存），演练一定要含"切换→运行→回切"闭环，否则真出事时"切过去回不来"。最后把容灾与日常打通：预案不是文档是剧本——值班表、切换 checklist、决策人、演练记录缺一不可，很多公司"预案在"但"没人会按它执行"。

**延伸考点：** 两地三中心的"双活"如何解决数据库写冲突与脑裂？容灾演练中如何安全地"模拟机房故障"而不影响真实流量？

### Q19. 大促流量 10 倍增长，弹性伸缩怎么做到"快、稳、不超支"？

**问题：** 你们准备迎接 10 倍流量的大促，目前应用部署在固定数量的 ECS 上，数据库连接数和磁盘 IO 已经吃紧。请设计一套弹性伸缩（AS）方案，覆盖指标伸缩、定时伸缩、预测伸缩，并说明伸缩后连带瓶颈怎么处理。

**期望加分项：**
- 方案框架：三层伸缩——应用层（ECS/容器 HPA 按 CPU/请求数/QPS 指标伸缩）、存储层（RDS 只读副本、Redis 集群扩容）、资源层（K8s 节点池/ASG 按需扩节点）
- 伸缩策略选型：基于指标（CPU>70% 持续 5 分钟扩容）适合常规波动；定时伸缩（大促前 2 小时预置）应对可预期峰值；预测伸缩（AWS Predictive Scaling/阿里云预测）基于历史曲线自动提前扩
- 讲"提前性"：扩容要抢在流量前面——冷启动时间（镜像拉取+启动 1-3 分钟）决定了"看指标再扩"会慢半拍，所以大促用定时 + 指标双保险
- 缩容要谨慎：指标下降后要有冷却期（cooldown）防抖动，用 P99 延迟而非平均值判断
- 连带瓶颈：扩容前先确认配额（ECS 配额、SLB 连接数、RDS 连接数上限、Redis 连接数）、数据库用连接池代理/只读副本扩容、发布镜像预热
- 无状态化是前提：伸缩的机器必须无状态（session 外置、日志外置），否则"扩出来的机器带不了流量"
- 成本控制：缩容策略与 Spot/竞价实例混部（On-Demand 保底 + Spot 弹性）

**减分项：**
- 只说"配个 CPU 伸缩策略"，不懂冷启动与提前量
- 伸缩只扩应用层，数据库/缓存瓶颈完全不提
- 缩容阈值与扩容混用，冷却期没设计导致抖动
- 实例有状态（session 在本地），扩出来也接不住流量
- 不检查配额与上限，扩容到一半触发配额限制

**解答：**

弹性伸缩的前提是无状态：session 外置 Redis、日志外置、本地无关键数据，否则"扩出来的机器接不住流量、缩掉的机器丢状态"。设计上分三层：应用层按指标伸缩（CPU 利用率、请求数、QPS 结合 P99 延迟，比如"CPU>70% 持续 5 分钟 +3 台，最多 N 台"）；资源层按节点池伸缩（容器场景节点数随 Pod 数扩，K8s cluster-autoscaler/阿里云节点池）；数据层单独处理（数据库不随应用盲目扩容——连接数上限是硬约束，应用扩容前先确认 RDS 连接池够不够，不够就加只读副本或用连接代理 RDS Proxy）。伸缩策略要"抢时间"：新实例冷启动要 1-3 分钟（镜像拉取、JVM 启动、健康检查通过），"看指标再扩"天然慢半拍——大促这种可预期峰值用"定时伸缩"提前 1-2 小时预置容量，指标伸缩做兜底，预测伸缩（基于历史流量曲线预测下一时段需求）做自动化补充；大促前把所有镜像预热到节点池。缩容比扩容更需要设计：冷却期（缩容后 5-10 分钟内不再触发）防抖动，判断用 P99 延迟而非平均值（平均值被少数慢请求掩盖），逐台缩、保留最低保底数。连带瓶颈清单要主动讲：ECS 配额与资源库存（大促前申请提额）、负载均衡的连接数与并发上限、RDS 连接数（max_connections 默认几十到几百，应用扩到 100 台每台 20 连接直接打爆——这是最典型的扩容事故）、Redis/缓存连接数与内存、消息队列积压能力。成本控制：弹性伸缩不要全 On-Demand——On-Demand 保底容量 + Spot/竞价实例承接弹性部分（Spot 便宜 50%-90%，被回收时有优雅退出机制：收到回收通知先摘除流量再停机），大促峰值算"峰值时长 × 价格"对比"包月固定容量"能省 30%-50%。最后是验证：大促前做全链路压测，验证"扩容速度跟不跟得上流量增长、数据库能不能扛住"——伸缩策略的成败不是配置了，而是"峰值真的来临时顶住了"。

**延伸考点：** K8s 的 HPA 与云 ASG 双层伸缩如何配合（Pod 扩了节点不够怎么办）？Spot 实例回收通知（2 分钟告警）下应用如何优雅缩容？

### Q20. 从零设计一个电商系统的云上高可用架构，怎么权衡？

**问题：** 你要从零为一家电商公司设计云上架构：日 UV 100 万、秒杀大促 10 倍流量、订单数据千万级、要求 99.99% 可用、预算有限。请给出完整的架构设计（计算/存储/网络/缓存/队列/容灾/成本），并说明每一处权衡的依据。

**期望加分项：**
- 架构分层完整：CDN（静态资源+图片）→ WAF → 负载均衡（跨 AZ）→ API 网关（限流/鉴权）→ 应用层（容器多 AZ 弹性伸缩、无状态）→ 缓存（Redis 集群）→ 消息队列（削峰）→ 数据库（RDS 主备+只读副本/分库分表）→ 对象存储（图片/日志）+ 大数据链路
- 每层给出取舍依据：为什么静态走 CDN（省源站带宽与延迟）、为什么秒杀用 MQ 削峰（订单落库是瓶颈）、为什么订单库要分库分表（单库千万级后写入与查询都受限）、为什么缓存只缓存热点（全量入缓存成本高且一致性问题多）
- 高可用与容灾：多 AZ + 跨地域备份、无状态化、故障演练、RPO/RTO 分级
- 安全与合规：IAM 最小权限、KMS 加密、日志审计、WAF 防护
- 成本预算：预留实例保底 + Spot 弹性、存储生命周期、缓存命中率优化、按需扩容的 FinOps 控制
- 会讲"为什么不是某方案"：为什么不用双活（成本与复杂度）、为什么不用自建（人力）、为什么不全 Serverless（订单场景的强一致与长事务）
- 量化：100 万日 UV 对应的峰值 QPS 估算（如峰值 5000 QPS）、扩容目标、缓存容量估算

**减分项：**
- 画完架构图讲不出任何一处"为什么"，不会权衡
- 秒杀场景没有削峰设计，直接打数据库
- 单库单表硬扛，没有分库分表/读写分离的演进思路
- 忽略安全（明文传输、无 IAM、无审计）与成本（全预留/全按量）
- 架构没有"演进"概念，一次设计到顶（一开始就两地三中心/微服务拆分）

**解答：**

架构设计先定目标与约束：100 万日 UV、峰值 QPS 约 3000-5000（按"日 UV × 平均访问 10 次 / 峰值时段占比"估算）、订单千万级、99.99% 可用、预算有限。分层设计如下：入口 CDN 承接静态资源与图片（命中率 90%+，源站压力骤降）；WAF 挡 Web 攻击；ALB/SLB 跨 AZ 接入；API 网关做统一限流鉴权（秒杀时先拦在网关，避免打到后端）；应用层容器多 AZ 部署 + 弹性伸缩（平时 20 副本、大促提前定时扩到 100，配指标伸缩兜底），实例严格无状态（session 外置）；缓存用 Redis 集群只缓存热点数据（商品详情、库存读、用户会话），按"缓存命中率 >95%"和一致性（写后失效/延迟双删）设计，而不是全量入缓存；秒杀链路必须削峰——下单请求先进消息队列（RocketMQ/Kafka），订单落库由消费端异步处理，"前端看到已入队"缓解体验，数据库峰值从"万级并发写"降到"队列消费速率"；数据库用 RDS 主备（多 AZ，RPO 秒级）+ 只读副本扛读流量，订单表按用户 ID 或订单 ID 分库分表（预估单表千万行后写入与查询都会退化，提前按 2 年数据量设计分片数），大促前做主备切换与只读副本扩容演练；图片与日志进对象存储，配生命周期（30 天转低频、90 天转归档）。每一处都要给"为什么"：为什么不用双活——成本翻倍 + 写冲突复杂度，99.99% 用多 AZ 自动切换就能达到；为什么不全 Serverless——订单的强一致事务与长链路不适合函数模型，Serverless 只用在图片处理、通知这类边缘功能；为什么不自建中间件——没有专职团队，托管 MQ/RDS 的免运维收益远超差价。安全与成本兜底：IAM 最小权限 + 角色代替密钥、KMS 加密存储与传输、操作审计；成本上"包年预留保底 + Spot 弹性 + 生命周期存储"组合，预估比全按量省 40%+。最后强调演进：先"单库 + 多 AZ + MQ 削峰"跑起来，监控驱动在流量和复杂度真正到来时再分库分表、加只读副本、上异地容灾——架构是"跟随业务复杂度演进"的过程，不是一步到位的艺术品。

**延伸考点：** 秒杀"库存扣减"如何用 Redis + 消息队列做到不超卖且最终一致？订单表到千万级后，分库分表的键（sharding key）选错会导致什么灾难？

### Q21. 云上账单一个月翻倍，成本归因分析与优化落地（标签、利用率、预留实例、存储降级）

**问题：** 你们云上账单这个月比上个月翻了一倍，财务找上门。你作为负责人，如何系统性做成本归因分析并落地优化？请给出从"数据拆解"到"机制防回弹"的完整方法。

**期望加分项：**
- 先拆账单：按服务/账号/地域/标签/计费项（计算、存储、流量、数据库）多维拆分，用成本分析工具（AWS Cost Explorer/阿里云成本管家）定位增量最大的 TOP 项
- 对比环比：本月 vs 上月的分项差异，聚焦"多出来的钱花在哪"（新增资源？规格变更？流量暴涨？），而不是凭感觉猜
- 常见翻倍元凶：公网出方向流量、新资源没打标签且规格越开越大、测试环境忘关、存储与快照只增不减、按量付费当默认
- 落地优化分优先级：预留实例/节省计划覆盖稳定负载 → 打闲置（7 天 CPU<5% 停机/降配）→ 存储生命周期（标准→低频→归档）→ 清理冗余快照与弹性 IP
- 机制防回弹：强制标签（未打标签资源自动回收/告警）、预算告警（80% 提醒/100% 告警）、月度成本复盘、新建资源纳入成本审批
- 有量化与取舍：先动"收益大风险低"的项，降配/关停必须用监控数据支撑并留弹性兜底

**减分项：**
- 只"关几台机器"或凭感觉猜原因，不做数据拆解
- 不对比环比，说不清翻倍的钱具体花在哪
- 忽略出口流量费、快照冗余这类隐形账单项
- 优化完没有防回弹机制，下个月又涨回去
- 不看实际利用率就降配/关停，引发线上故障

**解答：**

归因要"先算账再动手"。第一步数据拆解：用成本分析工具把本月账单按"服务 + 标签 + 地域 + 计费项"多维拆开，与上月做环比，直接锁定增量最大的 TOP 项——账单翻倍通常不是每一项都涨，而是某一个或两个大项失控。第二步针对 TOP 项归因：结合账单明细与资源清单回答"钱花在哪"，常见元凶按概率排序：①公网出方向流量——新上线的日志上报、CDN 回源配置错误、爬虫抓取都可能导致出口带宽暴涨几十倍，这是最容易翻倍的隐形项；②新项目/测试环境资源没打标签且游离在治理之外，规格越开越大；③存储与备份——数据只增不减、快照每天全量、日志无保留策略；④新增实例默认按量付费，一个月就是包年的 1.5 倍。第三步按"收益大 + 风险低"排序落地：最稳的是结构性优惠——把 7×24 稳定负载买成预留实例/节省计划（省 40%-60%）；然后是打闲置——用监控拉出连续 7 天 CPU<5% 的实例清单确认后停机/降配，测试环境晚上定时关机（节省停机模式，按磁盘收费几乎不花钱）；存储走生命周期（30 天转低频、90 天转归档，日志设保留 30 天），快照改"日增量 + 周全量 + 保留 30 天"；最后处理流量类问题（上 CDN、优化回源、限流防爬）。第四步防回弹：成本标签强制覆盖（未打标签的资源不允许创建或自动回收）、预算告警（消耗达预算 80% 通知、100% 告警）、月度成本复盘把"单位成本/请求"作为效率指标、新建资源走成本审批。实践中的坑：降配前必须用监控曲线佐证，"拍脑袋降配"引发线上故障是成本优化最常见的翻车；出口流量要看方向（回源流量可走内网/CDN 免收公网费）；标签治理要"从今往后强制"而非"回头补打"，否则防回弹就是空话。结论一句话：成本翻倍 90% 是"治理缺位"而非"业务增长"，先定位再优化，用机制锁死回弹。

**延伸考点：** 容器化之后"实例规格"消失，如何继续用标签与命名空间做成本分账？预留实例买多了（规格不匹配）如何调整或退款？

- 数据库只做"导出导入"，不知道增量同步与一致性校验，停机窗口按天算
- 没有演练与回退方案，切换当天只能"赌一把"
- 忽略硬编码 IP、批处理、下游白名单这些"迁移后必炸"的细节
- 迁完不验证，业务跑了几天才发现数据不对

**解答：**

迁移的核心矛盾是"数据不丢"与"窗口最短"，破解钥匙是"增量同步"而非"停服导数据"。方案分四阶段。第一阶段评估（迁移前 2-4 周）：用迁移评估工具或人工盘点 50 台机器的规格、OS、应用依赖关系（谁调谁、依赖哪些端口与共享目录）、数据量（MySQL 总量与增长速率）、定时任务清单（凌晨批处理要与切换窗口错开），输出"依赖地图"与停机窗口测算；同时排查迁移后必炸的细节：硬编码的 IP/内网域名、配置文件里的绝对路径、批处理依赖的本地磁盘、下游对接方的 IP 白名单（机房出口 IP 与云上出口 IP 不同，要提前通知对方加白）。第二阶段环境与网络：云上建 VPC/子网/安全组，专线或 VPN 打通机房与云上（迁移期间是数据同步通道，之后可作混合云兜底），按评估结果创建同规格 ECS 并固化基线镜像。第三阶段数据迁移：MySQL 用 DTS/数据传输服务做"全量迁移 + 增量同步"——不停服先全量迁过去，再持续追增量；应用用迁云工具（镜像导入或 Agent 持续复制）整体搬迁。第四阶段切换（核心窗口）：按 checklist 执行——停写（应用只读或维护页）→ 等增量追平（延迟为 0）→ 一致性校验（行数 + checksum 抽样）→ 切 DNS/改连接串 → 业务冒烟验证（登录、下单、对账）→ 开放流量；关键纪律是"切换前完整演练过一遍"：提前一周演练把切换从"预计 2 小时"压到"实际 30 分钟"，演练同时验证回退（切回机房旧库）可行。迁后验证与兜底：功能验证 + 性能对比（P99 延迟、错误率）+ 连续 7 天数据对账，旧环境保留 1 个月后再释放。实践中的坑：时区与 cron 调度差异（机房 UTC 云上 CST 差 8 小时）、证书与域名备案、只迁了应用没迁监控与备份体系（云上要重新配齐）。结论：评估越细、演练越多，正式切换就越"无聊"——无聊才是好事。

**延伸考点：** DTS 增量同步在"单向追平"与"双向同步"两种模式下的冲突处理差异？迁移切换后如何快速发现"数据不一致"（对账的抽样策略与口径）？

### Q23. 从零设计一个云上高可用微服务架构（接入层/应用/数据/容灾/成本），并说明取舍

**问题：** 你要为一个新业务（日请求量千万级、7×24 在线、允许秒级抖动但不允许长时间不可用）从零设计云上微服务架构。请给出接入层、应用层、数据层、容灾与成本五部分的完整设计，并说明每一处的取舍依据。

**期望加分项：**
- 接入层：CDN（静态）+ WAF + 负载均衡跨 AZ + API 网关（限流/鉴权/路由），说明为什么网关放这一层
- 应用层：托管容器（K8s）+ 多 AZ 多副本 + HPA 弹性伸缩 + 严格无状态（session 外置 Redis）；微服务按业务域拆 10-15 个，讲清"太碎"的代价
- 数据层：托管 RDS 多 AZ 主备 + 只读副本读写分离 + Redis 缓存集群（只缓存热点）+ 对象存储 + 消息队列削峰解耦，缓存一致性用"写后失效"
- 容灾：同城多 AZ 为基线（RPO 秒级/RTO 分钟级）+ 异地备份兜底，RPO/RTO 分级定义，季度故障演练常态化
- 成本：预留实例保底 + Spot 弹性、存储生命周期、标签分账 + 预算告警；按"峰值 QPS × 单实例能力 ÷ 冗余系数"估算容量
- 取舍要讲"为什么不是"：为什么托管而非自建、多 AZ 而非双活、不全 Serverless、服务粒度不能太碎

**减分项：**
- 只画架构图不讲任何一处取舍，或全用"最优解"堆砌
- 应用层有状态（session 本地）、数据库单点，谈不上高可用
- 不考虑容灾演练与 RPO/RTO 定义
- 服务拆得过碎（链路长、排障难、成本高）
- 完全忽略成本，或成本方案脱离业务形态

**解答：**

设计的出发点是两个约束：千万级日请求 + 可用性优先，所有取舍都围绕这两点。接入层：CDN 扛静态与图片（省源站带宽与延迟），WAF 挡攻击，负载均衡跨 AZ 接入，API 网关做统一限流/鉴权/灰度——网关的取舍在于"多团队、需要统一入口治理才值得"，本项目有鉴权与限流刚需所以放这层。应用层：托管容器（EKS/ACK）部署，多 AZ 各副本 + HPA 弹性伸缩，实例严格无状态（session 外置 Redis、文件进对象存储）；微服务按业务域控制在 10-15 个（订单、用户、支付、库存、商品、通知…），取舍是：太粗退化成单体，太碎则链路延迟、排障与运维成本爆炸——千万级请求对单服务约 3000 QPS 的规模，15 个服务完全够。数据层是可用性的重心：订单/交易类用托管 RDS 多 AZ 主备（自动切换 RTO 秒级），读多场景加只读副本做读写分离；Redis 集群只缓存热点（命中率 >95%），一致性用"写后失效"；异步链路（通知、对账、积分）走消息队列削峰解耦；文件与日志进对象存储配生命周期。取舍要点：数据库用托管而非自建——没有专职 DBA 的团队自建主从+切换是事故源；缓存不全量入——成本与一致性双失控。容灾：基线是同城多 AZ（RPO 秒级/RTO 分钟级），加异地备份（对象存储跨地域复制 + RDS 异地备份）兜底地域级灾难；分级定义目标（交易 RPO≤5min/RTO≤30min、非核心 RTO≤4h）；季度做一次故障演练，模拟 AZ 故障验证切换真实发生。成本：稳定负载用预留实例/节省计划（省 40%+），弹性部分用 Spot 混部（被回收有优雅退出机制），存储走生命周期，全量打标签 + 预算告警做分账；容量按"峰值 QPS × 单实例能力 ÷ 冗余系数"估算并对比包月与按量差异。最后讲清"为什么不是"：不上双活（写冲突与成本翻倍，99.99% 用多 AZ 自动切换足够）、不全 Serverless（交易强一致与长事务不适合函数模型）、不一开始拆 50 个服务（业务规模没到，运维成本先炸）——架构是"跟随业务复杂度演进"的过程，第一步先把"多 AZ + 无状态 + 托管数据层"这高可用三件套做扎实。

**延伸考点：** 微服务拆分粒度如何用"团队规模 × 变更频率 × 数据边界"三个维度量化判断？多 AZ 主备与同城双活在成本、RTO、数据一致性上的具体差距是多少？
