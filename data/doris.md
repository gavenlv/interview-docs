# 数据 · Doris（面试题库）

本文件聚焦 Apache Doris 在数据工程中的真实实践能力，覆盖三类表模型（Duplicate/Unique/Aggregate）选型与排序键设计、分区与分桶策略、Rollup/物化视图与查询加速、bitmap/HLL 去重、五种导入方式实战与错误处理、查询 Profile 与执行计划调优、compaction 与内存治理、FE/BE 集群运维与副本一致性、实时数仓分层落位、跨集群复制与 MySQL 协议兼容，以及与 ClickHouse/StarRocks 的选型对比。题目全部以可复现的线上场景切入，重点考察排查链路、量化依据与取舍判断，不考概念背诵。难度自 Q1 至 Q20 循序渐进，从建表与导入等实践基础，过渡到查询调优与内存治理等中阶议题，最后落到架构设计与开放性选型思考。

### Q1. 每天 5 亿行的事实明细表，表模型和分桶怎么设计？

**问题：** 要建一张用户行为明细表：每天新增约 5 亿行、保留 30 天，既要支持按天/小时做维度聚合，又要能按用户 ID 或订单号精确查明细。表模型、分区、分桶分别怎么选？为什么？

**期望加分项：**
- 选 Duplicate 模型保留全部明细，并能一句话说清三种模型的取舍——要明细选 Duplicate、要覆盖更新选 Unique、要预聚合选 Aggregate
- 分区按天，和 30 天保留周期对齐（配合动态分区/过期清理），查询走分区裁剪
- 分桶列选区分度高且常作为过滤条件的列（user_id/order_id），并给出桶数估算依据（单 tablet 数据量 1~10GB、桶数取 2 的幂）
- 知道排序键即 key 列，列顺序影响前缀索引命中，把高频「等值+范围」查询列放前面
- 主动说明聚合需求用物化视图/Rollup 承接，而不是为了聚合改用 Aggregate 模型丢明细

**减分项：**
- 为了「聚合快」直接上 Aggregate 模型，明细全丢，这是最常见的翻车点
- 分桶列选性别、is_new_user 这类低基数列，或干脆不分桶
- 桶数拍脑袋，说不出 tablet 量与数据量的关系
- 忽略查询模式来排 key 列顺序

**解答：**
先定模型再定分桶。表模型选 Duplicate：行为明细是 append-only 数据，需要 100% 保留且要按任意字段回溯，Aggregate 模型会在导入时按 key 合并、Unique 模型会按 key 覆盖，都会丢明细。分区按天建 Range 分区，天然对齐 30 天保留周期，配合动态分区自动建未来分区、TTL 自动删过期分区，查询按天裁剪后扫描量从 150 亿行降到 5 亿行以内。分桶用 Hash 分桶，列选 user_id——它区分度高、且「按用户点查」是最常见的查询模式，等值条件能直接命中分桶裁剪；分桶数按「单 tablet 1~10GB」估算：一天 5 亿行假设 200GB，桶数取 64（2 的幂，利于数据均衡与调度），每桶约 3GB，全表 tablet 总数控制在合理范围，避免小 tablet 过多拖垮元数据与 compaction。key 列顺序把 user_id 放最前：前缀索引按排序列顺序命中，等值 user_id + 时间范围过滤能走最短路径。实践坑：不要把排序键设计成和分区完全一样（如把日期放第一列），会导致分桶列无法参与前缀过滤；也不要贪多排序键，字节数超 36 的前缀索引会自动截断。聚合需求交给物化视图，与明细共存。

**延伸考点：** 同样的表如果高峰时某几个热点用户占一半查询，分桶/缓存层面你会怎么处理？如果业务方要求「按任意维度组合即席聚合」，物化视图建多少合适、建多了有什么代价？

### Q2. Aggregate 模型的 pre-aggregation 有什么限制？什么时候该放弃它？

**问题：** 用 Aggregate 模型建了订单汇总表，导入后查询发现某些维度组合的 SUM 结果不对，换个维度 group by 又慢得离谱。Aggregate 模型的预聚合到底在什么条件下才生效？哪些场景应该直接放弃它？

**期望加分项：**
- 说清预聚合触发条件：只有「同 key 的数据在导入时一起到达/落盘」才会合并；不同批次里 key 相同才会叠加，同 key 拆分到多次导入最终仍会正确聚合
- 知道 key 即排序键，按 key 前缀 group by 才能吃到预聚合，换成非前缀维度就退化成「全表扫描 + 现场聚合」，数据量大时反而比 Duplicate 更慢
- 点出 REPLACE/SUM 混用与「同一 key 不同指标语义不同」的坑，以及高频更新场景下 Aggregate 模型不适用
- 给出补救路径：改 Duplicate 模型 + 物化视图做汇总，或拆「明细表 + 汇总表」两层
- 能举出线上「看着能用、实际翻车」的例子（如多列 group by 顺序不对导致聚合失效）

**减分项：**
- 以为 Aggregate 模型任何聚合查询都快，说不出「同 key」这个前提
- 说不清预聚合发生在导入时而非查询时
- 忽略 REPLACE 列在多批次导入下的覆盖语义

**解答：**
先纠正一个常见误解：Aggregate 模型的预聚合发生在「导入时按 key 合并」，不是查询时。它隐含两个前提：第一，必须存在可合并的 key 集合，所有非 key 列都必须是聚合类型（SUM/REPLACE/MAX/MIN/BITMAP_UNION 等），否则建表直接报错；第二，只有按 key 前缀做 group by 时，查询才能直接读取已经聚合好的数据，此时扫描行数等于 key 数而非原始行数。你问的「某些维度 SUM 不对」多半是 REPLACE 列被后导入的脏数据覆盖，或同一批数据 key 拆分导致部分行落到了别的分区（时间字段参与 key 且时区错乱）；「换个维度慢得离谱」则是典型的非前缀聚合——预聚合完全吃不上，等于现场扫全表再算，行数还是导入前的量级。实践上我的原则：维度可以预先穷举且更新低频的场景（日汇总、渠道汇总）才用 Aggregate；需要明细回溯、维度组合开放、或行级频繁更新的场景，用 Duplicate/Unique + 物化视图更稳。判断是否真的吃到预聚合，用 EXPLAIN 看执行计划是否出现聚合下推与扫描行数骤降，不要只看建表模型。

**延伸考点：** Aggregate 模型里同一张表出现「SUM 的金额」和「REPLACE 的订单状态」两种列，同 key 多批次导入时状态会被中间值覆盖，你怎么设计避免？bitmap 去重列在 Aggregate 模型里预聚合的写入函数是什么？

### Q3. Unique 模型做订单状态更新，merge-on-write 和乱序覆盖怎么处理？

**问题：** 订单表会随业务流转更新状态（下单→支付→退款），每天还有离线订正数据回刷。用 Unique 模型怎么设计？2.x 的 merge-on-write 和旧实现有什么本质区别？批量更新与删除有哪些坑？

**期望加分项：**
- 用唯一键做主键，更新靠「同 key 导入覆盖」；能说清 merge-on-write 在写入时就标记旧版本、点查无需读多个版本合并，旧实现（merge-on-read）点查要现场合并、越查越慢
- 提到 sequence column 解决乱序覆盖：离线回刷的批次乱序到达时，用版本号/时间戳列保证「新值覆盖旧值」
- 删除：能用 DELETE 语句/导入带删除标记（delete sign）实现，清楚删除也走版本机制、需要 compaction 真正回收
- 知道大批量更新会放大写与 compaction 压力，回刷选低峰期、分片提交
- 量化点查收益：merge-on-write 下主键点查通常毫秒级，旧模型会随版本数劣化

**减分项：**
- 不知道乱序覆盖问题，回刷旧数据把新数据盖掉
- 只会 truncate 不会按条件删除
- 分不清 merge-on-write 与 merge-on-read 的读写路径差异

**解答：**
订单场景选 Unique 模型，主键即 order_id，更新就是同 key 导入覆盖。先讲 2.x 的 merge-on-write（默认开启）：导入时同步完成 key 去重并标记旧版本不可见，查询只读有效版本，主键点查、聚合都稳定；而 merge-on-read 只在查询时合并多版本，订单被频繁更新后版本堆积，点查性能线性劣化——所以老集群升级后点查慢的根因常常在这里。乱序是回刷场景的头号坑：离线任务晚到、时间戳旧，会把当天已支付订单覆盖回待支付。解法是加一个 sequence 列（用业务更新时间或版本号），Doris 比较 sequence 列决定谁覆盖谁，导入时在列里带上即可。删除分两种：小批量的 `DELETE FROM`（走 delete predicate），大批量回刷删除用导入的 delete sign 标记（1 表示删除），两者都要依赖 compaction 才真正物理回收。实践坑：大批量更新不要一把梭——几亿行的全量覆盖会把 compaction 打爆，查询与导入互相抢 IO；回刷拆成小批次、错峰执行，配合 `SHOW TABLET` 观察版本堆积。还有一点：Unique 模型同样可以建物化视图做预聚合，别以为只有 Aggregate 才行。

**延伸考点：** 一张大表同时被「实时流更新」（高频小批）和「离线回刷」（低频大批）写入，你会怎么控制两者的节奏避免版本爆炸？sequence 列用系统时间和业务时间各有什么风险？

### Q4. 大表分区与分桶的数量、列选择、数据倾斜怎么定？

**问题：** 一张日增 3 亿行的日志表，数据按日期增长，但存在少数热点用户产生大量记录。分区、分桶怎么选列、数量怎么定？分桶数据倾斜和 tablet 数量过多分别会带来什么问题？

**期望加分项：**
- 分区按天（或按业务周期），与保留策略/动态分区绑定；分桶列选高基数、常用于过滤的列，避开低基数列
- 桶数给出量化思路：单 tablet 1~10GB、总 tablet 数可控，桶数取 2 的幂，并说明桶数变化需要重建表（分桶不可动态修改）
- 能说清倾斜的表现：某分桶数据量远超均值、对应 BE 查询热点、磁盘不均衡；能用 `SHOW PROC '/statistic'` 或 tablet 分布确认
- 知道 tablet 过多的代价：元数据膨胀、compaction/调度开销大、FE 压力上升
- 权衡并行度：桶太少查询并行度不够，桶太多调度成本高，按查询并行度与数据量折中

**减分项：**
- 分桶列选性别、is_new 等低基数列，导致分桶形同虚设
- 桶数毫无依据，要么一个桶打天下，要么几万个 tablet
- 只说「会倾斜」，说不出怎么观察和怎么缓解
- 不知道分桶是建表时定死的

**解答：**
分区解决「时间维度的裁剪与生命周期」，分桶解决「并行度与数据分布」，两者分开想。分区按天建 Range 分区，天然支持按日期裁剪和 TTL 清理；如果查询常按周/月聚合，可考虑按月分区，代价是单分区更大、裁剪粒度变粗，按需取舍。分桶列：选高基数且高频出现在等值条件里的列（user_id/device_id/订单号）；低基数列（状态、性别）做分桶会让几乎全表落进少数几个桶，倾斜和热点一起爆。数量：先估单日数据量，按「单 tablet 1~10GB」反推每分区桶数，桶数取 2 的幂；再乘分区数得到总 tablet 数，单集群控制在万级以内，避免 FE 元数据与 compaction 调度成为瓶颈。倾斜的缓解思路：如果热点是少数大 key，考虑按更细粒度切分（如 user_id 加盐后分桶）、或接受倾斜但在查询侧用 runtime filter/资源组限制影响；先量化——一个桶占全分区 30% 以上就要处理，别凭感觉。最关键的坑：分桶数建表后不能改，想调只能重建表或建新分区（动态分区的分桶继承建表设置），所以上线前宁可多算两遍。

**延伸考点：** 热点用户集中在个别桶导致那台 BE 的 CPU 和磁盘都打满，你怎么在不重建表的前提下缓解？自动分桶（2.0+）解决了什么问题、还有哪些不适用场景？

### Q5. 明细表聚合查询要扫 2 分钟，Rollup 和物化视图怎么救？

**问题：** 一张 30 亿行明细表，按「省份、渠道」做日聚合要扫全表 2 分钟。不能重建表，怎么加速？Rollup 和物化视图有什么区别？怎么确认优化真的命中了？

**期望加分项：**
- 给出两种落地：建 Rollup（key 改为 省份+渠道+时间，SUM 指标）或建同步物化视图，用 EXPLAIN 确认命中（扫描行数骤降、执行计划出现对应索引）
- 说清 Rollup 本质是「另一棵按新 key 排序的索引表」，命中依赖前缀匹配，维度顺序有讲究；同步物化视图可带过滤条件/表达式、改写更灵活，1.2+ 官方更推荐
- 知道 2.1+ 的异步物化视图能承接多表 join 的预计算，刷新策略可选
- 量化收益：扫描行数从 30 亿降到 百万级，耗时从分钟级到秒级
- 主动指出命中不了的排查方法：EXPLAIN 看实际选择的 rollup，确认是前缀不匹配还是查询带了大范围过滤

**减分项：**
- 分不清 Rollup 与物化视图，把两者混为一谈
- 建完不验证命中，以为查询自动变快
- 维度顺序随意排，导致永远命中不了
- 认为 Rollup 是内存缓存，不知道它要占磁盘与导入开销

**解答：**
先说结论：明细表的聚合慢，正确解法是「建额外的预聚合结构」，而不是调内存。Rollup 在 Doris 里是基表的另一套排序数据：把 key 从原始明细列改成「省份、渠道、日期」，指标列 SUM，Doris 导入时同步维护这份子表，查询按新 key 前缀 group by 时直接读它。关键规则：命中依赖 key 前缀——所以建 Rollup 前先分析真实查询，把最高频的维度组合按「等值在前、范围在后」排进 key，保证谓词能走前缀。1.2 之后更推荐同步物化视图：支持过滤、表达式、多列重组，且自动改写查询，比 Rollup 表达力强；2.1+ 的异步物化视图则能对多表 join 结果预计算。验证命中是必修课：跑一遍 `EXPLAIN`，看执行计划里选中的 index/rollup 名和扫描行数——命中时行数从 30 亿掉到百万级，没命中就检查维度顺序、谓词类型（范围查询放中间会断前缀）。实践坑：预聚合结构不是免费的，每个 Rollup/物化视图都会在导入时同步更新、占磁盘，建三五个就够了，建 20 个的结果是导入变慢、数据膨胀、收益趋近于零；还有，Aggregate 模型下的 Rollup 受聚合语义限制，只对 key 前缀内的维度有效，别指望它覆盖任意维度组合。

**延伸考点：** 同一张表有「省份+渠道」和「渠道+省份」两类高频查询，Rollup 该建几个、key 怎么排？物化视图命中不了时，你能从 EXPLAIN 的哪几行看出原因？

### Q6. 30 亿行算 30 天 UV，bitmap 精确去重怎么做？

**问题：** 要按用户 ID 精确统计 30 天活跃 UV（去重），明细表 30 亿行。count(distinct) 慢且内存吃紧，怎么用 bitmap 做精确去重？基数特别大（几亿）时 bitmap 会不会崩？什么情况改用 HLL？

**期望加分项：**
- 建 bitmap 列（BITMAP_UNION 聚合）配合预聚合，导入用 `to_bitmap(user_id)`/`bitmap_from_string`，查询用 `bitmap_union_count`/`bitmap_count`
- 说清原理与成本：bitmap 把用户 ID 映射到位图，内存与「ID 取值范围/基数」相关、与明细行数解耦，亿级基数内存可控
- 知道 count(distinct) 在高基数下的内存爆炸问题，以及 DQC 结果需要精确时的理由
- 区分精确（bitmap）与近似（HLL）去重的误差与内存差异，能给出选型依据（对账/风控要精确，漏斗/大盘可近似）
- 有线上实践：UV、留存、漏斗计算，能谈 bitmap 与维度组合（几亿 × 多维度）的资源估算

**减分项：**
- 不知道导入要做 `to_bitmap` 转换，直接把 string 塞进 bitmap 列报错
- 以为 bitmap 只省空间不占内存，忽略维度爆炸
- 说不清精确去重与近似去重的适用边界

**解答：**
先算账：count(distinct) 走 hash set，基数 1 亿大概需要几 GB 内存，查询并发一高 BE 就顶不住；bitmap 把用户 ID 按序号映射到位图，1 亿基数约 12MB，内存与明细行数完全解耦，所以 UV 这类高基精确去重是 bitmap 的典型场景。落地三步：建表把去重列定义为 `BITMAP` 类型、指标聚合方式选 `BITMAP_UNION`；导入时对 user_id 做 `to_bitmap(user_id)`（字符串/整数都行，注意空值与非法值）；查询用 `bitmap_union_count(uv_col)` 或 `bitmap_count(bitmap_union(uv_col))`。想提速就在 Aggregate 模型或物化视图上做预聚合——按天先算好日 UV，30 天口径由 30 个日 bitmap 做 or 再 count，这就是「明细→日汇总→月汇总」的经典优化。坑有两个：一是维度组合爆炸，按「省份×渠道×日期」都建 bitmap 列会让导入预处理和存储成倍上涨，要按真实查询维度收敛；二是 bitmap 对「ID 分布稀疏」不友好，用户 ID 是 16 位随机串时先做字典映射（id_mapping）再入位图。HLL 是另一条路：基数大、能容忍 1% 左右误差的场景（大盘、漏斗、AB 指标）用 HLL，内存比 bitmap 还省；但涉及钱、对账、风控的口径必须 bitmap 精确值，别用近似值交差。

**延伸考点：** 日 UV 表 30 天口径要实时算，明细→日 bitmap 的预聚合链路由谁触发（物化视图还是离线任务），延迟和成本怎么权衡？如果用户 ID 是 UUID 字符串，你会怎么改造让它能进 bitmap？

### Q7. 实时、离线、临时三条数据链路，导入方式分别怎么选？

**问题：** 三条链路：Kafka 每秒 5 万条实时写入、每天 HDFS 全量 500GB 离线导入、测试环境偶尔手工灌几万行。分别选什么导入方式？各有什么坑？

**期望加分项：**
- Kafka 实时：Routine Load 直接消费（自动提交 offset、断点续传）或 Kafka→Flink 清洗后 Stream Load 微批，能说出两种方案的取舍
- HDFS 大批量：Broker Load（异步、并行、失败可重跑），知道它适合离线条带
- 手工小批量：Insert Into 或 Stream Load 即可
- 说清 label 幂等防重、max_filter_ratio 容错、导入事务性（成功原子可见、失败回滚）
- 对吞吐/实时性/成本有量化意识：Routine Load 单任务吞吐、Stream Load 批次大小

**减分项：**
- 所有场景一刀切 Stream Load，说不出理由
- 不知道 Routine Load 的 offset 由谁管理、作业失败怎么恢复
- 忽略 label 幂等导致重复导入、报表翻倍
- 用 Insert Into 灌亿级数据，导入慢且占 FE

**解答：**
按「实时性、数据量、数据源」三个维度选。实时链路分两派：如果 Kafka 数据本身就是清洗好的宽表行，直接建 Routine Load——它由 FE 调度、自动记录 Kafka offset、作业挂掉重启能续传，运维成本最低；如果原始数据要 Flink 做 join/清洗/补维，就在 Flink 里攒批后用 Stream Load 微批写（Stream Load 走 HTTP、单批次几十 MB 到 GB 级、秒级可见，是流写 Doris 的事实标准）。Routine Load 的坑：单作业吞吐有限（几万~十几万条/秒），要吞吐就得多作业分 topic/分表并行，且作业数量别堆太多。离线链路用 Broker Load：异步提交、自动并行切片、失败重跑只重跑失败批次，500GB 全量配合分区覆盖重刷是标准姿势；别用 Stream Load 硬拉——要自己控制并发和重试，纯属重复造轮子。手工小量用 Insert Into，注意它走 SQL 路径、单次别超过百万行。三个通用铁律：导入必须带 label（幂等：同一 label 重复提交直接跳过，防止网络重试和任务重跑造成重复数据）；设好 max_filter_ratio 决定坏行容忍度；导入是事务——成功提交才原子可见，失败不留半截数据。实践坑：别把 Routine Load 和离线 Broker Load 同时大压力跑在同一批 BE 上，导入写放大与 compaction 抢资源，查询会跟着抖动。

**延伸考点：** Routine Load 消费 Kafka 时如果数据里混了半分钟的脏批次（格式错乱），作业会挂还是跳过？你会怎么设计「重放已消费数据」的机制？为什么说 Stream Load 的 label 必须由上游（如 Flink）业务生成而不是随机生成？

### Q8. 导入报 data quality error 但数据看起来没问题，怎么排查？

**问题：** Stream Load 返回 `data quality error`（NumberFilteredRows > 0），抽样看文件却没问题。怎么定位具体是哪几行、什么原因？导入失败会不会污染已存在的数据？max_filter_ratio 是什么、该不该调大？

**期望加分项：**
- 知道去拿返回 JSON 里的 ErrorURL/ErrorLog，逐行看具体报错（字段数、类型、长度、分隔符），而不是对着文件猜
- 能分类常见真凶：字段数与表列数不匹配、时间格式/时区、科学计数法、字符串超长（varchar 超限）、非法 UTF-8、bitmap/to_bitmap 转换失败
- 说清事务语义：失败自动回滚、已成功数据不残留；同 label 重提幂等
- 正确理解 max_filter_ratio：默认 0 表示一行错误整体失败；调大是「接受 N% 坏行」的容错策略，要权衡脏数据入库的代价
- 有用 curl 复现单行、`SHOW LOAD` 查看历史导入状态的经验

**减分项：**
- 不看 ErrorURL 瞎猜原因，或只知道把 max_filter_ratio 调到 1 掩盖问题
- 以为部分成功会留下半截数据、还要手工清理
- 不知道 label 幂等，重复导入把数据翻倍

**解答：**
先分清两个阶段：Stream Load 的报错分为 ETL 阶段错误（解析、类型转换、长度超限，记入 filtered rows）和事务阶段错误（资源不足、超时）。data quality error 就是前者——定位的第一动作是看返回的 `ErrorURL` 字段，拉取错误明细文件，里面逐行列出错误行号、错误列、原始数据和原因，几秒钟就能看到是字段数不对还是某个字符串超长。数据「看起来没问题」通常是抽样偏差：几百 MB 文件里混了几行异常（多一个 tab、时间字段带毫秒格式不一致、金额列是科学计数法、中文编码串台），全量校验才能抓出来。拿到具体原因后分两类处理：上游能改数据就修上游；上游数据本身脏、业务可容忍，才考虑 max_filter_ratio——它默认 0（任何错误行导致整个导入失败），设 0.1 表示允许 10% 坏行被过滤，但过滤掉的行不会进表，之后必须靠对账发现丢了多少。关于污染：Doris 导入是事务性的，失败自动回滚，已提交的数据不受影响；同 label 重复提交会被幂等拒绝，所以重跑任务不用清数据。实践坑：时间字段报错往往不是格式错，而是 BE 的时区配置与导入数据的时区不一致；to_bitmap 遇到非法 ID 会整批失败，这种情况建议先在上游清洗。

**延伸考点：** 线上要求「坏行率超过 0.1% 就整批失败告警，低于则过滤入库」，你会怎么用 max_filter_ratio + 返回统计实现这个策略？Routine Load 连续报错时作业会进入什么状态，恢复流程是什么？

### Q9. 一条 SQL 跑 30 秒，怎么用 Profile 和 EXPLAIN 定位瓶颈？

**问题：** 线上一条 join+聚合 SQL 要跑 30 秒，业务催得急。怎么用 EXPLAIN 和 Profile 定位瓶颈？执行计划里各节点的耗时和行数怎么读？拿到结论之后你具体会改什么？

**期望加分项：**
- 先 EXPLAIN 看计划形状：join 类型（broadcast/shuffle）、join 顺序、扫描行数、分区/分桶裁剪是否生效、谓词下推情况
- 开启 profile（enable_profile）后按节点读 rows 与 time，区分瓶颈在扫描、join 膨胀、聚合还是网络传输
- 能识别典型病灶：扫描行数没被裁剪、join 产生大中间结果、某节点行数与输入不成比例（膨胀）、数据倾斜导致单节点拖尾
- 有「定位→假设→验证」的流程，而不是一上来加内存/加并发
- 结合 runtime filter、物化视图、表结构调整给出下一步动作

**减分项：**
- 不看执行计划直接猜是「数据太多」
- 分不清扫描慢、join 慢、聚合慢，说不出任何证据
- 只会调大 exec_mem_limit 或并发度，问题依旧
- 不会用 EXPLAIN 的 rows/选择率判断裁剪是否生效

**解答：**
定位分两步：先用 `EXPLAIN` 看计划，再用 Profile 看实际执行。EXPLAIN 阶段重点看四件事：一，扫描行数——如果 `TableScan` 的 rows 接近全表而不是目标分区，说明分区裁剪没生效（谓词没下推到分区键）或缺少分区字段条件；二，join 的 shape 与顺序——broadcast 会把右表全量广播，右表大时网络与内存都爆，shuffle join 则看两个表是否按 join 键分桶一致；三，join 中间结果膨胀——左右表行数乘积级的物化往往是过滤时机太晚；四，聚合节点的输入输出比。Profile 是验证：开启后执行 SQL，按节点看 `RowsReturned` 与 `ExecTime`，哪一步耗时占比最大就是瓶颈。最常见的三种结论和动作：扫描慢（行数多）→ 补分区/分桶裁剪、把过滤条件推到扫描阶段，或建物化视图缩小扫描；join 慢（大表 join 大表）→ 换 bucket shuffle/colocate join 让同 key 数据本地关联，或加 runtime filter 提前裁剪；单节点慢（倾斜）→ 看某 BE 的节点耗时远高均值，找倾斜 key，必要时拆 key 或加盐。别在没数据的情况下调参——任何改动都先用 EXPLAIN 前后对比行数和计划形状验证收益。

**延伸考点：** EXPLAIN 里 scan 的行数是「优化器估计值」，实际执行可能差 10 倍，你会用什么手段拿到真实行数？一个 10 亿行大表 join 一个 1000 万行中表，broadcast 和 shuffle 你怎么定，依据是什么？

### Q10. 10 亿大表 join 万行小表还是慢，Runtime Filter 到底怎么生效？

**问题：** 大表 join 小表（10 亿 × 1 万行）已经开了 runtime filter，查询还是慢。Runtime Filter 的原理是什么？什么情况下它不会生效？怎么验证优化真的起作用了？

**期望加分项：**
- 说清 runtime filter 机制：join 先扫描小表生成过滤条件（IN/Bloom Filter/Min-Max），下发给大表的扫描节点提前过滤，把 join 的输入大幅裁剪
- 知道不生效的典型原因：过滤列不在大表扫描输出里、join 列类型不一致导致 bloom 无法构建、小表不够小被优化器禁用、大表扫描本身已经是索引命中
- 用 EXPLAIN 确认 filter 生成与下推（执行计划中的 filter 标记），并对比开启前后大表的扫描行数
- 关联谓词下推：join 键恰好是大表分桶列时还能吃桶裁剪
- 知道大表 join 大表时 runtime filter 帮助有限，要靠 colocate/bucket shuffle 或重写查询

**减分项：**
- 把 runtime filter 当万能药，开关一开就以为完事
- 不会验证是否生效，拿不出前后扫描行数对比
- 忽略 join 键类型、谓词位置这些决定性细节

**解答：**
Runtime Filter 的思路是「先算后滤」：join 执行时先扫描小表（右表）得到 join 键集合，构造成过滤条件（默认是 Bloom Filter，小结果集退化为 IN 或 MinMax），把它下推给大表的扫描节点，让大表在扫描阶段就把命中不了的 90% 的行滤掉，减少后续 shuffle、join 和聚合的开销。它的有效条件有三条，缺一就不生效：一是 join 键要能关联到大表的扫描输出列，如果大表这侧 join 的列经过了表达式转换或不在表中，过滤就下不去；二是两表 join 键的类型要一致，类型不同 Bloom Filter 无法匹配（string vs varchar 宽窄也踩过坑）；三是小表要足够小，超过阈值（默认几十万行量级）优化器会认为过滤无益而禁用。验证是硬功夫：开 profile 对比大表扫描节点的实际行数——从 10 亿掉到 1000 万说明生效，没变化就去 EXPLAIN 里找 filter 标记是否存在、有没有被下推到正确的节点。配套手段：大表的 join 键如果是分桶列，等值 join 还能走桶裁剪（只扫命中分桶），此时 runtime filter 都省了。注意边界：大表 join 大表（两边都上亿）时 bloom 构建代价高、过滤收益小，这时优先考虑 colocate join/bucket shuffle 让数据本地化，或先聚合再 join，而不是死磕 runtime filter 参数。

**延伸考点：** 小表 5000 万行、大表 10 亿行，runtime filter 大概率被禁用，你还有什么手段让 join 变快？Bloom Filter 有假阳性，过滤后的行数比真实命中多，你怎么判断这影响可不可接受？

### Q11. 实时数仓分层里 Doris 放哪层、存什么数据？

**问题：** 团队要搭实时数仓：Kafka 里有 MySQL binlog 和埋点日志，目标是 T+0 出报表且支持明细回溯。Doris 在这条链路里放在哪一层、存什么？分层和明细保留策略怎么设计？

**期望加分项：**
- 给出完整链路：binlog/日志 → Kafka → Flink（清洗/补维/宽表）→ Stream Load/Routine Load → Doris，能说清每层职责
- 明确 Doris 的定位：同时承担 DWD 明细（Duplicate）与 DWS/ADS 汇总（物化视图/汇总表），也可做 ODS 镜像（Unique 存 MySQL 全量）
- 权衡明细存储成本：全量明细保留 vs 只留汇总 + 明细按需回刷，给出量化估算（行数×字节×保留天数）
- 回刷/订正策略：Unique 模型覆盖、分区重刷，与离线链路的衔接
- 有实时性设计取舍：Routine Load 直连 Kafka vs Flink 加工后写入，什么数据走哪条

**减分项：**
- 没有分层概念，所有数据一把梭进一张大宽表
- 忽略明细存储成本，30 天明细全量保留随口就来
- 认为 Doris 是万能存储，join 失败、扩展性差全往里塞

**解答：**
典型链路是：MySQL binlog 与埋点日志进 Kafka，Flink 做清洗、补维、格式化后写出，Doris 负责「存储与查询」——它就是实时数仓的 DWD~ADS 实体。分层上我的建议：ODS 层镜像（MySQL 全量主表）用 Unique 模型存 Doris（主键=业务主键，流式 upsert），供下游 join 维表；DWD 明细（订单、行为事件）用 Duplicate 模型，保留策略按「回溯需求 + 成本」定，比如行为明细留 30 天、订单明细留 90 天；DWS/ADS 汇总（日/小时级聚合、UV 等）直接建汇总表或用物化视图承接，避免每次从明细现算。存明细还是只存汇总是最重要的取舍：明细回溯（出问题重算、新口径重刷）必须靠明细，但 30 亿行/天 × 多天明细的存储与 compaction 成本不低——所以给明细设明确保留期，超过保留期的业务只能走汇总。回刷机制要提前设计：T+0 场景下数据错乱靠 Unique 模型同 key 覆盖或分区删除重导，别指望手动改数据。实时性取舍：简单清洗、吞吐大的事件走 Routine Load 直连；需要 join/窗口聚合的走 Flink 后 Stream Load，两者可并行。实践坑：不要把 Flink 和 Doris 的写入耦合成「Flink 崩溃即 Doris 缺数」，用 label 幂等 + 定期对账兜底。

**延伸考点：** 明细表 30 天 + 汇总表 90 天，某天明细口径要重算且只影响 3 天前的数据，你怎么组织回刷任务？Doris 的物化视图刷新是异步的，实时报表「看到的是汇总延迟 10 分钟」你能接受吗，怎么跟业务解释这个 SLA？

### Q12. 高并发点查（QPS 2 万）用 Doris 怎么扛？Row Cache 是什么？

**问题：** 风控要按用户 ID 点查画像，QPS 2 万、单条要毫秒级返回。Doris 能扛吗？Row Cache 解决什么问题、怎么配置才有效？什么情况下应该承认 Doris 不适合？

**期望加分项：**
- 用 Unique 模型 + 主键等值查询命中前缀索引，配合分桶裁剪；能估算单查询扫描行数与延迟
- 说清 Row Cache（2.0.3+）：缓存整行数据（key→行），点查命中免扫描免反序列化，适合「重复点查同一批 key」的热点场景
- 优化组合：merge-on-write 免去多版本合并、排序列精简、分桶数匹配并发
- 有边界意识：Doris 是分析型引擎，QPS 高到一定程度（几万以上）或 key 完全随机无热点时，该用 Redis 缓存/换 KV 引擎
- 用 EXPLAIN/Profile 确认点查确实走了索引路径而不是全表扫描

**减分项：**
- 不看 EXPLAIN 就断言「主键查询肯定快」，没验证是否全表扫描
- 无脑开 Row Cache，不分析命中率与缓存容量
- 认为 Doris 能扛任意 QPS，不设边界

**解答：**
先判断可行性：点查 SQL 是 `WHERE user_id = ?` 且 user_id 是主键（Unique 模型）或排序键首位（Duplicate），就能命中前缀索引 + 分桶裁剪——单条查询扫描 1 个分桶内的少量行，单 QPS 级别可以到几百到几千，但 2 万 QPS 直接打 BE 还是吃力，因为每次查询都有 RPC、解析、执行开销。Row Cache 就是为此设计的：Doris 把查询过的「整行数据」缓存进内存（2.0.3+ 支持），后续同 key 点查直接返回缓存，省掉扫描与读取；它只对「命中率高」的场景有效——比如风控短时间反复查同一批用户、画像服务重复拉取。配置上要估算：单行几百字节 × 活跃 key 规模 × 目标命中率 = 需要的内存，量级到了再开，否则缓存命中率低、纯浪费内存；开启后看 BE 的 cache 命中率指标验证。组合拳：确保 merge-on-write（点查不需要合并多版本）、主键等值查询带完整主键（避免前缀不完整退化为范围扫描）、把排序列精简到最小。边界要说清楚：2 万 QPS 随机 key、无热点、要求 99.9% 毫秒级，这是 OLTP 的场景，正确姿势是热点数据放 Redis/本地缓存，Doris 只做底层分析；硬用 Doris 扛到 QPS 更高时，BE 的 RPC 线程和内存会被打穿。选型本质：Doris 的高并发能力是「分析型点查」——几百上千 QPS 的明细查询、大结果集扫描，不是 KV 式无限扩展。

**延伸考点：** 点查 key 完全随机（命中率 1%），Row Cache 还值得开吗？你会用什么指标决定要不要前置一层 Redis？点查 SQL 带了 10 个 where 条件但只有一个等值，怎么设计排序键让过滤最大化？

### Q13. 高频小批次导入后查询变慢，compaction 和版本堆积怎么治理？

**问题：** 实时链路每 10 秒导一批小数据，运行一周后查询明显变慢，`SHOW TABLET` 看到部分 tablet 版本数上百。compaction 的原理是什么？版本多为什么拖慢查询？怎么治理？

**期望加分项：**
- 说清 compaction 分层：cumulative（合并近期小版本）+ base（全量合并），导入的每个批次都是新版本
- 解释读放大：查询要把多个版本的数据按 key 合并读，版本越多 IO 与 CPU 开销越大，点查/聚合都会劣化
- 治理三板斧：控制导入节奏（加大批次、延长 Routine Load 攒批时间、减少并发导入任务）、监控 compaction 积压与 score、必要时手动触发/调参
- 知道 compaction 与查询抢资源，高峰期大量导入会放大抖动
- 用 `SHOW TABLET`/compaction 相关指标验证治理效果

**减分项：**
- 不知道版本数与查询性能的关系，只会删数据
- 只调 compaction 参数，不控制导入节奏——治标不治本
- 忽略磁盘 IO 能力对 compaction 速度的制约

**解答：**
先建立因果链：Doris 每次导入都生成一个新版本（新数据文件），查询时要按主键把多版本合并读取；版本少时开销可忽略，版本上百时读放大会直接吃掉扫描与合并的 CPU/IO，表现就是「查询越来越慢、点查也慢」。compaction 就是后台的合并任务，分两层：cumulative compaction 把近期的小版本合并成较大的中间版本，base compaction 再把累积的数据做一次全量合并；它持续运行但速度受磁盘 IO 和 CPU 限制，写入太快就积压。治理的优先级：第一是源头，改导入节奏——10 秒一批改成 30~60 秒一批（Routine Load 有 max_batch_interval 攒批参数），合并小任务、控制并发导入作业数，让写入速率低于 compaction 能力；第二是监控，盯 BE 的 compaction score 与积压队列、磁盘 IO 使用率，score 持续高企说明要降压；第三才是调参（cumulative compaction 的合并大小阈值、并行度），但调参要小心，合并激进会抢查询资源，低峰期放开、高峰期收紧是常见做法。还有一个隐蔽坑：Stream Load 空批次、重复 label 也会生成空版本占位，别让上游刷无意义批次；以及大批量回刷（如离线补数）与实时导入同时进行时，compaction 会双重承压，离线任务错峰跑。

**延伸考点：** 一晚上回刷 200 亿行，凌晨查询 SLA 也要保障，你如何安排导入批次、compaction 参数与查询之间的资源分配？为什么说「compaction 积压」本身比「版本数」更能反映问题，监控上你会用哪个指标？

### Q14. BE 频繁被 OOM kill，内存都去哪了？怎么治理？

**问题：** 线上 BE 进程频繁被系统 OOM kill，查询偶发报 `Memory limit exceeded`，导入也失败。BE 内存由哪几部分构成？怎么定位谁吃掉了内存？治理手段有哪些？

**期望加分项：**
- 说清 BE 内存组成：Page Cache（查询/扫描缓存）、导入 MemTable（写盘前的行缓存）、查询执行（算子中间结果）、compaction 读入缓冲
- 定位方法：dmesg 确认 OOM killer、看 BE 日志中 MemoryTracker 的内存占用排序、BE 提供的 HTTP 内存接口、区分「进程 OOM」与「查询内存超限」
- 治理：调 be.conf 的 mem_limit（给 OS/内核留余量）、限制查询并发与单查询内存上限、控制导入并发与批次大小、调整 Page Cache 容量
- 能区分两类问题：系统级 OOM（进程被杀）与查询级 limit exceeded（单查询超预算）的处理方式不同
- 有资源隔离意识：导入与查询并发高峰叠加是 OOM 常见诱因

**减分项：**
- 只会调大 mem_limit，甚至调到 100%，引发更频繁的进程级 OOM
- 分不清内存都被谁占了，不做 MemoryTracker 定位
- 忽略导入 MemTable 和 Page Cache 两个大头
- 不限制查询并发，靠「机器内存大」硬扛

**解答：**
先分清两件事：`BE 进程被系统 OOM kill` 是进程级内存失控（RSS 超限被内核杀），`Memory limit exceeded` 是查询级超预算被拒绝——前者说明 BE 总内存管理失效，后者是正常的内存保护在工作。BE 内存的大头按常见顺序：Page Cache（数据块缓存，加速查询与扫描）、导入 MemTable（每个导入批次写盘前的行缓冲，量级 = 导入并发 × 批次大小）、查询执行（join/聚合的中间结果，尤其大 join 与高基数 group by）、compaction 读入。定位步骤：先 `dmesg | grep -i oom` 确认是不是真的被 kill（还有 load 高、IO 高、swap 占用等误判），再看 BE 日志里进程退出前的 MemoryTracker dump——它会把各组件内存从大到小列出来，一眼看到谁超标；BE 的 HTTP 内存接口也能实时查看。治理按定位结果分类：Page Cache 占大头就把 storage_page_cache_limit 压到合理值（给查询留空间）；导入 MemTable 大就降导入并发、缩小批次；查询执行爆就用 mem_limit 与查询内存上限配合，限制并发与单查询预算，必要时把大查询放到低峰或资源组；最关键的是 be.conf 的 mem_limit 千万别设 100%——要给操作系统和页缓存留 10%~20% 余量，否则系统先杀 BE 进程。实践坑：内存问题往往是「查询峰值 + 导入高峰 + compaction 叠加」共同造成的，调参不如削峰——把大查询、回刷导入错开，比任何单点调优都有效。

**延伸考点：** 一个 group by 千万基数 + 大 join 的查询内存超限，你会从哪几个方向压它的内存占用（而不只是提高限制）？怎么用资源组把导入和查询的内存隔离，避免互相挤爆？

### Q15. 集群扩容加机器，FE 和 BE 各怎么部署、挂了会怎样？

**问题：** 集群要加 3 台机器扩容，并做高可用改造。FE 和 BE 分别承担什么角色、怎么部署？新加 BE 后数据会自动均衡吗？FE 单点挂了会发生什么？

**期望加分项：**
- 说清分工：FE 管元数据、查询规划与导入调度，BE 管数据存储与执行；FE 元数据用 bdbje 存储
- 高可用：至少 3 个 FE（Follower 参与选举、Observer 只读扩展），BE 多副本即可
- 扩容流程：`ALTER SYSTEM ADD BACKEND` 后数据自动均衡（balance/clone 任务），有量化意识（均衡时间与数据量关系）
- FE 单点的后果：元数据不可写、导入与 DDL 全停、已有查询可能还能跑；恢复靠 image 与 journal 备份
- 运维检查项：`SHOW FRONTENDS`/`SHOW BACKENDS` 的 Alive 状态、版本一致性

**减分项：**
- 只部署 1 个 FE 还说做了高可用
- 不知道 BE 加节点后靠什么机制搬数据
- 忽略 FE 元数据备份，FE 磁盘坏了无从恢复

**解答：**
先说角色：FE 是无状态节点里的「大脑」——管元数据（库表 schema、分区、副本分布）、SQL 解析与执行计划生成、导入任务调度，元数据持久化在 bdbje（fe 目录下的 image 与日志）；BE 是「手脚」——存数据（tablet）、执行查询和 compaction。高可用部署的标配：3 个 FE（1 leader + 2 follower，leader 挂了自动选举，follower 失败多数派内继续工作），可再挂 observer 扛高并发的查询规划；BE 至少 2~3 台且副本数 ≥ 2，单 BE 挂由副本机制兜底。扩容 BE：`ALTER SYSTEM ADD BACKEND` 加节点后，FE 的 balance 调度会自动把部分 tablet 的副本 clone 到新节点，最终数据分布趋于均衡——但注意均衡是后台任务、速度受 IO 影响，几百 TB 集群可能要跑几天，期间查询性能会波动，最好低峰期加。扩容 FE：直接启动新 FE 节点加入即可，注意全集群版本一致。FE 单点的后果是最容易被低估的：FE 挂了导入、DDL、新建查询全部不可用（已有连接也可能断），所以「FE 至少 3 个 + 元数据定期备份到异地」是硬要求；恢复时用 image 文件 + journal 回放，没有备份就只能从 BE 反推 schema，非常痛苦。日常巡检就两条命令：`SHOW FRONTENDS` 和 `SHOW BACKENDS`，盯 Alive 与磁盘容量。

**延伸考点：** 扩容 BE 后你发现 tablet 均衡进度条走得很慢，可能是什么原因（副本数、磁盘容量、IO）？FE 的 observer 和 follower 有什么区别，你会什么时候加 observer？

### Q16. 三副本集群一台 BE 宕机/坏盘，写入会失败吗？副本怎么修？

**问题：** 三副本集群（replication_num=3），某台 BE 宕机或坏盘。此时写入会失败吗？查询会读到不一致的数据吗？副本怎么自动修复？副本数该怎么权衡？

**期望加分项：**
- 说清 quorum（多数派）写入语义：三副本中两副本写成功即成功，一台 BE 挂不影响写入，但「写成功」的判定是多数派而非全部
- 副本修复机制：FE 的 tablet scheduler 调度 clone 任务，从健康副本向缺失副本复制补齐，`SHOW REPLICA` 观察状态
- 查询侧：读副本可能读到稍旧数据（一致性级别），需说清 Doris 的一致性模型
- 权衡：2 副本（多数派=2，可容忍 1 挂但写要全写？）不，2 副本 quorum=2 即全部，容错 0；3 副本容错 1、4 副本容错 1（性价比差）
- 有坏盘/慢盘治理经验：坏盘机器摘除（decommission）后再换盘

**减分项：**
- 以为三副本「一台挂了完全没事」，说不出多数派与写时延关系
- 不知道副本靠 clone 任务自动修复
- 忽略坏盘持续 IO 错误对查询的拖累

**解答：**
副本语义是 quorum（多数派）：3 副本时，一次导入只要 2 个副本成功就认为成功（返回成功），第 3 个副本后续补齐；所以一台 BE 宕机不影响写入，但写入时延和副本修复的 IO 会上升。查询侧的模型要讲清楚：Doris 读的是「已提交且可见」的版本，读副本的选择由 FE 决定，极端情况下（某副本落后）可能读到稍旧的数据，这是分布式系统的一致性取舍，别承诺强一致。宕机后的自动修复链路：BE 恢复或新节点加入后，FE 的 tablet scheduler 发现副本数不足（小于 replication_num），会调度 clone 任务把健康副本复制过去——`SHOW REPLICA` 能看到每个 tablet 各副本的状态（ALIVE/NORMAL vs BAD/缺失），修复速度受磁盘 IO 限制，数据量大时要耐心并监控。真正要重视的是坏盘：盘坏了 BE 不一定自动摘除，坏盘上的 tablet 会持续报错、拖慢该 BE 上的查询，正确操作是 `ALTER SYSTEM DECOMMISSION BACKEND` 优雅下线（先把副本迁走）再换盘，而不是直接 kill 进程。副本数权衡：2 副本容错 0（多数派=全部，一台挂就没法定配额），3 副本容错 1 是性价比最优，4 副本容错仍是 1、多花的存储和写放大不划算——所以默认 3 副本，只有磁盘贵、可容忍短暂不可用的冷数据才降 2。

**延伸考点：** 坏盘 BE 没被自动摘除，查询开始报错/变慢，你判断是副本问题还是查询问题的手段是什么？如果业务要求「读到任何副本都不能是旧数据」，Doris 满足不了，你会怎么跟业务讲这个一致性边界？

### Q17. 200+ 报表 SQL 频繁出现慢查询，怎么建监控和治理闭环？

**问题：** 线上 200+ 张报表 SQL 跑在 Doris 上，最近频繁出现慢查询，业务投诉。你会建立什么样的监控与治理闭环？Doris 有哪些开箱即用的手段（审计日志、metrics、profile）？

**期望加分项：**
- 启用审计日志（audit_log）采集 SQL 文本、耗时、扫描行数，定期输出慢 SQL 榜单（按耗时/扫描量排序）
- Prometheus + Grafana 采集 FE/BE metrics，重点盯：BE 磁盘 IO、compaction 积压、内存、查询并发
- 治理闭环：识别→explain/profile 定位→优化（分区裁剪、物化视图、join 重写、索引）→回归验证，形成流程而非救火
- 能分类常见病灶：无分区条件全表扫描、join 膨胀、缺预聚合、大结果集回传
- 有规范意识：限制无 where 的大查询、设置慢查询阈值告警、新 SQL 上线前 explain 评审

**减分项：**
- 没有审计日志意识，靠业务投诉才知道
- 只会加资源（加内存/加机器）
- 治理不闭环，改了不验证、不沉淀规范
- 分不清监控指标该看 FE 还是 BE

**解答：**
治理的前提是能发现。第一层：审计日志——Doris 的 FE audit log 记录了每条 SQL 的库表、耗时、扫描行数、返回行数、内存，把它采集到日志平台或直接查审计表，就能产出「按耗时 Top、按扫描行数 Top」的慢 SQL 榜单，这是治理的入口；审计日志默认开启但要点是持续落盘与归档，别让它把 FE 磁盘写爆。第二层：指标——BE 通过 `metrics` 接口暴露 Prometheus 格式指标，重点盯四类：磁盘 IO（扫描与 compaction 争抢）、compaction 积压（版本堆积的前兆）、内存水位、查询并发与队列；FE 侧盯元数据操作与导入状态。有了榜单进入定位环节：单条慢 SQL 用 EXPLAIN 看是否全表扫描/裁剪失效/join 形状，结合 profile 看瓶颈节点——这是 Q9 的能力复用。优化手段按成本排序：加分区/分桶裁剪条件 → 建物化视图承接高频聚合 → 重写 join（缩小右表、提前过滤）→ 加索引（bitmap/bloomfilter 索引对低基/高基过滤列）。最后是闭环的「防」：定义慢查询阈值（如单条 >5s 告警、扫描行数 >1 亿告警），对高频报表 SQL 做 explain 评审，禁止无 where 条件的全表查询上线；每周复盘慢 SQL 榜单看治理趋势。实践坑：别把所有指标都建告警——告警泛滥等于没有告警，先解决 Top10，再逐步覆盖。

**延伸考点：** 审计日志显示某张报表每天扫 50 亿行，但 SQL 里明明带了日期条件，你会怎么排查是裁剪没生效还是数据真的多？慢 SQL 榜单和业务方「报表慢」的感知总是对不上（榜单没这条 SQL），可能是什么原因？

### Q18. 大表要加 5 个列、改字段类型，线上不能停，Schema 变更怎么做？

**问题：** 一张 200 亿行大表要批量加 5 个列，还要把某字段从 string 改成 int，线上查询和导入不能停。Doris 的 schema change 怎么做？哪些操作是危险/不可逆的？动态分区和 TTL 怎么配合生命周期？

**期望加分项：**
- 加列走 light schema change，快、不阻塞读写；改类型/删列等重操作会触发数据重写（数据量级决定耗时）
- 说清 schema change 是异步 job：`SHOW ALTER TABLE COLUMN` 看进度，期间查询/导入一般不受影响但会占资源
- 危险/不可逆清单：改排序键顺序、改分桶数（需重建表搬数据）、string→int 等不兼容类型转换、删列后无法恢复
- 动态分区（dynamic partition）自动建/删分区，配合 TTL 做数据生命周期
- 操作规范：低峰执行、先小表验证、评估重写耗时与磁盘余量

**减分项：**
- 不知道分桶建表后不可改，以为 ALTER 能随意调
- 白天高峰期对 200 亿行表做类型变更，导致重写风暴
- 忽略类型转换的兼容性限制
- 不知道 schema change 是异步的，执行完 DDL 就以为完成了

**解答：**
先分轻重：Doris 的 schema change 是异步 job，不是即时完成。加列这类「轻变更」走 light schema change，只改元数据不重写数据，秒级完成、不阻塞读写，所以批量加 5 个列可以一条 DDL 搞定；而改字段类型、删列、加索引这类「重变更」需要按新 schema 重写整表数据——200 亿行按写入速度估算可能跑数小时，期间导入查询一般仍可用，但磁盘 IO 和 CPU 被 job 占用，线上会出现性能波动，所以必须低峰执行、先在小表验证、确认磁盘有足够余量（重写是双份空间）。不可逆清单要背熟：分桶数是建表定死的（调整 = 重建表搬数据）；排序键顺序改动 = 重建；类型转换有兼容性白名单（string→int 这种跨类转换不支持，得重建或加新列算迁移）；删列丢了数据没法找回，删之前先备份。配合生命周期的正确姿势：动态分区（dynamic partition）让 Doris 按规则自动建未来分区、删过期分区，配合数据保留策略做 TTL——但注意 TTL 是物理删分区，删了就没法回溯，业务要「可查 90 天」就留 90 天加冗余，别省这点空间换来数据事故。操作规范上：DDL 前 `SHOW ALTER TABLE` 确认没有排队的旧 job，变更后 `SHOW ALTER TABLE COLUMN` 观察状态直到 FINISHED，别提交完就散会。

**延伸考点：** string 类型的日期字段要改成 DATE 类型以便分区裁剪，但类型转换不支持，你会怎么设计迁移方案（新表/新列/回填）？动态分区在「凌晨建当天分区」时刚好有查询进来，会失败吗？

### Q19. 两地容灾 + BI 直连，跨集群复制和 MySQL 协议兼容怎么做？

**问题：** 要做 A/B 两地容灾（数据从 A 集群同步到 B 集群），同时业务侧 BI 工具（Tableau/Superset）和 JDBC 程序要直连 Doris 查询。跨集群复制怎么做？MySQL 协议兼容到什么程度？有哪些容易踩的坑？

**期望加分项：**
- 跨集群复制用 CCR（cross cluster replication），`CREATE SYNC JOB` 单向同步表/库，用于容灾与读扩展；知道它是单向的、有同步延迟
- 备份恢复走 BACKUP/RESTORE 快照到远端存储（S3/HDFS），与 CCR 的定位区分（备份 vs 同步）
- MySQL 协议：3306 端口、JDBC/MyBatis 直连、标准 SQL 子集与 BI 工具适配良好
- 说清边界：非完整事务（无 ACID 事务、无外键）、DML 子集（UPDATE/DELETE 有条件限制）、高并发写不擅长的坑
- 有连接管理经验：连接池参数（连接数、超时）、时区/字符集配置

**减分项：**
- 以为 MySQL 生态的 SQL 全兼容，把存储过程/触发器搬过来
- 不知道 CCR 是单向的，拿它当双写双向同步
- 忽略 JDBC 连接池与 BI 直连对 BE 连接资源的压力

**解答：**
两条线分开讲。容灾/同步：跨集群复制用 CCR——1.2+ 引入的同步机制，`CREATE SYNC JOB` 把 A 集群的库表单向同步到 B 集群（B 只读），延迟秒级到分钟级，适合「同城主备」「迁移过渡」「B 集群分担查询」；必须说清三个边界：单向（B 的写入不会回 A）、延迟不是 0（严格 RPO 场景要加对账）、DDL 变更要手动同步（改表结构要两边都改）。备份恢复是另一回事：BACKUP 把表快照打到远端存储（S3/HDFS），RESTORE 拉回来，适合灾难重建与迁移，定期做、留多版本，别和 CCR 混为一谈。兼容性：Doris 兼容 MySQL 协议，3306 端口，JDBC/MyBatis、Tableau/Superset 直连基本无障碍，标准 SELECT/聚合/join 都能跑；但要明确边界：无完整事务（不支持跨表 ACID）、无外键/触发器/存储过程、UPDATE/DELETE 需要带条件（不支持无 where 更新），业务侧如果假设「MySQL 全兼容」就会在事务和多表更新上翻车。坑集中在连接层：BI 工具和 JDBC 连接池别开太多长连接（几百上千个连接直接打满 BE 的线程资源），限制连接池大小、设置合理的 socket 超时与重试策略；时区与字符集要与数据一致，否则时间字段对不上。

**延伸考点：** 业务要求 B 集群也要能写（双活），CCR 单向满足不了，你会用什么方案（主主、读写分离 + 冲突处理）？BI 直连高峰期把 BE 连接打满、查询互相挤爆，你会做哪些限制？

### Q20. Doris vs ClickHouse vs StarRocks，OLAP 引擎怎么选型？

**问题：** 团队评估 OLAP 引擎：核心需求是多表 join 多、需要更新/删除、BI 直连、有 Kafka 实时链路。Doris、ClickHouse、StarRocks 怎么选？结合你实际用过的坑谈取舍。

**期望加分项：**
- 按需求拆解而不是背参数：join 能力、更新删除、MySQL 协议/生态、实时数仓链路四维度对比
- 说清血缘与路线：Doris/StarRocks 同源（Palo 分叉），架构相近；ClickHouse 是另一条路线（MergeTree、单表分析极致）
- 点出各自痛点：CH 多表 join 弱（需大右表优化、无事务、更新删除弱）；StarRocks 与 Doris 特性迭代节奏不同（如物化视图、主键模型）；Doris 社区生态（Apache 背书、3.x lakehouse 演进）
- 结合团队能力与运维成本：Doris 系上手快（MySQL 协议）、功能全；CH 单表性能强但要自己兜 join 与一致性
- 有真实选型/迁移案例与量化对比（同样查询的耗时、资源）

**减分项：**
- 人云亦云「XX 就是最强」，说不出依据
- 忽略核心需求（join/更新），只比单表扫描性能
- 无实践佐证，全是网上看来的参数对比

**解答：**
选型先回到需求：你的四个核心点——多表 join、更新删除、BI 直连、实时链路——几乎每条都在指向 Doris/StarRocks 而不是 ClickHouse。理由：CH 的单表聚合和扫描是强项（MergeTree 列式存储、大宽表极快），但分布式 join 是它的短板（需要人为把右表塞进内存或做全局字典），更新/删除弱（需 ReplacingMergeTree 变通且难保证强一致），这些恰好是你最在意的场景；把 CH 硬套进「多 join + 更新」的数仓，运维复杂度会反噬。Doris 与 StarRocks 是同源的近亲（都源自 Palo），架构和运维模型高度相似，选型差异主要在生态与迭代：Doris 是 Apache 顶级项目、社区治理稳定，3.x 在湖仓一体（对接 Iceberg/Paimon、自动同步）上走得快，国内大厂落地案例多；StarRocks 在主键模型、物化视图刷新、query cache 等特性上迭代激进，查询优化器口碑好。实操建议：短期看团队——有 MySQL 使用经验的人上手 Doris 系最快（协议兼容、SQL 友好），中期看运维——两者都是「FE/BE 架构、内存敏感、compaction 需关注」，运维能力不足时选文档与社区更全的；长期看演进——如果有湖上分析、跨数据源联邦查询的规划，Doris 3.x 的 lakehouse 能力值得提前验证。我踩过的坑供参考：用 CH 做多 join 报表最后靠物化视图和重写 SQL 才扛住；Doris 系要注意版本升级节奏与内存配置。最终选型要跑通「你的真实 SQL + 数据量」的压测，别信 PPT。

**延伸考点：** 如果你们的 join 全是「大表 join 维表」且维表只有几十万行，CH 还完全不考虑吗？为什么？（给 CH 一个翻案机会）Doris 和 StarRocks 如果必须二选一，你会用什么测试用例（3~5 个）来做最终决策？
