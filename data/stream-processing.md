# 数据 · 流式计算（面试题库）

本文件聚焦流式计算通用核心能力的真实工程考察，覆盖事件时间与处理时间、Watermark 与乱序/迟到数据、窗口与倾斜、状态管理与状态后端、Checkpoint 与容错、exactly-once 一致性语义、背压、双流 join、去重、维表关联、实时指标计算、流批一体与对账等跨引擎实践主题，可结合 Flink、Kafka Streams、Spark Streaming 等引擎举例。题目均为可复现的线上场景问题，重点考察候选人的定位思路、取舍判断与稳定性意识，而非概念背诵。难度自 Q1 至 Q20 循序渐进，从实践基础逐步过渡到架构级开放性思考题。

### Q1. 这个场景用流式还是批式，你怎么判断？

**问题：** 业务方要求「报表数据要实时」，你的第一反应是直接上 Flink 吗？一个指标计算场景，你怎么判断该用流式计算还是离线批计算？如果业务方其实只要分钟级延迟，你还会选实时链路吗？

**期望加分项：**
- 能说出「延迟、准确性、成本」三者之间的取舍，而不是把实时当银弹
- 会先反问业务方对延迟的真实诉求（秒级/分钟级/小时级），再决定技术选型
- 能给出中间态方案：分钟级微批（Spark Streaming 或 Flink 定时触发）成本远低于秒级流式
- 提到实时链路的隐性成本：常驻资源、状态管理、运维与故障恢复复杂度
- 主动点出批流口径不一致的根源（时间归属、去重口径、维表快照），并给出统一口径的思路

**减分项：**
- 听到「实时」就上 Flink，答不出判断依据
- 只看延迟不看成本与维护复杂度
- 说不清批式与流式在「同一份数据能否重跑复现」上的本质差异
- 没有「先定口径再选引擎」的意识

**解答：**
判断的第一步不是选引擎，而是量化业务对延迟的真实诉求：秒级（风控、实时大屏）才值得上流式；分钟级用微批或准实时即可；小时级直接离线。第二步看成本：实时任务 7×24 常驻、状态需要管理、故障要恢复，运维复杂度比离线高一个量级，链路越多负担越重，所以「宁少勿滥」。第三步也是最容易翻车的：批和流算同一指标经常对不上，根因通常是事件时间归属不同（离线按业务时间、实时按处理时间）、去重口径不同（离线精确、实时近似）、维表快照时机不同（离线用当日快照、实时用当前值）。所以正确顺序是：先定统一口径（同一套 SQL 语义与指标定义），再谈引擎。实践上常用折中：核心对账指标走离线兜底，实时只承担「趋势与预警」职责。记住一句话：实时链路是消耗品，每个新任务都是长期运维负担，没有明确延迟收益就不该上。

**延伸考点：** 同一指标批式算 100、流式算 99，一般会差在哪几个环节？如果你只有分钟级延迟要求，用什么架构性价比最高？

### Q2. 事件时间和处理时间，这个指标该用哪个？

**问题：** 一个订单量实时统计任务，有人用处理时间开窗，有人用事件时间开窗。数据在传输链路里延迟忽高忽低，为什么处理时间的统计结果每次跑都不一样？你的订单统计怎么选？

**期望加分项：**
- 能准确说出两者语义：处理时间是数据到达引擎的系统时间，事件时间是业务发生时刻的时间戳
- 能指出处理时间窗口的边界由「到达时刻」决定，一旦任务重启、背压、延迟抖动，同一窗口包含的数据会变，结果不可复现
- 能说出事件时间的代价：需要 Watermark 容忍乱序，引入延迟与状态开销
- 结合业务判断：涉及金额、对账、考核的必须事件时间；纯监控类可接受处理时间
- 提到时间戳质量问题：日志里没有可信的业务时间戳时，事件时间无从谈起

**减分项：**
- 说不清两者的本质区别，或把「处理时间」理解成「数据处理耗时」
- 认为事件时间永远更好，答不出它带来的延迟与状态代价
- 无法解释「同一份数据两次跑结果不同」是处理时间的什么特性导致的
- 忽略日志时间戳缺失、客户端时钟不准等真实约束

**解答：**
先看业务对时间语义的要求。涉及金额、结算、对账、排名的指标，必须事件时间——因为处理时间窗口的边界取决于数据到达引擎的时刻，链路一抖动、任务一重启，同一个窗口装的数据就变了，结果不可复现，上线后对不上账就是大事故。而事件时间以业务时间戳为准，只要数据最终到达，归属就确定，结果可复现，代价是必须用 Watermark 容忍乱序，并且窗口状态要保留到水位线推进，延迟和状态成本上升。纯监控、日志告警这类「看到趋势就行」的场景，处理时间够用且便宜。实践上要处理两个坑：一是客户端时间戳不可信（用户改系统时间、跨机房时钟偏差），要选服务器侧可校准的时间来源；二是日志里没有时间戳时事件时间无从谈起，要在采集端就补齐。另外很多任务实际是「窗口用事件时间、触发与告警用处理时间」的混用，面试时能讲清这种混合语义各自承担什么职责，比背定义更体现水平。

**延伸考点：** 哪些场景即使有可信的事件时间，也必须以处理时间为准（比如实时熔断告警）？两个机房时钟偏差 5 分钟，你的事件时间统计会不会出问题？

### Q3. 数据乱序迟到，Watermark 怎么设才不丢数？

**问题：** 你的流任务按事件时间开窗，但上游数据会乱序、迟到：大部分迟到 10 秒以内，偶尔迟到 5 分钟。Watermark 设成事件时间减多少合适？设小了丢数据，设大了延迟高，你怎么平衡？窗口关闭后还到的数据怎么办？

**期望加分项：**
- 能说出 Watermark 的本质是「进度信号」而不是数据，代表「事件时间早于该值的数据已基本到齐」
- 会用数据分布做量化：统计线上事件时间与到达时间的延迟分位数（如 P95），据此设定容忍量
- 能说出多并行度下 Watermark 取各分片最小值的机制，以及无数据分片（idle source）会卡住整体进度的问题与 idleness 超时处理
- 能给出迟到数据的三种归宿：默认丢弃、allowedLateness 重新触发窗口、侧输出流落死信事后回补
- 提到乱序容忍与业务准确性之间的取舍逻辑

**减分项：**
- 把 Watermark 当成一条真实数据或一个时间点阈值，说不出它是「进度估计」
- 只会背「定期 + 水位线」公式，不会结合数据延迟分布给出量化依据
- 不知道并行度分片间 Watermark 取最小值，说不出某个分区没数据会拖慢全任务
- 迟到数据只会说「丢弃」，没有 allowedLateness / 侧输出流等兜底方案

**解答：**
先量化再设定：对线上数据统计「事件时间 vs 到达时间」的延迟分布，假设 P95 是 30 秒，Watermark 设为事件时间减 30~60 秒，就能覆盖绝大多数乱序，这是「准确性与延迟」的第一重取舍。工程上 Watermark 通常随消费进度周期推进（如每 2~3 秒发射一次，Flink 可用 `WatermarkStrategy.forBoundedOutOfOrderness(Duration.ofSeconds(30))`）。关键认知：Watermark 是启发式估计，永远有极少数数据落在它之后。对这些迟到数据，默认是窗口关闭后丢弃，但业务不能接受丢数时给三档兜底：一是 `allowedLateness`，让窗口状态多保留 N 分钟，迟到数据到达时重新触发计算并输出更新结果（下游要能处理「同一窗口输出多次」）；二是 `sideOutputLateData`，把迟到的数据单独打到侧输出流落 Kafka，事后离线回补；三是把「窗口统计」退化为「明细落地」，让准确性交给下游。实践中的坑：并行度大于 1 时 Watermark 取各分片最小值，某个分区长期没数据会卡住整个任务，必须配置 idle 超时强制推进；Watermark 只对事件时间有意义，混用处理时间触发时要清楚两者语义。记住：Watermark 的设计本质是「花钱买准确性」，设多大取决于业务愿意为多等那几秒付多少成本。

**延伸考点：** allowedLateness 让窗口重新触发后，下游拿到同一窗口的多条结果，怎么保证最终一致？侧输出流的迟到数据，你用什么机制回补到正确窗口？

### Q4. 三种窗口各适合什么场景？滑动窗口贵在哪？

**问题：** 实时大屏要每分钟展示「最近 5 分钟」的 GMV 曲线，用滚动窗口还是滑动窗口？用户行为要按「30 分钟无操作算一次会话」切分，用什么窗口？三种窗口的取舍分别是什么？

**期望加分项：**
- 能准确对应场景：固定周期统计用滚动窗口（Tumbling）、平滑曲线用滑动窗口（Sliding）、按活动间隙切分用会话窗口（Session）
- 能算出滑动窗口的计算放大倍数（窗口长 5min / 滑动步长 1min，数据被计算 5 次），并给出资源规划依据
- 能说出会话窗口的本质是「按 gap 合并」的状态机，状态大、要控制超时，大流量 key 容易撑爆状态
- 能给出增量聚合优化（先滚动预聚合、再滑窗）的思路
- 提到 SQL 中 TUMBLE / HOP / SESSION 窗口的语义对应

**减分项：**
- 只会背三种窗口定义，答不出各自的计算成本差异
- 认为滑动窗口只是「滚动窗口的升级版」，不知道数据放大问题
- 把会话窗口当成固定超时窗口，说不清它是动态合并的
- 忽略窗口结果重复输出对下游的影响

**解答：**
按业务诉求对号入座：每分钟的 PV/UV、整点报表这类「固定周期」用滚动窗口，窗口间不重叠、无重复计算，最便宜。要画平滑的滑动曲线（每 1 分钟展示最近 5 分钟 GMV），用滑动窗口——但代价要算清楚：窗口长 5 分钟、步长 1 分钟，同一批数据会被 5 个窗口重复聚合，计算量放大 5 倍，资源要按放大后的量规划。优化手段是先按 1 分钟做滚动预聚合（结果落状态），滑动窗口只聚合 5 个预聚合结果，把放大倍数从 5 降到接近 1。会话窗口用于「行为间隙切分」：连续行为间隔不超过 gap（如 30 秒）就合并为一次会话，适合用户行为路径、活跃时长统计；它内部是一个动态合并的状态机，每个 key 都要维护「最后活跃时间」并持续合并，状态开销远大于滚动/滑动窗口，gap 设小会疯狂合并、设大会把独立会话并到一起，且大流量 key（如平台级漏斗）容易把状态撑爆，必须配状态清理与超时。实践坑：滑动窗口每个周期都会把整窗口结果重算重发，下游若按窗口去重存储，要注意去重键设计；会话窗口在 SQL 引擎里实现差异大，迁移引擎时结果可能对不上。三种窗口的选择本质是「口径需求 vs 计算成本」的权衡。

**延伸考点：** 滑动窗口的两阶段预聚合，怎么保证中间结果不丢、最终结果准确？会话窗口的 gap 怎么根据业务数据确定，而不是拍脑袋？

### Q5. 热点 key 把窗口聚合拖垮了，怎么处理？

**问题：** 大促期间流量集中到少数几个爆款商品上，实时聚合任务的某些算子越来越慢、Watermark 迟迟不推进，数据全部积压。你怀疑是数据倾斜，怎么定位？怎么解决？

**期望加分项：**
- 能说清定位手段：看各算子反压状态与单 Task 处理耗时、按 key 计数抽样定位热点 key，而不是一上来就加并行度
- 能给出两阶段聚合方案：第一层按「key + 随机盐」局部聚合缩小数据量，第二层去掉盐做最终聚合，精度无损
- 能指出两阶段聚合的边界：盐只能缓解「key 多但个别 key 大」的倾斜，同一个超热 key 内部还得按业务子维度拆分（如直播间切片、商品分桶）
- 提到盐要动态（热点消失后固定盐白白放大数据）以及热点自动发现
- 理解实时倾斜与离线倾斜的区别：离线可以等，实时倾斜会直接拖慢 Watermark、放大端到端延迟

**减分项：**
- 只回答「加并行度」，说不出瓶颈在 key 分布而非并行度
- 不知道 local-global（加盐两阶段）聚合的存在，或说不清它怎么保证精度
- 答不出热点 key 单点超载时的处理
- 没有定位流程，直接给方案

**解答：**
定位先于解决：在 Web UI 看各算子的反压状态和每条链路耗时，反压 HIGH 的算子往往是聚合算子；再用「按 key 抽样计数」确认是不是个别 key 占了绝大多数数据——比如 1 万个 key 里 3 个 key 占了 80% 流量。解法分两级：第一级，两阶段聚合（local-global）：上游先按「原 key + 随机盐（如 0~127）」做第一层聚合，每个盐桶只处理原数据量的 1/128，再按原 key 汇合做第二层去掉盐的最终聚合。因为盐只是中间拆分、最终仍按原 key 汇总，精度无损，这是最常用的解法（Flink SQL 里常配合 minibatch 使用）。第二级，同一个 key 内数据量仍然过大（比如大主播直播间点赞流），盐也救不了，要按业务子维度继续拆：按直播间切片、按设备类型、按小时分桶，最后汇总层再合并。实践坑：盐必须是动态的——热点 key 消失了，固定盐还在放大每一条数据；要有热点自动发现机制（如按 key 计数超阈值自动打散）；倾斜如果发生在 join 而非聚合（Join 一侧的热 key），要用广播小表或倾斜 key 拆分；聚合算子的倾斜会通过反压传导回 source，拖慢整个任务的 Watermark 与 Kafka 消费位点。实时倾斜治理的核心目标不是「消灭倾斜」，而是让倾斜不拖慢全局进度。

**延伸考点：** 加盐两阶段聚合后，窗口触发时间会变吗？下游看到的结果和直接聚合完全一致吗？热点 key 自动打散怎么做才不引入结果误差？

### Q6. 状态越来越大，内存还是 RocksDB？

**问题：** 你的实时任务要按用户维护「近 30 天行为画像」，状态规模预计几十 GB，用什么状态后端？如果只有几个 GB 呢？两者各自牺牲了什么？

**期望加分项：**
- 能说清本质差异：内存后端状态放 JVM 堆，吞吐高但受堆大小与 GC 限制；RocksDB 落本地磁盘（SSD）+ 块缓存，容量大但每次读写要序列化，吞吐低一个量级
- 能给出量级判断：几个 GB 以内用内存后端，几十 GB 以上必须 RocksDB
- 能说出 RocksDB 的调优点：block cache 大小、write buffer、增量 Checkpoint 只快照变化的 SST
- 提到状态增长的治理：Keyed State TTL、窗口结束后的状态清理
- 指出状态后端切换需要重建状态的代价，选型要提前按数据量预估

**减分项：**
- 只会背「RocksDB 比内存大」，说不清吞吐、延迟、GC、序列化的具体取舍
- 认为 RocksDB 永远更好，忽略小状态场景下序列化开销反而拖慢性能
- 不关心状态只增不减的问题，没有 TTL / 清理意识
- 不知道 RocksDB 本地目录要放 SSD、托管内存要与堆内存统筹规划

**解答：**
选型的核心变量是「状态规模 × 访问频率」。状态小（几个 GB 以内）且读写频繁：用内存状态后端（Heap），数据在 JVM 堆内，吞吐高、延迟低，实现简单；代价是状态挤占堆内存、放大 GC 压力，且 Checkpoint 要把全部状态序列化快照，状态一大快照就成了瓶颈。状态大（几十 GB 以上）：用 RocksDB，按 key 排序落本地磁盘，配合块缓存提供接近内存的读性能，容量可以到 TB 级；代价是每条读写都涉及序列化/反序列化，吞吐比内存后端低一个量级，且要额外规划托管内存（RocksDB 块缓存、write buffer）与堆内存的比例。实践要点：RocksDB 状态后端务必配增量 Checkpoint（只快照新增变化的 SST 文件），否则全量快照几十 GB 每次都把任务拖到超时；block cache 要根据状态访问模式调（热点状态大就多分内存）；本地目录必须 SSD，机械盘会直接拉垮吞吐。比选型更重要的治理：状态只增不减是最大隐患——Keyed State 要设 TTL（如画像 30 天过期，`StateTtlConfig` 惰性清理），窗口状态要在窗口关闭后显式清理，否则再大的后端也会被涨满。最后记住：切换状态后端意味着任务重启 + 状态重建（从 checkpoint 或重新消费回放），代价极大，所以上线前就要按预估峰值数据量定好后端，而不是等 OOM 再换。

**延伸考点：** RocksDB 状态后端的增量 Checkpoint 和全量相比，恢复时有什么风险？状态 TTL 的惰性清理，什么时候才真正释放存储空间？

### Q7. 任务凌晨挂了，怎么保证重启后不丢不重？

**问题：** 实时任务凌晨 2 点因为磁盘故障挂掉，运维重启后，你怎么保证数据不丢、窗口不重算不错算？Checkpoint 是怎么在崩溃后把「状态」和「消费位点」一起恢复的？

**期望加分项：**
- 能说清 Checkpoint 的机制：Barrier 对齐保证所有算子在同一逻辑时刻做一致快照，快照内容含算子状态与源端消费位点
- 能说清恢复流程：从最近一次成功快照恢复状态与位点，上游数据从该位点重放，状态回滚到快照时刻
- 能区分恢复语义：对状态是「恰好一次」，对下游输出是「at-least-once」——重放会重复输出，要靠下游幂等或事务输出兜底
- 能分析 Checkpoint 间隔与恢复时间的关系：间隔越大，恢复时要重放的数据越多、恢复越慢，也越省快照开销
- 提到恢复后的二次风险：数据积压追平、状态热加载再次触发反压

**减分项：**
- 认为 Checkpoint 只在崩溃时有用，说不清它的周期性与恢复流程
- 不知道 Barrier 对齐是什么，或说不清未对齐的算子快照为什么不一致
- 答不出「状态恰好一次、输出 at-least-once」的差异
- 没有恢复时间（RTO）与重放量的概念

**解答：**
先建立模型：Checkpoint 是周期性的（默认每 3~5 分钟）一致性快照，由 source 注入 Barrier 标记，每个算子收到全部输入分区的 Barrier 后才把「本地状态 + 位置信息」写入快照存储——这个「对齐」机制保证了所有算子快照在同一逻辑时刻，恢复后整个图回到一致的过去。崩溃恢复时：从最近一次成功快照恢复状态，消费位点回退到快照时刻，上游从该位点重新放数据。关键认知：恢复对「状态」是恰好一次（状态回滚了），但对「下游输出」是 at-least-once——重放期间相同的窗口会再次触发、结果会重复发出去，所以下游要么幂等（唯一键 upsert），要么走事务输出（见 Q8），否则数据会翻倍。工程上的权衡：Checkpoint 间隔决定两个指标——间隔越大，快照频率越低、性能越好，但恢复时要重放的数据越多（重放量 = 间隔 × 吞吐），恢复越慢，RTO 越差；所以要按业务可接受的恢复时间反推间隔，而不是用默认值。实践坑：快照存储（HDFS/对象存储）故障会连坐所有 Checkpoint 失败，要配置重试与保留最近 N 个快照；恢复后 Kafka lag 会先涨后追平，追平期间要防止打爆下游；任务恢复后状态全部冷启动，热数据查询可能再次触发反压，必要时先降速追平再放量。

**延伸考点：** Unaligned Checkpoint 什么时候用？它牺牲了什么？恢复后积压了几千万条数据，怎么控制追平节奏不拉爆下游？

### Q8. 端到端 exactly-once 是怎么做到的？代价是什么？

**问题：** 实时任务把聚合结果写入 Kafka 或 MySQL，业务要求「不重不丢」，你怎么做到端到端 exactly-once？Flink 的两阶段提交具体怎么工作？为此付出的代价是什么？

**期望加分项：**
- 能说清端到端 exactly-once = 引擎状态恰好一次 + 下游存储支持事务提交或幂等写入，缺一不可
- 能讲出 TwoPhaseCommitSinkFunction 的流程：Checkpoint 时 pre-commit → 全部算子确认后 commit → 失败 abort，前提是下游（Kafka 事务、JDBC 事务）支持事务
- 能区分两种路线：真正的事务性 exactly-once，与「at-least-once + 下游唯一键幂等」在机制上的不同（后者结果等价但靠幂等兜底）
- 能列出代价：事务生命周期拉长到 Checkpoint 间隔、Kafka 事务数据放大与延迟可见、吞吐下降、下游必须是支持事务的系统
- 能结合业务做取舍：很多公司对 MySQL 用「事务 or 幂等表」近似，真正的两阶段提交留给 Kafka 链路

**减分项：**
- 认为 exactly-once 是引擎开个开关就自动给的，说不清外部系统的前提
- 把「at-least-once + 幂等输出」与「两阶段提交」混为一谈，讲不出机制差异
- 答不出代价：提交延迟、吞吐下降、Kafka 事务放大
- 忽略两阶段提交要求下游「可提交可回滚」，无状态接口无法做到

**解答：**
先破一个误区：exactly-once 从来不是引擎单方面的事。引擎负责的是「状态与消费位点恰好一次」（Q7 的快照语义），要扩展到端到端，下游必须配合。Flink 的做法是两阶段提交（TwoPhaseCommitSinkFunction）：每次 Checkpoint 完成时，算子把写入动作在外部系统里 pre-commit（数据暂不可见）；等所有算子确认快照成功后统一 commit，数据才对外可见；任何一步失败则 abort 回滚。这就要求下游是有事务能力的系统——Kafka 事务（幂等 producer + 事务）可以，支持事务的 JDBC 可以，普通文件系统和无状态 HTTP 接口做不到。如果下游不支持事务，退而求其次用「at-least-once + 唯一键幂等」：重放产生的重复写，靠目标表唯一键（业务事件 id）upsert 掉，结果与 exactly-once 等价，但机制不同——面试时能把这两条路线分清楚，比只会背概念有价值。代价要讲透：两阶段提交的 commit 时机被 Checkpoint 周期绑架，事务保持时间 = Checkpoint 间隔，意味着下游数据的可见延迟被拉长；Kafka 端事务会放大 topic 数据（事务标识、未提交的不可见数据），吞吐明显下降；MySQL 单事务过大还会拖死锁与 binlog。所以实践上常见组合：实时写 Kafka 链路用真事务 exactly-once，写 MySQL/ES 用幂等键近似，核心链路配对账兜底（Q17）。取舍的本质是：用多少吞吐和延迟，换「不重不丢」的保证。

**延伸考点：** Flink 的 Kafka 事务 producer 和 Kafka 自带的幂等 producer（enable.idempotence）有什么区别？什么业务场景下你会主动放弃 exactly-once 换吞吐？

### Q9. 背压是怎么传导的？怎么定位和治理？

**问题：** 实时任务某个算子处理不过来，Flink 的背压是怎么一级级传导到上游甚至 Kafka 的？你怎么定位到底哪个算子是瓶颈？确认后怎么治理？

**期望加分项：**
- 能说清背压机制：下游消费慢 → 网络缓冲队列积满 → 上游算子阻塞 → 一路传导到 source，Flink 1.5+ 是 credit-based 流控（按可用信用拉取数据）
- 能说清定位流程：看 Job 图各算子反压状态（OK/LOW/HIGH）、单算子处理耗时、Kafka lag 与 Watermark 延迟，找到「积压的起点」
- 能给出治理手段并按优先级：瓶颈算子加并行度（先确认不是 key 分布问题）、慢算子拆分（维表查询改异步 IO + 缓存）、聚合场景局部预聚合降量、状态访问优化
- 理解背压是「保命」机制：无界缓冲才会 OOM，治理目标是削峰不是消灭背压
- 能对比 Spark Streaming 的背压（动态调整批处理间隔限速）与 Flink 背压的差异

**减分项：**
- 把背压当成网络问题或简单的「处理不过来」，说不清传导链路
- 只会回答「加资源」，没有定位流程，也不知道加在哪个算子
- 不知道反压时 Kafka lag 涨的起点在积压算子而不是 source
- 认为背压应该被消灭，没有「削峰保命」的认知

**解答：**
先建立机制认知：背压是下游消费速度跟不上时，由缓冲区逐级向上传导的阻塞——下游算子处理慢 → 中间网络缓冲（Flink 1.5+ 用 credit-based 流控，下游按可用信用数向上游拉数据）被填满 → 上游算子被阻塞在输出 → 传导到 source，最终 Kafka 消费被拖慢、lag 上涨。这是一条完整的传导链，所以定位要「从后往前找起点」：打开 Web UI 看各算子反压状态，HIGH 的就是瓶颈；再看该算子单条处理耗时（区分 CPU 慢、IO 慢还是等外部依赖）、数据是否倾斜（个别 key 打满单 Task）；反压起点之前的算子都是「被堵住」而不是「慢」。确认瓶颈后按优先级治理：如果是外部查询慢（维表、远程服务），改异步 IO + 本地缓存，这是立竿见影的；如果是计算密集，瓶颈算子加并行度（但 keyBy 分布不均时加并行度无效，先解决倾斜）；如果是聚合算子，做预聚合降数据量；如果是状态读 RocksDB 慢，加大块缓存或加内存索引。实践坑：反压时盲目给 source 加并行度毫无意义；反压其实是分布式流处理的内建保护——把缓冲改无界会直接 OOM，正确目标是让背压「局部化」（瓶颈只影响自身链路）而不是「消灭」；反压治理是持续动作，监控反压状态与 Kafka lag 的变化趋势，比看瞬时值更有用。

**延伸考点：** Spark Streaming 的背压是「动态调整批处理间隔」限速，Flink 是「缓冲积压向上传导」，两者本质区别是什么？Kafka lag 涨了但任务没有反压，问题可能出在哪？

### Q10. 订单流和支付流延迟不一，join 怎么不错不漏？

**问题：** 你要把订单流和支付流 join 起来算支付转化率，但支付数据可能晚到 10 分钟，两边延迟完全不一样。怎么设计 join 才能结果准确、不错不漏？区间 join、外键 join、窗口 join 各用在什么场景？

**期望加分项：**
- 能区分三种 join 的本质：interval join（双流按时间区间匹配，依赖 Watermark）、lookup/外键 join（一路主数据、另一路按 key 查询补齐）、窗口 join（同窗口内关联）
- 能说出 interval join 的适用前提：两个流的延迟差异有界且可量化，边界要按两侧延迟分布分别设定
- 能指出晚到时间不可控时（如 T+1 到账）interval join 失效，要改成「先落主数据，到达后外键补全」
- 能给出 SQL 示例：`WHERE o.time BETWEEN p.time - INTERVAL '10' MINUTE AND p.time + INTERVAL '5' MINUTE`
- 提到未匹配数据必须有兜底（侧输出 + 对账补 join），以及状态缓冲量与流量的成本关系

**减分项：**
- 只会说「两个流 join 在一起」，讲不出三种 join 的差异与适用条件
- 不知道 interval join 依赖两个流都对齐事件时间和 Watermark
- 答不出延迟不可控流怎么处理（没有外键/明细落库方案）
- 忽略超界未匹配数据的丢失问题

**解答：**
先判断两个流的时序关系再选 join 方式。如果延迟差异有界（支付通常晚于订单 10 分钟内到达），用 interval join：设定上下界（`o.time BETWEEN p.time - 10min AND p.time + 5min`），引擎按 Watermark 缓冲两侧数据，落在此区间内的才匹配。边界怎么定：分别统计「支付时间 − 订单时间」的延迟分布，取 P95/P99 作为上界，而不是拍脑袋；边界设小了漏匹配、设大了状态和延迟都涨。如果晚到时间不可控（跨行转账 T+1 到账、离线补录），interval join 直接失效——正确做法是「主数据先落地」：订单流直接输出并入库，支付到达时通过外键查询补齐（lookup join），或把两条流都落到明细层由下游宽表合并，保证「先到的先展示、后到的再补全」。外键 join 适合「一路是主业务流、另一路是维度/事实补充」的场景。实践坑：interval join 的状态缓冲量与流量成正比，大流量双流 join 要关注 RocksDB 压力与状态清理；两侧 Watermark 进度不一致时，慢的一侧决定 join 的触发速度，整条链路的延迟会被拖到最慢一侧；inner join 下未匹配的数据默认丢弃，一定要开侧输出把超界未匹配数据落死信，定期对账补 join（Q17），否则转化率悄悄算低了你都不知道。

**延伸考点：** 两个流的 Watermark 一个走得很快一个很慢，interval join 的结果会不会一起变慢？未匹配的订单你用什么机制事后补回 join 结果？

### Q13. 实时 TopN 榜单怎么算才不慢？

**问题：** 实时榜单要输出「每分钟销量 Top100 商品」，商品几百万个。直接全量排序肯定不行，你的方案是什么？窗口内 TopN 和全局 TopN 有什么区别，各自怎么算？

- 能给出增量思路：小顶堆（size=k）维护 TopN，新元素比堆顶大才替换，复杂度 O(n log k) 而非全排序 O(n log n)
- 能说出 Flink SQL 用 `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY cnt DESC)` 的 TopN 语法，DataStream 用 PriorityQueue 状态
- 能区分窗口内 TopN 与全局 TopN：前者状态随窗口回收，后者状态无限增长，需要近似（Count-Min Sketch 估算 + 全局堆）或定时全量重算
- 能指出滑动窗口 TopN 的重算放大，以及热点商品 key 倾斜对聚合算子的影响（联动 Q5）
- 提到 TopN 边界问题：并列、阈值波动时展示口径要明确

**减分项：**
- 把 TopN 答成「group by + order by + limit 全排序」，没有增量概念
- 分不清窗口内 TopN 与全局 TopN 的状态代价差异
- 不知道 TopN 常与聚合倾斜、滑窗放大耦合
- 忽略实时榜单与离线榜单口径不一致的问题

**解答：**
先明确 TopN 是「聚合后的取前 K」，正确姿势是增量维护而不是全量排序：每个商品先聚合出计数，再维护一个容量 k 的小顶堆，新计数大于堆顶才入堆，复杂度 O(n log k)，k=100 时基本是 O(n)。Flink SQL 直接用 `ROW_NUMBER()` OVER 窗口语法（内部就是增量维护，且配 `ORDER BY cnt DESC`），DataStream API 里用 PriorityQueue 存状态。难点在语义分层：窗口内 TopN（每 5 分钟 Top100）状态随窗口关闭回收，好做；全局 TopN（跨全天累计 Top100）状态无限增长，实时精确算不现实，工程上用两类近似：一是 Count-Min Sketch 估算计数 + 全局堆（牺牲精度换内存），二是定期（如每分钟）从聚合结果全量重算一次 Top100（分钟级榜单够用）。实践坑：滑动窗口的 TopN 每次滑动重算，放大倍数与窗口重叠一致，先滚动预聚合再滑窗可缓解；TopN 的计算源头是聚合算子，热门商品集中在少数 key 上会先打爆聚合（倾斜，见 Q5），要先做加盐预聚合；榜单边界（第 99/100 名并列）的展示口径要与业务约定；实时 TopN 用近似或滑窗语义，和离线精确榜单对不上是常态，对账时要先对齐口径（窗口归属、去重方式）再谈差异。

**延伸考点：** 实时 TopN 和离线 T+1 榜单对不上，你会按什么顺序排查口径差异？TopN 的状态在后端怎么管理，窗口结束真的会立刻释放吗？

### Q14. 流量暴涨 10 倍，实时任务积压到 30 分钟，先做什么？

**问题：** 促销活动开始，实时任务流量暴涨 10 倍，Kafka lag 从几秒涨到几千万，数据到报表的延迟从 5 秒变成 30 分钟。你怎么应急处理？先做什么后做什么？积压的几十亿条数据怎么拉平而不把下游打爆？

**期望加分项：**
- 能给出分步应急：先确认是瞬时尖峰还是持续暴涨，定位反压瓶颈，再决定扩容点
- 知道扩容加在瓶颈算子上（先看是否 key 倾斜），而不是盲目给 source 加并行度
- 能给出临时止血手段：非核心算子降级/跳过、临时关大状态窗口、调大并行度、放宽异步 IO 限流
- 能说出积压拉平要控制节奏：一次性放行会打爆下游（DB/外部系统），要限速渐进追平并同步扩容下游
- 能区分「追平 lag」与「恢复实时性」是两个阶段，期间可以临时牺牲窗口准确性

**减分项：**
- 直接重启任务（从 checkpoint 恢复后积压重放，等于没解决，还丢进度）
- 只加资源不定位根因，或加错位置
- 忽略拉平积压时对下游的冲击（一次性放行打爆 DB/ES）
- 没有事后复盘：容量评估、热点预案、削峰设计

**解答：**
先定性：看反压状态和消费位点，判断是「瞬时尖峰」（促销开场几分钟）还是「持续暴涨」（流量结构性变高）。应急三步：第一步，确认瓶颈——如果算子是瓶颈（反压 HIGH），先确认是不是热点 key 倾斜（Q5），是倾斜就拆 key，不是就扩瓶颈算子并行度并加 TM 资源；如果瓶颈在外部依赖（维表查询），先改异步 IO 或降级为本地缓存，这是最快的止血。第二步，拉平积压要有节奏：几十亿条一次性放行，下游 DB、ES、外部接口全部被打爆，积压就从 Kafka 转移到下游——正确做法是限速追平（控制消费速率或逐批放量），同时同步扩容下游写入能力；追平期间可以临时关闭非核心算子、放宽 checkpoint 间隔降低快照开销。第三步，恢复实时性后做容量复盘：按峰值吞吐重新评估并行度与资源，给任务留 30%~50% 冗余，为大促场景设计削峰预案（Kafka 本身是缓冲，但要限制它的积压深度，避免无界背压）。实践坑：紧急扩容必须加在瓶颈算子而非 source；促销期间不要动 Watermark 与窗口语义，否则恢复后结果口径漂移，比慢一点更严重；重启任务会从最近 checkpoint 重放积压数据，问题原样回来，所以「重启」不是应急手段，只有「扩容 + 限速追平」才是。

**延伸考点：** 追平积压时怎么动态控制消费速率？什么指标能判断「追平过快」正在伤下游？

### Q15. 任务重启期间的数据缺口，怎么补才不重不漏？

**问题：** 实时任务因上游故障停了一晚上，重启后这段时间的数据缺口怎么补？补数时怎么保证和实时链路的结果不重复、不冲突？哪些情况其实根本不需要手工补数？

**期望加分项：**
- 能先区分数据在哪：数据已在 Kafka（保留期内）→ 重启后按 checkpoint 位点重放即可，不需要手工补数；数据没进 Kafka 或已过期 → 才需要补数
- 能说出补数的主流做法：离线任务按事件时间区间重算缺口，写入下游与实时结果合并
- 能给出幂等合并方案：下游表唯一键（业务事件 id）upsert，或补数窗口与实时窗口刻意错开
- 能提到对账脚本是补数的最后防线：源端总量 vs 目标端总量校验
- 能指出「把对账做成常态化机制」优于每次都应急补数

**减分项：**
- 认为任务重启就必须手工补数，不知道 checkpoint 位点重放机制
- 补数时不指定事件时间范围，把正常时段数据也算一遍
- 补数与实时并发写同表又无唯一键，导致数据翻倍
- 没有对账校验，补完数不知对错

**解答：**
先回答「要不要补」：如果数据一直在 Kafka 里（保留期够长），重启后任务从最近一次成功 checkpoint 恢复，消费位点回退、数据自动重放，根本不需要手工补数——这依赖 checkpoint 有效（Q7）和保留期覆盖停摆时长。只有两种情况才真正需要补数：一是停摆时间超过 Kafka 保留期，部分数据被物理删除；二是数据压根没进 Kafka（上游故障没发出来）。补数的标准做法：离线/批任务按「事件时间区间」重算缺口窗口，结果写入下游，与实时结果合并。合并的难点是幂等：实时任务恢复后还会把缺口尾部的数据再算一遍（位点回退重放），补数任务也在写同一批窗口，两边并发写同一张表，没有唯一键就会翻倍——正确做法是下游表加业务唯一键（订单 id、事件 id）做 upsert，重复写自动覆盖；或者让补数窗口与实时窗口在时间上错开，再用对账脚本确认重叠区间的数据只存在一份。实践坑：补数要显式指定事件时间范围，别默认「今天全量重算」把正常数据也重写一遍（虽然幂等表能兜住，但白白消耗资源、放大窗口期冲突概率）；补数任务的并行度与写下游的速率要控制，避免和恢复中的实时任务抢资源；补数完成后必须跑对账（Q17 的条数/金额/关键指标比对）作为验收，否则「补了但补错」比不补更危险。更优的长期方案是把「对账 + 自动回补」沉淀为平台能力，而不是每次故障都靠人工脚本应急。

**延伸考点：** Kafka 数据被误删或过期，你怎么保证可追溯和可恢复？补数窗口和实时重放窗口重叠的部分，幂等键怎么设计才有效？

### Q16. 流批一体做了，结果还是对不上，问题出在哪？

**问题：** 你们推行流批一体，同一份 SQL 既跑实时又跑离线，但两边的指标结果经常对不上。你会按什么顺序排查？流批一体的边界到底在哪，是不是所有场景都适合「一套代码两跑」？

**期望加分项：**
- 能点破流批一体的本质：一套逻辑（SQL 语义统一），两个执行引擎，收益是口径统一与开发效率，而不是「结果必然一致」
- 能按优先级列出对不上的根因：时间语义（处理时间 vs 事件时间）、去重口径（HLL 近似 vs 精确）、维表快照时机、窗口边界与迟到数据
- 能给出统一口径的做法：两边都用事件时间、去重方式约定误差或统一为精确、维表保留历史版本
- 能指出流批一体的边界：大状态、强一致、精确去重等场景实时不划算，对账类指标更适合离线兜底
- 提到 Flink 按 execution.runtime-mode 切换批/流模式，但批模式没有 Watermark 与状态语义，同一 SQL 的窗口实现不同，仍需对账

**减分项：**
- 把流批一体当银弹，认为「SQL 相同结果必然相同」
- 答不出对不上的具体根因，只会说「肯定有 bug」
- 忽略实时近似算子（HLL、BloomFilter）与离线精确计算的口径差异
- 没有「对账是流批一体必备配套」的意识

**解答：**
先纠正一个预期：流批一体的目标是一套逻辑、统一口径、减少两套代码，不等于两边结果天然相等。对不上了，按这个顺序排查：第一步查时间语义——实时任务如果用了处理时间（或窗口边界由到达时刻决定），离线按事件时间算必然对不上，统一为事件时间后大部分问题消失；第二步查去重与近似——实时 UV 用 HLL（误差约 0.8%）而离线 count distinct 是精确值，这个差是设计内的，要对业务约定误差容忍，或者核心指标实时也改精确去重（代价是状态成本，见 Q11）；第三步查维表——离线 join 的是当日快照维表，实时 join 的是当前时刻的值，回看历史数据时两者必然不同，维表要保留历史版本或约定「统一用当日最终快照」；第四步查迟到与窗口——实时窗口在 Watermark 推进后关闭，迟到数据默认丢弃，离线能看到全量，实时要开 allowedLateness 或侧输出回补后再对比。关于「一套代码两跑」：Flink 1.12 起提出统一批流、`execution.runtime-mode` 可切换批/流模式，但批模式没有 Watermark 推进和状态增量语义，同一份 SQL 在批/流下的窗口触发、join 缓存策略实现不同，所以「逻辑统一」不等于「行为统一」。流批一体的边界要诚实：实时承担趋势与秒级响应，离线承担精确与历史重算，关键指标以离线为准、实时对齐口径，中间用对账衔接——这才是流批一体的正确落地形态。

**延伸考点：** 同一份 SQL 在 Flink 批模式和流模式下，窗口聚合和 join 的行为有哪些具体差异？你们流批一体最终保留了哪几套代码、哪些指标允许误差？

### Q17. 实时链路上下游怎么对账，才不贵又不误报？

**问题：** 数据链路是「业务源 → Kafka → 实时任务 → 目标库/报表」，你怎么证明上下游数据是一致的？对账怎么做成本才可控？为什么实时对账特别容易误报，怎么处理？

**期望加分项：**
- 能分层设计对账：链路层（Kafka lag、消费位点、死信队列量）自动告警；数据层（条数、金额、去重 UV）定时比对；处置层（自动重跑/人工介入流程）
- 能说明实时对账误报的根源：迟到数据与窗口未关闭导致的「暂时不一致」，对账必须容忍时间差、按最终一致窗口比对
- 能给出一致性定义：消息级对账用唯一业务 id 幂等比对；指标级对账用「同一时间语义下汇总比对」
- 成本控制：总量 + 抽样 + 关键指标组合，而不是全量每天跑
- 对账结果要有处置闭环：差异告警后定位到环节（源端缺失 / 传输丢 / 解析丢 / 输出重复）

**减分项：**
- 只说「有对账」，讲不清对什么、多久对、差异怎么处置
- 把「消息条数相等」当全部对账，忽略语义正确性
- 不知道实时「最终一致」特性，对账脚本在迟到窗口内跑必然误报
- 对账全量每天跑，成本不可控

**解答：**
先定义「一致」再谈怎么对，实时对账最核心的心智是：实时数据是「最终一致」的，对账窗口必须覆盖迟到容忍。分层设计：第一层链路对账（实时、自动化）——Kafka lag、消费位点推进、解析失败率、死信队列积压量，这些指标超阈值直接告警，它们能发现「链路断了」但证明不了数据正确；第二层数据对账（定时、分钟~小时级）——消息级对账：源端按唯一业务 id 抽样/比对目标端是否存在且内容一致（幂等表天然支持这个比对）；指标级对账：把实时任务输出表与离线 T+1 重算表比对金额、条数、去重 UV，比对时间选在事件时间窗口关闭且水位线推进之后，并允许容忍阈值（如金额差 < 0.1% 或条数差在迟到范围内），超过阈值才告警——这一步解决「必然误报」问题；第三层处置闭环：告警后能定位到环节，源端缺数据找上游、传输丢查采集端、解析丢查死信队列、重复写查幂等键。成本控制：全量逐条比对最贵，用「总量 + 抽样 + 关键指标」组合——每日全量金额、每小时抽样明细、关键业务 id 全量幂等比对，成本与覆盖度平衡。实践坑：对账任务要和业务表做 IO/资源隔离，别把对账查询打在主库上；对账差异的处置要有 SLA（多久内必须处理），否则对账平台会沦为一堆没人看的告警；实时与离线的对账本质是「以离线为准」，所以离线口径必须先稳定，否则对账会变成「两边一起错」。

**延伸考点：** 对账发现金额差 0.5%，怎么快速定位丢在哪个环节？对账的容忍阈值怎么定，才既能拦住真问题又不天天误报？

### Q18. 一个日处理 10 亿条的任务，并行度和内存怎么定？

**问题：** 一个实时任务每天要处理 10 亿条数据、维护几十 GB 状态。上线前你怎么规划并行度、内存和 Checkpoint 间隔？估算依据是什么？上线后靠什么验证？

**期望加分项：**
- 能给出量化估算链路：吞吐（含峰值波峰系数）→ 单条处理成本 → CPU；状态规模 × 放大系数 → 内存；重放量 = Checkpoint 间隔 × 吞吐 → 恢复时间（RTO）
- 知道并行度与 Kafka 分区数联动（分区是消费并行度上限），key 分布均匀时取分区数整数倍
- 能说清内存规划的分层：堆内存（状态、算子缓冲）与托管内存（RocksDB 缓存）统筹，状态大时走 RocksDB + 增量 Checkpoint
- 能按 RTO 反推 Checkpoint 间隔，并指出间隔与吞吐、恢复耗时的关系
- 上线后靠反压状态、Kafka lag、Checkpoint 耗时、GC 指标验证并留 30%~50% 容量冗余

**减分项：**
- 并行度、内存、Checkpoint 间隔全部拍脑袋，给不出推导
- 不知道并行度与 Kafka 分区数的关系，或认为并行度越大越好
- 忽略峰值系数与容量冗余（按均值规划必然被峰值打爆）
- 上线后无监控验证闭环

**解答：**
资源规划的本质是「从吞吐和状态反推资源」，三个维度分别算。CPU：10 亿条/天按 1.2 万条/秒均值、3 倍波峰即峰值约 3.6 万条/秒；若单条处理成本（反序列化 + 状态读写 + 序列化）约 0.1ms，单核约 1 万条/秒，考虑 GC 与调度开销放大 2~3 倍，需要 20~40 核。内存：堆内存 ≈ 算子状态 + 窗口缓冲 + 网络缓冲；几十 GB 状态不要硬塞堆，走 RocksDB 状态后端并把托管内存（块缓存）单独规划，堆内存给足 JVM 开销即可；同时状态必须配 TTL（Q6）防止只增不减。并行度：与 Kafka 分区数联动——消费并行度不能超过分区数，key 分布均匀时取分区数的整数倍即可，过多并行度只会放大 Barrier 对齐与网络开销。Checkpoint 间隔：由 RTO 反推——重放量 = 间隔 × 吞吐，间隔 5 分钟、3.6 万条/秒峰值就要重放 1000 万条，恢复耗时 = 状态加载 + 重放时间，业务能接受的恢复时间决定间隔上限；间隔也不是越小越好，快照太频繁会拖慢吞吐。稳定性设计要一起做：外部依赖全部配超时重试；告警覆盖 lag、反压、Checkpoint 失败率、解析失败率；容量留 30%~50% 冗余应对峰值。实践坑：估算只是起点，上线前一定要用回放真实数据压测校准，估算公式的系数（单条耗时、GC 开销）只有压测才能确定；发布用灰度（新老并行、切流量），避免全量切换失败直接打爆线上。

**延伸考点：** Checkpoint 间隔从 5 分钟调到 1 分钟，对吞吐和恢复各有什么影响？加 10 个并行度能扛多少流量，这个账怎么算？

### Q19. 上游改了日志格式，实时任务怎么保证不丢数据？

**问题：** 上游业务偷偷改了日志格式（字段重命名、类型变化、嵌套结构调整），你的实时任务解析开始报错、数据大量丢弃。怎么保证这段时间数据不丢？解析失败的数据去哪了？怎么防止下次再被「偷袭」？

**期望加分项：**
- 核心原则：解析失败必须「隔离而非中断」——异常数据进侧输出/死信队列，主链路保活，而不是抛异常挂任务
- 能给出具体实现：解析算子 catch 异常，失败数据 + 失败原因 + 原始 payload 写入死信（Kafka 独立 topic 或对象存储），并监控死信量与解析失败率告警
- 有 schema 演进意识：解析器版本化、新旧格式兼容解析（灰度期双解析）、未知字段忽略、字段缺失给默认值并告警
- 故障处置流程：先回滚到旧解析器恢复主链路，再分析新格式、灰度放量，最后从死信回放补数（幂等）
- 与上游约定接口契约：变更评审、双写灰度、回滚方案，而不是事后补救

**减分项：**
- 解析失败直接抛异常导致任务挂掉，或静默丢弃数据
- 没有失败数据隔离（死信）与失败率监控告警
- 只修自己的解析器，不推动上游变更流程，下次还会被偷袭
- 死信队列没有消费监控，隔离变成「静默丢数据」

**解答：**
先立原则：解析是实时链路最容易「被打破」的环节，所以它的默认行为必须是「隔离，不是中断」。实现上：解析算子对每条数据 try-catch，成功的走主链路，失败的连同失败原因、原始 payload 一起打到侧输出流，写入死信队列（独立的 Kafka topic 或对象存储），同时埋点记录解析失败率——这个失败率是实时任务最重要的健康指标之一，超阈值必须告警。防再次被偷袭要靠 schema 治理：解析器按版本管理（字段名、类型、结构都纳入版本），升级时新旧版本并存跑 1~2 周灰度（同一份数据新旧解析器各算一遍做比对，或先兼容解析），确认无误再下线旧版本；解析本身要宽容——未知字段忽略、必需字段缺失给默认值并告警、类型不匹配尝试宽松转换，而不是直接抛异常。故障处置的顺序要讲清：发现失败率飙升 → 立即回滚到旧解析器恢复主链路（止血优先）→ 拿到死信里的原始数据离线分析新格式 → 开发新解析器灰度放量 → 确认稳定后从死信回放补数（回放要幂等）。实践坑：死信队列必须有独立的消费监控和 TTL 管理，否则「隔离」会退化成「静默丢弃」；只修自己不改上游，下个季度还会再挂一次——要与上游约定接口契约（schema registry、变更评审、双写灰度、一键回滚），把「防偷袭」变成流程而不是祈祷。

**延伸考点：** 新增一个字段算不算不兼容变更？你要求上游改格式前提供什么，才能保证实时链路零中断？

### Q20. 从零搭一套支撑核心业务的实时计算体系，怎么设计？

**问题：** 公司要做实时大屏、实时风控、实时报表三条链路，让你从零设计整个实时计算体系（分层架构、口径管理、稳定性保障、任务治理）。你怎么设计？如果只能承诺三条最重要的原则，是哪三条？

**期望加分项：**
- 有分层意识：ODS（原始明细）→ DWD（明细宽表：清洗、补维表、统一时间语义）→ DWS（主题汇总）→ ADS（应用），每层落 Kafka/OLAP，层间解耦，单任务故障不波及其他层
- 有口径统一机制：指标字典 + SQL 规范 + 维表统一管理，实时与离线共用定义，配套对账
- 有稳定性体系：监控告警（lag、反压、Checkpoint 失败、解析失败率、死信量）、容灾（自动重启、状态冗余）、发布规范（灰度、回滚）、容量冗余
- 能划清实时与离线的职责边界：精确对账、历史重算交给离线，实时不硬扛一切
- 回答有取舍与优先级，能说出「先保什么、后做什么」，而不是罗列一堆名词

**减分项：**
- 没有分层概念，任务之间毫无隔离
- 口径、监控、对账、发布规范只字不提
- 方案没有优先级，「什么都重要」等于「什么都不重要」
- 不考虑成本与运维负担（实时任务宁少勿滥）

**解答：**
开放性设计题看的是架构思维和取舍，标准答案不存在，但有几个必答点。第一，分层：借鉴离线数仓按实时约束裁剪——ODS 层是 Kafka 里的原始明细（尽量贴近源格式，清洗后入 DWD）；DWD 做明细宽表（统一解析、补齐维表、统一时间语义与字段规范）；DWS 做主题汇总（分钟/小时级指标）；ADS 直接服务大屏、报表、风控。每层各自落 Kafka 或 OLAP（ClickHouse/Doris），层与层之间解耦——DWS 挂了不影响 ODS 继续消费，这是实时体系稳定性的根基。第二，口径：所有指标要有字典定义（计算逻辑、时间语义、去重方式），实时与离线必须共用这套定义，维表统一管理，否则每条链路都会长出「自己的口径」，对账无从谈起。第三，稳定性：监控告警覆盖 lag、反压、Checkpoint 失败率、解析失败率、死信积压；容灾上任务自动重启、快照冗余；发布走灰度与回滚；容量留 30%~50% 冗余。最后是边界与取舍：实时不解决所有问题——精确对账、历史重算、复杂口径校验交给离线，实时只承担秒级响应与趋势预警；实时任务每多一个都是长期运维负担，宁少勿滥。如果只让说三条原则，我的答案是：数据不丢是底线（失败隔离 + 对账兜底）、口径统一是灵魂（一套语义，实时离线共用）、稳定性优先于新功能（先止血再优化，发布永远可回滚）。

**延伸考点：** 预算有限只能保留 3 个实时任务，你保留哪 3 个、砍掉哪些，依据是什么？实时数仓和离线数仓的 DWD 层为什么建议分开建设？
