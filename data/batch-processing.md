# 数据 · 批处理（面试题库）

本文件聚焦批处理与离线计算的工程实践能力考察，覆盖离线任务设计（全量/增量、分区策略）、调度依赖与补偿、任务幂等与重跑、数据质量校验与失败阻断、性能调优（数据倾斜、小文件、资源与队列管理）、批流口径一致性、Schema 变更兼容、增量 merge 性能及湖仓一体演进等通用主题。所有问题均以真实工程场景切入，考察候选人的问题定位能力、方案取舍与线上实践佐证，而非概念背诵。难度自 Q1 至 Q20 循序渐进，从实践基础逐步过渡到中阶调优与架构级开放性思考题。

### Q1. 新接入一张大表，全量、增量怎么设计，切换时如何保证不丢不重？

**问题：** 公司要把业务库的订单表（存量 3 亿行、每天新增几十万行）接入数仓，先跑全量还是直接跑增量？增量水位怎么选？从全量切到增量的那一刻怎么保证不丢数据、不重复？

**期望加分项：**
- 先回答"增量是什么"：源表只有 insert 还是有 update/delete，决定增量同步用自增 id/时间字段拉取还是 binlog/CDC
- 能给出全量→增量的衔接方案：全量先落到临时表或新分区，对账通过后再原子切换，或全量与增量重叠跑 1-2 天做行数比对
- 能说清 max(id) 与 max(update_time) 作为水位各自的坑：并发提交下 max(id) 可能漏数据、时间字段回拨或批量刷数导致水位跳变
- 主动提主键/唯一键是 upsert 的前提，无主键表如何处理
- 考虑时区、变更老数据（update 历史订单）这类边界

**减分项：**
- 只会说"先全量再增量"，说不清切换时点的对账、回退与灰度
- 忽略 update 老数据会破坏"增量只取新增"的假设
- 不知道增量同步必须有主键才能做 upsert 去重
- 答不出水位推进失败（漏数据）时如何发现与补救

**解答：**
先做判断：全量打底、增量续跑是通用思路，难点在"衔接"而非"启动"。第一步确认源表特性：只有插入且时间单调，可以用 `max(update_time)` 拉增量，但批量刷数、回拨时钟会让水位失真，稳妥做法是水位向前留一个重叠窗口（如水位取前一天的 00:00），跑完按主键 upsert 去重；若有 update/delete，用自增 id + 时间戳拉取必然丢更新，必须上 binlog/CDC。第二步执行全量：一次 SELECT 全表导入临时表或独立首日分区，同时启动增量任务并记录起始水位。第三步衔接对账：全量完成后，把增量数据回补进全量结果，按业务唯一键 count + sum 关键金额字段与源库核对；通过后原子切换（如 `INSERT OVERWRITE` 目标分区或切换视图），并保留 1-2 天双轨对账。实践中的坑：切换窗口内源库若发生跨水位更新（如凌晨补录前一天订单），增量会漏，所以对账期要覆盖业务峰值；无主键的表要提前与业务约定一个"业务上唯一"的组合键，否则只能全量重刷；时区统一按东八区还是 UTC 要在建表时定死，否则按天分区会错位。

**延伸考点：** 如果源表存在"先删后插"或软删除，增量链路怎么保证和全量结果最终一致？CDC 的 offset 丢了怎么重建？

### Q2. 重跑昨天的任务，报表数据和首次跑出来的不一样，怎么排查？

**问题：** 昨天有个任务失败了，今早补跑重跑了一遍，结果报表数据和昨天第一次跑出来的对不上，业务来投诉，你怎么排查？

**期望加分项：**
- 先区分两种根因再动手：源数据变了（上游回刷/数据订正）还是任务本身不幂等
- 能按优先级自查：目标表是 INSERT OVERWRITE 还是 INSERT INTO；任务里用的是显式分区还是动态日期；是否有随机/当前时间等非确定性因素
- 会设计对比实验：用相同的输入（固定 dt 分区）分别跑两次，或对源表做 count/sum 快照比对
- 主动查重跑期间是否有并发实例互相覆盖（两个任务同时写同一分区）
- 能说出重跑前的对账手段（先记录基线指标再重跑）

**减分项：**
- 直接怀疑"代码有 bug"，不先检查源数据是否被回刷
- 不知道 INSERT OVERWRITE 只覆盖分区、INSERT INTO 会累积的语义区别
- 忽略任务里 join 了实时表、用了 now()/rand()/uuid() 等非确定性因素
- 答不出"重跑必须先锁定输入再比输出"的排查方法

**解答：**
先说思路：重跑结果不同，99% 是"输入不同"或"写入不幂等"，按这个顺序查。第一步，确认输入：查上游表在两次运行之间有没有被订正或回刷——生产上最常见的是业务改数据、上游任务补跑导致源表变了；手段是比对两次运行日志里读到的源分区快照，或对源表做 `count`、`sum(金额)` 留基线。第二步，确认写入语义：`INSERT OVERWRITE` 按分区覆盖，重跑只影响目标分区，安全；`INSERT INTO` 每次追加，重跑一次就翻一倍，这是重跑后"数据变大"的典型原因；动态分区 + overwrite 组合下只覆盖"本次写入的分区"，残留旧分区会漏。第三步，排查任务内部的非确定性：join 实时结果表、`now()` 参与分区/过滤、`rand()` 参与抽样，都会让两次输出不同；应改为用显式业务日期（如参数 `dt`）驱动，保证"同输入必同输出"。实践中的坑：重跑和调度自动重试若并发执行同一任务，两个实例互相写同一分区，结果取决于执行顺序且无一致性，需要任务锁或幂等写入约束；排查时先记录基线（行数、指标 sum、样例数据指纹）再动手，否则改完无法对账。

**延伸考点：** 如果源表本身不可重放（比如依赖外部 API），重跑如何保证一致性？你如何给任务建立"输入指纹"以自动发现输入变化？

### Q3. 上游数据延迟到 6 点才到，整套依赖任务怎么处置？

**问题：** 离线链路平时凌晨 3 点跑完，今天上游数据延迟到早上 6 点才到位，后面十几个依赖任务怎么办？等、跳过还是降级？怎么避免频繁发生时的级联故障？

**期望加分项：**
- 先分清场景：延迟是偶发还是常态、受影响任务的 SLA 与业务影响面，再定"等/跳/降级/补跑"
- 能指出依赖应该建在"数据就绪"而非"时间"或"任务成功"上：上游任务成功 ≠ 数据可用（重试成功、空数据也算成功）
- 能说清跳过与补跑的配套：跳过要显式标记（避免脏数据进报表）、补跑要幂等且按血缘顺序重跑
- 有延迟预警机制：SLA 监控提前告警而不是事后补救
- 考虑级联：依赖链深时如何避免整套链路雪崩（如非关键路径可先放行降级版）

**减分项：**
- 只会说"等数据到了再跑"，没有跳过/降级的预案
- 把任务成功当数据就绪，忽略"成功但数据为空/不完整"的场景
- 补跑时直接重跑全链路，不考虑幂等和重复消费
- 没有延迟量化依据（等多久、SLA 容忍度），全靠拍脑袋

**解答：**
先定原则：能等则等、不能等则显式跳过并记录、事后补跑，降级只用于高 SLA 场景。第一步，把依赖从"任务状态依赖"改为"数据就绪依赖"：调度器不要依赖上游任务成功事件，而要检查分区文件/表就绪（如目标分区存在且行数达标），否则上游重试成功但数据没写全，下游照样用错数据。第二步，按 SLA 分级处置：核心报表链路，数据 6 点到位就自动触发下游（数据驱动天然完成"等"），但要评估整体延迟是否超 SLA；非核心或 T+2 的链路，配置跳过策略并写入调度记录，数据到位后按血缘顺序补跑；对高 SLA 场景准备降级预案——用前一版本或临时值发版并显式打标，次日修正。第三步，防御性建设：为每个关键链路配置延迟预警（预计 3 点完成，4 点未完成即告警），延迟预警比失败告警早数小时；配置"超时放弃"阈值避免无脑等；补跑工具要幂等（按分区覆盖）并按依赖顺序自动触发。实践中的坑：依赖链深时一个上游抖动会级联延迟，优先优化源头 SLA 或冗余链路；"跳过"最容易漏——跳过的任务要在调度系统里有明确状态和负责人，否则补跑清单永远不全。

**延伸考点：** 数据就绪检查本身要查什么（文件存在、大小、行数）？检查失败时怎么和"任务失败"的告警体系区分，避免告警风暴？

### Q4. 跑批完成后行数比预期少 10 万，怎么定位？平时怎么做数据质量校验与阻断？

**问题：** 一个跑批任务正常完成，但输出的行数和业务预期差了 10 万，怎么定位是哪一层丢的数据？平时应该在哪几个环节做校验、校验失败时怎么阻断脏数据进入下游？

**期望加分项：**
- 能给出"分层校验"思路：源层、中间层、结果层各查什么（行数、主键唯一、非空、枚举、金额汇总）
- 定位手法：与源表 count 逐层比对找丢失层，再按日期/渠道等维度下钻定位丢失数据特征
- 能说出三类核心校验：完整性（行数对比）、唯一性（主键重复）、有效性（空值率、负金额、非法枚举）
- 校验失败后的阻断机制：校验任务失败即任务失败不发版，避免脏数据流入报表
- 知道校验的成本控制：count 大表要估算、校验独立成任务而不是写死在业务 SQL 里

**减分项：**
- 只会说"加个 count 校验"，说不出校验哪几类指标、在哪一层做
- 不知道"行数一致 ≠ 内容一致"，缺少金额汇总、distinct 等内容级校验
- 校验失败后继续发版，或把校验和业务任务耦合在一起
- 无法解释校验的误报（阈值拍脑袋）与漏报问题

**解答：**
定位思路是"沿血缘逐层比对"：先对比源表与最终输出之间的每一层，用 `count` 和关键金额 `sum` 双指标缩小到某一层；再在该层按维度（日期、渠道、类型）下钻，找出丢失行的特征，常见根因有：join 因连接键不匹配丢数据（如订单 join 商品，商品维度缺失）、过滤条件过严、分区缺失（上游某天没跑）、去重误删。校验体系建设分三层：源层校验上游数据是否齐备（分区存在、行数、主键唯一性）；中间层校验加工后维度/指标合理性（空值率、枚举值分布、金额非负）；结果层校验下游消费所需的口径（行数容差、与业务对账）。每类校验要带阈值而非硬编码 0 容差，比如行数波动超过 5% 或主键重复超过 0.1% 才失败，避免因上游正常波动误杀。阻断机制：把校验做成独立任务挂在业务任务之后，失败即令下游任务不触发（失败标记），或让发布流水线卡住，而不是只发告警"人肉拦截"——靠人看告警必然有漏。实践中的坑：count 大表本身慢，优先用分区统计信息或抽样；校验任务的 SQL 里不要写死日期；行数通过但内容错（比如 join 错了维度）这类"对不上的对"，需要 sum/distinct/抽查样例兜底，这是最容易漏的一环。

**延伸考点：** 校验阈值怎么定才不误杀也不漏报（比如促销日行数暴涨 10 倍是正常的）？校验失败后的自动恢复（重跑校验通过后自动放行）怎么设计？

### Q5. 夜间跑批失败没人发现，第二天报表空白，重试与告警怎么设计？

**问题：** 夜间跑批一个任务失败后没有被及时发现，第二天早上报表空白、业务炸了。失败重试和告警体系应该怎么设计才能避免这类事故？

**期望加分项：**
- 能区分"值得重试"与"不值得重试"：瞬时错误（网络抖动、资源不足）可自动重试；SQL 逻辑错、数据问题重试无意义，应立即失败告警
- 重试策略有量化依据：有限次数 + 间隔，并强调重试必须幂等（重试 = 重复写）
- 告警分级：任务失败即时 P1 告警；延迟超 SLA 提前预警（预计 3 点完成、4 点未完成先预警）；静默窗口防半夜轰炸
- 失败要 fail-fast 并阻止下游用空数据跑，而不是让下游"成功"地用脏数据
- 有事后复盘机制：重试成功后也要归因，防止自动重试掩盖真问题

**减分项：**
- 只答"加大告警"或"多打点电话"，没有分级与收敛策略
- 自动重试不带幂等，重试成功反而写了两份数据
- 忽略"任务成功但数据为空/迟到"这种失败告警覆盖不到的场景（需要数据就绪监控）
- 不做延迟预警，永远事后补救

**解答：**
设计分三块：重试、监控、预案。重试上，先分类再定策略：对瞬时失败（YARN 队列排队、网络超时、依赖组件抖动）做有限次自动重试，比如最多 3 次、指数退避（1min/5min/15min）；对确定性失败（SQL 语法错、schema 不匹配、源数据非法）不要重试，直接失败并告警，重试只会浪费资源；重试必须以"写入幂等"为前提——INSERT OVERWRITE 分区或主键 merge，否则重试成功=数据翻倍，比失败更糟。监控上，三层：任务事件告警（失败即报，P1 即时、值班确认）；延迟预警（用历史运行时长分位数建基线，超过 P95 预估时间仍未完成先报"慢"，超过 SLA 截止时间报"超时"）；数据就绪监控（分区存在 + 行数/大小阈值），专门兜住"成功但没数据"的场景。告警要分级收敛：同一任务抖动限流，避免半夜连环短信导致"狼来了"失效。预案上，失败后 fail-fast，让下游依赖任务也失败或被阻断，绝不带着空数据往下跑；数据恢复后按血缘顺序自动补跑。实践中的坑：自动重试最隐蔽的问题是掩盖根因——重试成功后再也不查为什么失败，必须在任务元数据里记录重试次数并定期分析；夜间告警要接值班 on-call 而不是只发邮件；"延迟预警"依赖的历史基线要在数据量增长时定期重算，否则天天误报。

**延伸考点：** 自动重试与人工确认的边界怎么划（哪些失败必须人看）？数据就绪监控的阈值（行数/大小）怎么定才能既覆盖故障又不误报？

### Q6. 平时 30 分钟的任务今天跑了 4 小时，怎么定位瓶颈？

**问题：** 一个平时 30 分钟跑完的 Spark 任务，今天跑了 4 小时还没结束，可能是数据倾斜、资源不足还是 Shuffle 瓶颈？怎么用证据判断，而不是靠猜？

**期望加分项：**
- 用 Spark UI 看证据：Stage 各 task 耗时分布是否有长尾（中位数 10s、最大 1h = 倾斜）；shuffle read/write 量、GC 时间、磁盘溢出
- 能区分三种瓶颈的特征：倾斜（个别 task 慢）、资源不足（所有 task 都慢/排队、YARN 等待）、单 task 本身重（大 join 无裁剪）
- 会看 executor 日志与事件时间线，能定位到具体 Stage 与代码位置
- 能对比"今天 vs 昨天"的输入数据量、并行度、分区数找差异
- 知道倾斜不一定只在 reduce 端，map 端读放大（小文件多）也会表现为慢

**减分项：**
- 不先看监控，直接改代码（改并行度、加内存）碰运气
- 只会说"数据倾斜"，分不清倾斜、资源不足与单个算子重的区别
- 不看 task 长尾分布，用"整体变慢"一句话糊弄
- 无法指出具体是哪个 Stage、哪类算子（join/groupBy）慢

**解答：**
先拿证据再动手。第一步，打开 Spark UI 看 Job/Stage 时间线：哪个 Stage 耗时最长、耗时占比多少，把范围从"整个任务"缩小到"某个 Stage"。第二步，看该 Stage 的 task 分布：若中位数秒级、最大值几十分钟甚至 1 小时，是数据倾斜（长尾 task）；若所有 task 耗时均匀变长，且 Job 在"排队"状态耗时明显（YARN 队列等待、executor 申请慢），是资源不足；若单个 task 自身耗时大但数据量不大，是计算瓶颈（如笛卡尔、嵌套循环 join、无谓的 collect）。第三步，看 Shuffle 指标：shuffle write/read 总量是否异常大、是否大量 spill 到磁盘（说明内存不足、分区数据过大）、GC 时间占比是否过高。第四步，对比基线：与历史同任务今天的输入数据量、分区数、资源配比差异——比如上游小文件暴涨导致 map 端 task 数量从 200 涨到 2 万，表现为"每个 task 都很快但总数巨大"。定位到根因类型后再对症：倾斜走加盐/广播/拆分，资源不足走队列配额/错峰/提高并行度，shuffle 瓶颈走减少 shuffle（map join、预聚合、合理分区数）。实践中的坑：别一上来就调 `spark.sql.shuffle.partitions`，先确认瓶颈到底在哪个 Stage；长尾 task 要确认是"计算慢"还是"GC 慢"（GC 慢说明内存压力，加内存而非改分区数）；资源不足时盲目加并行度会加剧排队，先看 YARN 队列水位。

**延伸考点：** 你如何建立任务的历史性能基线（哪些指标、如何判定异常），让"今天变慢"能被自动发现？map 端慢和 reduce 端慢的排查手段分别是什么？

### Q7. 按城市聚合时一个 key 占了 80% 数据，reducer 卡死/OOM，怎么治理？

**问题：** SQL 里按 city 做 group by 汇总，北京这个 key 占了当天 80% 的数据，对应的 reducer 任务长时间卡死甚至 OOM，其他 key 早跑完了。怎么治理？count/sum 和去重场景的处理有什么区别？

**期望加分项：**
- 先验证再动手：用 count by key 确认热点，从 Spark UI 看长尾 task 与数据量对应关系
- 能说出两阶段聚合：加盐（随机前缀）→ 部分聚合 → 去盐再聚合，并知道只对 count/sum 等可分配聚合有效
- 明确 distinct 不能直接加盐：需要先按（盐,key）去重再聚合，或改写为 count(distinct) 的分步处理
- 区分 group by 倾斜与 join 倾斜：join 倾斜处理要考虑 join 语义，不能简单加盐
- 治标手段（提高并行度/内存）与治本手段（业务拆分、单独处理热点 key）的取舍

**减分项：**
- 不验证热点直接"加盐"，加了也不知道有没有用
- 对 distinct 也用随机盐直接聚合，结果算错
- join 倾斜用 group by 的加盐方案，导致关联结果错误
- 只答"提高并行度"，说不清为什么治标不治本

**解答：**
治理分三步：验证、治本、防复发。第一步验证：`SELECT city, count(*) FROM t GROUP BY city ORDER BY 2 DESC` 确认热点分布，结合 Spark UI 确认长尾 task 恰好对应热点 key。第二步按场景处理。group by 聚合：用"加盐两阶段聚合"——`SELECT city, sum(cnt) FROM (SELECT city, concat(city, '_', floor(rand()*N)) AS sk, sum(v) AS cnt FROM t GROUP BY city, sk) GROUP BY city`，随机盐把热点拆成 N 份并行聚合，再合总；只对 sum/count/avg 这类可分配聚合有效，对 `count(distinct user_id)` 必须先按（盐, user_id）去重再聚合，否则同一个 user 出现在多个盐桶里被重复计数。热点明确时更优的治本方案是"拆分热点单独处理再 union"，比如北京单独跑一条 SQL、其余 city 跑一条，最后合并，可读性和性能都最好。join 倾斜不能照搬加盐：大表 join 小表先考虑 broadcast；大表 join 大表且热点 key 集中在少数值时，对热点 key 的数据打散成（key,盐）与按同样规则打散的另一侧做 join 后再去盐，非热点走正常路径，最后 union——注意去盐时要做去重防放大。第三步防复发：对热点变化（如双十一某商品爆发）用动态检测——每天检测 top key 占比，超过阈值自动启用加盐。实践中的坑：加盐的 N 不是越大越好（盐太多小文件暴涨）；distinct 加盐若盐桶内不去重，结果偏大且难发现；治标手段（调大 `spark.sql.shuffle.partitions` 或加内存）能缓解 OOM 但长尾仍在，只能应急。

**延伸考点：** 热点 key 不固定、每天不同（比如爆款商品）时，加盐方案怎么动态适配？两阶段聚合在指标可加性上有什么前提（哪些指标不能这样算）？

### Q8. 动态分区写入一次生成了几万个小文件，任务 OOM，怎么处理？

**问题：** 用动态分区向 Hive/数据湖表写入，结果一下子生成了几万个分区/几万个小文件，任务 OOM 或者后续查询越来越慢，怎么办？什么场景该用动态分区、什么场景不该用？

**期望加分项：**
- 先讲"分区粒度"判断：按天/小时是合理粒度，按 user_id/订单维度是滥用；动态分区适合"分区数少且不确定"的场景
- 能说清 OOM 的两种位置：driver 端动态分区元数据过多（分区数量限制参数），executor 端每分区一个文件句柄/写入器过多
- 给出写入端控制：先重分区/coalesce 到目标文件数再写、调大每个文件的目标大小、限制单任务最大分区数
- 知道事后治理：小文件合并（重写分区）、Hive 的 merge 参数、Delta/Iceberg 的 OPTIMIZE
- 注意与 INSERT OVERWRITE 组合时的语义坑：只覆盖本次写入的分区，残留旧分区

**减分项：**
- 只说"别用动态分区"，说不出该用什么替代
- 分不清 OOM 在 driver 还是 executor，参数乱调
- 忽略动态分区 + overwrite 的残留分区问题
- 不知道合并小文件也要考虑幂等和并发写入

**解答：**
先做判断：动态分区适合"写入时才确定分区值、分区数量可控"的场景（比如按日期+地域写，每天几十个分区）；按业务主键（user_id）分区属于滥用，分区数动辄千万，任何方案都救不了。问题分两类处理。第一类 OOM：若是 driver 端报动态分区数超限（如 `hive.exec.max.dynamic.partitions` 默认几百），说明分区数量级不对，应改分区粒度或改为静态分区（先 `SELECT DISTINCT 分区键` 后逐个写）；若是 executor 端 OOM，多是每个分区各持一个文件写入器，同时打开的文件句柄/内存过多，通过"写入前重分区"控制每个 task 只写少量分区：`df.repartition(分区键, 目标分区数)` 或 `coalesce()`，让文件写入器数量与并行度匹配。第二类小文件：动态分区下每个 task 为每个分区各写一个文件，task 数 × 分区数 = 文件数，几个 task 一跑就是几万个文件。写入端控制：先聚合再写——`repartition(分区键, N)` 让每个分区只产生 N 个文件，N 按"数据量/目标文件大小（128MB~1GB）"估算；开启 AQE 让 Spark 自动合并小分区输出。事后治理：对已产生的小文件做合并任务（把分区数据读出按目标大小重写），Hive 用 `ALTER TABLE ... CONCATENATE` 或自写合并，Delta/Iceberg 用 `OPTIMIZE`；合并要与增量写入做好串行或锁，避免并发覆盖丢数据。实践中的坑：动态分区 + `INSERT OVERWRITE` 只覆盖"本次写入涉及的分区"，历史脏分区不会清掉，切换前先 TRUNCATE 或显式清理；合并任务本身也会产生写放大，频率按"文件数触达阈值"触发而不是每天跑。

**延伸考点：** 合并小文件任务与实时/准实时写入同一张表时，如何避免丢数据（版本冲突、锁、分区隔离）？如何监控文件数触达阈值自动触发合并？

### Q9. 数仓表小文件越来越多，查询越来越慢、NameNode 压力大，怎么治理？

**问题：** 一张每天写入的宽表，小文件越积越多，查询时 task 数暴涨、NameNode 元数据压力大，怎么从"写入端"和"存量端"两方面治理？

**期望加分项：**
- 能说清根因：动态分区、频繁小批量插入、并行度过高、流式微批写入、insert 后无合并
- 写入端：insert 前控制并行度/重分区到目标文件数、开启 AQE 输出合并、按分区预估文件数
- 存量端：定期 compaction（重写合并），Delta/Iceberg 用 OPTIMIZE + 文件跳过统计，Hive 用 merge
- 有量化指标：监控文件大小分布（中位数、小于 32MB 的占比）、文件总数，触达阈值自动触发合并
- 知道合并与增量写入的并发安全，以及合并频率与写放大的权衡

**减分项：**
- 只知道"跑个合并任务"，不知道从写入端预防
- 不关注文件大小分布，只会看"文件总数"这种笼统指标
- 忽略合并任务与实时写入并发会丢数据的问题
- 说不出为什么小文件会让查询变慢（task 启动开销、元数据开销、随机 IO）

**解答：**
治理要"写入端预防 + 存量端定期合并"双管齐下。根因先说清楚：小文件 = task 数 × 分区写入器，动态分区、每个微批次单独 insert、并行度与数据量不匹配都是源头，所以预防比清理更值钱。写入端三条：一是插入前重分区——`df.repartition(N)` 或按分区键 repartition，N 按"输入数据量 / 目标文件大小（128MB~1GB）"估算，让每个分区文件数=1~2 个；二是开启 Spark AQE 的 `coalescePartitions` 和输出合并，把尾盘小分区自动并掉；三是流式/准实时链路按批合并写，而不是每个微批次都 insert 一遍。存量端：对存量小文件做 compaction——读分区数据按目标文件大小重写，Hive 用 `ALTER TABLE ... CONCATENATE`（对 ORC）或自写重写任务，Delta Lake 用 `OPTIMIZE`，Iceberg 用 `rewrite_data_files`，同时会更新文件级统计信息，让查询谓词下推更准；合并要有幂等与并发控制（只合并不再有写入的冷分区，或用表锁/版本机制），否则和增量写入撞车会丢数据。治理要有指标闭环：监控每张表的文件总数、文件大小中位数、小于 32MB 的文件占比，按表设置阈值，比如"文件数 > 2000 或小文件占比 > 30% 触发自动合并"，合并后验证文件数与查询耗时回落。实践中的坑：compaction 也是写放大，每天全量重写不如按阈值触发；对 ORC/Parquet 合并后要重跑一次 ANALYZE 更新统计信息；最容易被忽略的是"上游临时表"和"中间表"的小文件——它们量级大但没人管，治理优先级反而最高。

**延伸考点：** compaction 与正在写入的分区冲突时，如何设计才不阻塞写入（增量合并、分区级锁、数据湖的版本冲突解决）？文件大小目标怎么按表定（宽表/窄表、列数多寡）？

### Q10. 实时看板 20 万、离线报表 25 万，对不上，怎么排查与治理？

**问题：** 实时看板显示当天订单 20 万，第二天离线报表却是 25 万，差 5 万。业务问哪个是对的，你怎么排查？怎么从根上治理批流口径不一致？

**期望加分项：**
- 先对齐口径再谈对错：事件时间 vs 处理时间、自然日/业务日的边界、时区、是否含取消单，这些定义不同天然对不上
- 能列出差异的工程来源：迟到数据（离线会等重跑、实时不等）、截断边界（滚动窗口 vs 固定日）、去重算法（实时近似 vs 离线精确）、实时链路丢数/重复消费
- 排查手法：拉同一时间窗同一口径对比、按渠道/类型下钻找差异集中点、查实时消费的 offset 与滞后
- 治理方案：统一口径层（指标字典、公共计算口径）、时间字段统一、在源层对账（源表行数 vs 实时消费量）
- 承认"允许差异"也是方案：明确波动容差与修复 SLA（T+1 以离线为准）

**减分项：**
- 直接说"实时不准，以离线为准"，不做排查
- 不知道事件时间与处理时间的区别会造成系统性偏差
- 忽略实时链路本身丢数/重复的可能
- 提不出"口径治理"层面的方案，只停留在单次对账

**解答：**
排查顺序：先对齐口径，再查工程问题。第一步，拉出两边各自的计数逻辑：实时看板若是"按事件到达时间计数"（处理时间），离线若按"业务日期+事件时间"，那么跨零点前的 5 万订单事件在实时里算昨天、离线算今天，天生对不上——先统一口径再看差值，很多"数据问题"其实是口径问题。第二步，查工程链路：查实时消费的 offset 与 lag（是否丢数据）、消费是否重复（重启重复消费导致偏大）、是否用了近似去重（HyperLogLog 会偏大/偏小）；离线侧查是否把"实时算当天"的截断边界（比如 23:59:59）与离线"次日 0 点"错位。第三步，下钻定位：把 5 万差值按渠道、订单类型、时间段拆解，定位差异集中在哪类（通常是某类特定场景，如跨境订单时区或取消单）。治理上分三层：口径层，建立统一指标字典，事件时间/业务日期/时区在字典里定死，实时离线共用一套口径配置，而不是各写各的 SQL；对账层，在源表做"源行数 vs 实时消费量 vs 离线处理量"三方对账，差异超阈值自动告警，把对账做进日常监控而不是出事故才查；SLA 层，明确"T+1 以离线为准、实时允许滞后修正"的共识，实时报表标注数据截止时间。实践中的坑：夏令时/时区转换会周期性制造差异；迟到数据在离线是"重跑修正"，在实时是"无解"，所以口径上要定义迟到容忍窗口；不要追求两个数字完全相等，定义容差（如 ±1%）与修复时限更务实。

**延伸考点：** 迟到数据（比如凌晨补录昨天的订单）在实时和离线分别怎么处理，才能让两边最终收敛？指标字典落地时由谁维护、怎么防"各算各的"？

### Q11. 整条链路 20 个任务串行，SLA 8 点出数实际 9 点半，怎么优化？

**问题：** 一条离线报表链路 20 个任务基本串行依赖，SLA 要求早上 8 点出数，最近总到 9 点半才出。怎么定位瓶颈并优化到 SLA 内？盲目加并行度为什么可能更慢？

**期望加分项：**
- 先量化：给每个任务打耗时点，找到长尾任务（大概率 1~2 个瓶颈），而不是平均用力
- 检查依赖是否被"过度串行"：无依赖关系的任务是否被人为排成线性；跨层可并行时错峰而非同时挤资源
- 有资源视角：并行度提升要与队列容量匹配，否则抢资源互相拖慢，总时长反而增加
- 能提出工程手段：中间结果物化复用、链路裁剪、时间依赖改数据就绪依赖、关键路径任务提前启动
- 给出 SLA 达成后的验证：压测/观察连续几天，确认延迟回落且无资源挤兑副作用

**减分项：**
- 不先量化直接"把任务并行跑"或"加机器"
- 忽略共享队列的资源上限，盲目并行导致整体更慢
- 只知道加资源，不会砍冗余计算（中间层重复计算、可复用的物化结果没复用）
- 答不出"早跑不一定省时间"（数据没就绪早跑=白跑+抢占资源）

**解答：**
优化链路延迟的正确顺序：量化 → 剪枝 → 并行 → 提速。第一步量化：给每个任务记录运行时长与等待时长（调度系统里都有），画出一条链路的时间线，找出占 70% 以上时间的那 1~2 个长尾任务，先优化它们，其余任务再快也省不了几分钟。第二步剪枝：检查链路里有没有冗余——上游已算过的中间结果下游又重算了一遍（物化中间表供多下游复用）；有没有"轻任务"可以合并（两个几秒钟的小任务合并成一个，省调度开销）；有没有非关键路径可以移到 SLA 之外（比如报表展示需要 6 点，但某些辅助表可以 10 点再刷）。第三步并行：把无依赖的任务真正并行起来——先检查 DAG 是否被人为排成串行（很多团队图省事把依赖串成一条线，其实可并行）；并行要考虑队列容量：N 个任务同时跑需要 N 倍资源，超过队列上限就会排队，互相拖慢，所以"错峰并行"（分波次）往往比"全量并行"更快。第四步提速：长尾任务用前几题的手段治理（倾斜、小文件、shuffle），并把"时间依赖"改成"数据就绪依赖"——任务不必等凌晨 1 点触发，而是上游数据一到就触发，能吃掉不少等待时间。实践中的坑：优化要"先剪后加"，很多人一上来加并行度，把队列打满，所有任务包括关键路径都变慢；链路优化后要连续观察几天（数据量有周期性波动），确认不是靠运气达标；SLA 优化到 8 点内之后，要留缓冲（比如目标 7:45），给异常抖动留余量。

**延伸考点：** 如何用历史运行数据自动识别链路中的瓶颈任务与关键路径？并行波次怎么规划（按资源容量分几波、每波跑哪些任务）？

### Q12. 历史分区占了 70% 存储，成本和查询都在恶化，怎么管理生命周期？

**问题：** 数仓一张大表保留全量历史分区，历史数据占了 70% 存储空间，冷分区还拖慢查询、推高存储成本。冷热分层和生命周期管理怎么设计？

**期望加分项：**
- 有分层模型：热数据（近 30/90 天）保持原格式高可用；温数据压缩归档但仍可查；冷数据转低成本存储或按合规删除
- 生命周期规则化：按分区 TTL 自动归档/删除（调度任务或表属性），策略可配置、可审计
- 有成本视角：对比"存储成本 vs 数据重建成本"（数据能否从源重放），不能删的做压缩归档而不是硬删
- 先治理"该删的"：临时表、测试表、废弃中间表往往占存储大头，删除最省成本
- 考虑合规与下游引用：删数据前确认血缘与合规要求，归档后保留元数据与按需恢复能力

**减分项：**
- 只知道"删老数据"，不区分可删/可归档/必须留（合规）
- 没有按访问频率分层的概念，一刀切
- 忽略"删了还要能恢复"的诉求（归档而非物理删除）
- 不先查血缘，直接把有下游消费的分区删了

**解答：**
核心思路是"按访问频率分层、按规则自动化、删前先看血缘"。第一步盘存量：先查存储分布——往往临时表、测试表、废弃的中间层表占了很大比例，这些"该删的"优先级最高，清掉后立竿见影；对有业务价值的表再谈分层。第二步分层设计：热数据（近 30~90 天）保持原格式、高频查询路径可用；温数据（按周/月查询的旧分区）做压缩归档（如改 Zstd 压缩、合并小文件降低文件数），查询仍可用但接受更慢；冷数据（几乎不查的历史）转低成本存储（对象存储冷存储/归档桶）或按合规要求删除，元数据保留、支持按需恢复。第三步规则化：把分层逻辑写成可配置的 TTL 策略（按分区保留天数/访问热度自动归档或删除），由调度任务执行并记录审计日志，不要靠人手工删；删之前查血缘，确认没有活跃下游引用，有引用的先通知下游迁移或做归档表承接。实践中的坑：删除前一定要确认合规要求（财务、风控类数据有法定留存期，删了是合规事故）；"归档"和"删除"要分开——能重放的数据（源库还在）可以删，不能重放的数据只做归档不做物理删除；冷数据的访问路径（BI 工具直接连数仓）也要跟着改造，否则归档后报表查不到又被业务投诉；生命周期任务的执行结果要有对账（删了多少、还剩多少），防止误删后无法追溯。

**延伸考点：** 归档到对象存储后，查询性能下降多少可接受？如何设计"按需恢复"的流程让冷数据在被查询时能自动拉回热存储？

### Q13. 新表建表，ORC 还是 Parquet？压缩用 Snappy 还是 Zstd？

**问题：** 数仓要新建一张大宽表，存储格式和压缩怎么选？同事说用 Parquet+Snappy（默认组合），有人建议 ORC+Zstd 压缩比更高。怎么选才合理，依据是什么？

**期望加分项：**
- 先讲清楚判断维度：查询引擎生态、压缩比、压缩/解压速度、文件统计信息与谓词下推能力
- 能说清差异：Parquet 跨生态兼容最广（Spark/Presto/Hive/Impala 都原生支持）；ORC 在 Hive 生态性能好、自带索引与统计信息、支持 ACID
- 压缩选择有量化依据：Snappy 解压快、压缩比低；Zstd 压缩比高（约比 Snappy 小 20%~30%）、解压也快，Spark 3 原生支持；Gzip 压缩比最高但最慢
- 结合场景取舍：存储成本敏感选 Zstd；查询延迟/CPU 敏感选 Snappy；列数多、稀疏数据压缩收益小的认知
- 提醒压缩级别可调（Zstd level），且压缩比要和查询性能一起看，不能只看存储

**减分项：**
- 只背"Parquet+Snappy 是默认"，说不出为什么、何时该换
- 不知道 ORC 与 Hive/Spark 版本的兼容性坑（老版本 ORC 支持不全）
- 只看压缩比不看解压 CPU 成本，选 Gzip 把查询拖慢
- 忽略"存储格式与查询引擎的适配"这个决定性因素

**解答：**
选择逻辑分两步：先定文件格式，再定压缩。文件格式上，Parquet 与 ORC 同为列式存储，核心能力（列裁剪、谓词下推、压缩）一致，差异在生态与细节：如果查询引擎是 Presto/Trino + Spark + Hive 混用，选 Parquet，兼容面最广，是事实上的交换格式；如果主要跑 Hive 且依赖 ACID（update/delete/merge），ORC 更合适——ORC 自带更丰富的文件级索引（bloom filter、min/max 统计）且是 Hive ACID 的默认存储格式；Delta/Iceberg 默认走 Parquet。压缩上，不要无脑 Snappy：它优势是快（压缩、解压延迟低），适合 CPU 紧张或查询延迟敏感的场景；Zstd 用略高的压缩 CPU 换来显著更小的文件（通常比 Snappy 小 20%~30%）且解压速度与 Snappy 相当，Spark 3.x、Presto 新版本均原生支持，是"存储成本敏感 + 查询吞吐优先"场景的主流选择；Gzip 压缩比最高但压缩慢、解压也慢，只适合"写一次读极少"的归档数据。实践建议：新建表默认列式格式（Parquet 或 ORC 按生态定）+ Zstd，关键大表实测对比——用同样数据分别建成 Parquet+Snappy 与 ORC+Zstd，比较文件大小、scan 耗时、CPU 消耗三个指标再定，别凭印象选。实践中的坑：压缩格式与文件格式必须配套（Parquet 文件里写 Zstd 与 ORC 里写 Zstd 是不同的 codec，混用会导致引擎不支持直接报错）；Zstd 有压缩级别参数，默认级别未必最优，写放大场景可调低；只优化存储不管查询，压缩比上去了查询却因解压变慢，属于捡芝麻丢西瓜；小文件场景下文件格式和压缩带来的收益会被文件数量开销淹没，先治文件数量再谈格式。

**延伸考点：** Presto/Trino 读 ORC 与 Hive 读 ORC 的性能差异是什么？你如何用数据（文件大小、查询耗时、CPU 占比）做一次格式选型的实测对比？

### Q14. 两个部门共用一个资源队列，夜里高峰互相抢资源，任务延迟抖动，怎么规划？

**问题：** 两个部门几百个离线任务共用 YARN 一个队列，晚上高峰期任务互相抢占资源，排队时间从 10 分钟涨到 2 小时，核心报表也跟着晚点。怎么预估每个任务的资源、怎么规划队列才能治本？

**期望加分项：**
- 有资源预估方法：按历史运行数据统计每个任务的执行器数、内存、CPU、输入数据量与耗时，建立"数据量→资源"的估算基线
- 能讲清队列规划：容量调度（Capacity Scheduler）分队列保底容量 + 弹性共享，核心任务队列独占保底、非核心队列共享余量
- 有错峰与优先级机制：非核心任务挪到低峰期、核心任务高优先级、低优先级任务可被抢占
- 有监控闭环：队列水位、任务排队时长、资源利用率指标，超阈值预警
- 知道调动态资源分配（Spark dynamic allocation）回收空闲执行器，避免任务跑完还占着资源

**减分项：**
- 只会说"加机器"，不分析任务真实的资源需求曲线
- 不分核心/非核心，所有任务一个队列一个优先级
- 资源预估凭经验拍脑袋，没有数据支撑
- 忽略动态资源回收，任务结束资源不释放，高峰更堵

**解答：**
治本思路是"算清需求 + 分层隔离 + 弹性共享"。第一步算需求：从任务历史运行记录里统计每个任务的实际资源使用——executor 数、每个 executor 内存/核数、输入数据量、运行时长，算出"每 TB 数据需要多少资源、并行度怎么配"的经验系数，以后新任务上线先按数据量估算资源再调优；同时记录每个任务的实际使用峰值 vs 申请量，把"申请 100 个核实际只用 20 个"的浪费查出来。第二步规划队列：用容量调度把集群分成几个队列——核心业务队列配置保底容量（比如 60%）保证关键链路不受冲击，非核心队列保底少量、但允许弹性占用其他队列的空闲容量；容量调度下空闲资源可以借用，高峰期借用的资源会被"归还"，所以核心队列的保底必须预留峰值余量，而不是排满。第三步错峰与优先级：把非核心任务（临时分析、批量回刷）挪到白天低峰或配置低优先级允许被抢占；核心任务配置高优先级和独立保底，保证即使高峰也不排队。第四步监控与回收：监控队列水位（排队任务数、平均排队时长、CPU/内存利用率）建基线，排队超过阈值自动预警；开启 Spark 动态资源分配，任务计算完自动释放空闲 executor，避免"跑完了还占着资源"把队列堵死。实践中的坑：队列容量和任务量会随业务增长变化，配额要定期按运行数据重算，不能配一次管一年；"保底容量"设太高会把资源锁死浪费（其他队列空着也用不了），要配合弹性共享理解容量调度的借还机制；抢占（preemption）要谨慎，被抢占的任务重跑也是成本，只在极端场景开启。

**延伸考点：** 你如何用历史运行数据做"任务资源画像"（哪些指标、怎么建模）？核心队列的保底容量怎么定才能既不饿死核心又不浪费资源？

### Q15. 上游表加了一列，下游任务全挂了；删一列又引发解析错位，怎么应对 Schema 变更？

**问题：** 上游业务表加了一个字段，下游 Hive 任务因为列数不匹配直接失败；又有一次上游删了列，下游因为按位置取字段取错了值。怎么设计才能让 Schema 变更不炸下游？加列、删列、改类型分别怎么处理？

**期望加分项：**
- 能分级看待变更：加列（向后兼容，只要给默认值）vs 删列/改类型（破坏性，需要排期协调），处理策略完全不同
- 下游写 SQL 的规范：显式列名、禁止 SELECT *，读取用列名而非位置
- 有 Schema 演进机制：Spark/Hive 自动演进配置、数据湖（Delta/Iceberg）的 schema evolution、字段级默认值
- 有变更管理流程：变更前用血缘做影响分析、通知下游、分阶段灰度（先加列让下游适应，再删旧列）
- 改类型的处理：新增列过渡而非原地 ALTER，避免隐式转换错误与精度丢失

**减分项：**
- 只说"加列没问题"，不区分删列/改类型的破坏性
- 不知道按位置取字段（SELECT * 或索引访问）在列变更后会静默错位——比报错更危险
- 没有变更通知与影响分析的流程，全靠下游自己发现
- 忽略类型变更（如 int→string、decimal 精度变化）可能静默截断或报错

**解答：**
原则是"兼容性分级 + 列名驱动 + 变更流程化"。第一步分级：加列是兼容变更（新增列不影响已有消费，但读取时要保证有默认值或可空，否则下游 insert 显式列列表会缺字段）；删列、改类型是破坏性变更，绝不允许"上游直接改、下游自求多福"。第二步规范：下游 SQL 一律显式列名、不用 `SELECT *`，插入时显式列出列名而不是依赖位置——按位置解析在列变更后不会报错而是"静默错位"，这种错位最难发现（数据是错的但任务成功）。第三步机制：Spark 读表开启 schema 兼容（`spark.sql.hive.convertMetastoreParquet` 与 schema evolution 相关配置），Hive 支持对已存在列做默认值回填；Delta/Iceberg 天然支持演进（加列、改名、可空性变更），但对删列有版本兼容限制（老文件里该列数据还在）。第四步流程：变更前查血缘列出受影响的下游任务和负责人，通知 + 评估；采用"分阶段"策略——先加列（下游无感知）→ 各下游消费/适配 → 确认无引用后再删旧列或做类型过渡；类型变更不原地改，新增一个同语义新列、双写一段时间、下游切换后再下线旧列，避免隐式转换和精度损失。实践中的坑：Hive 老版本里"加列到中间位置"会让 `SELECT *` 结果错位，这也是禁止 `SELECT *` 的原因；字段类型 string→bigint 的隐式转换在数据不规范时直接变 null 且不报错；变更后要做一次全链路回归（下游跑通 + 抽查数据对），不能只验证"任务成功"。

**延伸考点：** 你的团队如何建设"Schema 变更影响分析"的能力（靠血缘系统还是人工通知）？数据湖的 schema evolution 在并发写（一个任务加列、一个任务写旧 schema）时怎么保证不互相破坏？

### Q16. Spark 任务重跑一次输出就翻倍，"端到端至少一次/精确一次"在批处理里怎么实现？

**问题：** 一个 Spark 批任务因为失败重跑了一次，输出表里的数据翻倍了。批处理里怎么设计才能做到"端到端 at-least-once 甚至 exactly-once"？Spark Structured Streaming 里说的 exactly-once 又依赖什么？

**期望加分项：**
- 能讲清层次：批任务自身是 at-least-once（重跑 = 重写），要精确一次靠"确定性重放 + 幂等写入"组合，而不是靠引擎保证
- 写幂等的手段：INSERT OVERWRITE 按分区覆盖；主键 merge（Delta/Hudi/Iceberg/Hive ACID）实现 upsert，重跑不产生重复
- 流式场景：Spark Structured Streaming 的 end-to-end exactly-once = 可重放的输入源（Kafka offset）+ 幂等/事务性 sink + 检查点里记录消费进度
- 强调前提：sink 必须支持幂等（普通写 HDFS 文件是 at-least-once，需要输出提交协议）；merge 的 join 键必须有唯一性保证，否则 merge 也会重复
- 指出"数据级去重"是兜底手段：主键 row_number 去重，但成本高，应在源头保证

**减分项：**
- 以为"配置个参数"就 exactly-once，讲不清它依赖 sink 与源头可重放
- 不知道 INSERT INTO 重跑必然翻倍，而 INSERT OVERWRITE 分区只覆盖目标分区
- merge 用非唯一键，结果重复还说"已经精确一次了"
- 分不清任务级幂等与数据级幂等（任务成功 ≠ 数据不重复）

**解答：**
先说结论：批处理天然是 at-least-once，exactly-once 是"设计出来的"而不是引擎自带的，核心是"相同输入必得相同输出 + 输出写入幂等"。第一步保证输入可重放：任务要能锁定输入（显式 dt 分区、从 Kafka 消费则记录 offset），重跑时重放同一批数据，否则源变了结果自然变。第二步保证写入幂等：按分区覆盖——`INSERT OVERWRITE TABLE t PARTITION(dt=...)` 重跑只重写该分区，不会累积；需要"部分更新"的场景用主键 merge——Delta `MERGE INTO t USING s ON t.pk = s.pk WHEN MATCHED THEN UPDATE WHEN NOT MATCHED THEN INSERT`，重跑时重复的数据被 update 而非追加，前提是 pk 在该分区内唯一，否则 merge 后 join 出一对多，结果照样错。第三步，流式场景：Spark Structured Streaming 的 exactly-once 由三件套构成——源头可重放（Kafka/文件源记录 offset）、检查点里持久化消费进度与状态、sink 幂等（文件 sink 用"唯一输出目录 + 提交后可见"协议，或写 Delta 表用事务日志保证 commit 原子性）；任何一个环节不满足就退化为 at-least-once，比如你把结果写到普通 MySQL 表（无幂等约束）就是 at-least-once。实践中的坑：很多人以为"任务重跑成功就对了"，其实 INSERT INTO 类的任务重跑一次数据就翻倍且任务状态是 success，这类事故要靠"输出监控（行数/指标波动）"兜底；merge 表的 pk 唯一性靠业务保证，数仓侧要有校验（重复 key 检测），否则 merge 一遍重跑一遍，重复会悄悄累积；去重兜底（row_number 按主键取一）只在没有幂等写手段时用，是全表扫描级的昂贵操作，不要当成常规方案。

**延伸考点：** 如果 sink 是 MySQL（普通表），你怎么为它设计"批处理幂等写入"（业务幂等键 + 事务）？Flink 的两阶段提交和 Spark Structured Streaming 的幂等写机制在实现思路上有什么异同？

### Q17. 一张大表每天增量 merge，数据越多越慢，怎么优化？

**问题：** 一张几十亿行的订单明细表，每天用 Delta/Hive ACID 做一次增量 merge，刚开始还好，数据多了以后 merge 一次要跑几小时，越来越慢。瓶颈在哪，怎么优化？

**期望加分项：**
- 能定位瓶颈：全表扫描找匹配行（无分区裁剪）、文件数多导致 IO 放大、merge join 本身的开销
- 优化手段有层次：分区裁剪（增量只 merge 受影响分区）→ 数据布局（按 merge key 排序/Z-order 加快查找）→ 文件大小合理 → 增量小表广播
- 能想到架构层优化：增量先 append 再统一 merge、或"增量表 + 定期全量刷新"的分层方案
- 知道数据湖的辅助能力：Delta OPTIMIZE/Z-ORDER、文件级统计（data skipping）、Iceberg 的 hidden partitioning
- 有量化意识：先看 merge 花了多少时间在"读旧数据"上，用 EXPLAIN/UI 佐证

**减分项：**
- 只说"加机器加内存"，不分析 merge 的时间构成
- 不知道 merge 的性能大头是"找到并重写受影响的旧文件"，而非新增部分
- 忽略数据布局（排序/分桶）对 merge 查找效率的决定性影响
- 没想过用"追加 + 定期合并"替代每日全量 merge

**解答：**
merge 慢的本质：它要拿增量去匹配存量，找到受影响的行并重写包含这些行的旧文件——所以时间大头在"读存量找匹配"和"重写旧文件"，数据越多越慢是必然。优化按四层做。第一层裁剪：表按天/月分区，增量数据一般只落在最近分区，merge 前用条件只 merge 对应分区，避免全表扫描；增量数据本身尽量作为小表，Spark 用 broadcast join 减少 shuffle。第二层布局：把表按 merge 的 join 键（主键）排序或分桶存储——Delta 的 Z-ORDER BY、Hive 的 bucket，存量文件按 key 有序后，查找匹配行的 IO 大幅下降；同时文件大小控制在 128MB~1GB，文件太多扫描元数据也是成本。第三层增量：Spark 3 对 merge 有优化（如只处理变更分区），Delta 的 `MERGE` 会利用文件级统计（min/max、bloom filter）跳过不可能匹配的文件，前提是执行 ANALYZE 让统计信息新鲜。第四层架构：如果每天增量只占全量很小比例，考虑"分层"——当日增量先 append 到增量表/当日分区，查询时"存量分区 + 增量分区"合并读（或用数据湖的 CHANGE DATA FEED/CDC 能力），每周末或月末做一次全量 merge 收敛，把"每天全表 merge"变成"每天轻量 append + 低频合并"，查询侧用视图屏蔽两层。实践中的坑：merge 后旧文件是"标记删除 + 新文件"，不清理的话文件数只增不减，要配合 VACUUM/compaction 控制文件总量；merge 的目标表 key 不唯一时，一次 merge 可能把一行 update 成多行（join 放大），先加 key 唯一性校验；"每天 append + 定期合并"方案要处理好查询期间新旧数据的时间戳边界，避免同一笔订单被重复统计。

**延伸考点：** 增量数据里包含"删除"（业务删单）时，merge 方案怎么支持（删除标记 + 过滤）？"追加 + 定期合并"分层方案里，查询层的视图如何保证不重不漏？

### Q18. 业务规则改了，要重算过去 90 天的指标并修正已发布报表，怎么安全回刷？

**问题：** 业务口径调整（比如优惠券计入 GMV），需要重算过去 90 天所有历史数据，并修正已经发布到报表的数字。涉及几十张表、上百个下游任务，怎么安全地回刷，避免回刷期间下游读到新旧混杂的数据？

**期望加分项：**
- 先做影响评估：用血缘列出受影响的表、下游任务与报表，确认是"口径变更"还是"数据修复"，影响面多大
- 回刷顺序正确：按血缘从底层（ODS/DWD）向上逐层重跑，不能只刷中间层
- 有隔离手段：回刷写入临时表/新分区，校验通过后原子切换，避免回刷期间下游读到一半新一半旧
- 有对账与验证：回刷前后对关键指标做对比（快照基线），抽查样例
- 考虑回滚与审计：保留旧版本（数据湖时间旅行可回溯），回刷操作有记录

**减分项：**
- 直接对生产表原地 UPDATE/OVERWRITE 历史分区，回刷期间下游任务照跑，读到新旧混杂的数据
- 只刷中间层不刷底层，导致上下层口径不一致
- 不先做基线快照，回刷后没法对账和回滚
- 忽略"改口径"与"修 bug"要分开记录（口径变更影响分析报告、bug 修复复盘）

**解答：**
回刷的本质是一次"受控的重放"，风险在于"回刷期间的中间态被下游读到"，所以设计核心是隔离与顺序。第一步影响评估：用血缘把受影响的下游任务、报表、负责人全部列出来，按优先级通知；确认这次是纯口径变更还是叠加了数据修复——口径变更要改代码后重跑，数据修复可能只需重跑。第二步执行顺序：严格按血缘自底向上——先重刷底层（ODS/DWD）历史分区，逐层向上，每层刷完做校验（行数、关键指标）再刷上一层，绝不允许"只刷报表层"这种治标操作。第三步隔离发布：回刷写入临时表/独立分区（如临时库同名表），全部完成后与生产数据对账（count + 指标 sum 对比），通过后原子切换（ALTER TABLE EXCHANGE PARTITION / 切换视图 / 数据湖 commit 新版本）；Delta/Iceberg 支持版本管理，回刷就是一个新 commit，随时可以回滚到旧版本，这是数据湖做回刷的天然优势。第四步下游联动：回刷完成后，通知受影响的下游重新消费/重跑（或配置依赖事件自动触发），并明确"回刷完成前下游不得读取"的窗口约定——技术上用"切换后可见"保证。实践中的坑：回刷期间生产任务还在正常跑当天数据，回刷任务与日常任务写同一批历史分区会互相覆盖，需要锁或错开执行窗口；回刷"部分层"最隐蔽——底层刷了、上层没刷，上层指标对不上还不报错，所以要按血缘顺序整链刷完并在每个层做指标对账；90 天的回刷要评估资源占用（回刷任务通常并发高、吃资源，安排到低峰执行并限制并发）；改口径和修 bug 的审计记录分开维护，方便日后追溯口径演进历史。

**延伸考点：** 回刷 90 天数据时，如果中途失败（第 50 天刷了一半），如何保证状态可追踪、可续跑而不是从头再来？回刷与日常 T+1 任务并发写同一张表时怎么避免互相踩？

### Q19. 一张上游表要下线/改结构，怎么快速知道影响哪些下游并评估风险？

**问题：** 业务方通知某张上游表要下线，或者数仓自己要做一张表的重大结构变更，怎么快速列出所有受影响的下游任务、报表和负责人？如果公司还没有血缘系统，你怎么建设？

**期望加分项：**
- 能说清血缘采集的几种来源：解析任务 SQL（insert/select 依赖）、Spark/Hive 运行日志的 input/output 信息、手动登记，并知道各自的覆盖度与代价
- 有落地分层：先表级血缘（够用）再字段级血缘（更可靠），血缘数据入库并提供查询/接口
- 能讲血缘的三大应用：影响分析（变更前评估）、故障定位（数据异常沿血缘上溯）、数据治理（找孤表/无主表降本）
- 知道血缘的坑：动态 SQL、UDF 内读写、解析失败的 SQL 会导致血缘缺失或不准，需要兜底机制（运行日志 + 人工确认）
- 血缘要随任务发布更新，而不是一次性建设

**减分项：**
- 只会说"做个人工通知群"，没有系统化能力
- 不知道血缘可以用运行日志自动采集（Spark History 里有每个 Job 的 input/output 路径）
- 以为血缘建一次就行，不维护更新
- 只有表级血缘就拍胸脯说"影响分析没问题"，忽略字段级变更的静默影响

**解答：**
建设分三步：采集、存储、应用。第一步采集，三条通道互补：一是 SQL 解析——从调度系统的任务定义里解析 `INSERT INTO/OVERWRITE` 与 `FROM/JOIN` 关系，能覆盖绝大多数标准 SQL 任务；二是运行日志——Spark History Server / Hive 的执行记录里有每个 Job 真实的 input/output 路径（包括 UDF 内部读写、动态表名拼出来的表），能兜住 SQL 解析覆盖不到的部分，这是很多团队忽略却最可靠的来源；三是手工登记补充（临时脚本、外部数据交换）。第二步存储：把解析出的"表→表"依赖入库（元数据库加一张血缘表），支持按表查上下游、按任务查输入输出；先做表级血缘（成本低、覆盖大多数变更评估），关键链路再细化到字段级（字段级才能发现"上游改了个字段下游取错"这类静默问题）。第三步应用：变更/下线前跑影响查询，列出下游任务、报表、负责人，输出影响面报告并通知；数据异常时沿血缘自底向上定位源头（哪里开始变脏）；治理层面定期找"孤表"（无下游引用的表）和"无主表"，这是降本的好抓手。实践中的坑：动态 SQL（表名是拼接的）和复杂 UDF 会让解析结果缺失，必须用运行日志兜底并定期校准；血缘要随任务发布/下线实时更新，否则半年后影响分析就是错的；字段级血缘的解析成本高（要解析 SELECT 子句的列映射），分阶段建设，先保证表级全量覆盖、字段级覆盖核心链路；血缘系统上线初期要抽样人工核对准确率，别把"解析对了 60%"的系统直接用于生产决策。

**延伸考点：** 字段级血缘怎么采集（怎么从 SQL 里解析出列到列的映射，解决 select 别名、子查询、case when 的列传递）？血缘准确率如何量化评估，低于多少不能作为变更审批依据？

### Q20. 公司现在 Hive 离线数仓 + Flink 实时两套并存，指标总打架，老板想"统一"，你怎么评估和规划？

**问题：** 公司目前是 Hive 离线数仓（T+1）+ Flink 实时链路（秒级）两套并存，同样的指标两边算出来经常不一致，老板拍板要"统一批流"。你会怎么评估这个诉求、怎么规划落地路线？从哪些角度判断该不该上、怎么上？

**期望加分项：**
- 先澄清"统一"的本质诉求：是口径统一、存储统一还是算力统一？三者的方案和成本完全不同，别急着谈技术
- 能客观对比技术路线：湖仓一体（Delta/Iceberg/Hudi 统一存储，流写批读）vs 批流一体（统一计算 API）vs 只做口径治理，并给出适用场景
- 有落地节奏：先治理（统一指标字典/口径）、再试点（一张核心表）、后推广，而不是一步到位全量迁移
- 能给出评估指标：存储与运维成本、口径不一致率、SLA 达成率、迁移成本与风险
- 承认取舍：湖仓格式的实时查询性能不如专用实时数仓，迁移有团队学习成本，需权衡

**减分项：**
- 老板说"统一"就直接上 Iceberg 大迁移，不做诉求澄清与可行性评估
- 只谈技术选型，不谈口径治理——口径不统一，换了底座照样打架
- 全量迁移一步到位，没有试点与回退方案
- 不评估现有两套体系里各自的存量资产（几十万任务、报表）迁移成本

**解答：**
第一步永远是澄清诉求：老板说"统一"，可能想要的是"数字一致"（口径问题）、"少维护一套"（成本问题）还是"实时也要准"（能力问题），三者解法完全不同——如果核心是口径打架，换底座解决不了，先把指标字典和口径治理做起来。第二步评估现状：盘清楚两套体系各自的资产（任务数、报表数、核心链路、运维人力）、数据链路（哪些表双写、哪些指标重复计算）、不一致的根因分布（口径、迟到、链路丢数），用数据决定"该不该动"。第三步选路线，三条可组合：口径治理（短期必做，统一指标定义、时间口径、对账机制，成本低见效快）；湖仓一体（中期，用 Delta/Iceberg/Hudi 做统一存储底座，离线批写、实时流写同一张表，流批读同一份数据，从存储层消灭"两套数据"），适合"两套表 + 双份存储"矛盾突出的公司；批流一体（远期，Flink 统一计算 API，离线批任务也跑在流引擎上，适合团队以 Flink 为主、SQL 覆盖率高的情况）。第四步落地节奏：先治理口径（1~2 个季度见效）；再选一张核心大表做湖仓一体试点（比如订单事实表，流写批读跑 1 个月，验证数据一致性与查询性能）；试点通过后按链路分批迁移，每批有回退方案（数据湖版本机制天然支持回退）；评估指标量化：存储成本降幅、口径不一致告警次数、双链路运维工时。实践中的坑：最容易被忽略的是"迁移成本"——现有几十万行 Hive SQL 和调度依赖不会自动平移，迁移预算要按任务数估算而不是拍脑袋；湖仓一体的实时写入吞吐与查询性能未必优于专用实时数仓，试点阶段要实测对比再放量；"统一"过程中新旧链路要双跑对账，别把整个公司的数据可信度押在一次大迁移上。

**延伸考点：** 如果你选湖仓一体做统一底座，Delta、Iceberg、Hudi 三个选型你会怎么比（写入模式、并发控制、生态成熟度、运维复杂度）？"口径治理"和"架构统一"的优先级为什么必须先口径后架构，你能给出两者成本收益的对比吗？
