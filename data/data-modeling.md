# 数据 · 数仓建模（面试题库）

本文件聚焦数据仓库建模的工程实践：数仓分层设计、维度建模与事实表选型、指标口径统一与模型治理。所有题目均为真实场景化提问，考察候选人能否在「口径、粒度、成本、易用性」之间做出有依据的取舍，而非背诵理论。难度由实践基础逐步过渡到中阶调优与高阶架构设计，适合一线数据工程师 / 数仓工程师的面试考察。

---

### Q1. 新业务从零建数仓，怎么分层？各层职责和边界怎么定？

**问题：** 公司新上线一个电商业务，你是第一个数仓工程师，要从零搭建数仓。你会怎么设计分层？每层放什么、层间边界怎么划？

**期望加分项：**
- 能说清 ODS/DWD/DWS/ADS 每层职责，而不只是背四个缩写
- 能讲出分层的目的：屏蔽业务变动、统一口径、复用计算、控制查询成本
- 能给出每层典型内容物与命名前缀（dwd_/dws_）
- 能结合团队规模谈取舍（小团队是否砍层）
- 能明确层间约束：禁止跨层取数、明细只落在 DWD

**减分项：**
- 只会背分层名字，讲不出每层放什么的判断标准
- 说不清哪些活放 DWD、哪些放 DWS，边界含糊
- 不考虑团队规模与成本，照搬大厂模板
- 认为分层越多越好，给不出量化依据

**解答：**
先给判断：分层不是越多越好，目标只有一个——「屏蔽变更、复用计算、控制成本」，按团队规模裁剪。最小可用是 ODS → DWD → DWS → ADS 四层，小团队可合并为 ODS → DWD/ADS 两层。

各层职责：ODS 原样接入业务库与日志，只做全量/增量同步，不加工，字段以 `_src` 结尾便于溯源；DWD 是明细层，做清洗（去重、空值、枚举归一）、规范化（统一单位/时区/编码）、维度退化冗余与轻度打宽，粒度等于业务过程的一次发生；DWS 按主题域做轻度汇总（如「用户当日累计支付金额」），目的是复用；ADS 面向报表/接口按应用裁剪，一张报表一张表也可以。

实践要点：DWD 只做「明细的规范化」，不做聚合；DWS 不做明细级加工，避免数据反复膨胀。层间用命名规范与血缘工具约束，禁止 ADS 直接读 ODS。最常见的坑：把 ODS 当「清洗后的表」用，导致 ODS 与 DWD 职责重叠，数据漂移后对不上账。分层方案要写进建模规范并由评审会把关，否则各层边界很快被人为打破。

**延伸考点：** 如果业务经常改需求、底层表频繁变更，哪一层帮你们「扛住」这种变更？为什么？

### Q2. DWD 和 DWS 的边界在哪？一张明细表要不要再做一份汇总副本？

**问题：** 团队里对「日订单明细」吵起来了：有人说 DWD 保留明细即可，汇总需求直接在明细上跑；有人说必须再建一张 DWS 日汇总表。你怎么定？

**期望加分项：**
- 能给出决策依据：数据量、查询频率、并发下游数、实时性要求
- 能给量化方法：如明细日增千万级、报表每次全扫 30 分钟，则必须预聚合
- 能说清汇总表的粒度选择（按「天+渠道+业务线」而非每张报表单独建）
- 提到明细与汇总的一致性对账机制
- 主动考虑「半成品汇总」承接多份下游需求

**减分项：**
- 一口咬定必须建 DWS，说不出依据
- 或一口咬定明细万能，不考虑查询成本与稳定性
- 说不清汇总粒度怎么选，导致汇总表无人复用
- 忽略明细与汇总对不上数时的排查手段

**解答：**
先给判断：这不是「要不要建」，而是「按什么粒度建」。核心量化是「数据量 × 查询频率 × 下游并发数」：明细日增百万级、报表能容忍秒级扫描，可以不加汇总；日增千万级且多张报表反复全量扫明细，就必须建 DWS，否则凌晨任务和报表查询互相挤压、接口超时。

建 DWS 的关键是「粒度复用」：不要为每张报表建专属汇总，而是按业务通用的维度组合（如「天 + 业务线 + 渠道」）做轻度汇总，让多张报表共用。同时保留对账手段：DWS 各字段加总应等于 DWD 对应口径加总，定期跑一致性校验，防止汇总口径漂移。

实践坑有两个：一是 DWS 越建越多、粒度五花八门（有的按天、有的按小时、有的带用户维度），反而比明细更难维护，所以新汇总粒度必须先查是否已有相似粒度；二是汇总表与明细表同时被下游引用，两边数字偶尔不一致，必须靠「以 DWD 为基准的日对账」兜底。若数据量中等，也可以不建 DWS，用明细 + 分区裁剪 + 索引优化来满足查询。结论：给出现量化的依据，而不是背「必须分层」。

**延伸考点：** 一张报表要求 T+0 出数（当天 10 点前必须看到前一天汇总），而明细任务要跑到中午才结束，你会怎么调整分层与调度？

### Q3. 交易流水场景，事实表用事务事实表还是周期快照？怎么选？

**问题：** 要统计「每笔订单的支付金额」和「每天各渠道的成交金额」，还要知道「某时点每个仓库还剩多少库存」。这几类统计是不是同一张表能解决的？

**期望加分项：**
- 能区分事务事实表（每笔交易一行）与周期快照（每周期每对象一行）的粒度差异
- 能说清事务事实表支撑「发生量/累计量」，周期快照支撑「时点状态横截面」
- 能给两张表的分工，而不是一张表硬扛
- 能提到快照表全量重算的成本与保留窗口
- 能举线上实例：库存/余额用周期快照，交易流水用事务事实表

**减分项：**
- 把所有统计都塞进一张事务事实表
- 讲不清两种事实表的粒度定义
- 不考虑快照表的存储成本与重算成本
- 无法举例说明哪种场景必须用快照

**解答：**
先给判断：三类问题要分开建模，一张表硬扛会同时破坏粒度和可加性。事务事实表记录业务过程的一次发生，一行一笔交易，随事件持续增长，支撑按任意维度切片、累计、明细回溯；周期快照按固定周期（如每天）记录每个对象的时点状态，如「某日某仓库的库存量」。

- 每笔订单的支付金额 → 事务事实表 `dwd_trade_pay_di`，一行一笔支付，含支付时间、金额、订单号；
- 每天各渠道的成交金额 → 可直接从事务事实表按天聚合，查询量大则沉淀 DWS 日汇总；
- 某时点的库存余额 → 事务事实表算不出来（只记录了进出明细），必须用周期快照或拉链。

核心判断口诀：要「发生量/累计量」用事务事实表，要「某时点的存量/状态」用周期快照。实践坑：有人给订单表不断加状态字段，把支付、退款、发货多个事实混在一张表，导致粒度被破坏（一行既代表支付又代表退款），下游永远在自造过滤逻辑。建模评审要守住「一个事实表一个业务过程、粒度声明明确」这条红线。

**延伸考点：** 一张事实表里既有支付事实又有退款事实，合并还是拆分？依据是什么？

### Q4. 订单全生命周期要分析「各环节耗时」，怎么建事实表？

**问题：** 业务要统计「下单到支付的平均时长」「支付到发货的平均时长」「整体履约时长分布」。订单状态会经历下单、支付、发货、签收多个阶段，这类需求怎么建模？

**期望加分项：**
- 能想到累积快照事实表（accumulating snapshot）这一形态
- 能说清其粒度：一单一行，多个业务时间戳字段
- 能说出环节时长字段的预计算设计
- 能说明随订单状态更新而增量更新的机制
- 提到与事务事实表的分工（各环节明细仍可单独留事务事实表）
- 主动考虑状态回退、异常单的处理

**减分项：**
- 只想到事务事实表或拉链表，回答不出「多时间戳」建模
- 把累积快照与周期快照混为一谈
- 不考虑状态回退对时长计算的干扰
- 给不出时间戳字段级别的设计

**解答：**
先给判断：订单从下单到签收是「生命周期短、阶段清晰」的流程，适合累积快照事实表：一单一行，各里程碑时间戳做字段，环节时长直接可算。

```sql
CREATE TABLE dwd_trade_order_lifecycle_df (
  order_id      BIGINT,      -- 一单一行
  order_ts      TIMESTAMP,   -- 下单时间
  pay_ts        TIMESTAMP,   -- 支付时间
  ship_ts       TIMESTAMP,   -- 发货时间
  sign_ts       TIMESTAMP,   -- 签收时间
  pay_to_ship_sec BIGINT,    -- 支付→发货秒数，随更新重算
  ship_to_sign_sec BIGINT,   -- 发货→签收秒数
  order_status  STRING       -- 当前状态
) PARTITIONED BY (dt STRING);
```

设计要点：当日有状态变化的活跃订单做增量更新（覆盖写该行），已完结订单不再更新，减少每天处理量；环节时长在更新时预计算落字段，避免下游到处 `date_diff` 导致口径不一致。库存、余额那种「时点状态」用周期快照；而订单这种「状态沿时间推进、有明确里程碑」的流程，累积快照是标准解。

实践坑：状态回退（支付失败退回待支付）、异常单（超时未支付）会让时长出现负值或空值，要预先约定空值语义与异常单过滤口径；累积快照只适合生命周期短的流程，别套用到用户生命周期分析。最后说明分工：环节明细仍可保留在事务事实表中，累积快照是它的「按单收敛视图」。

**延伸考点：** 如果订单生命周期长达一年（如保险保单），还适合累积快照吗？你会怎么改？

### Q5. 营销活动要统计「覆盖了多少人、其中多少领了券」，很多人没有发生交易，怎么建模？

**问题：** 运营要统计某次营销活动「触达了多少用户、其中多少人领了券」，统计对象是「被活动覆盖的用户集合」，很多用户没有任何交易行为。事实表怎么建？

**期望加分项：**
- 能想到无事实事实表（factless fact table）这一形态
- 能说清其粒度：活动 × 用户 一行，无度量字段
- 能说明它承载「覆盖度、参与率」等计数场景
- 能给出 DDL 级别的设计（活动、用户、时间等维度外键）
- 能联系其他场景：用户-权限、课程-学员等覆盖类建模
- 能说明计数方式（count distinct 或置 1 值列）

**减分项：**
- 不知道无事实事实表这种建模形态
- 硬塞度量导致大量空值
- 粒度定义不清（活动×用户 还是 活动×用户×券）
- 讲不出这种表与 join 性能的关系

**解答：**
先给判断：这是「只有事件、没有可加性度量」的覆盖场景，标准建模是无事实事实表——表里没有度量，只有各维度外键（活动、用户、时间、渠道），一行表示「某用户参与了某活动」。

```sql
CREATE TABLE dwd_mkt_campaign_coverage_df (
  campaign_id BIGINT,
  user_id     BIGINT,
  channel_id  BIGINT,
  join_ts     TIMESTAMP,
  is_get_coupon TINYINT
) PARTITIONED BY (dt STRING);
```

统计时用 `count(distinct user_id)` 算覆盖人数，对 `is_get_coupon` 求和算领券人数；还可以与订单事实表 join，看覆盖用户里多少人最终成交（活动 ROI）。它能统一支撑「覆盖度、渗透率、参与率」这类指标，避免每次从活动宽表硬 join。

实践要点：数据量大，按活动周期分区、按活动裁剪；粒度先定死——同一个用户领多张券时，是「活动×用户」还是「活动×用户×券」要看统计口径，别让表结构绑架口径。坑：这类场景常被忽略，导致用「活动宽表 + 大量 distinct join」硬算，查询慢且口径分散。选型口诀：有事件且有度量 → 事务事实表；有事件无度量 → 无事实事实表；看时点状态 → 周期快照。

**延伸考点：** 「参与率 = 领券人数 / 触达人数」，而触达人数的口径来自另一个系统，怎么保证两者在同一天、同一活动下对得上？

### Q6. 库存「时点余额」和「出入库流水」怎么建模？每天还要出各仓库库存日报

**问题：** 库存业务每天要输出「各仓库当日库存余额」，也要能追溯「某 SKU 某天的进货/出货流水」。同一份数据怎么建两张表？怎么保证它们不打架？

**期望加分项：**
- 能想到周期快照表存余额、事务事实表存流水
- 能说清快照粒度：天 × 仓库 × SKU 一行，含期初/期末/入库/出库
- 能说明快照表全量重算机制与保留窗口
- 能说出「期末 = 期初 + 入库 - 出库」的对账校验
- 能说明快照表不需要 join 订单就能出库存看板
- 能考虑促销负库存、冲正等异常口径

**减分项：**
- 只用事务事实表试图算余额，导致时点状态取不到
- 快照粒度定义错（同 SKU 多行重复）
- 不考虑快照表膨胀的存储与重算成本
- 讲不清快照与流水的校验关系

**解答：**
先给判断：库存是典型「状态型」数据，必须用周期快照：每天结束时为每个「仓库 × SKU」生成一行，记录该时点余额及当日变动；出入库流水用事务事实表单独存，两表职责分离。

```sql
CREATE TABLE dwd_inv_warehouse_sku_snap_df (
  dt           STRING,      -- 快照日
  warehouse_id BIGINT,
  sku_id       BIGINT,
  begin_qty    BIGINT,      -- 期初
  in_qty       BIGINT,      -- 当日入库
  out_qty      BIGINT,      -- 当日出库
  end_qty      BIGINT       -- 期末
) PARTITIONED BY (dt);
```

设计要点：快照表是「天 × 对象」的横截面，查任意一天直接读对应分区，无需按事件回放；历史保留 30~90 天即可，更早的转汇总或拉链控制存储。流水表与快照表做交叉校验：任意分区必须满足 `end_qty = begin_qty + in_qty - out_qty`，不满足即说明同步丢数，这是库存质量的核心防线。

坑：快照重算时若直接覆盖历史分区，会把期初/期末算错，重算必须从断点日期顺序重放；夜间促销、冲正导致负库存时，要提前和业务约定口径（是否过滤、如何展示），否则报表和运营对不上。选型原则一句话：能读时点状态就上快照，别用事务事实表回放，回放成本高且口径难统一。

**延伸考点：** 快照表重算会覆盖历史分区，但下游报表已经消费了昨天的分区，怎么设计重算机制保证下游感知与联动刷新？

### Q7. 用户维度既改手机号又改实名状态，SCD1/SCD2/SCD3 怎么取舍？

**问题：** 用户维度表里，手机号会换绑，实名状态也会变（未实名→已实名）。历史分析要追溯「某月新增用户的当时状态」，而当前报表只需要最新值。同一张表怎么设计？

**期望加分项：**
- 能说清 SCD1（覆盖）、SCD2（加版本行保留历史）、SCD3（加列存上一次）的成本与适用
- 能给出组合策略：不同字段不同策略（混合 SCD）
- 能区分「分析需要」与「运营需要」，由口径驱动
- 能联系实践：用户主数据走 SCD2 拉链，手机号等敏感字段走 SCD1
- 能说清 SCD2 的代价：事实表 join 时点版本、行数膨胀、查询变复杂
- 主动考虑换绑手机号对历史归属统计的影响

**减分项：**
- 只会说「用 SCD2」，讲不出代价
- 所有字段一刀切，不考虑字段属性差异
- 忽略 join 时点版本的复杂度与性能开销
- 不会举「SCD1 就够了」的实例

**解答：**
先给判断：没有万能策略，按字段的业务属性分桶，混合 SCD 才是实践常态。

手机号：绝大多数分析（按归属地统计、短信触达）只用当前值，历史值无分析价值，走 SCD1 直接覆盖，简单高效；除非合规审计要求留痕，但那是单独的数据留痕需求，不该拖累主维度表。实名状态：运营常做「实名 vs 未实名」对比，还要看状态变化路径，走 SCD2 保留版本，或直接拉链表。若只关心「上一次的值」（如换绑前后），SCD3 加一列 `last_mobile` 成本最低，但只能回看一步。

SCD2 实现：维度表加 `start_dt/end_dt/is_current`，每天扫描变更、闭口旧版本、新增新版本；事实表 join 时按「业务时间 between start_dt and end_dt」取「当时的」属性。代价要讲透：维度表膨胀数倍、区间 join 导致广播成本上升、必须有上游 CDC 支撑否则每天全量比对代价巨大。最大的坑：为「保历史」把所有字段都 SCD2，维度表膨胀到比事实表还大，查询性能断崖——正确姿势是先问业务「哪个历史值真的会被分析」，只对这类字段保留版本。

**延伸考点：** 手机号走 SCD1 覆盖后，某次审计要求回溯某用户全部历史手机号，不改主维度表的情况下你能用什么办法补救？

### Q8. 订单里的渠道、支付方式、优惠券，要不要单独建维度表？

**问题：** 订单表里有渠道字段、支付方式字段、优惠券码字段，值就那么几种。有人提议为它们建独立维度表做规范化，你怎么看？

**期望加分项：**
- 能说清退化维度（degenerate dimension）概念：低基数、无附加属性的字段直接冗余进事实表
- 能给出判断标准：基数值、变更频率、是否有独立属性、是否被多表引用
- 能举例：渠道就 5 种值无属性 → 退化维度；商品有几十个属性 → 必建维度表
- 能说清星型（冗余）与雪花（规范化）的权衡
- 提到一致性维度：同一渠道定义在多张表必须一致
- 联系实践：优惠券后续要关联活动与面值，才考虑建维度表

**减分项：**
- 觉得必须三范式，什么都建维度表
- 或什么都冗余进事实表，导致口径不一致
- 不会区分高基数与低基数维度
- 忽略事实表行膨胀的成本

**解答：**
先给判断：低基数、无附加属性、无独立维护需求的字段，直接冗余进事实表做退化维度；真正需要独立维度表的是「有属性、被多表引用、需单独维护」的维度。这本质是星型建模（事实表冗余常用属性）与雪花建模（全部规范化）之间的权衡——星型免 join 快，雪花省空间但查询要多次 join，数仓实践几乎总是偏向星型。

判断三步：① 基数与属性：值很少（几十个以内）且没有独立维护的属性 → 退化维度；② 变更频率：基本不变或变化不影响历史统计 → 可冗余；③ 引用需求：是否被其他事实表复用、是否需要展示附加信息 → 需要时才建维度表。

例如：渠道、支付方式 → 直接冗余 `channel_id + channel_name`；优惠券：运营要看「某活动发的券用了多少」，券关联活动与面值、且被多张事实表引用，则建 `dim_coupon`，订单表只存 `coupon_id`。商品、用户、门店这类「有大量属性、高频 join、多表复用」的，必建维度表。真正的坑：同一渠道在订单表叫 `channel_id`、在支付表叫 `pay_channel`，枚举还不一致——退化维度的前提是统一维度口径（OneData 的维度定义），否则不如建维度表。另外冗余字段要保持单一来源，别在事实表和维度表各维护一份。

**延伸考点：** 退化维度字段在事实表里维护，上游新增了一个渠道值，谁能保证事实表及时感知、全量刷新？

### Q9. 维度表主键用自增代理键还是业务自然键？

**问题：** 商品维度表，业务系统里商品有 `sku_id`（自然键）。有人说主键直接用 `sku_id` 简单，有人说要建 `sku_key` 代理键。你怎么定？

**期望加分项：**
- 能说清代理键与自然键的区别与演进背景
- 能说清自然键的问题：跨系统重复、业务键值可能被复用/变更
- 能说清代理键的代价：映射表维护、ETL 多一步、排查不便
- 能按场景取舍：单系统、稳定自然键可直接用；多源融合必用代理键
- 能说代理键与 SCD2 的配合（同一自然键多版本）
- 提到无论哪种方案都要有主键唯一性校验

**减分项：**
- 只会说「用代理键更规范」，讲不出自然键失效的场景
- 不考虑团队规模与系统复杂度，一律代理键
- 忽略代理键生成与回填的成本
- 讲不清代理键与 SCD 版本的关系

**解答：**
先给判断：取决于「自然键是否稳定唯一、数据是否多源」。单一业务系统、`sku_id` 长期稳定且全局唯一，直接当主键完全可行，省掉映射维护；多源融合（多个系统产生同一实体）或业务键可能被删改/复用时，必须上代理键。

代理键的价值：① 隔离业务变更——业务键被删改重用时，事实表 join 不受影响；② 容纳多源冲突——不同系统对同一实体编码不同，统一映射到一个 `xxx_key`；③ 配合 SCD2——同一自然键有多个历史版本，靠「key + 版本」定位。

代价要讲透：需要维护「自然键 → 代理键」映射（雪花自增 + upsert 回填）、ETL 复杂度上升、排查时看到 key 还得反查业务 id。所以小团队单系统直接自然键；跨业务线、数据整合型仓库用代理键，并用稳定的业务 `code` 做去重依据。实践坑：用自然键但没建唯一约束，上游重复数据进来导致主键冲突、join 翻倍；用代理键但回填写错，同一商品被拆成两个 key，比不用代理键还糟。无论哪种，都要配套「主键唯一性 + 自然键到代理键 1:1」的基线校验。

**延伸考点：** 两个系统合并后商品 id 冲突了（都叫 10001 但不是同一商品），怎么用代理键解决？合并时历史事实表的 key 要不要重映射？

### Q10. 用户状态要支持任意历史时点回溯，怎么建拉链表？怎么回刷？

**问题：** 需求是「任意查询某一天的活跃用户状态」「统计某月新增用户的当前状态」，用户状态每天变化。你决定建拉链表，说说怎么建、怎么回刷？

**期望加分项：**
- 能给出拉链表结构：`user_id, start_dt, end_dt, 状态字段`
- 能说出增量构建原理：与昨日当前版本比对，闭口 + 新增
- 能说任意时点查询：`where '某天' between start_dt and end_dt`
- 能说回刷/补数的处理：定位变更起点、重建受影响版本区间、端到端对账
- 能比较拉链表与 SCD2、周期快照的差异与选用
- 能说明 end_dt 用 9999-12-31（或 null）表示当前版本

**减分项：**
- 不会写建表语句或讲不清「闭口/开口」机制
- 回刷逻辑说不清，只说「重新跑一遍」
- 不考虑历史分区被覆盖的幂等性
- 拉链表与周期快照概念混淆

**解答：**
先给判断：拉链表用 start/end 双时间戳表达版本，专治「要看任意历史时点状态」。结构：

```sql
CREATE TABLE dim_user_status_lz (
  user_id  BIGINT,
  start_dt STRING,     -- 状态生效日
  end_dt   STRING,     -- 状态失效日（当前版本为 9999-12-31）
  is_active INT
);
```

增量构建：每天拿「当天全量用户状态」与「昨天当前版本」比对——状态没变不动；状态变了把旧版本 `end_dt` 改为昨天（闭口），再插入 `start_dt=今天, end_dt=9999-12-31` 的新版本；新用户直接插入当前版本。查询任意时点：`WHERE '2024-05-01' BETWEEN start_dt AND end_dt`，可秒回当天状态。

回刷是重点：补数不能只重跑某一天，因为「那天的状态」依赖历史变更链。常规做法：定位状态变化起始日，从上游重新拉取该区间数据，整体重建受影响版本区间，并做端到端对账（某日快照 = 该日拉链查询结果）。坑：闭口与新增不在同一事务/任务里，导致数据不一致；end_dt 用 null 与 9999-12-31 混用导致区间查询漏行；「全量 join 全量」比对成本高，要借助上游 CDC 只取变化行。拉链 vs 周期快照：快照每行是「天×对象」，读分区即得但存储随天数线性增长；拉链只在变化时新增行，长期更省，适合低频变化对象。

**延伸考点：** 上游某天状态数据延迟 2 天才到，你的拉链表会怎样？如何设计才能让补数与延迟数据互不污染？

### Q11. 业务方要「当日新增付费用户数」，数仓怎么保证口径统一、被各报表复用？

**问题：** 运营、财务、产品三边都在报「新增付费用户」，数字总对不上。你作为数仓，怎么把口径固定下来并让各报表复用？

**期望加分项：**
- 能先定义口径四要素：什么是「新增」（首次付费判定）、什么是「付费用户」（支付成功且未退款？）、T 日时间边界、去重粒度
- 能说「首次付费」需要全量历史判定（首次付费日 = min(支付完成时间)），不是当天有单就算
- 能说指标在 DWD/DWS 定义一次，报表只引用，而不是各报表自算
- 能提指标字典/命名规范的登记
- 能说退款、刷单、测试账号等边界的处理
- 能说口径变更的版本管理

**减分项：**
- 只回答「统一口径」这种空话，不给落地机制
- 把「当日新增付费」理解成「当天有支付」，忽略首次判定
- 不涉及退款、刷单等边界
- 说不清三端数字对不上的常见原因（时区、去重、时间点）

**解答：**
先给判断：数字对不上的根因是「口径没有沉淀为数据资产」，每张报表各自从明细算。解决分三步：定口径、落实现、管变更。

定口径：明确四要素——定义（当日首次成功付费的用户数）、时间边界（按支付完成时间、业务时区 T 日）、去重粒度（按 user_id）、边界（退款单不算、测试/内部账号剔除）。写成口径说明挂到指标字典。

落实现：DWD 沉淀「支付事实」，并先算 `first_pay_ts`（首次成功支付时间）落为字段；DWS 按日聚合出「当日新增付费用户」，ADS 报表直接读：

```sql
INSERT OVERWRITE TABLE dws_user_first_pay_d PARTITION(dt=...)
SELECT first_pay_dt, count(distinct user_id)
FROM dwd_trade_pay_df
WHERE is_success = 1 AND is_refunded = 0 AND first_pay_dt = '${dt}'
GROUP BY first_pay_dt;
```

管变更：口径调整（如「新增」改按注册时间而非首付时间）走变更评审，先改 DWD/DWS 再通知下游统一刷新，禁止各报表私下改口径。常见对不上的原因：有的按支付创建时间、有的按支付完成时间；有的按订单去重、有的按支付流水去重；0 点后延迟成功的单归属不同。这些在口径文档里逐条写明，并登记「口径版本」。核心方法论是 OneData：指标定义（口径）+ 模型设计（落地）+ 命名规范统一。

**延伸考点：** 运营说「新增」按注册时间，财务说按首次支付时间，你听谁的？有没有让两边都能对上的设计？

### Q12. 指标字典和命名规范怎么落地？定了规范没人执行怎么办？

**问题：** 你们定了指标字典和表命名规范，但新同事还是各写各的：`total_amount`、`pay_sum`、`订单金额汇总` 都有。规范怎么真正落地？

**期望加分项：**
- 能说「规范靠工具与评审强制」而非自觉：命名校验、模型评审、模板化
- 能说指标字典的治理机制：指标 = 口径定义 + 归属域 + 责任人，变更谁负责
- 能举例命名规范：dwd_业务过程_粒度、度量字段映射到原子指标
- 能说存量治理：先冻结新增口径，再逐步收敛存量，不推倒重来
- 能说用血缘/元数据工具做非法命名校验，CI 卡点
- 能说字典与线上模型绑定：模型上线必须先改字典

**减分项：**
- 只会说「开会强调、写文档」
- 没有存量治理思路，想推倒重来
- 不涉及组织机制（责任人、评审）
- 分不清规范文档与强制工具的区别

**解答：**
先给判断：规范落不了地，是因为靠「文档 + 自觉」，要靠「工具 + 评审 + 治理机制」三重约束。

① 工具强制：表命名、字段命名写入校验规则，建模平台/CI 中不合格直接拒绝上线（如 `dws_` 前缀、度量字段必须能映射到指标字典中的原子指标）；字段注释与口径链接：字段带指向指标字典 ID 的 comment，防止同名不同义。② 评审机制：新模型必须过评审会，清单包括：粒度声明、是否复用已有指标、命名是否合规、是否需要新 DWS，评审记录责任到人。③ 存量治理：老表不再扩字段，新需求一律走新规范建表；通过「指标字典 + 血缘」找出同名不同义存量，逐一确认后下线或改名，按季度设定收敛节奏，不要一次性推倒重来。④ 组织保障：每个指标有业务 + 数据双 owner，口径变更走审批流；模型变更必须先改字典再上线。

最大的坑：指标字典建了没人维护，半年后字典与线上不一致，反而成为第二套「真相」。所以要把字典绑定到模型上线流程里——没有字典登记的模型不允许上线，字典与血缘互相校验。总结一句话：规范是「评审的门禁 + 字典的登记 + 血缘的校验」，不是一份 Markdown 文档。

**延伸考点：** 线上已有一个用得很广的 `pay_sum`，口径与指标字典里的「支付金额」不一致，怎么迁移存量报表而不闪断？

### Q13. 事实表粒度与宽表：要不要把用户、商品属性全冗余成一张超大宽表？

**问题：** 分析师说「明细表 join 维度太慢」，提议把商品、用户的所有属性都冗余进订单明细，做成一张超大宽表。你同意吗？

**期望加分项：**
- 能说清宽表的收益（免 join、查询快）与代价（存储、一致性、变更成本）
- 能说取舍依据：join 频率、字段稳定性、维度属性变更对历史的影响
- 能说「事实表粒度」是前提：宽表的前提是粒度明确、一行一个事实
- 能提「按需打宽」：高频字段冗余，低频仍 join
- 能说冗余字段的一致性风险与「业务发生时点的值」语义
- 能说宽表与 DWD 明细、DWS 汇总的关系

**减分项：**
- 无脑同意或反对
- 不先确认粒度就谈宽表
- 不考虑维度属性 SCD 变更对宽表历史的影响
- 忽略宽表的产出延迟与存储成本

**解答：**
先给判断：宽表是「查询性能」与「一致性 + 成本」的交换，要按需打宽，而非全量冗余。前提是先守住事实表粒度：一行只代表一个事实（一笔订单明细），在此之上打宽才有意义；粒度混乱的表打宽后是灾难。

决定哪些字段冗余进事实表：高频切片/过滤字段（渠道、省份、品类）冗余进来省 join；业务发生时点已确定的稳定属性可以直接冗余；易变属性（如用户当前等级）冗余会带来「快照值 vs 当前值」的混乱，一般只冗余「业务发生时点的值」。打宽实现：DWD 生成时一次性 join 维度快照，把需要的字段落为物理列，之后查询不再 join。

代价要讲清：① 存储膨胀数倍；② 维度属性变更时已生成的宽表行不会自动更新，必须明确「宽表里是发生时的值」这一语义（这正是维度建模原则：事实表维度外键永远关联业务发生时的维度版本）；③ 产出链路变长，DWD 生成变慢。实践建议：以「周查询次数 × join 复杂度」排序，只打宽 Top 热点字段，其余留 join。星型建模里事实表本就可以冗余常用属性，但「全属性冗余」是过度设计。坑：宽表越加越宽，字段上百后无人敢动，任何维度变更都要全量重刷历史——建议设「冗余字段登记表」记录每个打宽字段的依据与刷新策略。

**延伸考点：** 用户等级在订单发生后变了，宽表里是旧等级，分析师要「按当前等级统计历史订单」，你怎么办？改宽表还是另建关联表？

### Q14. 主题域怎么划分？订单、支付、退款该归哪个域？

**问题：** 你们要梳理主题域，有人说按「业务部门」分（交易域、运营域、财务域），有人说按「业务过程」分（下单、支付、退款、发货）。你怎么定？支付会不会因为既被交易看又被财务看而分裂？

**期望加分项：**
- 能说主题域按「业务过程 + 实体」划分，而非部门
- 能说主题域是逻辑分层，物理实现可跨域引用
- 能说「同一业务过程只归一个域」，避免口径分裂
- 能处理跨域场景：支付事实归交易域（只存一份），财务域引用而非复制
- 能给出域的划分结果并说明边界判断标准
- 能联系 OneData 规范实践与域 owner 机制

**减分项：**
- 按部门切域，导致同一指标两边各算一套
- 主题域划分凭感觉，无判断标准
- 把域当成物理隔离，域间完全不能引用
- 不考虑存量系统与人员归属的落地阻力

**解答：**
先给判断：主题域按「业务过程的自然边界」划分，与组织架构解耦——同一个业务过程（如支付成功）只归一个域，其指标由该域负责定义，其他域引用而非复制。

常用划分（电商）：交易域（下单、支付、退款、发货等业务过程）、商品域（商品、类目、品牌）、用户/会员域（注册、登录、画像）、营销域（活动、优惠券、触达）、履约域（库存、物流、签收）、财务域（对账、结算）。判断标准问三个问题：① 这个业务过程由谁产生、谁消费？② 它与哪些实体强相关？③ 与其他域的耦合是否通过「外键 + 指标引用」而非数据复制？

跨域处理是重点：支付既被交易域统计（支付金额），也被财务域对账（实收金额）。做法是支付事实表物理上只存一份、归交易域，财务域通过引用 + 口径差异（含手续费/退款）建立自己的汇总，而不是复制一张支付表改个名。这样口径源唯一，域间只有引用关系。坑：为部门 KPI 各自建域，交易域算一遍 `order_amount`、运营域又算一遍，数值不同——这就是主题域划分失败的典型信号。落地时每个域配 owner，域内数据模型与指标由 owner 负责评审与质量。

**延伸考点：** 支付事实既归交易域又被财务域引用，两边对「支付成功」的定义不一致（含不含退款单）时，数仓怎么仲裁？

### Q15. 数据血缘：上游字段改名/调整含义，怎么提前评估影响面？

**问题：** 业务系统要改订单表字段（比如把 `pay_time` 改名 `payed_at` 并调整含义），你作为数仓负责人，怎么评估影响面、怎么把损失降到最小？

**期望加分项：**
- 能说清字段级血缘的作用：定位受影响的下游表与任务
- 能说评估流程：血缘 → 定位 DWD/ADS → 判断改名还是语义变化 → 排期改造
- 能说血缘获取方式：解析 ETL SQL、调度依赖、人工登记
- 能说没有血缘时的应对：命名规范 + 变更窗口 + 自动对账
- 能提到「上游变更管理」：与业务系统的变更通知机制
- 能说 ODS 保留原始字段、DWD 显式映射，隔离上游变更

**减分项：**
- 只想到「等报错再修」，没有主动影响面评估
- 不知道字段级与表级血缘的区别
- 不考虑口径变化（不只是改名）
- 没有落地的血缘治理机制

**解答：**
先给判断：影响面评估依赖「字段级血缘 + 上游变更管理」双机制，没有血缘就只能被动挨打。

① 血缘建设：解析数仓所有 ETL SQL（Hive/Spark 解析器可产出表级 + 字段级血缘），存储到血缘库。评估时输入 `pay_time`，直接输出下游全部表与任务清单，按报表重要度排序。② 评估流程：拿到清单后逐个判断——纯改名（语义没变）：DWD 同步映射、验证即可；语义变化（如从「支付创建时间」改为「支付完成时间」）：会影响所有依赖该字段的指标口径，必须联动指标字典，评估哪些报表数字会变、是否需要新旧字段双轨并行一段时间。③ 落地机制：与业务系统约定「变更提前通知窗口」（如 1 周），上游变更评审纳入数仓；ODS 保留原始字段命名（`_src`），DWD 做显式映射，这样上游改名只影响 ODS→DWD 一段，DWD 下游通过血缘刷新。

坑：很多团队血缘只做到表级，字段改名根本查不出来，只能等凌晨任务失败才发现；血缘解析会漏掉动态 SQL、union、临时表，评估结论不准。建议以「字段级血缘 + 变更评审流程 + 变更后自动对账（上线前后字段值分布对比）」组合兜底。

**延伸考点：** 业务系统没有版本管理，改了字段也不通知，你们怎么做到「改了也能及时发现」？

### Q16. 同样的指标在多张表重复计算，怎么治理？

**问题：** 你们仓库里「支付金额」这个指标在 5 张表里都有，口径还不完全一样，维护成本很高。怎么治理模型复用与冗余？

**期望加分项：**
- 能说「指标只在一个地方实现，其他引用」的原则（OneData）
- 能说清「原子指标 + 派生指标」体系：支付金额是原子指标，不同过滤/聚合是派生
- 能说从血缘找重复实现、合并
- 能说治理节奏：先冻结新增，再存量收敛，避免一刀切
- 能说同一指标不同口径的仲裁机制（口径 owner）
- 提到用指标字典与模型评审强制复用

**减分项：**
- 只会说「减少重复」没有手段
- 建议推倒重来，不考虑存量迁移风险
- 不考虑「合理差异」不能合并
- 没有「冻结新增」的治理节奏

**解答：**
先给判断：先分清「真冗余」与「合理差异」——同一个原子指标因维度、过滤条件不同产生多个派生，是正常建模；真正要治理的是「同口径同粒度却在多处重复实现」。

治理四步：① 盘点：用血缘找出「支付金额」的所有实现点，按粒度、过滤条件、时间边界归类，标出完全同口径的实现。② 建体系：定义原子指标（支付金额 = 支付成功且未退款的支付流水金额）沉淀到指标字典；派生指标 = 原子指标 + 维度 + 过滤 + 聚合方式，统一由 DWS 按「原子指标 × 维度组合」实现，报表不再自算。③ 冻结新增：新指标先查字典，已有原子指标一律引用，不允许重新实现，模型评审卡这一点。④ 存量收敛：对完全冗余的实现，选最底层的权威实现（一般是最早的 DWS），迁移下游引用后逐个下线，按优先级排期。

坑：迁移时旧实现口径可能漂移过，数字会暂时对不上，所以要「对账 + 双跑」确认一致再切换；另一个坑是把「合理差异」当成冗余合并掉——财务口径（含未结算）与运营口径（剔除退款）本就不该合并。总结：治理的本质是把「指标的实现权收归到 DWS 层，报表层只做引用」。

**延伸考点：** 两个团队都维护着自己的支付金额表且口径不同，其中一个数字和财务对不上，如何在不推翻双方的前提下让数字收敛？

### Q17. 业务库表结构经常变，数仓怎么跟上？增量同步怎么做才稳？

**问题：** 业务方经常在订单表加字段、改字段类型，你们的同步任务隔三差五挂掉。怎么设计 ODS 同步与 DWD 映射，让数仓对上游变更更鲁棒？

**期望加分项：**
- 能说 ODS 全字段同步 + DDL 变更自动感知（加字段兼容、删字段/改类型破坏）
- 能说增量同步选型：binlog/CDC、时间戳增量、全量对比，各自适用
- 能说 DWD 显式映射：字段变更先在 DWD 调整，不在 ODS 层丢数据
- 能说同步监控：延迟、乱序、重复、行数波动
- 能说幂等设计与重跑机制
- 能说 CDC 的 schema 演进处理

**减分项：**
- 只会说「用 binlog」，不考虑字段变更的兼容性
- ODS 只同步需要的字段，变更时直接挂
- 不区分破坏性与兼容性变更的处理差异
- 没有同步质量监控的考虑

**解答：**
先给判断：鲁棒性的关键在于「ODS 全量字段 + 变更分级 + DWD 显式映射」，把「上游变」与「数仓稳」解耦。

① ODS 层：同步全字段（不裁剪），保存上游原始结构；通过元数据比对自动感知 DDL 变更——加字段是兼容变更，自动放行并告警记录；删字段/改类型/改长度是破坏性变更，自动阻断并通知负责人评估。② 增量同步选型：需要近实时 → binlog/CDC，注意 DDL 变更时 CDC 的 schema 演进（能否自动加列）、乱序与延迟；T+1 且量大 → 时间戳增量（需业务表有稳定更新时间字段），注意当日窗口边界；量小或可靠性优先 → 每日全量对比。③ DWD 映射：用显式 `SELECT a AS b` 映射，新增字段先在 DWD 元数据登记、补映射再上线，防止 DWD 悄悄丢列。

坑：同步挂的典型原因——上游加字段后 CDC 解析 schema 不一致；时间戳增量漏掉「更新时间没变但内容被改」的行（建议结合业务校验字段）；凌晨任务因上游大事务延迟被误判为故障。最后是监控三件套：延迟分钟数、本日行数 vs 昨日波动率、主键唯一性校验，异常先告警再人工介入，别等报表方来找。

**延伸考点：** 业务方直接改了一条历史数据（未走正常更新流程），增量同步感知不到，怎么发现并修复？

### Q18. 实时数仓和离线数仓建模的差异在哪？同一套分层能用吗？

**问题：** 你们要上实时数仓（分钟级看板、实时风控特征），离线那套 ODS/DWD/DWS/ADS 建模体系还能照搬吗？差别在哪？

**期望加分项：**
- 能说分层思想沿用，但每层实现形态与粒度不同
- 能说实时 DWD 更「轻」：只做必要清洗打宽，不做重加工
- 能说实时 DWS 按分钟/小时窗口预聚合，明细流 + 汇总流并行
- 能说流批对账：实时汇总与离线汇总每日交叉校验收敛
- 能说流式 join 的窗口与状态管理难点、乱序迟到处理
- 能说存储选型差异：Kafka/OLAP 替代 Hive
- 能说「先离线保底，实时补时效」的稳妥策略与成本考量

**减分项：**
- 说「完全一样」或「完全不一样」，讲不出具体差异
- 把实时做成「离线的加速版」而没有对账机制
- 忽略乱序、迟到、状态管理等实时特有难点
- 不考虑实时资源成本，一股脑全实时化

**解答：**
先给判断：分层思想（清洗-明细-汇总-应用职责分离）可以沿用，但每层实现形态都不同，且要新增「流批一体」的对账机制。

实时 ODS：Kafka 中的原始事件，保留原始结构；实时 DWD：轻加工——必要解析、字段补齐、维度打宽（维表 join 需注意维表版本管理），不做重的多流 join 聚合，复杂逻辑留给离线；实时 DWS：按分钟/小时窗口预聚合高频指标；实时 ADS：直接对接看板与接口。关键差异：① 乱序与迟到：事件时间 vs 处理时间，需 watermark 与延迟补算策略；② 流式 join 的状态管理：双流 join 维护窗口状态，状态膨胀要设 TTL；③ 幂等与重放：checkpoint + 下游幂等写，别让 Exactly-once 被下游打破；④ 对账：每天用离线 DWS 对实时 DWS 交叉校验，偏差超阈值（如 0.5%）告警并写明容忍度——这是实时质量的生命线；⑤ 成本：实时资源与存储更贵，只把时效敏感指标上实时，其余走离线。

坑：很多团队把离线任务用 Flink 重写一遍就叫实时数仓，结果延迟只快了 2 小时、资源多了 3 倍、还经常对不上账。正确姿势是「离线保底 + 实时补时效」，且对账闭环必须有。

**延伸考点：** 实时看板的「支付金额」和离线报表每天差 3%，你怀疑是乱序或迟到数据，怎么定位？怎么收敛？

### Q19. 指标中台 / 指标平台怎么设计？「指标」应该怎么管理？

**问题：** 公司要做「指标平台」，让业务自助取数。指标怎么定义、怎么落地、怎么做到「同一指标全公司一个数」？讲讲你的设计。

**期望加分项：**
- 能说指标四要素：原子指标、派生指标、维度、口径（过滤条件）
- 能说「逻辑定义与物理实现分离」：平台管逻辑指标，映射到 DWD/DWS 物理字段
- 能说指标生命周期：登记→评审→上线→变更→下线
- 能说自助取数：指标 + 维度组合自动生成 SQL，业务不接触物理表
- 能说指标字典与血缘联动、变更影响分析
- 能说指标 owner（业务 + 数据双签）机制
- 能区分指标平台与 BI：平台是口径治理，BI 是展示

**减分项：**
- 把指标平台理解成「报表平台」
- 只做元数据登记，不做口径统一
- 不考虑指标与物理模型的映射（指标找不到实现）
- 不考虑权限、质量监控、变更流程
- 把平台当成纯前端系统，无治理闭环

**解答：**
先给判断：指标平台的核心不是「查指标」，是「口径治理」——让指标的逻辑定义、物理实现、变更流转全生命周期被管理。

设计要点：① 指标建模：原子指标（支付金额、新增用户数）只定义一次；派生指标 = 原子指标 + 维度 + 过滤（如「华东区、移动端、支付成功」）；维度统一维护。这是 OneData 体系在平台上的体现。② 逻辑与物理分离：每个指标映射到 DWS 物理字段，上线必须经过「找实现、落模型」两步——先查已有模型能否覆盖，不能才新建 DWS，保证指标有唯一实现，避免「字典里定义了但没人用」。③ 自助取数：业务选指标 + 维度 + 时间，平台自动拼 SQL 从底层模型查询，业务不接触物理表名；平台记录查询血缘，反向补充指标热度。④ 治理闭环：指标 owner 双签；变更先做影响面分析（字段级血缘给出受影响报表清单），评审后发布，历史口径保留版本；质量监控挂在指标上（与前日波动、对账基准对比）。⑤ 扩展：下钻、预警、权限与脱敏。

最大的坑：指标平台只做了「字典登记」，业务自助取数时发现平台指标与报表数字对不上，因为物理实现漂移了——所以「指标的物理映射 + 定期对账」必须纳入平台功能，而不是靠文档。总结：指标平台 = 口径定义（逻辑）+ 模型映射（物理）+ 变更管理（流程）+ 质量监控（数据）四件套。

**延伸考点：** 业务提了个新指标「高价值用户支付金额」，其中「高价值用户」有 3 种定义，平台怎么建模？让业务自己选过滤条件还是平台统一口径？

### Q20. 大促后日报数字对不上：GMV 少了 800 万，怎么排查？

**问题：** 大促结束后，运营日报显示 GMV 8000 万，财务系统核对是 8800 万。让你牵头排查，你从哪入手？给个完整的排查路径。

**期望加分项：**
- 能结构化排查：先确认「比对的是不是同一件事」（口径），再查数据链路
- 能列出常见原因：口径差异（含退款/未支付/刷单）、时间边界、重复/丢失、DWD 加工 bug、同步延迟
- 能从差异方向与量级反推：数仓少 vs 财务多，先怀疑丢数据还是口径
- 能给出验证手段：ODS 原始数据重算、与业务库 count/sum 对账、抽样明细比对
- 能说「先止血再根治」：临时修正报表 → 定位根因 → 加监控对账
- 能提到每日自动对账是防止此类问题的根本
- 主动考虑佣金、退款、优惠券抵扣等口径要素

**减分项：**
- 上来就怀疑代码 bug，不先核对口径
- 无排查路径，想到哪查哪
- 只查数仓，不回到源系统验证
- 没有「事后预防」的建设意识

**解答：**
先给判断：排查顺序是「先对齐口径 → 再定位链路 → 最后根因修复 + 建立对账」。80% 的此类问题第一关就出在「两边数的是不是同一件事」。

排查路径：① 对齐口径：让运营和财务把口径逐条列出——统计时间边界（是否都按支付完成时间、哪个时区）、含不含退款/取消/未支付、是否剔除测试与刷单、是否含虚拟商品/优惠券抵扣。多数情况下到这里数字就解释通了（比如财务含退款，运营剔除了）。② 若口径一致，查链路：沿「业务库 → ODS → DWD → DWS → 报表」逐层对账，每层用 count + sum 与上游对比定位断点。常见断点：ODS 增量同步丢分区（延迟/乱序）、DWD 去重把正常单当重复删了（如同一订单多支付流水）、DWS 时间边界实现错误（00:00:00 边界算错）、刷单过滤口径两侧不一致。③ 回到源系统：对业务库直接跑同一口径 SQL（低峰期），与数仓 DWD 明细做全量或抽样比对，锁定「是源没进数仓」还是「数仓算错」。④ 止血与根治：紧急先出修正口径的报表；根因定位后修 ETL 并补数；然后建立「每日自动对账」——数仓汇总 vs 业务系统汇总、DWS vs DWD 重算，偏差超阈值自动告警。

坑：大促期数据量大，对账 SQL 要控制资源（抽样 + 分区裁剪）；排查时别只盯 SQL 逻辑，同步链路（CDC 延迟、乱序消费）和人为操作（有人手动改过数据）也是高频原因。这套「口径第一、分层对账、自动监控」的机制，就是数仓质量体系的日常工作，问题排查只是它的应急形态。

**延伸考点：** 财务说多、数仓说少，两边都坚称自己口径正确，怎么用「证据」而不是「辩论」让双方收敛？（提示：最小对账集合、抽样明细）
