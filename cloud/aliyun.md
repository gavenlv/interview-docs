# 云 · 阿里云（面试题库）

本文件考察候选人在阿里云平台工程落地上的真实能力，覆盖地域可用区、ECS、容器 ACK、存储 OSS、数据库 RDS/PolarDB、网络 VPC、RAM、安全与成本等核心领域。题目全部为场景化提问、不考八股文——重点看候选人能否给出量化依据、说清产品选型的取舍、引用线上实践佐证、主动覆盖边界条件，难度从实践基础渐进到架构级设计。能用 CLI 命令、控制台配置和真实数字说清楚问题，比背诵产品文档更关键。

### Q1. 系统要上线海外市场，阿里云地域怎么选？

**问题：** 公司要把面向东南亚的电商 App 从国内迁到海外，团队里有人建议选新加坡、有人建议选印尼雅加达，还有人建议直接买 AWS 的海外节点。请从地域（Region）、可用区（AZ）、全球节点布局出发，说明阿里云与 AWS/Azure 的差异，以及你如何决策部署地域。

**期望加分项：**
- 说清地域与可用区的层级关系：地域是物理隔离的数据中心集群，可用区是同一地域内电力/网络独立的单元；同地域跨可用区延迟 1-2ms，跨地域 30ms+
- 量化选区依据：主目标用户所在地的延迟（如雅加达机房对印尼本地延迟 <10ms，从新加坡回源则 30-50ms）、合规（数据本地化要求）、成本（印尼带宽与机器成本低于新加坡）
- 指出阿里云海外节点特色：新加坡是出海默认枢纽、与 AWS 的全球节点差距主要在拉美/非洲覆盖；阿里云提供全球加速 GA 与跨境专线（如 CEN + 海外 POP）
- 给出多可用区部署方案：同一地域至少 2 个可用区做高可用，跨可用区用 SLB + 多活，RDS 用主备跨可用区
- 能说出阿里云与 AWS 的差异点：账号体系（RAM vs IAM）、产品命名（SLB vs ELB、OSS vs S3）、可用区概念一致但 API 风格不同，迁移需考虑云厂商锁定
- 主动提及"双区域容灾"或"就近接入 + 中心化数据"的混合架构

**减分项：**
- 说不清地域与可用区的区别，把"多可用区"等同于"多地域"
- 只凭感觉选"新加坡是东南亚枢纽"，拿不出延迟/合规/成本数据
- 不知道阿里云与 AWS 在可用区概念、计费、IAM 等上的本质差异，只说"都差不多"
- 忽略合规（印尼要求数据本地存储）与网络链路（回源延迟、跨境专线费用）
- 不做多可用区高可用设计，单可用区裸奔

**解答：**

先厘清概念：地域（Region）是物理上隔离的数据中心集群，可用区（AZ）是同一地域内电力、网络、制冷独立的单元。同地域跨可用区专线延迟约 1-2ms，跨地域通常 30-100ms，这是架构决策的物理前提。选地域要按三个维度打分：一是延迟，用主目标用户所在城市测速（阿里云提供延迟测试工具），雅加达机房对印尼本地延迟个位数毫秒，从新加坡接入则多一跳；二是合规，印尼、菲律宾等国要求用户数据本地存储，合规风险直接否决远程地域；三是成本，印尼的 ECS/带宽单价通常低于新加坡，但国际带宽回源国内很贵。阿里云海外布局与 AWS 的差距主要在拉美、非洲和澳大利亚，东南亚反而是阿里云深耕区（新加坡、雅加达、吉隆坡、马尼拉均有节点）；若主战场在欧美，AWS 的节点密度和生态可能更合适。架构上：选雅加达为主地域，至少跨 2 个可用区部署，SLB 挂后端 ECS，RDS 开启多可用区主备自动切换，OSS 用同城冗余；如果用户遍布东南亚多国，可以新加坡做接入点、通过全球加速 GA 就近回源，数据统一落到合规地域。实践中的坑：一是跨境回源要走专线或 GA，直接公网回源抖动大且带宽费高；二是可用区满用或新品上架延迟，上线前要确认目标 AZ 的 ECS 实例库存；三是账号体系差异，海外账号的 RAM 策略、账单币种、备案政策与国内版不同，很多国内团队的 Terraform 脚本直接迁到国际站会踩 API endpoint 差异的坑。

**延伸考点：** 如果同时服务东南亚与中东用户，且业务要求单写多读的全球一致性，地域如何设计？用什么产品解决跨地域数据同步与就近读？

### Q2. 大促流量翻 20 倍，ECS 规格和计费怎么设计？

**问题：** 你们有个 Web 服务跑在 2 台 4C8G 包年包月 ECS 上，双 11 大促流量预计翻 20 倍且持续 6 小时。请设计 ECS 的规格选型、计费组合（包年包月/按量/抢占式）与容量方案，并解释安全组在这套方案里的作用。

**期望加分项：**
- 说清规格族选型逻辑：通用型 g8i 适合 Web 应用，计算型 c8i 适合 CPU 密集，内存型 r8i 适合缓存/内存计算，突发性能 t6 只适合低负载开发环境；选型看 CPU 主频、网卡能力（如 g8i 支持 100G 内网）与 vCPU:内存比
- 计费组合给出量化方案：基线 2 台包年包月保底（约 5-7 折），大促 18 台按量扩容（按小时付费），批处理/无状态任务用抢占式（价格约为按量 1-5 折，但可能被回收）
- 容量规划有依据：按 QPS 与单机并发能力测算（单台 4C8G 大概 3000-5000 QPS 纯 API），预留 30% 冗余，峰值规模 = 2 台 × 20 倍 ÷ 单机容量
- 说明弹性扩缩容流程：负载均衡 + 弹性伸缩组 + 自定义镜像一键拉起，预热完成再切流量；安全组按应用分层（Web/APP/DB 各一组），控制台可见性隔离与最小权限
- 指出抢占式实例的坑：中断回收（阿里云回收前给 5 分钟通知，5 分钟内的实例直接释放），必须配合无状态设计 + 自动重拉
- 提到底层资源隔离：独享型 vs 共享型（突发性能实例有 CPU 积分限制），大促核心链路必须独享

**减分项：**
- 只会说"加机器"，说不清规格族差异与选型依据
- 不知道抢占式实例会被回收，把有状态服务（如 Redis）也放上去
- 忽略安全组，或者一个安全组管所有机器、端口全开
- 不算账：包年包月 vs 按量 vs 抢占式的价格差异与适用场景说不清
- 忽略镜像与启动脚本，扩容要人工一台台装环境

**解答：**

设计分三步。第一步定规格：核心链路选通用型（如 g8i/g7 的 4C16G 或 8C32G），Web 层是 IO 与网络混合负载，通用型性价比最高；纯计算任务用计算型 c 系列，内存密集用 r 系列。特别注意 g 系列的新一代实例提供更高的内网带宽与 PPS（如 8C 规格支持 25Gbps 内网），对高并发 RPC 很重要。第二步定计费组合：基线容量（常态流量 + 30% 冗余）用包年包月，通常 1 年 5-6 折、3 年更低；弹性增量用按量付费，随启随停；可重入的批处理/离线任务用抢占式（spot），价格约为按量的 1-5 折，但实例可能被回收——阿里云回收前约 5 分钟通知（通过 Metadata 或事件），无状态任务靠自动重建扛过去。第三步定弹性与安全：用弹性伸缩组 ESS 绑定自定义镜像（含环境与启动脚本），配合 SLB 的加权轮询，通过"先扩容预热 → 再切流量 → 结束后缩容"流程平滑支撑大促。安全组按层划分：Web 组只对 SLB 的 80/443 开放，APP 组只对 Web 组的内网网段开放，DB 组只对 APP 组开放且不开公网；每个安全组遵循最小权限，修改安全组规则即时生效（状态化防火墙）。实践中的坑：一是包年包月机器大促前想扩容要先转按量或另开按量机器，跨可用区注意库存；二是抢占式在华东 1 等热点地域回收率高，要配置多可用区分散；三是别忘开"节省停机"（按量实例停机不收费但保留数据盘），大促后及时释放多余实例；四是镜像要内置 jemalloc、fd 限制等生产参数，避免扩容后性能不一致。

**延伸考点：** 抢占式实例被回收后，伸缩组如何保证容量？为什么说"先扩容后切流"的顺序在大促期间是命门？

### Q3. 公司要做容器化，ACK、ASK、SAE、FC 怎么选？

**问题：** 你们有一个 30 个微服务的老系统要容器化，同时有一个新的实时数据处理任务要用事件驱动。技术选型会上出现四个方案：ACK（托管 K8s）、ASK（Serverless K8s）、SAE（Serverless 应用引擎）、函数计算 FC。请给出选型决策框架和各自的适用边界。

**期望加分项：**
- 明确四者的定位：ACK 是托管 K8s 控制面、节点自管；ASK 是免节点、Pod 按量付费的 Serverless K8s；SAE 是免容器概念的应用托管 PaaS（部署 WAR/JAR/镜像，支持微服务治理）；FC 是事件驱动 FaaS
- 决策依据分层：团队有没有 K8s 运维能力 → 工作负载是否无状态/突发 → 应用是不是微服务/是否要服务治理 → 是否需要常驻进程与长连接
- 给出场景匹配：老 Java 微服务（Spring Cloud/Dubbo）选 SAE 最省事（自带注册中心、限流降级、链路追踪）；标准 K8s 化团队选 ACK；不想管节点、突发量大选 ASK；事件驱动/定时任务选 FC
- 能算弹性账：ASK/SAE 的弹性粒度到秒级、Pod 数随流量增减，FC 到函数粒度；对比 ACK 需要节点级伸缩（Cluster Autoscaler 分钟级）
- 指出成本差异：ACK 节点常驻费 vs ASK/SAE 按资源用量计费（注意 ASK 的调度延迟与抢占式 Pod 限制），FC 闲置零成本但有冷启动
- 提醒迁移坑：老系统迁 SAE 要考虑 JDK 版本、中间件版本兼容；迁 ACK 要考虑存储、Ingress、日志采集改造

**减分项：**
- 四个产品分不清，把 ASK 和 FC 混为一谈
- 不评估团队能力，只会"上 K8s 最潮流"
- 忽略 SAE 对微服务治理（注册中心/配置中心/限流）的内置支持，这是它最大的差异化
- 不知道 FC 的约束（冷启动、时长上限、无状态），把常驻任务硬塞进去
- 不讲迁移成本与存量改造，只谈"新架构多好"

**解答：**

选型框架看三个变量：团队 K8s 能力、负载形态、治理诉求。第一，团队有 K8s 运维能力且负载常驻 → ACK：控制面托管（etcd 自动备份、版本一键升级），节点自管，适合有明确容器化路线、需要自定义调度/网络插件的团队；注意 ACK 节点按量付费常驻，低峰也要付钱。第二，负载突发强、不想管节点 → ASK：免节点，Pod 按用量计费，适合批处理、定时任务、突发 Web；坑是 Pod 调度有秒级延迟、不能挂常规 DaemonSet（如日志采集要开 sidecar 模式）、部分实例族不可用。第三，存量 Java 微服务 → SAE 往往是性价比之王：它包装了"容器"概念，直接部署 WAR/JAR/镜像，内置注册中心（Nacos）、配置管理、服务鉴权、限流降级、全链路灰度，不用自己搭 K8s 全家桶；适合 Spring Cloud/Dubbo 老应用平滑上云，运维成本远低于 ACK 自建微服务底座。第四，事件驱动/任务型 → FC：按调用计费、闲置零成本、自动弹性到函数粒度，配合 EventBridge、定时触发、OSS/SLS 事件触发非常顺滑；约束是冷启动（Java 严重）、最长执行时长（默认 24h 内）、无状态、不适合长连接。混合架构很常见：核心业务跑 ACK/SAE，外围事件任务跑 FC，中间用事件总线解耦。实践中要避免的坑：把有状态应用（如带本地缓存的网关）直接迁 FC；在 ACK 里为临时任务常驻节点浪费成本；存量应用迁 SAE 时忽略 JDK 版本与中间件（如 Redis 客户端）兼容性验证。

**延伸考点：** 选 ACK 的话，Pod 级弹性（HPA）和节点级弹性（CA）分别解决什么问题？为什么大促前要预热？

### Q4. 日志和用户图片都放 OSS，存储成本怎么控制？

**问题：** 你们的 OSS Bucket 里既有 1 年内的业务日志（每天新增 200GB）、又有用户上传的图片（总计 5TB，最近 3 个月活跃），还有监管要求必须保留 7 年的订单归档。月度账单里存储费越来越贵。请设计 OSS 的 Bucket 划分、存储类型与生命周期方案，并说明权限如何管控。

**期望加分项：**
- 说清 OSS 四种存储类型与价格梯度：标准（0.12 元/GB/月）、低频（0.08 元）、归档（0.033 元）、冷归档（0.015 元），并指出访问时额外收取数据取回费（低频 0.06 元/GB、归档 0.06-0.12 元/GB）
- 生命周期规则落地：日志按天目录前缀（log/2026/08/），规则"创建 30 天后转低频、90 天后转归档"；图片冷热分离：活跃图片转标准 + CDN，90 天未访问转低频
- 给出"取回费 + 最小对象大小"的算账：归档存储最小计量 64KB、低频最小计量 64KB，小文件不适合转低频（存储省了但取回费和请求费可能倒挂）
- 权限与安全：Bucket 私有 + STS 临时凭证给前端直传（post policy），RAM 策略按 Bucket/前缀授权，不开公共读，防盗链 Referer 白名单
- 版本控制与合规：开启版本控制防误删，但老版本也占用存储（费用翻倍风险），要配合生命周期清理非当前版本
- 跨区域复制与容灾：异地容灾用 CRR，但注意复制后的存储费双份

**减分项：**
- 只会说"日志放低频、归档"，说不出价格与取回费，算不清小对象是否划算
- 不知道生命周期规则的最小计量（64KB）与取回费，方案算完反而更贵
- 给前端直传开了公共读写权限，或者整个 Bucket 公共读泄露用户图片
- 忽略版本控制导致的存储膨胀
- 不按目录前缀设计生命周期，规则写死全 Bucket 统一策略

**解答：**

先按数据特征分桶：业务日志、用户图片、订单归档分属不同 Bucket，每个 Bucket 生命周期独立，避免互相影响。存储分层用标准→低频→归档的梯度：日志用目录前缀 log/YYYY/MM/DD 组织，生命周期规则设为"对象创建 30 天后转低频、90 天后转归档、730 天后删除"；图片用标准 + CDN 加速活跃访问，配合"最后访问时间"（OSS 支持基于 LastAccessTime 的生命周期）把 90 天未访问的转低频；订单归档直接归档存储，7 年到期用生命周期删除。关键在算账：归档存储 0.033 元/GB/月看似便宜，但取回要 0.06 元/GB 起步，且最小计量 64KB——大量 1-10KB 的小日志对象转低频后，存储费只省一点、请求费与取回费可能倒挂，所以小对象要么合并（如日志先聚合再上传）、要么留在标准层。权限管控是另一条线：Bucket 一律私有，前端直传用 STS 临时凭证 + post policy 限定 object key 前缀与大小（防止绕过成本限制传大文件），RAM 用户按"Bucket/前缀"粒度授权，运维只用子账号+角色，关键 Bucket 开版本控制防误删——但版本控制会让每次覆盖产生历史版本占用存储，务必加"清理非当前版本"的生命周期规则，否则存储成本悄然翻倍。实践中的坑：一是生命周期规则写错前缀导致数据被提前删除且不可恢复（测试环境先小范围验证）；二是跨区域复制（CRR）会产生双份存储费；三是没开日志转存（OSS 访问日志转 SLS）就无从分析成本构成。

**延伸考点：** 用 OSS 做前端直传时，为什么用 STS 而不是 AccessKey 写死在客户端？post policy 如何限制文件大小和数量？

### Q5. 业务量涨了 10 倍，RDS 还是 PolarDB？

**问题：** 你们的核心订单库跑在 RDS MySQL 8 双机高可用（4C16G）上，最近业务量涨 10 倍，CPU 经常打满，DBA 提议上只读实例做读写分离，架构师则建议迁 PolarDB MySQL。请对比 RDS 与 PolarDB 的架构差异，给出你的选型结论和迁移要点。

**期望加分项：**
- 点出本质差异：RDS 是"主备 + 只读副本"的传统架构，存储是云盘；PolarDB 是"计算与存储分离 + 共享分布式存储"架构，一写多读，存储层多副本自动容错
- 说清 PolarDB 三大优势：只读节点共享同一份存储（加只读节点秒级生效、不用拷贝数据）、Binlog 复制改共享存储读取（主备延迟毫秒级 vs 传统主备秒级）、存储扩容自动（不用迁移数据）
- 量化对比：PolarDB 只读节点最多 15 个、集群规格弹性升降不影响数据；RDS 只读实例需要数据拷贝，加节点要等同步完成
- 选型逻辑：读写比高（读占 80%+）、并发抖动的在线业务 → PolarDB；对 MySQL 版本、已有运维工具链强依赖或预算敏感 → RDS 加只读
- 迁移要点：DTS 支持不停机迁移（全量+增量），回滚方案保留原 RDS 一段时间；连接串切换、账号权限同步、存储过程/触发器兼容性测试
- 提醒成本陷阱：PolarDB 按"计算规格 + 存储用量"计费，存储按 GB 收费、只读节点按规格收费，算清与 RDS 磁盘价格的差异

**减分项：**
- 把 PolarDB 当"更强的 RDS"，说不出计算存储分离的架构差异
- 只谈"性能好"，答不出为什么快（共享存储、只读不拷贝、延迟低）
- 忽略迁移的停机窗口、兼容性与回滚，拍脑袋"直接迁"
- 不评估读写比，无条件无脑推 PolarDB
- 不知道 DTS 迁移的增量同步与校验流程

**解答：**

先讲架构，选型才有依据。RDS MySQL 是经典主备架构：一个主实例 + 一个备实例（同步复制）+ 可选的只读实例，所有实例各自挂云盘，只读实例要独立拷贝一份数据，所以加只读节点耗时且主备延迟受网络和 IO 影响（正常 1 秒内，大事务可飙到几十秒）。PolarDB MySQL 把存储抽出来做成分布式共享存储（PolarStore）：计算节点（主 + 最多 15 个只读）共享同一份存储，只读节点扩容秒级生效、不拷贝数据；主从之间走共享存储而非 Binlog 复制，延迟压到毫秒级；存储空间随数据自动扩容，IO 能力随节点数线性扩展。对你们"读多写少 + CPU 打满"的场景，PolarDB 的优势非常直接：加 2-4 个只读节点即可把读压力平摊，且不用等数据拷贝。选型结论：读写比高、希望在分钟级内弹性扩读、且对 MySQL 兼容性要求高（PolarDB 兼容 MySQL 8.0 语法与协议，业务代码几乎不用改）→ 选 PolarDB；如果团队对 RDS 运维体系（监控、备份、Binlog 订阅）非常熟练、预算敏感，也可以 RDS 主实例 + 2 个只读实例做读写分离，但要注意只读实例的同步延迟与扩展瓶颈。迁移要点：用 DTS 做"全量 + 增量"不停机迁移，业务切换前做数据校验（行数、checksum），切换后保留原 RDS 至少一周用于回滚；应用层用 ProxySQL/ShardingSphere 或 PolarDB 自带的集群地址做读写分离，连接串与账号权限要提前对齐。实践中的坑：PolarDB 的 Binlog 默认保留时长与 RDS 不同，依赖 Binlog 做数据订阅的链路要单独配置；只读节点是共享存储，跑大查询（全表扫描）会占存储 IO 影响主节点，要用一致性读与限流兜底。

**延伸考点：** PolarDB 的只读节点为什么没有传统主备的同步延迟？大查询在 PolarDB 上对主节点的影响路径是什么？

### Q6. 双缓存热点与双 11 削峰，Redis 和消息队列怎么搭？

**问题：** 你们的商品详情页缓存用自建 Redis 在 ECS 上跑，双 11 预热后仍被热点商品打爆；同时订单系统要承接瞬时 10 万 QPS 的下单洪峰，订单要可靠落库。请给出阿里云 Redis/Tair 的选型与高可用设计，以及 RocketMQ/Kafka/MNS 在削峰场景的选型对比。

**期望加分项：**
- 选型依据：自建 Redis 的运维成本（主从、持久化、监控、故障切换）vs 云 Redis 的托管收益；Tair 相对 Redis 的增强（持久内存型 Tair 降低成本、TairString 避免大 Key 热 Key、读写分离版支持只读副本）
- 热点缓存解法：热 Key 检测 + 本地缓存（JVM/多级缓存）+ 热点 Key 分片（key 加随机后缀分散到多节点），Redis 集群版打散热点；避免"缓存击穿/穿透/雪崩"三板斧（互斥重建、布隆过滤器、过期时间加随机抖动）
- 高可用设计：Redis 主从 + 哨兵/集群版（默认主备自动切换，RPO=0 或秒级），开启 AOF + RDB 双持久化，开启自动备份与一键恢复
- 削峰选型对比：RocketMQ（事务消息、延迟消息、重试队列、顺序消息，适合订单链路强一致）、Kafka（吞吐最高、适合日志/流计算，不擅长小消息队列语义）、MNS（轻量简单队列，成本低，适合简单解耦）；瞬时 10 万 QPS 下单用 RocketMQ 异步削峰 + 事务消息保证最终一致
- 量化削峰方案：前端秒杀请求 → 本地限流 → RocketMQ 缓冲（单 topic 每秒可写入百万级）→ 消费者按 DB 能力限速落库，把 10 万 QPS 削成 2000 QPS
- 指出坑：消息积压监控与告警、消费幂等（订单幂等键）、死信队列处理、RocketMQ 与 Kafka 的 consumer 语义差异（Kafka 无真正的 push、位移管理不同）

**减分项：**
- 不知道 Tair 与 Redis 的区别，不知道热 Key 分片这种实战手段
- 只背"缓存三兄弟"概念，说不清各自触发场景与解法
- 选型只说"RocketMQ 好"，说不出与 Kafka、MNS 在吞吐、顺序、事务上的差异
- 削峰只停留在"用 MQ 缓冲"，没有消费限速、幂等、积压监控的闭环
- 忽略消息可靠性：不聊 ACK 机制、重试、死信

**解答：**

缓存侧先解决架构问题：自建 Redis 在 ECS 上意味着主从、持久化、监控、故障切换全自己扛，双 11 前升级迁移风险大；迁移到云 Redis（托管主从自动切换、内置告警）是最稳妥的一步，规格选集群版或标准版 + 哨兵。热点缓存是另一个痛点：详情页热点 Key 集中在少数商品，单点缓存扛不住，实战组合是"本地缓存（Caffeine，命中率 90%+）+ 中心 Redis 兜底"，热 Key 在 Redis 侧做分片（原 key 加 16 个随机后缀分散到不同节点），再配合缓存重建的互斥锁（只允许一个线程回源 DB）、布隆过滤器挡住不存在的 ID（防穿透）、过期时间加随机 1-5 分钟抖动（防雪崩）。如果数据量级大、希望降低成本，Tair 持久内存型按容量计费约是 Redis 内存型的 1/3，且 TairString 等扩展结构能缓解大 Key 问题。削峰侧：下单链路用 RocketMQ 是最合适的选择——它提供事务消息（本地事务 + 半消息保证订单与消息一致）、延迟消息（30 天后未支付自动关单）、顺序消息（同一订单串行消费）与消费重试；Kafka 适合日志、埋点、流计算，吞吐最高但队列语义弱（无延迟消息、无内置事务回查）；MNS 适合轻量解耦、成本敏感场景。方案落地：10 万 QPS 先经网关限流（每用户 + 总量）→ 写入 RocketMQ（写入吞吐百万级）→ 消费者按 DB 写能力限速（如 2000 QPS）批量落库，Redis 原子扣减库存（Lua 脚本防超卖），成功后再异步写订单库。必须配套：消费端幂等（orderId 幂等键）、积压监控（ConsumerLag 告警）、死信队列人工处理、RocketMQ 的 ACL 与消息轨迹追踪。实践中最常见的翻车点是消费端忘了手工 ACK 导致消息无限重试，以及顺序消息场景误用普通队列打乱顺序。

**延伸考点：** 扣库存用 Redis Lua 脚本如何保证原子性？如果 Redis 在扣减后、落库前宕机，如何保证最终一致（事务消息）？

### Q7. 混合云网络打通，VPC、NAT、CEN 怎么搭？

**问题：** 你们有 3 套环境：北京机房自建 IDC（跑核心 ERP）、阿里云华北 2 的 VPC（跑互联网应用）、上海 VPC（跑大数据）。请设计 VPC/交换机/安全组划分、NAT 网关与弹性公网 IP 的使用，以及用 CEN 云企业网打通 IDC 与多云账号的方案，并说清安全边界。

**期望加分项：**
- 说清 VPC 层级：VPC（逻辑隔离网络）→ 交换机（可用区内的子网）→ 安全组（实例级状态化防火墙）；IPv4 CIDR 规划（如 10.0.0.0/8 大网段按环境细分，避免与 IDC 网段冲突）
- 出网入网设计：EIP 是静态公网 IP，NAT 网关是 SNAT 出口（按实例粒度/按交换机粒度配置）、DNAT 是端口映射入网；公网入口走 SLB，出网走 NAT 共享带宽包更省钱
- CEN 的价值：多 VPC 互通（不用逐对打对等连接）、与 IDC 通过专线（Express Connect）/VPN 网关互联、支持跨地域互通（走阿里云骨干网，跨地域延迟稳定）
- 私网访问控制：跨账号 VPC 用 CEN 或云企业网 + RAM 授权，安全组互信（对端安全组 ID 白名单）、路由表按需发布（避免全网段互通扩大爆炸半径）
- 高可用与边界：专线主备（双专线冗余或专线+VPN 备份）、NAT 网关主备切换、EIP 绑定的 SLB 跨可用区
- 量化：IDC 到云的专线带宽按业务量估算（如 2Gbps），跨地域用 CEN 的互通费用按 GB 计费

**减分项：**
- VPC 和交换机概念混淆，说不清子网与可用区的关系
- 出网一律绑 EIP 到每台机器，不知道 NAT 共享出口省 IP 和钱
- 不知道 CEN 与对等连接（VPC Peering）的差异，多 VPC 场景傻乎乎逐对打通
- 安全组规则一刀切（0.0.0.0/0 全放通），不提最小权限与双向规则
- 不做专线冗余，单条链路故障即全断

**解答：**

网络设计从规划 CIDR 开始：VPC 按环境分（生产/测试），网段用 10.x.0.0/16 体系细分且与 IDC 的 172.16.0.0/12 错开，避免专线互通后地址冲突——这是很多混合云事故的根源。VPC 内按可用区分交换机（每个可用区至少一个，用于跨可用区高可用），实例用安全组做应用层隔离：Web 组仅对 SLB 开放 80/443、APP 组仅对 Web 组内网开放、DB 组仅对 APP 组开放，安全组规则可以引用对端安全组 ID（如放行 sg-web 的 8080），比写网段更直观且自动跟随实例变动。出网入网分开设计：入网走 SLB（四层/七层）挂 ECS，绑定 EIP 提供公网入口；出网用 NAT 网关做 SNAT，共享带宽包按需购买，避免给每台机器绑 EIP（既费公网 IP 又费钱，还扩大暴露面）；需要被外部直接访问的少数服务用 DNAT 端口映射或直接 EIP。多 VPC 与 IDC 互联用 CEN 云企业网：把华北 VPC、上海 VPC 都加入同一个 CEN，通过"转发路由器（TR）+ 路由表"实现网段间互通，跨地域流量走阿里云骨干网，稳定性和延迟优于公网；IDC 侧通过专线（Express Connect）接入就近的 VBR 再挂到 CEN，双专线做主备或专线 + VPN 做逃生链路，专线带宽按峰值业务流量 × 1.5 规划（如 2Gbps）。安全边界必须强调：CEN 内路由按需发布（只发布该互通的网段），跨账号接入用 RAM 角色授权（不共享主账号 AccessKey），关键网段之间用安全组互信 + 网络 ACL 双保险；所有出网流量建议经 NAT 或云防火墙统一审计。实践中的坑：一是 VPC 创建后 CIDR 不可改，规划时留足扩展位；二是 CEN 互通后路由冲突会导致黑洞，上线前用 ping/traceroute 验证双向连通；三是 NAT 网关是单点，生产环境要选双可用区部署或购买高可用版本。

**延伸考点：** 如何用云企业网实现"北京 IDC 与上海 VPC 走专线、互访绕过公网"？如果 VPC 网段与 IDC 冲突，迁移成本有多高，事前如何避免？

### Q8. 域名、负载均衡、CDN，一套对外入口怎么搭？

**问题：** 你们有个电商站，域名 www.example.com 解析在第三方 DNS，后端 4 台 ECS 直连公网，用户反馈国内访问慢、华南地区经常打不开。请给出云解析 DNS、SLB/ALB/NLB、CDN 的完整入口架构设计，并说明三种负载均衡器的适用场景。

**期望加分项：**
- 说清三种负载均衡差异：SLB 传统四层/七层、支持 TCP/UDP/HTTP；ALB 应用型（HTTP/HTTPS/gRPC、七层路由、WebSocket、QUIC）、更细粒度的路由规则；NLB 四层性能型（超高并发 TCP/UDP、静态 IP、VPC 内网）、适合网关/数据库前
- DNS 设计：云解析 DNS 支持解析线路（运营商/地域）、TTL 调低利于切换、健康检查联动、CNAME 到 CDN/负载均衡域名
- CDN 方案：静态资源（图片/JS/CSS）走 CDN 缓存（命中率 90%+），动态请求直连源站或走 DCDN 全站加速；回源地址指向 SLB/ALB，配置回源 Host 与回源带宽上限防源站被打爆
- 分层回源与降级：CDN → ALB → ECS 三级，ALB 层做限流/重试，ECS 健康检查失败自动摘除
- 安全联动：接入 WAF（Web 应用防火墙）放在 ALB 前面或 CDN 回源链路，DDoS 高防保护源站 IP 不泄露
- 量化性能指标：CDN 首字节延迟、缓存命中率监控、ALB 的 QPS 与并发连接数

**减分项：**
- SLB/ALB/NLB 三者分不清，不知道 ALB 支持七层路由、NLB 面向四层高性能
- 全部流量直接回源，CDN 只放静态、动态请求也硬走 CDN 或完全不缓存
- 源站 ECS 暴露公网 IP，DDoS 打源站直接挂
- 不知道 TTL 与健康检查在故障切换中的作用，切换域名靠改解析等缓存过期
- 忽略回源配置（回源 Host、回源协议、回源超时），流量回源后 502 一片

**解答：**

入口架构按"DNS → CDN → 负载均衡 → ECS"四层设计。第一层 DNS：把域名从第三方迁到阿里云云解析（免费版够用，企业版支持自定义线路与 SLA 99.99%），A 记录/CNAME 指向 CDN 加速域名，TTL 设 60-300 秒方便故障时快速切换；云解析支持按运营商和地域分线路解析，配合健康检查实现解析级容灾（如华东解析到华东 SLB、故障自动切换）。第二层 CDN：静态资源（图片、JS/CSS、字体）全量进 CDN，配好缓存规则（图片缓存 30 天、HTML 缓存 60 秒），监控缓存命中率到 90% 以上；动态 API 走 DCDN（全站加速）或直连源站，避免动态请求在 CDN 层被错误缓存。回源配置是重点：回源地址写 ALB 域名而不是具体 ECS IP，回源协议 HTTPS、回源 Host 保持与访问域名一致，否则拿到 404/证书错误；同时设置回源带宽上限与回源超时，防热点流量打穿源站。第三层负载均衡选型：对外 HTTP/HTTPS 用 ALB——支持域名/路径路由（/api 打到订单集群、/static 直接回源）、WebSocket 长连接、HTTP/2/QUIC、连接级限流；需要极致 TCP/UDP 性能（如游戏、数据库中间层、NAT 之后的四层转发）用 NLB，单实例百万并发、静态 IP 不随资源变化，适合对端做白名单；传统场景 SLB 也能覆盖但功能少、演进空间小。第四层 ECS：挂在 ALB 后端组，开启健康检查（HTTP 路径 /healthz，间隔 5 秒），配合弹性伸缩组按 CPU 自动扩缩容。安全必须前置：WAF 挂在 ALB 前做 Web 层防护（SQL 注入、CC 攻击），DDoS 高防洗流量，CDN 开启回源鉴权（私有 OSS 或回源签名），源站 ECS 不绑公网 IP、只走内网接 ALB——否则一次扫端口就能打瘫源站。实践中的坑：CDN 缓存了不该缓存的登录态接口（鉴权失败 401 被缓存）；健康检查路径写错导致后端全部摘除；ALB 的会话保持开关与后端 cookie 冲突。

**延伸考点：** 为什么动态接口不能开 CDN 缓存？如果 CDN 回源链路断了，如何设计"缓存兜底 + 降级页"的容灾方案？

### Q9. 新同事要开服务器权限，RAM 怎么给才安全？

**问题：** 公司新招了一名运维工程师，需要他能管理华东 2 地域的 ECS 和 RDS、查看所有地域的账单，但不能删库、不能改 RAM 权限、不能碰生产数据库数据。请设计 RAM 的账号体系、授权策略与权限边界，并说明 RAM 策略语法与最小权限的落地方法。

**期望加分项：**
- 说清 RAM 核心模型：主账号（Account）只做财务与授权管理、绝不用于日常操作；用户（User）对应人/程序、组（Group）对应角色集合、角色（Role）用于跨账号/临时授权（如 ECS 实例 RAM 角色、RAM 用户扮演角色）
- 策略语法要点：Action 精确到 api 级别（ecs:CreateInstance、rds:DeleteDatabase），Resource 限定地域与实例 ID（acs:ecs:cn-beijing:*:instance/i-xxxx），Condition 条件（如限定 IP 来源、限定时间、限定 MFA）
- 方案落地：建运维组（拥有 ECS/RDS 管理权限 + 只读账单权限），生产数据用"不授权 + 数据库账号权限最小化"双重隔离；核心操作（删除实例、改安全组）开"高危操作保护"（MFA 二次校验）
- 权限边界（Permission Boundary）：用管理策略给子用户划上限，防止越权提权（如只能操作华东 2，策略里写死 region）
- 最佳实践：AccessKey 只在服务器/CI 用（用 RAM 角色 + OIDC 更安全），人员用 RAM 用户 + 控制台密码 + MFA；不用主账号 AccessKey 调 API
- 能讲出排查手段：使用 RAM 控制台"策略模拟器"验证策略效果，ActionTrail 审计授权后行为

**减分项：**
- 不知道 RAM 用户/组/角色的区别，把角色当用户用
- 主账号 AccessKey 到处贴、或给所有人管理员权限（AdministratorAccess 一键授权）
- 授权粒度只到"产品级"（整个 RDS 管理权），做不到"资源级 + 条件级"
- 策略语法写错（Action/Resource 大小写、通配符），授权后权限不足或过度
- 忽略 MFA、高危操作保护与审计，事后追责无记录

**解答：**

RAM 安全设计分四步。第一步账号分层：主账号只留财务与全局授权能力，日常一律用 RAM 用户（一人一账号 + MFA）；程序调 API 用"RAM 用户 + AccessKey"或更安全的"ECS 实例 RAM 角色"（实例内自动获取临时凭证，无硬编码密钥）；跨账号协作（如外包团队）用 RAM 角色，外部账号通过"扮演角色"拿到限时凭证。第二步授权模型：新建"运维"用户组，组上挂策略，人员进组即得权、移组即失权，比逐个授权好管理。给这位新同事的权限设计为：管理华东 2 的 ECS（ecs:CreateInstance/StartInstance/StopInstance 等，Resource 限定 acs:ecs:cn-beijing:*）、管理 RDS 实例本身但禁止数据操作（RDS 的数据权限走数据库账号，与云账号权限是两个平面，不给数据库账号 DDL/DML 权限即可）、只读查看账单（bss:DescribeInstanceBill 等只读 Action）；核心高危操作（ecs:DeleteInstance、rds:DeleteDatabase、修改安全组）在策略中用"不授权 + 高风险操作开启 MFA 保护"双保险。第三步策略语法要写对：Action 用产品 API 全名，Resource 用 ARN 限定到地域与实例（如 acs:ecs:cn-beijing:*:instance/i-2zeXXXX），Condition 加"SourceIp 限定公司出口 IP、acs:MFAPresent=true 要求 MFA 在线"；写完用控制台"策略模拟器"逐条验证，避免通配符过度授权。第四步权限边界与审计：给子账号挂 Permission Boundary（管理边界策略）限定其可授权的最大范围，即使拿到权限也超不出边界；开启 ActionTrail 记录所有 RAM 与云资源操作，出现安全事件按 AccessKey ID + IP 溯源。实践中的坑：把 AdministratorAccess 当"先给上再说"；主账号 AccessKey 泄漏导致整账号被接管（这类事故每年都有）；RDS 数据安全只做了云账号层，忘了数据库账号还有 root 权限。

**延伸考点：** ECS 实例 RAM 角色与 RAM 用户 AccessKey 相比有什么安全优势？OIDC 免密接入 CI 是怎么实现的？

### Q10. 公司要做等保三级，安全体系怎么补？

**问题：** 公司要过等保三级（政府客户要求），安全团队让你评估阿里云上的系统。当前架构：ECS 直接暴露公网 80/443、无 WAF、无堡垒机、数据库密码明文存在配置中心、无日志审计。请梳理阿里云云盾体系（DDoS 防护/WAF/云安全中心）与 KMS 的使用，并给出等保合规的落地清单。

**期望加分项：**

- 只知道"上 WAF 就安全了"，说不清等保三级的具体控制项与测评流程

- 忽略堡垒机与运维审计，或日志留存时间不足 6 个月
- 分不清 DDoS 高防、WAF、云安全中心各自防什么
- 把"买了安全产品"等同于"过了等保"，忽略管理制度与测评环节

**解答：**

先纠正架构级风险，再对齐等保三级控制项。第一层是暴露面收敛：所有 ECS 摘掉公网 IP，公网入口统一走 ALB（挂 WAF），ALB 前面按需上 BGP 高防（保底清洗 30-100G，弹性到 T 级），源站 IP 永不暴露；DDoS 基础防护默认开启（5G 内免费清洗），突发大流量触发高防联动。第二层主机安全：ECS 全部装云安全中心（安骑士）Agent——开暴力破解防护（SSH 失败 5 次封 IP）、网站后门/Webshell 查杀、漏洞扫描与基线核查（等保三级要求主机基线合规，如口令策略、SSH 配置加固），高危漏洞按 CVSS 定级修复 SLA。第三层数据安全：密钥统一进 KMS，采用信封加密——业务侧生成数据密钥 DEK 加密数据，DEK 再由 KMS 主密钥 CMK 加密存储，解密时向 KMS 请求解密 DEK，主密钥定期轮换且所有 KMS 调用被 ActionTrail 审计；RDS 开透明数据加密（TDE，KMS 托管）、OSS 开服务端加密（SSE-KMS），数据库账号最小权限 + 不用 root。第四层运维与审计：上堡垒机，SSH/RDP 全部经堡垒机（录屏 + 指令审计 + 双人审批），配置中心里的密码改由 KMS 凭据或参数加密存储；日志全量汇入 SLS——云安全中心日志、ActionTrail 操作审计、OSS/RDS 访问日志，留存 ≥180 天（等保三级要求 6 个月），配置"日志告警"（登录异常、SQL 注入拦截、权限变更）。最后是流程认知：等保三级走"定级备案 → 差距分析 → 整改 → 测评机构评测"，阿里云提供等保合规包（一键自查 + 差距报告 + 安全管家），但制度文件（安全管理制度、应急预案）和持续运营（漏洞月度巡检、账号季度盘点）必须自己做，测评机构只看产品是不够的。实践中的坑：WAF 只护了域名没护 IP 入口、云安全中心没开"基线核查"导致测评不通过、日志只留了 3 个月被测评打回、KMS 主密钥忘了配置自动轮换。

**延伸考点：** KMS 信封加密为什么比直接用主密钥加密数据更合理？如果 KMS 故障，业务如何降级而不中断？

### Q11. 线上半夜告警刷屏，监控、日志、审计怎么搭才靠谱？

**问题：** 你们刚接手一个线上系统，半夜每 5 分钟收到一条告警（CPU 超 80%、错误率超阈值、磁盘满……），值班同学已经麻木。同时排查问题全靠登机器看日志，操作审计完全缺失。请设计云监控（指标/告警）、SLS 日志服务和 ActionTrail 审计的三层可观测体系。

**期望加分项：**
- 说清云监控用法：ECS/RDS/Redis/OSS 等产品指标自动上报，自定义监控（业务指标通过 SDK 上报），告警支持阈值/环比/同比与多条件组合（AND/OR），通知渠道（电话/短信/钉钉/Webhook）
- 告警设计要点：区分 P0/P1/P2 分级（P0 电话、P1 钉钉+短信、P2 邮件/群机器人）；告警聚合与抑制（同一个应用 5 分钟内合并为一条）；告警去噪（静默期、升级机制）；告警必须带排查入口（跳转日志查询）
- SLS 落地方案：应用日志按"应用/环境/级别"建 Project- Logstore，采集用 Logtail（容器用 SLS 采集器 sidecar），全链路 TraceId 贯穿；关键能力：实时查询与分析（SQL）、告警（日志触发）、投递（OSS 归档/大数据）

- 给出"告警 → 日志 → 链路 → 审计"的排查链路：告警点击即看日志上下文，TraceId 贯穿上下游

**减分项：**
- 告警只会"CPU>80% 发短信"，没有分级、去噪、升级机制，告警疲劳
- 日志只在机器上 tail，不采集、不检索、不关联 TraceId，排查靠猜
- 不知道 ActionTrail 记录的是 API 层审计，把操作审计和业务日志混为一谈
- 没有告警复盘流程（每周 review 告警准确率），告警越加越多
- 忽略日志成本：全量留存导致 SLS 账单爆炸，不设存储周期与归档策略

**解答：**

三层可观测体系分别解决"现在坏没坏、为什么坏、谁动了什么"。第一层云监控做指标与告警：核心产品指标（ECS CPU/内存/磁盘、RDS 连接数/慢查询、Redis 内存/命中率、SLB QPS）都开默认监控，业务指标（下单量、支付成功率、订单积压）通过 SDK 自定义上报。告警规则设计是重点：按影响面分级——P0（可用性/支付链路异常，电话 + 钉钉群，响应 10 分钟）、P1（单模块错误率、连接数飙升，钉钉 + 短信，响应 30 分钟）、P2（磁盘水位 70%、慢查询增多，邮件/群机器人）；同一应用 5 分钟内同类告警聚合为一条，配置静默期避免夜间刷屏；阈值要动态（如 CPU 按"环比突增 50%"而非固定 80%，避免日常波动误报）。第二层 SLS 做日志：按"Project = 应用集群、Logstore = 日志类别"建结构（如 app-prod / access-log、app-log），Logtail 采集并自动解析字段，应用日志统一 JSON 格式并注入 TraceId（配合 ARMS 链路追踪贯穿微服务调用）；打开 SLS 的实时分析（支持 SQL 聚合：按接口统计错误率、按 IP 聚合慢请求）与日志告警（错误率 5 分钟滑动窗口超 1% 触发）；日志留存策略：热数据 15 天、冷归档投递 OSS 180 天，控制 SLS 存储成本（按索引字段精配，不开全字段索引）。第三层 ActionTrail 做审计：默认记录所有 OpenAPI 调用（包括控制台操作，如谁删了 RDS、谁改了安全组），投递到 SLS 做留存与告警（权限变更、删除实例等敏感操作即时告警），等保与安全事故复盘靠它还原现场。排障闭环：告警消息里带 SLS 查询链接 → 查异常时间段错误日志 → TraceId 串起调用链 → 定位代码或依赖 → 修复后更新告警阈值。实践中的坑：忘了给 SLS 配索引导致查询巨慢；告警没绑"告警联系人组"导致半夜没人响应；ActionTrail 默认只保留 90 天，归档要提前配置。

**延伸考点：** 告警去噪的常见手段有哪些（聚合、静默、升级、SLO 燃烧率）？如何用"SLO 燃烧率"设计告警而不是拍脑袋定阈值？

- 敏感信息（密码、AccessKey）明文写进代码库
- 无 plan/审批流程，生产环境 apply 前不看 diff，改错配置直接上线

先理清三者定位：Terraform 是跨云 IaC 事实标准，阿里云 Provider 完善，适合"多云治理 + 已有 Terraform 技能"的团队；ROS 是阿里云原生编排，模板与云产品 API 对齐紧密、自带资源栈回滚能力（失败时自动回滚已建资源）、天然适配阿里云体系与云效联动，适合"深度绑定阿里云"的场景；CADT 是架构可视化工具，画图即部署，适合架构评审、迁移方案设计与快速原型（生成 Terraform/ROS 模板再交 IaC 管理）。对你们"半年 300 台 + 1 小时交付"的目标，推荐 Terraform（或 ROS）+ CI 流水线的组合。落地规范四条：一是目录与状态——按 environment 分目录（prod/staging/dev）、按资源域分子模块（network/compute/db），每个环境独立 state；state 必须存远程（阿里云 OSS 开通版本控制 + 加锁），杜绝本地 state 与团队冲突；二是变量与敏感信息——VPC CIDR、实例规格等用变量，数据库密码、AccessKey 引用 KMS/Parameter Store（如 alicloud_kms_secret），代码库里禁止出现明文凭据；三是流程——模板改动走 MR 评审，流水线自动执行 terraform plan 生成 diff 贴到 MR 评论，生产 apply 需人工审批后执行，apply 输出记录到审计；四是存量收敛——老资源用 terraform import 逐个纳入（先 import 再 plan，收敛漂移），同步打标签（env/cost-center/owner）支撑成本分摊。重点讲踩坑：Terraform 无内置回滚，apply 中途失败会留下半成品资源（如建了磁盘没建实例），要写"资源依赖 + 幂等"的模板并用 plan 提前暴露；destroy 误操作会整环境删除，生产环境必须开"删除保护"（OSS 版本控制 + 流程上禁止直接 destroy）；Provider 版本不锁定，半年后升级 Provider 可能行为变化导致大面积 diff。量化收益：新环境从"人工点 3 天"降到"流水线 1 小时内建完"，所有变更可追溯、可快速重建（容灾演练直接起一套全新环境验证）。

**延伸考点：** Terraform 的 state 文件包含什么敏感内容？为什么建议用远程 state 加锁而不是本地文件？ROS 的"资源栈回滚"与 Terraform 的失败处理有何不同？

- 流水线设计：触发方式（提交触发/合并请求触发/定时/手工）；阶段划分：代码扫描（SonarQube/云效自带）→ 单元测试 → 构建（Maven 多模块）→ 制品上传 → 部署（ACK 滚动更新/SAE 应用发布）→ 冒烟验证；环境串行：dev → staging → prod 逐级放行
- 灰度与回滚：云效支持分批发布与金丝雀（ACK 场景用部署策略），发布异常一键回滚到上一版本镜像；配合 SLB/ALB 权重调整做流量灰度
- 迁移策略：先"双轨运行"（Jenkins 继续跑存量，新项目上云效）→ 流水线模板化（统一部署脚本为模板）→ 存量项目按优先级迁移；制品仓库先同步，构建产物不再依赖内网私服
- 权限与审计：分支保护（main 分支禁止直推、MR 审批）、流水线执行记录与操作审计、密钥（SSH key/凭据）集中管理
- 量化收益：发布频率从周级到日级、发布成功率提升、MTTR 降低

**减分项：**
- 只把云效当"Jenkins 换皮"，不设计流程只搬脚本
- 没做灰度与回滚设计，发布失败只能"人肉改代码重新部署"
- 迁移一刀切停掉 Jenkins，存量项目全乱
- 忽略制品库与镜像仓库的迁移，构建依赖内网私服导致云效流水线构建失败
- 分支策略混乱、无代码评审，直推 main 到处飞

**解答：**

云效迁移的核心不是"换工具"而是"统一研发流程"。第一步搭代码与制品基座：代码迁到 Codeup（保留 Git 历史与分支），设置分支保护——main 禁止直推、强制 MR + 代码评审（2 人 approve）、push 前跑代码扫描；制品从自建 Nexus 同步到云效制品仓库（Maven 仓库与 Docker 镜像仓库），存量镜像用脚本批量推入，私服内网地址在构建脚本里全部换成云效仓库地址，避免流水线构建拉不到依赖。第二步建流水线标准：用流水线 Flow 写 YAML 定义统一模板——阶段一代码扫描（云效安全扫描 + SonarQube 质量门禁，阻断高危漏洞）；阶段二构建（Maven 多模块构建、单元测试、失败即停）；阶段三制品（JAR 进 Maven 仓库、镜像进 ACR）；阶段四部署（先 dev 自动部署 → staging 人工确认 → prod 走审批 + 灰度）；阶段五验证（部署后自动跑接口冒烟 + 健康检查）。环境逐级放行，生产部署用"分批发布"：ACK 场景第一批 10% 流量验证 10 分钟（观察错误率与延迟），再放量到 50% 再到 100%；一旦指标异常，一键回滚到上一镜像（镜像标签 + 版本号管理，回滚即重新部署旧 tag）。第三步迁移策略：双轨运行 1-2 个月——Jenkins 继续服务存量项目，新项目强制上云效，流水线模板沉淀后再按项目优先级批量迁移（先内部服务后核心链路），迁移验收标准是"新流水线跑通 dev/staging/prod 全链路且发布指标达标"。第四步配套治理：流水线执行记录与操作审计默认开启，构建密钥（SSH key、镜像仓库凭据、云账号 RAM 子账号）集中到云效凭据管理，环境变量里不出现明文密码。实践中的坑：存量 Jenkins 脚本里的服务器 IP 硬编码导致部署到新环境失败；Docker 镜像仓库迁移后忘了更新 K8s 拉取凭据（ImagePullSecret）；灰度发布没接监控，放量到 100% 才发现异常。

**延伸考点：** 灰度发布与蓝绿发布的区别是什么？在金丝雀发布期间，如何用 ARMS/云监控判断"继续放量还是回滚"？

### Q14. 订单状态变更要触发下游 5 个系统，EventBridge 怎么设计？

**问题：** 你们有个订单服务，订单状态变化（已支付/已发货/已取消）需要实时通知下游 5 个系统（库存、财务、短信、推荐、BI），目前是订单服务用 HTTP 回调一个个调，耦合严重且经常超时重试。请用阿里云 EventBridge（事件总线）+ 函数计算/SAE 设计解耦方案，并说明与直接调 MQ 的差异。

**期望加分项：**
- 说清 EventBridge 定位：事件总线（EB）作为事件中心，支持事件源接入（云产品事件/自定义事件/API 网关）、事件规则过滤与转换、多目标分发（FC/SAE/MQ/HTTP 等）；"事件 → 规则 → 目标"三层模型
- 与 MQ 对比：EB 是"事件驱动架构总线"，语义是发布订阅 + 规则路由（按事件内容过滤、转换），MQ（RocketMQ/Kafka）是"消息通道"，语义是队列/主题与可靠传输；EB 更适合"异构系统间事件驱动 + 多目标按需路由"，MQ 更适合"点对点削峰与顺序保证"
- 方案设计：订单服务发事件（order.paid，事件源自定义）→ 事件总线 → 规则 1 过滤"已支付"分发给库存/财务（FC 处理），规则 2 过滤"已发货"发给短信/物流；失败重试（EB 内置重试 3 次 + 死信）、幂等（订单号 + 事件 ID 去重）
- 云产品事件源：OSS 上传、RDS 变更、ECS 快照、DTS 等可直接进 EB，配合 FC 做自动化（如快照完成后通知、文件上传触发处理）
- 事件格式：CloudEvents 规范（source/type/id/time/data），自定义事件与云产品事件统一 schema，schema 注册中心做版本管理
- 可靠性设计：EB 的投递保障（At-Least-Once + 幂等消费）、重试与死信队列、目标限流保护

**减分项：**
- 分不清 EventBridge 与 MQ 的边界，认为"EventBridge 就是另一个 MQ"
- 事件没有规范 schema，5 个下游各自解析，字段变更全部爆炸
- 忽略幂等与重试，下游重复处理导致重复扣库存/重复发短信
- 只做"HTTP 改 EB 的替换"，没有过滤/转换/多目标的路由设计
- 不考虑失败场景（下游挂了事件丢失怎么办），没有死信与补偿

**解答：**

先用事件总线替代硬编码回调。方案结构：订单服务在状态变更事务提交后，把事件（type=order.paid、order.pending、order.cancelled，含订单号、金额、商品明细）按 CloudEvents 规范发到 EventBridge 自定义总线；总线上配三条规则——规则 A 过滤 type=order.paid 且金额>0，目标分发到库存系统（FC 减库存）、财务系统（SAE 记账）、推荐系统（离线落表）；规则 B 过滤 order.shipped 分发到短信/物流；规则 C 是兜底规则捕获所有未匹配事件进死信/审计。EventBridge 的价值在于"事件 → 规则 → 目标"的声明式路由：字段级过滤（如只转发某渠道订单）、事件转换（裁剪字段、映射成下游格式）、多目标一对多分发，下游增减不需要改订单服务代码，只改规则配置。与 MQ 的分工要说清：EventBridge 是事件驱动架构的总线，擅长按事件内容路由给多个异构目标（FC/SAE/HTTP/OSS/MQ 都可做目标），且天然连接云产品事件（OSS 上传、RDS 变更、DTS 同步完成都能触发）；RocketMQ/Kafka 是消息通道，适合需要削峰、顺序、事务保障的可靠传输——实际架构经常"EB 做事件分发 + RocketMQ 做关键链路削峰"叠加使用（如已支付事件同时投递给 RocketMQ 供订单结算消费）。可靠性设计不能省：EB 投递是 At-Least-Once 语义，所有消费端必须幂等（用 orderId + eventId 做去重键，Redis SETNX 或 DB 唯一索引）；EB 内置失败重试（默认 3 次，可配策略），超过进入死信队列由值班兜底处理；下游 FC 要设置并发上限保护自己。实践中的坑：事件 schema 没有版本管理，字段改名后下游解析全炸（用 schema registry + 兼容性检查）；在事务未提交前发事件，回滚后下游已消费造成数据不一致（要"事务提交后发事件"或使用本地消息表 + 事务消息）；事件体太大导致 EB 投递失败（超过 256KB 要拆分或走 OSS 引用）。

**延伸考点：** 为什么"事务提交后再发事件"仍然可能丢事件？如何用"本地消息表 + 定时补偿"保证事件不丢？EventBridge 与云产品事件源（如 OSS 事件）结合的自动化场景有哪些？

### Q15. 30 个微服务上线，网关和服务治理怎么选？

**问题：** 你们把单体拆成 30 个 Spring Cloud 微服务（含 Dubbo 接口），面临三个问题：外部流量入口要做统一鉴权/限流/灰度，服务间调用要做熔断降级，全链路要可观测。请对比 MSE、云原生网关（ALB/网关 ASM 网关）、API 网关，给出服务治理与网关分层方案。

**期望加分项：**
- 说清网关分层：第一层流量入口网关（云原生网关/API 网关）：统一鉴权、限流、路由、灰度（按 header/cookie 分流）；第二层微服务治理（MSE 微服务引擎）：注册中心 Nacos、配置中心、服务熔断降级、流量染色与全链路灰度；第三层 Service Mesh（ASM）：Istio 形态的边车代理，对业务无侵入的服务治理
- 选型依据：Spring Cloud/Dubbo 生态选 MSE（Nacos 注册配置中心 + 治理能力与 Spring Cloud 原生对齐）；K8s 化程度高、想统一南北向+东西向用云原生网关（基于 Envoy，支持 Ingress/API 网关能力二合一）；跨语言/异构微服务用 ASM（Sidecar 无侵入）
- 方案落地：入口层用云原生网关（或 ALB + WAF），做鉴权（JWT/OIDC）、限流（按用户/接口/IP 维度）、路由与灰度（金丝雀权重）；服务间用 MSE 做注册发现、熔断（慢调用/异常率阈值触发）、降级（fallback 兜底）、限流（Sentinel）；链路用 ARMS 全链路追踪（TraceId 贯穿）
- 量化与容错：熔断阈值设计（错误率 >50% 触发、半开试探 5 秒）、超时与重试策略（读接口 200ms 超时 + 1 次重试，写接口不重试）、隔离（线程池/信号量隔离防级联）
- 灰度全链路：网关按 header（x-version=v2）路由 + 服务间调用按流量标签（MSE 流量染色）贯穿到 DB 读写，实现端到端金丝雀
- 提醒演进路径：先 API 网关 + 注册中心治理（低成本），规模大了再上 Service Mesh，不要一上来就 ASM

**减分项：**
- 网关和微服务治理混为一谈，不知道"入口网关 vs 服务间治理"是两个层面
- 不知道 MSE 提供注册中心/配置中心，以为治理就是 Hystrix 注解
- 熔断降级说不出阈值、半开策略与隔离机制，只背概念
- 一上来就推 Service Mesh，不考虑团队成本与 Istio 复杂度
- 忽略全链路灰度的"流量标签贯穿"，只做入口灰度

**解答：**

先分层再选型，微服务治理体系分三层。第一层入口流量网关：用云原生网关（基于 Envoy 内核，阿里云在 ASM 之上的托管网关，支持 Ingress 与 API 网关能力合一）或 API 网关（阿里云 APIGW）——承担统一鉴权（JWT/OIDC 校验、签名）、限流（按用户/接口/来源 IP 多维度，令牌桶）、路由（域名/路径 → 服务）、灰度（按 header 或 cookie 分流 10% 流量到新版本）、以及 WAF 联动防 Web 攻击；这一层把"脏活"收口，业务服务不再各自实现鉴权限流。第二层服务间治理：用 MSE（微服务引擎）——它提供 Nacos 注册中心与配置中心（Spring Cloud/Dubbo 原生接入，只需改依赖与地址）、Sentinel 限流熔断（接口级规则：慢调用 RT>500ms 或异常率>30% 触发熔断，熔断后 5 秒半开试探，成功恢复则关闭，配合信号量/线程池隔离防级联故障）、以及服务鉴权与全链路灰度（流量染色：网关按 header 打标签，MSE 保证带标签的调用一路打到灰度实例，实现端到端金丝雀，包括灰度 DB 读写分离）。第三层可观测：ARMS 接入全链路追踪（TraceId + 耗时瀑布），配合 SLS 日志与云监控指标，形成"指标-日志-链路"闭环。选型边界要讲清：Spring Cloud/Dubbo 团队首选 MSE（治理能力与框架天然对齐，改造量最小）；如果服务是 Go/Java/Python 异构、且希望治理对代码零侵入，再上 ASM（Istio Sidecar，但引入边车性能损耗与排障复杂度，一个 30 服务的团队不建议一上来就 ASM）；纯 K8s 团队可以直接用云原生网关把 Ingress 和 API 网关合一。实践中常见坑：熔断与重试叠加导致"重试风暴"（网关重试 + 服务重试 + DB 重试层层放大）；限流只做在网关、服务间不限流，热点服务照样被打挂；全链路灰度只做了入口，服务间调用还是全量打到老版本，灰度形同虚设；Sentinel 规则没有持久化到 Nacos，重启后规则丢失。

**延伸考点：** 熔断、限流、降级的区别与协作方式是什么？"重试风暴"如何避免（重试次数、退避策略、与熔断的配合）？

### Q16. 数仓每天跑 50 个作业，MaxCompute 还是 EMR？

**问题：** 公司数据分析需求爆发：离线数仓（日增量 2TB）、临时 SQL 查询、每周一次的 Spark 作业。团队有 3 个数仓工程师，倾向用开源 Spark/Hive，架构师提议 MaxCompute（ODPS）。请对比 MaxCompute 与 EMR 的选型逻辑，说明 PAI 在其中的位置，并给出数仓分层方案。

**期望加分项：**
- 说清产品定位：MaxCompute 是阿里云自研 PB 级 Serverless 数仓（按量计费、SQL 为主、无需运维集群）；EMR 是托管开源 Hadoop/Spark/Flink 生态（自管集群、可定制、按集群规格计费）；PAI 是机器学习平台（建模、训练、部署一体）
- 选型逻辑：标准 SQL 数仓 + 不想运维 → MaxCompute（免费开通、按扫描量计费、支持存储与计算分离、有 MaxCompute SQL/Spark 兼容模式）；要跑开源生态作业（Spark 自研代码、Flink 流计算、Hudi/Iceberg 数据湖）→ EMR（兼容性好、可挂自研 jar、集群弹性伸缩）
- 成本量化：MaxCompute 按存储（0.12 元/GB/月）+ 计算（按 CU 或按扫描量）计费，低频数据可归档；EMR 按集群规格按量计费，低峰可缩容但要自管调度
- 数仓分层：ODS（原始数据 MaxCompute 表）→ DWD（明细宽表）→ DWS（汇总）→ ADS（应用），用 DataWorks 做数据开发/调度/质量监控（DQC）一体化
- 混合架构：实时链路用 Flink（实时计算 F）写实时数仓，离线用 MaxCompute，数据湖（OSS + Hudi）放明细层供 Spark 分析，PAI 做模型训练从数仓取特征
- 迁移与坑：Hive SQL 迁 MaxCompute 有语法差异（如 ROW_NUMBER 支持、UDF 规范），存量脚本要兼容性测试；EMR 集群版本升级与大版本锁定；MaxCompute 的作业并发与配额（Quota）会影响排队

**减分项：**
- 分不清 MaxCompute 与 EMR 的差异，以为"都是跑 SQL 的"
- 不评估团队运维能力与作业形态，无脑选"开源免费"（EMR 的运维与集群成本常被低估）
- 不知道 DataWorks 与 MaxCompute 的关系（DataWorks 是开发平台、MaxCompute 是计算引擎）
- 迁移 Hive SQL 不测语法兼容性，上线才发现 UDF/函数差异
- 没有分层与成本治理，全表扫描查询把账单打爆（MaxCompute 按扫描量计费）

**解答：**

先给结论框架：这个团队 3 人数仓工程师、以标准 SQL 为主，首选 MaxCompute + DataWorks。MaxCompute 是 Serverless 数仓：存储与计算分离、按量计费（存储约 0.12 元/GB/月，计算按扫描数据量或按 CU 包年包月），不需要运维集群，SQL 引擎面向 PB 级优化，配合 DataWorks 完成数据开发、调度（DAG 依赖）、数据质量（DQC 规则）、数据地图（元数据管理）的一体化。它支持 MaxCompute SQL、Spark 兼容作业与 Flink 任务，大部分 Hive SQL 可直接迁移（少数函数与语法差异要测试）。EMR 是托管开源生态：适合跑自研 Spark 作业、Flink 流计算、需要 Hudi/Iceberg 数据湖能力或依赖特定开源版本的场景；代价是集群要自己规划规格、自己管理调度与监控，人少时隐性成本很高。选型边界：80% 场景是"写 SQL、跑调度、出报表"→ MaxCompute；需要"跑开源 jar、深度定制引擎、数据湖开放格式"→ EMR（甚至可以 MaxCompute 为主 + EMR 按需拉起跑特定作业，二者共用 OSS 存储）。PAI 的位置：机器学习平台，从数仓（MaxCompute）取特征做建模训练，模型上线用 PAI-EAS，与数仓形成"数据 → 特征 → 模型"链路。数仓分层：ODS 层原始数据入 MaxCompute（分区表按天/小时分区，生命周期管理，如原始日志 30 天归档 OSS）；DWD 清洗成明细宽表（维度退化、去重）；DWS 按业务主题做汇总（订单汇总、用户留存）；ADS 面向报表应用输出。实践中的坑：MaxCompute 按扫描量计费，SELECT * 全表扫描一次账单几十块，开发规范必须"先看分区再查询"、用 LIMIT 限制、建分区分桶表；DataWorks 调度配置错误导致任务死循环或重复跑（加幂等与重跑机制）；Hive UDF 迁移要重写为 MaxCompute Java UDF/UDTF；作业并发撞上 Quota 限制排队，要按业务重要性分 Quota 组。

**延伸考点：** MaxCompute 按扫描量计费下，如何设计表与查询规范控制成本？实时数仓（Flink）与离线数仓（MaxCompute）的分层如何衔接（实时明细 → 小时级汇总 → 落 MaxCompute 离线补算）？

### Q17. 云账单每个月超预算 30%，FinOps 怎么做？

**问题：** 你们月度云账单 100 万，已连续 3 个月超预算 30%，财务要求"下季度降 20% 且不再超支"。当前状态：ECS 按量实例 200 台、其中 60 台 CPU 使用率长期低于 5%，RDS 规格买大，OSS 存储无生命周期，弹性公网 IP 绑了一堆闲置机器。请用节省计划/资源包/成本分析给出 FinOps 落地方案。

**期望加分项：**
- 成本构成分析先行：用阿里云"成本分析"与分账账单（按标签 env/cost-center/owner 拆分）定位 TOP 成本项，先砍"浪费"再谈"折扣"
- 三类折扣工具算清账：包年包月（1 年 5-6 折）、节省计划（Savings Plan，承诺消费额换折扣，覆盖 ECS/RDS 弹性实例，1 年 5-7 折、3 年更低）、资源包（按量抵扣，适合 OSS 流量/CDN/NAT 等）；量化：60 台低负载 ECS 从按量改包年包月/节省计划，单价降约 40-50%
- 治理动作落地：闲置实例关停/释放（按 CPU 低于 5% 连续 7 天出清单 → 下线）；RDS 规格降配（4C16G → 2C8G，按峰值利用率选型）；OSS 开生命周期（90 天转低频、180 天归档）；EIP/NAT 闲置回收；快照与镜像清理（快照按最新策略只留必要份数）
- 预算与预警机制：设置预算（Budgets，按月度/季度/年度 + 按标签维度），超 80% 告警、超 100% 强告警；"节省计划/资源包"用率监控（用率低说明买多了）
- 组织机制：成本 Owner 制（每个业务线认领账单）、每周成本周会、成本优化项按 ROI 排序（先动大额且低风险的）
- 量化目标：100 万 → 80 万（降 20%），拆分目标：关停浪费省 10%、折扣省 15%、规格优化省 5% 等

**减分项：**
- 一上来就"买节省计划"，没先做浪费治理（先砍浪费再买折扣，顺序反了）
- 分不清包年包月、节省计划、资源包三者的计费与适用差异
- 不做分账标签治理，说不清 100 万花在哪，优化无从下手
- 只做一次性清理，没有预算预警与持续治理机制（下季度又超）
- 忽略成本与性能平衡（一刀切降配把核心业务搞挂）

**解答：**

FinOps 的顺序是"先看清、再砍浪费、再谈折扣、最后立机制"，四个动作对应四个问题。第一步看清：开通"分账账单"——给所有资源打标签（env/cost-center/owner/project），按标签拆账，用成本分析按月/按产品/按标签多维下钻，定位 TOP 成本项（通常是 ECS + RDS + 带宽 + OSS 四类）。第二步砍浪费（这部分是纯利润，不牺牲性能）：清单化治理——60 台 CPU 长期低于 5% 的 ECS 直接关停或释放（用云监控拉近 30 天平均利用率排序），RDS 按峰值规格重新选型降配，OSS 补生命周期（90 天转低频、180 天归档、日志 1 年后清理），释放闲置 EIP（按量 EIP 空置也收费）与多余快照（快照按"最新一份 + 每日保留 N 份"策略）。第三步谈折扣：先确定"基准用量"再买权益——把长期运行的弹性实例（ECS/RDS 按量）转为包年包月或"节省计划"（承诺 1 年/3 年消费额换折扣，灵活覆盖规格变更与新增实例），OSS 流量/CDN 按实际量买资源包；要监控权益"使用率"，用率 <80% 说明买多了、>98% 说明买少了。第四步立机制：预算设置按标签维度（生产/测试/业务线各自预算），消费达 80% 告警、100% 强告警（钉钉/邮件）；每周成本周会 review 浪费清单；成本 Owner 制让每个业务线认领并解释自己的账单；优化项按"金额 × 成功率 / 风险"排序，先做高 ROI 低风险动作。量化拆解：100 万 → 80 万的路径——关停浪费 + 降配省 10%（10 万）、节省计划/包年包月省 15%（15 万）、带宽/OSS 资源包省 5%（5 万），超出目标且留余量。实践中的坑：没做分账就谈优化（数据看不清，全靠拍脑袋）；先买节省计划后砍资源导致"权益用率暴跌"浪费更多；降配不做峰值评估把大促链路搞崩（降配前看 P99 利用率与峰值时段）；忽略快照与日志存储这种"看不见的账单"。

**延伸考点：** 节省计划（Savings Plan）与包年包月在"规格变配、实例增减"上的灵活性差异是什么？如何用"成本归因"定位一次账单暴涨（是新业务上线还是资源泄漏）？

### Q18. 电商大促弹性，弹性伸缩 ESS 怎么调才不崩不浪费？

**问题：** 你们的 Web 集群 20 台 ECS 挂在 ALB 后面，大促流量是平时 20 倍，去年大促出现过"扩容太慢打爆"和"活动结束缩容不及时白烧钱"两个事故。请设计弹性伸缩组 ESS（伸缩配置/规则/冷却时间）与 SLB、RDS 的联动方案，给出伸缩策略的量化参数。

**期望加分项：**
- 说清 ESS 组成：伸缩组（组内最小/最大实例数）、伸缩配置（实例模板：镜像/规格/安全组/UserData）、伸缩规则（目标追踪/步进/定时）、冷却时间（冷却期内不触发新伸缩，默认 300 秒）
- 混合策略：定时扩容（大促前 1 小时提前扩 10 台做预热）+ 动态扩容（CPU >70% 持续 3 分钟扩 5 台，目标追踪模式按负载自动调）+ 缩容保护（大促结束延迟缩容 1 小时，防止流量回弹）
- 联动设计：新实例自动加入 ALB 后端组（伸缩组绑定负载均衡）与 RDS 连接池（新实例启动后预建连接，避免连接风暴打垮数据库）；预热（启动脚本预热本地缓存与 JIT）完成前不切流量
- 量化参数：冷却时间 180-300 秒防抖动；扩容步进 5 台/次、最大实例数 = 峰值容量 × 1.2；缩容规则用"CPU <30% 持续 10 分钟"而非瞬间掉峰
- 容量保障：大促前确认实例库存与规格可用（按量配额申请），抢占式实例混部降低 30-50% 成本但要有兜底实例数
- 监控与复盘：伸缩活动记录（伸缩历史）留档，大促后复盘"扩了几次、提前多久、利用率曲线"，持续调参

**减分项：**
- 只有 CPU 阈值一种规则，没有定时预热、没有步进与冷却设计，扩容永远慢半拍
- 缩容用"CPU 低于 50%"瞬间触发，流量一抖就来回抖动，浪费又伤稳定性
- 新实例没做预热直接接流量，启动 3 分钟内大量超时（JIT 未热、缓存未载）
- 忽略 RDS 连接数上限，扩容 20 台把数据库连接打爆
- 不提前确认库存与配额，大促当天扩容失败

**解答：**

ESS 的核心是"伸缩组 + 伸缩配置 + 规则 + 冷却"四件套，工程要点是"提前、平滑、有界"。第一步建伸缩组与配置：伸缩组设最小 20 台、最大 60 台（峰值容量 × 1.2 冗余）；伸缩配置定义实例模板——镜像（含环境与生产参数）、规格（g 系列 8C32G）、安全组、UserData 启动脚本（拉代码、初始化缓存、注册到 APM）；绑定 ALB 后端组（新实例自动挂载、健康检查通过才接流量）与 RDS 白名单（自动加入 IP）。第二步定伸缩策略，三种规则配合：一是定时扩容——大促开始前 90 分钟触发，预扩 10 台并把 JVM/本地缓存预热好（预热脚本跑一遍核心接口）；二是动态扩容——目标追踪模式（Target Tracking）：以"CPU 平均利用率 60%"为目标，系统自动决定扩缩，或步进规则"CPU >70% 持续 3 分钟 +5 台、>85% 持续 1 分钟 +10 台"；三是缩容——"CPU <30% 持续 10 分钟"才缩，且开启"缩容保护"（大促结束后 1 小时内禁止缩容，防流量回弹抖动）；冷却时间设 180-300 秒，防止扩完又被缩。第三步联动与预热：新实例接入 ALB 前必须通过健康检查，启动脚本里做"预热"（本地缓存加载、线程池初始化、JIT 预热请求），否则扩容后前几分钟全是超时；RDS 侧要给伸缩组预留连接配额（如连接数上限 ×1.5），实例启动后限制并发接入，防连接风暴；数据库连接用连接池 + 限流，必要时开启 RDS 代理（Proxy）做连接复用。第四步成本与容量保障：大促前提前在目标可用区确认实例库存与按量配额（提交配额申请），核心容量用按量/包年包月保证，混入抢占式实例（占 30-50%）降成本，但伸缩组里配置"最低按量兜底台数"，避免抢占式被回收导致容量塌方。复盘：看伸缩历史（扩缩时间点、次数、冷却触发情况）与实例利用率曲线，迭代规则参数。实践中的坑：冷却时间太短导致振荡（扩 5 缩 3 反复横跳）；UserData 里脚本报错导致新实例全部异常（伸缩配置上线前先在单台验证）；忘了给 RDS 白名单自动放行，新实例连不上库。

**延伸考点：** 目标追踪扩缩容和步进规则有什么区别？"预热"在扩容链路里为什么如此关键（启动到就绪的时间线）？

### Q19. 100 台 IDC 服务器与 3TB 数据库要迁上云，方案怎么做？

**问题：** 公司决定把 IDC 里的 100 台物理机（业务 + 数据库）整体迁到阿里云，其中 MySQL 库 3TB（有 8 小时停机窗口），Web 服务可短暂停机，但要求迁移期间业务不停。请设计服务器迁移中心 SMC、DTS 数据迁移与 OSS 数据同步的组合方案，给出迁移顺序与回滚预案。

**期望加分项：**
- 说清工具分工：SMC（服务器迁移中心）做整机迁移（源服务器 Agent 采集 → 制作镜像 → 云端重建，支持不停机迁移）；DTS（数据传输服务）做数据库迁移（结构+全量+增量，支持不停机）；OSS 用于对象数据（文件、图片）批量同步与迁移中转
- 迁移顺序：先小后大、先非核心后核心：①网络打通（VPN/专线）→ ②OSS 文件先同步 → ③非核心服务 SMC 迁移验证 → ④核心应用 + DTS 数据库迁移（切换）→ ⑤流量切到云上 → ⑥老机房只读观察 + 回滚窗口
- DTS 不停机迁移细节：全量迁移 + 增量同步（binlog 实时追平），切换时"应用停写 → 增量追平 → 切换读写 → 应用改连串"，切换窗口从 8 小时缩到分钟级；迁移前做兼容性检查（版本、字符集、大小写敏感）
- SMC 迁移要点：先做迁移演练（测速、带宽评估：100 台 × 50GB ≈ 5TB 数据，按 100Mbps 专线估算 5-6 天，要提前同步）；Windows/Linux 迁移到目标实例规格与目标盘的规划；迁移后验证（IP 变化、域名解析切换）
- 回滚预案：切换后保留老环境 1-2 周（DTS 反向同步或老库只读），出问题一键回切；DNS 与负载均衡切换用 TTL 调低
- 风险与量化：总数据量估算、带宽成本（专线/公网传输）、停机窗口控制（切换窗口 vs 迁移总时长）、业务验证清单（核心接口冒烟、数据校验行数）

**减分项：**
- 工具混淆：用 SMC 迁数据库或把 DTS 当整机迁移用，分工不清
- 没算传输带宽与时间，100 台数据同步一半发现带宽不够、迁移遥遥无期
- 不做兼容性检查（MySQL 版本、字符集），迁移后乱码/语法报错
- 切换时"直接停机迁移"不用增量同步，8 小时窗口全用来拷数据
- 没有回滚预案，切完发现有问题回不去，只能硬扛

**解答：**

迁移工程的关键是"工具分工 + 顺序 + 不停机 + 可回滚"。工具分工：SMC 管整机（物理机/虚拟机 → 云端 ECS：源端装 Agent 做数据同步与增量，云端生成目标镜像重建，支持原机不停机迁移）；DTS 管数据库（结构迁移 + 全量 + 增量持续同步，业务完全不停）；OSS 管对象数据（存量文件先走 OSS 批量上传/工具迁移，增量用 OSS 同步或云备份）。迁移顺序：第一步先打通网络（专线或 VPN，评估带宽：100 台总数据量约 5-10TB，100Mbps 专线全量传输约 6-10 天，所以先起量、后起业务）；第二步 OSS 文件层先同步（图片/附件/日志，量大且不敏感）；第三步非核心服务用 SMC 迁移、做首次端到端验证（域名、内网互通、依赖配置）；第四步核心数据库用 DTS：结构 + 全量（分批 3TB 约数小时到天级）后开增量同步（追 binlog），保持与源库毫秒级一致；第五步切换——选业务低峰（如周日凌晨），先停应用写入口，等增量追平（lag 归零），RDS 提升为主库，应用改连串指向云上 RDS，切换窗口从 8 小时压缩到 10-30 分钟。第六步核心应用 SMC 迁移收尾，DNS/ALB 权重灰度切流量到云端。每个环节都要有验证与回滚：迁移后跑数据校验（表行数、checksum 抽样、关键报表对账）；老环境保留 1-2 周，DTS 开反向同步（云上 → 老库）或老库只读，出问题一键回切（DNS 切回 + 应用连串切回）。实践中的坑：迁移前没做 MySQL 兼容性检查（5.7 → 8.0 的排序规则、sql_mode、保留字差异），上线后 SQL 报错；SMC 迁移后目标实例的内网 IP 变了，没同步改依赖配置（用内网域名或按需保留 IP）；忽略了增量期间的 binlog 保留时长（源库 binlog 只留 24 小时，全量跑 3 天导致增量断流，要先调大 binlog 保留）；切换当天忘了把源库连接清掉，双写冲突数据不一致。

**延伸考点：** DTS 迁移中"全量 + 增量"的追平阶段，如何确认数据一致再切换？如果增量断流（binlog 过期），现场怎么处理？回滚窗口内老库如何保持可用？
