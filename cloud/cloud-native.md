# 云 · 云原生（面试题库）

本文件考察候选人在云原生工程落地上的真实能力：Serverless 与函数计算、托管容器（ACK/EKS）、事件驱动、可观测性、弹性设计、成本治理（FinOps）、存量应用改造迁移、云原生安全。题目全部为场景化提问、不考八股文——重点看候选人能否给出量化依据、说清取舍、引用线上实践佐证、主动覆盖边界条件，难度从实践基础渐进到架构级设计。

---

### Q1. 你说自己懂云原生，先解释它到底解决什么问题？

**问题：** 面试官请你用 3 分钟给团队讲清楚"云原生"是什么。要求不能只背定义，要讲明白：为什么传统"把单体塞进虚拟机"不算云原生？四大支柱（容器/编排/微服务/DevOps）各自解决什么问题？它和"上云"（云计算）是什么关系？

**期望加分项：**
- 给出可判定的定义：云原生 = 利用云的弹性/按量付费能力，通过容器、编排、微服务、DevOps 四要素构建的系统，强调"面向云设计"而非"把旧系统搬到云上"
- 用"搬上云 vs 长在云上"对比说清与云计算的关系：IaaS 只是改变了资源获取方式，云原生改变的是系统架构与交付节奏
- 四大支柱能落到工程价值上：容器解决环境一致性与打包；编排（K8s）解决调度、自愈、弹性；微服务解决独立部署与故障隔离；DevOps 解决交付频率与反馈闭环
- 给出反例佐证：单体部署在 ECS 上、手工扩容、每周一次发布，这种"上了云但不算云原生"
- 能说出云原生的最终衡量标准：部署频率（周→天/小时）、扩容时间（天→分钟）、故障恢复（人工→自动）
- 不把云原生等同于 K8s，能指出微服务化的代价（分布式事务、可观测性）与不适用场景

**减分项：**
- 只背 CNCF 官方定义或念"云原生=容器+微服务+K8s+DevOps"的关键词组合，说不清各自解决什么问题
- 分不清"上云"与"云原生"，把"用了云服务"当成云原生
- 认为云原生就是 K8s，或认为必须全微服务才算云原生
- 只讲好处，不讲微服务化的代价与适用边界
- 无量化指标，说不出改造前后部署频率、扩容速度、故障恢复时间的变化

**解答：**

先用一句话定性：云原生是一套"面向云的能力设计系统"的方法论，核心不是用了多少云产品，而是系统是否生来就适配云的弹性、按量付费与自动化。它与"上云"的区别在于：上云只是把资源获取方式从自建机房换成云厂商 API，架构没变；云原生要求从架构层面利用云的特性。四大支柱逐个说价值：容器（Docker）把应用连同依赖一起打包，解决"在我机器上是好的"的环境漂移，也才有了秒级启停的粒度；编排（K8s）把成百上千容器的调度、自愈、扩缩容、滚动更新变成声明式声明+控制器自动执行，这是"故障恢复从小时级降到分钟级"的关键；微服务把大单体拆成可独立部署的小服务，让故障爆炸半径可控、团队可独立迭代；DevOps（CI/CD + IaC）把发布从人工脚本变成流水线，交付从月/周级压缩到天/小时级。判断一个系统是不是云原生，看三个量化指标就够：部署频率、扩容时间、故障自愈时间——传统虚拟机时代是"周级发布、天级扩容、人工故障转移"，云原生是"小时级发布、分钟级扩容、控制器自动拉起"。但要提醒：云原生是手段不是目的，微服务会引入分布式事务、链路追踪、多服务运维等新复杂度，低频小团队强拆微服务往往得不偿失，容器化 + 托管编排 + CI/CD 就足以覆盖大部分收益。

**延伸考点：** 如果一个系统全部用托管 PaaS（如 RDS、托管容器），但应用本身仍是单体重架构、每天人工发布，它算不算云原生？为什么？

### Q2. 团队想把一个低频内部工具迁到函数计算，要注意什么？

**问题：** 你们有个内部报表聚合服务：每天固定时段被调度系统触发 20 次，每次处理 1 万条数据、运行约 3-5 分钟，目前跑在一台常年闲置的 2C4G ECS 上（月费约 200 元）。有人提议迁到函数计算（Lambda/阿里云 FC）省成本。请评估这个迁移：函数计算的核心特性是什么？冷启动、无状态约束对这次迁移有什么影响？

**期望加分项：**
- 点出 FaaS 三大特性：事件驱动按调用计费（闲置零成本）、平台托管免运维、自动弹性；同时明确代价：冷启动、无状态、运行时长与内存上限（Lambda 15 分钟/10GB、FC 同样有上限）、并发受限
- 算清成本账：该任务月费约 20 元（20 次/日 × 3 分钟 × 1GB 内存），相比 ECS 200 元/月省 90%，但需把"闲置 ECS 的成本"与"改造工时、冷启动、限时风险"一起算 TCO
- 冷启动应对：预留并发（Lambda Provisioned Concurrency / FC 预置实例）消除冷启动，但要为预置实例付常驻费；或接受冷启动因为低频任务不敏感
- 无状态约束的落地：状态写外部（S3/RDS/Redis），任务分段切分到超时上限内，用幂等保证重试安全
- 指出平台限制：3-5 分钟任务没问题，但函数不能有长连接、不支持 WebSocket 服务端、出网 IP 池变化会影响白名单对接
- 说清"弹性"对这类低频任务的实际意义：峰值本来就是 20 次并发内，弹性价值有限，成本才是主因

**减分项：**
- 只喊"Serverless 省钱/免运维"，说不清计费公式（内存×时长×次数）和冷启动机制
- 把无状态约束当耳旁风，原封不动把持本地状态/临时文件的代码搬进函数
- 不知道超时上限（15 分钟），也不谈任务切分与重试设计
- 认为冷启动只发生在"第一次"，说不清实例回收机制（空闲后回收、下次触发重新初始化）
- 只算云账单不算改造工时和边界条件（白名单、出网 IP、日志）

**解答：**

函数计算的核心是"按调用计费 + 平台托管 + 自动弹性"：费用 = 分配内存 × 实际执行时长 × 调用次数，函数执行完实例即回收，所以闲置期间零成本。这个任务非常适合：月费用估算 20 次/日 × 30 天 × 0.05GB-时长级计量，约 10-30 元，对比 ECS 的 200 元/月，省 90% 以上——前提是接受两个约束。第一是冷启动：实例空闲回收后，下一次触发要重新拉取代码、初始化运行时，冷启动 200ms-2s（Java 更慢）。对本任务，20 次/天的低频调用且无用户等待，冷启动完全无感，不必开预留并发（预留并发 = 常驻计费，反而回到 ECS 的成本结构）。第二是无状态约束：函数不保证实例复用，代码里绝不能写本地文件、内存缓存当唯一状态源。落地做法：中间结果写 S3，进度写 Redis，任务用"分段 + 续跑"模式拆到单次 5 分钟内；触发器用定时触发器（cron）或 EventBridge 调度。实践中的坑：一是超时——如果数据量涨到超 15 分钟，要改成把任务拆成多段由每次调用处理一段，或改用容器形态（Step Functions 编排）；二是出网 IP——函数实例 IP 池是动态的，下游数据库白名单要放开函数所在 VPC 的子网段，或让函数接入 VPC；三是依赖层——大体积依赖要打层（Layer）避免每次冷启动拖慢。迁移后用云监控核对每次执行的时长、内存、错误率，确认成本与耗时符合预期即可。

**延伸考点：** 如果这个任务要求 500ms 内返回且 QPS 稳定在 1000，函数计算还合适吗？预留并发和冷启动的账怎么算？

### Q3. 托管 K8s（ACK/EKS）比自己搭集群贵一倍，还值得用吗？

**问题：** 你们从裸 K8s 集群（自建 3 master + 5 node）迁移到托管集群（ACK/EKS/GKE），运维反馈"托管集群每月控制面费用和 EKS 集群费让账单涨了，而且还得自管节点"。请你作为架构负责人回答：托管容器服务和自建 K8s 到底差在哪？这笔"托管成本"买到了什么？什么情况下自建反而更划算？

**期望加分项：**
- 能准确画出责任边界：托管服务厂商管控制面（API Server、etcd、调度器）+ 核心组件（kubelet 自动升级、节点组自愈），用户只管节点与工作负载；EKS 控制面 $0.10/小时 + 每集群每月约 73 美元，ACK 免控制面费但节点与集群本身按量
- 用"隐性成本"说服人：自建的 etcd 备份恢复、控制面高可用（3 master）、K8s 版本升级（每季度一次大版本，一次升级演练 2-3 天人力）、证书过期、组件故障排查，这些每月折算人力远超托管费
- 说清托管的核心收益：控制面 SLA（99.9%+）、版本升级一键完成、etcd 自动备份、节点组（NodeGroup）支持自动替换故障节点与自动伸缩
- 能给出自建更划算的边界：超大规模（上千节点）用云厂商节点费用与托管费分摊后、强合规要求完全自控、需要深度定制 K8s 组件（如自研调度器）或离线/私有化环境
- 给出折中方案：托管集群 + 托管节点组，或 EKS + 自管节点（Fargate/EC2 混合）降低节点管理成本
- 提醒托管不等于免运维：节点补丁、工作负载、Ingress、镜像仓库仍需自管，常见误区是"上了托管就什么都不管"

**减分项：**
- 只比较"控制面费用数字"，算不出自建的人力/升级/备份隐性成本
- 认为 EKS/ACK 就是"把 K8s 装到云上"，说不清控制面托管与节点组自愈的差异
- 不知道自建集群升级的痛（etcd 版本兼容、kubelet 与 API Server 版本差、coredns/ingress 依赖）
- 一刀切"托管永远优于自建"，说不出自建的适用场景
- 忽略迁移过程本身（从裸 K8s 迁到 EKS 的 kubeconfig、网络 CNI、存储类、Ingress 迁移）

**解答：**

托管与自建的差异本质是"控制面运维责任"的转移。自建集群里，etcd 备份与故障恢复、3 master 高可用、证书轮换、每季度一次大版本升级（先升级控制面、再逐个节点排空升级 kubelet）、异常组件排查，这些是你每个季度 2-3 天的人力消耗，而且出一次 etcd 脑裂事故，恢复成本是托管费的上百倍。托管服务（EKS/ACK/GKE）把这些收编为厂商职责：控制面 99.9%+ SLA、etcd 自动备份、一键版本升级、节点组支持自动替换故障节点和节点级自动伸缩。EKS 的显性成本是每集群每月约 73 美元控制面费 + 每节点按量；ACK 控制面免费但卖的是"免运维"和产品化能力。判断是否值得，别只比账单数字，要算 TCO：一个 30 节点规模的自建集群，专职或半专职运维每月至少 0.5-1 人天持续投入，按 2 万/人月的市场价折算，每月隐性成本 1-2 万元，远超托管费。自建反而划算的场景很窄：一是超大规模（上千节点）且团队有成熟 K8s 运维体系，控制面分摊成本低于托管费；二是强合规/离线私有化，数据不能出域；三是需要深度定制组件（自研调度器、准入控制器）。多数企业应选托管，但必须清楚边界：托管只管控制面和节点生命周期，镜像扫描、工作负载配置、Ingress、RBAC、成本治理仍是你的事。迁移时注意 CNI 选型（VPC-CNI vs overlay）、StorageClass 重建、原有 helm/ingress 兼容，先小流量灰度再全量切。

**延伸考点：** 托管集群的节点补丁和内核安全更新谁负责？如果等保合规要求审计 K8s 控制面，托管集群如何满足？

### Q4. 订单状态变化要通知下游 5 个系统，事件总线还是消息队列？

**问题：** 电商订单创建/支付/退款时，需要触发库存扣减、通知推送、风控检查、物流下单、数据同步五个下游动作。有人建议用消息队列（Kafka/RocketMQ）做解耦，有人建议用事件总线（EventBridge/云上 EventBridge）。请对比两者，给出选型结论，并说明事件源、规则路由、事件模式（Event Pattern）怎么设计。

**期望加分项：**
- 准确说出本质区别：消息队列是"点对点/分组消费"的点对点语义，一条消息被一个消费者组消费一次；事件总线是"发布-订阅 + 按规则路由"，同一事件可按事件模式（JSON Schema 过滤）广播给多个不同目标的订阅者
- 场景对应：通知推送/数据同步这类"每个下游都要拿到全部订单事件"用事件总线（EventBridge 一个事件路由到 5 个目标，规则按 type/source 过滤）；需要"逐条有序消费 + 重试补偿"的库存扣减用队列（保证 at-least-once + 幂等消费）
- 能说出事件总线核心概念：事件源（source，如订单服务/API 网关/定时器/云服务事件）、事件模式匹配（Event Pattern，按 JSON 字段过滤）、目标（Target，函数/HTTP/SQS/Kinesis）、死信队列（DLQ）
- 处理投递语义差异：事件总线默认 at-least-once、目标可能重复收到，所以下游必须幂等；队列也有 at-least-once，但消费顺序和批量、ack 机制更精细
- 提醒混用常见误区：事件总线不适合做"需要精确一次、强顺序"的流水线，也不适合替代业务数据库表间同步
- 实践佐证：云上 EventBridge 免运维、支持 schema registry、与 AWS 服务原生集成（S3 事件→EventBridge→Lambda），成本按事件量计费

**减分项：**
- 把事件总线和消息队列混为一谈，说不出"广播路由 vs 分组消费"的语义差异
- 只谈概念，答不出事件模式（Event Pattern）怎么写、DLQ 怎么配、目标重试策略
- 忽略幂等：事件总线是 at-least-once 投递，下游不幂等会重复扣库存/重复推送
- 不分场景，一律推荐 Kafka 或一律推荐 EventBridge
- 不考虑顺序性与回放：需要顺序消费时事件总线规则目标各自独立，顺序无法保证

**解答：**

两者都是解耦工具，但语义完全不同：消息队列解决"点对点/分组消费"——一条消息被某个消费者组消费一次，天然适合工作流接力（订单→扣库存→出库）；事件总线解决"发布-订阅 + 规则路由"——一个事件按事件模式广播给多个订阅目标，适合"一个变化通知多个系统"。这个场景两个都要：库存扣减、物流下单是有顺序和精确性要求的业务链，用队列（RocketMQ 按订单 ID 分区保序，消费者组内顺序消费，失败进重试队列）；通知推送、风控检查、数据同步是"每个系统都要独立拿到事件、可独立失败"的，用事件总线——订单服务只发一个事件（source=order.service, type=order.paid, data=订单 JSON），EventBridge 上写规则：规则 A 匹配 type=order.paid 且 amount>0 投递到推送函数，规则 B 匹配 type=order.* 投递到数据同步任务。事件模式是 JSON 过滤表达式，如 {"source":["order.service"],"detail-type":["order.paid","order.refunded"]}，比队列的 tag 过滤强大且免运维。实践中三个坑：一是投递语义都是 at-least-once，下游函数必须幂等（按 event id 去重或业务幂等键），否则重复推送/重复写数仓；二是目标失败要配 DLQ + 重试策略（如指数退避 3 次后进 DLQ，另起巡检任务重放）；三是不要用事件总线做强顺序流水线，规则目标并行投递无全局顺序，需要顺序用队列分区。选型一句话：广播/扇出用事件总线，逐条接力/强序用消息队列。

**延伸考点：** 事件总线的重试和 DLQ 策略怎么设置才能既不丢事件又不会无限重试拖垮下游？事件总线如何和 S3 对象创建、定时器等云服务事件联动做自动化？

### Q5. Serverless 应用的数据层怎么办？RDS 还是 DynamoDB，怎么组合？

**问题：** 你们要把一个用户积分服务改造成 Serverless（Lambda/函数计算 + API 网关）。原服务依赖 MySQL（用户表、积分流水表）和本地 Redis 缓存。改造时有人建议"数据层也全 Serverless"（DynamoDB/云上表格存储 + Serverless Redis），有人建议继续用托管 RDS + 连接池。请给出你的数据层方案，并说明托管数据库、对象存储与 Serverless 计算如何组合。

**期望加分项：**
- 说清 Serverless 数据层选型的第一原则：连接数瓶颈——Lambda 每实例一个连接，1000 并发 × 每函数 3-5 个连接会瞬间打爆 RDS 连接上限（默认 100-200），所以要么用无连接的数据服务（DynamoDB/表格存储，HTTP 调用无连接池），要么用代理层（RDS Proxy/Aliyun RDS Proxy）复用连接
- 能按数据特征分类：用户画像、积分余额这类 KV/文档型高并发低延迟用 DynamoDB（按 RCU/WCU 计费，自动弹性，单表设计 + GSI）；强事务、复杂 SQL、报表统计用 RDS（Aurora Serverless 或 RDS Proxy + 常规 RDS），把事务边界集中在事务表
- 状态/大对象外置：临时文件、图片、导出结果放 S3/OSS（事件触发 Lambda 做缩略图/转码），函数本身零磁盘
- 说出组合模式的量化设计：DynamoDB 按需模式（on-demand）起步，读 100 并发时成本可接受；RDS 用 Proxy + 预留连接池，最大连接数 = 并发 × 每函数连接数 ÷ 复用率
- 冷热分层：热数据 Redis（Serverless Redis/ElastiCache）+ 冷数据对象存储，积分流水表按时间分区归档 S3（Athena 查询）
- 指出常见坑：把事务逻辑用多个 Lambda 跨服务拼凑会破坏原子性；DynamoDB 需要熟悉单表设计与查询模式前向设计

**减分项：**
- 无视连接数问题，直接"Lambda 连 RDS"，1000 并发时数据库被连接池打爆
- 只提"全上 DynamoDB"，不分析事务/复杂查询需求，也不提 RCU/WCU 成本模型
- 不知道 RDS Proxy 的作用（连接复用、突发保护、IAM 鉴权）
- 函数里写本地临时文件当状态存储，或用函数实例内存做缓存
- 不讨论幂等与重试对数据一致性的影响（函数重试会重复写流水）

**解答：**

Serverless 数据层的核心矛盾是"连接 vs 无状态"：Lambda 的并发实例各自建连接，数据库连接数是硬上限，所以第一原则是"能用无连接数据服务就不连数据库"。积分余额、用户画像这种 KV/文档型数据，直接上 DynamoDB（或表格存储）：HTTP 协议按请求计费，读按 RCU（1 RCU = 4KB/s 强一致读）、写按 WCU 计费，自动弹性无连接上限，单表 + GSI 设计可满足查询；用 on-demand 计费起步，避免预留容量浪费。有强事务和复杂 SQL 的部分（积分发放与流水写入要原子，账务对账要 SQL 聚合），保留托管 RDS：数据库前挂 RDS Proxy（连接复用 + 突发保护），把连接池上限设到 并发 × 每函数连接数 ÷ 复用率，例如 500 并发 × 2 连接 × 复用 10 倍 ≈ 100 连接上限。大对象和中间产物一律 S3/OSS：导出报表、头像图片、转码原片放对象存储，S3 事件直接触发 Lambda 做后处理，函数彻底无状态。组合模式的经典链路：API 网关 → 鉴权 → Lambda → DynamoDB 做读写（热点 key 前加 Serverless Redis 缓存，TTL 控制一致性窗口）→ 积分流水每 N 条异步批量写 S3 归档。实践中三个坑：一是函数重试会重复扣积分/重复写流水，写操作必须带幂等键（如 requestId 做唯一键或条件写，DynamoDB 的 ConditionExpression）；二是不要把分布式事务拆成多个函数编排，宁可一个函数内完成一个事务边界，跨服务用 Saga 补偿；三是预热与缓存一致性，DynamoDB 的 TTL 删除与 Redis 缓存要设计好失效窗口，避免读到脏数据。

**延伸考点：** DynamoDB 的容量模式（按需 vs 预留）在流量有明确波峰波谷时怎么选更划算？RDS Proxy 的连接复用如何解决 Lambda 突发并发下的"连接风暴"？

### Q6. 微服务拆了一堆，线上出问题怎么快速定位？可观测性三件套怎么落地？

**问题：** 你们把单体拆成 40 个微服务部署在 ACK/EKS 上，发布后用户反馈"下单偶尔超时"。排查时发现：日志散落在几千个 Pod 里、每个服务都有自己的一套监控大盘、一次请求跨 8 个服务根本串不起来。作为负责人，你如何用云原生可观测性（指标/日志/链路）解决这个问题？托管监控产品（ARMS/Prometheus 托管版/CloudWatch）怎么选怎么配？

**期望加分项：**
- 说清三件套分工：指标（Metrics）回答"有没有问题"（红黄绿大盘）、日志（Logs）回答"到底发生了什么"（结构化 + 检索）、链路（Traces）回答"问题出在哪个服务哪一环"（请求级瀑布），缺一不可
- 给出标准化落地：指标用 Prometheus 托管版 + 统一告警规则（RED 指标：Rate/Errors/Duration，SLO 落地）；日志统一采集（Fluent Bit → 托管日志服务/CloudWatch Logs），全链路 Trace 用 OpenTelemetry（OTel）埋点 → 托管 APM（ARMS/CloudWatch X-Ray），服务间透传 traceparent 头
- 打通"三合一"：把 traceID 打进日志，日志、指标、链路通过同一 ID 关联（ARMS 的 TraceID 搜索、Grafana 联动 Loki+Tempo+Prometheus 的 LGTM 栈）
- 给出排查 SOP：先看 SLO/告警定影响范围 → 看服务 RED 指标定位异常服务 → 看链路瀑布图定位慢调用/错误 → 看该 span 上下文日志定位根因
- 说出云原生环境的特有难点：Pod 频繁重建导致指标维度爆炸（用工作负载聚合标签而非实例标签）、日志多行与容器重启丢日志、采样策略（高 QPS 服务按 10% 采样避免存储爆炸）
- 提到托管 vs 自建的成本与运维边界：自建 Prometheus 在 100 万序列时的存储与查询压力，托管版按序列数/日志量计费，长期成本要预估

**减分项：**
- 只说"上 Prometheus + Grafana + Jaeger"，说不清三者如何协作、数据如何关联
- 指标/日志/链路混为一谈，分不清各自回答什么问题
- 不知道 OpenTelemetry 标准和 traceparent 上下文透传，全靠业务代码手写埋点
- 无排查 SOP，答不出"拿到一次超时怎么从大盘一步步定位到根因"
- 忽略采样、存储成本、日志与 traceID 关联等工程细节

**解答：**

三件套的正确分工是：指标回答"哪里红了"，日志回答"发生了什么"，链路回答"是哪一环"。落地先定标准：指标统一用 Prometheus 协议，服务暴露 /metrics 端点，由托管版 Prometheus（ARMS Prometheus/Amazon Managed Prometheus）抓取，大盘只按业务看 RED 三件——请求速率、错误率、P99 延迟，按服务和接口聚合；告警围绕 SLO 设置（如下单链路 P99 < 500ms 的 30 天达成率 99.9%）。日志用 Fluent Bit DaemonSet 采集到托管日志服务，要求应用输出 JSON 结构化日志并携带 trace_id。链路用 OpenTelemetry SDK 埋点，把 traceparent 头在 API 网关和各服务间透传，发送到托管 APM（ARMS 或 X-Ray），采样按错误全采 + 成功 10% 采样控制成本。三合一的关键是关联：APM 的每个 trace 都有一个 traceID，日志也带上它，这样排查时"点开一个慢 trace → 拿 traceID 去日志服务搜该请求的完整日志"就完成闭环。上线后的排查 SOP：收到"下单超时"告警 → 打开 RED 大盘确认错误率/延迟异常集中在哪个服务（假设是支付服务）→ 进 APM 看该服务的慢 trace 瀑布图，发现某次外部 HTTP 调用占 800ms → 拿 traceID 查支付服务与外部网关的日志，定位到是对方网关限流导致。云原生环境特有坑：一是 Pod 重建导致实例指标维度爆炸，聚合标签必须用 Deployment/Service 级别，实例级只用于排障；二是容器日志要处理多行拼接（Java 异常栈）和重启丢日志，用 Filebeat/Fluent Bit 的 multiline 解析；三是 OTel 探针版本与服务框架兼容问题，Java 用 agent 方式免改代码但要注意和 Spring Cloud 网关等框架的埋点覆盖。

**延伸考点：** 指标、日志、链路三者如何通过 traceID 和标签做关联查询（Grafana 的 Tempo+Loki 联动）？高 QPS 下 trace 采样率怎么定才既省成本又不漏问题？

### Q7. 有人说服务网格（Service Mesh）是"下一代微服务基础设施"，你怎么看？

**问题：** 团队在用 Spring Cloud（含 Hystrix 熔断、Ribbon 负载均衡）跑 60 个微服务，有架构师提议引入 Istio 服务网格，理由是"治理能力下沉、对业务代码零侵入"。请评估这个提议：Service Mesh 到底解决了什么？和云网络（云上 LB/NLB、VPC）怎么结合？这个团队该不该上？

**期望加分项：**
- 说清 Service Mesh 的本质：把流量治理（熔断、限流、重试、灰度）、可观测性（mTLS 加密、指标）、安全（身份认证）从业务 SDK 下沉到 Sidecar（Envoy）数据面，控制面（Istiod）下发配置，业务代码零侵入
- 能讲透取舍：收益是治理能力统一、语言无关、灰度/熔断配置化；代价是每个 Pod 多一个 sidecar（+1 核 512M 起步、每请求多一跳 ~1-2ms 延迟、整体资源 +10%-30%）、架构复杂度（控制面故障、sidecar 升级、配置下发风暴）
- 与云网络结合：南北向流量用云上 LB/NLB 或 API 网关终结（不入 mesh），东西向服务间流量才进 mesh；外部服务（RDS/Redis 出站）默认 passthrough 或通过 egress 网关控制
- 给出该团队的现实判断：Spring Cloud 已覆盖熔断/负载均衡/服务发现，SDK 模式在 60 服务规模是可维护的；上 Istio 的收益主要在"多语言混合、K8s 原生灰度（canary 按权重/Header 分流）、统一 mTLS 与审计"，若全是 Java 单语言且已有成熟 SDK 治理，收益有限、复杂度上升
- 给出渐进路线：先上托管 mesh（阿里云 ASM/Google Anthos 双栈）降低控制面运维成本，先只做 mTLS + 可观测性，再逐步接管流量治理；或用 Nacos + Spring Cloud 保持现状，等出现多语言需求再迁
- 提醒典型坑：Istio 与 K8s 版本兼容、注入后启动变慢、大集群配置下发延迟、与自研网关/SDK 重复治理的混乱

**减分项：**
- 只会背"Service Mesh 是基础设施层、sidecar 模式"，说不出它替代了什么、引入了什么成本
- 不谈取舍，直接结论"必须上 Istio"或"全是噱头"
- 不知道 sidecar 的资源开销和每请求延迟增量，也不做压测对比
- 分不清南北向（网关/LB）与东西向（服务间）流量的治理边界
- 不考虑团队现有 Spring Cloud 技术栈的迁移成本与重复治理问题

**解答：**

Service Mesh 的价值一句话：把流量治理能力从"每个服务的 SDK"下沉成"基础设施能力"。传统 Spring Cloud 把熔断、负载均衡、重试写在业务代码依赖里（Hystrix/Ribbon），换语言就得重写一套；Mesh 用 Envoy sidecar 代理所有进出流量，控制面 Istiod 通过 CRD 下发熔断/超时/灰度/限流配置，业务代码零侵入，还顺带拿到 mTLS 加密、全链路指标和基于身份的鉴权。但收益要拿成本换：每个 Pod 多一个 sidecar（约 1 核 256M-512M 起步），请求多一跳（P99 延迟 +1-2ms），全集群资源开销 +10%-30%，还要运维控制面（配置下发风暴、sidecar 与 K8s 版本兼容）。所以要不要上，取决于你现在缺不缺这些能力：如果团队是纯 Java 单语言、Spring Cloud 的 SDK 治理已稳定跑了一年，60 个服务规模完全可以不迁——SDK 模式的问题（多语言、治理与业务代码耦合、升级 SDK 要发版）在你这里都不存在，迁入 Istio 只会增加复杂度。反之，如果出现多语言服务（Go/Python）、需要"不改代码的流量灰度/熔断/限流"、或要统一 mTLS 和审计，Mesh 就是正解。架构上记得切分边界：南北向（用户入口）用云上 NLB/API 网关终结，不塞进 mesh；mesh 只管东西向服务间调用；RDS/Redis 等外部依赖走 egress。落地建议用托管 mesh（ASM/Anthos）先做可观测性与 mTLS，灰度策略从"Header 分流"这种低风险能力开始，等验证稳定后再逐步接管熔断限流，避免一步到位引入双治理体系冲突。

**延伸考点：** Istio 的金丝雀发布（按权重/按 Header/按实例标签）怎么做？如果 sidecar 注入后启动变慢、大集群配置下发延迟，你会怎么排查和优化？

### Q8. 秒杀来了，HPA 扩到 200 个副本还是扛不住，弹性设计哪里出了问题？

**问题：** 电商大促前，你们把服务部署在 ACK 上并配置了 HPA（按 CPU 使用率 70% 触发扩容），结果秒杀开始 30 秒后 HPA 才反应、5 分钟后才扩到目标副本数，期间大量 503。而且大促过后流量跌回平时，HPA 缩容太慢导致峰值费用挂了 2 小时。请复盘弹性设计：HPA/定时伸缩/指标伸缩怎么配合？缩容怎么做得又快又稳？弹性的边界（配额、数据库、下游）在哪？

**期望加分项：**
- 说清"3 层弹性"组合：①HPA（工作负载副本数，基于指标）；②节点级伸缩（Cluster Autoscaler/Karpenter 扩节点）；③定时伸缩（HPA Cron/Advanced StatefulSet，提前 30 分钟预热）。秒杀这种可预知峰值，必须用定时伸缩预扩 + 指标伸缩兜底，不能只靠 HPA 反应
- 量化分析 HPA 慢的原因：指标采集周期（Prometheus 15s scrape + HPA 默认 15s 同步 + 平滑窗口），从流量上来看到副本数变化有 2-5 分钟延迟；且 CPU 指标在大流量下会因队列堆积失真，建议用"每秒请求数/队列深度"这类业务指标（KEDA 或自定义 metrics）
- 缩容稳定方案：HPA stabilizationWindowSeconds（稳定窗口默认 300s，可调到 60-120s）、缩容阈值与扩容阈值解耦（如扩 70% / 缩 30%）、优雅下线（preStop sleep + 移除 endpoint + 排空连接）避免缩容把在途请求掐断
- 说清弹性边界：配额（vCPU 配额、Pod 数上限、镜像拉取并发）、节点池扩容速度（新节点初始化 3-8 分钟，要预留缓冲节点/Spot 竞价实例）、数据库连接数与下游限流（扩了 200 副本但 RDS 连接数 200，白扩）
- 成本控制：缩容要配合节点级缩容与 spot 实例（spot 便宜 60-70% 但可能中断，适合无状态服务）
- 兜底手段：提前压测确定单副本吞吐（如 1 副本 200 QPS），反推目标副本数 = 峰值 QPS ÷ 单副本 QPS × 1.5 冗余，直接配置为期望副本数

**减分项：**
- 只答"HPA 按 CPU 扩"，不知道 HPA 反应延迟从哪来（采集周期、同步周期、平滑窗口）
- 不做可预知峰值预案，全指望指标伸缩被动反应
- 只讲扩容不讲缩容，不知道 stabilizationWindow、优雅下线，导致缩容杀连接
- 无视弹性边界：扩了副本但节点池没容量/配额不够/数据库打爆，扩了白扩
- 不做压测数据支撑，副本数全靠拍脑袋

**解答：**

复盘结论是：秒杀弹性不能只靠 HPA，要"定时伸缩 + 指标伸缩 + 节点伸缩"三层配合。秒杀是典型可预知峰值，正确做法是大促前通过定时伸缩（K8s HPA Cron 或 ACK 弹性伸缩定时策略）提前 30-60 分钟把副本扩到位并预热 JIT/连接池，HPA 只做兜底。HPA 慢的根因要量化：Prometheus 15s 抓取周期 + HPA 默认 15s 同步周期 + 副本增长平滑窗口（默认 300s），一个突发流量从出现到副本数反应约 2-5 分钟；而且 CPU 指标在排队积压时失真（请求全堵在队列里，CPU 可能不高）。改法：用业务指标驱动——KEDA 按 SQS/队列深度或自定义 metrics（如每秒请求数）扩容，秒级反应；或直接用"压测得出的单副本吞吐"反推目标副本数一次性配置。副本数公式：压测得单副本 200 QPS，峰值 5 万 QPS → 期望副本 250 × 1.5 冗余 = 375，直接设为初始副本数，秒杀开始前就绪。缩容要稳：HPA 的 stabilizationWindowSeconds 从默认 300s 调小到 60-120s，扩缩容阈值解耦（CPU 扩 70% 缩 30%），且缩容前必须优雅下线——preStop 里 sleep 5-10s + 从 Service endpoint 摘除 + 等待在途请求排空（terminationGracePeriodSeconds），否则流量会瞬间打到存活副本。弹性边界是必答题：副本数 × 每副本配额不能超 vCPU 配额；节点池扩容要 3-8 分钟，节点级伸缩（Cluster Autoscaler/Karpenter）要提前配好最大节点数与 Spot 缓冲；最容易被忽略的是下游——RDS 连接数、Redis、下游限流，扩容前要同步放大数据库连接池上限和网关限流阈值，否则 503 从网关变成数据库报错，更难看。大促后把节点级伸缩的缩容策略（ScaleDown UtilizationThreshold、冷却时间）配好，配合 Spot 实例，峰值费用只会在峰值时段存在。

**延伸考点：** KEDA 基于队列深度/自定义指标扩容和 HPA 基于 CPU 有什么区别？缩容时优雅下线（preStop + Readiness 探针 + 连接排空）的完整时序是什么？

### Q9. 从 Jenkins 到 GitOps：云上 CI/CD 和"以 Git 为唯一事实来源"怎么落地？

**问题：** 你们现在用 Jenkins 手动构建镜像、kubectl apply 发布到 ACK，发布靠人盯、回滚靠翻历史命令。老板要求"发布要可审计、可回滚、任何人都能自助上线"。请设计一套云原生 CI/CD 方案：云上流水线怎么搭？GitOps 模式（Argo CD/Flux）解决了什么？发布策略（滚动/蓝绿/金丝雀）怎么选？

**期望加分项：**
- 说清 GitOps 核心：Git 仓库是集群期望状态的唯一事实来源，Agent（Argo CD/Flux）持续对比 Git 与实际集群状态，发现漂移自动收敛；一切变更走 MR（code review）→ 合并 → 自动同步，天然可审计、可回滚（git revert）
- 给出完整流水线设计：CI（CodeCommit/GitHub Actions/云效）构建镜像 + 扫描 + 测试 → 推镜像仓库（按 commit sha 打 tag，不可变）→ 更新 Git 仓库的 manifest（image tag 变更）→ CD Agent 感知变更自动同步到集群；发布记录 = Git 历史，回滚 = revert 一次 merge
- 发布策略选择：默认滚动更新（maxSurge/maxUnavailable 控制）；核心交易用蓝绿（NS 级/Service 切流，回滚秒级）；金丝雀用 Argo Rollouts/Istio 按权重或 Header 灰度（5%→50%→100%，接监控自动放量/自动回滚）
- 落地细节：不可变镜像 tag（sha256 摘要），避免 latest 漂移；环境隔离（dev/staging/prod 用不同 Git 分支或目录 + 不同 Argo Application）；Sealed Secrets/External Secrets（SOPS + KMS）管理密钥，密钥不进 Git 明文
- 说清与 Jenkins 的本质差异：Jenkins 是"过程型"（流水线步骤），GitOps 是"声明型"（期望状态对比），后者把权限模型收归 Git（MR 审批 = 发布审批），配合 IaC（Terraform）管理集群外资源
- 指出坑：Argo CD 同步权限过大要按 Application 隔离 RBAC；漂移问题（热更新 kubectl 被覆盖）需要团队纪律；镜像更新频率高时 manifest 仓库会变成瓶颈（可用 Kustomize/Helm 参数化 + Argo CD 的 image updater 自动更新）

**减分项：**
- 只会背"CI/CD 就是 Jenkins 流水线"，说不出 GitOps 与传统 CD 的本质区别
- 发布策略只答"滚动更新"，不知道蓝绿/金丝雀的适用场景与实现方式
- 镜像用 latest tag，回滚无法定位到具体版本
- 密钥写进 Git 仓库或 manifest 里明文，无 Sealed Secrets/外部密钥方案
- 不设计权限与审计：任何人 kubectl apply 都能绕过流程

**解答：**

先纠正认知：Jenkins 式 CD 是"过程驱动"——流水线里写 kubectl apply，发布结果取决于这次命令执行，回滚靠翻历史；GitOps 是"声明驱动"——Git 仓库里放集群期望状态（Deployment/Service/ConfigMap manifest），Argo CD 或 Flux 作为 Agent 每 3 分钟对比 Git 与集群实际状态，发现不一致就自动收敛（自愈），因此 Git 历史就是完整发布审计日志，回滚就是 revert 一个 merge 或改回旧 tag。落地架构：CI 阶段用云上流水线（GitHub Actions/云效/CodePipeline）做构建 + 单元测试 + 镜像扫描 + 推镜像仓库，镜像 tag 用 commit sha（不可变，如 order-svc:7f3a1c9）；CD 阶段 CI 更新 Git 仓库里的 manifest（Kustomize 改 image tag 或 Argo CD Image Updater 自动提交），MR 合并即触发 Argo CD 同步，全程无人 SSH 进集群。发布策略按业务风险选：默认滚动更新，配 maxSurge=25% maxUnavailable=0 保证不中断；支付这类核心交易用蓝绿——新版本 Deploy 起来后切 Service selector，出问题一条命令切回，秒级回滚；重大版本用金丝雀（Argo Rollouts），先 5% 流量观察错误率/延迟，达标自动放量到 50%→100%，不达标自动回滚并告警。工程细节三件套：一是密钥——用 SOPS + KMS 加密或 External Secrets 对接云上 Secret Manager，Git 里只有密文引用，绝不明文；二是环境——dev/prod 用不同目录 + 不同 Argo Application 隔离，prod 的 Application 绑只读/审批权限，MR 审批即发布审批；三是权限——Argo CD 的 RBAC 按项目隔离，普通开发者无 write 权限，杜绝 kubectl 直连绕过流程。这套方案把"上线"从个人能力变成组织流程。

**延伸考点：** Argo CD 的"自动同步 + 自愈"遇到热更新怎么办（drift 检测与覆盖策略）？金丝雀发布如何接监控指标自动判断放量还是回滚？

### Q10. 镜像里有漏洞、容器能逃逸、凭证可能泄露——云原生安全从哪抓起？

**问题：** 安全团队扫描发现：你们的应用镜像里有一个高危 CVE（如 log4j）、部分 Pod 以 root 权限运行且挂载了宿主机目录、CI 里把 AWS/阿里云密钥明文写进了环境变量、生产集群任何人拿到 kubeconfig 都能提权。请给出一套分层的云原生安全方案：镜像扫描、运行时防护、安全策略（准入控制）、凭证与合规分别怎么落地？

**期望加分项：**
- 给出分层模型（Supply Chain → Cluster → Workload → Runtime → Compliance）：镜像供应链（扫描 + 签名）、集群配置（RBAC/网络策略/审计）、工作负载加固（非 root、只读根文件系统、丢弃能力）、运行时防护（Falco/托管 RASP）、合规基线（CIS Benchmark）
- 镜像安全落地：CI 里集成 Trivy/Grype（或托管镜像扫描，ACR/ECR 自带）在推送时扫描，高危 CVE 阻断构建；用 cosign 对镜像签名，准入控制只放行已签名镜像；镜像 tag 不可变，禁止 latest
- 准入控制落地：K8s 的 OPA/Gatekeeper 或 Kyverno 写策略：强制 securityContext（runAsNonRoot: true、readOnlyRootFilesystem、drop ALL capabilities、禁止 privileged、禁止 hostPath）；对新建 Pod 强制注入 sidecar（如安全 agent）
- 运行时防护：Falco 检测异常行为（容器内执行 shell、访问敏感路径、提权尝试、异常出网）→ 告警/阻断；云上可用托管安全产品（阿里云容器安全/Amazon GuardDuty + Security Hub）
- 凭证安全：不用长期 AK/SK，用 IAM Role + OIDC（EKS Pod Identity/ACK RRSA）给 Pod 授予临时凭证（STS 15 分钟过期）；CI 用 Secrets Manager/Parameter Store 引用，密钥不进代码与环境变量
- 合规：CIS Kubernetes Benchmark 定期扫描（kube-bench）、审计日志开启（API Server audit log 接云上日志审计）、最小权限 RBAC + 定期权限 review、多租户用 namespace + NetworkPolicy 隔离
- 排优先级：先堵最痛的（明文密钥 + root 权限 + 未扫描镜像），再逐步加固

**减分项：**
- 只提"装个镜像扫描器"，无分层思维，不知道准入控制与运行时防护
- 不知道 OPA/Gatekeeper/Kyverno 能做什么，说不出具体策略 YAML 要点
- 密钥用环境变量明文传递，不知道 OIDC/IAM Role for Pod 这种临时凭证方案
- 忽略 RBAC 最小权限与审计日志，认为"内网就安全"
- 不给优先级，方案大而全但无法落地（一次性推 50 条策略导致线上全挂）

**解答：**

云原生安全按"镜像 → 集群 → 工作负载 → 运行时 → 合规"分层治理，按风险排优先级落地。第一层镜像供应链：CI 里对每个构建跑 Trivy/Grype（或用 ACR/ECR 内置扫描），高危 CVE 直接阻断推送；镜像签名（cosign keyless）并把"只允许已签名镜像"写进准入规则，杜绝从公网拉未知镜像。第二层集群配置：RBAC 最小权限（namespace 级 Role 而非集群级 ClusterRole）、开启 API Server 审计日志接云上日志审计、按命名空间 NetworkPolicy 隔离。第三层工作负载加固，这是性价比最高的一层：用 Kyverno（比 Gatekeeper 上手快）写准入策略，强制所有 Pod 满足 runAsNonRoot: true、readOnlyRootFilesystem: true、securityContext.drop: ["ALL"]、禁止 privileged 与 hostPath 挂载，违规直接拒绝创建——策略要分两批灰度（先 audit 模式收集违规，再 enforce 模式阻断），否则一次全量 enforce 会打死所有存量工作负载。第四层运行时防护：Falco 以 DaemonSet 部署，检测容器内异常（如 Java 进程内出现 /bin/sh -i 反弹 shell、访问 /etc/shadow、提权 syscall），告警接 PagerDuty/云上威胁检测（GuardDuty、容器安全中心），配合"异常出网告警"发现数据外传。第五层凭证，最常见的致命伤：把 AK/SK 明文放进 CI 环境变量或用 secret 挂载到 Pod，泄露一次全库可删。正解是云厂商的 IAM + OIDC 联邦：EKS 用 Pod Identity / ACK 用 RRSA，Pod 启动时从 OIDC 换 STS 临时凭证（默认 1 小时过期自动轮换），代码里零密钥。合规上定期跑 kube-bench（CIS Benchmark）并修复差异项。落地节奏：第一周堵密钥与 root 权限，第二周接镜像扫描与准入策略灰度，第三周上 Falco 与审计日志，层层递进不搞一刀切。

**延伸考点：** Kyverno 的 audit/enforce 两种模式和"先收集违规再阻断"的灰度策略具体怎么做？EKS Pod Identity / ACK RRSA 的 OIDC 临时凭证换取流程是什么，为什么比挂 Secret 安全？

### Q11. 函数计算里跑支付回调：状态外置、幂等、超时重试、并发控制怎么设计？

**问题：** 你们用 Lambda/函数计算实现支付回调处理：第三方支付网关回调 → 函数验签 → 更新订单状态 → 通知发货。上线后发现三个问题：函数超时重试导致同一回调被处理两次（重复发货）；并发回调同时更新同一订单产生竞态；函数冷启动时验签所需的公钥要重新加载。请设计这个函数的完整方案：状态外置、幂等、超时重试、并发控制分别怎么做？

**期望加分项：**
- 状态外置：所有状态写外部存储（订单表/Redis），函数内不持状态；验签公钥放外部配置/Parameter Store 并本地缓存（全局静态变量 + 定期刷新），避免每次冷启动都拉取
- 幂等设计：数据库唯一约束或业务幂等键（order_id + event_id 联合唯一索引），或条件更新（UPDATE ... WHERE status='pending'），重试时命中已处理直接返回成功
- 超时与重试链路：网关回调解密验签后立即返回 200（异步化），实际业务处理放函数内部或 SQS 队列；函数超时设合理值（如 30s），失败抛异常让平台重试（Lambda 同步调用重试 2 次、异步 2 次/事件源按消息队列消息保留期重试）；重试必须指数退避 + 最大重试次数，配 DLQ 兜底人工补偿
- 并发控制：同一订单并发更新用乐观锁（版本号/条件更新），跨函数竞争用 DynamoDB 条件写或数据库行锁；事件源（SQS/Kinesis/EventBridge）并发数用保留并发（Reserved Concurrency）限制，避免打爆下游
- 处理"重复触发"与"乱序"：支付回调可能乱序到达（如先退款后支付成功），需要时间戳/状态机校验合法流转
- 可观测性：日志带 traceId/orderId，回调处理延迟与重试次数接入监控告警

**减分项：**
- 只说"用 Redis 存状态"，说不清幂等键怎么设计、重试为什么会导致重复处理
- 不知道平台重试语义（同步/异步触发重试次数不同），也没设计 DLQ 兜底
- 不做并发控制，直接"两个回调同时改订单状态"产生覆盖写
- 不处理乱序回调，认为回调一定按顺序到达
- 把验签公钥在函数里硬编码或每次冷启动实时拉取，不做缓存

**解答：**

这个场景的四个坑对应四种设计。第一，状态外置：函数是无状态沙箱，订单状态、处理进度必须落外部存储；验签公钥这类低频变化配置可以放 Parameter Store/OSS，用模块级静态变量做进程内缓存（首次加载后复用，定时刷新），避免每个实例冷启动都花 200ms 拉取。第二，幂等：平台重试是默认行为（Lambda 同步调用失败重试 2 次、异步 2 次、SQS 事件源最长按消息保留期重试），所以回调处理必须幂等——给回调事件生成 event_id，订单表加 (order_id, event_id) 联合唯一索引，重复插入直接命中已存在返回成功；更细的做法是条件更新：UPDATE orders SET status='paid' WHERE order_id=? AND status='pending'，行数=0 说明已处理过，直接幂等返回。第三，超时与重试：验签通过后立即向网关返回 200（避免网关 5xx 重试风暴），真正的业务处理建议放进函数或 SQS 队列异步执行；函数执行超时设置要大于外部调用最坏时延（如 30s），失败重试用指数退避（Lambda 异步自动退避，SQS 里配 maxReceiveCount=3 + DLQ），最终进 DLQ 由巡检任务人工/脚本补偿。第四，并发控制：同一订单的两个并发回调（如同时到"支付成功"和"退款成功"）会竞态——乐观锁：表加 version 字段，UPDATE ... WHERE order_id=? AND version=?，版本不符说明已被并发修改，重读再判断；并给该订单的处理放到单一串行通道（按 order_id 哈希分片到同一 SQS 分区）保证同订单串行。最后别忘了乱序：网关可能先送"退款成功"再送"支付成功"，函数里要按支付状态机校验合法流转（已退款状态收到支付成功回调应拒绝并告警）。四个设计做完，这个回调函数才能说"可靠"。

**延伸考点：** Lambda 同步与异步调用的重试次数差异是什么？SQS 作为事件源时 maxReceiveCount、visibilityTimeout、DLQ 怎么配合才算"不丢不重"？

### Q12. 一个 API 稳定在 2000 QPS 且延迟敏感，Serverless 还是容器？

**问题：** 你们有一个核心报价 API：白天稳定 1500-2000 QPS、晚上回落到 200 QPS，P99 延迟要求 300ms 以内，每次调用要查 Redis 和 MySQL。团队内部争论：上 Serverless（Lambda + 预留并发）还是上容器（EKS/ACK + HPA）？请给出决策框架：请求型 vs 常驻型负载怎么区分？冷启动容忍度怎么评估？两种方案的成本模型分别怎么算？

**期望加分项：**
- 先按负载形态分类：请求型（低频、突发、可容忍秒级冷启动）适合 FaaS；常驻型（持续流量、延迟敏感、长连接/长耗时）适合容器；这个 API 白天 2000 QPS 稳定、延迟 300ms 严格，是典型"常驻型"，容器 + HPA 或至少预留并发覆盖
- 冷启动容忍度量化：无预留并发时 Lambda 冷启动 P99 可能 500ms-1s（Java 更差），直接吃掉 300ms 预算；预留并发（Provisioned Concurrency）能压到 10-50ms 但要付常驻费，算下来和容器费用相当甚至更贵
- 成本模型对比：Lambda 费用 = 请求数 × 内存 × 时长 + 预留并发常驻费；容器费用 = 节点费用 + 弹性冗余。算账：2000 QPS × 100ms × 1GB 内存 ≈ 每分钟 1.2 万 GB-秒 × 0.00001667 美元 ≈ 每小时约 3.3 美元，加预留并发常驻费后与 4 台 4C8G 容器（约 1.2 美元/小时 × 冗余）的差距不大；流量 24 小时稳定时容器甚至更便宜，流量剧烈波动时才体现 FaaS 优势
- 混合方案：白天用容器或预留并发，夜间低谷把流量切到按需 Lambda（或容器 HPA 缩到 2 副本），用"形态随流量切换"拿两头的好处
- 其他约束：常驻连接（MySQL 连接池）在 FaaS 上是灾难，容器天然支持；Java/GraalVM 冷启动差异、WebSocket 长连接不支持 FaaS
- 提醒"规模拐点"：低流量时 FaaS 显著便宜，高且持续流量时容器更划算，拐点取决于单价与利用率，要自己压测算

**减分项：**
- 不区分负载形态，张口"全部 Serverless"或"全部容器"
- 不知道冷启动对 300ms 延迟预算的影响，也不提预留并发
- 算不出两种方案的成本，只会说"Serverless 省钱/容器贵"
- 忽略连接（MySQL/Redis 连接池）在 FaaS 下的问题
- 不提供混合/演进方案，答完选型就结束

**解答：**

先给结论：白天稳定 2000 QPS、P99 300ms、要连 MySQL/Redis 的 API，是典型的常驻型负载，正解是容器（EKS/ACK + HPA），或"容器为主 + 预留并发兜底"。决策框架分三步。第一步，形态判断：请求型负载的标志是"调用稀疏、突发、可容忍秒级初始化"，如低频报表、图片处理、定时任务；常驻型的标志是"流量持续、延迟严格、需要维持连接池与热缓存"——你们的 API 三项全中。第二步，冷启动容忍度：无预留并发时，Lambda 冷启动 P99 普遍 500ms-1s（Java 2-3s），直接超出 300ms 预算；用预留并发可以把冷启动压到 10-50ms，但预留并发就是常驻计费，等于"用 FaaS 的价格买容器的特性"。第三步，成本模型：Lambda 按 请求数×内存×时长 计费，2000 QPS × 100ms 平均时长 × 1GB 内存，每分钟消耗 1.2 万 GB-秒，按 0.00001667 美元/GB-秒约每小时 3.3 美元；加预留并发常驻费后，一天 7×24 约 80-120 美元。容器方案：压测单副本 4C8G 扛 500 QPS，需要 4-6 副本 ≈ 2-3 台 4C8G 节点（按量约 0.2-0.3 美元/小时），加 HPA 弹性与节点冗余，一天约 15-25 美元——明显更便宜。也就是说，流量持续且可预测时，FaaS 的"按量计价"反而变成劣势：你为每个请求付单价，而容器是固定成本摊薄。反过来，如果流量波动剧烈（白天 5000 QPS 晚上 50 QPS），FaaS + 预留并发（按时段开）就划算。所以最佳实践是混合：白天流量期用容器（或预留并发），夜间低谷用 HPA 缩容或切 Lambda 兜底，再结合预留实例/Spot 把容器成本再压 40-60%。最后提醒：连接问题——Lambda 每个实例一个连接池，2000 QPS 下并发实例 × 连接数会打爆 MySQL，必须 RDS Proxy；容器天然无此问题，这也是常驻型别硬塞 FaaS 的硬理由。

**延伸考点：** 预留并发（Provisioned Concurrency）的计费逻辑和"按时段自动开关预留并发"（如夜间关闭）怎么做？什么流量特征下 Lambda 按量计费比容器划算？

### Q13. 云原生账单涨了 30%，FinOps 从哪下手？成本归属和闲置治理怎么搞？

**问题：** 采用云原生后，云账单环比涨了 30%。分析发现：开发环境集群 24 小时跑满（实际只有工作时间用）、很多 Deployment 配了 8 核但实际用 0.5 核、几十个无用的 NLB/存储卷没人清理、有的团队把测试流量打到生产集群蹭"生产稳定性"。作为负责人请设计成本治理方案：成本归属怎么定？闲置资源怎么治理？请求计费型（Serverless）和常驻实例型（容器）的成本抓手有什么不同？

**期望加分项：**
- 先做成本归属：按 namespace/label 打成本标签，云账单按标签拆分到团队/项目（EKS 的 Cost Management/阿里云 ACK 成本分析），每月"成本看板 + 环比 + 预算告警"，让每笔钱找到主人
- 容器闲置治理量化：用 VPA（推荐）或 Prometheus 抓实际用量，把 8 核 16G 的 request 降到实测 P95 用量（如 1 核 2G），request 不是 limit——超卖靠 limit 控风险；用 K8s 的 idle 分析工具（kube-cost/开源成本分析）直接输出"每工作负载浪费 X 美元/月"
- 环境级治理：开发/测试集群用定时缩容（夜里/周末 CronJob 缩到 0 副本，KEDA 定时或节点池缩容），非工作时间可省 50%-70%；环境隔离：测试集群与生产集群物理分离（namespace 隔离挡不住资源互相挤占）
- 常驻型 vs 请求型抓手差异：容器主要抓手是 request/limit 合理化 + 节点利用率（目标 60%-80%）+ 预留实例/Spot 覆盖（可省 40%-70%）；FaaS 主要抓手是内存规格（超额内存贵 3 倍且冷启动更慢）、超时时间（过长的 timeout 会积压并发实例）、预留并发开关、错误重试风暴（重试也计费）
- 设置治理闭环：成本预算（预算 >80% 告警）、闲置资源自动清理（未使用的 NLB/EBS/快照打标签 + 定期巡检清理脚本）、月度 review 会
- 说清"降本有边界"：不能牺牲稳定性——request 下调后要保留 buffer，SLO 不达标时成本治理优先级让位

**减分项：**
- 只会说"上 FinOps"，说不清成本标签、归属、预算的具体落地动作
- 不看实际用量就一刀切缩 request，导致 CPU throttling / OOM
- 忽略开发环境与测试环境这一最大浪费源（24 小时空转）
- 分不清请求计费型和常驻实例型的成本抓手差异
- 没有"治理后验证"环节（改完不看账单环比与 SLO 是否达标）

**解答：**

成本治理的第一步永远是"归属清晰"：给所有资源打标签（team/env/cost-center），K8s 层面用 namespace + label 标注工作负载，云账单按标签拆分（EKS Cost Management / ACK 成本分析 / 各云厂商的 cost explorer 标签视图），每月输出"团队 × 环境 × 服务"成本报表，配预算告警（超预算 80% 告警、100% 阻断测试环境自动发布）。归属清楚后，按浪费源排序治理：第一大头通常是开发/测试环境——开发集群 24 小时空转，直接上"定时伸缩"：工作日 9:00-20:00 运行，其余时间 CronJob 把 Deployment 缩到 0、节点池缩容到最小，能省 50%-70%；同时要求测试流量不得打生产集群，namespace 隔离改为物理集群隔离。第二是 request 虚高：用 VPA（Vertical Pod Autoscaler）或 Prometheus 拉 30 天 P95 实际用量，把 request 降到实测值 + 20% buffer（8 核→1.2 核），注意 request≠limit，limit 按峰值×2 保留防 OOM，改完观察 throttling 指标确认没被限流。第三是孤儿资源：未绑定的 NLB、快照、EBS 卷、容器镜像旧 tag，打标签 + 定期巡检自动清理（例如快照保留 30 天策略）。常驻实例型（容器）的进阶抓手是节点利用率：目标是 60%-80%，低于就做 request 合理化或合并工作负载，再叠加预留实例 + Spot 覆盖非关键工作负载（省 40%-70%）。请求计费型（FaaS）抓手不同：内存规格降档（1GB→512MB 价格直接减半且冷启动更快）、超时时间合理化（避免长 timeout 让并发实例堆积）、预留并发只在高峰期开启（低谷关掉）、排查"重试风暴"（Lambda 重试也计费，错误率高时成本异常飙升往往源于此）。治理闭环：每季度 review 账单环比 + 每项治理动作单独记录节省金额，确认 SLO 无回退，成本优化才算成立。

**延伸考点：** 为什么 request 和 limit 要分开设置？VPA 的三种更新模式（Off/Initial/Auto）在生产上应该怎么用？预留实例/Spot 的覆盖策略怎么定才不牺牲可用性？

### Q14. 把一个单体 Spring Boot 应用改造成云原生，改造清单怎么排优先级？

**问题：** 你们有个 8 年历史的老单体：Spring Boot + MySQL，跑在一台 16C32G ECS 上，配置写在 application.properties 里打进了 jar、本地写临时文件、内置了内存缓存、每天半夜有一个全量定时任务。目标是把应用容器化并部署到 ACK，并且后续要能平滑拆微服务。请给出改造路线图：12-Factor 应用原则怎么落地？配置外置、无状态化、可水平扩展分别怎么做？优先级怎么排？

**期望加分项：**
- 给出 12-Factor 对照改造的落地映射：配置外置（ConfigMap/Secrets 或环境变量，config 不进镜像）、进程无状态（临时文件写 /tmp 或对象存储）、日志输出 stdout（由容器运行时采集）、进程可替换（健康检查探针）、并发（多副本水平扩展）、一次性进程（定时任务独立成 Job）
- 按"不改变业务行为"排优先级：第一步容器化 + 配置外置 + 探针（收益最大风险最低）；第二步无状态化（会话外置 Redis、临时文件外置、内存缓存改为 Redis/本地缓存降级）；第三步定时任务拆分（Spring @Scheduled 抽成独立 K8s CronJob，避免多副本重复执行）；第四步才是微服务拆分（按边界用 DDD 限界上下文拆 2-3 个）
- 说清配置外置细节：application.properties → 环境变量（SPRING_PROFILES_ACTIVE + ConfigMap），敏感配置用 K8s Secret/云上 Secrets Manager，镜像用不可变 tag，构建产物与配置解耦
- 无状态化的关键判断：内存缓存/会话是否可容忍丢失；事务与补偿是否可跨进程；本地文件（上传/导出）必须迁移到 OSS/S3 挂载
- 给出探针配置要点：livenessProbe（进程是否存活）/readinessProbe（能否接流量）分开配，Spring Boot Actuator 暴露 /actuator/health 与 /actuator/ready，就绪探针先于存活探针，启动预热（initialDelaySeconds + 慢启动）避免刚启动就被摘除
- 提醒坑：多副本后定时任务重复执行、分布式锁（如 ShedLock + Redis）；JVM 在容器里的内存感知（-XX:MaxRAMPercentage）；本地 Session 依赖需外置到 Redis；数据库连接池按副本数调整

**减分项：**
- 一上来就拆微服务，不先做容器化与无状态化，风险不可控
- 配置打进镜像，环境差异靠"重新打镜像"解决
- 本地写文件/内存缓存/内置会话不改造，直接上多副本必然出事故
- 定时任务不处理多副本重复执行问题
- 探针乱配（liveness 和 readiness 混用、就绪探针不存在），发布时流量打到未就绪 Pod

**解答：**

改造优先级原则是"先容器化、再无状态化、后拆微服务"，每一步都不改变业务行为。第一阶段容器化（1-2 周）：写 Dockerfile（用 JRE 基础镜像 + 分层缓存，注意 JVM 加 -XX:MaxRAMPercentage=75 让 JVM 感知容器内存限制），应用镜像只含代码与依赖；配置外置——application.properties 里的环境差异项（数据库地址、密钥、开关）全部改为环境变量，通过 ConfigMap 注入、敏感项用 Secret/Secrets Manager 注入，镜像 tag 用 commit sha，彻底告别"打镜像改配置"。第二阶段无状态化（2-3 周）：①会话/缓存外置——内置内存缓存和 HTTP Session 迁到 Redis（或明确降级策略），否则多副本后同一用户请求被路由到不同副本会丢会话；②本地文件外置——上传文件、导出临时文件改 OSS/S3（业务量大时用对象存储事件触发后续处理）；③定时任务拆分——把 @Scheduled 的每日全量任务抽成独立 Job 模块，用 K8s CronJob 调度，避免多副本时任务执行 N 遍（若暂时不拆，加 ShedLock + Redis 分布式锁）。第三阶段部署到 ACK：配好探针——livenessProbe 用 /actuator/health（进程卡死才重启），readinessProbe 用 /actuator/health（就绪才进 Service），启动加 initialDelaySeconds 10-20s 和 slowStart（就绪探针的 initialDelay + failureThreshold），否则发布时流量打到还在预热 JIT 的 Pod 产生超时；再配 HPA、优雅停机（preStop + Actuator 的 graceful shutdown 等请求处理完）。第四阶段才谈拆微服务：先按 DDD 限界上下文识别 2-3 个高内聚模块（如用户、订单、报表），数据库先逻辑分离再物理拆分，用"绞杀者模式"（Strangler）灰度。整个改造的验收标准：多副本水平扩展后功能与性能不劣化，发布可以滚动无感，这才是云原生就绪。

**延伸考点：** JVM 在容器中的内存感知问题（MaxRAMPercentage、cgroup 限制）怎么解决？Spring Boot 优雅停机（graceful shutdown + preStop）的完整时序怎么配置？

### Q15. 老系统迁到托管集群：5 个服务、全量流量直接切，还是先灰度？

**问题：** 你们把 5 个 Java 服务（含一个 stateful 的调度服务和两个写库的订单服务）从自建 ECS + 自建 K8s 迁移到 EKS/ACK 托管集群。老板催得紧，要求"周末直接切"。作为负责人你怎么说服大家别硬切？迁移评估、灰度切换、探针、排障预案分别怎么做？

**期望加分项：**
- 先给迁移评估清单：依赖盘点（数据库/Redis/MQ 的连接方式与白名单）、存储类型（PVC 迁移/StorageClass 重建）、网络（CNI 选型 VPC-CNI vs overlay、Service CIDR 冲突）、配置与密钥（ConfigMap/Secret 重建）、版本差异（kubelet/ingress/helm 兼容）
- 明确"stateful 服务是最大风险点"：调度服务（@Scheduled/Quartz）双集群同时运行会重复执行任务，必须先停旧集群该服务或用分布式锁；写库服务灰度期间双写/切库要设计好（新集群只读→低峰双写→切主）
- 灰度策略分层：①基础设施先行（非关键服务先迁，验证 CNI/存储/探针）；②按服务从无状态到有状态排期；③流量灰度用"双集群 + 网关按比例分流"（旧集群保留，Ingress/网关按权重 10%→50%→100%），或按内部测试流量先打新集群
- 探针与就绪验证：readinessProbe 配好才能接流量，灰度后对比新旧集群同一服务的错误率、P99、CPU/内存、GC 指标，量化差异后再放量
- 排障预案：回滚方案必须提前演练——新集群 Service 权重归零、保留旧集群 7 天（数据回切窗口），数据库迁移（如自建 MySQL→RDS）用 DTS/双向同步保证可回切；监控、日志、告警在新集群就绪后才切流量
- 提醒"一次性切换"的灾难场景：CNI 或 DNS 配置问题在流量全量时引爆、stateful 双跑丢数据、StorageClass 不存在 PVC Pending

**减分项：**
- 只谈"周末切了再说"，没有评估清单与回滚预案
- 忽略 stateful 服务双集群运行的风险（定时任务重复执行、写库双写）
- 不做灰度，全量流量直接打到新集群
- 探针不配或乱配，就绪校验缺失就放流量
- 没有量化对比（错误率/P99/资源）就宣布迁移成功

**解答：**

"周末直接切"的结局通常是：新集群 CNI 和自建集群的 overlay 差异导致服务间不通、PVC 指向的 StorageClass 不存在 Pod 全 Pending、调度服务双集群跑导致订单重复处理——所以必须按"评估 → 灰度 → 验证 → 回滚预案"走。第一步评估盘点：5 个服务的依赖图谱（连的库、Redis、MQ 地址与白名单是否指向新 VPC）、存储（确认新集群有对应 StorageClass，PV 用快照迁移或重新初始化）、网络（CNI 选型：VPC-CNI 直通性能好但要规划 Pod CIDR 与安全组，overlay 迁移成本低；Service 网段不能与旧集群冲突）、配置密钥（ConfigMap/Secret 全部迁到 GitOps 管理）、组件版本（ingress-controller、helm 版本与自建集群对齐）。第二步按风险排序灰度：先迁无状态且流量小的服务（如报表、配置中心），验证 CNI、DNS、探针、日志采集全部正常；订单这类写库服务用"新集群先只读、低峰期双写验证一致性、再切主"三步；调度服务最危险——@Scheduled/Quartz 双集群会双跑，切流前必须停掉旧集群的调度任务或引入分布式锁（ShedLock + Redis），切完验证任务执行次数无重复。第三步流量灰度：不靠"改代码"，用网关/Ingress 权重分流，新旧集群 Service 并存，10% → 50% → 100% 逐步放量，每档至少观察 1 个业务周期（含一次全量任务）。第四步量化验证：对比新旧集群同一服务的错误率、P99 延迟、CPU/内存、GC 时长、慢 SQL，指标持平才放下一档；探针必须提前配好（readiness 决定能否接流量、liveness 决定自愈，Spring Boot Actuator 暴露 /actuator/health），否则放量瞬间流量打进未就绪 Pod。第五步回滚预案：灰度期间旧集群不销毁、Service 权重随时归零；数据库迁移用 DTS 双向同步保证 7 天可回切；写一份"切流失败 10 分钟回滚"的清单并演练一次。全部通过后，旧集群保留观察一周再下线。迁移不是一次事件，是一个有 gate 的流程，每过一个 gate 都有数据说话。

**延伸考点：** 双集群灰度期间如何保证"同一订单只在一边被处理"（幂等与锁）？自建 MySQL 迁到托管 RDS 的 DTS 双向同步回切方案怎么设计？

### Q16. API 网关、K8s Ingress、云上 SLB/NLB——流量入口到底放几层？

**问题：** 你们的服务都部署在 ACK/EKS 里，目前架构是：云上 SLB/NLB 直接挂到 Service，服务里再用 Spring Cloud Gateway 做路由和鉴权，每个微服务自己又写了一套限流。现在要统一治理（鉴权、限流、灰度、Mock），有人建议引入 Kong/APISIX 或云上 API 网关，把 Spring Cloud Gateway 干掉。请给出流量入口的完整设计：API 网关、Ingress、SLB/NLB 各自的职责边界是什么？怎么选型？

**期望加分项：**
- 画清三层职责：SLB/NLB 是 L4 负载均衡（四层转发、证书终结、高可用，不感知 HTTP 语义）；Ingress 是 K8s 标准的七层入口（路由规则、TLS，如 ALB Ingress/Nginx Ingress）；API 网关是"业务面"入口（鉴权、限流、灰度、Mock、API 生命周期管理、监控），三者可以并存也可以合并
- 给出层叠架构与取舍：公网入口 → SLB/NLB（四层+证书）→ API 网关（Kong/APISIX/云上 API 网关，做鉴权限流）→ Ingress（路由到 Service）→ Pod；也可以"SLB → Ingress 直通"简化但功能少
- 说清"为什么需要独立 API 网关"：认证鉴权（JWT/OAuth/API Key）、按 API 维度限流、调用方维度配额、灰度发布（按 Header/权重分流）、Mock 与版本管理、访问日志与计费——这些放 Ingress（Nginx 配置）里维护成本高且易错，网关把策略配置化、可视化
- 与微服务网关的关系：有 Spring Cloud Gateway 时二选一，原则是"网关只留一层"——统一到 API 网关后，微服务内不再重复实现鉴权限流（重复治理 = 配置漂移 + 故障面扩大）
- 选型维度：开源（Kong/APISIX，APISIX 对 K8s 友好、支持 K8s 原生 CRD）vs 云上托管（阿里云 API 网关/AWS API Gateway，免运维、按调用量计费、与云产品集成）；性能（网关 P99 增加 1-5ms 可接受，用压测验证）
- 落地要点：网关层的高可用（多副本 + 无状态）、熔断（网关对下游服务故障降级）、限流策略（按 AppId/密钥维度 + 全局 QPS）、灰度先于网关落地（Header 分流规则）

**减分项：**
- 分不清 L4 负载均衡、Ingress、API 网关的层次，混为一谈
- 认为"Ingress 就能做鉴权限流"，忽略 Nginx 配置型治理的维护成本与错误率
- 网关层叠加多层（Spring Cloud Gateway + Kong + Ingress 全上），职责重复、故障面扩大
- 不谈网关性能损耗与压测验证
- 不谈网关自身高可用与限流/熔断配置

**解答：**

三层入口各司其职：SLB/NLB 是 L4 转发层——四层分发、TLS 证书终结、跨可用区高可用，不解析 HTTP 内容；Ingress 是 K8s 生态的七层路由——把外部流量按 host/path 路由到 Service，是"K8s 标准做法"；API 网关是业务治理层——鉴权、限流、配额、灰度、Mock、API 版本与文档、调用方管理。设计原则是"层数够用就行、治理能力唯一化"。推荐架构：公网 → SLB/NLB（四层 + 证书，自动高可用）→ API 网关（Kong/APISIX 或云上 API 网关）→ K8s Ingress（或网关直接路由到 Service，APISIX 支持 K8s CRD 可替代 Ingress）→ Pod。为什么必须独立网关而非用 Nginx Ingress 做鉴权限流：限流算法、AppId 密钥管理、按调用方配额、灰度 Header 分流这些用 Nginx 配置写，规则一多就配置漂移、改错一个正则就 502，且没有可视化；API 网关把策略做成配置对象（Kong 的 Plugin、APISIX 的 PluginConfig CRD），可审计可灰度。与 Spring Cloud Gateway 的关系：同一治理职责只保留一层——统一收口到 API 网关后，微服务内的鉴权限流代码删掉，用网关的插件能力替代（JWT 校验、按密钥限流），避免"网关限了、服务里又限一次"的双重限流互相打架。选型：Kong 生态成熟、APISIX 对 K8s 原生更友好（CRD 直管、支持 K8s Service 发现），云上托管网关（阿里云 API 网关/AWS API Gateway）免运维、按调用量计费、与云上日志/监控/认证集成，适合团队没有网关专职运维能力的情况。工程上三个必配：一是网关本身高可用——无状态多副本 + 副本数≥2、与 NLB 双 AZ 绑定；二是网关对下游的熔断降级——下游故障时网关快速失败（熔断后返回兜底 JSON），别让故障穿透到用户；三是灰度能力先于业务放量——网关按 Header（如 x-canary: true）分流到金丝雀版本，这是秒级回滚的兜底。最后用压测确认网关增加的 P99 延迟在 1-5ms 内，可接受再上线。

**延伸考点：** APISIX/Kong 的限流插件（按密钥/按 IP/全局）怎么配置，限流超限时的返回策略怎么定？网关层做鉴权后，微服务内部还需要二次鉴权吗（信任边界）？

### Q17. 老板说"多云，鸡蛋不放在一个篮子里"，你怎么设计多云云原生？

**问题：** 公司要在阿里云和 AWS 两个云上各部署一套业务（同一套代码），理由是"避免厂商锁定 + 单云故障容灾"。请你评估：K8s 的一致性在这里值多少钱？多云编排（同一套 manifest 管理两个集群）怎么做？哪些地方必然出现差异，怎么避免"伪多云"（两朵云各自为政，维护两套体系）？

**期望加分项：**
- 说清 K8s 在多云中的价值：工作负载层抽象统一（Pod/Service/Deployment 无差异），是"一份代码两份部署"的基础；但 K8s 只抽象了编排层，云厂商差异（LB、存储类、IAM、CNI、托管组件）依然存在，要靠抽象层隔离
- 给出多云编排方案：GitOps 双集群（同一 manifest 仓库 + 两个 Argo CD Application，按集群打 overlay/kustomize 差异）；基础设施差异用 IaC（Terraform Provider 两套，或 Terragrunt/Crossplane 抽象）；Service/Ingress 差异用 K8s 抽象（Ingress 由各云 Ingress Controller 实现）
- 诚实评估"多云容灾"的难度：双活需要数据层跨云同步（MySQL 跨云同步延迟与一致性、DNS 智能解析、会话同步），多数企业实际做成"主备 + 数据单向同步"；同云多 AZ 的可用性远高于"跨云主备"且成本低一个量级，先算账再决策
- 指出"伪多云"陷阱：只用了两朵云的 ECS+容器，没有统一 CI/CD、监控、日志、成本体系，等于运维两套平台；真正的多云要"统一治理面"（GitOps + 统一可观测性 + 统一成本）
- 防锁定的实操边界：K8s 原生 API 之外，慎用云厂商专有 CRD/服务（如 ALB Ingress 直接用专有注解、EKS Fargate、云上托管 RDS 的专有特性），这些才是真正的绑定点；选择标准接口（Ingress/CSI/CNI 标准、S3 兼容对象存储、MySQL 兼容）
- 提醒多云的成本真相：两套基础设施、两倍运维、云间流量费，多云通常比单云贵 30%-100%，"避免锁定"是长期期权不是即时收益

**减分项：**
- 认为"用了 K8s 就自然多云了"，看不到存储/LB/IAM/托管组件的差异
- 只谈"双活"，不说数据层跨云同步的现实约束（延迟、一致性、回切）
- 没有统一治理面（GitOps/监控/成本），做成了"伪多云"
- 不考虑云间专线/公网流量成本与延迟
- 不做成本评估，只说"防锁定"不看现实代价

**解答：**

K8s 在多云里的真实价值：它是工作负载层（Deployment/Service/Pod）的通用抽象，让"一份部署清单跑两个集群"成为可能，但别高估它——K8s 只抽象了编排，云厂商的存储、LB、IAM、CNI、托管组件依然是差异点。多云的落地架构分三层：第一层基础设施，用 Terraform 两套 Provider（或 Crossplane 抽象成统一资源）分别管理两朵云的 VPC/节点池，差异留在 IaC 层而不进业务代码；第二层编排，用 GitOps 双集群——同一个 manifest 仓库，两个 Argo CD Application 分别指向两个集群，环境差异（镜像仓库地址、StorageClass 名、Ingress 类名）用 Kustomize overlay 按集群打补丁；第三层数据，这是最难的：数据库要么各自独立（业务层做双写/对账）、要么主备单向同步（DTS/跨云同步任务，延迟分钟级，只能做主备不能双写）。必须诚实面对两个现实。一是"多云容灾"的真实性价比：同云内多 AZ 的 RPO/RTO 是分钟级、成本低一个量级；跨云双活的数据同步延迟和一致性窗口让很多"双活"沦为"看起来双活"，多数企业最终做成"主云 + 备云 + 数据单向同步 + DNS 切换"，先算这笔账再决定要不要多云。二是"伪多云"陷阱：只把 ECS 换成两朵云的容器，但 CI/CD、监控大盘、日志、成本报表各管各的，等于维护两套平台、两倍人力，锁定反而更重。真正的多云必须是"统一治理面"：GitOps 一套发布、Prometheus 联邦或托管监控统一看板、日志统一入湖、成本统一标签分析。防锁定的实操边界：K8s 原生 API 之外慎用云专有 CRD 和注解（比如 ALB Ingress 的专有注解、EKS Fargate、云上托管 RDS 独有特性），优先选标准接口——S3 兼容对象存储、MySQL/PG 兼容数据库、标准 Ingress/CSI/CNI。最后算成本：两套基础设施 + 云间流量 + 两倍运维，多云通常比单云贵 30%-100%，把"防锁定"当长期期权看，别当短期省钱方案。

**延伸考点：** Crossplane 与 Terraform 在多云 IaC 中的分工是什么？跨云数据同步（如 DTS/双向同步）的延迟、冲突、回切难点怎么处理？

### Q18. 云原生化之后数据库和缓存怎么办？连接池、弹性、一致性

**问题：** 你们把应用容器化并上了 ACK，HPA 能轻松把副本从 5 扩到 50，但数据库（托管 RDS）和缓存（Redis）没变。大促压测时发现：副本翻倍后 RDS 连接数告警、Redis 热 key 打满单分片、跨服务的数据一致性开始出错。请设计云原生数据层方案：托管数据库/缓存的弹性边界在哪？连接池怎么设计？数据一致性（最终一致）怎么保证？

**期望加分项：**
- 先说清"计算弹性 ≠ 数据层弹性"：HPA 扩的是计算副本，数据库连接数、Redis 容量、MQ 吞吐是固定上限，弹性设计必须把数据层纳入（扩容副本前先确认数据层余量）
- 连接池设计量化：单副本连接池上限（如 20）× 最大副本数 ≤ RDS max_connections × 0.8；连接池与 HPA 联动（KEDA 按数据库连接数/队列深度扩容），必要时用 RDS Proxy/连接池中间件；连接池参数（minIdle、maxTotal、获取超时）要按副本数重新核算，别用单机默认值
- 托管数据库弹性：RDS 主从升配（大促前升规格 + 只读实例挂从库分担读）、Aurora/云上 Serverless 形态、Redis 集群版（分片扩容）而非单分片；把"大促数据层预案"写进弹性清单：提前升配、预热连接、分库分表评估
- 缓存一致性：Cache-Aside 是默认（读穿透、写后删缓存而非更新），热点 key 用多级缓存（本地 Caffeine + Redis 兜底）与热 key 探测；保证"最终一致"的具体手段：写库后删缓存、消息队列异步补偿、版本号/时间戳比对，接受短暂不一致窗口并设 TTL 兜底
- 跨服务一致性：分布式事务尽量少用（2PC 代价大），用本地消息表 + 消息队列 + 幂等消费（Saga/事务消息，RocketMQ 事务消息），每个服务保证自己本地事务 + 发可靠消息
- 指出坑：副本数暴涨时缓存击穿/雪崩（热点 key 过期、缓存空值穿透打爆 DB），要用空值缓存 + 互斥重建 + 随机过期时间；大促后副本缩回来但连接池与数据库规格没降回来，成本浪费

**减分项：**
- 只讲计算弹性，无视数据库连接数/Redis 容量这些"弹性之外"的硬边界
- 连接池参数直接沿用单机默认值，副本翻倍后连接数打爆 RDS
- 缓存一致性只会说"缓存更新"，不知道写后删、双写不一致的坑
- 跨服务强一致用分布式事务硬解，不懂 Saga/事务消息/幂等
- 不做大促数据层预案（升配、只读实例、预热），压测才发现打爆

**解答：**

云原生数据层的第一个认知：HPA 扩的是"计算副本"，但数据库连接数、Redis 容量、MQ 吞吐是独立于副本数的硬边界——扩容前先确认数据层余量，否则 50 副本的 503 会变成数据库连接耗尽，更难恢复。具体设计按四块。第一，连接池：单副本连接池上限 × 最大副本数 ≤ RDS max_connections × 0.8（留 20% 给管理连接和突刺）。例如 RDS 上限 200，目标最大副本 50，则单副本池上限 = 200×0.8÷50 ≈ 3，必须关闭或调小每个副本的池子，避免 50×20=1000 个连接直接打爆；更优做法是挂 RDS Proxy（连接复用 + 突发保护），副本随便扩，连接数被代理层收敛。连接池参数要按副本数核算：maxTotal、maxIdle、获取连接超时（避免池满时副本内线程全部阻塞）。第二，托管数据库弹性：大促预案要写进弹性清单——提前升 RDS 规格、主库加只读实例分担读流量、Redis 从单分片升级集群版按需扩分片；同时用 KEDA 按"数据库连接数/慢查询数"反向驱动副本伸缩，让计算和数据层联动。第三，缓存一致性：默认 Cache-Aside——读先查缓存、miss 回源 DB 并回填；写则"先写 DB 再删缓存"（不要更新缓存，更新会有并发写脏），删除失败用 MQ 重试兜底；热点 key 上多级缓存（进程内 Caffeine + Redis），配空值缓存（缓存 5 分钟空结果）防击穿、随机过期时间（TTL ± 30%）防雪崩、互斥锁重建防并发回源。第四，跨服务一致性：别用 2PC 硬解，用本地消息表（业务操作与消息在同一本地事务写库）+ 可靠消息投递 + 消费端幂等（唯一消息 ID 去重），或 RocketMQ 事务消息——先发 half 消息、本地事务成功才 commit；下游消费失败进重试队列，最终一致。验收标准：压测从 5 副本扩到 50 副本，RDS 连接数、Redis 命中率、缓存 miss 回源 QPS 三条曲线都平稳，才算数据层弹性过关。

**延伸考点：** Cache-Aside 下"先删缓存再写库"与"先写库再删缓存"的时序差异，各自会有什么不一致？RocketMQ 事务消息的 half/commit/回查机制怎么保证"本地事务与消息发送"原子性？

### Q19. 自建 Prometheus + ELK 还是托管监控？云原生可观测性底座怎么选？

**问题：** 你们集群规模涨到 200 节点、400 个服务，现在自建了一套 Prometheus（单实例）和 ELK（3 台 ES），监控告警开始出问题：Prometheus 查询变慢、TSDB 频繁 OOM；ES 每天新增日志 200GB，磁盘、内存告警不断，索引生命周期管理没人维护。请评估：自建 vs 托管的取舍标准是什么？监控、日志两套底座分别怎么选？

**期望加分项：**
- 先量化现状问题根源：Prometheus 单实例在 50 万+ 序列时的查询与内存瓶颈（需要 Thanos/VictoriaMetrics 分片或降采样）；ES 在 200GB/天日志量下的存储成本（副本 ×2、冷热分层、ILM 索引生命周期）、集群运维（分片均衡、滚动重启）
- 给取舍框架：按"团队运维能力 × 数据量 × 定制需求"决策——数据量小（<10 万序列、<50GB/天）且团队有 SRE 时自建可控；量大或团队无专职可观测性运维时用托管（ARMS Prometheus/托管版 Prometheus、Amazon Managed Prometheus + CloudWatch/托管日志服务）
- 监控选型细节：托管 Prometheus 免 TSDB 运维、按序列数与采集量计费，数据量暴涨时成本也要估算（100 万序列 × 单价对比自建 2-3 台机器）；自建路线要明确组件拓扑（Prometheus 联邦/Thanos + 告警 Alertmanager 高可用 + 远程存储），别再用单实例
- 日志选型细节：托管日志服务（SLS/CloudWatch Logs/ELK 托管版）免 ES 运维，按存储量与查询量计费，日志量大时分层存储（热存 7 天 + 冷存归档 OSS，查询走冷存低频）；自建 ELK 则必须配 ILM（rollover + 冷热 + 删除策略）和压测索引吞吐
- 混合方案：监控托管（SLO 指标）+ 日志自建（合规需要数据不出域）或反之，给出"核心链路托管、审计日志自留"的折中
- 提醒迁移成本：自建→托管的迁移要评估历史数据迁移（Prometheus remote write/Thanos 归档导入、日志回放）、告警规则迁移、大盘（Grafana）复用（托管通常兼容 PromQL/Grafana）
- 指出"托管不等于免费"：托管按量计费在日志量暴涨时账单同样失控，配套降采样（指标按时间降精度）、日志采样与分层存储

**减分项：**
- 不分规模无脑推荐"自建省钱"或"托管省心"，说不出决策变量
- 不知道 Prometheus 单实例的扩展边界（序列数、内存、查询）和 Thanos/VictoriaMetrics 等扩展方案
- 自建 ELK 不配 ILM/冷热分层，磁盘被日志撑爆
- 不算托管按量计费的成本，误以为托管就是免费
- 忽略迁移成本与兼容性（PromQL/Grafana/告警规则）

**解答：**

自建 vs 托管的决策变量就三个：数据量、团队运维能力、定制/合规需求——把现状数字代入：200 节点 400 服务意味着指标序列轻松到 50-100 万、日志 200GB/天，这已经越过自建舒适区。先看监控：自建 Prometheus 单实例到 50 万序列后，查询慢、TSDB OOM、高基数问题都会爆发，扩展要么联邦+分片（运维复杂度高）、要么 Thanos/VictoriaMetrics（多一套组件），还要维护 Alertmanager 高可用；托管版 Prometheus（ARMS Prometheus/Amazon Managed Prometheus）把 TSDB、高可用、长期存储全收编，兼容 PromQL 与 Grafana，告警规则、大盘几乎零迁移成本——按"序列数 × 采样率"计费，100 万序列月成本大致相当于 2-4 台自建机器，但省掉的是专职运维人力和"集群挂了监控先挂"的讽刺局面。再看日志：自建 ELK 在 200GB/天 的量级必须配 ILM（索引按天 rollover、7 天热存 + 30 天冷存 + 归档删除）、副本、冷热节点分层，还要处理 ES 分片均衡和滚动重启——这些都是隐性人力；托管日志服务（SLS/CloudWatch Logs/日志服务托管版）免运维，按存储量与查询计费，关键设计是分层存储：热存 7 天（快速检索）、冷存转 OSS（合规留存、低频查询），配合日志采样（debug 日志采样 10%）、多行合并、过滤掉无用字段，把入湖量先砍一半。选型结论：团队没有专职可观测性 SRE、数据量到这个规模，建议监控+日志都走托管，用托管 Prometheus + 托管日志，Grafana 保留做统一大盘；只有两种情况坚持自建——强合规（数据不出域，日志必须本地）或深度定制（自研告警引擎、特殊降采样）。折中方案很常见：核心业务指标托管（SLO 必须可靠）、审计类日志自建本地留存。迁移要点：历史指标用 remote write 双写过渡、历史日志保留只读归档不迁移、告警规则与大盘先在 Grafana 里导出验证兼容。最后提醒：托管不是免费——日志量暴涨、指标高基数（如把 pod 实例维度做成长期标签）都会让账单失控，治理（降采样、标签收敛、日志分层）在托管下同样要做。

**延伸考点：** Prometheus 高基数问题的根源（标签维度爆炸）怎么识别和治理？日志分层存储（热/冷/归档）的保留周期与成本怎么定才平衡？

### Q20. 单体转微服务转云原生，这条演进路线的节奏和止损点在哪？

**问题：** 公司业务处于快速扩张期，现有架构是：一个 8 人团队维护的 Spring Boot 单体 + MySQL，每天发布 1-2 次，偶发性能瓶颈。CTO 说"今年必须完成微服务化 + 全面云原生"。你作为技术负责人要给出演进路线：单体 → 微服务 → 云原生的每一步目标是什么？节奏怎么排？怎么判断"该不该拆、拆到哪、何时停"（止损点）？

**期望加分项：**
- 先纠正方向：微服务化/云原生是手段不是目标，演进以"业务增长带来的痛点"驱动而非"技术先进性"驱动；每天发布 1-2 次、8 人团队的单体，当前痛点（性能、部署、协作）未必需要拆微服务解决
- 给出三步演进路线：第一步云原生化（不改架构）：容器化 + 托管集群 + CI/CD + 探针 + 可观测性，把部署频率、回滚能力、环境一致性提上来——这一步对单体同样成立，收益最大风险最低；第二步模块化：单体内先按模块拆代码边界（模块化单体/Modulith），数据库先逻辑隔离，找出真正的性能瓶颈（是 SQL 还是热点模块）再决定拆什么；第三步按需拆微服务：只拆"独立伸缩需求、独立团队边界、独立故障域"三个条件至少满足其一的模块，用绞杀者模式灰度
- 量化每步收益的验收指标：第一步看部署频率（天→小时）、回滚时间（小时→分钟）、环境搭建（天→分钟）；第二步看单模块独立发布的可行性；第三步看某模块独立扩缩容与故障隔离的实际效果
- 止损点设计：拆分的每笔投入必须对应可量化的收益（如某模块 QPS 独立波动、某团队独立发布频率差异），若拆完一个服务后部署频率/故障隔离没有改善，停止继续拆分；设置"拆分预算"——每次拆分需过架构评审且回填复盘
- 风险与反模式提醒：分布式事务、跨服务调用延迟、多服务可观测性成本，微服务化前期反而更慢；拆服务不拆数据库/连接共享是伪微服务；为拆而拆（微服务架构师陷阱）
- 兼顾成本：云原生化能立刻用上托管集群/Spot/弹性伸缩的省钱能力，微服务化的运维成本（多服务监控/告警/依赖）要算进账

**减分项：**
- 无脑支持"全面微服务化"，说不出每一步的验收标准与止损条件
- 第一步就拆微服务，跳过容器化/可观测性/DevOps 的地基
- 拆了服务不拆数据（共享库），事务/耦合问题原封不动
- 只看技术收益不算成本（分布式事务、多服务运维、可观测性投入）
- 没有"止损点"概念，拆到一半发现收益为负仍继续

**解答：**

先把目标对齐：云原生/微服务是手段，业务增长带来的具体痛点才是演进动力。8 人团队、日发布 1-2 次的单体，当前痛点是"性能瓶颈偶尔出现、发布偶尔出问题"，这不等于"需要微服务"。正确路线分三步，每步有独立验收标准。第一步云原生化（不拆架构，4-8 周）：单体容器化 + 上托管集群（ACK/EKS）+ CI/CD 流水线 + 探针 + 可观测性（指标/日志/链路），验收标准：部署从"人盯"变流水线、发布频率从每天 1 次到每天 5 次、回滚从小时级到分钟级、环境从"手搭"到一键——这一步单体能获得 70% 的云原生收益，是性价比最高的一步。第二步模块化（观察 1-2 个季度）：先不拆进程，把单体按模块（用户/订单/报表）重构代码边界，数据库表先按模块逻辑归集（仍在一个库），同时用链路追踪找到真实瓶颈——是某模块热点、还是 SQL、还是缓存缺失。多数单体到这一步就够了。第三步按需拆服务：只有同时满足"独立伸缩需求（模块 QPS 与整体波动不同）、独立团队边界（多人协作冲突）、独立故障域（模块故障要隔离）"中至少两个条件才拆，用绞杀者模式（新功能走新服务、旧功能逐步迁移）灰度，数据库同步拆分（每个服务独立 schema/库，共享库是伪微服务）。止损点必须显性化：每次拆分前写下预期收益（如"订单模块独立扩缩容，大促不再整体扩 3 倍"），拆分上线后一个季度回填实测（该模块是否真的独立扩展了、故障是否真的被隔离、发布频率是否真的提升），没达标就停止继续拆并评估回退；同时设"拆分预算"——每年最多拆 N 个服务，超预算必须走 CTO 特批。别忘了算账：微服务化的运维成本（每多一个服务就多一套监控/告警/依赖管理/链路追踪）、分布式事务与最终一致的业务改造成本，前期通常"更慢更贵"，只有当服务规模与团队规模都上来后收益才转正。演进不是终点冲刺，是"每步有收益、每步可止损"的连续决策。
