# 云 · 云网络（面试题库）

本文件考察候选人在云网络工程落地上的真实能力：VPC 规划与子网设计、安全组与 ACL 的分层防护、公网访问与 NAT、负载均衡选型、DNS/CDN、专线与 VPN 混合网络、跨 VPC/跨地域互联、内网服务发现、延迟丢包排障、云防火墙与 DDoS 防护、弹性网卡与多 IP、网络成本、高可用架构、网络监控、全球加速、东西向流量治理、三层架构落网以及 IPv6 演进。题目全部为场景化提问、不考八股文——重点看候选人能否给出网段与配置的量化依据、说清安全与性能的取舍、引用真实排障与事故案例、主动覆盖边界条件与降级方案，难度从实践基础渐进到架构级设计。

### Q1. 新业务要上云，VPC 的网段和子网怎么规划才不后悔？

**问题：** 你们要把一套微服务系统（前端网关、业务应用、Redis、MySQL、还有和外部合作伙伴的数据交换区）迁到阿里云 VPC（或 AWS VPC）。公司规划五年内业务规模翻三倍，还要和现有机房做专线打通。你会怎么设计 CIDR、子网划分和规模预留？

**期望加分项：**
- 有 CIDR 规划原则：业务网段用私网大段（如 10.0.0.0/8 内切分），每个 VPC 至少预留 16 位以上空间，禁止在生产环境用"正好够用"的 /24
- 子网按角色切分而非按团队：公有子网（接入层/NAT）、私有子网（应用）、隔离子网（DB/缓存，不放公网路由），数据交换区单独 VPC 与专线/伙伴对接
- 量化预留逻辑：给出单子网规模推导，如"按单 AZ 400 台 ECS、每台 3-4 个弹性网卡估算，子网至少 /22"，并保留整段扩展空间
- 主动考虑跨域冲突：与 IDC、伙伴、其他云厂商的网段统一登记，避免专线/CEN 打通后路由冲突；可用多 VPC 相同网段但禁止直接互通来规避
- 提到 AZ 与子网的关系：子网归属单 AZ，跨 AZ 高可用要求每个 AZ 有独立子网；网段预留要为新增 AZ 留足空间
- 有演进意识：提前规划 VPC 内网 CIDR 不可改、子网不可扩的约束，靠预留解决（如应用子网从 /24 预留 /22）

**减分项：**
- 只报一个 /24 就开干，没有规模推导与预留概念
- 按团队或按环境把子网切得又碎又乱，路由和 ACL 无从管理
- 不考虑与 IDC/伙伴网段冲突，专线一打通就路由冲突
- 不知道"子网绑定一个 AZ"这一基本约束，跨 AZ 高可用设计错误
- 没有"公有/私有/隔离"分层意识，数据库直接暴露在能出公网的子网

**解答：**

VPC 网段规划是"一次决策、终身买单"的事，因为内网 CIDR 创建后不可修改，子网一旦创建只能删了重来。我常用的套路是"大段切分 + 角色分层 + 双倍预留"。先在 10.0.0.0/8 里给每个 VPC 划 /16（如生产 10.1.0.0/16、测试 10.2.0.0/16），VPC 内部再按角色分三层：公有子网放 SLB/NAT/堡垒机（默认路由指向公网），私有子网放应用 ECS（仅内网路由），隔离子网放 Redis/MySQL（连 NAT 都不给，出公网走专用代理或完全禁止）。子网大小按"单 AZ 峰值实例数 × 每实例网卡数 × 2（冗余）"算：假设单 AZ 200 台应用、每台 3 个内网 IP，至少 /23，我通常直接给 /22 留翻倍空间。最关键的一步是先建一张全网段分配表：把 IDC 机房段、伙伴段、其他云段全部登记，新划网段先查冲突——我踩过专线打通后 10.0.0.0/16 与 IDC 段重叠、路由表里出现黑洞的坑，事后只能改 IDC 侧网段，代价极大。另外记住子网绑定单一 AZ，想做到多 AZ 容灾，每个 AZ 都必须有完整的一套子网，所以规划时就要为第三个 AZ 预留空间。总结一句：网段宁可大、不可重，子网宁可整、不可碎。

**延伸考点：** 子网创建后不能扩大，那业务增长导致 IP 耗尽时有哪些演进方案（新子网迁移 / VPC 迁移）？代价如何评估？

### Q2. 安全组和 NACL 都能拦流量，到底该信谁、怎么分层？

**问题：** 你们在云上部署了一套电商应用：SLB 对外，应用 ECS 在私有子网，数据库在隔离子网。安全团队要求"应用服务器只允许 SLB 访问 8080、数据库只允许应用网段访问 3306"。安全组和 NACL 都写了规则，但排查时发现两条链路行为不一致，你会怎么设计这套访问控制？

**期望加分项：**
- 讲清本质区别：安全组是实例级、有状态（回程流量自动放行），NACL 是子网级、无状态（必须成对配出入规则），两者是"纵深防御"的两层而非二选一
- 给出分层设计：NACL 做粗粒度子网边界（禁止公网直连数据库子网、默认拒绝跨子网横向），安全组做细粒度实例白名单（SLB→8080、app→3306），尽量"宽进严出、窄口化"
- 能说清优先级与规则匹配语义：安全组规则按序号从小到大逐条匹配、先命中先生效；NACL 是"默认拒绝 + 显式放行"，写错出入规则对会导致"出得去、回不来"
- 指出有状态 vs 无状态的坑：安全组只要入方向放行，回包自动通过；NACL 出方向忘了配回包端口范围（临时端口 1024-65535）就会丢包
- 有排障实战：同时命中安全组和 NACL 时，任一者拒绝即拒绝（交集生效），排查时先看哪一层挡的（VPC Flow Logs / 安全组事件）
- 提到数量与变更维度：安全组支持实例级动态成员（SLB 后端 IP 变化不影响），NACL 挂在子网上，变更影响整子网、需走变更窗口

**减分项：**
- 分不清有状态/无状态，不知道安全组回包自动放行
- 只用一个机制打天下，或把数据库 3306 用 NACL 对所有网段放行
- 不知道 NACL 无状态必须成对配规则，踩"能发出收不到回包"的坑
- 说不清规则匹配顺序与默认拒绝/默认放行语义
- 排障时不区分两层，抓包半天发现是 NACL 挡的

**解答：**

正确姿势是分层而不是二选一：安全组管"谁能访问我的实例"，NACL 管"哪个子网之间的流量该存在"，两层都拒绝才生效，所以先按最粗的边界设计 NACL，再用安全组收口。以这套电商为例：数据库子网的 NACL 入方向只放行应用子网网段到 3306，出方向放行回包与更新流量；应用子网 NACL 默认拒绝公网直入。安全组层面：SLB 安全组放 80/443 入方向，应用 ECS 安全组只放行 SLB 安全组 ID 到 8080（用安全组 ID 而不是 IP 段，后端扩缩容不用改规则），DB 安全组只放行应用安全组 ID 到 3306。这里有几个必踩的坑：NACL 是无状态的，出方向必须显式放行回包（一般放 1024-65535 临时端口），很多人只配了入方向，结果应用"能连上但请求全部超时"；安全组规则按序号顺序匹配，把 `0.0.0.0/0 拒绝` 写在放行规则前面会把所有流量挡掉。排障时先确认是哪层拒绝：抓包能看到 SYN 发出但无响应，多半是 NACL 无状态回包没放；连接直接 RST 或超时但在安全组规则里能看到，则看安全组事件。最终建议把 NACL 当"最后防线"（防子网横向扩散、防误配安全组时的裸奔），把安全组当"日常变更主战场"。

**延伸考点：** 为什么说"安全组用 ID 引用比用 IP 段更优雅"？多实例挂载同一安全组时，如何避免后加的实例意外获得过宽权限？

### Q3. 服务器出公网、用户进公网，EIP、NAT 网关、公网 LB 怎么搭配？

**问题：** 你们有个业务：用户要访问 Web 服务，同时部分 ECS 需要定时拉取外部 API、上传日志到对象存储。现在有人建议"给每台 ECS 都绑 EIP 得了，简单"。你会怎么设计公网访问方案，并说明 EIP、NAT 网关、公网 SLB 各自的定位？

**期望加分项：**
- 明确分层职责：入方向流量走公网 SLB（统一入口、隐藏后端 IP），出方向流量统一走 NAT 网关（SNAT，单点出口、可审计），EIP 只用于确实需要独立公网身份的实例（如对公网做回调、白名单源 IP 固定）
- 能算 NAT 的成本与容量账：NAT 网关按规格 + 实例计费，并发连接数、带宽上限、SNAT 条目数（阿里云按 EIP 数分配端口范围）都是规划点
- 讲清公网 IP 绑定方式差异：EIP 是独立资源可绑定/解绑，固定不变，配合白名单场景（第三方回调、SFTP 对接）必须用 EIP 而非动态 IP
- 指出典型反模式：给所有 ECS 绑 EIP——公网 IP 暴露面大、安全组难收敛、换实例后公网 IP 漂移、费用不可控（EIP 保有费 + 流量费）
- 有高可用考虑：NAT 网关双可用区部署、公网 SLB 多 EIP、出方向失败降级路径（如换备 NAT/直连 EIP）
- 提到 IPv4 地址枯竭与费用意识：能 SNAT 共享出口就不占用 EIP 配额，带宽计费（按固定带宽 vs 按流量）选型

**减分项：**
- 一句"给每台绑 EIP"解决一切，没有入/出方向分层概念
- 不知道 NAT 网关做的是 SNAT，不知道它与 EIP 的端口复用关系
- 不区分"入方向公网"与"出方向公网"，两者设计混为一谈
- 不考虑第三方白名单场景需要固定出口 IP，换 NAT 后源 IP 全变
- 没有容量评估：NAT 并发连接打满导致新连接失败、SNAT 端口耗尽

**解答：**

先分清楚两个方向：入方向（用户→服务）和出方向（服务→外部）是两套完全不同的设计。入方向推荐全走公网 SLB：用户只面对 SLB 的 EIP/域名，后端 ECS 全在私有子网、无公网 IP，攻击面收敛到 SLB 一层，配合 WAF/DDoS 防护统一挂载。出方向统一走 NAT 网关做 SNAT：所有 ECS 共享出口 IP，出口集中、日志可审计（NAT 网关有连接日志），也方便在第三方侧配白名单——注意出方向源 IP 就是 NAT 网关绑定的 EIP，一旦更换 NAT 或 EIP，所有依赖白名单的对端全部断连，这是线上事故高发点，变更前必须评估。EIP 只在三类场景独立使用：对公网提供回调/Webhook 的实例、需要固定源 IP 被对端白名单的实例（如 SFTP 对接）、以及 NAT 网关自身。反模式是"全员绑 EIP"：暴露面大、每实例都消耗公网 IP 配额和保有费，且 ECS 释放后 EIP 若没解绑会继续产生保有费。容量上要盯 NAT 的并发连接数与 SNAT 端口条目：TCP 连接 TIME_WAIT 堆积会耗尽端口映射导致新连接失败，常见对策是降低 keep-alive 超时、扩大 EIP 绑定数量（每个 EIP 对应一组端口范围）。一句话：入方向收口到 SLB，出方向收口到 NAT，EIP 是例外不是常态。

**延伸考点：** NAT 网关 SNAT 端口耗尽（丢连接）如何定位与缓解？把连接数、TIME_WAIT 和 SNAT 条目数串起来讲。

### Q4. 上云后入口从 Nginx 换成了负载均衡，SLB/ALB/NLB 怎么选？

**问题：** 你们有一套老系统用 Nginx 做入口：HTTP 层有路径路由、限流、改 header，TCP 层有长连接游戏服务和 MQTT 接入。上云后想用云负载均衡替换，有人说"一个 SLB 全搞定"。你会怎么选型和配置，健康检查与会话保持又该怎么设？

**期望加分项：**
- 讲清产品分层：NLB 是四层（TCP/UDP，高并发、长连接、私有网络接入），ALB/SLB 七层（HTTP/HTTPS，路由、证书、gRPC/WebSocket），"一个 SLB 全搞定"要分协议场景验证
- 场景匹配：Web API 用七层（路径路由到不同服务、证书卸载、HTTP/2）；游戏/MQTT 长连接用四层 NLB，避免七层代理打断长连接、降低转发时延
- 健康检查有量化设计：HTTP 健康检查用专门的 `/healthz` 端点而非业务页面（避免业务抖动误摘流量），间隔/超时/失败阈值按"摘除后重建时间"权衡，如间隔 5s、超时 3s、连续 3 次失败摘除
- 会话保持讲清机制差异：四层按源 IP、七层按 Cookie 插入，均与健康检查联动（后端宕机时会话重分配），并说明会话保持与水平扩容的冲突
- 有连接数/性能评估：NLB 单实例可支撑百万级并发连接，七层按 QPS/新建连接评估规格；后端 ECS 并发连接数（keep-alive 复用）与 LB 侧连接数的匹配
- 提到配额与坑：监听端口配额、后端服务器组数量上限、七层转发规则条数、连接超时时间（idle timeout）对长轮询/SSE 的影响

**减分项：**
- 分不清 L4/L7，把 WebSocket 长连接塞进会断连的七层超时配置
- 健康检查直接探测业务主页，促销抖动导致整组被摘除
- 不会设 idle timeout，SSE/长轮询连接被 LB 掐断
- 只字不提会话保持机制与扩容冲突
- 没有规格估算，随意选个最小规格上线，大促打爆新建连接

**解答：**

选型先回答两个问题：协议是 TCP/UDP 还是 HTTP/HTTPS？要不要做路径/域名级路由？四层用 NLB：游戏服、MQTT、Redis 代理这类长连接或非 HTTP 流量交给它，NLB 只做四元组转发、不解析应用层，百万连接轻松扛；它也不做 TLS 卸载，证书在客户端和后端之间直通。七层用 ALB：Web API、前后端分离、按 path 路由（`/api/*` 到订单服务、`/static/*` 到 CDN 回源）都是它的事，还能挂 WAF、做请求头改写。健康检查是排障高频点：正确做法是后端暴露专用 `/healthz`，返回 200 且不依赖 DB——我曾见过健康检查打到查询数据库的接口，DB 抖动时整组实例被摘流量，业务直接雪崩；参数上间隔 5s、超时 2-3s、健康阈值 3、不健康阈值 3，可以让"故障摘除"和"恢复上线"都在 15s 左右完成。会话保持按需开：七层默认按 Cookie（LB 插入会话 Cookie），四层按源 IP，但要知道会话保持会降低负载均衡的均衡性，大促扩容时老连接都钉在旧实例上，所以只对确实有状态的会话（购物车、登录态）开启，无状态服务全关。最后是连接超时：默认 idle timeout 60s 会掐断 SSE 和长轮询，线上遇到过前端"每 1 分钟准时断线"，把超时调到 300s 并让应用层发心跳才解决。

**延伸考点：** 健康检查"摘流量"机制在滚动发布中的应用：如何利用 LB 优雅摘除和放回实现零中断发布？

### Q5. 用户报"部分地区打不开网站"，从 DNS 入手怎么查？

**问题：** 你们用云解析（阿里云云解析 / AWS Route 53）管理域名，用户陆续反馈"某些地区打不开网站"，而你们确认服务器和负载均衡都正常。从 DNS 角度你会怎么排查，解析记录、TTL、CNAME/A 的选型又该怎么定？

**期望加分项：**
- 完整讲清域名解析链路：本地缓存 → 递归服务器 → 根/权威服务器，逐层找"哪里断了"，并说明运营商递归服务器缓存是"部分地区打不开"的常见原因
- 排查手段量化：用 `dig +trace`、`nslookup -type=A` 对比正常/异常地区、查权威 NS 是否一致、看解析是否被劫持/污染（TTL 异常、A 记录被改）
- 记录类型选型有理：顶级域名/对外主域名用 A 记录直指 SLB EIP，业务子域用 CNAME 指向云上域名（如 `app.xxx.com → lb-xxx.aliyuncs.com`），CNAME 不能与同名字段共存的其他记录混用
- TTL 有讲究：变更窗口期用低 TTL（如 300s）预热、稳定后调回 600-3600s；事故紧急切流量时 TTL 太长会导致切换要等整段 TTL 失效
- 有解析故障预案：DNS 切换（备 IP/备域名）、分线路解析（运营商线路）、故障时快速把 TTL 调低再切流量
- 提到云解析高可用特性：主备 DNS 节点、健康检查联动智能解析、以及 CNAME 链过长（超过 3 跳）在部分递归服务器上解析失败

**减分项：**
- 只会说"ping 一下域名看通不通"，不了解逐级缓存链路
- 不知道 TTL 在故障切换里的双刃剑作用
- CNAME/A 乱用：主域名加 CNAME 导致 MX 等记录冲突、或 CNAME 链过长解析失败
- 不区分运营商缓存与权威解析，看到本地能解析就断言域名没问题
- 没有切换预案，故障时才发现 TTL 还有一小时

**解答：**

"部分地区打不开"先默认是 DNS 问题，因为服务器正常的话，链路最脆弱的就是解析和运营商缓存。排查按链路逐级走：先用 `dig` 对比正常与异常地区的解析结果（让用户用公共 DNS 如 223.5.5.5 试），如果公共 DNS 正常、运营商 DNS 异常，就是运营商递归缓存问题；再用 `dig +trace` 看权威服务器响应是否正常、`dig NS` 确认权威 NS 配置一致；同时核对 A 记录 IP 是否与 SLB 当前 EIP 一致——域名泛解析或记录被改是另一个高频坑。定位到是"自己的解析配置"问题后，走应急切换流程：第一步把 TTL 从 600s 临时调低到 60-120s（让旧缓存快速失效），等切换生效窗口过去再改解析目标，否则 TTL 一小时，改完记录全世界还要等一小时才生效，这本身就是一次事故。记录选型：主站域名用 A 记录指 SLB，因为要配合分线路解析（电信/联通/移动各回各线）和健康检查；业务子域多用 CNAME 指向云负载均衡的官方域名，好处是 LB 换 IP 你不用改 DNS，坏处是 CNAME 链别超过 2-3 跳，有真实案例是 CDN→LB→回源的 CNAME 链在部分老递归服务器上解析超时。日常运维建议：变更 DNS 前先 `dig` 存底，变更后全线路抽查，线上事故时"先降 TTL、再切流量、最后复盘配置"。

**延伸考点：** 域名被劫持/投毒如何识别（对比公共 DNS、检查 TTL 突变、DNSSEC）？云解析的 DNSSEC 怎么开？

### Q6. 图片和静态资源越来越慢，CDN 配置完发现命中率很低，问题出在哪？

**问题：** 你们给网站接入了云 CDN（阿里云 CDN / AWS CloudFront）加速图片、CSS/JS 等静态资源，配置后测速确实快了，但看报表发现缓存命中率只有 40%，部分"动态页面"也走了 CDN 导致回源频繁。你会怎么排查命中率、设计缓存与回源策略，并判断是否该上动态加速？

**期望加分项：**
- 讲清 CDN 加速原理：边缘节点缓存 + 就近接入 + 回源（回源是最后手段），命中率是核心 KPI；静态资源与动态资源要分流
- 命中率排查有量化手段：按 URL/目录拆命中率、看不同节点命中率差异、查缓存键（cache key）是否被 query 参数打碎、查是否命中强制不缓存规则
- 缓存策略清晰：静态资源按文件类型设长缓存 TTL（如图片 30 天）+ 版本号/内容 hash 文件名来突破 CDN 缓存（`app.abc123.js`），HTML 短缓存或 no-cache 走回源
- 讲清回源策略：回源 HOST、回源协议跟随、源站为 OSS 时配回源鉴权防盗链；源站为 ECS 时注意回源带宽会打满服务器
- 对动态加速有判断：API 类请求走 CDN 反而更慢（加一跳），真需要动态加速的是跨地域的 App 接口（动态路由加速、TCP 优化），且要评估成本
- 有缓存一致性意识：资源更新后如何主动刷新/预热（URL 刷新、目录刷新、预热），了解 CDN 边缘缓存与源站版本不一致的坑

**减分项：**
- 只说"配了 CDN 就快了"，说不清命中率、缓存键、回源这些核心指标
- 把带随机参数的 URL（如 `?t=timestamp`）也默认缓存，或反过来全不缓存
- 不知道文件改名（hash 命名）与 CDN 刷新是两套思路，缓存无法失效
- 动态接口也套 CDN，延迟反而变高还烧流量费
- 没有防盗链/回源保护意识，源站被拖垮

**解答：**

CDN 的价值全在"边缘命中"，命中率上不去就是白花钱。排查命中率从三层看：第一层看缓存键，URL 里带 `?v=123` 这类参数如果默认参与 cache key，同一文件每种参数都算一个新对象，命中率必然被"打碎"——对策是把 query 里非关键的参数从缓存键里去掉（忽略参数），或者干脆劝前端用路径版本号而不是 query 版本号；第二层看缓存规则，确认没有把静态资源目录误配成不缓存，并确认响应头 `Cache-Control`/`Expires` 没被源站覆盖掉 CDN 的 TTL 设置——源站返回 `Cache-Control: no-cache` 时 CDN 再长 TTL 也白搭；第三层看刷新/预热，发版后如果既不改名也不刷新，用户拿到的是 30 天前的老文件。正确组合拳是：静态资源走"hash 文件名 + 长 TTL"（内容变了文件名就变，天然绕过缓存，基本不需要刷新操作），HTML 走短 TTL 或强制回源保证新版本秒级可见。回源侧注意两点：源站是 OSS 的话配回源鉴权（Referer/签名）防止 CDN 节点被当公开代理、源站被刷；源站是 ECS 的话回源带宽是隐藏瓶颈，边缘全漏回源时会把服务器网卡打满。动态加速要冷静：纯 API 动态请求走 CDN 是负优化（多一跳边缘回源），只有对跨地域 App 场景（弱网、长链路）才值得上动态加速产品，它做的是路由选路和 TCP 优化，且按流量计费明显偏贵，先想清楚是否真的有异地用户再说。

**延伸考点：** 缓存命中率与源站压力的关系：如何用命中率反推回源带宽，并设计"CDN 峰值 - 回源带宽"的容量告警？

### Q7. 机房和云要打通，专线和 IPSec VPN 到底选哪个，怎么做到可靠？

**问题：** 你们公司 IDC 机房有一套核心业务系统，云上跑着新业务，两边数据库需要实时同步、应用需要互相调用。网络团队提了两个方案：拉一条物理专线，或者用公网建 IPSec VPN。你会怎么评估两者，带宽、可靠性、成本和冗余怎么设计？

**期望加分项：**
- 对比维度完整：专线走物理链路（低延迟、稳定、独占带宽、不受公网抖动影响、支持大带宽 1G/10G/100G），IPSec VPN 走公网（便宜、开通快、带宽共享、受公网质量影响），核心业务选专线、备份/测试链路用 VPN
- 有量化依据：说清专线接入点（POP）、物理距离对延迟的影响、专线 MTU/分段问题；VPN 的性能受 CPU 加解密与公网抖动影响，带宽上限与丢包关系
- 冗余设计达标：专线至少"双线双路由"（不同物理路径/不同运营商/主备或负载分担），VPN 作为专线故障时的逃生通道；BGP 双活或多活、路由优先级（专线优先、VPN 兜底）与自动切换
- 讲清路由与 NAT 细节：云侧专线网关（VBR）与 VPC 路由、IDC 侧 BGP 会话、对端路由通告（避免环路）、本端/对端网段不重叠
- 有验收与运维手段：专线施工周期与成本（月租 + 端口费 + 带宽费，起步贵）、SLA 指标（可用性 99.9%+）、链路质量监控（ping/mtr 基线）与告警
- 提到安全合规：专线数据不经过公网、满足金融合规；VPN 需加 IPsec 安全策略、IKE 生命周期管理

**减分项：**
- 一句"都行"或"专线一定最好"，没有成本/时效/场景权衡
- 只谈单条链路，没有冗余设计，专线一断业务全挂
- 不知道专线通了还要配路由、BGP、MTU，以为物理通就完事
- 忽略网段冲突：IDC 与 VPC 网段重叠，路由直接黑洞
- 没有验收基线，链路质量恶化两周都没发现

**解答：**

选择的核心不是"哪个好"而是"核心链路与非核心链路分开建"。专线适合承载数据库同步、核心应用调用这类低延迟、高稳定的流量：物理链路时延可预期（同一城市通常 1-3ms 级别）、带宽独占、不受公网拥塞影响，还满足金融监管对数据通道的要求；代价是开通周期长（从申请到调通一般 2-4 周）、起步费用高（端口费 + 带宽费，且按带宽阶梯计价）。IPSec VPN 走公网，优势是半小时开通、按需付费，缺点是公网抖动直接反映到业务上，且 VPN 网关性能受加解密能力限制，大流量下 CPU 打满丢包。工程上几乎都是"专线为主 + VPN 兜底"的混合组网：专线跑主流量，VPN 保持常开作为逃生通道；路由层面用 BGP 通告优先级（专线路由 MED/本地优先级高），专线故障自动切到 VPN，恢复后回切——这里要反复验证回切不震荡。细节坑比链路本身多：①两端口网段必须规划不重叠（IDC 用 172.16.0.0/16、云上 VPC 用 10.1.0.0/16），否则路由冲突流量黑洞；②专线 MTU 1500 或 9000（巨型帧）要与对端协商一致，不一致会导致"大包通、小包通、中间大小包丢"的诡异问题；③上线前用 iperf3 跑双向带宽验收、用 ping/mtr 记录 24h 基线，之后按基线告警——我见过专线光衰恶化导致丢包率从 0.01% 爬到 2% 而业务毫无感知的案例，直到数据库同步延迟报警才被发现。

**延伸考点：** 专线故障自动切换 VPN 的瞬间，已建立的 TCP 连接会怎样？如何设计应用层重连与数据库同步的断点续传？

### Q8. 多套 VPC 之间要互相调用，对等连接、云企业网（CEN）怎么选？

**问题：** 你们有生产、测试、安全隔离的数据交换区三套 VPC，未来还要在华东、华北各建一套 VPC 做多地域部署。现在要求各 VPC 之间能内网互通，有人提议"直接全两两建对等连接"。你会怎么设计跨 VPC 互联，对等连接和云企业网（CEN/Transit Gateway）各自的适用边界与成本怎么权衡？

**期望加分项：**
- 讲清对等连接（VPC Peering）：点对点、无中转、不支持传递（A-B、B-C 不自动带出 A-C）、同账号同地域通常免费或低成本，适合少量 VPC 简单互通
- 讲清云企业网（CEN/Transit Gateway）：中心化枢纽、支持跨地域、支持 VPC-VBR-VPN 一体化接入、路由自动学习与收敛，适合多 VPC/多地域/混合云复杂拓扑
- 有规模化判断：VPC 数量从 3 增长到 10，对等连接是 O(n²) 的配置爆炸（10 个 VPC 需要 45 条对等），CEN 是 O(n) 的星型接入，且有配额上限（一个 VPC 对等数量有限）
- 能讲路由细节：对等连接要双向配路由表条目，CEN 路由自动下发但要注意路由冲突（重叠网段 CEN 会拒绝或取最长前缀匹配）；跨地域互访数据要过 CEN 的跨地域带宽包（按地域对与带宽计费，贵）
- 有安全与隔离意识：数据交换区 VPC 通过 CEN 只放开必要路由（分段路由、安全组/NACL 收口），或通过云防火墙做东西向审计
- 提到混合云扩展：VPC 通过 VBR/专线、VPN 接入 CEN，一套 CEN 把云上云下全打通，相比对等连接只能连 VPC 更完整

**减分项：**
- 不知道对等连接不支持传递性，B-C 通不了才发现没配
- VPC 一多还坚持两两对等，配置与排查成本爆炸
- 不清楚跨地域走 CEN 要买带宽包，账单爆了才问
- 重叠网段直接接进 CEN，路由冲突全网踩雷
- 没有互联后的安全收口，数据交换区 VPC 被当跳板横向渗透

**解答：**

先给结论：同地域、两三个 VPC、单向明确依赖，用对等连接；VPC 数量会涨、要跨地域、要接专线/VPN，直接上云企业网（CEN）。对等连接的本质是"两个 VPC 之间打一条直连"，它有三个硬约束：点对点（A 连 B 不能顺带连 C）、无传递性（A-B、B-C 通了但 A-C 不通，必须再建一对）、路由靠手动双向添加。VPC 数量到 5 个以上，两两互连的配置量是 O(n²)，10 个 VPC 要 45 对，而且单 VPC 的对等数量还有配额上限，所以"全两两对等"只在 2-3 套 VPC 时成立。CEN 则是中心化枢纽：所有 VPC 各用一条连接挂进 CEN，路由由 CEN 自动学习下发，新增一套 VPC 只加一条连接即可；更重要的是它能挂 VBR（专线网关）和 VPN 网关，把 IDC 也纳进来，云上云下一个平面，这就是"云企业网"名字的由来。工程上的坑：①路由冲突——如果两个 VPC 用了重叠网段，CEN 可能拒绝下发或只按最长前缀匹配，规划时跨 VPC 网段要全局唯一（这也是 Q1 网段规划重要性的延续）；②跨地域流量要单独买带宽包（华东↔华北按带宽包计费），跨地域传输的流量成本可能比同地域贵一个数量级，别等账单爆炸；③互联不等于开放——接入 CEN 后默认全互通，数据交换区 VPC 要单独收敛：只下发必要路由 + 安全组/云防火墙做东西向管控，否则一个 VPC 被攻破，CEN 就是横向扩散的高速路。

**延伸考点：** CEN/Transit Gateway 里"重复网段 VPC 如何接入"（改网段 / NAT / 分段路由）？三种方案各付出什么代价？

### Q9. 微服务多了，内网 IP 谁记谁查？内网 DNS（PrivateZone）怎么落地服务发现？

**问题：** 你们的微服务从 20 个涨到 80 个，配置中心里全是"http://10.1.3.25:8080"这种硬编码地址，扩容换 IP 后总要改配置。运维想引入云 PrivateZone（阿里云 PrivateZone / AWS Route 53 Private Hosted Zone）做内网域名解析。你会怎么设计域名规范、解析体系，并和注册中心（Nacos/Eureka）的服务发现划清边界？

**期望加分项：**
- 讲清内网 DNS 的价值：给内网服务一个稳定域名（如 `order.svc.internal`），IP 变更只改解析不动配置，配合云产品联动（SLB 内网域名、RDS 内网地址）
- 有域名规范：层级清晰，如 `{app}.{env}.internal`，或阿里云私有域名 `{app}.local`，区分测试/生产（`dev.order.internal` vs `prod.order.internal`），禁止用裸 IP 和下划线主机名
- 讲清与注册中心的分工：注册中心做进程级动态发现（实例上下线、多副本负载均衡，秒级感知），内网 DNS 做"稳定的服务入口别名"，两者不是替代关系——注册中心适合 RPC 直连，PrivateZone 适合"基础设施地址 + 外部系统引用"
- 有缓存与变更意识：内网 DNS 记录变更的 TTL 生效问题（改解析后存量实例缓存多久）、实例侧 nscd/systemd-resolved 缓存、扩缩容 IP 复用导致的解析脏缓存
- 提到联动场景：PrivateZone 与 VPC 绑定、自动解析云产品内网域名（RDS/OSS 的私网地址）、跨 VPC 共享解析（阿里云 PrivateZone 支持跨 VPC 关联）
- 有排障手段：`dig @100.100.2.136`（阿里云 PrivateZone 默认 DNS IP）、`nslookup` 对比公共/内网解析、查看是否走了公网解析导致内网域名被解析到公网 IP

**减分项：**
- 让注册中心干 DNS 的活，或反过来让 DNS 干注册中心的活，边界说不清
- 没有域名规范，`10.1.3.25:8080` 改成 `order-service:8080` 就算完事
- 不知道内网 DNS 有缓存 TTL，改完解析业务还是连老 IP
- 不知道云产品联动，RDS/OSS 的私网域名、跨 VPC 解析能力一个都说不出来
- 排障时只会 ping，说不清 `dig` 该查哪个 DNS 服务器

**解答：**

先划边界，这是这道题的分水岭：注册中心（Nacos/Eureka/Consul）解决的是"运行时的服务实例发现"——服务有 10 个副本、哪个挂了、哪个新上，靠心跳和注册表在秒级感知，供 RPC 客户端做负载均衡与摘除；内网 DNS 解决的是"稳定的逻辑地址"——一个服务对外永远有一个域名，IP 换了不用通知任何调用方。真实架构里两者共存：内部 RPC 走注册中心直连，对外提供 HTTP 接口或被其他系统（老系统、外部协作方、运维脚本）引用时，暴露内网域名。落地内网 DNS 的关键是域名规范，我用的规范是 `{app}.{env}.internal`：`prod-order.internal`、`dev-order.internal` 一眼可读，环境隔离天然成立；解析指向优先用内网 SLB 域名或固定 VIP，而不是直接指实例 IP（实例 IP 会因扩缩容漂移）。配置上：PrivateZone 要绑定 VPC，云产品（RDS、Redis、OSS）的内网地址会自动生成私网域名，应用配置里全部换成域名。变更的坑是缓存：内网 DNS 记录改了，但实例上 nscd/systemd-resolved 的缓存和业务连接池还捏着老 IP——所以"改解析"不等于"立即生效"，要么提前降 TTL，要么改完后主动刷新实例缓存，我见过扩容时 IP 被复用，旧实例缓存指向新实例导致请求打到错误节点的案例。排障时在实例上 `dig @100.100.2.136` 直接问内网 DNS，对比 `/etc/resolv.conf` 的 nameserver 是否配了内网 DNS——很多人没把实例 DNS 指向 PrivateZone，内网域名请求被转发到公网解析，自然解析不到。

**延伸考点：** 如果内网 DNS 挂了，服务间调用全断吗？如何设计"DNS 不可用时的降级"（连接池保活、本地 hosts、注册中心兜底）？

### Q10. 用户反馈"时快时慢偶尔超时"，用 ping、traceroute、mtr 怎么定位丢包？

**问题：** 有客户反馈访问你们公有云上的服务"时快时慢，偶尔直接超时"，你们自己测没复现。你会用哪些工具、按什么顺序从云上网络的角度排查，ping、traceroute、mtr 各自能回答什么问题，云上抓包又该怎么抓？

**期望加分项：**
- 工具分工明确：ping 验证"通不通、延迟多高"（但被限速/禁 ICMP 时不代表业务不通），traceroute 看"路径走哪、哪一跳有问题"（注意中间节点不响应不等于丢包），mtr 结合两者做持续统计（丢包率/抖动按跳分布，是丢包定位的第一工具）
- 排障顺序有章法：先客户端→云上入口分段 ping（客户端→SLB EIP→后端 ECS），再 mtr 定位丢包跳，最后按"丢包在边界内还是边界外"判断责任
- 有基线概念：丢包率 0.01% 与 2% 对业务的体感完全不同，建立历史基线（如 24h 内 ping 延迟 p50/p99）才能判断"现在是否异常"
- 讲清 traceroute 的误读：公网中间路由器 ICMP 限速/不响应是常态，不能凭"某一跳 * * *"就断言故障；要看持续丢包且下游全丢才是真断点
- 云上抓包有方案：VPC Flow Logs 看流量的允许/拒绝与字节数，丢包不一定发生在云内；实例上用 tcpdump 抓 SYN/重传（`tcpdump -i eth0 tcp port 8080`），分析重传率与 RTO 分布
- 能区分丢包类型：物理链路丢包（光衰、端口错包）、带宽打满丢包（入方向带宽用尽，出方向限速丢包）、安全策略丢包（安全组/NACL 丢弃）

**减分项：**
- 只会 ping，而且"ping 通 = 网络没问题"的粗暴结论
- 把 traceroute 中间节点的 * 当成故障，直接甩锅给运营商
- 不知道 mtr，或不会读 mtr 输出（哪一跳是源头、哪一跳是叠加）
- 没基线意识，网络质量恶化几天都无感
- 不会用 Flow Logs/抓包区分"丢在哪一层"，只会重启

**解答：**

排查顺序按"分段 + 定责"推进。第一步分段验证：从用户侧到 SLB EIP 连续 ping 200 个包记录延迟分布，再从后端 ECS 上 ping SLB 内网 IP、ping 对端业务 IP，把"用户到云边界"和"云内部"切成两段——如果用户侧丢包但云内全绿，问题在公网/运营商段。第二步用 mtr 定位：mtr 同时做 ping+traceroute 的持续统计，重点看两个指标——哪一跳开始出现持续丢包、丢包是否"传导"（某一跳丢 30% 且之后所有跳都丢 30%，丢包源头就在这一跳；只有某一跳丢但后面恢复，多半是那一跳限速 ICMP，不是真故障）。第三步定责：丢包在"客户到云边界"之间，通常是运营商链路或客户侧出口带宽打满，让客户换线路测试（切 4G 对比）辅助定位；丢包在云内，用 VPC Flow Logs 看连接是被 ACCEPT 还是 REJECT，再看实例的入方向带宽监控是否打满——云上最常见的假丢包是"带宽用满"：入方向带宽打满后，丢的是新连接和突发流量，业务体感就是"时快时慢"。最后是抓包实证：实例上 `tcpdump -i eth0 'tcp[tcpflags] & (tcp-syn|tcp-ack) != 0 and port 8080' -w cap.pcap` 抓握手与重传，统计 SYN 重传次数和 RTO，如果 SYN 重传频繁但服务端日志无连接，说明报文没到或响应没回来。一句话总结：ping 看通断、mtr 看路径、Flow Logs 看策略、tcpdump 看证据，四件套配合基线数据，没有定不了的丢包。

**延伸考点：** mtr 输出里"中间一跳丢包但后续跳正常"和"某跳开始全链路丢包"分别怎么解读？云厂商和运营商互相甩锅时你怎么用数据说话？

### Q11. 线上被 DDoS 打了，WAF、云防火墙、DDoS 高防各干什么、怎么协同？

**问题：** 你们网站某天突然收到阿里云 DDoS 防护的告警：清洗后仍有部分用户超时，安全团队同时发现应用层有大量恶意请求（刷接口、撞库），运维排查时又看到内网有实例在对外扫描。你会怎么组织 DDoS 防护、WAF、云防火墙三层防线，它们分别挡什么、怎么联动、告警怎么定级？

**期望加分项：**
- 分层讲清分工：DDoS 防护挡"流量型攻击"（SYN Flood/UDP Flood/CC 的带宽与连接层，DDoS 高防/IP 高防 + 清洗中心），WAF 挡"应用层攻击"（SQL 注入/XSS/恶意爬虫/刷接口，基于 HTTP 语义），云防火墙挡"东西向与南北向的访问控制"（跨实例横向扫描、非法端口访问、DNS 外联审计）
- 有协同意识：DDoS 防护用 BGP 高防或 DDoS 高防 IP 把入口流量引到清洗中心，清洗后回源；WAF 挂在七层 SLB 前（DNS 切 CNAME 或 SLB 前置 WAF）；云防火墙做全网统一策略与攻击日志留痕
- 防护等级量化：阿里云 DDoS 防护的"全力防护/增强"等级、防护能力（如最高 300Gbps+）、CC 防护阈值、清洗规则（IP 黑名单、限速）；紧急时切 DNS 到高防 IP
- 有业务影响评估：DDoS 清洗可能误杀正常业务（如高防限流后的错误 502）、WAF 规则太严误拦正常请求，上线前要灰度放量与规则调优
- 有监测与联动：告警分三级（带宽超阈值、清洗开始、回源失败），DDoS 高防、WAF 告警联动 SLB 健康检查；被攻击时先保业务（切高防、封源站）再取证
- 提到攻击成本意识：流量型攻击靠带宽打，防护要买够"抗 D 能力"，而不是事后再救；无防护裸奔的公网入口是事故定时炸弹

**减分项：**
- 三层产品一个都说不清分工，混为一谈"反正都是防火墙"
- 不知道被攻击时"先保业务再排查"的次序，先开 console 慢慢查
- 没有攻击告警分级与演练，真被打时一片混乱
- 不知道 WAF 误杀、DDoS 清洗误伤业务的可能性
- 不做日常东西向管控，内网被横向渗透后全 VPC 沦陷

**解答：**

按攻击面把三层防线摆正位置：DDoS 防护在"最外层带宽"上挡流量洪水，WAF 在"应用层"上挡业务逻辑攻击，云防火墙在"网络层"上做访问控制与审计——三者不是替代关系，而是"外面挡洪水、中间挡应用攻击、里面做管控留痕"的纵深。具体落法：公网入口买 DDoS 高防（高防 IP 或 BGP 高防），DNS 把业务域名 CNAME 到高防，流量先过清洗中心（过滤 SYN Flood、UDP Flood、反射放大攻击，阿里云单实例防护能力可达几百 Gbps），清洗后回源到 SLB；WAF 挂在七层 SLB 前面（阿里云 Web 应用防火墙做 CNAME 接入或透明接入），专职拦 SQL 注入、XSS、恶意爬虫、撞库/刷接口——注意 WAF 规则别一上来全开"严格模式"，线上见过 WAF 把正常分页请求当扫描拦掉的事故，要灰度放量；云防火墙（阿里云云防火墙）管南北向和东西向：全网统一访问控制策略、阻断内网实例外联可疑 IP（挖矿/扫描）、审计跨实例流量，攻击进来后留下的东西向横向移动路径全靠它兜底。被攻击时的动作序列要固化：①确认 DDoS 告警等级，带宽接近高防容量上限立即联系云厂商升级清洗/换更高级别防护；②若高防被打穿或回源 IP 泄露被直打，先把源站 ECS 的 EIP 摘掉或切换源站 IP，别让攻击直达源站；③WAF 侧开人机验证/限速规则压 CC，同时准备降级页（排队页）保核心下单链路；④事后从高防/CFW/WAF 三份日志对攻击源、攻击特征、被撞的接口做复盘。日常就要做攻击演练（模拟 CC、SYN Flood），因为真被打的 20 分钟里根本没时间看文档。

**延伸考点：** 攻击回源 IP 泄露（通过 DNS 历史记录、证书透明日志）导致源站被打，如何设计"源站不可见"的架构（高防 + 回源白名单 + 隐藏源 IP）？

### Q12. 一台服务器要跑多个隔离业务、还要热迁移 IP，弹性网卡和多 IP 怎么用？

**问题：** 你们有一台高配 ECS 要同时承载三个相互隔离的业务（每个业务有自己的安全组和带宽诉求），并且其中一个业务要迁移到新实例但不允许对外 IP 变化。你会怎么用辅助弹性网卡（ENI）和多 IP 解决，普通实例内网 IP 和辅助网卡 IP 的适用边界在哪？

**期望加分项：**
- 讲清弹性网卡（ENI）的价值：一块独立资源可挂载/解绑，随实例绑定多块网卡后每个业务一张卡，各自配安全组、独立流量统计与带宽控制，网卡随迁保证 IP 不变
- 场景落地：多业务隔离用"一卡一业务"（每张网卡独立安全组），IP 迁移用"解绑再绑"（辅助网卡从旧实例解绑挂到新实例，私网 IP 不变，业务无感）；私有 IP 从主网卡解绑到辅助网卡实现单 IP 迁移
- 讲清 IP 类型：主私网 IP（实例生命周期内默认不变，但删实例即释放）、辅助私网 IP（可在实例间迁移）、弹性公网 IP（独立于实例，可绑定到任意网卡/实例）
- 有系统侧配置知识：Linux 多网卡要配路由策略（策略路由，按网卡分流）否则默认路由只走主网卡，Windows 多网卡需要关掉弱主机（weak host）行为；多网卡跨子网要配网关
- 知道配额与坑：单实例网卡数上限（按规格，如 g 系列 8 张）、每网卡辅助 IP 数上限（如 20 个）、网卡不能跨 VPC 挂载、迁移时目标实例规格要支持同数量网卡
- 有高可用意识：网卡解绑前确认没有流量在跑（优雅摘流量），SLB 后端用网卡实例 ID 而非 IP 以免迁移后引用失效

**减分项：**
- 不知道辅助网卡能"带着 IP 跨实例迁移"，只会删了重配
- 多网卡挂了但系统里不配策略路由，流量全走主网卡，多卡形同虚设
- 分不清主私网 IP、辅助 IP、EIP 的迁移能力差异
- 不知道单实例网卡/辅助 IP 有配额，规划时没算
- 迁移时直接拔卡导致在线连接全断，没有优雅摘流量

**解答：**

先分清楚三类 IP 的"迁移性"：主私网 IP 随实例生命周期，实例删了就没；辅助私网 IP 和辅助网卡是独立资源，可以在实例之间迁移；EIP 更灵活，绑到谁就跟着谁。所以"业务迁移但 IP 不变"的标准做法是辅助网卡方案：把业务网卡（连同其私网 IP 和安全组）从旧实例解绑，挂到新实例上，IP 完全不变，调用方零感知——这是云上做"换机器不换地址"的核心手段，数据库从单机迁到主备、老应用迁到新规格实例都靠它。多业务隔离场景：高配 ECS 挂 3 张辅助网卡，每张网卡对应一个业务，各自绑定独立安全组（A 业务网卡只放 8080、B 业务网卡只放 9090），流量和带宽还能按网卡分开监控与限速，互不干扰。这里最大的坑在操作系统侧：Linux 默认只配主网卡的默认路由，辅助网卡挂上后不通——要写策略路由（`ip rule` 按源地址分流 + 多路由表），否则辅助网卡上的流量都会从主网卡出去，既不通也乱；Windows 侧要关闭弱主机接收（weak host receive），否则辅助网卡收不到包。另一个坑是配额：单实例网卡数量、每网卡辅助 IP 数都按实例规格有硬上限，规划前先查规格表，别把 8 卡规格的实例规划出 12 张卡。迁移流程要优雅：先在 SLB/接入侧把该实例摘流量（权重调 0）等存量连接发完，再解绑网卡、挂到新实例，最后恢复权重——直接硬拔网卡会让在线连接全部中断，这是"迁移事故"最常见的翻车点。

**延伸考点：** 辅助网卡解绑再挂载时，已建立的 TCP 长连接（如数据库连接池）会怎样？如何与 SLB 摘流量、应用重连机制配合做到业务无感？

### Q13. 云上网络账单每个月都在涨，流量费、带宽费怎么算、怎么优化？

**问题：** 你们上云后发现网络费用占了云账单的大头：公网出方向流量、跨地域 CEN 流量、对象存储回源流量都在花钱。你怎么讲清云网络"流量计费 vs 带宽计费"两种模式，并给出可落地的成本优化清单？

**期望加分项：**
- 讲清计费模式差异：按固定带宽（峰值上限、包月/包年，适合稳定业务）vs 按流量（按出方向 GB 计费、适合弹性突发），同一地域内网流量免费、公网入方向免费、出方向收费，跨地域/跨 AZ 流量收费
- 有量化账本：给出例子，如固定带宽 100Mbps 包月 vs 按流量 0.8 元/GB（阿里云大陆按流量单价约 0.8 元/GB，需按带宽利用率算盈亏平衡点），利用率高选带宽包、利用率低选流量
- 优化手段成体系：①静态资源全部走 CDN（边缘出流量远低于源站直出）+ OSS 回源流量用 CDN 回源走内网/回源优惠；②跨地域业务改为同地域部署或把频繁互访的组件拉近；③出方向流量压缩/减量（gzip、图片压缩、协议优化）；④NAT/公网入口收敛（SNAT 共享出方向流量）；⑤用流量分析报表（云监控、成本分析）找出"流量大户"和低效外联
- 提到隐藏成本点：跨 AZ 流量（可用区之间流量计费）、CEN 跨地域带宽包、LB 本身规格费 + 流量费、备份/日志同步的公网流量（应改内网/专线）
- 有成本治理机制：网络费用按月环比告警、按业务打标签（Tag）分摊成本、异常流量飙升（被刷、被攻击、爬虫拖数据）时先查流量来源
- 知道省钱杠杆：峰值平滑（错峰）、利用免费额度（每自然月免费公网流量额度）、长期使用转预付费

**减分项：**
- 不知道"公网入方向免费、出方向收费"，账单方向都搞不清
- 只会说"换成流量计费"或"换成带宽计费"，没有盈亏平衡点计算
- 不区分跨地域/跨 AZ 流量收费，架构拉远后默默买单
- 静态资源直连源站，CDN/OSS 回源省钱路径一条都说不出来
- 没有成本监控与分摊机制，账单暴涨后才知道

**解答：**

云网络计费先记三条"铁律"：同地域内网互通免费、公网入方向免费、公网出方向和跨地域/跨 AZ 流量收费——所以成本问题的本质是"把流量尽量留在内网、把出方向流量尽量压小"。计费模式选择：固定带宽适合"带宽长期稳定跑满"的业务（如视频点播源站、稳定 API），按流量适合突发型业务（活动页、下载站）。量化判断：阿里云大陆按流量约 0.8 元/GB，100Mbps 带宽跑满一个月约 32TB，折合约 2.5 万元，而 100Mbps 包月带宽远低于这个数——所以月均利用率高的买带宽包，利用率低（如日均几十 GB）的按流量。优化清单按收益排序：①静态资源全部上 CDN，边缘出流量单价远低于源站公网直出，且 CDN 回源 OSS 走内网或享受回源流量优惠——一次配置长期省钱，同时把源站带宽从 500Mbps 砍到 20Mbps 的例子很常见；②架构上把"高频互访的组件"拉到同一地域甚至同一 AZ，别让缓存服务跨地域读取（一次缓存回源跨地域的流量费可能比计算费还高）；③应用层减量：gzip/brotli 压缩、图片 WebP、API 响应裁剪，出方向字节数直接决定流量费；④出方向收敛：下载类走对象存储直传而非经应用服务器转发（服务器转发 = 流量费 × 2），日志同步走内网/专线。治理机制上：给资源打业务 Tag 做成本分摊，按月对"公网出方向流量、CEN 跨地域、跨 AZ 流量"三张报表环比告警——我见过一次"爬虫拖全站数据"导致 CDN/出方向流量账单 10 倍飙升的案例，因为没设流量突增告警，第二个月对账才发现。

**延伸考点：** 大促前怎么评估"带宽峰值"成本？临时扩容带宽、CDN 预热、流量降级三种手段的成本曲线怎么画？

### Q14. 网络要扛"机房级故障"，双线路、多 AZ 的网络高可用怎么设计？

**问题：** 你们的核心系统要求"机房故障不丢可用性"，云厂商也承诺了 AZ 级可用性。但纯靠多部署实例还不够，网络链路本身也要高可用。你会怎么设计"入口层（DNS/公网）、接入层（LB/公网 IP）、转发层（VPC 内部链路）、出向层（NAT/专线）"四个层面的网络高可用？

**期望加分项：**
- 有全链路视角：网络高可用不是单点产品，而是 DNS（多线路解析/健康检查切换）→ 公网入口（多 AZ 多 EIP + 高防）→ LB（多 AZ 实例 + 后端跨 AZ）→ 内部链路（多 AZ 子网、跨 AZ 路由）→ 出方向（NAT 多可用区、专线双线）每一层都不能有单点
- 量化 SLA 与成本：单可用区网络故障概率 vs 双 AZ 的可用性提升，说明"网络层双活"比"计算层多副本"更难（流量需要可迁移），跨 AZ 流量费是成本
- 具体机制讲清：DNS 健康检查联动智能解析（某个 LB 挂了自动切解析）、LB 多可用区（主备可用区/多可用区实例）、后端 ECS 跨 AZ 部署 + 安全组不绑死单个 AZ、NAT 网关多可用区、专线双物理路由 + BGP 双活
- 故障切换有演练：混沌演练定期模拟"断一条专线/挂一个 AZ 的 LB"，验证 RTO（如 <5 分钟）与 RPO，记录切换动作清单
- 有降级设计：核心链路故障时先降级（静态页、限流、只读）保核心功能，网络高可用永远与成本/复杂度平衡
- 提到区域边界：单地域多 AZ 扛不住地域级故障（地震、大规模断网），真正的多活要跨地域 + DNS 就近解析，成本再上一个量级

**减分项：**
- 只谈"多部署几个实例"，网络入口/出口链路全是单点
- 不知道 DNS 解析也要参与故障切换（LB 挂了解析还指向老地址）
- 跨 AZ 部署了但网络链路没打通/没验证，故障演练才暴露
- 高可用方案只写在 PPT 里，没有切换演练与 RTO 验证
- 没有降级方案，把高可用赌在"永不故障"上

**解答：**

网络高可用是"每层都别留单点"的工程：用户访问链条上任何一个单点（单 EIP、单 LB 实例、单 NAT、单条专线）都可能成为故障引爆点。分层设计如下：①DNS 层：用云解析的智能解析 + 健康检查，配置多条 A 记录指向不同可用区的 LB 地址，某个 LB 健康检查失败自动摘除解析（阿里云云解析支持故障转移）；②公网入口：至少两个可用区各挂 EIP/高防，避免"一个可用区挂掉整个入口没了"；③接入层：SLB 选择多可用区部署，后端服务器组跨 AZ 分布，同一服务在两个 AZ 各 2 台，健康检查自动摘除故障 AZ 的实例；④内部链路：VPC 内跨 AZ 走云上骨干网，天然冗余，但要确认子网在每个 AZ 都有（Q1 的规划就为此铺路）；⑤出方向：NAT 网关开多可用区（阿里云 NAT 网关支持主备可用区），专线走双物理路由（两个接入点）配 BGP 双活，VPN 兜底。比设计更重要的是验证：至少每季度做一次故障演练——模拟"断专线 A"，观察 BGP 是否 30 秒内收敛、业务连接是否按预期切换、RTO 是否达标（比如 5 分钟内恢复入口）；模拟"挂掉一个可用区的 LB"，看 DNS 健康检查是否自动切换。我见过最典型的翻车：双 AZ 部署了，但 SLB 只建在一个可用区、另一个可用区的后端实例根本没接入，演练时才发现"双 AZ"只是计算层双 AZ、网络层还是单点。最后记住：高可用是有成本的（跨 AZ 流量费、双专线月租），要先定"可用性目标（SLA 99.95%？RTO？）"再倒推该建几层冗余，永远给核心链路加"降级开关"（限流、只读、静态页）。

**延伸考点：** 如果某 AZ 的 LB 实例故障但 DNS 切走用户了，已建立的长连接（WebSocket）会怎样？应用层如何设计"连接重建"才能让用户无感？

### Q15. 网络出问题总是后知后觉，监控网络该盯哪些指标、怎么配告警？

**问题：** 你们之前线上发生过"带宽被打满 2 小时才发现""跨地域链路丢包一周没人知道"的教训。现在要做一套云网络监控体系。你会盯哪些指标（流量、连接数、丢包、端口）、用什么工具（云监控、Flow Logs、自定义探针）、告警阈值和降噪怎么做，以及如何定位瓶颈？

**期望加分项：**
- 指标分层完整：入口/出口带宽（利用率 %，区分出/入）、SLB 的 QPS/新建连接/活跃连接/健康检查失败数、NAT 的并发连接与 SNAT 端口使用率、实例网卡的丢包率/错包率、跨地域链路 RTT/丢包、DNS 解析成功率与延迟、TCP 重传率
- 告警有量化阈值与级别：带宽 > 70% 预警 / > 90% 告警（留出突发余量）、健康检查连续 3 次失败告警、SNAT 端口使用率 > 80% 预警、丢包率 > 0.5% 且持续 5 分钟告警、RTT 相对基线 p99 翻倍告警——阈值要基于基线而非拍脑袋
- 工具组合：云监控（指标 + 告警）、VPC Flow Logs（流量明细：源/目的 IP、端口、字节数、允许/拒绝，做异常流量与安全审计）、Prometheus 自采网络指标（node_exporter 的 netstat 指标、tcp_retrans 等）、主动探针（跨地域/跨云 synthetic 探测）
- 有瓶颈定位方法：带宽打满时用 Flow Logs 聚合出"流量 Top 对话"（谁在占带宽）、TCP 重传率高用抓包定位重传源、连接数打满看 TIME_WAIT/ESTABLISHED 分布
- 告警降噪：聚合（同一告警源聚合）、抑制（已知变更窗口抑制）、分级路由（P1 短信电话 / P2 群消息）、告警有效期（避免告警风暴）
- 有 SLA 意识：核心链路配置"端到端探测"（拨测）比单点指标更能反映用户体感，DNS/CDN/LB 全链路拨测兜底

**减分项：**
- 只监控 CPU/内存，网络指标一条都不看
- 阈值拍脑袋（带宽 100% 才告警，等于不告警），或没有基线
- 告警只设不降噪，告警风暴后全部被忽略（狼来了效应）
- 看不到"谁在占带宽/连接"，只有总量没明细
- 没有主动探测，用户报障才知道网络有问题

**解答：**

监控体系按"资源指标 + 流量明细 + 主动探测"三层搭。第一层资源指标（云监控 + node_exporter）：公网带宽利用率（入/出分开盯，出方向更贵也更容易被打满）、SLB 活跃连接与健康检查失败数、NAT 并发连接与 SNAT 端口使用率、实例网卡丢包/错包、TCP 重传率——这些都是"会先于业务告警出现"的先行指标。第二层流量明细（VPC Flow Logs）：把日志推送到日志服务（SLS）或 S3，按"源 IP、目的 IP、端口、字节数、accept/reject"聚合，瓶颈定位全靠它——带宽告警时跑一条"按目的 IP 聚合出流量 Top10"的查询，立刻知道是哪个实例在把带宽吃满（常见答案：日志同步、备份任务、被爬虫拖数据）；安全组/NACL 误拒时看 reject 明细。第三层主动探测：跨地域/跨云链路用拨测（synthetic monitoring）每 30 秒发一次 HTTP/TCP 探测，DNS 解析、CDN 命中、全链路延迟都在用户视角下监测——单点指标都绿但用户体验差，往往要靠拨测暴露。告警配置的关键是"基线化 + 分级 + 降噪"：先用 2-4 周跑出各指标的基线（如带宽峰值 p95、RTT p99），阈值按"基线 + 余量"设：带宽利用率 70% 预警、90% 告警；丢包率 0.5% 持续 5 分钟告警；SNAT 端口使用率 80% 预警。分级：P1（入口不可用、SLB 摘流量）短信+电话，P2（带宽逼近阈值、重传率升高）群消息；变更窗口内告警自动抑制，同一原因告警聚合为一条。最后补一句：告警动作必须有人认领，否则就是"狼来了"——每条 P1 告警都要有对应的应急预案（切 DNS、扩带宽、摘节点）。

**延伸考点：** 告警风暴怎么防？大促压测期间如何临时调整监控策略，既不失真又不被海量告警淹没？

### Q16. 海外用户访问又慢又丢包，全球加速（GA）和就近接入到底解决什么？

**问题：** 你们 App 上线海外市场，东南亚用户反馈首屏加载要 5 秒以上、视频播放卡顿，而你们服务部署在华东。网络团队提议上全球加速（阿里云 GA / AWS Global Accelerator）。你会怎么评估这个方案：它和 CDN 的区别、加速原理、成本，以及哪些场景真的需要它？

**期望加分项：**
- 讲清定位：全球加速（GA）是"动态内容 + 公网链路优化"的加速产品，解决的是"跨地域公网链路质量差"（国际链路丢包、抖动、绕路），而 CDN 解决"静态内容就近缓存"——两者解决不同问题，可叠加
- 加速原理讲透：GA 通过 Anycast 把用户流量就近接入边缘 POP，再走云厂商的优质骨干网（专有网络）到源站，避免用户流量直接走"国际公网烂链路"；UDP/TCP 四层加速 + 传输层优化，动态 API 也受益
- 有量化评估方法：上线前后对比（同地区多个探测点、首屏耗时、RTT p50/p99、丢包率），用国际拨测数据算 ROI——如果丢包 > 2%、RTT > 150ms 且对体验敏感，值得上
- 对比其他方案：多地域部署（就近计算，最彻底但成本最高）、CDN（只解决静态）、专线/加速通道（解决公司内部链路）；App 场景往往"GA 接入 + 静态走 CDN"组合
- 有工程细节：GA 的接入 IP（任播 IP 不变）、按带宽/流量计费（贵，约是普通公网流量的数倍）、要评估是否值得全量接入还是仅核心接口
- 提到场景边界：同城/同地域用户不需要 GA（多一跳反而变慢）；GA 对跨地域的"动态 API、长连接、游戏、视频流"价值最大

**减分项：**
- 分不清 GA 和 CDN：静态加速和动态链路优化混为一谈
- 没有量化验证意识，上完 GA 说不清快了多少
- 不知道 GA 按带宽/流量计费很贵，全量接入后成本失控
- 同地域也套 GA，多一跳反而变慢还白花钱
- 不考虑后端也要配合（源站带宽、LB 容量），只优化了入口一段

**解答：**

先分清"静态缓存"和"链路优化"是两件事：CDN 把图片、JS 缓存到离用户近的边缘节点，动态 API、登录态、游戏长连接没法缓存，这类流量跨地域走国际公网就是"慢 + 丢包 + 绕路"的重灾区——全球加速（GA）正是治这个的：用户在东南亚访问，流量先就近进入 GA 的 Anycast POP（新加坡/香港等），然后走云厂商的骨干专网直接到华东源站，绕开国际公网的拥塞段；对客户端而言 GA 只暴露一个任播 IP，不管用户在全球哪里，路由都自动选最优路径。所以判断要不要上的量化口径是：先跑一轮国际拨测（在目标地区用探测点测源站 IP 的 RTT/丢包），如果丢包率超过 1-2%、RTT p99 明显超出体验阈值（首屏 < 3s 对应的 RTT 预算），且业务是动态 API 或长连接，就值得上 GA；如果主要是静态资源慢，先上 CDN 更划算。工程上 GA 的正确用法是"组合拳"：GA 只接入核心动态链路（登录、下单、实时接口），静态资源继续走 CDN，两个产品各管一段；成本上 GA 按带宽/流量计费且单价远高于普通公网流量（量级约数倍），所以要对"哪些接口值得走 GA"做流量分级，全量接入会把成本打爆。踩过的坑：有人把 GA 接到一个带宽只有 50Mbps 的源站，前端链路优化了后端出口又成瓶颈；还有人同地域内网调用也套 GA，多一跳反而多 5ms。结论：GA 是"远端用户体验"的兜底手段，先量化链路质量、再分级接入核心流量，最后用拨测验证 ROI。

**延伸考点：** 全球加速和"多地域部署 + 就近解析"相比，各自适用什么阶段？从成本、运维复杂度、数据一致性三个维度对比。

### Q17. 微服务之间流量越来越大，服务网格（Istio）和云网络怎么分工、怎么协同？

**问题：** 你们微服务规模上来后，团队想上 Istio 做灰度发布和可观测性，但有人担心"服务网格会不会和云上的网络能力（内部 LB、安全组）打架"。服务网格管的东西（Sidecar、虚拟服务）和云网络管的东西（VPC、内部 LB、安全组）边界在哪，两者怎么协同治理东西向流量？

**期望加分项：**
- 分层讲清职责：云网络管"基础设施层"——VPC/子网/内部 LB/安全组决定"流量能不能到、怎么路由"；服务网格管"应用层"——Sidecar 决定"到了之后发给哪个版本、做什么策略（重试/超时/熔断/灰度）"，两者是"南北向 + 东西向"的不同平面
- 有协同场景：网格的入口网关（Ingress Gateway）挂在内部 LB 后面（LB 做 L4 接入与健康检查，网关做 L7 路由）；网格数据面流量经 Sidecar 转发，仍受安全组约束（安全组管"实例层面是否可达"，网格管"应用层面是否放行"）
- 讲清性能与容量关系：Sidecar 每个 pod 一个 Envoy 代理，东西向流量全部经代理会带来额外 CPU/内存开销与延迟（约 1-3ms），网络规划要按"网格放大系数"预留实例资源；大规模网格对 k8s 集群网络（CNI、Pod 网络）有硬要求
- 有治理意识：网格提供 mTLS（服务间加密）与细粒度策略，与云防火墙的东西向审计互补——云防火墙看"网络层访问关系"，网格看"应用层调用链"，两者日志对得上才能查横向移动
- 有实践坑：网格全面接入前先灰度（先接非核心服务）、Sidecar 注入与现有安全组/NACL 策略的兼容性验证、跨集群/跨 VPC 的网格控制面（Istio 多集群）配置复杂度
- 提到可观测性价值：网格的指标（成功率、延迟、重试）天然按"服务对"统计，和云网络监控（带宽、丢包）互补，共同定位"是网络问题还是应用问题"

**减分项：**
- 认为"上了服务网格就不用管网络"或"网格是网络的东西"，边界全无
- 不知道 Sidecar 带来的资源开销与延迟，容量没预留
- 把网格策略（重试/熔断）和网络能力（安全组）混用，责任不清
- 网格 mTLS 和云防火墙日志不打通，安全审计断链
- 一上来全量接入，Sidecar 爆炸式增长后回退困难

**解答：**

先立边界：云网络解决"字节能不能到达、走哪条路"（VPC 路由、内部 LB、安全组/NACL），服务网格解决"到达之后怎么处理"（按版本分流、重试、超时、熔断、mTLS、调用级观测）——一个在数据面的"网络层"，一个在"应用层"，不是替代而是分层叠加。典型协同拓扑：南北向流量进来 → 内部 LB（四层接入，健康检查、高可用）→ Ingress Gateway（七层路由，做 host/path 分发）→ Sidecar → 服务；东西向流量每个 Pod 的流量都经过 Sidecar（Envoy），Sidecar 之间建立 mTLS。注意两点联动：第一，Sidecar 流量照样过安全组——安全组管"实例能不能被访问"，网格管"被访问后策略怎么执行"，配置策略时两层都要考虑，别在网格里开了全放行却忘了安全组挡着（或反过来）；第二，网格和云防火墙的日志要能对上——云防火墙/Flow Logs 给"网络层谁访问谁"的图，网格给"应用层谁调用谁"的图，横向移动攻击排查时两张图叠加才能定位到具体服务和账号。工程上网格的账必须算清：每个 Pod 多一个 Envoy，CPU 约增加 0.1-0.5 核、内存 50-150MB、一跳延迟 1-3ms，大规模集群要按 20-30% 的资源放大系数扩容节点；所以接入策略是"先接 2-3 个非核心服务跑通灰度、巡检、mTLS，再逐步扩大"，切忌全量一把梭——见过网格全量接入后节点资源被打满、回退比接入还难的真实案例。另外多集群网格（跨 VPC 的 Istio 控制面）复杂度很高，优先用"每集群一套网格 + 集群间走云网络"的简化方案。

**延伸考点：** 服务网格的 mTLS 和"云网络安全组"在安全模型中分别承担什么？攻击者拿到一个 Pod 后，两层防护各能挡住什么？

### Q18. 线上"应用偶尔超时"，一次完整的云网络排障全流程怎么走？

**问题：** 你们订单服务最近三天偶发"请求超时"：不是持续故障，而是每分钟零星几个请求要 10 秒以上才返回，业务日志里能看到超时但应用本身无异常，监控也显示 CPU/内存正常。作为网络负责人，你会按什么顺序、用哪些证据完成这次排障，直到定位根因？

**期望加分项：**
- 有完整的排障方法论：从"现象 → 假设 → 验证 → 缩小范围"循环推进，先切分故障域（用户侧/公网/云边界/云内链路/实例/应用），每步用数据排除而不是靠猜
- 第一轮证据收集：应用日志（超时发生的时间点、调用方）、SLB 日志/访问日志（哪个后端实例的响应时间异常）、云监控（带宽/连接数/丢包按时间点对齐）——先看"超时是否集中在某实例/某时段/某接口"
- 第二轮网络验证：对可疑实例看 TCP 重传率（`ss -s`、`netstat -st` 看重传）、Flow Logs 看该实例的流量是否异常、抓包对比正常/异常时刻的握手与响应时序
- 能提出并验证关键假设：连接数打满（TIME_WAIT/ESTABLISHED 数）→ 端口耗尽；TCP 重传率高 → 物理链路/带宽/丢包；MTU/分片问题（大包小包行为不一致）；后端单实例 GC/慢调用被健康检查误摘；NAT/SNAT 端口耗尽导致新连接失败
- 有定位到根因后的动作：修复 + 验证（压测复现不了就持续观察指标回落到基线）+ 复盘沉淀（补监控项、加告警）
- 提到"偶发"类问题的特征：往往不是持续故障而是"触发条件性"（特定时刻、特定连接、特定大小包），要抓住"异常时刻"而不是看平均值

**减分项：**
- 没有方法论，东看西看，抓到什么算什么
- 只盯着应用日志，不知道先切分"网络 vs 应用"的故障域
- 不会看重传率、连接数这些网络先行指标
- 把"偶尔超时"当玄学，不建立时间对齐的分析（监控数据没对齐到超时时刻）
- 找到表面现象（如"某实例响应慢"）就收工，不追根因（为什么慢）

**解答：**

偶发超时是最考验排障功力的题，核心方法论是"时间对齐 + 故障域切分"。第一步收集三个时间序列并对齐到超时发生时刻：应用侧（超时调用的接口、来源 IP、时间点）、负载均衡侧（后端响应时间分布、健康检查记录）、云监控（带宽、连接数、丢包率、重传）。拿到后先切分故障域——如果超时集中在某一个后端实例：假设它是"实例自身问题"还是"链路到该实例的问题"。第二步验证网络层，在超时时刻看实例的 TCP 状态与重传：`ss -s` 看连接数是否打满（如果 TIME_WAIT 上万且新连接失败，就是连接表/端口耗尽）、`netstat -st` 看 TCP retrans 是否骤增（重传率飙升指向链路丢包或带宽打满）。我真实排过的一个案例：订单服务偶发超时，最后定位是 NAT 网关 SNAT 端口耗尽——出方向连接数在高峰瞬间超过 SNAT 条目，新连接排队等端口，表现为"偶发 10 秒超时"；现象在应用侧，根因在网络出口，靠"连接数时间曲线 + SNAT 使用率"对齐才找到。另一个经典根因是 MTU 问题：ECS 与对端 MTU 不一致时，大包（如带大 header 的 POST）被丢弃、小包正常，表现为"特定接口偶发超时"——验证方法是抓包看是否只有大包重传，或 `ping -s 1400` 对比大小包行为。第三步抓包取证：在超时时刻前后 tcpdump 抓可疑连接，对比"SYN 发出去没有 ACK"（链路丢）还是"应用迟迟不响应"（应用问题），一举定责。修复后不能立刻收工：持续观察 2-4 天确认指标回落到基线，并把这次发现的问题补成监控告警（如 SNAT 端口使用率、TCP 重传率），把"偶发"变成"可观测"。

**延伸考点：** 如果超时集中在"特定客户端 IP 段"而不是"特定实例"，故障域怎么切？公网链路的责任如何用 mtr/拨测数据向运营商举证？

### Q19. 经典三层架构（接入/应用/数据）上云，网络层怎么落到 VPC 和子网？

**问题：** 你们要迁移一套经典三层架构到云上：接入层（Nginx/API 网关）、应用层（业务服务集群）、数据层（MySQL 主从 + Redis）。要求：①接入层对外提供服务；②应用层要出公网调第三方 API；③数据层不允许有任何公网暴露；④各层之间最小权限互访。请给出完整的 VPC/子网/路由/安全组落地设计。

**期望加分项：**
- 子网三层划分：公有子网（接入层，配公网 LB/EIP + NAT）、应用子网（私有，仅内网 + 出公网走 NAT）、数据子网（隔离，无任何公网路由，连 NAT 都不路由），每层一个或跨 AZ 两个子网
- 路由设计完整：公有子网默认路由指向公网网关（IGW），应用子网默认路由指向 NAT 网关（SNAT 出公网），数据子网无默认公网路由（或指向黑洞），层间互访走 VPC 内网路由
- 安全组白名单：接入层安全组放 80/443（来源 0.0.0.0/0 或高防/WAF），应用层安全组只放接入层安全组 ID 的 8080，数据层安全组只放应用层安全组 ID 的 3306/6379；用安全组 ID 引用而非 IP 段
- 高可用叠加：每个子网分布在两个 AZ，SLB 多可用区、应用集群跨 AZ 部署、MySQL 主备跨 AZ（同步复制）或主备同 AZ + 跨 AZ 只读；数据库用内网 SLB/私网域名暴露给应用
- 有出口管控细节：应用出公网统一 NAT，NAT 网关绑固定 EIP 供第三方白名单；数据层如需出公网（如拉补丁）用临时 NAT 或白名单代理，事后回收
- 能讲边界与例外：堡垒机放公有子网做运维入口，数据库备份导出走内网到对象存储（不占公网），压测/大促扩容时的子网 IP 预留

**减分项：**
- 三层全放一个子网，靠安全组"裸奔式"隔离，路由上数据层还能出公网
- 安全组用 IP 段硬编码，扩缩容一次改一次
- 数据库直连公网或应用直连公网不收敛 NAT，暴露面失控
- 没有高可用考虑，每层都单 AZ 单点
- 说不清路由表怎么配，默认路由谁指向谁一片模糊

**解答：**

经典三层上云的落地核心是"子网分三层 + 路由断公网 + 安全组收口 + 跨 AZ 高可用"。子网设计：接入子网（公有）放 SLB/Nginx/API 网关，默认路由指向公网网关，对外暴露 80/443；应用子网（私有）放业务集群，默认路由指向 NAT 网关——应用要调第三方 API 就经 NAT 出公网，且 NAT 绑定固定 EIP 方便第三方配白名单；数据子网（隔离）放 MySQL/Redis，路由表里**不给**任何公网出口（默认路由直接不配或指向黑洞），从网络层就掐死数据层出公网的可能——这是"即便有人误开端口也出不去"的纵深防御。每个子网都在两个 AZ 各建一个（Q1 的 AZ 预留在这里兑现），保证跨 AZ 高可用。路由与访问控制的细颗粒：层间互访走 VPC 内网路由（默认互通，靠安全组收口）：接入层安全组放 80/443（来源是高防/WAF 段或 0.0.0.0/0），应用层安全组只放行"接入层安全组 ID → 8080"，数据层安全组只放行"应用层安全组 ID → 3306/6379"——用安全组 ID 互相引用，扩容不加规则、换 IP 不失效。高可用：SLB 多可用区、应用集群两个 AZ 各 N 台、MySQL 一主一备跨 AZ（同地域内网延迟通常 1-2ms，半同步可接受）、Redis 主备同 AZ；数据库对应用暴露用内网 SLB 或私网域名（配合 Q9 的 PrivateZone），应用不感知主备切换。运维边界也要画清楚：堡垒机放接入子网并开临时白名单访问，数据层备份走内网到 OSS（走内网不占公网流量费），第三方要联调数据库时通过应用层接口而非直连数据层。这样一套设计，"最小权限 + 无公网暴露 + 可扩展 + 可容灾"四个要求全部落到具体配置上。

**延伸考点：** 如果数据层需要"每天定时拉取外部黑名单文件"，在"不允许出公网"的约束下怎么实现（白名单代理 / 定时任务走应用层 / 临时开 NAT 并回收）？

### Q20. 客户要求支持 IPv6，云上双栈、过渡和演进怎么落地？

**问题：** 有客户（或监管要求）提出服务要能被 IPv6 用户访问，你们现有系统是纯 IPv4 架构：DNS 是 A 记录、SLB 绑的是 IPv4 EIP、应用代码里可能有硬编码 IPv4 地址。你会怎么设计云上 IPv6 的演进方案：双栈怎么开、域名和 LB 怎么改、应用层要动哪些、过渡期怎么保障 IPv4 用户不受影响？

**期望加分项：**
- 讲清双栈（Dual Stack）原理：同一资源同时具备 IPv4 与 IPv6 地址，两类用户各自走自己的协议栈，互不影响；云上 VPC 开 IPv6 CIDR、子网开 IPv6、实例分配 IPv6 地址
- 演进路径清晰：接入层先行（SLB 开 IPv6 监听、DNS 加 AAAA 记录）→ 内部逐步（应用/数据库暂可纯 IPv4，SLB 做协议转换或双栈转发）→ 存量 IPv4 用户完全不受影响（DNS 按客户端协议栈返回 A/AAAA）
- 讲清产品支持现状：阿里云/AWS 的 VPC、SLB/ALB/NLB、CDN、DNS（AAAA）、ECS 均支持双栈；IPv6 地址是公网地址（全球唯一、免 NAT），天然解决"公网地址枯竭"，但也要注意暴露面与安全组规则要同时覆盖 IPv6 地址段
- 有工程细节：DNS 同时配 A + AAAA（AAAA 配好后优先被 IPv6 客户端解析）、SLB 双栈监听、应用层检查是否有硬编码 IPv4（白名单、日志、配置里的 IP 字面量）、安全组/NACL 规则要新增 IPv6 网段（::/0）的白名单
- 有过渡与灰度策略：先灰度（新用户/特定地区走 IPv6）、保留 IPv4 一段时间（双栈过渡期以"年"计）、IPv6 优先但 IPv4 兜底（happy eyeballs 机制）、监控双栈访问量与失败率
- 提到纯 IPv6 的坑：IPv6 地址不可记忆/不可 NAT、日志与审计系统要能记录 IPv6 地址、部分老代码/中间件对 IPv6 处理不当（如日志截断、正则校验）、安全产品（WAF/高防）要确认支持 IPv6

**减分项：**
- 认为 IPv6 只是"加个地址"，不涉及 DNS、LB、安全组、代码四处联动
- 只加 AAAA 记录不配 LB 监听，IPv6 用户访问直接超时
- 不知道 IPv6 是公网地址、无 NAT，暴露面理解错误
- 安全组只配了 IPv4 白名单，IPv6 网段裸奔
- 没有过渡策略，幻想"一天切完"，或完全不动等客户投诉

**解答：**

IPv6 演进的关键认知是"双栈过渡"：不是把 IPv4 删了换成 IPv6，而是让两者共存、逐步迁移，过渡期以年计。云上落地分四步：第一步网络层——VPC 开通 IPv6 网段，给接入层子网开 IPv6 并分配地址（SLB/ECS 自动获得 IPv6 地址，它是全球唯一的公网地址，不再需要 NAT，但也意味着暴露面直接对公网开放，安全组必须补 IPv6 规则）；第二步接入层——SLB 增加 IPv6 监听（阿里云 SLB 支持 IPv4/IPv6 双栈监听），DNS 在 A 记录旁增加 AAAA 记录指向 LB 的 IPv6 地址，客户端按自己协议栈自动选（IPv6 优先、IPv4 兜底，即 happy eyeballs，所以 AAAA 配好后老用户不受影响）；第三步应用层排查——代码里硬编码的 IPv4（白名单、连接串、日志格式）要改为域名或同时支持双栈，正则校验、IP 截断这类对 IPv6 字符串不友好的逻辑要修；第四步安全与监控——安全组/NACL 在原有 IPv4 规则外补 IPv6 规则（如只放 `::/0` 的 80/443），WAF/DDoS 高防确认支持 IPv6 清洗（不支持的话 IPv6 入口裸奔，这是最常见的坑），监控增加"IPv6 访问量、IPv6 成功率"双指标并与 IPv4 对比。灰度上：先在测试环境全链路验证 AAAA → 双栈 LB → 双栈后端，再对少量用户/地域放开 IPv6，稳定后放开全量但**保留 IPv4 入口**至少一年——纯 IPv4 的老用户、部分政企内网、老旧操作系统（Windows 7 以下、老 Android）还在，一刀切就是事故。我见过最典型的翻车：只加了 AAAA 记录，LB 没开 IPv6 监听，IPv6 用户解析到了地址但连接全部超时，还怪"IPv6 用户少不用管"。总结：双栈是"网络层开、接入层配、应用层查、安全层补、灰度期留"五件事，缺一不可。

**延伸考点：** 双栈架构下如何做 IPv6 优先但 IPv4 兜底（happy eyeballs）？纯 IPv6 客户端访问纯 IPv4 后端时，SLB/网关的 NAT64/协议转换怎么兜底？
