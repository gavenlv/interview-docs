# 云 · 云迁移（面试题库）

本文件考察候选人在云迁移工程落地上的真实能力：迁移决策框架（6R 选型）、迁移前评估与复杂度分析、迁移工具（AWS MGN/阿里云 SMC/DTS 等）的选型与使用、专线/VPN 网络打通与 DNS 切换、全量+增量数据同步与校验、停机窗口与在线迁移（双写）设计、同构/异构数据库迁移、回退与一致性保障、分批渐进迁移、上云后优化与复盘，以及贯穿始终的迁移项目管理。全部为场景化提问、不考八股文——重点看候选人能否给出量化依据、说清取舍、引用线上迁移实例与踩坑经历、主动覆盖边界条件与回退路径，难度从实践基础渐进到架构级设计。

---

### Q1. 业务要上云，6R 策略到底怎么选才算想清楚了？

**问题：** 你们有一套自建机房的几十个应用、数据库和中间件要迁上云。老板问"哪些直接搬、哪些改造、哪些下线"，你打算用 6R 框架来定，但担心流于形式。你会怎么基于资产盘点和业务诉求给出每类资产的 6R 归属？

**期望加分项：**
- 准确说出 6R：Rehost（搬迁上云）、Replatform（换平台/改配置）、Refactor（重构改造）、Repurchase（购买 SaaS 替换）、Retire（下线）、Retain（保留不动）
- 有决策维度模型：按"业务价值/变更风险/技术债/生命周期"四象限打分，而非拍脑袋
- 用数据说话：如按迁移工作量（人天）、改造收益（弹性/性能/成本）算 ROI，给出量化排序
- 指出常见取舍：EOL 的旧版本系统优先 Retire；功能与 SaaS 能力重叠的选 Repurchase；有明确弹性诉求的 Replatform 到托管服务
- 强调 6R 是"迁移前的设计产物"而非口号，每个 R 都要落到资产清单的一行
- 提到组织现实：Retain 往往不是技术选择而是合规/工期约束，要明说

**减分项：**
- 只会背 6R 名词，答不出"这个系统到底该选哪个 R、依据是什么"
- 不做资产盘点就谈策略，所有系统一刀切 Rehost
- 忽视 Retire/Retain，好像所有系统都必须迁移
- 不谈 ROI 和优先级，无法回答"先迁什么后迁什么"
- 把 6R 当一次性动作，没有在迁移过程中动态复核

**解答：**

6R 不是选择题而是"决策框架"：先盘点、后打分、再归类。第一步是资产盘点：把每个系统按实例数、CPU/内存规格、数据库/中间件依赖、版本、负责人、业务重要性登记成表——没有这张表，6R 全是空谈。第二步建立决策维度，我常用的四维模型是：业务价值（在线交易 vs 内部工具）、变更风险（有状态/无状态、是否核心链路）、技术债（EOL 系统、老 JDK、无 CI）、迁移收益（弹性、算力成本、运维人效）。三维都低且无收益的，直接 Retire；与现有 SaaS 能力（如 OA、监控）重叠的，Repurchase；核心交易库和关键业务，优先 Rehost 保行为一致、控制风险，再考虑二期 Replatform。量化也很重要：我给过一组真实数字——某 60 台虚拟机的自建机房，按"每系统评估人天"算下来 Rehost 平均 3 人天/系统、Replatform 12 人天、Refactor 60 人天，最终 34 个系统 Rehost、8 个 Replatform、5 个 Repurchase、6 个 Retire、7 个 Retain（合规要求数据不出域）。还要说明 Retain 不是失败：先迁无状态的、收益大的，把有强合规约束和历史包袱的留在原地，是成熟团队的正常选择。最后，6R 结果要落到迁移批次计划里，每个 R 决定走哪条迁移流水线（镜像搬运 vs 改造走 CI/CD），这是框架真正产生价值的地方。

**延伸考点：** 某系统版本已 EOL 但业务仍在用，你是选 Rehost 还是 Refactor？判断依据是什么？如果老板坚持"全部上云"，你怎么管理这个预期？

### Q2. 迁移前要做哪些评估，才能不把风险留到割接那天？

**问题：** 你负责一个包含 200 个微服务、3 套 MySQL 主从、若干 RabbitMQ 和 Redis 的系统的上云评估。割接窗口只有 4 小时。开工前你打算做哪些维度的评估，让"迁移复杂度"可量化、可排期？

**期望加分项：**
- 覆盖四类评估：应用画像（规格、状态、日志）、依赖分析（服务调用/DB/中间件/外部 API）、资源盘点（CPU/内存/磁盘/带宽基线）、迁移复杂度分级（T-shirt size 或 ABC 级）
- 有可执行手段：用 cmdb 导出资产、抓监控基线数据（压测/生产高峰采样）而非凭感觉估资源
- 识别隐藏依赖：静态 IP、内网域名、定时任务、文件服务器路径、硬编码配置、License 绑定 MAC
- 给迁移复杂度打分级并换算人天：如 A 级 1-2 天、B 级 3-5 天、C 级 1-2 周，支撑排期与风险清单
- 提到存量配置/密钥清单（如 JDBC 串、密钥、证书过期时间），评估 DNS/防火墙/安全组策略差异
- 主动暴露"评估不出来的风险"：如遗留系统无人维护、数据量无法预估，要在计划里留 buffer

**减分项：**
- 只评估规格（几核几G）不做依赖与配置分析，割接时才发现连不上内网数据库
- 资源评估拍脑袋，不做基线采样，上云后性能不足或资源浪费
- 忽略定时任务、IP 硬编码、License 这类"迁移杀手"
- 复杂度分级凭感觉，不给量化依据，排期全靠赌
- 不做风险登记，把所有风险留到割接当天集中爆发

**解答：**

迁移评估的本质是"把未知变已知"，我按四步做：第一步资产盘点，从 CMDB 和监控平台导出全量清单，关键字段是实例规格、OS 版本、运行的应用、依赖端口、数据目录大小、近 30 天 CPU/内存/带宽峰值——资源评估必须用生产基线采样，我曾遇到一个系统按日常均值配了 4C8G，割接当晚双 11 预热流量一来直接打满，这就是没看峰值基线的教训。第二步依赖分析，用服务调用链和端口扫描找出所有外部依赖：数据库、Redis、MQ、短信/支付 API、License 服务器，特别要查三种隐藏依赖：代码里硬编码的 IP、crontab 定时任务、NFS/CIFS 共享路径——这些在评估期不暴露，割接期必踩。第三步配置梳理：JDBC 串、Redis/MQ 地址、密钥、证书有效期、日志路径，全部登记并标注"迁移后是否需要改写"。第四步复杂度分级：无状态服务 A 级（直接镜像迁移）、有状态但无强依赖 B 级（需停机窗口）、核心链路+数据+强一致性 C 级（需演练）。分级后按 A=1-2 人天、B=3-5 人天、C=1-2 周换算总工作量，同时给 20%-30% buffer 覆盖"未知的未知"。评估产出物必须是三张表：资产清单、依赖矩阵、风险登记表（含缓解措施与负责人），这才叫可执行的评估，而不是一篇 PPT。

**延伸考点：** 评估阶段发现某个老系统的代码包和配置已经找不到维护人了，你怎么办？这会怎么影响你的迁移批次和风险登记？

### Q3. 迁移工具怎么选：AWS MGN、阿里云 SMC、镜像搬运、还是重装？

**问题：** 你手上有三类资产要迁：200 台无状态应用虚机（CentOS 7）、10 台有本地盘的数据库服务器、一批可以重新部署的中间件。你会分别用什么迁移工具/路径，依据是什么？工具迁移和"重装部署"各自的适用边界在哪？

**期望加分项：**
- 工具认知准确：AWS MGN（源端安装 agent 持续复制磁盘块，可测试化割接）、阿里云 SMC（快照/镜像导入或 agent 迁移）、自建镜像搬运（qcow2/vmdk 转换导入）各有适用场景
- 按资产匹配路径：无状态应用走镜像导入或重装+自动化部署；数据库走 DTS 类数据同步而非整机迁移；中间件推荐重装保证版本纯净
- 能对比"整机迁移 vs 重装"：整机迁移保行为一致但带病（补丁旧、垃圾文件多），重装干净但要解决配置/数据搬迁
- 讲清 agent 迁移原理与前提：源端要能装 agent、打通到目标端的网络（VPN/专线）、磁盘块级复制持续同步、注意内核与 OS 版本兼容
- 提到演练能力：MGN/SMC 支持"测试割接/克隆"不中断源端，这是判断工具是否合格的关键
- 有量化决策：如"单机迁移成本 + 停机时间"对比表，或按"是否方便重装"一刀切规则

**减分项：**
- 分不清工具适用场景，所有机器一律"装 agent 镜像迁移"
- 不了解 agent 迁移的前提（网络、OS 兼容、块级复制原理），遇到黑屏启动失败不会排查
- 不考虑演练/回滚能力，直接正式割接
- 数据库也整机搬，忽视数据一致性必须走日志同步
- 只会背工具名，说不出选型依据和踩过的坑

**解答：**

选工具前先给资产分类：无状态应用、有状态数据库、可重装中间件，三条路径完全不同。无状态应用虚机我倾向镜像导入或 agent 迁移：阿里云 SMC 支持把本地 VM 通过 agent 或 OVA/qcow2 镜像导入，AWS 用 MGN（Application Migration Service）——它在源端装 agent 做持续块复制，目标端可以反复"测试割接"演练，正式割接时只需短停源机做最后一次增量同步然后切换，这个"可测试化"能力是生产环境选它的核心理由。但要注意前提：源机必须能装 agent、OS 在支持列表内（比如老 CentOS 5 不在列表就得用镜像转换）、网络要能通到目标端。数据库服务器绝不要整机搬：正确姿势是用 DTS/DMS 这类数据同步工具做全量+增量（后面 Q5 展开），因为数据库的割接一致性靠 binlog/WAL 而不是磁盘快照。中间件（Redis、Kafka、Nginx）我推荐"重装+配置脚本化"：整机迁移会把源机多年的补丁缺失、垃圾文件、环境残留带过去，重装反而干净，代价是配置要梳理成 IaC。我经历过一次反面教材：用镜像迁移了一台跑着老版本 glibc 编译产物的应用机，启动时动态库兼容问题排查了整整半天——如果当初按"应用必须重装、数据必须走同步"的规则就不会有这个坑。所以我的决策规则是：无状态且可重装的走自动化部署，必须保行为一致的走镜像/agent 迁移，有状态数据一律走数据同步工具，每类资产配一条固定流水线而不是临时选。

**延伸考点：** MGN/SMC 的 agent 迁移在目标端启动时，常见启动失败原因有哪些？如何预先验证内核驱动（如 virtio/xen）兼容性？

### Q4. 专线还没通，迁移期间源端和目标端的网络怎么打通、带宽怎么算、DNS 怎么切？

**问题：** 你们机房在上海，阿里云 VPC 在华东 2，迁移期间要同时跑"源端在线 + 目标端同步"模式。老板不想等专线（工期 2 个月），问能不能先干。网络方案、带宽规划、DNS 切换你分别怎么设计？

**期望加分项：**
- 给出阶段性网络方案：初期 IPSec VPN（几天内打通）→ 迁移期 VPN/公网加速 → 稳定期拉专线，不同阶段不同方案
- 带宽可计算：按"迁移窗口要搬的数据量 / 时间窗"估算，如 5TB 数据 48 小时搬完需 ≥ 250Mbps 实际带宽，考虑 VPN 开销和线路抖动留余量
- 讲清 DNS 切换方案：TTL 预降（如 300s→60s 提前 48h）、切换顺序（内网优先→外部流量灰度）、切换回滚（DNS 记录改回即可但要注意会话与缓存）
- 边界与取舍：专线成本高、VPN 简单但带宽受限且不稳定；对时延敏感（数据库同步）的业务要评估 RTT 对同步延迟的影响
- 有验证手段：切换前做连通性/带宽基准测试（iperf3 打流）、灾备演练验证链路质量
- 覆盖安全：VPN 加密、安全组/防火墙放行清单、迁移期间数据在公网传输的合规评估

**减分项：**
- 一口咬定"没有专线不能迁"，或反过来全程裸公网无加密
- 不估算带宽，同步 10TB 数据在 VPN 100Mbps 上跑到天荒地老才发现
- DNS 切换不考虑 TTL 缓存，割接后部分用户长时间访问旧地址
- 忽略数据库同步对网络 RTT/丢包的敏感性，链路抖动导致同步持续追不上
- 没有切换前验证和回滚步骤，切了就回不来

**解答：**

网络打通要分阶段而不是一步到位：迁移启动阶段用 IPSec VPN（自建 strongSwan 或云上 VPN 网关），两三天就能通，满足 agent 迁移和数据同步的加密通道需求；数据量大的批次走公网+大带宽或者临时带宽包加速；进入长期共存期再拉专线降本。带宽按公式算：所需带宽 ≥ 迁移数据量 / 时间窗。举个例子，全量 5TB、要求 48 小时完成首轮同步，5TB×8/48h ≈ 233Mbps，加上 VPN 封装开销和重传余量，至少买 300M 上行；如果只有 100M VPN，5TB 要 111 小时，排期直接翻倍——所以带宽是迁移排期的输入而不是事后发现。带宽买好后先用 iperf3 打流验证实际吞吐（专线/ VPN 经常只有标称的 60-70%），再决定数据同步的并发数。DNS 切换是割接的关键动作：提前 48 小时把 TTL 从 300s 降到 60s（让旧记录尽快过期），割接时先切内网解析验证，再切外部域名；注意 A 记录切到云上 SLB 后，要保留旧机房 IP 一段时间（比如 3-5 天）作为回退路径，同时用全局流量管理（GTM/SLS 的 GTM 或 AWS Route53）做故障转移会更优雅。数据库同步对链路质量最敏感：RTT 超过 50ms 或丢包 >0.5% 时 DTS 的增量延迟可能从秒级变成分钟级，所以要监控"同步延迟"而不是只盯带宽。最后，公网传输的数据要做合规评估（PII 数据建议走加密通道或直接等专线），这是很多团队忽略的一环。

**延伸考点：** VPN 和专线怎么选型？在什么数据量/时延/合规要求下"必须等专线"？DNS 灰度切换（按用户群比例引流）怎么和 GTM 配合实现？

### Q5. 数据库迁移：全量+增量怎么设计，割接后怎么证明数据没丢？

**问题：** 你们要把 2TB 的 MySQL 主库从自建机房迁到云上 RDS，业务不允许超过 10 分钟不可用。请设计一条全量+增量的迁移链路，并说明割接瞬间如何保证一致、割接后如何做数据校验。

**期望加分项：**
- 链路设计标准：先用全量（DTS/DMS 首次全量迁移）跑底，再开增量同步（订阅 binlog）追平延迟，最后短停源库做最后一次追平再切换
- 讲清增量原理：源库开 binlog（row 格式）、DTS 从 binlog 位点/GTID 持续拉取回放，目标端与源端保持秒级延迟
- 一致性保障：切换前校验"增量延迟归零 + 主从位点一致"；用一致性快照（如 RDS 只读实例+单线程校验）或校验工具（pt-table-checksum、DTS 内置校验）比对全表
- 有量化方案：2TB 数据全量阶段几小时、增量追平后延迟 < 5s 才允许切换；校验抽样比例与耗时给出估算
- 考虑切换后验证与回滚：保留 binlog 备份、源库不立刻销毁，切换异常可回切
- 覆盖边界：大表无主键、字符集差异、自增主键冲突、外键/触发器在目标端的行为差异

**减分项：**
- 只会说"用 DTS 同步"，讲不出全量/增量两阶段和 binlog 位点原理
- 不做数据校验，或者只抽查几条记录就当完成
- 不考虑自增主键、无主键大表等特殊对象的迁移风险
- 切换后立刻销毁源库，出问题没有回退能力
- 忽视增量同步的延迟监控，割接时才发现追不上

**解答：**

标准链路是"先全量、再增量、短停追平、切换校验"四步。第一步全量：用 DTS（阿里云）或 DMS（AWS 用 DMS）建迁移任务，先跑 2TB 全量——注意 DTS 全量阶段按表并发拉取，大表建议先按主键分片，全量阶段大概 3-6 小时（取决于网络与源库 IO）；期间源库正常读写，DTS 会记录 binlog 位点。第二步增量：全量结束后自动进入增量阶段，DTS 通过订阅源库 binlog（务必 row 格式、binlog_row_image=FULL）持续回放，此时目标库随时追平到秒级。第三步割接：申请 10 分钟窗口，先停源库写流量（应用切换只读或直接停服），等 DTS 增量延迟归零且位点不再前进，把目标库提升为可写（DTS 里"切换"按钮或手动改目标库），然后切 DNS/连接串。一致性靠两层保障：割接前用 pt-table-checksum 或 DTS 自带校验比对核心表的行数与校验和（2TB 全表校验可能跑 1-2 小时，建议只对业务表全量、日志表抽样）；割接后立刻跑应用冒烟（登录、下单、对账）并比对当日关键业务数据总量。真实案例提醒：增量阶段最常见的坑是目标库有自增主键冲突（源库自增值落后于目标库已有数据）或字符集不一致（utf8mb4 与 latin1 混用导致乱码），所以建任务时就要把"主键冲突策略"（覆盖/忽略）和字符集转换规则确认好。最后，源库 binlog 至少保留 7 天、源库本身保留 30 天再销毁，这是回退的物理保障——回退时把应用切回源库即可，数据以源库为准。

**延伸考点：** 异构迁移（Oracle→MySQL 或 PG→MySQL）时，数据类型、分区表、存储过程这些怎么处理？无主键大表 DTS 为什么同步慢，怎么优化？

### Q6. 停机窗口只有 4 小时，有状态系统怎么设计割接，能不能做"在线迁移"？

**问题：** 一个核心交易系统（MySQL + Redis + 无状态应用集群）要迁上云，允许的停机窗口 4 小时，但业务方希望尽量"不停机"。请设计停机迁移方案，并讨论什么时候可以走"在线迁移/双写"以及它的风险。

**期望加分项：**
- 区分两种模式：停机迁移（短停、数据追平、切换）与在线迁移（双写、灰度切换、源端持续运行）的适用条件
- 停机窗口拆解：把 4 小时分解为"停写→增量追平→校验→切换→验证"各阶段，说明数据库同步通常能压到分钟级，真正的耗时在应用发布与验证
- 双写设计具体：应用层先写云上再写本地（或反之）、失败补偿（MQ/对账任务）、双写期只读灰度验证
- 讲清双写的风险：数据不一致（先写后写顺序、部分失败）、写放大、双写代码要可下线
- 给停机窗口的量化预算：如全量已提前完成、增量追平预留 30 分钟、校验 30 分钟、切换+验证 60 分钟、buffer 60 分钟
- 提到工具化切换：连接串集中配置（配置中心/环境变量），切换=改配置+重启，而非逐台改代码

**减分项：**
- 一说"不停机"就无脑双写，不评估双写的代码成本和一致性问题
- 4 小时窗口没有时间预算分解，现场才现想
- 双写没有补偿和校验机制，出问题无法自愈
- 不提前演练，割接窗口当成第一次执行
- 忽略 Redis 这类内存态数据的同步（纯内存库没有 binlog 概念）

**解答：**

先明确一个判断：不是所有系统都值得在线迁移。无状态服务天然可以"先切流量再切数据"，但有状态系统（交易库）的在线迁移=双写，双写的成本（改代码、一致性问题、可回退性）往往比一次 30 分钟的短停高得多。所以我的方案分层：核心交易库走"短停迁移"，把 4 小时窗口当预算来花——全量与 99% 的增量提前几天做完，窗口内只剩"停写 5 分钟→增量追平 10 分钟→校验 15 分钟→切连接串+重启 30 分钟→业务验证 60 分钟"，实际用 2 小时左右，剩下全是 buffer。Redis 注意纯内存库没有 binlog，增量靠 RDB+AOF 装载 + 应用双读兜底，或者干脆在窗口内重建缓存（预热）而不是追求无感。如果业务方坚持在线：双写方案要设计成"应用层双写云上新库+本地旧库，读走新库灰度验证，双写失败进本地 MQ 补偿，最后关闭双写并切换读写"——双写期最怕"先写 A 成功写 B 失败"导致两边不一致，所以必须有对账任务（按 ID 比对两条链路的写入结果）和一键关停双写的开关。我给过一个真实的判断标准：如果双写改造超过 5 人天，而短停迁移只需要 2 小时窗口，就别做双写。另外无论哪种模式，连接串必须集中管理（配置中心或环境变量），割接=改配置+滚动重启，逐台改代码的方式在 4 小时内必翻车。窗口前至少做一次完整演练（含回退演练），把演练实测耗时写进正式计划——演练是迁移唯一可以 100% 提前做的事。

**延伸考点：** 双写方案里"先写新库还是先写旧库"怎么选？对账任务怎么设计才能发现所有不一致？如果割接后发现云上新库有数据损坏，回退动作具体是什么？

### Q7. 虚拟机整机迁移 vs 容器化改造，应用这一层怎么迁才不翻车？

**问题：** 你们一批 Java 应用跑在自建机房的虚拟机里，有的应用直接依赖服务器本地目录、crontab 和静态 IP。上云后是"原样搬 VM"还是"改造成容器/托管服务"，你怎么决策？配置和依赖怎么迁才安全？

**期望加分项：**
- 决策逻辑清晰：迁移目标决定路径——快速上云（Rehost）搬 VM，追求弹性/可移植（Refactor）上容器，无状态应用优先容器化
- 识别"容器化杀手"：本地磁盘写文件、crontab 定时任务、静态 IP 绑定、依赖特定内核/系统库——这些要提前改造
- 配置迁移标准化：配置外置（环境变量/配置中心）、密钥走 KMS/Secret 管理、构建产物统一（Jar/War 版本锁定）
- 有依赖迁移清单：JDK 版本、动态库、时区、字符集、NTP、日志采集 agent 都要纳入
- 给出灰度策略：先迁低风险应用验证流水线，再批量推广；VM 与容器并存期用相同发布流程保证一致性
- 讲量化：容器化改造每个应用的人天估算与收益（部署时间、扩缩容、资源利用率）

**减分项：**
- 把所有应用一律容器化，不考虑有状态和依赖本地资源的老应用
- 不知道 crontab/本地文件/静态 IP 是容器化障碍，改造到一半才发现
- 配置硬编码在代码或启动脚本里，迁移后逐台手改
- 不做依赖版本核对，旧 JDK 应用在新环境运行出兼容问题
- 只讲"用 Dockerfile 打镜像"，讲不出从 VM 到容器的完整落地路径

**解答：**

应用迁移要按"状态"分类决策：无状态应用走容器化（收益最大），有状态或强依赖本地环境的先 VM 迁移（Rehost）保行为一致，后续再渐进容器化。容器化前先做"障碍清单"体检：①写本地磁盘——容器重启数据丢失，要改成挂卷或对象存储；②crontab——容器里要么拆成独立定时任务服务，要么用 K8s CronJob；③静态 IP 绑定——许可证或白名单依赖 IP 的，要么改配置要么用 EIP 方案；④系统库依赖——启动报 `libc.so` 找不到这类问题要在镜像构建时就验证。配置迁移我坚持三条原则：配置外置（Spring Cloud Config/环境变量）、密钥进密钥管理（KMS/Secrets Manager，绝不放镜像）、版本锁定（构建产物带 hash，记录 JDK 版本）。我踩过的一个典型坑：某老应用依赖服务器上的 `/opt/app/config` 目录和 `/usr/bin/ffmpeg`，原样搬 VM 没事，容器化后启动即挂——这类应用就应该排在容器化批次末尾，先让无状态新应用跑通容器流水线。迁移路径上建议"双轨并行"：先建好 CI/CD 流水线（打镜像→推仓库→部署），选择 2-3 个低风险应用走完整流程（含回滚演练），验证后批量推广；VM 和容器并存期保持发布流程一致（同一个制品仓库、同一套部署编排），避免两套维护成本。量化参考：一个标准 Java 应用容器化改造约 2-3 人天（含流水线接入），有本地依赖的 5-8 人天——这个数字可以直接用来排批次。

**延伸考点：** 日志采集在容器化后怎么做（文件挂载 vs stdout）？多副本部署后，原来写本地磁盘的临时文件逻辑怎么改造最省事？

### Q8. 数据库异构迁移（Oracle→MySQL）或者同构升级（5.7→8.0），有哪些坑是迁移团队必踩的？

**问题：** 你们的订单库要从自建 Oracle 11g 迁到云上 MySQL 8.0（异构），另一套 MySQL 5.7 要原地升到 8.0（同构）。这两类迁移分别要处理哪些兼容性问题？字符集、时区、自增主键这些具体怎么处理？

**期望加分项：**
- 异构迁移重点讲清映射：数据类型（NUMBER→DECIMAL/BIGINT、DATE→DATETIME/TIMESTAMP、CLOB→TEXT/LONGTEXT）、SQL 方言（ROWNUM→LIMIT、NVL→IFNULL、dual、(+) 外连接→JOIN）
- 同构升级讲清版本差异：MySQL 8.0 的默认字符集 utf8mb4、认证插件 caching_sha2_password 对旧客户端的兼容、sql_mode 变化（如 ONLY_FULL_GROUP_BY）
- 字符集与排序规则：统一 utf8mb4/utf8mb4_unicode_ci，迁移前后做乱码验证（全角字符、emoji、四字节汉字）
- 时区处理：DB time_zone、应用 JDBC 连接参数（serverTimezone）、TIMESTAMP 与 DATETIME 在时区下的语义差异
- 自增主键/序列：Oracle 用 SEQUENCE+触发器、MySQL 用 AUTO_INCREMENT，迁移后主键续值、无主键表要补键
- 有验证手段：SQL 兼容性预检（DTS 任务预检查）、数据校验、业务接口回归测试清单

**减分项：**
- 只会说"DTS 支持异构迁移"，讲不出具体映射与方言差异
- 忽略认证插件/字符集/sql_mode 这类配置级差异，上线后应用连不上或乱码
- 不处理时区，TIMESTAMP 数据跨时区全偏 8 小时
- 主键/序列不规划，割接后插入直接主键冲突
- 不做预检和回归，靠上线后发现问题

**解答：**

异构迁移的核心是"SQL 与数据模型的双重翻译"。数据层面：NUMBER 要按精度映射（整数用 BIGINT、带小数用 DECIMAL(38,18)）、DATE 映射 DATETIME、CLOB 映射 LONGTEXT，字段长度和默认值逐表核对；语句层面：Oracle 的 `ROWNUM`/`FETCH FIRST` 改 `LIMIT`、`NVL` 改 `IFNULL`、`(+)` 外连接改标准 `LEFT JOIN`、PL/SQL 存储过程基本要重写——所以异构迁移前必须让开发跑一遍 SQL 兼容性预检（DTS 任务预检查会列出不支持的对象），并出"改造工作量"给排期。同构升级相对小但同样有坑：MySQL 8.0 默认认证插件是 caching_sha2_password，老版本 JDBC 驱动（5.1.x）直接报 `Public Key Retrieval is not allowed`，必须升级驱动或改回 mysql_native_password；8.0 默认 utf8mb4、默认 sql_mode 含 ONLY_FULL_GROUP_BY，老应用写法的 GROUP BY 可能直接报错——升级前用 `SELECT @@sql_mode` 对比、在测试环境跑全量接口回归。通用项必须显式处理：①字符集统一 utf8mb4/utf8mb4_unicode_ci，迁移后用含 emoji 和生僻字（如"𠮷"）的数据做乱码验证；②时区：数据库 `time_zone='+08:00'`、JDBC 连接串加 `serverTimezone=Asia/Shanghai`，否则 TIMESTAMP 显示偏差 8 小时；③主键：Oracle 的 SEQUENCE+触发器迁移后要换成 AUTO_INCREMENT 并确认自增值从当前 MAX(id) 续起，我在迁移中遇到过目标表已有残留数据导致自增值回退、插入冲突的真实事故——所以"迁移前清空目标表或锁定自增值"要写进操作手册。最后，异构迁移务必全表校验（行数+关键字段抽样校验和）+ 核心交易接口回归，数据差异必须"零容忍"才放行。

**延伸考点：** MySQL 5.7 升 8.0 时，binlog 格式、undo 表空间、`utf8` 与 `utf8mb4` 的实际差异怎么影响迁移方案？主从复制版本跨大版本升级的先后顺序是什么？

### Q9. 回退方案怎么设计：触发条件、回退流程、数据回退怎么保证一致？

**问题：** 你们核心订单系统已通过双写过渡到云上，但业务方要求必须有"回退到本地机房"的方案。回退的触发条件是什么？回退流程怎么设计？回退后数据一致性如何保障？

**期望加分项：**
- 触发条件明确可执行：如可用性（云上错误率 >5% 持续 15 分钟）、性能（P99 延迟超基线 2 倍）、数据（校验不一致超过阈值）、安全事件——且写死为"谁有权按下回退键"
- 回退流程分阶段：流量回切（DNS/网关回切本地）→ 应用回退（镜像/制品回滚）→ 数据回退（增量同步方向反转），每个阶段有验证点
- 数据回退一致性设计：双写期以旧库为准、云上数据是"增量"而非"唯一源"，回退时把云上增量同步回本地、幂等回放、冲突以本地为准
- 强调"回退演练"与可逆性：回退不是灾难场景的临时动作，而是演练过的常规操作，可逆（切回去还能再切回来）
- 保留窗口：云上资源保留期（如 30 天）、binlog/快照保留策略支撑数据对账
- 有时间预算：回退总耗时（如 30 分钟）有预估，不把回退设计成"无限期修复现场"

**减分项：**
- 只有"出问题就切回去"一句口号，无触发阈值、无流程、无负责人
- 回退不看数据一致性，回退后业务数据两头不对账
- 没有演练过回退，紧急时刻第一次执行
- 回退后云上资源立刻释放，想再上去要重新迁移
- 把回退和"放弃迁移"混为一谈，没有"切回-修复-再切上"的循环能力

**解答：**

回退方案的本质是"降低切换的可逆成本"，设计分四块。第一块触发条件要写成可观测的数字而不是感觉：例如云上 API 5xx 错误率 >5% 持续 15 分钟、核心接口 P99 超过本地基线 2 倍且持续 10 分钟、数据校验不一致条数超过阈值、或安全事件（如密钥泄露）——每条都要有监控告警支撑，并且明确"回退决策人"（通常 1-2 人，避免现场开会 30 分钟没人敢按）。第二块回退流程按"先流量后数据"分阶段：①流量回切——网关/DNS/GTM 把读流量切回本地，观察本地指标；②应用回退——云上应用保留但不接流量，本地保留割接前的制品版本可一键回滚；③数据回退——双写期若本地旧库是权威，把云上双写期间新增的数据增量同步回本地（DTS 反向任务或应用对账任务幂等回放），冲突策略以本地为准，同步完成后再校验行数与金额合计。第三块一致性：双写方案从设计上就要保证"本地库始终是完整数据源"，云上只承载增量双写流量——这样回退=反方向同步一次，而不是"找谁丢了数据"。第四块可逆性与演练：回退必须演练过至少一次（我在迁移计划里固定排"T-1 回退演练"），并验证"切回后能再切上去"（云上资源保留 30 天、数据库快照保留，避免回退=永久放弃）。最后给回退时间预算：熟练团队流量回切 10 分钟内完成、数据回退视增量量级 30 分钟到数小时——把预算写进方案，让业务方对"最坏情况"有预期，而不是承诺"回退就是点一下"。

**延伸考点：** 双写期回退时，云上已产生的新数据（本地没有的）怎么处理？回退与"继续修复"的分界点怎么定？

### Q10. 迁移验证与验收：怎么证明"迁移成功"，验收标准怎么写才不是走过场？

**问题：** 你们完成了一个核心系统的上云割接。业务方要求出一份"迁移验收报告"。验证要覆盖哪些维度？每个维度用什么手段、什么量化标准？验收不通过怎么办？

**期望加分项：**
- 覆盖四类验证：功能验证（核心链路冒烟+全量回归）、性能验证（对比基线：P99/吞吐/TPS）、数据一致性验证（行数/校验和/抽样比对）、可用性验证（健康检查/故障注入/切换演练）
- 有明确量化标准：如"核心接口 P99 ≤ 本地基线 1.2 倍、错误率 ≤ 0.1%、数据校验差异 0、4 小时压测无内存泄漏"
- 验证有"基线"意识：迁移前先采集本地基线，对比才有意义；性能对比要考虑流量差异（同期对比、压测替代）
- 验收标准有分级：P0（数据一致性、核心功能）必须全过，P1（性能指标）允许限期整改，不是一票否决一切
- 验收流程化：验收清单（checklist）、验收负责人、遗留问题清单（含责任人/期限）、上线观察期
- 覆盖割接后观察期：如 72 小时密切观察（错误率、延迟、资源水位），而非验收完就散场

**减分项：**
- 只做"能登录、能下单"的功能冒烟就宣布成功
- 不做基线对比，性能好还是坏没有参照系
- 验收标准一票否决、没有分级，P1 问题卡死整个上线
- 没有数据一致性验证，拍胸脯说"数据肯定没问题"
- 验收报告写"一切正常"，无数据、无截图、无问题清单，后续无从复盘

**解答：**

验收的本质是"用数据证明迁移没有改变业务行为"。我按四维来组织：①功能验证：核心链路冒烟（登录、下单、支付、对账）必须在割接窗口内跑完，全量回归用例在割接后 24 小时内跑完（自动化用例优先，手工回归按 P0/P1 分级）；②性能验证：关键在"基线对比"——迁移前就用压测工具（JMeter/ab）在本地采集核心接口的 TPS、P99、错误率基线，上云后用同一套脚本同流量重压，标准写死：TPS 不低于本地 90%、P99 不超过本地 1.2 倍、错误率 ≤0.1%、4 小时压测无内存泄漏与连接池耗尽；要注意对比的坑：生产流量有季节性（月底对账高峰），拿迁移周和普通周比不公平，要同期对比或直接压测替代；③数据一致性验证：行数比对全表、核心字段抽样校验和比对、当日交易金额合计对账，差异必须为 0，发现差异先查增量链路而不是先宣布失败；④可用性验证：健康检查、实例故障演练（杀一台看是否自动恢复）、多可用区切换演练。验收标准要分级：P0 项（数据一致性、核心功能、安全）必须全过否则回退；P1 项（性能余量不足、非核心功能小缺陷）允许记录为遗留问题并限 2 周整改，不能一票否决整个上线——否则验收永远过不了。产出物是一份带数据的验收报告：每项验证的用例、命令、结果截图、与基线的对比数字、遗留问题清单（责任人+期限），外加 72 小时观察期的监控截图（错误率、P99、CPU/内存/连接数水位）。我见过最差的验收是"一切正常"四个字，没有任何数字支撑——那样的验收没法为后续迭代提供任何依据。

**延伸考点：** 压测时怎么保证测试流量不污染生产数据（影子表/压测标记）？验收发现 P99 超基线，你怎么定位是网络、规格还是应用配置的问题？

### Q11. 分批迁移：200 个应用不可能一次割接完，批次怎么划、顺序怎么排、渐进迁移怎么做？

**问题：** 你们有 200 个微服务和 30 个独立系统要上云，不可能一次性割接。请给出批次划分的原则、每批的优先级排序逻辑，以及"分批迁移"过程中如何保证系统间调用不被迁移撕裂。

**期望加分项：**
- 批次划分有依据：按"业务域/依赖关系/风险等级"分组，或按 6R 结果分（先 Rehost 快赢、后 Refactor），而不是按部门或随机
- 优先级排序有量化：低风险高收益优先（无状态、无外部依赖、独立系统），核心链路后置且带演练
- 处理跨机房调用：分批期间本地与云上并存，跨系统调用走 VPN/专线打通，网络延迟与带宽要纳入每批评估
- 依赖方向约束：被依赖方（数据/中间件）先迁或后迁要有规则——如"数据库先迁、消费者后迁"或相反，避免流量黑洞
- 渐进迁移有过渡机制：灰度流量、双写、两地运行观察期（如 2 周稳定再迁下一批）
- 有批次间学习机制：每批做复盘并沉淀 checkbook（操作手册），后批复用前批经验，批次节奏可控（如每周一批）

**减分项：**
- 按"哪个部门催得急"排批次，没有技术依据
- 忽略分批期间跨机房调用的网络时延和带宽成本
- 把有依赖的系统拆到不同批次却不管调用链（如 B 依赖 A，A 迁走了 B 还连本地）
- 每批都当第一次做，没有复用前批的经验和工具
- 没有观察期，批接批地割接，出问题无法定位是哪一批引入的

**解答：**

分批迁移的目标是"把一次大爆炸变成 N 次小可控变更"，核心是三件事：分组、排序、过渡机制。分组：我按"业务域 + 依赖边界"切，把同一业务域、互相强依赖的服务放一批（比如订单域含订单服务+订单库+订单 MQ），避免"服务迁走了数据库还在本地"这种撕裂；同时按风险分：无状态、无外部依赖、独立系统归"快赢批"，核心交易链路归"重批"（最后迁且必须演练）。排序的量化逻辑是"风险低、收益高、依赖被依赖最少"优先——典型顺序是：监控/日志/基础组件 → 内部工具与报表 → 无状态应用 → 有状态中间件 → 数据库 → 核心交易链路。分批期间的"撕裂"问题用网络与调用方向解决：本地-云上之间必须提前打通 VPN/专线，跨机房调用的 RTT 会从 0.5ms 涨到 20-50ms，每批迁移前要评估受影响调用的超时设置是否还够（我遇到过某服务超时 2s、跨机房调用峰值 3s 导致的雪崩）；方向规则上，我倾向"先迁被依赖方（数据、基础服务），再迁依赖方（应用）"，这样应用迁过来时数据已在云上，不需要长时间跨机房读写——但数据库先迁意味着迁移期间本地应用要跨机房访问云上库，所以数据库批次必须配 DTS 双写/延迟监控。每批的节奏：割接 → 观察 1-2 周（指标稳定、无回退）→ 复盘 → 下一批，同时维护一份"迁移 checkbook"把第一批踩过的坑（比如安全组遗漏端口、DNS 缓存）写成标准操作手册，后面批次直接照着执行，批次间隔也可以从两周缩短到一周。最后，每批都要有独立的验收和回退，因为"分批"最大的风险是出了问题不知道是哪一批引入的——批次边界清晰、可回退，是渐进迁移成立的前提。

**延伸考点：** 如果订单服务先迁了、但订单报表系统（依赖订单库）还在本地，跨机房查库延迟高怎么办？批次间数据库 DTS 同步一直开着，成本怎么控制？

### Q12. 上云不是终点：迁完后架构调整、资源与成本优化、遗留问题治理怎么做？

**问题：** 你们核心系统已全部迁上云并稳定运行 3 个月。老板要求"迁移的第二阶段"：释放云的价值。你会从架构、资源、成本三个维度分别做什么？哪些"迁移期妥协"是现在要还的债？

**期望加分项：**
- 架构优化有主线：从"本地架构照搬"走向云原生——无状态化、弹性伸缩（HPA/自动扩缩容）、多可用区高可用、托管服务替换自建（RDS/Kafka/ES 托管化）
- 资源优化有数据依据：基于迁移后真实监控数据缩容/升配（如按峰值 90% 用量的 4C8G 实际只用到 20%，降配省钱），闲置资源清单治理
- 成本优化有手段：预留实例/节省计划（Savings Plans）、按量转包年包月、存储生命周期（冷热分层）、成本标签与预算告警
- 主动还"迁移期债务"：迁移时为保证成功而做的妥协（双写代码、临时镜像搬的旧系统、超配规格、临时带宽包）逐一登记并排期清理
- 有量化成效：如优化后月度成本下降 X%、部署频率提升、弹性伸缩在流量高峰自动扩容 N 台
- 建立持续机制：FinOps 周报、资源回收流程、架构评审，而不是一次性优化

**减分项：**
- 认为"迁完就结束"，没有第二阶段规划
- 优化不做数据支撑，凭感觉缩配或升配
- 忽视迁移期的临时妥协（双写开关、临时带宽、手动部署脚本），债越欠越多
- 只谈省钱不谈架构演进，或反过来只谈架构不谈成本
- 优化动作一次性，没有机制保证不再反弹

**解答：**

迁移完成只是"上云"的 30%，剩下 70% 是把架构从"搬过来的本地系统"变成"长在云上的系统"。我按三条线推进：第一架构线：先做无状态化与弹性——应用接入自动扩缩容（K8s HPA 或云上弹性伸缩组），用真实的峰值监控数据配伸缩策略（如 CPU >70% 持续 5 分钟扩容、低峰缩到最小副本），然后多可用区部署消除单点（RDS 主备跨 AZ、应用双 AZ 分布），最后逐步把迁移期自建的中间件替换为托管服务（自建 Kafka/ES 换托管版，省运维人效）。第二资源线：给每台云主机拉 30 天监控报告，按"峰值使用率"重定规格——我做过一次真实治理：120 台机器里 35 台 CPU 平均使用率 <10%，降到一半规格，月成本直降 18%；同时清理僵尸资源（未绑定的 EIP、过期快照、无人使用的测试实例），建立"资源回收"例会。第三成本线：把按量计费的长稳实例转包年包月或买节省计划（通常能省 20-40%），对象存储配生命周期（30 天转低频、90 天归档删除），打成本标签（项目/环境/负责人）并设预算告警，出 FinOps 周报让每个业务方看到自己账上的成本变化。别忘了"迁移期债务"清单：双写代码开关、临时带宽包、镜像搬过来的旧系统、手动运维脚本——逐一排期清理，迁移时"为了成功做的妥协"如果不还，会成为永远的历史包袱。量化验收：优化后月度成本下降 25%、核心应用弹性扩容生效（双 11 自动扩到 3 倍副本）、自建中间件托管化后告警处理人效提升——这些数字写进第二阶段的验收报告。

**延伸考点：** 弹性伸缩的"缩容下限"怎么定才不影响可用性？成本优化和性能保障冲突（比如降配后偶发 GC 长暂停）时怎么取舍？

### Q13. 时区、字符集、文件路径、网络延迟、隐藏依赖——迁移现场最常见的"隐形坑"有哪些？

**问题：** 你们在一次迁移后遇到：①日志时间比业务时间早 8 小时；②导出报表里中文变乱码；③定时任务凌晨没跑；④某应用访问本地文件失败。这些典型的"隐形坑"根因分别是什么？迁移前怎么系统性排查？

**期望加分项：**
- 逐个给根因：时区（OS/DB/JVM/应用四层时区不一致）、字符集（源库 latin1 目标库 utf8mb4、文件编码、连接串 charset 参数）、定时任务（crontab 时区、容器无 cron、跨机房时钟）、文件路径（本地盘 vs 挂载盘、权限、Windows/Linux 分隔符）
- 有系统性排查清单：把"时区/字符集/路径/依赖"做成迁移 checklist 的固定项，评估阶段逐项核对
- 讲边界条件：夏令时、四字节 emoji、含空格/中文/特殊字符的文件名、超长路径（Windows 260 字符限制）
- 谈网络延迟的隐形影响：跨机房 RTT 变大导致超时、批量任务变慢、连接池占满，这类问题迁移前要评估
- 依赖不可用的典型场景：License 服务器、内网 DNS、邮件/短信网关、NTP 源、第三方 IP 白名单在云上不通
- 有线上排查经验佐证：如"时间差 8 小时"用 `date`、`SELECT NOW()`、JVM `-Duser.timezone` 三层对照定位

**减分项：**
- 只会列现象不会定位根因，或把所有问题都归到"配置问题"一句话
- 没有系统性 checklist，靠出问题才排查
- 忽略文件名/路径这类"低技术含量"但高发的问题（中文文件名在 Linux 的编码差异）
- 不考虑跨机房网络延迟对应用超时和连接池的影响
- 依赖项（License/白名单/内网 DNS）不做迁移前验证

**解答：**

这些坑的共性是"迁移前后环境差异被低估"，逐个拆根因：①时间早 8 小时——三层时区不一致：OS 的 `/etc/localtime`、JVM 启动参数 `-Duser.timezone`、数据库 `time_zone` 变量和 JDBC 连接串 `serverTimezone`，任何一层没配齐就会出现偏移，排查用 `date`、`java` 打印 TimeZone、`SELECT @@time_zone, NOW()` 三层对照；更隐蔽的是"存储层用 UTC、展示层用本地时区"的正确架构，很多人不懂反而"纠正"错。②乱码——源库字符集是 latin1（老库常见）、目标库 utf8mb4，DTS 转换或导出导入时 charset 参数没对齐；文件层面的编码（GBK 导出文件在 UTF-8 环境打开）同样高发，迁移前要跑"特殊字符样本验证"：中文、emoji、全角符号、生僻字各几条。③定时任务没跑——crontab 用的时区和容器内时区不一致，或者容器化后 cron 根本没装（容器里没有 cron 服务）、K8s 里定时任务要改用 CronJob；另外跨机房后服务器时钟漂移（没配 NTP）也会导致任务提前/延后。④文件路径——应用写死本地路径如 `/data/app`，迁移后盘符/挂载点变了；Windows 路径分隔符 `\` 与 Linux `/` 的差异、中文文件名在两端的编码差异、超长路径——这些都是"评估清单里必须有的一行"。系统性解法是把四类坑做成迁移 checklist 固定项：评估阶段逐项核对时区配置、字符集样本、路径/权限、外部依赖（License 服务器、IP 白名单、内网 DNS、邮件网关）并逐项打勾，割接前做一次"环境体检"脚本自动比对（diff 关键配置）。我的一次真实事故：报表系统依赖的 License 服务器只在本地网段放行了源 IP，上云后应用连不上 License 直接宕机——这种"隐藏依赖"必须在评估期用端口扫描+进程网络连接清单找出来，而不是割接后靠告警发现。

**延伸考点：** 怎么判断"时间偏差"是 OS/JVM/DB 哪一层的问题？容器化后 crontab 任务的最佳迁移路径是什么（CronJob vs 独立定时服务）？

### Q14. 迁移项目管理：上百号人、跨团队、数月周期，怎么保证不失控？

**问题：** 你们组织了一次涉及 30 个业务团队、周期 6 个月、预计上百次割接的云迁移战役。作为迁移 PMO，你会怎么搭团队分工、定时间线、管风险、做沟通与变更管理，让迁移不变成"混乱的持久战"？

**期望加分项：**
- 组织分工清晰：PMO（全局节奏）+ 迁移技术组（工具/网络/数据平台）+ 各业务域迁移 Owner（每域一人背结果）+ 基础设施组（网络/账号/配额），角色有明确职责与接口人
- 时间线管理有节奏：里程碑划分（评估→试点→批次迁移→收尾）、每批固定节奏（W 制定计划、W+1 预演、W+2 割接）、用计划表（如甘特图/迁移日历）管理
- 风险清单机制：风险登记表（风险/概率/影响/缓解/负责人）、每周 review、红黄绿状态；高危风险有预案（如专线延期、工具失败）
- 变更管理：割接变更走变更流程（预案+审批+回退），冻结期管理（割接窗口前后禁止业务大版本发布）
- 沟通机制固定：每日站会（割接周）、每周周报（批次进度/风险/依赖阻塞）、割接指挥群（红蓝军角色：操作者/检查者/决策者）
- 有指标度量迁移进度：系统迁移数、批次成功率、回退次数、累计停机时长，让管理层看到数字而非 PPT

**减分项：**
- 只有技术方案没有组织保障，各团队各自为战
- 时间线是一张"理想图"，没有 buffer、没有依赖管理，延期一次全线崩
- 风险只登记不上会 review，风险清单形同虚设
- 变更管理缺失，割接窗口撞上业务发版，事故责任说不清
- 没有进度指标，管理层只能靠感觉判断迁移是否健康

**解答：**

迁移战役失败多半不是技术而是组织，我按"组织、节奏、风险、变更、沟通"五件事搭 PMO。组织上避免"全看一个人"：设迁移 PMO 管全局节奏与资源协调；迁移技术组管工具平台（SMC/DTS/网络）和通用流程；每个业务域设一个"迁移 Owner"——他对该域割接成败负全责（域内排期、演练、验收、回退决策）；基础设施组管账号、配额、网络、安全组。节奏上按里程碑 + 固定批次节奏推进：评估期 1 个月 → 试点（2-3 个系统走通全流程）→ 批次迁移（每批 2 周：W1 排期与预检、W2 演练+割接+观察）→ 收尾（遗留问题与债务清理）；关键路径要标出来（如专线、账号体系、DTS 平台能力），延期只允许延非关键路径。风险管理用一张风险登记表：每行"风险/概率/影响/缓解措施/负责人/状态（红黄绿）"，每周 PMO 例会逐行 review，红项必须当场出预案——例如专线延期 30 天的预案是"VPN 带宽升级+分批压缩"，DTS 全量慢的预案是"分库拆分迁移"。变更管理是防事故的关键：所有割接走变更流程（方案+演练记录+审批+回退预案），割接窗口 72 小时内冻结相关业务的版本发布，防止"迁移撞发版"事故责任不清。沟通机制：割接周每日 15 分钟站会，每周发迁移周报（本批进度、下批预告、风险状态），每次割接建指挥群并明确三个角色——操作者（执行操作）、检查者（核对结果）、决策者（唯一能说"回退"的人），避免现场多头指挥。最后给管理层一组数字：已迁系统数/总数、批次成功率、回退次数、累计额外停机时长、剩余风险数——迁移健康度用数字说，而不是"感觉挺顺利"。

**延伸考点：** 割接窗口内"操作者、检查者、决策者"三角色具体怎么配合？如果某批次演练连续两次失败，你是推迟割接还是带病割接，依据是什么？

### Q15. 云上性能和本地比反而差了，怎么定位归因？迁移前怎么做基准测试设计？

**问题：** 你们把一个核心系统迁上云后，业务反馈接口变慢，压测显示 P99 从本地的 200ms 涨到 600ms。怎么设计"迁移前后对比的基准测试"？如果确认性能劣化，定位问题的排查路径是什么？

**期望加分项：**
- 基准测试设计有对比公平性：同压测脚本、同并发、同数据量（最好同数据快照）、同业务场景，压测环境尽量一致；生产对比要同期/同流量
- 基准测试覆盖分层：应用层（TPS/P99/错误率）、数据层（DB 延迟/QPS）、网络层（RTT/丢包/带宽），每层都有指标
- 性能归因有路径：先看网络（跨机房 RTT、公网 vs 专线）→ 再看规格（CPU 型号差异、突发性能实例 t 系列被限流）→ 再看配置（连接池、JVM 堆、DB 参数、实例规格 IOPS）→ 最后看应用
- 提到云特有的坑：共享型实例 CPU 突发受限（如 AWS t3/阿里云 t6 的 CPU 积分）、ESSD 的 IOPS/突发能力、网络 QoS、相邻租户影响（少见但要会排除）
- 用工具与数据：压测（JMeter/ab/wrk）、逐层 trace（APM 链路）、慢 SQL 分析、`top`/`vmstat` 观察资源瓶颈
- 有优化动作：升配、换机型、调参（连接池/超时/JVM）、CDN/就近接入、数据库读写分离

**减分项：**
- 迁移前根本没做基准测试，没有对比基线，只能"凭感觉说变慢"
- 对比不公平：压测流量、数据量、网络路径不一致，结论没意义
- 归因靠猜，不按"网络→规格→配置→应用"的分层排查
- 不懂云机型差异（突发性能实例、不同代 CPU），一上来就甩锅给"云不行"
- 不测数据层，只盯着应用层指标，DB 慢查询才是根因却没发现

**解答：**

先纠正一个常见错误：很多团队"迁移后才想起要对比"，此时已经没有本地的基准了。正确的做法是迁移前就建立基线——用同一套压测脚本（JMeter/wrk，固定并发、时长、场景）分别在本地和云上压同一业务，数据量尽量一致（推荐用同一份脱敏数据快照），网络路径按真实访问链路模拟；生产环境对比则必须同期（如与去年同月同日同时段比）或同流量（同一批用户行为）。指标要分三层采集：应用层 TPS/P99/错误率、数据层 DB QPS/慢查询/连接池、网络层 RTT/丢包/带宽，每层独立对比才能定位。如果确实劣化，按"网络→规格→配置→应用"顺序排查：第一步看网络——如果是跨机房调用，RTT 从 0.5ms 变 20ms 是物理事实，重点看应用超时设置是否受得了，公网链路再叠加丢包；第二步看规格——最常见的坑是买了突发性能实例（AWS t 系列/阿里云 t6），它用 CPU 积分换低价，持续高负载时被限流到基础频率，压测 P99 必然劣化，查 `t3` 的 CPU 积分消耗曲线或直接换通用型/计算型；同时注意同规格不同代的 CPU 性能差异（老 xeon vs 新 epyc）和 ESSD 的 IOPS 上限（云盘 IOPS 和容量绑定，小容量盘 IOPS 很低）；第三步看配置——云环境默认参数可能和本地不一样：连接池大小、JVM 堆、MySQL `innodb_buffer_pool_size`、TCP 参数（比如云上默认 `net.core.somaxconn` 小导致连接排队）；第四步才是应用与慢 SQL，用 APM 逐层看调用链耗时分布。我处理过一个真实案例：P99 劣化 3 倍，排查发现是共享型实例 CPU 积分耗尽，换了计算型实例同代码同规格 P99 直接回到本地水平——这类问题不按路径排查，很容易误判成"云上网络不行"而白花钱升带宽。

**延伸考点：** 压测对比时"同数据量"为什么重要？DB 层劣化怎么区分是实例规格、参数配置还是慢 SQL 引起的？突发性能实例的 CPU 积分机制怎么监控和规避？

### Q16. 迁移成本怎么算才不算糊涂账？一次性迁移成本和长期 TCO 分别怎么估算？

**问题：** 老板要你算一笔账：本地机房 5 年要花多少钱，迁上云 5 年要花多少钱，顺便给出一次性迁移投入。你会怎么建模？哪些成本项最容易被漏掉？

**期望加分项：**
- 本地 TCO 模型完整：硬件采购+折旧、机房（电力/制冷/机柜/带宽）、运维人力、软件许可、备份灾备、容量冗余
- 云上 TCO 模型完整：计算/存储/网络费用（按量 vs 包年）、托管服务费、出网流量费、备份快照、预留实例/节省计划折扣、支持服务费
- 一次性迁移成本列全：评估咨询、工具/软件许可（如迁移工具订阅）、网络（专线一次性建设）、数据迁移流量费、改造人力（人天×单价）、演练与割接加班、双轨运行期的双份资源
- 有对比结论与场景化：按"实际用量利用率"对比而非全价对比，指出云的优势在弹性（峰值计费）与运维人效
- 指出易漏项：出网流量费（云上最大隐形账单）、快照/备份存储费、公网 IP 费、跨区流量费、License 在云上的兼容、支持计划费用
- 有敏感性分析：利用率从 10% 到 80% 时 TCO 曲线的差异（利用率低时云更省，满载时本地可能更省）

**减分项：**
- 只对比"买服务器 vs 租云主机"的裸价，漏掉电力/人力/流量这些大头
- 不算出网流量费，被月底账单吓一跳
- 把一次性迁移成本排除在对比外，决策失真
- 不做利用率敏感性分析，得出"云一定省"或"云一定贵"的武断结论
- 成本模型不更新，凭一份估算管 5 年

**解答：**

成本测算的关键是"口径完整 + 场景化"，我分成三张表来算。第一张"本地 5 年 TCO"：硬件（服务器/存储/网络设备采购+5 年折旧）、机房（机柜、电力按 PUE 折算、制冷、带宽专线月租）、运维人力（按人均成本×专职运维人数折算）、软件许可（数据库/中间件/防病毒）、备份与容灾（另一机房或异地备份成本）、容量冗余（为峰值多买 30-50% 的机器闲置）。第二张"云上 5 年 TCO"：计算（按实际利用率配置+包年或节省计划折扣 20-40%）、存储（按实际容量+生命周期分层，低频/归档成本差 3-10 倍）、网络（出网流量费是最大隐形账单——某 1Gbps 的下载站一个月流量费可能超过主机费，务必按业务实际出网量建模）、托管服务（RDS/ES/Kafka 托管版贵于自建但省人力，要换算人效）、备份快照存储、公网 IP/负载均衡等小项。第三张"一次性迁移投入"：评估与咨询、迁移工具/订阅费用、专线一次性建设费、数据迁移产生的流量与中转存储费、改造人天（按各系统 6R 分级的人天×单价）、演练与割接（每次割接的双份人力、周末加班）、双轨运行期（本地和云上同时跑的双份资源成本）。对比要分场景：真实利用率低于 30% 的系统，云上的弹性优势明显（本地要为峰值买机器闲置，云上按量付费）；利用率持续 70%+ 的重负载系统，云上包年+流量费用可能反超本地——所以结论要写成"哪类资产适合云、哪类保留"，而不是一个总数字。最后做敏感性分析：把利用率、增长曲线、折扣这几个变量各摆 3 档算矩阵，告诉老板"在什么假设下云更省"。模型要每季度更新一次，因为云价目表和你的实际用量都在变，一份 5 年前的估算没有任何决策价值。

**延伸考点：** 出网流量费怎么评估一个业务是否适合上云（比如视频/下载类高带宽业务）？迁移双轨期的成本怎么精确估算和压缩？

### Q17. 混合云过渡期：本地和云上要长期共存，数据怎么同步、流量怎么灰度、风险怎么控？

**问题：** 由于合规和分批迁移的需要，你们的系统要"本地+云上"并行运行至少一年。请设计混合云过渡期的整体方案：数据双向/单向同步怎么做、流量灰度怎么切、长期共存期有哪些特有的风险和治理要求。

**期望加分项：**
- 数据同步方案分层：DB 用 DTS 单向/双向同步（含冲突处理）、对象存储用跨源同步（如 OSS 同步工具/rsync 任务）、缓存/文件用定时同步+校验
- 流量灰度机制：按比例（DNS 权重/网关按用户 ID hash）、按地域/渠道切流，灰度比例与观察指标绑定（如 5%→20%→50%→100%）
- 双向同步的冲突策略明确：单向为主（本地写、云上读）、双向分片（按业务域分写端）比"两边都写同一张表"安全得多
- 长期共存风险识别：网络链路单点（专线故障）、数据一致性漂移（同步延迟/丢单）、两套环境配置漂移（版本不一致）、账号/权限双体系
- 治理手段：同步监控（延迟/失败率告警）、一致性对账任务（定时跑）、配置统一源（GitOps）、双环境发布联动
- 明确退出条件：混合云是过渡态，要定义"何时切完、如何收尾"（如目标业务全部上云后停同步、退本地）

**减分项：**
- 把混合云当"永久的正常态"，没有退出计划
- 双向同步不做冲突设计，两边都写同一张表，数据互相覆盖
- 只做同步不做监控和校验，漂移了没人知道
- 灰度切流没有回切机制，比例切上去发现有问题撤不回来
- 忽视网络单点：专线一断，混合云全瘫

**解答：**

混合云过渡期的设计原则是"本地为主、云上为备 + 渐进灰度 + 明确退出"。数据同步是核心：数据库用 DTS 做"本地→云上"的单向实时同步（业务读大部分还在本地时），云上实例做只读副本供新上云的周边系统读，这样能避免双向写冲突——真需要双向时，务必按业务域分片（订单写本地、营销写云上，各自只有一端写），绝不能让两边写同一张表然后靠"最后写入者胜"；对象存储/文件用跨源同步任务（如 OSS 的数据同步或自建 rsync+校验），缓存类数据走"重建"而非同步（冷数据回源）。流量灰度用网关/DNS 权重分比例：先 5% 读流量切云上副本验证（观察 P99、错误率、数据一致性），稳定后 20%→50%，再切写流量；每个比例档都有"观察期+回切预案"，回切=权重改回+验证，必须在演练里做过。长期共存期特有的风险要逐项治理：①网络单点——专线是混合云的生命线，必须做双链路或 VPN 备线，专线故障要自动/手动切备线且演练过；②一致性漂移——DTS 延迟、失败任务都要有监控告警（延迟 >30s 告警），每天定时跑对账任务比对两边核心表行数与金额，漂移了 24 小时内发现而不是月底发现；③配置漂移——本地和云上两套环境，必须用同一套 IaC/配置源（GitOps），发布走同一流水线，否则半年后两边代码版本差出几个大版本，回退都不可能；④账号权限双体系——统一 SSO 对接两边，避免"本地有权限云上没权限"的日常事故。最后明确退出条件：当某业务域全部流量切到云上且稳定运行 1-2 个月，就停掉它的同步任务、下线本地资源——混合云是过渡态不是目标态，每季度 review 一次"还有哪些系统在双轨、为什么还没切完"，防止它变成没人敢动的永久历史包袱。

**延伸考点：** DTS 双向同步的冲突处理机制（主键冲突策略）具体怎么配置？专线故障演练怎么做才不吓到业务（故障注入的度）？

### Q18. 迁移复盘与改进：迁完 100 个系统，怎么把经验变成团队的资产？

**问题：** 你们完成了一整轮云迁移（100+ 系统），老板要求做迁移复盘并形成可复用的方法论。复盘怎么做才能不流于形式？沉淀哪些东西才是"团队资产"？

**期望加分项：**
- 复盘有结构化方法：分"数据复盘（指标）→ 问题复盘（事件）→ 根因与改进 → 资产沉淀"四层，而不是"大家说说感受"
- 指标度量完整：批次成功率、回退次数与原因、平均割接时长 vs 预估、累计停机时长、返工人天、迁移后 30 天线上问题数
- 问题复盘用事实：每次回退/事故都做 RCA（根因分析），区分技术根因、流程根因、组织根因，改进项落到"人/流程/工具"三类
- 资产沉淀具体：迁移 checkbook（标准操作手册）、风险登记库（常见风险与缓解）、工具脚本库（体检脚本/校验脚本）、模板（迁移方案/验收报告）
- 有改进闭环：复盘输出"改进行动清单"（负责人+期限+验证方式），下轮/下个项目强制复用，防止同类问题再犯
- 经验组织化：把方法论固化成"迁移 SOP/流程文件"或培训，让新人能按文档执行

**减分项：**
- 复盘变成"表扬与自我表扬"的茶话会，没有数据和根因
- 只复盘失败的批次，不分析"侥幸成功的批次"里埋的雷
- 问题分析停留在表面（"沟通不畅""时间不够"），不挖到根因
- 复盘完没有行动项，或行动项没有跟进，明年同样的问题再来一遍
- 经验留在个人脑子里，没有沉淀成文档/工具，人走了经验就没了

**解答：**

复盘的目的是"让下一轮迁移（或新项目）站在这一轮的肩上"，我按四层做。第一层数据复盘：拉全量指标——100 个系统里批次成功率、回退次数（我遇到过 100 批回退 7 次）、每次割接的实际耗时 vs 预估（发现预估普遍乐观 30%）、迁移后 30 天线上问题数（回退后 30 天内由迁移引入的问题才算迁移债）。这些数字先给全貌，再进第二层问题复盘：把每次回退和线上事故逐一做 RCA，用"5 Why"挖到三类根因——技术根因（如 DTS 字符集配置遗漏）、流程根因（如没有预检清单）、组织根因（如业务方没有参与验收）；注意"侥幸成功"的批次也要复盘，很多批次是"踩了坑但被运气救了"，把那个坑找出来记录。第三层改进与闭环：输出一张改进行动清单，每项有负责人、期限、验证方式，例如"DTS 任务建前强制跑预检查"（改进工具）"所有批次割接前 24h 必须完成演练"（改进流程）"验收必须包含数据一致性比对项"（改进模板）；改进项要在下一次割接中强制复用并验证有效，否则复盘就是 PPT。第四层资产沉淀，这是最容易被忽略的：把经验变成三类可复用物——①迁移 checkbook：标准操作手册（从评估到验收的每一步操作、命令、验证点）；②风险登记库：本轮遇到的风险+缓解措施，下一轮迁移直接导入作为初始风险清单（我见过第二轮迁移把第一轮 80% 的坑提前堵住）；③工具脚本库：环境体检脚本、数据校验脚本、DNS 切换脚本，统一放仓库管理。最后把这些固化成公司级迁移 SOP 并做一次全员培训，让"迁移"从"靠老员工的经验"变成"按文档执行的标准流程"——这才是迁移带给组织的真正资产。

**延伸考点：** 复盘发现 80% 的回退都发生在"没有预检就割接"的批次，你怎么用机制而不是靠自觉保证不再发生？成功率和"割接速度"之间怎么平衡？

### Q19. 跨云迁移：AWS 迁到阿里云（或反之），和本地机房上云比，多了哪些坑？

**问题：** 你们要把 AWS 上运行了 3 年的一套业务（EC2 + RDS + S3 + Kinesis + IAM）迁到阿里云（ECS + RDS + OSS + 自建 Kafka + RAM）。跨云迁移和"本地机房上云"相比，流程和工具有什么差异？哪些环节最容易出问题？

**期望加分项：**
- 工具差异清楚：跨云没有"源端 agent 直迁"的官方通道（MGN/SMC 都是迁到自家云），通常走"导出数据→中转→导入"或第三方工具（如 CloudEndure 已并入 AWS MGN、双写重建、AWS 的 Application Migration 不能迁到阿里云）
- 数据迁移路径：S3→OSS 用 OSS 的跨云同步工具或 rclone/aws s3 sync，RDS→RDS 用 DTS 跨云（DTS 支持公网/VPN 源）或 mysqldump+binlog，注意跨云网络要自己打通
- 云生态差异是主坑：IAM→RAM 的权限模型差异、Kinesis→Kafka 的消费语义差异、CloudWatch→云监控的告警迁移、VPC 安全组规则重写
- 服务映射表：迁移前先出一张"AWS 服务 → 阿里云服务"映射表并逐项验证兼容性（如 Lambda→FC、SQS→MNS、Aurora→PolarDB），没有等价物（如 S3 的强一致 vs OSS 一致模型差异）要标注
- 账号/成本/合规：新账号体系、账单体系重构、跨云期间数据出入境合规
- 停机窗口更大：跨云网络打通和增量同步更重，双写或重建方案要更早设计

**减分项：**
- 以为 MGN/SMC 能"跨云直接迁"，对工具边界没概念
- 只迁数据不迁生态，权限/告警/日志体系全断
- 没做服务映射，Lambda 迁 FC 时发现函数代码全是 boto3 依赖
- 忽视跨云数据迁移的网络带宽与费用（跨云流量贵、跨境合规）
- 把跨云迁移当成"本地上云"的复制粘贴，流程和节奏完全照搬

**解答：**

跨云迁移的第一认知是"没有源端 agent 直迁通道"：AWS MGN 只能迁到 AWS，阿里云 SMC 只能迁到阿里云——跨云必须走"导出→中转→导入"或"重建"，所以工具链路完全不同：数据库用 DTS（阿里云 DTS 支持公网/VPN 把 AWS RDS 作为源）或 mysqldump+binlog 自己搭增量；对象存储用 OSS 的跨云同步（OSS 有从 AWS S3 一键迁移的工具）或 rclone `rclone sync s3:bucket oss:bucket`；Kinesis 没有等价物，得用自建 Kafka 重建并重写消费者。第二认知是"迁的不只是数据，是整个云生态"：IAM→RAM 权限模型（策略语法不同，boto3 里的 `arn` 全要改）、CloudWatch 告警→云监控（监控项和表达式重写）、S3 事件→OSS 事件通知、安全组规则逐条重写——我建议第一步就产出"服务映射表"：AWS 的每个服务对应阿里云哪个服务、能力是否等价、代码/配置要改多少，不等价的服务（如 Kinesis 的 shard 语义 vs Kafka 的 partition）要单独立项重写。第三认知是网络与数据迁移成本更高：跨云之间没有专线，靠公网或 VPN，RTT 和带宽都受限，全量 2TB 的数据库跨云同步时间和费用都要重新估算（跨云流量费比本地上云贵，跨境还要考虑合规与数据出境审批）。第四是账号与运维体系重构：新账号、新账单、新监控、新 CI/CD 都要迁移或重建，这块最容易被低估成"和业务一起搬过去就行"。执行节奏上建议"应用重建优先、数据同步其次"：先把无状态应用用 IaC 在阿里云重建并走通 CI/CD（顺便完成容器化），再切数据库同步（DTS 全量+增量+短停切换），最后迁存储与消息——每一块都单独验收。真实教训：某团队按本地上云的节奏只排了 6 周，结果 IAM 权限和 Kinesis 消费者改造就花了 3 周，跨云迁移的项目计划至少要比同规模本地上云多排 30-50% 的时间。

**延伸考点：** Kinesis→Kafka 迁移时，消费位点（shard 序列号 vs offset）怎么对齐才能不丢不重？跨云同步期间两边数据都是活的，主从判定和切换怎么设计？

### Q20. 上云成功的标准是什么？除了"系统跑在云上"，还要交付什么？

**问题：** 迁移项目全部完成后，你的团队向管理层汇报"上云成功"。但老板问：怎么证明成功？除了"系统在云上跑"，业务指标、性能可用性、成本、团队能力这些维度分别用什么标准衡量？什么情况算"上云失败"？

**期望加分项：**
- 成功标准多维化：业务指标（无重大业务中断、功能无回退）、性能/可用性（可用性 ≥ 迁移前、P99 不劣化、SLA 达成）、成本（TCO 不超预算、单位成本下降）、团队能力（掌握云平台运维、CI/CD、成本优化技能）
- 量化可验证：如"迁移后 6 个月可用性 99.95% 且无 P0 事故""P99 ≤ 本地基线 1.2 倍""月度成本 ≤ 预算 1.1 倍且 12 个月内下降 15%""团队可独立完成云上发布与扩缩容"
- 有"失败"的明确定义：持续返工（多次回退）、成本失控、可用性劣化、能力未转移（云上运维仍依赖外部顾问）——敢于定义失败才算真懂成功
- 区分"迁移完成"与"上云成功"：迁移完成=系统搬完，上云成功=业务价值兑现（弹性、成本、效率确实变好）
- 团队能力转移有验收：内部团队能独立发布、扩容、排障（故障演练中团队独立处理），不依赖原厂商/外部支持
- 有长期观察与持续改进：成功不是验收那一刻，而是 6-12 个月的运营结果，有持续优化机制

**减分项：**
- 把"系统全部迁完、验收通过"等同于"上云成功"，只讲过程不讲结果
- 成功标准全是定性描述（"运行稳定""成本可控"），无法验证
- 只看技术指标不看业务指标（迁移后业务增长受限、新功能交付变慢也算不上成功）
- 回避"失败"的定义，或把失败只归因于外部
- 团队能力没有转移，云上出问题还要原厂商/外部人员处理

**解答：**

"上云成功"和"迁移完成"是两件事：迁移完成是"系统在云上跑起来了"，上云成功是"云的承诺兑现了"——弹性、成本、效率确实带来业务价值。我建议用四个维度打分，每个维度都是可验证的数字：①业务指标：迁移后 6 个月内无因迁移导致的 P0/P1 业务事故；业务功能完整无回退；新功能交付周期不慢于迁移前（如果迁完上不了新功能，迁移就是负资产）。②性能与可用性：可用性 ≥ 迁移前水平（本地 99.9% 云上至少 99.9%），核心接口 P99 ≤ 本地基线 1.2 倍，SLA 兜底（云厂商 SLA + 自身架构冗余），故障恢复时间（MTTR）比本地更快（这是云的隐性收益，要量化出来）。③成本：迁移后月度成本在预算的 ±10% 内，且 12 个月内有持续下降趋势（弹性/节省计划/生命周期生效），单位请求成本或单用户成本有下降——成本不是"省了多少"而是"花得值不值"。④团队能力转移：这是最容易被忽略的一条——迁移后团队能独立完成云上发布、扩容、缩容、故障定位与回滚（用一次"故障演练"来验收：拔掉一台实例/注入故障，团队能否独立按 SOP 处理）；云上架构决策（选型、容量、成本）由内部团队而非外部顾问主导；掌握成本看板、预算告警这些 FinOps 基础动作。同时要敢于定义"失败"：持续返工（某核心系统回退超过 2 次）、成本失控（超预算 50% 以上且无优化行动）、可用性劣化、以及"人没学会"（一年后云上运维仍依赖原厂商驻场）——定义失败不是唱衰，而是让成功标准可检验。最后，成功的判定不是验收当天，而是 6-12 个月的运营结果，每季度 review 一次这四维指标，把"上云成功"从一次汇报变成持续运营的标尺。

**延伸考点：** "团队能力转移"具体怎么验收（故障演练的通过标准是什么）？如果上云后成本比本地高但弹性收益明显，这个"成功"怎么向管理层呈现？
