# 通用 · Web 与 HTTP（面试题库）

本文件考察 Web 基础与 HTTP 的真实工程实践能力，而非八股背诵，适用于前后端所有岗位。重点覆盖：HTTP 语义与状态码在真实场景中的排查定位（缓存、重定向、鉴权、网关错误）、HTTPS/TLS 与 DNS 的链路优化、Cookie/Session/Token 会话安全、跨域与长连接（CORS、WebSocket、SSE）、连接并发与协议演进（HTTP/1.1 → 2 → 3）、CDN/负载均衡/流式响应等基础设施调优，以及接口设计（幂等、分页、版本化）与传输安全（XSS/CSRF）。所有问题均来自一线生产场景，期望候选人用真实项目经验、抓包/命令佐证与取舍判断作答。

### Q1. 静态资源有时返回 304、有时返回 200 (from disk cache)，缓存为什么不稳定？

**问题：** 页面的 JS/CSS 资源在 DevTools 里一会儿显示 `304 Not Modified`、一会儿显示 `200 (from disk cache)`，同一个资源表现还不一样。请解释这两种命中的本质区别，并给出排查思路。

**期望加分项：**
- 能讲清强缓存（命中不发请求，直接走 memory/disk cache）与协商缓存（仍发一次请求，服务器回 304）的机制差异
- 能说清 `200 from memory cache` 与 `200 from disk cache` 的区别（会话内短生命周期 vs 落盘持久）
- 能给出实操排查手段：DevTools Network 面板看请求是否发出、Response Headers 中 `Cache-Control`/`Expires`/`ETag`/`Last-Modified` 的取值
- 能主动解释影响表现的因素：刷新方式（普通刷新会重新协商、强刷跳过缓存）、资源大小、缓存淘汰
- 能指出后端配置问题，如未配 `Cache-Control` 导致每次都走协商、`max-age` 配置过短

**减分项：**
- 只背"强缓存 vs 协商缓存"定义，说不清 DevTools 里两者表现差异
- 以为 304 也是从本地缓存的，讲不清"304 仍有一次网络往返"
- 忽略刷新行为、缓存淘汰等变量，把现象归于"缓存不稳定"就结束了
- 说不清 `ETag` 与 `Last-Modified` 的优先级与各自缺陷

**解答：**

先给判断：这不是"缓存不稳定"，而是"强缓存未命中、落到协商缓存"的正常表现，两者是不同层级的缓存策略。命中**强缓存**（`Cache-Control: max-age` / `Expires` 未过期）时，浏览器直接从本地读取，**不发任何请求**，DevTools 显示 `200 (from disk cache)` 或 `(from memory cache)`，耗时接近 0。命中**协商缓存**时，请求仍会发给服务器，带上 `If-None-Match`/`If-Modified-Since`，服务器比对后返回 `304`，体积极小但**仍有一次网络往返**——所以响应时间会明显高于本地命中。

为什么同一资源有时 A 有时 B：最常见是**没有给资源配置 `Cache-Control`**，导致每次只能走协商；或 `max-age` 到期后自动降级为协商。其次是刷新行为差异：普通刷新（F5）会让页面主文档强制重新验证，资源子请求仍走强缓存；强制刷新（Ctrl/Cmd+Shift+R）则完全绕过缓存。此外 disk cache 会被 LRU 淘汰，`from memory cache` 只在当前会话内存在，内存态资源关闭标签页后失效，这也是表现"不稳定"的来源。

排查路径：DevTools Network 面板逐个看资源，`Size` 列会标注来源（`memory cache`/`disk cache`/`304`/服务器字节数）；点击请求看 Response Headers 中 `Cache-Control`、`ETag`、`Last-Modified` 是否存在。期望的静态资源配置是 `Cache-Control: public, max-age=31536000, immutable`（文件名带版本 hash 的发布策略），如果看到接口/HTML 也被缓存，反而要警惕。

实践中的坑：很多 CDN/网关对 `ETag` 做了改写，导致源站与边缘节点 ETag 不一致、304 判断失效；`max-age` 过长且文件名不带 hash，改版后用户拿到旧资源——所以"强缓存"必须配合"版本化文件名"才安全。

**延伸考点：** 为什么 `immutable` 指令能避免用户刷新时的不必要重新验证？如果 CDN 层强制 `s-maxage`，与源站 `max-age` 冲突时以谁为准？

### Q2. 接口从浏览器访问正常，从服务器上 curl 却 502，怎么定位？

**问题：** 某个接口浏览器/客户端调用一切正常，但运维从服务器上 `curl https://api.example.com/x` 复现时返回 `502 Bad Gateway`。同一时刻同一接口，为什么链路结果不同？

**期望加分项：**
- 能先区分"同一链路"还是"不同链路"：浏览器可能走 CDN/就近节点，服务器 curl 可能走公网回源，两条链路经过的节点不同
- 会用 `curl -v` 看响应头（`Server`、`Via`、`X-Cache`）与 TLS 握手细节，确认 502 到底出自哪一层（边缘网关 / Nginx / 后端）
- 能排查代理层变量：服务器上是否有 `http_proxy`/`https_proxy` 环境变量，导致 curl 走了内部代理
- 能检查 Host 头差异：curl 默认带 `Host: api.example.com`，若通过其他域名/IP 访问则可能命中不同 `server_name`，进而路由到不同 upstream
- 能给出 Nginx 侧排查：`upstream` 定义、`proxy_read_timeout`、后端 error log、健康检查状态
- 主动考虑 IPv4/IPv6、防火墙/安全组放行差异等链路层因素

**减分项：**
- 只答"502 是网关连不上后端"这个定义，不给出定位步骤
- 忽略 curl 会读 `http_proxy` 环境变量这个高频坑
- 不检查 Host 头/SNI 差异，以为"curl 就等于浏览器"
- 定位不到"谁返回的 502"（边缘 vs 本地 Nginx vs 后端框架）

**解答：**

先确认"浏览器与 curl 是不是同一条链路"——这是最常见的盲区。浏览器请求可能被 CDN 或办公网出口解析到边缘节点，而服务器上的 curl 走的是另一条路径（比如直连源站、或经内部代理），链路不同、结果自然可能不同。先执行 `curl -v https://api.example.com/x`，重点看三处：`Connected to` 显示实际连到的 IP（与浏览器解析到的 IP 对比）；响应头里的 `Server`/`Via`/`X-Cache` 指明是哪个组件吐出的 502；TLS 握手域名（SNI）。

第二步排除 curl 自身变量：检查环境变量（Linux `env | grep -i proxy`），curl 会默认走代理，而代理到上游失败恰好会产生 502/504；再看请求的 `Host` 头是否与浏览器一致——如果服务器上访问的是 IP 或内网域名，Nginx 会按 `server_name` 匹配到别的 server block，路由到错误 upstream。用 `curl -H "Host: api.example.com"` 做对照即可验证。

第三步定位 502 出自哪一层：若返回头是 Nginx 的，看它的 error log 中对应的 `upstream timed out` / `connect() failed` / `no live upstreams`；确认后端进程是否存活、`proxy_read_timeout` 是否太短导致慢接口被网关掐断。若响应头无 Nginx 痕迹，则是更外层网关或云 LB 返回的，去查那一层的日志与健康检查。

实践中的坑：服务器 curl 慢接口时常见"浏览器 3 秒内返回、curl 却 504"，原因是浏览器复用了已建立的长连接而 curl 每次新建连接，叠加后端首字节慢；另外云厂商 LB 健康检查用独立探活路径，探活 200 但真实请求 502 的情况也要查后端路由规则。

**延伸考点：** 如果发现 502 时后端 error log 里什么都没有，下一步该查哪里？如何区分"连接被拒绝"与"连接超时"两种 upstream 失败在日志中的不同表现？

### Q3. 线上出现大量 301/302 跳转导致页面变慢，如何定位跳转链并评估影响？

**问题：** 用户反馈页面打开很慢，抓包发现一次页面访问连续跳转 4-5 次（301/302 连环跳）。请说明如何定位完整跳转链、判断每跳的语义，以及这类问题的常见成因与修复方向。

**期望加分项：**
- 能用 `curl -iL` / DevTools Network 面板查看完整跳转链，数出跳转次数与每跳 Location
- 能说清 301（永久，浏览器会缓存跳转结果）与 302（临时，不缓存）在语义与缓存行为上的本质区别，以及 307/308 对 method/body 的保留语义
- 能指出常见成因：http→https 跳转、www/非 www 域名归一、CDN 强制 HTTPS 而源站只收 HTTP、旧域名迁移
- 能评估影响：每跳多一个 RTT（弱网/移动端放大），301 被浏览器强缓存后"改不回来"的坑
- 能给出修复方案：合并跳转链（如 CDN 直接回源 HTTPS，避免 302→301→200 多跳）、HSTS 替代 301 的取舍

**减分项：**
- 分不清 301/302 对浏览器缓存的影响，说不清"301 改不回来"的后果
- 只会看结果不会数跳转链，给不出排查命令
- 忽略 307/308 的存在，说不清 PUT/POST 在跳转时的方法保持问题
- 把跳转慢简单归因于"网络差"，不做链路拆解

**解答：**

先量化跳转链再谈优化。`curl -iL https://example.com/` 会打出每一跳的状态码与 `Location`；DevTools Network 面板里把响应按时间排序，能看到每次跳转对应一个完整请求-响应周期，每跳都是一次新的 RTT。典型连环跳：`http://example.com` → 301 `https://example.com` → 302 `https://www.example.com` → 200。要评估影响，明确两点：跳转次数（多少个 RTT）与每跳的状态码语义。

语义上：**301 永久重定向**，浏览器（和搜索引擎、书签）会把结果缓存起来，后续直接访问目标地址——好处是省去重复跳转，坏处是服务器想改回时，老用户浏览器仍直连旧地址、行为不可控；**302 临时重定向**不缓存，每次都会重新发起跳转，代价是永久多一次往返。**307/308** 是 302/301 的语义修正版：跳转时保留 method 与请求体——用 302 跳 POST 请求时，不少客户端/网关会把 POST 降级为 GET 并丢 body，这正是电商下单页"跳转后丢参数"的经典现场。

修复方向：把跳转链收敛到一步以内。例如域名统一走 CDN 强制 HTTPS 并直接回源 HTTPS，避免"浏览器→CDN http→https→源站 http→https"这类嵌套；主域名用 301 归一但通过 HSTS（`Strict-Transport-Security`）替代每次 http→https 的 301，浏览器后续自动走 https 直连。排查时若发现跳转在 CDN 层与源站层重复发生，优先把逻辑收敛到一层。

实践中的坑：301 一旦被浏览器缓存，联调时改配置不生效是常态，需在 DevTools 里勾选 Disable cache 或清站内数据验证；另外代理/网关层配置了 http→https 强制跳转，业务代码里又做了一次，就会形成"回环式"多跳。

**延伸考点：** 移动端弱网下减少一跳能省多少时间（按 RTT 估算）？POST 请求在 302 跳转时浏览器通常怎么处理，为什么幂等接口反而推荐用 307/308？

### Q4. 接口偶发返回 401/403/429，如何快速区分是鉴权失败、权限不足还是被限流？

**问题：** 生产环境某个接口开始间歇性报错，错误码在 `401`、`403`、`429` 之间摇摆。请说明这三者的语义差异，以及如何定位"偶发"背后的真实根因。

**期望加分项：**
- 能准确区分：401 未认证（token 缺失/过期，响应带 `WWW-Authenticate`）、403 已认证但无权限（或网关 WAF 拦截）、429 被限流（响应应带 `Retry-After`）
- 能给出复现与取证手段：抓请求头看 Authorization/Cookie 是否存在、比对服务端日志与客户端时间戳
- 能列出"偶发"的高频根因：token 刷新竞态、多实例时钟偏移、限流维度误配（按 IP 但出口 IP 共享）、WAF 误拦
- 能讲清 403 是业务层还是网关层返回的（看响应头 `Server`/错误体格式）
- 能针对 429 给出正确应对：读 `Retry-After`、客户端退避，而不是无脑重试放大

**减分项：**
- 三个状态码语义混淆，把 403 当"没登录"讲
- 对"偶发"不做归因，只说"可能是网络问题"
- 不知道 `WWW-Authenticate` 与 `Retry-After` 这两个关键响应头
- 遇 429 就建议"加大限流阈值"，不分析触发维度

**解答：**

先明确语义边界：**401 Unauthorized** 是"没认证或认证失效"，服务端应返回 `WWW-Authenticate` 头提示认证方式，典型场景是 token 过期；**403 Forbidden** 是"认证通过但没权限"，可能是角色不足、IP 白名单、或更上层的 WAF/网关把请求判定为恶意；**429 Too Many Requests** 是"被限流"，规范要求带 `Retry-After` 告知多久后可重试。三者混出，说明链路里存在多层判断（网关限流、网关鉴权、业务鉴权、业务权限），先按"谁吐的错"分层：看响应头 `Server` 与错误体格式，Nginx/WAF 返回的错误体通常固定，业务框架返回的则是 JSON 结构。

针对"偶发"逐层排查：401 偶发，先查**时钟偏移**——JWT 的 `exp` 校验依赖服务器时间，多实例若 NTP 不同步，会出现部分节点判定过期；再看前端 token 刷新逻辑是否有竞态（并发请求同时发现 401，重复刷新，后到的刷新请求被旧 token 拒绝）。403 偶发，重点查 IP 维度的安全策略：公司出口 IP 池被某个爬虫连坐、WAF 规则对 User-Agent 匹配过严。429 偶发，先确认限流维度——按 IP 限流时，NAT 出口共享 IP 的用户会被集体误伤；按用户限流时，要查是否有异常调用方（定时任务、未去重的前端请求）打爆配额。

应对策略：客户端对 429 必须读 `Retry-After` 并指数退避，避免重试风暴；401 用单飞（single-flight）刷新 token，多个并发 401 只发一次刷新请求；403 若来自网关，需要前后端约定错误体规范，把"网关拒绝"与"业务拒绝"用错误码区分，否则前端只能统一弹"无权限"，排查成本极高。

实践中的坑：很多团队把网关限流错误码配成 403 而不是 429，导致客户端不敢重试、业务误报"权限问题"；反过来 429 返回过快（如 1 秒内多次）会让健康检查探活失败，引发负载均衡摘节点——限流配置要避开健康检查路径。

**延伸考点：** 如何让前端一次请求就能区分"token 过期需跳登录"与"token 无效需重登"？网关限流时，`Retry-After` 与 `X-RateLimit-Remaining` 头分别应该在哪个组件上产出？

### Q5. 同一个"更新"接口，为什么有人用 POST、有人坚持用 PUT？差异到底在哪？

**问题：** 团队评审接口设计，甲说资源更新必须用 `PUT /users/{id}`，乙说一律用 `POST /users/{id}/update` 更省事。请说明 PUT 与 POST 在 HTTP 语义上的核心差异，以及"语义正确"在真实工程里到底值不值得坚持。

**期望加分项：**
- 能讲清幂等性差异：PUT 是完整替换、重复执行结果一致（幂等）；POST 语义上非幂等，用于创建/提交动作
- 能说明为什么幂等性在工程里重要：客户端/网关/代理自动重试的前提是幂等，POST 重试可能造成重复扣款/重复下单
- 能讲清 PUT 是全量替换、PATCH 是局部更新，以及三者取舍
- 能结合实践谈妥协：大量团队"全用 POST"的真实原因（网关日志、历史接口、框架习惯），并指出这需要配套幂等键兜底
- 能主动提出：幂等性最终要靠服务端实现（幂等键/唯一约束）兜底，方法名只是第一步

**减分项：**
- 只背"PUT 更新、POST 创建"的课本定义，说不出"为什么"
- 认为语义差异是学院派问题，讲不出幂等与重试的工程关联
- 不知道 PATCH 的存在，或把 PUT 当"局部更新"讲
- 只说"按 REST 规范来"，给不出真实项目里的权衡依据

**解答：**

核心差异只有一条：**幂等性**。PUT 要求"用请求体完整替换目标资源"，同一个请求发 1 次和发 100 次，资源最终状态一致；POST 不承诺这一点，常用于"创建/触发动作"。而幂等性在工程里是**可重试性**的前提：网络层重试、网关自动重试、客户端超时重发，这些场景只有幂等的接口才安全。POST 下单接口被重试两次就可能产生两笔订单——所以真正该讨论的不是"用哪个方法名"，而是"这个操作重放后是否安全"。

从协议语义看，PUT 需要客户端提供完整资源（缺字段即覆盖为默认值），PATCH 才表示局部更新。REST 纯主义下：创建用 POST、完整替换用 PUT、局部更新用 PATCH。但实践中"全用 POST"非常普遍，理由也很实际：历史接口难以迁移、统一网关要记录动作、团队无 REST 文化。这种做法的代价必须用**服务端幂等**来补：客户端每次请求带 `Idempotency-Key`（如 UUID），服务端对同一个 key 只执行一次、重复请求返回首次结果；或依赖唯一约束（订单号、`UNIQUE(商户号, 业务号)`）在数据库层兜底。

判断标准：如果接口会被客户端重试、会被网关重放、或涉及资金/库存等敏感状态，就必须保证幂等，无论方法名叫什么；如果只是一次性上报类操作，POST 无妨。面试时能说出"幂等性由服务端实现兜底，方法名只是契约声明"，比背任何规范都更有说服力。

实践中的坑：有人给 POST 接口加了幂等键，却在重试时换了 key，等于白做；还有人把幂等表放在单机内存里，多实例部署后重试打到另一台机器照样重复执行——幂等判断必须落在共享存储（DB 唯一索引 / Redis）上。

**延伸考点：** PUT 全量替换时，如果客户端漏传某个可选字段，服务端应该怎么处理？幂等键的过期时间怎么定，过期后又重试会怎样？

### Q6. 域名切换 CDN 后部分地区/用户访问异常，怎么排查 DNS 层的问题？

**问题：** 业务域名刚把解析切到新 CDN（CNAME 指向新的调度域名），随后陆续收到"部分地区访问超时、老用户仍访问旧节点"的反馈。请说明排查路径与 DNS 相关知识。

**期望加分项：**
- 能讲清 DNS 解析链路：浏览器/系统缓存 → Local DNS（运营商递归服务器）→ 权威 DNS，任一层的缓存都会影响生效时间
- 能说清 CNAME 与 A 记录的区别，以及 CDN 通过 CNAME + 调度（按 Local DNS 出口 IP 就近分配）的工作原理
- 会用 `nslookup -type=CNAME` / `dig +trace` 逐层验证，对比不同地区/运营商解析结果
- 能给出灰度切换实操：提前调低 TTL（如 600 → 60）再切，出问题可快速回滚
- 能讲清"老用户访问旧节点"的根因：Local DNS 缓存旧记录、客户端 hosts、CDN 节点状态未同步
- 主动考虑边缘情况：DNS 污染、Local DNS 对 CNAME 链解析异常、IPv6（AAAA）解析失败

**减分项：**
- 只背"DNS 是域名转 IP"，给不出逐层排查方法
- 不知道 TTL 与切换/回滚的关系
- 忽略 Local DNS 缓存与运营商差异，把锅全甩给 CDN
- 不懂 CNAME 与 CDN 调度的关系

**解答：**

先给判断：切换后"部分用户异常"绝大多数不是新配置错，而是**旧解析结果还在缓存里**。DNS 是分级缓存体系：浏览器缓存（通常几十秒到几分钟）→ 操作系统 → Local DNS（运营商递归服务器，缓存时长遵循权威返回的 TTL）→ 权威 DNS。切 CNAME 后，只有 TTL 到期的 Local DNS 才会重新向权威查询，没到期的继续返回旧 A 记录——所以"老用户还访问旧节点"是预期行为，不是事故。

排查路径：先在自己机器上 `nslookup -type=CNAME your.domain` 确认 CNAME 已指向新调度域名，再 `nslookup cdn.example.com` 看返回的节点 IP 是否合理（CDN 会按请求来源 Local DNS 的出口 IP 就近分配，注意这是"按解析者"而非"按用户"调度）；`dig +trace` 可逐层看缓存链。跨地区对比建议用多地拨测（云厂商的拨测工具或第三方），因为不同运营商 Local DNS 的刷新节奏不同，且部分 Local DNS 无视 TTL、强制缓存 10 分钟以上。

实操建议：任何权威记录变更前，先提前把 TTL 从小时级调低到 60 秒，等 1-2 个 TTL 周期让旧缓存自然过期，再执行切换；出问题时回滚同理，TTL 没调低就回滚等于"再来一遍完整生效周期"。客户端侧可同时用 HTTP DNS（DoH/DoT）或 IP 直连兜底，绕过运营商 Local DNS 的污染与缓存问题。

实践中的坑：CDN 切换后源站侧的回源 Host 与证书域名对不上，导致边缘节点回源 502/证书告警，与 DNS 无关但最容易被误判为"解析问题"；另外部分客户端禁用了 AAAA 查询或 IPv6 路由不通，而权威返回了 AAAA，表现同样是"解析成功但连不上"——排查时用 `dig AAAA` 对照。

**延伸考点：** 为什么 CDN 调度必须基于"Local DNS 出口 IP"而非"用户 IP"？如果切换后发现新 CDN 节点有故障，如何在 TTL 未过期前让所有用户尽快离开该节点？

### Q7. 登录会话该用 Cookie+Session 还是 Token（JWT）？安全属性怎么配？

**问题：** 新项目要设计登录方案，前端多端（Web/App/小程序），后端会拆多个服务。团队在"Cookie+Session"与"JWT Token"之间争执。请给出选型分析与安全落地要点。

**期望加分项：**
- 能讲清两种方案的机制差异与各自代价：Session 服务端存储、可即时吊销，但多实例需共享存储；JWT 无状态、跨端友好，但吊销难、payload 有大小限制
- 能结合场景谈取舍：多端/移动端优先 Token；有强吊销需求（封号、改密失效）时 Session 或 Token 黑名单
- 能讲清 Cookie 安全属性：`HttpOnly`（防 XSS 窃取）、`Secure`（仅 HTTPS 传输）、`SameSite`（Lax/Strict/None 的 CSRF 防护）、`Domain/Path`、过期策略
- 能指出 JWT 落地关键：刷新 token 轮换、过期时间权衡、敏感信息不放 payload、算法固定（防 `alg=none` 攻击）
- 能给出混合方案：短时效 Access Token + 刷新 token，或 Token 存 Cookie（HttpOnly）兼顾 CSRF/XSS

**减分项：**
- 只背"JWT 更快、Session 更重"，说不出吊销、多端、SSO 等真实约束
- 把 `HttpOnly`、`SameSite` 当"了解过"概念，说不清各自防什么攻击
- 忽略刷新 token 与续期机制，把 JWT 当"一劳永逸"
- 不知道 `SameSite=None` 必须搭配 `Secure` 这类硬性约束

**解答：**

先给判断：这不是二选一，而是"**谁能满足吊销、多端、共享存储**这三个约束"的权衡。**Cookie+Session**：sessionId 存 Cookie，会话数据存服务端（内存/Redis），优点是**可即时吊销**（删掉 session 即失效）、可服务端踢人，缺点是服务多实例必须共享 session 存储（Redis/粘性会话），且移动端/小程序对 Cookie 支持不统一（小程序要手动携带）。**JWT**：无状态、天然跨端，服务端不用查存储，但**吊销是硬伤**——签发后到过期前无法撤销，封号/改密场景只能靠黑名单或缩短有效期，而黑名单又让"无状态"名存实亡。业务有强吊销诉求（安全产品、金融），选 Session 或 Token+Redis 黑名单；内部 API 系统、多端强一致性场景，选 JWT + 刷新轮换更省事。

无论选哪种，Cookie 安全属性是通用底线：**HttpOnly** 禁止 JS 读取，防 XSS 窃取；**Secure** 仅 HTTPS 下发；**SameSite=Lax**（默认）阻止跨站请求携带 Cookie，这是 CSRF 的现代解法——若确实需要跨站携带（如第三方登录回调），才用 `SameSite=None`，但**必须同时配 `Secure`**，否则浏览器直接拒绝；**Domain/Path** 要收紧到最小范围，别让 Cookie 污染整个主域。

JWT 落地细节：Access Token 短时效（如 15 分钟）+ Refresh Token 长时效并做**轮换**（每次刷新换新，旧刷新 token 立即作废，防重放）；payload 只放 uid 等最小信息，别塞手机号/邮箱（base64 可解码，任何人可见）；服务端校验必须锁定算法（只允许 HS256/RS256），拒绝"从 token 头读取算法"的弱校验，防 `alg=none` 伪造。Token 放哪：localStorage 防不了 XSS、Cookie 防不了 CSRF，稳妥做法是 access token 存内存（刷新页面前提走刷新接口）、refresh token 存 HttpOnly Cookie。

实践中的坑：登录态跨域共享时（主域 + 子域），`Domain=.example.com` 与 `SameSite=Lax` 组合会让第三方域名下的 iframe 无法取到会话，联调时先分清"跨站"与"跨子域"两种场景。

**延伸考点：** 用户改密码后，已签发的 JWT 为什么仍然有效？如何设计"改密即全部设备下线"的机制？刷新 token 轮换时，如果客户端同时发起两个刷新请求，如何避免并发把会话搞失效？

### Q8. 前端跨域接口报 CORS 错误，预检请求到底是怎么回事？代理方案和 CORS 头怎么选？

**问题：** 前端页面调用 `https://api.example.com` 的接口报 `No 'Access-Control-Allow-Origin' header is present`，部分请求还会多出一个 `OPTIONS` 预检请求。请解释 CORS 机制，并给出"配置 CORS 头"与"前端代理"两种方案的取舍。

**期望加分项：**
- 能讲清同源策略（协议+域名+端口）与 CORS 的关系，以及浏览器"先拦截、后报错"的表现
- 能准确说出预检（preflight）触发条件：非简单方法（PUT/DELETE 等）、自定义请求头、`Content-Type` 非 `application/x-www-form-urlencoded`/`multipart/form-data`/`text/plain`
- 能说清简单请求（GET/HEAD/POST + 表单类 Content-Type + 无自定义头）不发预检、直接带 `Origin` 请求的流程
- 能讲清关键响应头：`Access-Control-Allow-Origin`（与 credentials 同时使用时的限制）、`Access-Control-Allow-Headers`、`Access-Control-Allow-Methods`、`Access-Control-Max-Age`（预检缓存）
- 能对比方案：开发期用 Vite/Webpack 代理、生产用 Nginx 反向代理/网关统一加头，与后端直接加 CORS 头的场景边界
- 能主动提坑：`Allow-Origin: *` 与 `credentials: include` 互斥、预检在网关被 401/403 拦掉、允许头列表不全

**减分项：**
- 分不清"跨域报错是浏览器拦截、不是服务端没响应"
- 说不出预检触发条件，只会说"加个 Access-Control-Allow-Origin 就行"
- 不知道 `*` 与 credentials 的互斥关系
- 对"代理 vs CORS 头"讲不出取舍，只会背"用 nginx 代理"

**解答：**

先明确报错本质：**请求大概率已经发出去了，是浏览器把响应拦了下来**——CORS 是浏览器侧的跨域访问控制，服务端即使返回了 200，只要响应头缺 `Access-Control-Allow-Origin`，浏览器就不把数据交给页面。所以第一步用 `curl -i -H "Origin: https://app.example.com" https://api.example.com/x` 直连，看服务端到底有没有返回 CORS 头，先区分"服务端没配"还是"被网关剥掉"。

预检请求：当请求**不是简单请求**（非 GET/HEAD/POST、或带了自定义头如 `Authorization`/`X-Requested-With`、或 `Content-Type` 是 `application/json` 等非表单类型）时，浏览器会先发一个 `OPTIONS` 预检，问服务器"允许这种跨域请求吗"，服务器返回 `Access-Control-Allow-Methods`/`Access-Control-Allow-Headers`/`Access-Control-Max-Age` 后，浏览器才发真实请求。注意：**预检本身不带业务数据，它也是一个真实请求**，会打到网关、会经过鉴权——很多团队预检 401/403 就是因为网关把 OPTIONS 也拦了，需要放行。

配置要点与坑：`Access-Control-Allow-Origin` 若配 `*`，就**不能**与 `credentials: include`（带 Cookie）同用，后者要求 Origin 必须回显具体域名且 `Allow-Credentials: true`；`Allow-Headers` 必须把自定义头列全，少一个预检就失败；预检结果可被浏览器缓存（`Max-Age`），合理设置能省掉大量 OPTIONS。

方案取舍：开发期前端代理（Vite/Webpack devServer proxy）最省事，把跨域变成"同源"；生产环境如果 API 有统一网关，在网关层统一加 CORS 头是性价比最高的（一处配置、多端生效）；后端框架加头适合接口归属明确的单体项目，但要保证**每个错误分支**（404/500）也带上 CORS 头，否则错误响应照样被浏览器拦、前端拿到的是莫名其妙的网络错误。前端代理的局限是只对浏览器生效，App/小程序/第三方直接调 API 时还是得靠服务端头或网关。

实践中的坑：Nginx 配置 `add_header Access-Control-Allow-Origin *;` 时，`add_header` 默认只在 200/3xx 生效，404/500 分支不会带上，需加 `always` 参数；还有团队把 CORS 头写进了 CDN 缓存，导致不同 Origin 的用户拿到同一个 Allow-Origin 值。

**延伸考点：** 预检请求会不会也触发服务端限流或埋点统计，导致数据虚高？如果服务端返回 `Vary: Origin` 对 CDN 缓存命中率有什么影响？

### Q9. HTTPS 比 HTTP 慢多少？TLS 握手过程里哪些环节可优化？

**问题：** 站点全站切 HTTPS 后，首屏变慢，监控显示 TTFB 上涨明显。请说明 TLS 握手的基本过程、它对性能的影响点，以及可落地的优化手段。

**期望加分项：**
- 能讲清 TLS 1.2 握手的主要往返：ClientHello → ServerHello+证书 → ClientKeyExchange+ChangeCipherSpec → Finished（常见约 2 个 RTT）
- 能说出 TLS 1.3 的改进：握手减到 1-RTT、移除 RSA 密钥交换（强制前向保密）、0-RTT（含重放风险）
- 能讲清会话恢复机制：Session ID 复用、Session Ticket、TLS 1.3 的 PSK
- 能从工程角度量化：新增的 RTT 在移动端弱网下放大的程度、加解密 CPU 开销（AES-NI 后已很小）
- 能给出优化清单：TLS 1.3 + OCSP stapling + 会话复用 + HSTS（省去 http→https 的 301 跳转）+ 证书链精简（避免断链导致额外握手失败）
- 能主动提坑：老客户端不支持新协议、证书链不完整导致部分设备握手失败、0-RTT 重放防护、CDN 与源站的双层 TLS

**减分项：**
- 只会说"HTTPS 用加密更安全"，说不清握手过程与 RTT 代价
- 分不清 TLS 与 SSL、说不清 1.2 与 1.3 的差异
- 不知道会话复用/OCSP stapling 等成熟优化手段
- 忽略移动端弱网下 RTT 的放大效应，只说"服务器性能不够"

**解答：**

先量化：HTTPS 的额外开销主要在**握手阶段的 RTT**。TLS 1.2 全握手通常需要 2 个 RTT（TCP 1 个 + TLS 2 个 ≈ 首包前 3 个 RTT），移动端弱网 RTT 50-100ms 时，仅握手就多出 100-200ms，这就是 TTFB 上涨的主要来源；加解密本身在 AES-NI/硬件加速下开销已可忽略（约 1-3% CPU），真正的成本在往返次数。TLS 1.3 把握手压到 1-RTT，条件允许优先升级。

优化优先级建议：**① 启用 TLS 1.3 + 会话复用**——Session Ticket 让短时内重连的客户端跳过全握手（TLS 1.3 下 PSK 恢复），收益立竿见影；**② HSTS**——浏览器首次访问后记住"只走 HTTPS"，省掉每次 http→https 的 301 跳转；**③ OCSP stapling**——把证书吊销状态查询由浏览器独立发请求改为服务器随握手附带，省一个证书链上的额外请求；**④ 证书链精简**——只下发必要中间证书，避免根证书缺失触发额外下载（部分老设备下载根证书会显著变慢甚至握手失败）；**⑤ 优先保证全部资源走 HTTPS**，否则"https 页面混入 http 资源"会触发 mixed content 拦截，表现是资源加载失败而非变慢。

几个常被忽略的坑：CDN 开启"边缘 TLS + 回源 TLS"双加密时，边缘握手优化做了、回源却在裸奔或反复握手，回源 TTFB 会掩盖边缘优化效果；0-RTT 恢复省了 RTT 但存在**重放攻击**风险，只建议用于幂等请求（GET）；同一证书覆盖多域名时用 SAN 而非开多个证书，减少证书链体积；另外 TLS 版本回退问题——部分老 Android 系统不支持 TLS 1.3，配置时要评估用户设备分布，别一刀切禁用旧版本。

实践中的坑：升级后若发现部分用户报"SSL 握手失败"，优先检查证书链是否完整（用 `openssl s_client -connect host:443 -showcerts` 验证）与密码套件是否把老设备支持的套件全禁用掉了；监控指标上，把 TTFB 拆成 DNS/TCP/TLS/首字节四段（`curl -w` 或浏览器 Timing API）才能定位慢在哪一段。

**延伸考点：** TLS 1.3 的 0-RTT 为什么存在重放风险，什么样的业务场景坚决不能用？会话 Ticket 存在客户端，服务端如何做到多实例间共享密钥而不泄露？

### Q10. 页面资源请求被浏览器限制并发，HTTP keep-alive 与连接池又是什么关系？

**问题：** 压测发现单页面加载大量资源时，HTTP/1.1 下浏览器对同一域名只开约 6 个连接；而服务端压测工具却能轻松跑满千级 QPS。请说明浏览器并发限制、keep-alive 与后端连接池之间的关系，并给出"连接"维度的优化手段。

**期望加分项：**
- 能说清 HTTP/1.1 同一连接串行请求、浏览器每域名并发连接上限（Chrome 约 6 个）的约束，以及"域名分片"这个历史手段
- 能讲清 keep-alive 的本质：TCP 连接复用，省掉重复的 TCP 握手与慢启动
- 能讲清服务端视角：Nginx 的 `keepalive_timeout`/`keepalive_requests`、到后端的 upstream keepalive 连接池、应用层 HTTP client 的连接池配置（maxConnections/空闲清理）
- 能指出两者关系：浏览器并发上限决定客户端侧连接数，服务端连接池决定后端能承接多少并发；连接泄漏/池耗尽会导致请求排队超时
- 能给出连接维度优化清单：切 HTTP/2（同域单连接多路复用）、合并请求、CDN 分摊域名、服务端调大连接池与空闲超时
- 能讲 TIME_WAIT 大量堆积与"服务器主动关闭连接"的关联

**减分项：**
- 把 keep-alive 与连接池混为一谈，说不清"复用谁"
- 不知道浏览器有并发上限，也无法解释为什么 HTTP/2 能解决
- 对服务端连接池泄漏、耗尽的表现无概念
- 答不出 TIME_WAIT 的成因（主动关闭方产生）

**解答：**

三个概念分清楚：**keep-alive** 是"同一条 TCP 连接上连续收发多个请求-响应"（HTTP/1.1 默认开启），**浏览器并发限制**是客户端侧的约束——HTTP/1.1 下 Chrome 对同一域名默认最多约 6 条连接（每条连接上请求串行），**连接池**是服务端/中间件侧的复用机制（Nginx 到 upstream 的 keepalive 池、应用里 HTTP client 与 DB 连接池）。三者共同决定一条链路的并发上限：客户端最多 6 条连接 × 每连接串行 → 一个页面 60 个资源至少 10 批串行往返，这就是 HTTP/1.1 下页面慢的根源之一。

连接维度的优化分两头：**客户端侧**，HTTP/2 是最优解——同一域名一条连接即可多路复用所有请求，绕开 6 连接限制；没条件上 h2 时可用"域名分片"（静态资源分散到多个子域名）稀释并发限制，但这是 hack，副作用是 DNS 查询增加；再把小图标/雪碧图合并，减少请求数本身。**服务端侧**，Nginx 到 upstream 默认不开 keepalive（需 `proxy_http_version 1.1` + `Connection ""` + upstream 块配 `keepalive`），漏配会导致每个请求都新建 TCP 连接到后端，后端瞬间产生大量 TIME_WAIT（主动关闭方留下的）——这是高并发下"后端连接数暴涨、TIME_WAIT 堆积"的经典现场；应用层 HTTP client 则要合理设置连接池上限与空闲回收，池太小高并发排队、池太大空闲连接占内存，还要防**连接泄漏**（异常分支没归还连接，最终池耗尽、新请求全部等待超时）。

实践中的坑：开启 upstream keepalive 后，后端如果空闲超时比 Nginx 的 `keepalive_timeout` 短，会出现"连接已被后端关闭、Nginx 不知情"的残留连接，第一次复用报 `upstream prematurely closed connection`——解决办法是让后端空闲超时 > Nginx 的，或调低 Nginx 池的保活时间；另外压测与线上差异：压测工具通常不受浏览器并发限制约束，导致压测指标与真实用户体验（首屏）严重背离，做前端性能评估一定要考虑浏览器并发模型。

**延伸考点：** HTTP/2 下为什么还要限制每个连接的最大并发流（SETTINGS_MAX_CONCURRENT_STREAMS）？后端服务里 HTTP client 连接池的 `maxIdleTime` 设多大合理，依据是什么？

### Q11. 站点要升级 HTTP/2 甚至 HTTP/3，收益和坑分别是什么？

**问题：** 站点目前 HTTP/1.1，资源加载慢、队头阻塞明显，团队讨论是否升级 HTTP/2（或直接上 HTTP/3）。请说明从 1.1 到 2、再到 3 的演进解决了什么问题、各自代价，以及落地的注意点。

**期望加分项：**
- 能讲清 HTTP/1.1 的两个核心问题：同一连接请求串行（队头阻塞）、无头部压缩
- 能讲清 HTTP/2 的关键机制：二进制分帧、多路复用（stream 并发）、HPACK 头部压缩、Server Push（并指出已被 Chrome 移除）
- 能指出 HTTP/2 的遗留问题：**TCP 层的队头阻塞**——一个流丢包会阻塞整条连接上所有流的后续数据
- 能讲清 HTTP/3 = QUIC over UDP：0-RTT、无 TCP 队头阻塞、连接迁移（换网不重连）、但依赖 UDP 可达性
- 能给出落地注意点：HTTP/2 需要 HTTPS（ALPN 协商）、老库/老设备兼容性、代理层（Nginx/网关）必须支持并正确配置、压测要按真实并发模型验证多路复用收益
- 能主动提坑：h2 下大量并发流仍受 `MAX_CONCURRENT_STREAMS` 限制；CDN 边缘支持但回源仍 1.1 时优化打折；QUIC 被部分企业网防火墙拦 UDP

**减分项：**
- 只背"h2 多路复用、h3 更快"，说不清各自解决了什么、遗留了什么
- 不知道"TCP 队头阻塞"与"HTTP 层队头阻塞"是两回事
- 把 Server Push 当 h2 核心卖点（已被移除），显得知识停留在宣传稿
- 答不出升级对基础设施（代理、证书、压测）的连锁要求

**解答：**

先给判断：升级 h2 是"低风险高收益"，升 h3 是"看场景的增量优化"。**HTTP/1.1** 的痛点是每条连接上请求串行（应用层队头阻塞）且头部不压缩——所以浏览器要靠多开连接弥补，Nginx 层 `keepalive` 也只是复用连接、不解决串行。**HTTP/2** 用二进制分帧把一条连接切成多个并发 stream，请求互不阻塞，配合 HPACK 头部压缩，对小文件多、头部大的场景收益明显；代价是它跑在 TCP 上——**TCP 层的队头阻塞**依然存在：一个包丢了，这条连接上所有 stream 都得等重传，弱网下反而可能比 1.1 更糟（1.1 至少有多条独立连接可以分摊损失）。Server Push 曾被寄予厚望，但已被 Chrome 移除，别再把它当卖点。

**HTTP/3** 换 UDP（QUIC）解决了 TCP 队头阻塞，还带来 0-RTT 建连与连接迁移（Wi-Fi 切蜂窝不断连），但对基础设施要求更高：中间设备（企业防火墙/运营商 NAT）对 UDP 的友好度参差，部分网络会直接丢 QUIC 包；监控与抓包工具链要更新（QUIC 加密了传输头，传统 tcpdump 分析手段失效）。它不是 h2 的替代，而是叠加——客户端通常同时协商，QUIC 不通自动回退 h2。

落地清单：① h2 前提是全站 HTTPS（通过 ALPN 协商，客户端只对 https 用 h2，h2c 基本不用）；② 代理链路全部升级——浏览器→CDN 是 h2，但 CDN→源站若仍走 1.1，多路复用只覆盖了边缘一段，回源侧还有串行问题；③ 压测工具要支持 h2（wrk 需 `--http2` 或换 h2load），否则压测结果会误导；④ 老设备（部分 Android WebView、旧系统库）不支持 h2 时要保留 1.1 回退路径，别在服务端把 1.1 禁掉；⑤ h2 单连接承载所有请求，连接被中间设备意外掐断的影响面比 1.1 大，服务端 `keepalive` 与超时参数要重新调。

实践中的坑：h2 下慢请求仍会占用连接内资源，个别超长接口需要配合流优先级或单独限流，别指望"上了 h2 所有慢都变快"；还有团队在 CDN 上开了 h2 但忘了看"连接复用率"指标，实际大部分请求在新建连接，收益没吃到。

**延伸考点：** 同一资源在 h2 与 1.1 下的性能差异为什么在"小文件多"与"大文件少"两种场景下完全相反？QUIC 的 0-RTT 与 TLS 1.3 的 0-RTT 有什么本质区别？

### Q12. WebSocket 长连接在生产环境不稳定：心跳、断线重连、多实例广播怎么搞？

**问题：** 团队用 WebSocket 做实时通知，上线后发现：连接隔一阵就静默断开（客户端感知不到）、重启服务端后大量客户端没有重连、消息推送要广播时多实例之间不同步。请逐项给出方案。

**期望加分项：**
- 能讲清 WebSocket 的握手（Upgrade 头）与帧结构，以及"静默断开"的根因：中间代理/网关的空闲超时（如 Nginx 默认约 60s 掐断空闲连接）、TCP 半开连接（断网无感知）
- 能给出心跳方案：应用层 ping/pong 间隔（如 30s）小于代理超时，超时无 pong 判定断线并触发重连
- 能给出断线重连设计：指数退避 + 随机抖动、重连时携带 last message id 做断点补偿、页面可见性变化时主动重连
- 能讲清多实例架构：连接挂在各实例上，广播需经 Redis Pub/Sub（或 MQ）分发到所有实例再各自下推；负载均衡层需开启长连接相关配置（如 proxy_read_timeout 调大、`proxy_http_version 1.1`）
- 能讲清优雅下线：服务端实例缩容/发布时主动发关闭帧并等客户端重连到其他实例，避免连接"吊死"
- 能主动提坑：鉴权放握手阶段（query/cookie）而非消息里、心跳与业务消息复用同一条连接、连接数上限与内存

**减分项：**
- 只知道"WebSocket 是双向长连接"，说不出断线感知与重连机制
- 心电间隔随便设，不考虑与代理超时参数的匹配
- 广播方案答不出"多实例需消息中间件分发"，只说"遍历所有连接"
- 忽略服务端发布/缩容时的连接迁移问题

**解答：**

逐个拆：**① 静默断开**——客户端与服务器之间的 TCP 连接可能早已断开（NAT 老化、中间代理超时、手机切网），但双方都没有数据流动就感知不到，这就是"半开连接"。根因排查先看链路：浏览器→Nginx→后端，Nginx 对空闲连接有 `proxy_read_timeout`（默认 60s 左右），超时直接掐；后端进程重启/发布时旧连接被 RST。**② 心跳**——应用层约定 ping/pong：客户端每 30s 发 ping，服务器回 pong；超过 2-3 个周期没收到 pong 判定断线。间隔的取值要与**所有中间代理的超时**匹配（心跳间隔 < 任一代理空闲超时），否则心跳白打。心跳消息要与业务消息区分（自定义 opcode 或消息类型字段），别把业务流量当心跳（长时间无业务时照样断线）。**③ 断线重连**——纯指数退避（1s、2s、4s…）会在大批客户端同时断线时形成"重连风暴"，必须加随机抖动；重连后要做**断点补偿**：客户端记录收到的最后一条消息 id（或服务端存游标），重连握手时带上，服务端把漏掉的消息补推——否则"重连成功但丢了通知"更隐蔽。**④ 多实例广播**——连接分散在各实例内存里，直接遍历是"单机广播"；正确做法是业务消息先发到 Redis Pub/Sub / MQ，所有实例订阅后各自推给本机连接，再配合"在线状态"（谁在哪些实例）做定向推送。**⑤ 优雅下线**——发布/扩缩容时服务端先发 close 帧（code 如 4001）通知客户端"我要下线"，客户端收到后切到其他实例重连；负载均衡要支持连接 drain（停止接收新连接、等存量连接处理完）。

实践中的坑：鉴权必须放在**握手阶段**（`Sec-WebSocket-Protocol`、query 或 Cookie），升级成功后再鉴权会导致"已建连才发现无权限"且无法返回 HTTP 错误码；连接数要监控（每连接内存 + 定时器），并设置单 IP 连接上限防刷；长连接使负载均衡的会话保持策略失效——WebSocket 是**逐连接粘住**的，健康检查探活的是新建连接而非存量连接，后端某个实例的存量连接全部异常时探活可能仍然 200，需要被动探测配合。

**延伸考点：** 心跳间隔 30s、代理超时 60s，为什么偶尔还是断？心跳与业务消息同时到达时如何避免 ping/pong 状态机错乱？WebSocket 在 HTTP/2 下的实现（RFC 8441）与普通 ws 有什么差异？

### Q13. 大文件上传怎么设计？分片、断点续传、秒传分别解决什么问题？

**问题：** 平台要支持用户上传几 GB 的安装包/视频，浏览器直传体验差：中途断网全丢、重传成本高、重复文件占用存储。请设计大文件上传方案，说明分片、断点续传、秒传各自的原理与取舍。

**期望加分项：**
- 能讲清分片上传：`File.slice` 切块（如每片 1-8MB）、并行上传受控并发、服务端按"上传任务+分片序号"暂存、全部完成后合并
- 能讲清断点续传：已传分片记录（客户端本地记录 + 服务端接口查询），续传只传缺失分片
- 能讲清秒传：前端算文件内容 hash（Web Crypto 或 SparkMD5），服务端按 hash 查库，已存在直接返回成功，不传内容；大文件 hash 全量计算耗时，可抽样 hash 权衡
- 能讲清合并与一致性：分片乱序/缺失处理、合并校验（大小 + 最终 hash）、失败清理
- 能给出服务端配套：上传分片接口幂等（同一分片重传不报错）、临时存储配额与过期清理、合并任务异步化、`client_max_body_size` 限制的规避
- 能提坑：多实例部署时临时分片必须共享存储（对象存储/分布式文件系统）而非本地盘；浏览器内存/大文件 hash 卡顿；iOS Safari 对 slice 与并发上传的兼容性

**减分项：**
- 只答"前端切片、后端拼接"，说不清秒传与断点续传的实现差异
- 不知道 hash 计算的位置与性能代价，把秒传讲成"前端自己判断"
- 忽略多实例下临时分片的共享存储问题
- 不聊失败恢复、超时与清理，方案停留在"能传上去"

**解答：**

三件事是分层解决的：**分片上传**解决"单次传输体量过大"——网络层对单请求有大小与超时限制（Nginx `client_max_body_size` 默认 1m，即使调大，几十 GB 单请求只要断一次就全废）。做法：前端 `File.slice` 切成统一大小分片（视频类建议 5-8MB），发"初始化上传"拿到 uploadId，然后**限并发**上传分片（如同时 3-5 个，避免打满带宽且便于重试），全部完成后调"合并"接口，服务端把分片按序号拼接。**断点续传**解决"失败后全重来"——客户端本地持久化已传分片列表，重传时先调服务端"查询已传分片"接口（比本地记录可靠，因为本地记录可能丢/换设备），只补传缺失分片。关键：**分片上传接口必须幂等**——同一 uploadId+分片序号重复上传直接返回成功，这样客户端重试才安全。**秒传**解决"重复文件白传"——先算文件内容 hash（Web Crypto 的 SHA-256 对几百 MB 也快；超大文件可抽样 hash 或 hash 前几 MB+大小，牺牲一点准确性换速度），带上 hash 调"检查"接口，服务端在存储里查重（可对 hash 建索引），存在即秒成功、把引用指向已有对象。注意 hash 依赖整个文件内容，**任何改动 hash 全变**，所以秒传只对"完全相同的文件"生效。

服务端配套是成败关键：多实例部署时分片必须存**共享存储**（对象存储 OSS/S3、或分布式文件系统），存本地盘会导致"分片打到 A 实例、合并请求打到 B 实例"时找不到分片；合并前校验分片完整性（序号连续 + 每片大小/最终总 hash），失败要支持"补传缺失分片后重新合并"而不是整单作废；临时分片要有过期清理（TTL，如 24h），否则用户传一半放弃会占满存储。

实践中的坑：大文件 hash 计算在移动端可能耗时数秒且占内存，要放在 Worker 里避免卡 UI，并给进度反馈；iOS Safari 对 `File.slice` 的兼容性、以及"App 切后台上传中断"的恢复，都要在真机验证；进度条要按"已确认上传的分片数"而不是"网络已发送字节"计算，否则重试会导致进度回跳。

**延伸考点：** 如果两个用户同时上传相同文件，秒传的"查重-建引用"如何保证不产生竞态（同时建了两份）？服务端合并大文件时是"边收边拼"还是"收完再拼"，各自对存储和带宽有什么要求？

### Q14. 流式输出：SSE 与 chunked 响应在代理层"不流式"了，怎么排查与解决？

**问题：** 团队做 AI 对话/日志实时推送，后端用 SSE（`text/event-stream`）流式吐字，但用户看到的效果是"等很久然后一次性全出来"，甚至超时断掉。请分析原因并给出方案。

**期望加分项：**
- 能讲清 SSE 的实现：`EventSource` 接口、`text/event-stream` MIME、`data:` 事件格式、`id:` 字段支持断线续传（Last-Event-ID）、单向且只能 GET
- 能讲清 chunked 传输：`Transfer-Encoding: chunked` 与 Content-Length 互斥，响应体边生成边发
- 能指出"不流式"的典型根因：**中间代理缓冲**——Nginx `proxy_buffering on` 默认攒满缓冲才转发；语言框架自带的输出缓冲（PHP ob_start、Java servlet 缓冲）；以及代理层对空闲连接的超时掐断
- 能给出解决方案：Nginx `proxy_buffering off` 或后端返回 `X-Accel-Buffering: no`；框架侧关闭缓冲/手动 flush；配置 `proxy_read_timeout` 覆盖长时间无数据场景
- 能对比 SSE 与 WebSocket 的选型：单向 vs 双向、自动重连 vs 手动、SSE 对 HTTP/1.1 与 HTTP/2 的支持差异、兼容性（老浏览器需 polyfill）
- 能提坑：SSE 客户端断线重连会带 `Last-Event-ID`，服务端要支持断点补发；负载均衡/多实例下重连可能落到不同实例；移动端切后台连接被挂起

**减分项：**
- 分不清 SSE 与 WebSocket、说不出 SSE 是单向的
- 不知道代理缓冲是"不流式"的第一嫌疑，只会改业务代码
- 不知道 `Transfer-Encoding: chunked` 与 Content-Length 的关系
- 忽略断线重连后的消息补偿问题

**解答：**

先判断"是不是真流式"：抓包或 `curl -N https://host/stream` 看响应是否逐块到达（`curl -N` 关闭缓冲逐行输出）。如果 curl 是流式的但浏览器不流式，说明问题在**代理或中间层**：Nginx 默认 `proxy_buffering on`，会等上游响应攒满缓冲区（或到请求结束）才转发给客户端——表现就是"一次性全出"；如果 curl 也不流式，问题在后端：PHP 的 `ob_start`、Java Servlet 默认缓冲、Node 里忘调 `res.flush()`，以及框架开启了 gzip 压缩把小块合并（流式场景通常关闭压缩或按块压缩）。

排查顺序：① 确认响应头有没有 `Transfer-Encoding: chunked`（有 Content-Length 就说明整包缓冲了）；② 看中间层：Nginx 对 SSE 接口 `proxy_buffering off`，或后端在响应头里带 `X-Accel-Buffering: no` 让 Nginx 对该响应自动关缓冲（**更推荐**，可按接口控制，不用全局关闭影响其他大文件）；③ 超时断流：`proxy_read_timeout`（默认 60s）只管"两次读取之间的间隔"，AI 流式场景吐字慢、间隔长会误杀，需调大或按路径单独配置。

SSE 协议要点：`EventSource` 只能 GET、单向、**自带重连**（断线后自动重连并带 `Last-Event-ID` 头），服务端要利用 `id:` 字段记录每条消息序号，重连时从断点补发——这是 SSE 相比"自己用 fetch 读流"的最大红利。事件格式每行 `data: xxx`、空行分隔，多行 data 合并为一条消息。与 WebSocket 的取舍：只需要"服务器→客户端"单向推送、且希望自动重连，SSE 更简单可靠；需要双向（聊天、游戏）才上 WebSocket。

实践中的坑：代理层开启 gzip 且 `proxy_buffering off` 同时存在时，部分版本 Nginx 会对流式响应做缓冲以做压缩，需确认关闭；SSE 在 HTTP/2 下事件流共享连接，代理需支持 h2 的流式转发；移动端页面切后台时浏览器会挂起 EventSource，回前台要主动重连并核对 Last-Event-ID；多实例部署时重连落到不同实例，SSE 的断点状态要放共享存储而不是实例内存。

**延伸考点：** SSE 在 HTTP/1.1 下会占满浏览器对同一域名的连接配额（最多 6 个），大量同时打开的 EventSource 会造成什么后果，怎么规避？`curl -N` 与浏览器对 chunked 响应的处理有什么差异？

### Q15. CDN 命中率低、回源波动，怎么定位与调优？

**问题：** 站点接入 CDN 后，监控显示缓存命中率只有 40% 左右，高峰期回源量把源站打得很痛。请说明排查路径与调优手段。

**期望加分项：**
- 能讲清 CDN 缓存决策依据：源站返回的 `Cache-Control`（`public`/`s-maxage`/`max-age`）、`Expires`、是否有 `Set-Cookie`/`Authorization`（默认不缓存）、URL 是否带随机参数
- 能给出命中率低的常见根因：资源 URL 带时间戳/随机参数（每次都是新 key）、动态接口被误配缓存策略、`Cache-Control: private`/`no-cache`、移动端与 PC 端 URL 不统一、边缘节点碎片化
- 能讲清回源相关排查：回源 Host、回源协议（http/https 不一致导致内容差异）、回源超时/重试、源站限流误伤回源
- 能给出调优手段：版本化文件名 + 长 max-age、对静态资源统一缓存策略、query 参数归一（CDN 忽略或只按固定参数缓存）、边缘压缩、缓存预热与刷新
- 能主动提坑：动态内容被误缓存（用户数据泄露风险）、刷新/预热有生效延迟、边缘节点把跨域/CORS 头缓存下来导致误伤、CDN 命中率指标与业务收益的对应关系

**减分项：**
- 只会说"把缓存时间调长"，说不清 CDN 按什么决定缓存不缓存
- 不知道 Set-Cookie/Authorization 会阻止缓存
- 忽略"URL 随机参数"这个头号命中率杀手
- 把 CDN 命中率当唯一指标，不考虑命中率与业务正确性的矛盾

**解答：**

先明确 CDN 的缓存决策链路：边缘节点收到请求，先看 URL 是否命中已有缓存，未命中则**回源**，回源后按源站响应头决定是否缓存以及缓存多久——`Cache-Control: public, max-age=3600` 会被缓存 1 小时；`private`/`no-cache`/`no-store` 不缓存；**响应带 `Set-Cookie` 或 `Authorization` 时大多数 CDN 默认不缓存**。所以调命中率，本质是调"源站响应头 + URL 设计"。

排查命中率低的套路：① 看**命中率分布**——是整体都低，还是特定目录低（/api 低正常，/static 低才异常）；② 抽查一个静态资源，用 curl 带 `-H "Accept-Encoding: gzip"` 直连 CDN 域名看响应头里有没有 `Age` 字段（有 Age 说明命中缓存）与源站 `Cache-Control` 是否按预期返回；③ 检查 URL 结构——**URL 带时间戳/随机 query（`?t=1688...`）或 session 参数是头号杀手**，每个用户一个 key、永远不命中；④ 检查响应头是否被污染：源站若对静态资源也返回 `Set-Cookie` 或 Vary 头（如 `Vary: User-Agent`），会把缓存按 UA 拆碎。

调优手段按优先级：**版本化文件名 + 长 max-age**（`app.8f3a2c.js` 配 `max-age=31536000, immutable`，改版换文件名，彻底解决"缓存与更新"的矛盾）；对无法改名的资源用 `s-maxage` 让 CDN 层缓存时间与浏览器层分开；query 参数归一（配置"忽略指定 query"或"只按白名单参数缓存"）；确认静态资源不带 Cookie；需要时做**缓存预热**（发布后主动回源一批关键资源）避免首波回源高峰。

实践中的坑：把带用户信息的动态接口误配成可缓存，会串用户数据——缓存配置前先确认响应"与谁无关"；**刷新/预热有生效延迟**（全节点刷新通常要分钟级），别在线上事故时指望"刷一下立刻好"；CDN 边缘缓存了缺少 CORS 头的旧版本，前端更新后跨域报错，需要"带 Origin 头回源验证 + 刷新"；另外命中率不是越高越好——对登录态页面强开缓存换来的是错误数据，衡量指标应是"命中率提升后回源带宽下降 + 用户体验指标不变坏"。

**延伸考点：** 如果源站必须返回 `Set-Cookie`，又要让静态资源被 CDN 缓存，怎么办（如去掉静态资源的 Cookie、或配置 CDN 忽略该头）？CDN 节点按什么粒度缓存（目录粒度/单 URL），调整粒度会有什么副作用？

### Q16. 负载均衡选 L4 还是 L7？会话保持和健康检查怎么配才不出事？

**问题：** 新服务上线要接负载均衡（云 LB 或 Nginx），团队纠结用四层（TCP）还是七层（HTTP），还担心"用户登录后请求被分到别的机器导致会话丢失"。请给出选型与配置要点。

**期望加分项：**
- 能讲清 L4 与 L7 的差异：L4 按 IP:PORT 转发（内核态、吞吐高、透明、适合长连接/非 HTTP 协议），L7 解析 HTTP 内容（可按路径/域名路由、可改头、可做 TLS 终结与更细的会话保持），L7 需要更多 CPU
- 能结合场景选型：纯 TCP/自定义协议/极致吞吐用 L4；HTTP 服务需要路由与治理用 L7；WebSocket/gRPC 对两者的适配差异（gRPC 常走 L7 或 L4 直通）
- 能讲清会话保持方案：Cookie 粘性（L7）、源 IP hash（受 NAT 影响）、一致性哈希（扩容/缩容影响面小）；以及"会话保持 ≠ 必须"——无状态化（Session 外置 Redis/Token 自包含）后连粘性都不需要
- 能讲清健康检查：主动探测（HTTP 探活路径、间隔/超时/失败阈值）、被动探测（连接失败计数）、慢启动；探活路径要选真实依赖（别探一个空 200）
- 能主动提坑：L4 下后端 TCP 连接残留（后端重启后旧连接仍被转发）、会话保持失效导致登录态乱跳、健康检查探活通过但业务 502

**减分项：**
- 分不清 L4/L7 的转发层级，说不出各自能做什么
- 只知道"配粘性会话"这一招，不知道无状态化才是根治
- 健康检查只答"ping 一下"，说不出探活路径选型与阈值设计
- 忽略"后端重启后残留连接"这类 L4 特有的坑

**解答：**

先给判断：HTTP 业务服务默认选 **L7**，除非有明确的吞吐/协议理由才用 L4。L4（如云 LB 的 TCP/UDP 监听、LVS）在内核态按 IP:端口转发，吞吐高、协议透明，但**不解析 HTTP**，所以做不了路径路由、Header 改写、TLS 终结，会话保持也只能用源 IP hash；L7（Nginx、云 LB 的 HTTP/HTTPS 监听）解析请求，可以按域名/路径分发、统一加头、证书集中管理，代价是每层多一次解析的 CPU 开销。选型逻辑：纯 TCP 协议（自定义协议、数据库、大量长连接）用 L4；HTTP/gRPC 服务要治理能力用 L7；WebSocket 在 L7 下要确保代理不缓冲、长连接超时调大（或在 L7 上配置 TCP 直通）。

**会话保持**的讨论要分两层：如果服务端会话是**有状态**的（Session 存内存），才需要粘性——Cookie 粘性（L7 下发 cookie 标记后端）比源 IP hash 可靠（NAT 下多用户共享出口 IP 会被 hash 到同一台）；更优的做法是**无状态化**：Session 外置 Redis、或 Token 自包含，任何实例都能处理任何请求，粘性会话直接不需要，后端扩容缩容也不影响——这才是根治。如果仍然要粘性，用一致性哈希或 Cookie 粘性，避免"hash 取模"在后端数量变化时大面积迁移会话。**注意粘性会话与健康检查的联动**：后端实例宕机时，粘性会话会把请求继续打到它身上（直到探活失败摘除），所以要配合"探活失败快速摘除 + 客户端重试"。

**健康检查**设计：主动探活用 HTTP 探活路径，**路径要反映真实可用性**——探一个 `/health` 空接口返回 200 不代表数据库/下游可用，建议探活接口内部做轻量依赖检查（DB ping、关键缓存），但别做全量重量级检查（会放大回源/DB 压力，反过来把探活打挂）；阈值设计要防抖动：失败 2-3 次才摘除、恢复 2-3 次成功才重新接入（避免网络抖动导致实例在"摘除-接入"间反复横跳）；新接入实例建议**慢启动**（逐步放流量），否则缓存/连接池是冷的，一接入就被打爆。

实践中的坑：L4 下后端实例重启（连接残留）——TCP 连接仍存在但进程已死，请求打过去被 RST，表现为"偶发连接被重置"，需要后端优雅关闭（drain 后 close）或 LB 配 TCP 被动探测；L7 会话保持的 Cookie 要设置 HttpOnly + 只用于粘性标识（别混业务会话）；健康检查探活的是**新建连接**，存量长连接（WebSocket）异常时探活照样 200，需要结合被动探测与业务心跳。

**延伸考点：** 一致性哈希做会话保持时，后端从 3 台扩到 5 台，会话迁移比例怎么算？L7 负载均衡做 TLS 终结后，后端拿到的是明文还是密文，对后端的安全要求有什么影响？

### Q17. 接口升级如何做到不破坏老客户端？版本化、分页与幂等怎么设计？

**问题：** 接口要给 1000 万用户的 App 升级，改动涉及"列表分页行为变化"与"某个字段必填化"。老版本客户端无法立即发版。请设计兼容方案，并说明分页、版本化、幂等的常见做法。

**期望加分项：**
- 能讲清版本化策略：URL 路径 `/v1`/`/v2`、Header 协商（`Accept: application/vnd.x+json;version=2`）各自的优劣（路径直观、Header 不污染 URL 缓存），以及"何时必须新版本"（破坏性变更）
- 能讲清分页方案的演进：offset/limit 的深分页性能问题（大 offset 扫描）与并发下"插入导致重复/漏数据"问题；cursor/keyset 分页（按排序键 + 游标）的稳定性与实现注意点（排序键需唯一）
- 能讲清兼容的落地手段：新老版本双实现并存 + 灰度、字段"加不加必填"的兼容期策略（先可空+告警日志，再收紧）、缺省值兜底
- 能讲清幂等在升级场景的意义：客户端重试/网络抖动下重复请求，配合 `Idempotency-Key` 与唯一约束
- 能讲 REST vs GraphQL vs RPC 的选型（版本化策略各自不同：REST 版本化 URL、GraphQL schema 演进 + deprecation、RPC 靠 proto 字段兼容）
- 能主动提坑：老客户端对未知字段的容忍度（JSON 加字段默认向后兼容，但强类型解析会炸）、时间戳格式变更（int vs string）这类"隐形破坏"

**减分项：**
- 只答"加个 /v2 就行"，说不出 Header 版本化与路径版本化的取舍
- 分页只答"limit/offset 翻页"，不知道深分页性能问题与 cursor 方案的原理
- 不做兼容期设计，直接改接口导致老客户端线上崩
- 不知道"新增必填字段"对老客户端的破坏性

**解答：**

核心原则：**兼容是默认要求，破坏性变更必须走新版本**。先分类变更：加字段（向后兼容，老客户端忽略即可，但注意强类型/严格反序列化的客户端可能因未知字段报错，JSON 下通常安全）、改语义（分页行为、排序、鉴权方式——这是隐形破坏的重灾区）、删字段/必填化（直接破坏）。对第三类，方案是**新老并存**：服务端 `/v1` 保留原逻辑，`/v2` 上新行为，客户端灰度发版后再按节奏下线 v1。版本化位置的选择：路径 `/v1/users` 直观、网关路由简单，但会让同一资源在不同版本路径下缓存分裂；Header 版本化（`Accept: application/vnd.company+json;version=2`）不污染 URL、便于 CDN 缓存，但对客户端实现要求更高（很多 HTTP 客户端不便于自定义 Accept）。实践上内部服务多用路径版本，对外 OpenAPI 生态常结合两者。

**分页**要区分两种需求：**翻页浏览**（用户看第 N 页）与**增量拉取**（feed/同步）。offset/limit 在大 offset（如百万级）时数据库扫描成本线性上涨，且"列表中间插入新数据"会导致下一页重复/漏数据——因为 offset 是相对当前位置的。**cursor/keyset 分页**用"上次最后一条的排序键"作为游标（如 `WHERE id > ? ORDER BY id LIMIT 20`），深翻页性能恒定，且天然免疫插入导致的偏移漂移；代价是排序键必须唯一稳定（常用主键或 (created_at, id) 复合），且无法"跳页"（没有第 N 页概念，但大多数 feed 场景不需要）。升级分页行为就是典型的"语义变更"：新老客户端请求同一接口要按版本返回不同分页结构，这正是要版本化的原因。

**幂等**在升级期尤为重要：老客户端可能因新网关重试机制、弱网而重复提交，下单/转账接口必须防重。做法：客户端生成 `Idempotency-Key`，服务端按 key 去重（Redis 或 DB 唯一约束），重复请求返回首次结果；**兼容期特别注意**——老客户端不带幂等键，服务端要用业务唯一键（如订单号、请求指纹）兜底，不能等客户端升级。

最后说选型：REST 用 URL/Header 版本化；GraphQL 靠 **schema 演进**（新增字段、deprecation 标记，客户端按需取字段，版本化压力小得多，但缓存与 N+1 是代价）；RPC（gRPC/proto）靠字段号兼容（**永不复用已删除的字段号**，加字段用新号，老客户端读到未知字段跳过），内部服务间契约维护成本最低。选型背后都是同一件事：**谁承担兼容成本**——REST 由服务端多版本承担，GraphQL 由查询灵活度换，RPC 由代码生成保证。

实践中的坑：时间戳格式从秒（int）改成毫秒（string）这类"看起来没变"的变更，会静默破坏老客户端的时间解析；删除接口字段前要在新版本灰度期内持续观察老版本调用量归零，否则切流量瞬间老客户端全挂。

**延伸考点：** cursor 分页如果排序键是"点赞数"这种会变化的字段，翻页时会出什么问题，如何用"游标快照 + 冗余排序键"解决？GraphQL 的 deprecation 机制对"必须移除字段"的场景为什么不够用？

- 能主动提坑：TTFB 高不一定是服务端慢（可能是 TLS 握手或代理缓冲）；用浏览器"性能面板"看瀑布图比猜更可靠；优化要有量化前后对比

**减分项：**
- 把 TTFB 直接等同于"服务端慢"，不做拆段
- 分不清 TTFB 与 LCP 的关系，把两者当独立问题
- 优化手段只背名词（"加缓存、上 CDN"），说不出每项解决的是哪一段
- 不做前后对比，凭感觉判断优化生效

**解答：**

先拆 TTFB。`curl -w` 一次能拿到各段耗时：`time_namelookup`（DNS）、`time_connect`（TCP 握手）、`time_appconnect`（TLS 握手）、`time_starttransfer`（收到首字节，含服务端处理）。把四段和基线对比，就能立刻定位"慢在哪一段"：DNS 涨 → 查 Local DNS 与 DoH；TCP 涨 → 查网络质量/跨地域访问；**TLS 涨 → 查握手配置（协议版本、会话复用）**；只有 `starttransfer` 与 `connect` 的差值涨 → 才是**服务端处理慢**，去查接口的慢查询、下游依赖、线程池/连接池排队与 GC。还要排除代理层：Nginx `proxy_buffering` 会攒包导致"服务端其实快、用户首字节晚"。

再看 LCP。LCP 是"最大内容元素可见"的时刻，拆开看：**TTFB（首字节）→ 资源加载（LCP 元素通常是图片/首屏大块）→ 渲染**。常见的 LCP 病灶：LCP 图片没加 `fetchpriority="high"`/`preload`，被其他资源挤占带宽或排在队列后面；首屏需要的 CSS/JS render-blocking（关键 CSS 未内联、JS 未 defer）；图片没有宽高占位导致布局抖动与晚加载；服务端首屏数据接口串行等待。工具上用 Performance 面板的瀑布图（或 Lighthouse）逐项对照，比猜更快。

优化按"收益/成本"排序：**网络层**——CDN 就近 + h2 + TLS 会话复用 + `preconnect`/`dns-prefetch`（提前建连第三方域名）；**服务端**——热点接口加缓存、慢 SQL 索引、把非关键逻辑异步化、加大连接池；**前端**——关键 CSS 内联、非关键 JS `defer`/异步加载、图片加 `width/height` 与 `fetchpriority`、首屏组件按路由拆分。每项优化前后用同一套指标（TTFB 分位、LCP P75）量化对比，避免"优化了但没验证"。

实践中的坑：TTFB 的"首字节"是从**请求发出**算起的，包含网络往返，所以跨地域用户的 TTFB 天生比同机房高，别拿两地数据直接比；监控 TTFB 要按 P50/P95 分位看，平均值会被长尾掩盖；LCP 优化里最容易忽略的是**字体加载**（`font-display: swap` 与 preload 关键字体）与**图片体积**（未压缩的 JPEG 可能占掉一半 LCP 时间）。

**延伸考点：** 如果 curl 直连源站 TTFB 正常、浏览器访问 CDN 域名 TTFB 高，应该优先怀疑哪几层？`fetchpriority="high"` 与 `preload` 在浏览器调度机制里有什么本质区别？

### Q19. 超时与重试：下游慢就把服务拖垮，重试为什么反而会放大故障？

**问题：** 线上服务依赖一个慢接口，调用端设了 10s 超时和"失败重试 3 次"，结果下游故障时本服务线程池被打满、请求雪崩式超时。请分析超时/重试的错误设计，并给出正确方案。

**期望加分项：**
- 能讲清超时分层：连接超时（connectTimeout，短）与读超时（readTimeout，按业务特性定），且**全链路超时递减**（客户端 < 网关 < 服务端），避免内层比外层长导致"外层等着、内层先超时重试"叠加
- 能讲清重试的放大效应：失败重试在故障期等于"把请求翻倍打给已故障的下游"，多级重试（网关重试 × 服务重试 × 客户端重试）会指数级放大，形成重试风暴
- 能给出正确策略：指数退避 + 抖动（jitter）、限制最大重试次数（1-2 次）、**只对幂等请求重试**、对"连接失败"与"读超时"区别对待（读超时可能已执行，重试需幂等兜底）
- 能讲清保护机制：熔断（连续失败阈值后快速失败、半开探测恢复）、限流（信号量/线程池隔离）、舱壁隔离（Bulkhead，独立线程池/信号量防止慢依赖拖垮整个服务）
- 能主动提坑：超时设置过大导致线程/连接被占满（等待即占资源）、重试导致的下游"排队雪崩"、健康检查也走慢依赖把自己拖挂

**减分项：**
- 把"超时 10s + 重试 3 次"当标配，说不清 10s 意味着线程被占 10s
- 不知道全链路超时递减原则
- 重试策略不讲幂等前提，敢对扣款接口无脑重试
- 只答"加熔断"，说不出熔断的阈值、状态与半开机制

**解答：**

先看为什么"慢"会放大成"雪崩"：假设超时 10s，一个线程处理一个请求最多被占 10s——下游故障时所有请求都挂满 10s，线程池（比如 200 线程）只能同时处理 200 个，其余全部排队，排队时间又叠加在 10s 超时里，客户端看到的全是超时；再叠加"失败重试 3 次"，失败率直接放大 4 倍打到下游，下游更慢——这就是故障期的**重试风暴**。所以超时与重试的设计原则，第一优先级是"**别让资源被无效占用**"。

**超时分层**：连接超时要短（如 1-2s，连不上立刻失败），读超时按业务 SLA 定（如 3s），且**全链路递减**——浏览器/App 的超时 < 网关 < 服务端内部依赖，否则会出现"外层 10s 等着、内层 5s 已超时重试，重试结果再叠加"的级联。**重试**三原则：只重试"可安全重放"的请求（GET、幂等操作）；最大重试 1-2 次且**指数退避 + 随机抖动**（1s→2s→4s 并加 0-30% 抖动，防止大批客户端同时重试）；区分失败类型——`connect timeout`/连接拒绝可重试，`read timeout` 可能"服务端已执行"，重试必须依赖幂等键或查询兜底，否则扣款类接口会重复执行。**关键认知：故障期重试是负收益**，流量已经在失败，重试只是把失败再打一遍。

保护机制三件套：**熔断**（circuit breaker）——连续失败率达到阈值（如 50%、30 秒窗口）后熔断，直接快速失败不再请求下游，一段时间后进入**半开**状态放少量探测流量，成功恢复、失败继续熔断——熔断解决的是"让故障下游喘息"；**限流/隔离**——信号量或独立线程池（Bulkhead）为慢依赖单独划分资源，即使依赖全挂也只占它的舱位，不影响主流程；**兜底**——对非关键依赖给默认值/降级响应（如推荐位失败返回空列表），比重试更符合业务价值。

实践中的坑：健康检查探活路径如果也依赖故障下游，服务会被标记不健康、被 LB 摘除，形成"依赖挂了整个服务下线"的连锁——探活要做轻量自检；超时时间要按 **P99 而非平均值**设定，否则长尾请求天天超时重试；重试风暴最典型的现场是"网关重试 × 服务重试 × 客户端重试"三层叠加，每层 2 次，故障流量放大 8 倍，设计重试策略时必须看整条链路的乘数。

**延伸考点：** 熔断器的"半开状态"应该放多少探测流量，如何避免探测请求本身把刚恢复的下游又打挂？读超时后请求可能已执行，对于"转账"这种操作，除了幂等键还有哪些兜底方案？

### Q20. XSS、CSRF 与传输安全：安全防护的优先级到底怎么排？

**问题：** 安全审计报告指出站点存在反射型 XSS、登录接口未启用 CSRF 防护、部分内网接口走明文 HTTP。团队资源有限，请给出防护优先级与落地清单，并说明各措施的防护原理。

**期望加分项：**
- 能讲清 XSS 三类（反射/存储/DOM）与核心防御：**输出转义**（上下文正确转义是根本）、CSP 兜底、`HttpOnly` Cookie 防窃取、输入侧白名单校验
- 能讲清 CSRF 的机制（浏览器自动携带 Cookie，跨站请求"借用户身份"）与现代防御：`SameSite` Cookie 为主、CSRF Token（同步器模式）为辅、敏感操作校验自定义头/二次确认
- 能讲清传输层：全站 HTTPS、HSTS（`max-age` + `includeSubDomains` + 预加载列表）、证书校验不豁免（客户端代码里关闭校验是红线）
- 能给优先级排序：① XSS（最容易被利用、影响面大）→ ② HTTPS/传输层 → ③ CSRF（有 SameSite 后成本低）→ ④ 纵深（CSP、安全头）
- 能主动提坑：只做输入过滤不做输出转义（XSS 的本质在输出）、把 token 放 URL 参数（日志泄露）、CSP 配置过严误伤内联脚本、`SameSite=None` 且无 Secure 直接失效

**减分项：**
- 只会背"转义、加 token"，说不清 XSS 的根因是"不可信数据进入了执行上下文"
- 把 CSRF 防御还停留在"加 token"单一方案，不知道 SameSite 已是主流
- 不知道 HSTS 与 CSP 的具体配置字段
- 优先级排序拍脑袋，说不清"为什么先修 XSS"

**解答：**

先给优先级：**① XSS → ② 传输层（HTTPS/HSTS）→ ③ CSRF → ④ 纵深防护**。理由是风险敞口：XSS 一旦可利用，攻击者能偷 Cookie、钓鱼、伪造请求，且反射型 XSS 修复成本最低（改一处输出转义）；传输层裸奔时，中间人能把明文响应**注入脚本**，等于绕过了所有 XSS 防护，所以 HTTPS 是 XSS 的前置防线；CSRF 在现代浏览器 + `SameSite` 下默认已缓解大半，修复成本最低。

**XSS**：根因不是"输入没过滤"，而是"**不可信数据进入了 HTML/JS/CSS/URL 的执行上下文**"。所以核心是**输出转义**——按输出位置转义（HTML 上下文、属性上下文、JS 字符串上下文、URL 上下文各不相同，错了等于没转），配合：输入侧白名单校验（只允许业务期望的字符）、CSP（`Content-Security-Policy: default-src 'self'; script-src 'self'`，限制脚本来源，即使注入也执行不了）、`HttpOnly` Cookie（XSS 拿到页面却拿不到会话）。**CSP 是性价比最高的兜底**，但配置要留好灰度（`report-only` 模式先观察误报再 enforce），`script-src` 过严会误伤内联脚本与第三方 SDK。

**CSRF**：攻击原理是"浏览器自动携带 Cookie + 跨站请求伪造"——用户已登录，攻击页面发请求，服务端无法区分请求是否来自本人页面。现代防御第一选择是 **`SameSite` Cookie**：`Lax`（默认）阻断跨站 POST，`Strict` 连 GET 都断（影响第三方登录跳转，慎用）；需要跨站场景才 `None + Secure`。其次是 **CSRF Token**（同步器模式：页面下发随机 token，提交时校验），注意 token 必须与用户会话绑定、放请求头而非 URL（URL 会被日志/Referer 泄露）。服务端还可校验 `Origin`/`Referer` 头做补充。**注意**：只靠"验证码/二次确认"只能防自动化，防不了真人的恶意操作，适合转账类强操作叠加，不适合做通用防线。

**传输层**：全站 HTTPS + **HSTS**（`Strict-Transport-Security: max-age=31536000; includeSubDomains`，告知浏览器"这个域名永远只走 HTTPS"，从源头消灭"先 http 明文再跳转"的窗口期，也省一次跳转）；客户端/内部服务**禁止跳过证书校验**（自签证书联调时临时豁免、严禁带进生产）；证书私钥权限收紧、自动化轮换。HSTS 的坑：一旦下发，浏览器在 max-age 内强制 HTTPS，若证书/域名配置出错，用户无法通过降级访问，排障时要用新无痕窗口验证。

实践中的坑：后端框架的 ORM/模板引擎默认转义不等于全转义——`v-html`/`innerHTML`/`dangerouslySetInnerHTML` 这类"信任口子"必须逐个审计，这是存储型 XSS 的最大来源；安全头要成套配：`X-Content-Type-Options: nosniff`（防 MIME 嗅探）、`X-Frame-Options`/`frame-ancestors`（防点击劫持）、`Referrer-Policy`（防 Referer 泄露 token）。安全是组合拳，任何单点方案都假设"防线会被绕过"，纵深才有意义。

**延伸考点：** CSP 的 `script-src 'nonce-xxx'` 方案怎么配合动态内联脚本使用，与 `'unsafe-inline'` 相比安全性差异在哪？如果攻击者能控制你的前端构建产物（供应链攻击），CSP 还能防住吗？
