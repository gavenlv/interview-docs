# 通用 · 计算机网络（面试题库）

本文件面向后端、运维与网络岗位，考察候选人在真实网络工程中的排查与调优能力：TCP/UDP 连接与可靠传输、DNS 与 HTTP/TLS 协议链、抓包与延迟/带宽故障定位、代理与负载均衡、NAT/CDN/WebSocket、IPv6/子网规划与云网络容灾。所有题目均为线上可复现的场景化问题，重点考察排查路径、量化依据与方案取舍，而非协议概念背诵。难度自 Q1 至 Q20 从实践基础、中阶调优逐步过渡到高阶架构与开放性思考。

### Q1. 服务器上 TIME_WAIT 上万导致端口耗尽，怎么处理？

**问题：** 线上服务报"Address already in use"或新建连接失败，`netstat` 看到数万个 TIME_WAIT，你们是怎么定位和处理这类问题的？

**期望加分项：**
- 先量化确认是否真的端口耗尽：`ss -s` 看 TIME_WAIT 量、查 `/proc/sys/net/ipv4/ip_local_port_range` 可用端口数，结合连接建立速率算出是否会触顶
- 能说清 TIME_WAIT 存在的原因（可靠终止连接 + 防旧报文串扰），而不是"它没用就要清掉"
- 处理顺序正确：优先解决短连接根因（连接复用/连接池/keep-alive），而不是一上来就调内核参数
- 知道 `tcp_tw_reuse`（依赖 tcp_timestamps）与已废弃的 `tcp_tw_recycle`（内核 4.12 移除、NAT 下有严重副作用）的区别
- 能联系线上实践：服务端短连接 + 高 QPS 场景的典型处理过程

**减分项：**
- 张口就开 `tcp_tw_recycle`，不知道它已被内核移除且 NAT 下会误杀报文
- 分不清 TIME_WAIT 与 CLOSE_WAIT，遇到连接异常统一甩给"TIME_WAIT 太多"
- 只改参数不解决"每秒大量新建连接"这个根因
- 说不出端口耗尽的量化条件（端口数 vs 2×MSL 内新建连接数）

**解答：**
先确认问题再对症。TIME_WAIT 是主动关闭方进入的状态，默认停留 2×MSL（Linux 通常 60s）。端口耗尽与否取决于"每 60s 新建连接数"与"可用端口数"的关系：默认 `ip_local_port_range` 约 32768-60999，可用约 2.8 万个端口，若每秒新建连接超过约 450 个（且保持 60s），就会触顶；CLOSE_WAIT 与 ESTABLISHED 也占端口，实际可用更少。判断方法：`ss -s` 看各状态数量，对比连接建立速率（`ss -s` 或监控新建连接数），即可估算。处理顺序：第一优先是消灭短连接——HTTP 场景开 keep-alive、DB/Redis 用连接池、内部 RPC 用长连接，绝大多数服务这才是根因；第二才是调参数：`net.ipv4.tcp_tw_reuse=1` 允许出站连接复用 TIME_WAIT 端口（依赖 tcp_timestamps 开启，仅对主动发起方有效），`tcp_max_tw_buckets` 过高无意义、调太低会直接丢包且无日志；`tcp_tw_recycle` 已在内核 4.12 移除，且对 NAT 后面的用户因时间戳问题会丢包，绝不能用。第三，服务监听开启 SO_REUSEADDR 避免重启时报 bind 失败。实践中的坑：TIME_WAIT 本身内存开销很小，危害主要是端口占用，所以正确姿势是"复用"而不是"清掉"；调大 `tcp_fin_timeout` 只影响 FIN_WAIT，对 TIME_WAIT 无直接作用。

**延伸考点：** CLOSE_WAIT 堆积的排查思路是什么（应用未关闭连接）？服务端大量 TIME_WAIT 但客户端是 NAT 出口时，调参需要注意什么？

### Q2. 三次握手偶发超时，SYN 发出后没有响应，怎么定位？

**问题：** 线上某客户端连服务端偶发"连接建立超时"，抓包看到 SYN 发出后无响应，也没有 SYN-ACK，你会按什么顺序排查？

**期望加分项：**
- 有分层排查思路：先确认 SYN 是否到达服务端、服务端是否回 SYN-ACK、响应是否回得去，用两侧同时抓包对照
- 能区分半连接队列（SYN Queue）溢出与全连接队列（Accept Queue）溢出，知道 `ss -lnt` 的 Send-Q/Recv-Q 含义与 `netstat -s` 的 ListenOverflows、SYNs to LISTEN dropped
- 知道 SYN Cookie 的触发条件与副作用
- 会查防火墙/安全组/云白名单这类"静默丢包"：iptables、安全组、黑洞路由、IDC 封禁
- 了解 TCP SYN 重传的指数退避间隔（1s、2s、4s...）与 `tcp_syn_retries` 对总超时的影响

**减分项：**
- 只会说"网络不好"或反复重启服务
- 只看客户端一侧抓包，不做两侧对照，无法定位丢在哪
- 分不清"服务端没收到 SYN"与"收到 SYN 但没回 SYN-ACK"是两类完全不同的问题
- 不知道 `netstat -s` / `ss -lnt` 这些能直接暴露队列溢出的统计项

**解答：**
按"SYN 是否到达 → 服务端是否回应 → 响应是否回得来"三步定位，核心是两侧抓包对照。客户端 `tcpdump -i any host 服务端IP and tcp[tcpflags] & tcp-syn != 0`，服务端同步抓，然后逐种情况排查：1) 服务端没收到 SYN：问题在中间链路或入方向策略——云安全组/白名单未放行、IDC 防火墙 ACL、黑洞路由（DDoS 防护误封）、运营商线路问题。这类"静默丢包"无任何 ICMP 报错，只能靠两侧对照发现；2) 服务端收到 SYN 但没回 SYN-ACK：优先怀疑半连接队列溢出——SYN 洪峰或攻击防护误判，看 `netstat -s` 的 `SYNs to LISTEN sockets dropped` / `ListenOverflows`，对策是开 SYN Cookie（`net.ipv4.tcp_syncookies=1`）或调大 `tcp_max_syn_backlog`；3) 服务端回了 SYN-ACK 但客户端没收到/不回 ACK：查服务端出方向路由与防火墙、NAT 映射、客户端防火墙；4) 客户端回了 ACK 但连接仍不成功：全连接队列溢出——应用 accept 太慢，表现为 `ss -lnt` 的 Recv-Q 长期接近 Send-Q 上限，应查应用处理瓶颈。实践中的坑：四层 LB 前面的 SYN 由 LB 代答，服务端抓不到客户端原始 SYN，要先明确拓扑；云厂商安全组丢包完全无痕，两侧对照是唯一高效手段；客户端没设 connect 超时的话，默认 SYN 重试 5 次、总耗时可达 127 秒，表现为"请求挂死"而非报错。

**延伸考点：** 开启 SYN Cookie 后，为什么大并发握手下 CPU 会上升？如何通过监控提前发现 accept 队列溢出而不是等用户投诉？

### Q3. 抓包看到大量 TCP 重传，怎么定位是哪一段链路？

**问题：** 线上服务偶发超时，抓包发现大量 TCP 重传，你会怎么定位是"中间链路丢包、发送端问题还是接收端处理慢"？

**期望加分项：**
- 能区分真实重传与假象：DUP ACK 触发的快速重传（多路径乱序）、Spurious Retransmission（ACK 延迟误判）与 RTO 超时重传（真实丢包，间隔呈指数退避）
- 会用两侧同时抓包做对照：客户端看到重传而服务端确实没收到 → 丢在中间；两端都收到 → 路径或接收端问题
- 会用 tshark/tshark -z 做聚合统计（`tshark -q -z io,stat,60`、`-z conv,tcp`）看重传的时间分布并关联流量高峰
- 能列举常见根因并逐一排除：带宽打满（伴随 RTT 上升）、MTU 黑洞（大包丢小包通）、接收端零窗口（应用/GC 慢导致"假重传"）、网卡丢包（`ethtool -S` 看 rx_dropped/rx_missed）
- 有健康阈值意识：重传率（重传包/总包）通常 1% 以内才算健康，TLS 加密下仍可通过握手与 TCP 层分析

**减分项：**
- 看到 retransmission 就断言"链路丢包"，不做两侧对照
- 分不清快速重传、Spurious Retransmission 与 RTO 重传的差异
- 只盯网络层，忽略应用层（GC 停顿、CPU 打满、慢查询）造成的零窗口"假重传"
- 没有量化与验证闭环，抓完包不知道怎么输出结论

**解答：**
先别急着下"丢包"结论，看清重传类型：Wireshark 中 DUP ACK 之后的重传多为乱序或快速重传（多链路负载均衡、对端网卡哈希不均），Spurious Retransmission 是 ACK 延迟导致的误判，而伴随 RTO（重传超时）的重传才是真实丢包，间隔呈 1s、2s、4s 指数退避。第二步定位链路：客户端与服务端同时抓包（`tcpdump -i any host x -w cap.pcap`），若客户端重传但服务端确实没收到该 seq，丢在中间；若两端都收到，则问题在接收端或路径上被特定设备丢弃。用 `tshark -r cap.pcap -q -z io,stat,60` 看重传包的时间分布，与业务流量、带宽监控曲线对齐。第三步逐根因排查：1) 带宽打满——出口利用率接近 100%（`sar -n DEV`、网卡监控），拥塞丢包往往伴随 RTT 同步上升；2) MTU 问题——大包超时小包正常，抓包看到 ICMP fragmentation needed 被丢弃（PMTUD 黑洞）；3) 接收端处理慢——GC 长停顿、CPU 打满导致接收窗口为 0，发送端表现为 Zero Window 探测，这是"假重传"，要看应用指标而不是加带宽；4) 网卡/驱动丢包——`ethtool -S` 看 rx_dropped、rx_missed 持续增长，重启网卡驱动或调整中断绑定。实践中的坑：云环境虚机抓不到宿主机入口流量，镜像流量要开 ENI/网关抓包或依赖 LB 侧日志；TLS 全加密后看不到应用内容，但 TCP 层分析不受影响；重传率低于 1% 且业务无感时不必过度治理，优先处理与超时告警相关的热点时段。

**延伸考点：** 为什么频繁出现 DUP ACK 但业务完全正常？QUIC 的丢包重传与 TCP 在排查手段上有何不同？

### Q4. 游戏/音视频/日志传输，UDP 和 TCP 怎么选？

**问题：** 游戏动作同步、实时音视频、日志上报三个场景，你们分别用 TCP 还是 UDP？依据是什么？

**期望加分项：**
- 能按业务诉求拆解选型维度：实时性 vs 可靠性、可容忍的延迟与乱序、丢帧可否接受、是否有 NAT 穿透需求
- 知道 TCP 的代价：丢包触发重传导致队头阻塞（HOL blocking），实时场景下延迟抖动剧烈
- 知道选 UDP 后应用层要自己补齐的功课：序号、丢包检测、重传/丢帧策略、FEC（前向纠错）、抖动缓冲、拥塞控制
- 了解行业现状：WebRTC 底层是 UDP（SRTP/QUIC），游戏动作同步多用 UDP + 快照/插值，日志/支付/消息走 TCP 或可靠通道
- 能给出折中方案：QUIC（UDP 之上实现可靠传输 + 多路复用 + 0-RTT）、KCP 等自研可靠 UDP

**减分项：**
- 只会说"UDP 快、TCP 稳"这种空话，说不出代价与适用边界
- 不知道 TCP 在弱网下重传导致的延迟放大与队头阻塞
- 选 UDP 却不提拥塞控制，忽略了"打满链路挤死同机房其他业务"的风险
- 不区分场景谈协议，把游戏和支付一概而论

**解答：**
选型本质是"业务对延迟与可靠性排序"：TCP 提供可靠有序，代价是队头阻塞与重传抖动；UDP 尽力交付，代价是丢包、乱序、无拥塞控制都要应用层处理。分场景：实时音视频（WebRTC）选 UDP——音视频帧天然可容忍丢帧、不可容忍高延迟，用 FEC 前向纠错 + NACK 按优先级重传关键帧 + jitter buffer 平滑，穿透用 ICE/TURN；游戏动作同步选 UDP 为主——状态快照优先于逐包可靠，丢包时用预测 + 插值保持流畅，登录、下单、背包等强一致操作才走 TCP/HTTPS；日志上报、支付、消息这类对完整性敏感的场景选 TCP 或可靠消息通道——延迟可接受，重传换来不丢不漏。工程上还有统一答案 QUIC：在 UDP 上实现可靠传输、多路复用（stream 间互不阻塞）、0-RTT 握手、连接迁移，弱网表现远优于 TCP，适合替代 HTTP 长连接场景；KCP 等基于 UDP 的可靠协议适合自研游戏内部传输。实践中的坑：UDP 应用不做拥塞控制会打满链路，挤压同机房 TCP 业务，需要限速或仿 TCP 的拥塞控制；NAT 下 UDP 映射超时（一般 30s-5min）导致长连接失效，要用心跳保活；UDP 无重传，监控告警要结合包量而非仅字节量，否则丢包时流量"正常"掩盖了问题。

**延伸考点：** 为什么 QUIC 能消除队头阻塞而 HTTP/2 在 TCP 上做不到？游戏里"最终一致性"如何落实到协议层？

### Q5. 用户反馈解析到错误 IP、部分地区访问慢，怎么排查 DNS？

**问题：** 用户反馈部分地区访问变慢甚至解析到错误 IP，你遇到过 DNS 劫持吗？从域名解析到访问慢，你会怎么定位是哪一层的问题？

**期望加分项：**
- 会用 `dig +trace` / `dig +short` 分步定位解析链路（本地缓存 → 运营商 local DNS → 递归 → 权威），用 `nslookup` 指定不同 DNS 对照
- 能区分 DNS 劫持（响应被篡改）与 DNS 污染（网络层丢包/伪响应导致 timeout 或假 IP），知道用 DoH/DoT（如 8.8.8.8 的 853 端口）验证
- 理解 TTL 与故障切换窗口的关系：CDN/切流前把 TTL 调小预热，TTL 太长导致切流后用户仍命中旧 IP
- 了解 split-horizon（内外网解析分离）、智能解析/按地域解析的配置与一致性
- 有监控意识：解析成功率、解析耗时、权威服务器与递归服务器的监控告警

**减分项：**
- 只会说"换个 DNS 试试"，说不清换的是哪一层
- 分不清"解析慢"和"连接慢"，把网络问题都甩给 DNS
- 不知道 DNS 有多层缓存（浏览器、系统、local DNS、递归），排查不区分层
- 不提 TTL 与切换生效窗口，无风险意识

**解答：**
先分清是"解析问题还是连接问题"：`dig 域名` 看解析耗时与结果，再 `curl -w` 测实际连接；解析正常但连接慢，是链路问题，别甩锅 DNS。第二步拆链路：本机缓存（浏览器/系统）→ 运营商 local DNS → 递归（8.8.8.8/114.114.114.114）→ 权威服务器。用 `dig +trace` 看每一跳的响应时间与结果，再对照"走运营商 DNS"与"绕过 local DNS 直接查权威"的差异：若指定权威/公共 DNS 正常、走运营商 DNS 异常，基本锁定运营商缓存污染或劫持。劫持分两类：响应内容被篡改（返回假 IP），可用 DoH/DoT 验证（加密查询无法被篡改）；网络层丢包导致的超时（境外域名常见，表现为 timeout 或返回 0.0.0.0/127.0.0.1），属于污染而非劫持。第三看 TTL 与业务影响：TTL 决定故障切换生效窗口，域名变更前把 TTL 调小（如 60s）并预热；CDN 切流时 TTL 太长会导致用户长时间命中旧节点，处理手段是提前调 TTL + 双写灰度观察。线上做法：内网自建 DNS 做 split-horizon（内网域名走内网 VIP、公网域名转发权威），用 dnsmasq/coredns + 解析成功率/耗时监控。实践中的坑：k8s 里 Pod 的 resolv.conf 默认 ndots:5，短域名查询会先走 search 域产生大量额外查询，偶发解析超时多半与此有关，要调 ndots 或改 FQDN；systemd-resolved 的缓存会干扰抓包与调试结果；不要忽略 `dig @local_dns 域名` 与 `dig @权威 域名` 两者 TTL 值的差异（递归可能截断 TTL）。

**延伸考点：** CDN 切流后 TTL 内用户仍访问旧节点，你们的平滑切换方案是什么？内网 DNS 的缓存命中率如何监控、故障时怎么降级？

### Q6. HTTP/1.1、HTTP/2、HTTP/3 各解决什么问题？你们怎么升级选型？

**问题：** 给现有服务升级 HTTP 协议版本，HTTP/2、HTTP/3 相比 1.1 到底改进了什么？升级前你会怎么评估、升级中会遇到哪些坑？

**期望加分项：**
- 能具体说 1.1 的痛点：同连接请求串行（队头阻塞）、浏览器 6 连接限制、头部冗余
- HTTP/2 的核心：单连接多路复用（stream）、HPACK 头部压缩、二进制分帧；但 TCP 层队头阻塞依旧存在
- HTTP/3 基于 QUIC/UDP：stream 独立重传消除队头阻塞、0-RTT 握手、连接迁移（换网络不重建）
- 选型有取舍：公网 Web/API 上 h2 收益大且代价小；弱网移动端/大流量场景 h3 更优；内网 RPC 通常不值得升级
- 知道升级的工程代价：h2 需要 TLS（h2c 少被网关支持）、老客户端降级兼容、中间设备（LB/防火墙）对 UDP 的支持、监控与抓包配套

**减分项：**
- 只知道"2 比 1.1 快"说不出机制
- 不知道 HTTP/2 在 TCP 上的队头阻塞并未消除
- 忽略部署环境约束（老设备不支持 h2、UDP 被防火墙拦）
- 只谈协议收益不谈改造代价（网关、日志、兼容、监控）

**解答：**
先理解 1.1 的瓶颈：一个 TCP 连接上请求串行，浏览器开 6 个连接并行，但仍受 TCP 拥塞控制限制，且大量请求重复携带头部。HTTP/2 用单连接多路复用（一条连接上多个 stream 并发）解决应用层队头阻塞，HPACK 压缩头部，二进制分帧便于处理——但它跑在 TCP 上，一个 stream 丢包重传会阻塞同连接所有 stream（TCP 层队头阻塞仍在）。HTTP/3 把传输层换成 QUIC（基于 UDP）：每个 stream 独立丢包重传、0-RTT 握手、连接 ID 支持网络切换不重建，真正消除了队头阻塞。选型建议：面向公网的 Web/API，中间链路（CDN、LB、防火墙）支持的话升级 h2 即可获得大部分收益且改动小；弱网移动端、直播/实时推送等大流量长连接，h3 收益明显；内网服务间 RPC 通常不值得升级——长连接 + protobuf 已经够快，引入 h2/h3 反而增加排障复杂度。工程注意点：h2 必须走 TLS（h2c 极少被网关支持），老客户端不支持要保留 1.1 降级；h3 的 UDP 流量要确认云 LB/安全组放行；抓包要配 SSLKEYLOGFILE 才能在 Wireshark 看明文。实践中的坑：h2 的 stream 并发上限与 SETTINGS 协商不当会限制并发；nginx 开启 http2 后 keepalive 配置不当反而性能下降；h2 与 HTTP/1.1 混跑时，按 `$http2` 或 ALPN 分流，日志与限流规则要注意协议差异。

**延伸考点：** HTTP/2 的 Server Push 为什么后来被移除？QUIC 的连接迁移是怎么实现的，对移动弱网体验提升有多大？

### Q7. 全站 HTTPS 后握手变慢，怎么优化？遇到过 OCSP 导致的卡顿吗？

**问题：** 全站开启 HTTPS 后首屏明显变慢，抓包发现 TLS 握手占了大量耗时，你会从哪些层面优化？OCSP 相关的问题遇到过吗？

**期望加分项：**
- 能算清握手成本：完整握手 2-RTT（TLS1.2），每次握手还包含 ECDHE/RSA 非对称运算，弱网下 RTT 是主要成本
- 会用会话复用砍掉一次 RTT：session ticket / session cache，并知道多实例部署要共享 ticket 密钥
- 知道 TLS1.3 把握手降到 1-RTT（0-RTT 部分场景提前发数据），性能收益主要来自协议升级
- 理解 OCSP stapling 机制与"CA 的 OCSP 响应慢/失败导致握手挂起"这个高频坑
- 有量化手段：`curl -w` 各阶段耗时、`openssl s_time`、Wireshark 握手时间分析

**减分项：**
- 只背"HTTPS 更安全"，不会算握手开销
- 不知道 session resumption 与 0-RTT 的区别与适用边界
- 遇到 OCSP 卡顿只会调浏览器/客户端超时，不知道服务端 stapling 可以根治
- 忽略 ECDSA 证书、X25519 曲线、禁用慢套件这类工程细节

**解答：**
TLS 握手慢的本质是"多轮 RTT + 非对称运算"。优化分三层：第一层减少握手轮次——升级 TLS1.3（握手从 2-RTT 降到 1-RTT，且 0-RTT 可在部分场景提前发送应用数据），这是收益最大的一步；第二层会话复用——TLS1.2 场景开启 session ticket 或 session cache（nginx：`ssl_session_cache shared:SSL:10m; ssl_session_timeout 1h;`），复用客户端跳过完整握手（省一次 RTT）；多实例部署时 session ticket 的密钥要统一（共享 `ssl_session_ticket_key`），否则命中不同机器还是要走全握手；第三层降低运算成本——证书用 ECDSA 而非 RSA（验签更快，移动端收益明显），密钥交换用 ECDHE 的 X25519，禁用 3DES/RC4 等慢且弱的套件。OCSP 是高频坑：浏览器验证证书吊销会向 CA 的 OCSP 服务器发查询，公网往返可能数百毫秒，且 CA 偶发宕机或限流时握手直接挂起（表现为偶发"无法建立安全连接"）。解法是 OCSP stapling：由服务器（nginx）定期向 CA 取 OCSP 响应并缓存，握手时随证书一起下发，浏览器不再单独请求；配置 `ssl_stapling on; ssl_stapling_verify on;` 并用 `openssl s_client -status` 验证返回的 OCSP 响应非空。实践中的坑：session ticket 密钥轮换要平滑（保留新旧两套密钥过渡），否则批量失效引发握手风暴；HSTS preload 之前首次访问必然完整握手，靠复用和 TLS1.3 兜底；0-RTT 有重放风险，敏感写操作（支付、下单）不要用 0-RTT 发送。

**延伸考点：** 0-RTT 的重放攻击是怎么发生的，如何防御？客户端→CDN→源站多段各自握手，如何从全链路减少总 RTT？

### Q8. 跨国/跨地域链路带宽大但吞吐上不去，怎么调？

**问题：** 接了一条带宽很大的跨国专线，RTT 约 200ms，但 TCP 吞吐始终上不去，iperf3 实测只有带宽的几分之一，你会怎么分析和调优？

**期望加分项：**
- 能提出带宽延迟积（BDP）模型：BDP = 带宽 × RTT，理想窗口就是 BDP，并给出量化算例
- 知道吞吐上限 ≈ min(接收窗口, 拥塞窗口) / RTT，未开 window scaling 时窗口最大 64KB 是高延迟链路的大坑
- 会调 socket 缓冲与内核参数：SO_SNDBUF/SO_RCVBUF、net.core.wmem_max/rmem_max、tcp_wmem/rmem，并知道应用层设了缓冲后内核不会自动加倍
- 知道拥塞控制算法对"高带宽高延迟高丢包"链路的影响：BBR 按带宽探测而非丢包探测，常能把吞吐提升数倍
- 用 iperf3 加不同 -w/-l 参数实测验证，而不是拍脑袋调参

**减分项：**
- 只知道"加大缓冲区"，说不出窗口与吞吐的定量关系
- 不知道 window scaling（TCP 窗口默认上限 64KB）
- 只看带宽不看 RTT，不理解高 BDP 链路为什么难跑满
- 换 BBR 不考虑内核版本与中间网络设备（队列管理）的兼容性

**解答：**
先建立模型再动手：TCP 吞吐 ≈ 窗口 / RTT，窗口是接收窗口与拥塞窗口的较小者；BDP = 带宽 × RTT 是跑满带宽所需的理想窗口。算例：100Mbps 专线、RTT 200ms，BDP = 100Mbps × 0.2s ≈ 20Mbit ≈ 2.5MB。而 TCP 默认窗口上限 64KB（未开 window scaling），显然远不够，所以高延迟链路上吞吐上不去的第一嫌疑是"窗口不够"，不是带宽。调整步骤：1) 确认两端开启 window scaling（默认开启，但留意中间 NAT/网关设备是否在握手中重置该选项，抓包看 SYN 的窗口缩放因子）；2) 调大缓冲：内核 `net.core.wmem_max/rmem_max`、`tcp_wmem/rmem` 设范围，应用层设 SO_RCVBUF/SO_SNDBUF；注意应用自己设了 SO_RCVBUF 后内核不会按系统默认再自动加倍，且 rcvbuf 上限直接限制接收窗口；3) 换拥塞控制算法：标准 Reno/CUBIC 靠丢包信号收敛，在高丢包链路上窗口被反复打下来，BBR 按"带宽-延迟积"探测模型运行，跨国/跨云链路上常能把吞吐提升数倍；4) 用 iperf3 验证：`iperf3 -c 对端 -t 60 -w 4M`，逐档加大窗口看吞吐变化，定位瓶颈是窗口还是链路丢包。实践中的坑：内核 < 4.9 要手动加载 tcp_bbr 模块；BBR 与中间 FIFO 队列/运营商的队列管理相互作用，可能触发对端限速或与对端其他流量不公平，上线前要在测试链路验证；调大缓冲要防内存滥用（连接数 × 缓冲上限），注意 rmem_max 全局生效；别忽略 qdisc 的 bufferbloat——发送队列过长导致 RTT 膨胀，表现为"带宽上去了延迟爆炸"，用 fq/fq_codel 调度或限速收敛队列。

**延伸考点：** 为什么高 BDP 链路上 CUBIC 呈"锯齿"而 BBR 更平滑？iperf3 多线程（-P）与单线程结果的差异说明了什么？

### Q9. 小请求正常、大请求超时，怎么排查 MTU/分片问题？

**问题：** 线上一个服务"网页能打开、小请求正常，但上传大文件/大包请求超时"，tcpdump 看不到应用层报错，你会怎么定位？遇到过 MTU 相关的问题吗？

**期望加分项：**
- 能联想到 MTU/PMTUD 问题：大包被分片或被丢弃、ICMP "Fragmentation Needed" 被防火墙拦截形成黑洞
- 会用 ICMP 探测路径 MTU：Linux `ping -M do -s size` / Windows `ping -f -l size`，从 1472 递减找"最大不丢包大小"
- 会用 mtr/traceroute 看每一跳丢包位置，并知道中间节点不回 ICMP 是正常现象（关注最后一跳与整体模式）
- 知道常见成因：VPN/GRE/IPSec 隧道封装减小 MTU、PPPoE 1492、云/容器 overlay（VXLAN）MTU 偏小、Jumbo Frame 不一致
- 知道 MSS clamp 这个网关级解法（iptables TCPMSS），比全局改 MTU 更精准

**减分项：**
- 只会看应用日志，不做网络层探测
- 不知道 ICMP 被过滤会导致 PMTUD 黑洞
- 分不清 IPv4 分片与 TCP MSS 协商的区别
- 改完 MTU 不做双向验证

**解答：**
这类问题的经典根因是路径 MTU 小于本地 MTU，且 ICMP "Fragmentation Needed" 被中间防火墙丢弃（PMTUD 黑洞）。TCP 通常靠 MSS 协商（MSS = MTU - 40）自动规避，所以"小包正常、大包失败"多发生在：UDP 大包、TCP 超 MSS 场景（应用手动构造大包）、以及路径 MTU 比 MSS 协商值更小的情况。排查步骤：1) 分层确认——`curl` 上传 1MB vs 100KB 对照，再用 ICMP 探测：Linux `ping -M do -s 1472`（MTU 1500 的满包）与 `-s 1400` 对照，从 1472 递减找到最大不丢包的包长，加 28 字节（IP+ICMP 头）即路径 MTU；2) 若满包丢而小包通，基本锁定 MTU；3) `mtr -n --report 目标` 看每一跳丢包分布（注意中间节点丢包率高是常见假象，重点看最后一跳与整体模式）；4) 抓包确认是否出现 ICMP type3 code4 且被丢弃。常见成因：IPSec/GRE 隧道封装（MTU 减小 20-50 字节）、PPPoE（1492）、云上 overlay 网络（VXLAN 下容器默认 1500 会踩坑，k8s 常配 1450/1400）、机房 Jumbo Frame 配置不一致。修复：网关/隧道场景做 MSS clamp——`iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu`，让 TCP 自动用小 MSS，比全局改 MTU 更精准且只影响过网关的流量；直连场景则把网卡 MTU 调小（如 1400）统一路径。实践中的坑：只调应用层超时是治标不治本；云上裸金属、容器网络 MTU 普遍偏小，要按平台默认值对齐；改动后必须双向验证（A→B 与 B→A 都测），隧道两端要一致。

**延伸考点：** 为什么 MTU 黑洞对 TCP 影响有限、对 UDP 影响大？Jumbo Frame 配置不一致会表现为什么样的间歇性故障？

### Q10. 连接池、keep-alive、TIME_WAIT 是什么关系？连接池该设多大？

**问题：** DB/Redis 连接池的 maxActive、minIdle 你们怎么定？HTTP keep-alive、TCP keepalive、连接池三者是什么关系？改错了会踩什么坑？

**期望加分项：**
- 能给出连接池大小的推导逻辑（并发需求 = TPS × 单请求耗时），而非固定值，并受 DB max_connections 约束
- 能理清三个概念：TCP keepalive（内核级探测死链，默认 2h）、HTTP keep-alive（应用级连接复用）、连接池（连接的借还管理）
- 知道 keep-alive 与 TIME_WAIT 的关系：复用减少握手与 TIME_WAIT，但空闲连接被服务端超时回收时要能感知重建
- 会配连接池关键参数：maxActive、maxIdle/minIdle、获取连接超时、空闲回收、泄漏检测（如 HikariCP leakDetectionThreshold）
- 有监控意识：active/idle、wait 次数、连接创建速率，主从切换后能快速剔除死连接

**减分项：**
- 背"连接池越大越好"，说不出推导与约束
- 把 HTTP keep-alive、TCP keepalive、连接池混为一谈
- 不知道连接池参数语义，或不知道服务端 keepalive_timeout 与客户端空闲回收时间要匹配
- 不监控连接池指标，出问题只能重启

**解答：**
连接池大小不是固定值，而是"并发需求 + 复用率"的产物：并发需求 ≈ TPS × 平均请求耗时（如 1000 TPS × 50ms = 50 并发），DB 连接池在此基础上留 1-2 倍余量，但必须受 DB max_connections 约束——所有实例 × 每池 max 的总量超过 DB 上限就会排队或报错，连接池不是越大越好。理清三个概念：TCP keepalive 是操作系统级探测死链（默认 7200s，可调 tcp_keepalive_time），HTTP keep-alive 是应用级"同一条 TCP 连接上复用多个请求"，连接池是应用对连接生命周期的借还管理。keep-alive 的收益是减少握手与 TIME_WAIT；风险是空闲连接占用资源，且服务端主动断开（nginx keepalive_timeout 65s）后客户端复用会拿到死连接——所以连接池的"空闲连接最大存活时间"要大于服务端 keepalive_timeout，很多 HTTP client 会自动重试一次来兜底。参数要点：maxActive 控制上限、maxIdle/minIdle 控制空闲水位（minIdle=0 会导致冷启动大量建连、TIME_WAIT 短时暴涨）、获取连接超时设置过短会在 DB 抖动时瞬间打满、泄漏检测（HikariCP leakDetectionThreshold、Druid removeAbandoned）抓未归还的连接。实践中的坑：主从切换/实例重启后，连接池里全是死连接，靠 validationQuery/ping 逐条校验会引入额外开销且拖慢恢复，成熟方案是监听连接建立事件或主动清池重建；连接池与线程池要匹配（线程数 > 池上限时大量线程在等连接）；别忽略"连接创建本身的开销"——每秒新建连接数决定 TIME_WAIT 与 CPU 开销，连接池核心价值是复用。

**延伸考点：** 从连接池拿到一条"已失效"的连接，首次请求失败第二次成功，为什么？主从切换后连接池如何快速收敛、避免雪崩？

### Q11. 接口平均 20ms 偶尔飙到 500ms，怎么用抓包定位延迟在哪？

**问题：** 接口平均 20ms，但偶发飙到 500ms，业务日志和 DB 慢查询都没异常，你会怎么用抓包定位延迟发生在"网络中还是两端处理"？

**期望加分项：**
- 会用 Wireshark 的 TCP 时间分析：Statistics → TCP Stream Graphs（RTT/Time-Sequence 图）、Expert Info，区分链路耗时与两端处理耗时
- 会用 tshark 聚合统计（`-q -z io,stat`、`-z conv,tcp`）看延迟分布是全局（链路）还是个别连接（应用/连接自身）
- 知道 Nagle + 延迟 ACK 交互导致的 40ms 延迟经典坑（TCP_NODELAY）
- 会做单请求时间分解：客户端发出 → 服务端收到 → 服务端响应 → 客户端收到，两侧抓包时间戳对齐
- 结合应用证据交叉验证：GC 日志、线程 dump、CPU，判断延迟点在应用内还是网络

**减分项：**
- 只看平均延迟，不分析 P99 与分布形态
- 抓了包不会看 Expert Info 和 RTT 图，只会数包
- 拿"网络波动"背锅，没有两侧数据对照
- 不知道 40ms（延迟 ACK 定时器）这个经典数字

**解答：**
定位偶发延迟要用"时间分解"而非拍脑袋。两侧同时抓包（客户端与服务端，中间有 LB 再抓 LB 侧），用 Wireshark 打开后：1) Statistics → TCP Stream Graphs → Time-Sequence（吞吐）与 Round Trip Time 图，RTT 图能直接看出"哪一段往返变长"；对单请求（按请求 ID/payload 过滤）做时间分解：客户端发请求到服务端收到 = 上行链路耗时，服务端收包到回包 = 服务端处理耗时，回包到客户端收到 = 下行链路耗时；2) 用 `tshark -q -z conv,tcp` 聚合所有连接的 RTT 分布——所有连接同时飙高说明链路/交换机问题，仅个别连接飙高说明该连接自身问题（Nagle、应用阻塞、连接老化）；3) 经典坑排查：Nagle 算法（小包合并）与延迟 ACK（对端等 40ms 才回 ACK）互相等待，产生规律性 40ms 级毛刺，解法是应用层设置 TCP_NODELAY（HTTP/2、多数 RPC 框架默认已关闭）；4) 延迟点在"服务端收到 → 发出响应"之间的话，去看 GC、慢查询、线程池队列与 CPU，而不是继续抓包。实践中的坑：Wireshark 默认显示相对时间，跨端对齐要用 `frame.time_epoch` 统一绝对时间戳，或找对称报文（如握手、PING）做锚点，两侧时钟不同步时不要直接相减；只抓业务端口会漏掉 DNS、TLS 握手、代理层耗时，把 DNS/证书/建连时间一并纳入分解；CDN/LB 场景延迟分布常呈双峰（命中缓存 vs 回源），先按是否命中拆组再分析；偶发问题抓包时长要够（覆盖故障时段），用 ring buffer 持续抓，别抓 10 秒就收工。

**延伸考点：** P99 高但平均低，你们的监控怎么捕捉这种长尾？两侧抓包时间不同步时，如何判断延迟在客户端侧还是服务端侧？

### Q12. nginx 反代出现 502/504，超时和排查怎么配？

**问题：** nginx 反代后端，线上偶发 504，日志显示 upstream timed out；另一个服务频繁 502。你会怎么配置超时？502 和 504 的排查路径有何不同？

**期望加分项：**
- 能说清三个超时的语义：proxy_connect_timeout（连不上）、proxy_send_timeout/proxy_read_timeout（读写间隔，默认 60s，是"间隔"不是总时长）
- 知道 502 vs 504 的差异：连接建立失败/无效响应 vs 连接成功但响应超时，对应不同的故障类型
- 会配 upstream keepalive 复用连接（upstream keepalive 32 + proxy_http_version 1.1 + Connection ""）
- 知道 proxy_next_upstream 重试的幂等性风险，写请求默认不重试或仅重试连接错误
- 会看 error.log 的具体错误行与 access.log 的 upstream_response_time / request_time 对比

**减分项：**
- 只会调大 proxy_read_timeout，不查后端为什么慢
- 不知道 502 和 504 的根因差异
- 不了解 proxy_next_upstream 对非幂等请求的重复执行风险
- 不看日志就猜，或不知道 upstream 域名解析是启动时缓存

**解答：**
超时配置是"保护层"，根因在后端，但配错会放大故障。nginx 三个超时：proxy_connect_timeout（连接 upstream 超时，默认 60s）、proxy_send_timeout（两次写之间的间隔）、proxy_read_timeout（两次读之间的间隔，默认 60s）——注意是"间隔"而非总耗时，慢接口只要持续有数据就不会超时。排查先分类型：502 = 连不上或收到无效响应（upstream 未启动、拒绝连接、DNS 解析失败、防火墙拦截），504 = 连接成功但响应超时（后端慢、队列积压、GC 停顿、死锁）。看 error.log 具体行：`connect() failed (111: Connection refused)` 是 502，`upstream timed out` 是 504；再对比 access.log 的 upstream_response_time（后端耗时）与 request_time（含 nginx 排队与网络）——request 大而 upstream 小，说明耗时在 nginx 侧（连接建立、排队）。配置要点：1) 后端超时匹配：proxy_read_timeout 60-120s 且与后端应用超时对齐，避免 nginx 先断而后端还在算；2) 复用连接：upstream 块 `keepalive 32;` + `proxy_http_version 1.1;` + `proxy_set_header Connection "";`，否则每次请求新建连接、TIME_WAIT 暴涨；3) 重试谨慎：proxy_next_upstream 默认重试错误与超时，对 POST 可能重复扣款，写接口要显式关闭或仅 `error timeout` 且业务侧做幂等；4) 健康检查：被动检查（max_fails/fail_timeout 摘除）够用，主动检查需要 plus 或外部探活。实践中的坑：upstream 写域名时 nginx 启动解析一次并长期缓存旧 IP（要 njs 动态解析或直接写 IP）；upstream 是 HTTP/1.0 时 keepalive 无效；SSE/长轮询/WebSocket 需要 `proxy_buffering off` 否则数据被缓冲到连接结束才返回，表现为"实时数据延迟到达"。

**延伸考点：** access.log 里 request_time 远大于 upstream_response_time，说明了什么？WebSocket/SSE 过 nginx 还需要哪些配置才能正常工作？

### Q13. 负载均衡用 L4 还是 L7？怎么选、有哪些坑？

**问题：** 你们对外 HTTP 网关用的是四层还是七层 LB？数据库、Redis 为什么通常用四层？各自的坑在哪里？

**期望加分项：**
- 能清晰对比：L4（IP:PORT 转发，TCP/UDP 透明、性能高、连接数大、不解析应用层）vs L7（HTTP 路由、Header/Cookie 维度、SSL 终结、限流、灰度、压缩）
- 选型有依据：DB/Redis/Kafka/自研长连接协议用 L4（或客户端一致性哈希）；对外 HTTP/API 用 L7，SSL 终结放 L7
- 知道 L4 的坑：DR 模式回包问题、TCP 探测健康检查的误判（accept 队列满仍探测成功）、连接数 vs 新建连接数
- 知道 L7 的坑：X-Forwarded-For 可伪造、header 大小限制、SSL 终结后明文的信任边界、WebSocket 长连接配置
- 了解常见实现与取舍：LVS/HAProxy/nginx、云 ALB/NLB，会话保持（sticky/一致性哈希）的差异

**减分项：**
- 说不清"四层不解析 HTTP"带来的能力边界
- 不知道 SSL 终结放在哪一层对性能与架构的影响
- 把"会话保持"与"一致性哈希"混为一谈
- 只谈协议对比，不谈健康检查、故障切换等高可用细节

**解答：**
选型核心是"转发粒度与能力"的取舍。L4 负载均衡（LVS/DR、云 NLB）按 IP+端口转发，不解析应用层：转发快、并发连接上限高、对协议透明（TCP/UDP 都能负载），但无法按 URL/Cookie 路由、不能做 SSL 终结与七层限流。L7（nginx、云 ALB、HAProxy 可配）解析 HTTP：能按域名/路径路由、SSL 终结、Header 改写、限流、灰度、压缩，代价是每请求解析、连接数上限低、加解密吃 CPU。工程选型经验：数据库、Redis、Kafka、自研 TCP 长连接用 L4（或客户端内置一致性哈希做负载）；对外 HTTP/API 用 L7 且 SSL 终结放 L7（后端内网走明文，省去每实例加解密）；混合场景用 L4 透传 + 业务自管理。L4 的常见坑：DR 模式后端要在 lo 绑 VIP 并禁用 ARP 应答，否则回包打到 LVS 自身（请求的源 IP 是客户端），表现为"连得上但请求超时"；TCP 探测健康检查只验证"能建连"，accept 队列满时仍探测成功，需要配合应用层探活；新建连接速率才是 L4 的瓶颈指标（连接数大不等于新建连接快）。L7 的常见坑：X-Forwarded-For 可伪造，取真实 IP 要信任最右侧或专用头，否则限流/风控可被绕过；默认 header 上限 8KB，大 Cookie/长 token 会被截断；SSL 终结后到后端的明文链路要纳入信任边界（内网可被横向时不可信）；WebSocket/SSE 要调长超时并关缓冲。实践中的坑：四层 LB 后端是 HTTP 服务时无法按域名分流，只能多 VIP；一致性哈希 vs sticky session：前者按 key 哈希分发（无会话状态也可用），后者按连接/会话绑定（有状态场景），选错会导致热点不均或会话丢失。

**延伸考点：** 四层 LB 做会话保持（源 IP hash）有什么问题？健康检查探活要多深才算"可靠"？

### Q14. NAT 类型与内网穿透：打洞失败怎么办？

**问题：** 内网部署的服务要暴露给公网，有人用端口映射、有人用 frp/ngrok、有人做 P2P 打洞。它们分别解决什么问题？P2P 打洞失败怎么办？

**期望加分项：**
- 能说清 NAT 类型（Full Cone / Restricted Cone / Symmetric）与打洞成败的关系，symmetric NAT 基本打不通只能走中继
- 理解 STUN/TURN/ICE 的分工：STUN 探测公网映射地址、TURN 中继兜底、ICE 是"先打洞、失败退化中继"的决策框架
- 了解 frp/ngrok 的服务端中转原理（内网端主动外联注册、两路连接桥接），以及转发延迟/带宽/安全边界
- 知道 NAT 映射会话超时与保活（UDP 心跳、TCP keepalive 维持映射）
- 有安全意识：frp 等于给内网开了一扇门，要鉴权、TLS、限制来源

**减分项：**
- 分不清 SNAT/DNAT 与端口映射的差别
- 不知道 symmetric NAT 下打洞基本失败，必须 TURN 中继
- 只谈工具（frp 怎么配）不谈原理与边界
- 忽略安全：不鉴权、无加密的 frp 暴露

**解答：**
本质是解决"内网地址不可路由 + NAT 会话状态"两个问题，方案分三类：1) 显式映射——NAT 端口映射（DNAT），把公网 IP:PORT 固定映射到内网 IP:PORT，适合有公网 IP 的场景（办公室、云主机）；2) 主动外联中转——frp/ngrok 原理：内网端主动连公网的 frps 注册，公网客户端连 frps，frps 把两条连接桥接，适合完全无公网 IP 的纯内网环境，代价是流量都要经过中转（带宽、延迟受限于中转机）；3) P2P 打洞（NAT 穿透）——两端各自向公网 STUN 服务器注册 NAT 映射（公网 IP:端口），再互相对着对方的映射地址发包"打通"直连。能否打通取决于 NAT 类型：Full Cone 最容易（任意外部地址可复用映射）、Restricted Cone 次之（需先向内发包）、Symmetric（每个会话独立映射端口）基本打不通，只能退化为 TURN 中继。ICE 就是把"打洞 + 中继兜底"串起来的决策框架（WebRTC 标配）。实践中的坑：NAT 映射有会话超时（UDP 一般 30s-5min），长连接要心跳保活维持映射，否则打通的通道会静默失效；企业出口多层 NAT（防火墙 + 路由器）会加剧对称性，打洞成功率大降；安全上 frp 中转等于开了内网门——必须加 token 鉴权 + TLS、限制访问来源与端口、监控异常流量，历史上 frp 未鉴权被滥用扫描的事件不少；云上端口映射还要注意安全组与外层 LB 的叠加放行（两层都放行才通）。选择建议：有公网 IP 用端口映射 + 白名单；无公网 IP 用 frp 中转；追求低延迟点对点用 ICE 打洞 + TURN 兜底。

**延伸考点：** UDP 打洞成功后为什么还要持续发心跳？NAT 会话表溢出（家用路由器带机量超限）会表现为什么故障？

### Q15. 接入 CDN 后命中率低、回源频繁，怎么分析和提升？

**问题：** 服务接入 CDN 后，有的用户还是慢，监控发现回源率很高、源站带宽吃紧。你会怎么分析命中率问题并优化缓存策略？

**期望加分项：**
- 能讲清 CDN 链路：DNS 调度（就近选点）→ 边缘节点 → 命中缓存或回源（多级回源），命中率是核心指标
- 知道缓存决策机制：Cache-Control（max-age/s-maxage）、Expires、ETag/Last-Modified 协商、private/no-cache 的区别
- 能分析"回源频繁"的常见成因：URL 带随机参数导致缓存 key 爆炸、动态内容误配缓存、TTL 过短、节点新增后的回源上升
- 会用指标区分问题：请求命中率 vs 字节命中率（动态小文件看字节命中率更准）、回源带宽/回源次数监控
- 知道刷新（purge）与预热（prefetch）的适用场景：版本更新、源站压测前预热避免回源风暴

**减分项：**
- 只知道"CDN 是缓存加速"，说不出链路与命中率指标体系
- 不知道 Cache-Control 与 Expires 的优先级、协商缓存与强制缓存
- 把动态接口也设置成长缓存（或反之），无业务区分意识
- 忽略 HTTPS 证书与回源配置（回源 HOST、证书不一致）

**解答：**
CDN 的核心指标是命中率与回源成本。链路是：DNS 按运营商/地域调度到就近边缘节点 → 节点查缓存命中直接返回，未命中回源（源站或上级节点）。接入后"还是慢"先拆环节：1) 调度问题——解析结果离用户远（运营商 local DNS 缓存脏 IP、劫持），用 `dig 域名` 与 `curl -I` 对比，必要时上 HTTPDNS/DoH 或调整调度权重；2) 命中率问题——回源频繁的常见原因：响应头没带 Cache-Control 或带了 no-cache、URL 带随机参数（时间戳/token）导致缓存 key 爆炸、TTL 太短、动静未分离。指标要看全：请求命中率与字节命中率是两个维度，小文件动态内容多时字节命中率更能反映回源带宽成本。3) 缓存策略优化：静态资源版本化（文件名带 hash，设置 s-maxage 一年）、统一缓存规则（按目录/后缀/Cookie 决定）、忽略无关 query 参数、动态接口用 s-maxage 控制 CDN 层缓存（公开接口可缓存数秒到分钟）或走私有缓存（private 不缓存）。4) 运维配套：版本发布用 purge 精确刷新（按 URL/目录，通配符有限制）、核心资源上线前 prefetch 预热（避免发布瞬间回源雪崩）、源站带宽与回源频率监控告警。实践中的坑：HTTPS 场景 CDN 证书与回源证书必须一致，否则回源 526/证书错误；新增边缘节点或调度策略调整后短期回源上升是正常现象，不是故障；Range 回源（大文件断点续传）没开会导致大文件回源效率低；压缩（gzip/br）要在 CDN 层统一开启，否则回源重复压缩。

**延伸考点：** 动态 API 接口能不能用 CDN 加速？节点调度除了 DNS 还有哪些手段（HTTPDNS/Anycast）？预热在什么场景必须用？

### Q16. WebSocket 百万长连接：断线重连、重连风暴、会话路由怎么做？

**问题：** 你们做实时推送，WebSocket 连接偶发断开，客户端恢复时出现"重连风暴"打垮网关；连接数涨到百万级后单机扛不住。你会怎么设计心跳、重连与会话路由？

**期望加分项：**
- 能说清 WebSocket 与 HTTP 的关系：Upgrade 握手（101）、全双工帧、与 HTTP 长连接的差异
- 心跳设计合理：服务端 ping 客户端 pong，超时（如 30s 未 pong）即断，防"假活"僵尸连接
- 重连策略：指数退避 + 随机抖动（1s、2s、4s…上限 60s ±30% 抖动），避免服务恢复瞬间雪崩重连；重连状态机防重复定时器
- 量化认识单机容量：fd 上限（ulimit/file-max）、单连接内存（socket 缓冲 + 应用对象几 KB~几十 KB）、epoll 事件循环而非每连接一线程
- 水平扩展后的会话路由：用户连接在哪台节点，推送如何定位（一致性哈希 + 注册中心/会话表、消息广播）
- 平滑发布：先摘流量 → 排空 → 再关连接，或连接迁移协议

**减分项：**
- 说不出 101 升级过程，把 WebSocket 当独立协议
- 重连不做退避，故障恢复时自己把服务打垮
- 不处理假活（连接还在但已死），fd 被僵尸连接吃光
- 不知道单连接内存与 fd 上限的量化关系，百万连接没有内存/内核层面的准备

**解答：**
长连接工程的核心是"状态维护与生命周期管理"。握手：WebSocket 复用 HTTP 通道升级（Upgrade: websocket 返回 101），之后全双工帧通信；nginx 反代要配长超时 + `proxy_buffering off` 并透传 Upgrade 头。断连是常态，重点在重连与保活：客户端 onclose 后不能立即重连（服务端抖动瞬间所有客户端同时重连 = 重连风暴），用指数退避 + 随机抖动（1s、2s、4s…上限 60s，加 ±30% 随机量），并保证重连定时器互斥（重连中不触发第二个定时器）；服务端定期 ping（如 30s），超时未 pong 直接断开，清理"假活"僵尸连接——它们占着 fd 与内存却不产生流量，是长连接服务内存缓慢上涨的元凶之一。单机容量量化：Linux 默认 fd 上限 1024 远不够，要调 ulimit -n 与 file-max；每连接内存按 socket 收发缓冲 + 应用对象估算（几 KB ~ 几十 KB），16G 内存单机扛几十万连接需要 epoll + 合理缓冲设置，绝不能每连接一个线程；百万连接要靠水平扩展，扩展后出现"会话路由"：用户连在节点 A，推送方要找到它——常见方案：连接信息上报注册中心（Redis/zk）建会话表、一致性哈希定位节点、或基于 MQ 广播由持有该连接的节点消费；发布/缩容要平滑：摘流量 → 等待存量连接排空/优雅下线 → 再关闭，配合客户端重连即可无缝迁移。实践中的坑：移动网络 NAT 超时回收（30s-5min）导致连接假活，心跳间隔要小于 NAT 映射超时；wss（TLS）在 LB 终结后要确认客户端与服务端协议一致；推送积压要处理背压（单条慢连接拖垮内存），按房间/用户限速或丢弃策略明确。

**延伸考点：** WebSocket 与 SSE 怎么选？连接迁移时用户的订阅状态如何恢复（reconnect 后重新拉取还是服务端推送）？

### Q17. 机房子网规划与 IPv6 改造，怎么设计不踩坑？

**问题：** 你们要规划一套新机房的私有网段（或做一次 IPv6 双栈改造），你会按什么原则设计？遇到过网段重叠、IPv6 改造失败的坑吗？

**期望加分项：**

- 双栈改造完整：DNS AAAA、应用/中间件监听 v6（::）、安全组/防火墙 v6 规则、客户端 happy eyeballs 回退
- 有过渡认知：NAT64/DNS64 仅作临时过渡，运营商量级 v6 路由质量要监控

**减分项：**
- 只会算掩码，说不出设计原则与扩展性
- 不知道 IPv6 无 NAT、SLAAC 等核心差异，拿 v4 思维套 v6
- 改造只喊"开启 IPv6"，忽略 DNS 与安全组配套
- 不考虑网段冲突（合并/对等连接时才发现重叠）

**解答：**
分两种场景。规划场景：私有网段设计原则是"按环境 + 业务维度切割 + 预留余量 + 两两不重叠"。例如在 10.0.0.0/8 内：10.1.x.x 生产、10.2.x.x 测试、10.3.x.x 工具链，环境内再按业务切 /24~/20，每段预留 30% 扩容空间；关键约束是"不重叠"——未来 VPC 对等、专线互联、k8s 多集群时网段重叠是灾难（路由冲突、地址不可达），容器网络要同时规划 Pod CIDR / Service CIDR / Node 网段三套，避免与业务网段打架；子网切小段便于 ACL 精细化，但过碎会浪费地址与路由表项，按业务规模取 /24~/22 比较合理。IPv6 改造场景：核心差异是"无 NAT、地址即公网、SLAAC 无状态分配"，改造不是改个 IP 格式：1) DNS 配 AAAA 并验证解析；2) 应用/中间件确认监听 v6（::）并处理双栈 socket；3) 安全组/防火墙必须对 v6 前缀放行（很多人只配了 v4 规则，改造后"看起来开了实际不通"）；4) 过渡期用双栈共存而非直接替换，客户端"优先 v6、失败快速回退 v4"靠 happy eyeballs（浏览器已内置）；5) 无 v6 的存量网络用 NAT64/DNS64 过渡，仅作临时方案。实践中的坑：IPv6 的临时地址（privacy extension）导致出口 IP 频繁变化，白名单类业务要按前缀放行而不是按具体地址；k8s IPv6-only 集群很多镜像、探针不支持，双栈更稳；运营商 v6 路径质量参差，上线后要监控 v6 的 RTT/丢包，质量差就降级 v4；IPv6 地址太长易写错，配置下发要做一致性校验。

**延伸考点：** IPv6 没有 NAT，内网访问外部时"地址暴露"与访问控制怎么处理？子网合并/拆分时如何做到业务无感迁移？

### Q18. 机房带宽被某个业务打满，其他业务全挂，怎么做限速与 QoS？

**问题：** 一个离线任务把机房出口带宽打满，线上业务延迟暴涨。你们怎么做带宽隔离与限速？"带宽没满但延迟很高"又是什么原因？

**期望加分项：**
- 能分维度限速：单连接限速、每 IP 限速、总带宽 QoS；应用层限速（令牌桶/漏桶）vs 网络层限速（tc）的区别
- 会用 tc 的 qdisc/class/filter 三层结构做分层限速（HTB：根设总带宽、子 class 按 rate/ceil + priority 分级），或用 iptables hashlimit
- 理解 bufferbloat：pfifo 队列下突发流量导致队列膨胀、RTT 飙升，表现为"带宽没满但延迟高"，要用 fq/fq_codel 收敛
- 先做流量画像（sFlow/NetFlow/按端口监控）定位谁在占带宽，再治理，而非盲目加带宽
- 应用层配套：nginx limit_req/limit_conn、网关令牌桶，与网络层限速结合

**减分项：**
- 只会说"加带宽"
- 不知道 tc 是 Linux 流量控制入口（qdisc/class/filter），或把限速与限并发混为一谈
- 不懂 TCP 丢包反馈与队列管理的交互（bufferbloat 认知缺失）
- 不做根因治理（业务本身无节流），只靠网络层硬限

**解答：**
先看清形态：是"单个大流量业务挤占"还是"瞬时洪峰打满全带宽"。治理分层：1) 监控先行——按业务/端口/IP 的流量画像，Prometheus 网卡总量不够，要用 sFlow/NetFlow 或按端口拆分，先定位"谁在占带宽"；2) 应用层限速——业务侧有节流能力最好：nginx 的 limit_req（速率，漏桶）、limit_conn（并发）、网关令牌桶，控制单客户端与全局速率；3) 网络层 QoS——Linux tc 分层限速：`tc qdisc add dev eth0 root handle 1: htb default 30`，根上设总带宽，为关键业务建高优先级 class（rate 保证带宽 + ceil 上限 + priority 高），离线任务给低权重 class，保证关键业务有保底带宽；对单 IP 用 iptables hashlimit 或 tc filter 匹配源 IP 限速；4) 理解与 TCP 的交互——网络层丢包会触发 TCP 拥塞控制降速（隐性限速），但默认 pfifo 队列在突发时会"排队不丢包"，造成 bufferbloat：队列膨胀、RTT 飙升、TCP 探测不到丢包而不降速，表现为"带宽没满但延迟爆炸"，对策是把 qdisc 换成 fq/fq_codel（主动队列管理，按流公平排队 + 控制队列延迟）。实践中的坑：tc 配置重启/网卡重启即丢失，要固化到启动脚本；HTB 的 rate（保证）与 ceil（上限）别用反；按端口限速会误伤同端口的其他业务；云上注意入方向与出方向是两条链路，入方向大流量要配合云厂商的流量清洗/带宽包；别忘了日志、备份、监控同步这类"隐形大流量"，定期 review 流量账单与带宽分布。

**延伸考点：** bufferbloat 为什么会导致"带宽未满但延迟高"？fq_codel 如何改善多租户共享出口的公平性？

### Q19. 网关转发大流量 CPU 吃满，零拷贝和网卡多队列能解决什么？

**问题：** 你们的网关/代理转发大流量时 CPU 居高不下，有人说用零拷贝和网卡多队列，有人提 DPDK。它们分别解决什么问题？什么场景值得上？

**期望加分项：**
- 能说清默认数据路径的代价：DMA → 内核缓冲 → 用户态 read/write 多次拷贝 + 内核/用户态切换，CPU 消耗在软中断、拷贝、上下文切换
- 理解零拷贝手段与适用边界：sendfile（page cache 直达 socket）、splice（fd 间零拷贝），前提是"数据不需要修改"（压缩、加密、加头都要过用户态）
- 知道网卡多队列（RSS）按哈希分散流量到多队列 + 软中断绑核（smp_affinity），以及 RPS/RFS 的软件兜底
- 能用 perf top / ethtool -S 验证瓶颈在拷贝还是协议栈，再决定优化手段，有压测数据
- 知道 DPDK 是旁路内核的另一条路：用户态驱动收包、自带协议栈，适合网关/DPDK 场景，代价是耦合网卡与内核放弃

**减分项：**
- 只会背"零拷贝减少拷贝"，说不清减在哪几处、为什么
- 不知道 sendfile 对 HTTPS/加密场景失效
- 把 DPDK 当万能药，不考虑业务是否值得
- 不做瓶颈定位与压测，凭感觉优化

**解答：**
先讲清默认路径的代价：网卡收包 DMA 到内核 ring buffer → 软中断处理 → 拷贝到 socket 接收缓冲 → 用户态 read 拷到应用缓冲 → 写回 socket 发送缓冲 → 发送队列 → DMA 发出，同一份数据被拷贝多次、内核/用户态来回切换多次，CPU 热点集中在软中断、memcpy 与上下文切换。优化分两条路：一是减少拷贝（零拷贝）——sendfile 让数据在内核内直接从 page cache 发到 socket（省掉用户态拷贝），splice 可在两个 fd 之间搬移而不经过用户态，nginx 的 `sendfile on` 是典型应用（静态文件、大文件下载收益明显）；前提是数据无需修改，一旦要压缩、加密、加 HTTP 头就必须过用户态，所以全站 HTTPS 后静态文件的 sendfile 收益打折。二是摊平中断——多队列网卡（RSS）按五元组哈希把流量散到多个队列，每个队列独立软中断，再配合绑核（irqbalance 或手动写 /proc/irq/*/smp_affinity）让软中断与处理进程同核，减少 CPU 争抢与 cache miss；软件层面 RPS/RFS 可做类似分发。更进一步是 DPDK：旁路内核，用户态驱动直接收包、自带协议栈，能到百万级 PPS，但代价是应用耦合特定网卡、放弃内核协议栈，适合网关/转发类专用场景，普通业务没必要。实践中的坑：先验证瓶颈再动手——`perf top` 看热点（软中断 vs memcpy vs 锁），`ethtool -S` 看 rx_dropped/队列分布，多队列要网卡支持（ethtool -l/-L 查看与开启）；绑核要确认与 cgroup cpuset、CPU 隔离配置一致，否则白绑；零拷贝对小包、低吞吐场景收益不明显，别为了"先进"而改。

**延伸考点：** 为什么 TLS 终结后 sendfile 失效？RSS 哈希不均导致某个队列打满，怎么查、怎么调？

### Q20. 从客户端到源站的整条链路有哪些单点？容灾与云网络怎么设计？

**问题：** 你们整个对外服务的网络链路从用户到源站，画出来有哪些单点？机房级/云厂商级故障时怎么切换？切换后为什么有时还是不可用？

**期望加分项：**
- 能画出完整链路拓扑并逐一识别单点与故障模式：DNS → CDN/入口 LB → 网关集群 → 业务集群 → 缓存/DB，并说明每一层的冗余手段
- 容灾体系完整：多线路/多运营商接入、多机房（同城双活/异地多活）、DNS 切换（TTL 前置调小）、健康检查自动摘除、长连接可重连
- 知道"切换后仍不可用"的常见坑：DNS TTL 与客户端缓存、长连接未重连、依赖链未迁移、数据层仍是单点
- 云网络设计有要点：VPC 网段规划（避免冲突）、多 AZ 子网、安全组/ACL 最小权限、NAT 网关统一出网、ALB/NLB 按场景选型
- 有演练意识：故障注入、RTO/RPO 指标、定期演练切换剧本，能说清同城双活与异地多活的差异

**减分项：**
- 画不出链路，只会说"做高可用"
- 只有入口高可用，数据层（缓存/DB）无容灾，切了等于没切
- 忽略 DNS TTL 与客户端缓存导致的切换生效延迟
- 安全组/ACL 凭感觉开端口，无最小权限与生命周期管理
- 没有演练，切换剧本停留在文档里

**解答：**
容灾设计的正确姿势是"先画链路，再逐点消单点"。典型链路：用户 → 运营商网络 → DNS 调度 → CDN/入口 LB → 网关集群 → 业务集群 → 缓存/DB。逐点看：DNS 是第一个单点（厂商故障/TTL 切换慢），用多 DNS 厂商 + 监控自动切换、关键域名 TTL 保持较小；入口 LB 多 AZ 部署（云 ALB 天然跨 AZ，自建 LVS 双机 keepalived 要处理脑裂——加仲裁/双活检测）；CDN 与直连入口互备（CDN 故障时把解析切回源站入口，前提是源站带宽扛得住）；网关与业务必须多副本 + 健康检查自动摘除（探活深度要够，TCP 探测不够，要 HTTP 层）；数据层才是容灾重头——缓存、DB 做主从/多副本与跨机房复制，只做"入口高可用"而数据单点是假容灾。切换手段要配套时效管理：DNS 切换受 TTL 与客户端缓存影响（最长可能数小时），机房级切换前先把 TTL 调小；长连接（WebSocket、连接池、RPC 连接）在切换后必须能自动重连，否则"切了等于没切"。云网络设计要点：VPC 网段预留并避免与专线/对端冲突；业务子网与 DB 子网隔离；安全组最小权限（只放行必要端口 + 来源段）、ACL 做边界收紧，且安全组规则要有生命周期管理（上线加、下线回收）；出网统一走 NAT 网关（避免每台机器绑公网 IP，出网带宽可管理）；HTTP 服务用 ALB（自带健康检查、跨 AZ、可挂 WAF/限流），TCP 长连接/自研协议用 NLB。实践中的坑：容灾演练要"拔网线"式真演，暴露的问题远多于开关模拟；切换剧本要包含缓存预热、连接池重建、监控恢复三步；同城双活"双活"名不副实的常见原因是写路径仍依赖同机房 DB、读双写单；切换后的流量回切比切换更危险，也要演练。

**延伸考点：** 同城双活与异地多活的 RTO/RPO 分别是多少、靠什么实现？安全组的"只加不减"会导致什么问题，怎么治理？
