# 通用 · 算法与数据结构（面试题库）

本文件聚焦算法与数据结构在真实工程中的落地能力，覆盖复杂度分析、数据结构选型、排序与 TopK、二分与滑动窗口、树/图/DP 等经典模型在业务中的映射、海量数据处理、高并发下的算法设计与代码质量等主题。题目均以线上场景为背景，重点考察候选人的工程权衡（时间/空间/精度）、边界意识、量化能力与沟通思路，而非八股概念背诵。难度自 Q1 至 Q20 循序渐进，从实践基础逐步过渡到中阶调优与架构级开放性思考题。

### Q1. 接口耗时随数据量增长 100 倍，如何用复杂度分析定位并优化？

**问题：** 一个查询接口平时 20ms，数据量增长 10 倍后耗时涨到约 2s（近 100 倍），怀疑代码里有 O(n²) 的算法。你会怎么验证假设、定位热点，并给出优化方案？

**期望加分项：**
- 先做量化推断：数据量 10 倍、耗时 100 倍，是 O(n²) 的典型信号，能据此缩小排查范围
- 会用 profiler 或分段打点把耗时拆到函数级，而不是凭感觉猜代码
- 能区分"复杂度阶数"与"常数因子"，知道优化常数只是缓解、降阶才是根治
- 能给出具体降阶手段（哈希、缓存、索引、双指针等）并预估收益
- 优化后会用数据量-耗时曲线验证复杂度确实降下来

**减分项：**
- 只会背"O(n²) 不好"，说不出如何从实测数据反推复杂度
- 不先定位就凭经验改代码
- 忽略数据分布：最好/平均/最坏情况的差别
- 把"加机器、换语言"当方案，没有定位到算法本身

**解答：**
复杂度分析在生产排障里的价值是"用数据说话"。数据量涨 10 倍、耗时涨 100 倍，这个倍数关系本身就在强烈提示 O(n²)：O(n) 应近似涨 10 倍，O(n log n) 约涨 30~40 倍，O(n²) 约涨 100 倍。第一步用对照实验验证假设：取 1k/10k/100k 三档输入各压测若干次，画数据量-耗时曲线，看增长趋势是否贴合 n²。第二步定位热点：用 profiler（Go 的 pprof、Java 的 async-profiler）或给可疑函数分段打点，把耗时占比最高的函数找出来——常见的 O(n²) 来源包括循环内做线性查找、循环内字符串拼接（每次产生拷贝）、两层嵌套遍历、在数组头部反复插入。第三步才是优化，按场景选：内层线性查找换哈希表（O(n²)→O(n)）、预处理结果缓存、用双指针/索引代替两层循环；如果算法本身无法降阶，再考虑限制输入规模或缓存结果。最后一定要验证：压测确认新曲线符合预期，并留意最坏情况（全是冲突键、全是逆序数据）没有回归。实践中的坑：只看平均耗时会漏掉"特定数据分布触发最坏情况"的问题；降阶优化后还要关注常数与内存增量，避免用大内存换来的"假优化"。

**延伸考点：** 如果耗时曲线是"10 倍 → 40 倍"，该怀疑什么复杂度？定位到 O(n²) 后，什么场景下你会选择保留 O(n²) 但通过缓存友好性优化常数？

### Q2. 每秒 10 万条事件顺序写入本地缓冲，用数组还是链表？

**问题：** 事件采集服务每秒写入约 10 万条事件到内存缓冲，消费者按批（每批 1000 条）顺序取走处理，读写都是顺序的。这个缓冲用数组还是链表？如果业务改成"高优先级事件随时插到队首"呢？

**期望加分项：**
- 能按访问模式选型：顺序追加+顺序消费用数组（环形缓冲），缓存局部性好
- 知道链表每个节点有指针与分配开销，百万级节点时内存碎片和 cache miss 明显
- 能给出"优先级插入"场景的改造方案：多桶环形缓冲或链表，并说清取舍
- 考虑容量上限与满时策略（丢弃/阻塞/覆盖最旧）对业务的影响
- 能给出量化估算：10 万条/秒 × 每条结构体大小，估算内存与扩容策略

**减分项：**
- 只会背"链表插入删除快、数组随机访问快"的教科书结论
- 不了解 CPU 缓存对连续内存访问的加成
- 不讨论容量上限与丢数据策略
- 忽略生产-消费速率不匹配时的积压问题

**解答：**
判断标准不是"哪个结构更好"，而是"你的访问模式是什么"。本题是严格的顺序写、顺序读（FIFO），数组是明显更优解：用环形缓冲（ring buffer），写入与消费各持一个游标，读写都是 O(1)，且内存连续，消费端批量读 1000 条时能充分利用 CPU 缓存，吞吐远超链表。链表的劣势在百万量级下很具体：每个节点至少 2 个指针（各 8 字节）+ 分配头，还要承担 malloc/free 的开销与内存碎片；顺序遍历时每次跳指针都伴随 cache miss。但如果业务改成"高优先级事件随时插到队首"，数组头插是 O(n)，此时要么用链表，要么更工程化地拆成"普通队列 + 高优队列"两个环形缓冲（甚至 4 个优先级桶），消费时按优先级轮询——这比单链表在真实系统里更常见，还能天然支持批量取。实践中的坑：环形缓冲的"满"策略必须显式决定——丢弃新事件还是阻塞生产者（涉及背压），否则数据会静默丢失；游标用无符号整数自然溢出取模，别在热路径做除法；缓冲只是"削峰"，生产与消费速率长期不匹配时，要靠消费者扩容或丢弃策略兜底，单纯加大缓冲只会延迟问题爆发。

**延伸考点：** 如果高优先级事件占比很小（每 1000 条最多 5 条），多环形缓冲方案比单链表快多少，瓶颈在哪？环形缓冲在"头尾相接"时的边界判断容易出什么 bug？

### Q3. 解析嵌套括号/引号为什么用栈？深嵌套时为什么不能直接递归？

**问题：** 要解析嵌套的配置/模板表达式（如 `{{a {b {c}}} d}`）并校验括号是否匹配。用递归还是栈？如果嵌套深度可能到 1 万层，直接递归会不会出问题？

**期望加分项：**
- 能写出 O(n) 栈解法：遇左括号入栈、遇右括号匹配出栈、结束时栈空且过程不出现"右括号多于左括号"
- 能说清"栈天然匹配递归调用的 LIFO 语义"，递归本质是隐式栈
- 知道深递归会栈溢出：默认线程栈约 1~8MB，每层栈帧几 KB，1 万层可能已撑爆
- 能给出"递归转显式栈"的方法：把状态与阶段压栈，用循环驱动
- 联系真实场景：表达式求值、JSON/XML 解析、SQL 子查询解析

**减分项：**
- 只会背"用栈"，说不出为什么栈恰好匹配括号
- 认为递归一定能用，忽略栈溢出与可观测性问题
- 不考虑输入规模与嵌套深度的边界
- 不会区分"右括号多余"和"左括号多余"两类错误

**解答：**
括号匹配是天然的 LIFO 问题——最近打开的括号最先被关闭，与栈"后进先出"一一对应，复杂度 O(n)、空间 O(n)，核心实现很短：遇左括号入栈，遇右括号时若栈空则"右括号多余"，否则弹栈；遍历结束后若栈非空则"左括号多余"。为什么递归也能解？因为递归调用本身就是系统维护的隐式栈：进入一层等于压栈、返回等于弹栈，两者是同一件事的两种写法。真正的工程问题是深度：默认线程栈约 1~8MB，每层递归栈帧（局部变量+返回地址）通常几 KB 到几十 KB，嵌套到 1 万层很容易爆栈崩溃。解法有二：一是先估深度，若输入规模受控（如配置校验器限制嵌套不超过 100 层）就放心用递归，代码最清晰；二是显式栈：把"当前状态 + 处理到哪一步"压入堆上的自定义栈，用 while 循环驱动，深度 10 万层也没问题。实践中的坑：解析器遇到非法输入不能只报"不匹配"，要能指出具体位置与原因，方便业务方排查；注意单引号/双引号内的括号不应参与匹配（很多模板引擎的经典 bug）；递归版本难以在深栈时打印清晰的调用现场，而显式栈可以随时检查栈顶状态，可观测性更好，这也是大厂解析器倾向显式栈的隐性动机。

**延伸考点：** 中缀表达式求值（含优先级与括号）怎么用两个栈实现？"递归转显式栈"的通用套路是什么，除了防爆栈还有什么动机？

### Q4. 高并发 KV 缓存，哈希冲突策略与扩容怎么选才不影响线上？

**问题：** 要写一个内存 KV 缓存，key 是字符串、读写比例约 8:2、QPS 几十万、容量上限 1000 万条。冲突用链地址法还是开放寻址法？自动扩容怎么做才能不出现"扩容瞬间毛刺"？

**期望加分项：**
- 能说清两种策略的取舍：链地址法实现简单、对装载因子容忍度高（0.75~1.0）；开放寻址法缓存友好但装载因子高时性能陡降（需 <0.7）
- 知道扩容要渐进式/分批迁移，避免一次性 rehash 造成停顿（如 Redis dict 的增量 rehash）
- 能考虑字符串 key 的哈希计算成本：不缓存 hash 值则每次访问都要重算
- 主动提负载因子、扩容阈值与内存翻倍的代价
- 联系实际：Java HashMap 链表转红黑树的动机、Go map 的 bucket 设计、并发场景加锁或分片

**减分项：**
- 只会背"哈希 O(1)"，不知道冲突率随装载因子变化的曲线
- 不知道扩容是全量 rehash，会阻塞线上
- 不考虑哈希函数质量（分布差会退化成链表/线性探测）
- 不讨论并发读写的一致性

**解答：**
先明确访问模式再选策略。读多写少、要求高吞吐，两者都可行，关键看装载因子与扩容方式。链地址法（Java HashMap 的做法）用数组 + 链表，装载因子可以放到 0.75，实现与删除简单，最坏情况退化成链表（所以 Java 8 后链表超 8 个转红黑树）；开放寻址法（Go map 的做法）数据全在数组里、缓存命中率好，但装载因子到 0.7 以上后探测链变长、性能断崖，删除要打"墓碑"标记，很麻烦。工程上更关键的是扩容：一次性把 1000 万条重哈希，即使每条花几十纳秒也要零点几秒，高 QPS 下就是一次明显毛刺。缓解手段：一是渐进式 rehash——新旧两表并存，每次读写顺带迁移一小批，直到迁完（Redis dict 就是这么做的）；二是分片——把哈希表按 key 哈希的高几位分成 N 片，每片独立扩容，单次扩容影响面缩到 1/N；三是把 key 的哈希值缓存在 entry 里，rehash 和查找直接复用，省掉字符串重算哈希。坑还有几个：哈希函数要足够散（FNV-1a、xxHash 等），恶意构造相同哈希的 key 会打爆性能；容量取 2 的幂可用位运算代替取模，但取幂会让低 bit 分布差，需要先做一次混淆（如 `hash ^ (hash >>> 16)`）；任何自研哈希表都不如先用标准库，真要自研通常是冲着"内存可控"或"并发度"去的，这两点要能说清收益。

**延伸考点：** 为什么 Go map 用 bucket（每桶 8 槽 + 溢出桶）而不是纯链表？哈希表在"内存受限、只要存在性判断"时有什么更省内存的方案？

### Q5. 5000 万条订单记录的排序接口很慢，怎么优化？

**问题：** 一个接口要对 5000 万条订单记录排序，响应要几十秒，而用户实际要的是"Top 100 排行"和"导出全部"。你会怎么优化？先想清楚需求，再谈算法。

**期望加分项：**
- 第一反应是追问需求：TopK、全量导出还是分页查询，三者解法完全不同
- TopK 用小顶堆：O(n log k)，5000 万取 Top 100 只需一轮扫描
- 全量排序且数据放不下内存时，能说出外部排序（归并）：分块排序落盘 + 多路归并
- 能结合数据库/索引：数据在库里就让存储引擎用索引 + `LIMIT` 干活，别把 5000 万条拉进应用层
- 关注比较器性能：避免每次比较重算排序键

**减分项：**
- 不澄清需求就直接说"用快排"或"加内存"
- 分不清"排序 5000 万条"与"取 Top 100"的复杂度差异（O(n log n) vs O(n log k)）
- 忽略内存放不下的情况，说不出外部排序
- 不考虑数据来源（数据库/文件/日志），一上来就谈纯内存算法

**解答：**
这道题考的是"先定义问题再选算法"。第一步必须反问：全量排序的唯一意义是"展示全部或导出全部"，而绝大多数业务（排行、TopN、分页）只需要部分有序结果。如果是 Top 100：用小顶堆扫一遍，堆大小为 k，复杂度 O(n log k)，5000 万条也能在几秒内完成；甚至可以进一步按订单金额分桶，排除掉不可能进前 100 的桶。如果是分页查询：优先让数据库走索引（`ORDER BY create_time LIMIT 10000, 20`），应用层只拿一页，别全量拉取。如果确实是全量导出 5000 万条：内存一般放不下（每条几百字节就是几个 GB 甚至十几 GB），此时用外部排序——把数据切成能装进内存的块，每块内部快排后写临时文件，再用 K 路归并（败者树或堆优化）合并成最终有序文件；总复杂度 O(n log n)，但瓶颈是磁盘顺序 IO 而非 CPU。实践中的坑：这类接口慢的常见真凶是"全量拉取 + 应用层排序 + 再丢弃"，先看 SQL 有没有利用索引；比较器里反复拼接字符串、调用 getter 链会放大常数，应预处理出排序键并缓存；外排要注意缓冲区大小与 IO 模式，碎片化随机 IO 会拖垮吞吐。最后补一句：50 万到 5000 万量级的排序需求，先问"用户真的需要全量吗"，大多数答案是不需要。

**延伸考点：** 5000 万条里取"销售额 Top 100 且每个类目至少 10 条"这种带约束的 TopK 怎么做？外部归并里 K 路归并的 K 与每路缓冲区大小怎么权衡？

### Q6. 在 1 亿条有序日志里找"某时刻之后的第一条"，二分怎么写才不出错？

**问题：** 日志按时间戳升序存放，要查询"时间戳 >= T 的第一条记录"，这是典型的二分下界（lower_bound）。请写出无死循环、无溢出的实现，并说明边界情况。

**期望加分项：**
- 能写出正确二分，`mid = l + (r - l) / 2` 防整数溢出
- 能说清区间不变式（左闭右开 [l, r) 或闭区间 [l, r]），并解释为什么 `l = mid` 时可能死循环
- 知道目标不存在时返回插入位置，会处理"全部 < T"和"全部 >= T"两个极端
- 能联系真实系统：B+ 树页内二分、Redis ZSET 按分数定位、有序数组区间统计
- 主动提大场景下二分只是最后一步，前面要靠索引/分块先缩小范围

**减分项：**
- 不知道 `(l + r) / 2` 在 l + r 溢出整数时的坑（Java/C++ 经典问题）
- 写出的二分在找不到目标时返回错误位置
- 不会分析死循环原因，只会背模板，换个变体（upper_bound、旋转数组）就不会了
- 不检查数据是否真的有序、排序口径是否一致

**解答：**
二分的关键不是背模板，而是守住"区间不变式"：声明清楚你维护的区间里"可能的答案"是什么。以"找第一个 >= T 的下标"为例，用左闭右开 [l, r)：不变量是"l 之前都 < T，r 及之后都 >= T"，初始 l = 0, r = n；循环 `while l < r`，`mid = l + (r - l) / 2`，若 `a[mid] < T` 说明 mid 及左边都不满足，令 `l = mid + 1`；否则令 `r = mid`；退出时 `l == r` 即为答案（若 `l == n` 说明全部 < T）。两个细节是防错的根源：一是用 `l + (r - l) / 2` 而非 `(l + r) / 2`，后者在 l + r 超过整数范围时会溢出（Java/C++ 的经典坑）；二是当条件分支写 `l = mid` 时，mid 必须上取整 `(l + r + 1) / 2`，否则区间长度收敛到 2 时会死循环——这就是"为什么有的二分写法会卡死"的答案。理解了不变式，各种变体（第一个 > T、最后一个 <= T）都只是改比较符号与边界更新。真实系统里二分几乎不会直接对 1 亿条裸做：要么数据在数据库索引里（B+ 树页内二分）、要么在 Redis ZSET 里（skiplist 也是分段比较）、要么先按天/月分文件再在文件内二分，所以可以强调"二分负责块内定位，分块/索引先缩小范围"。坑还有一个：二分前必须确认数据确实有序且排序口径一致（如时间戳与存储时区一致），否则正确性无从谈起；并发写入场景要先取快照或加读锁。

**延伸考点：** 旋转有序数组（如 [4,5,6,1,2,3]）里找目标值，怎么在 O(log n) 内完成？为什么 Redis 用 skiplist 而不用数组二分？

### Q7. 实时监控要展示"最近 1 小时每分钟的 QPS"，每秒 10 万条数据，怎么存？

**问题：** 监控面板要展示最近 1 小时里每分钟的 QPS，并能查询任意一分钟的值，数据流每秒约 10 万条。方案要内存可控、更新和查询都 O(1)，用什么数据结构？跨分钟对齐、过期分钟这些边界怎么处理？

**期望加分项：**
- 能给出环形数组（固定 60 个槽）+ 计数器，而不是把每秒 10 万条全存下来
- 知道槽位 = 分钟数对 60 取模，写入时处理好"上一分钟残留计数"（清零或惰性清零）
- 能处理跨分钟对齐：同一秒数据可能横跨两个槽，先按秒聚合再入分钟槽
- 能给出内存量化：60 个槽 × 8 字节 ≈ 480 字节，与 QPS 无关
- 主动提可扩展到多粒度：多组环形数组或分层聚合（秒级 + 分钟级）

**减分项：**
- 老老实实每一条都存，然后说"内存不够就加机器"
- 知道用数组但不会处理槽位复用时的旧数据污染（取模覆盖但不清零）
- 忽略跨分钟边界的计数归属
- 说不清这与"存全部时间戳"的本质区别（聚合 vs 明细）

**解答：**
这类问题的本质是"聚合 + 滑动窗口"：用户要的不是每条原始数据，而是分钟的聚合值，所以没必要存明细。方案：定长 60 的环形数组，每格存一个计数器，当前分钟在 slot = minute % 60。写入侧：先把时间戳归一到分钟粒度，若分钟变了，把"旧的当前槽"清零再累加（或者读的时候发现槽的时间戳不是当前分钟就视为 0，即惰性清零，省掉每次写入的判断）。查询侧：直接读 slot = target_minute % 60，O(1)。要处理的关键边界有三个：第一，跨分钟边界——同一秒的请求可能落在上一分钟的最后一刻和这一分钟的第一刻，正确做法是内部先按秒聚合再按分钟累加，或统一以"事件时间"而非"处理时间"归槽；第二，槽位覆盖——60 个槽只保留 60 分钟，查询超过 1 小时前的数据查不到，这是滑动窗口的代价，需要明确说明；第三，乱序/晚到事件——晚到的旧事件是否计入旧分钟槽要业务决策（一般直接忽略或归入当前分钟并标注）。内存账要算：60 × 8 字节 ≈ 480 字节，与 QPS 无关，这就是聚合的价值。如果想同时看"每秒"和"每分钟"，就开两组环形数组（60 秒槽 + 60 分钟槽），秒槽每分钟归零并入分钟槽。坑：不要把窗口内所有明细都保留来凑数，除非还要支持 drill-down；分钟槽的计数写入集中在同一个槽上，用原子累加即可，但要注意 CPU 缓存行的伪共享（false sharing）问题。

**延伸考点：** 如果想查"任意连续 30 分钟的总量"，怎么在 O(1) 时间内算出来（前缀和）？环形数组方案改成"最近 1 小时 UV"（按用户去重），单个计数器不够了，怎么改造？

### Q8. 用户活跃度报表要"最近 7 天每天 DAU 的趋势"，滑窗去重怎么做？

**问题：** 产品要一张"最近 7 天每天去重用户数"的趋势报表，数据源是每天上亿条登录事件日志。直接对每天全量去重很贵，怎么用滑动窗口 + 近似算法控制成本，同时保证趋势曲线可用？

**期望加分项：**
- 能点破"精确去重 vs 近似去重"的取舍：报表趋势看形状，容忍小误差，不值得全量精确去重
- 知道经典方案：HyperLogLog（HLL）对"去重后数量"近似，误差约 1~2%，内存约 12KB 即可统计任意规模
- 能讲清 HLL 原理的直觉：用哈希值的前导零个数估算基数，而不是真的存每个用户
- 能给出"按天粒度拆窗口"的做法：每天一个 HLL，查近 7 天趋势读 7 个 HLL；跨天滚动再考虑合并（HLL 可并）
- 知道什么时候必须精确：对账、计费、法律合规场景不能用近似
- 联系生产实践：UV 报表、运营看板、反作弊的疑似重复检测

**减分项：**
- 只会说"加机器暴力去重"，给不出成本账
- 把 HLL 当黑盒，说不清误差来源与适用边界
- 不了解"近似算法要能合并/可增量"，否则多天聚合做不了
- 不考虑业务对误差的容忍度，一律上精确方案
- 说不清 HLL 不能解决"有哪些用户"（它只回答"有多少个"）

**解答：**
先分清楚需求：报表要的是"去重后的数量变化趋势"，不是"每个用户是谁"。精确方案（如布隆过滤器的兄弟——精确集合）在单天规模上亿时内存和时间都不可控，而趋势报表对 ±2% 的误差无感，所以用近似算法是合理决策。HLL 是首选：它把每个用户哈希成一个 64 位整数，用"二进制表示里前导零的最大个数"来估算集合大小，原理是对数稀疏特性——哈希值越随机，前导零多的越少见，据此倒推规模。内存只占约 12KB（用 2^14 个寄存器），却能统计到 2^64 量级，误差约 1~2%，且支持 union（按位取最大），这正是多天聚合需要的性质。落地方式：每天一个 HLL，流入的登录事件不断更新当天 HLL；查"近 7 天趋势"就是读 7 个 HLL 各自估值；要"7 天合计"就把 7 个 HLL 合并再估。进阶问题是"跨天连续活跃窗口"：如果窗口随日历滚动（如任意最近 7 天），需要支持按天粒度的 HLL 前缀和/树状聚合，或用 Timely Rolling HLL（分桶淘汰）做流式滚动去重。必须画出的红线是：HLL 只回答"有多少"，不回答"有哪些"；近似结果在计费、对账、出审计报告时不可用，那种场景要退回到精确集合（牺牲内存）或抽样精确核验。实践中的坑：哈希函数质量直接影响误差，必须用稳定随机的哈希（如 MurmurHash）；小基数时 HLL 有系统性偏差，需用小范围纠偏表（原版论文有补丁）；别把 HLL 估值直接用于"环比 = 0 的判断"，误差可能掩盖微小变化。

**延伸考点：** 如果要求"最近 7 天都在线（连续 7 天）的用户数"，HLL 能算吗，为什么不能，有什么变体？位图（bitmap）去重和 HLL 的内存-精度曲线分别怎么选？

### Q9. 千万级 ID 判"是否在黑名单"，误判能容忍 0.1%，用什么结构？

**问题：** 网关要对千万级用户/设备 ID 做黑名单拦截，查询 QPS 很高。需求是"在名单中"必须 100% 拦截，但"不在名单中"偶尔被误判拦截一次可以接受。用什么数据结构？误判率怎么控制？

**期望加分项：**
- 能说出布隆过滤器：k 个哈希函数 + m 位位图，查询 O(k)，内存远小于存集合本身
- 能给出误判率公式与参数选择：误判率 p 与位图大小 m、哈希数 k 的关系，标准结论 p ≈ (1 - e^(-kn/m))^k
- 会算内存账：给定误判率 1% 和千万级 n，m 约 n × 9.6 bit，可现场估算（如 1000 万 → 约 12MB）
- 知道"误判只出现在查询不在集合时"：误报（false positive）可接受，漏报（false negative）绝不允许——这正是布隆过滤器的特性
- 能讲清删除难题：标准布隆不支持删除，带计数器的 Counting Bloom 才支持，但计数会放大内存
- 联系生产：URL 去重、垃圾邮件过滤、缓存穿透防护

**减分项：**
- 只背"布隆过滤器"名字，说不出参数如何确定
- 误判率与内存的权衡说反（加大位图是降低误判率）
- 不知道布隆"只误报不漏报"，即可能把白名单误判为黑名单，但不会漏掉真黑名单
- 不会处理"名单会更新"时的删除/重建问题
- 不估算内存，直接说"反正比集合省内存"

**解答：**
黑名单判定的性质决定数据结构：真名单必须全拦截（不能漏），非名单偶尔误伤可接受——这是"只误报、不漏报"的典型场景，布隆过滤器恰好满足。原理：初始化 m 位全 0 位图，插入元素时用 k 个独立哈希函数各算一个位置并置 1；查询时算 k 个位置，只要有一个是 0 就"一定不在"；全部为 1 则"可能在"（可能因碰撞误判）。关键在参数：设 n 为元素数，误判率 p 的最优哈希数 k ≈ (m/n) × ln2，位图大小 m ≈ -n × ln p / (ln2)²。工程速记：p = 1% 时每个元素约需 9.6 bit，1000 万元素约 12MB；p = 0.1% 时约 14.4 bit/元素，20MB 左右。所以"0.1% 误判率 + 千万级"的答案是"不到 20MB 位图"——远小于把 1000 万 ID 存下来（按 8 字节一个也要 80MB 且查询无索引）。实现要处理的坑：一是哈希函数要用独立且分布好的（可用一个种子化哈希派生 k 个，或用 MurmurHash 不同种子），否则碰撞集中、误判率虚高；二是名单会变动——标准布隆不能删，只增不减时到量就重建（双缓冲轮换）；若必须删，升级成 Counting Bloom（每个槽多 bit 存计数，删除时减计数），但要支付 4~8 倍内存；三是并发场景下位图写入有竞争，要么用分片位图，要么接受"查询时短暂读到未写完位"的极小误差。最后强调校验手段：上线前用真实名单构造测试集，实测误判率是否贴合理论值，并准备"被误伤用户的申诉/放行通道"，把偶发误判对业务的影响降到可接受。

**延伸考点：** 为什么很多缓存场景用"布隆过滤器挡空 key 穿透"？如果名单还要求支持"统计每个 ID 被查询的次数"，布隆还能做吗，怎么做？

### Q10. 高并发读的 KV 缓存，容量有限，淘汰策略 LRU 的落地与坑？

**问题：** 一个读多写少的服务要缓存热数据，容量固定（比如 100 万条）。用 LRU 淘汰，你会在数据结构和实现上怎么做？LinkedHashMap 够用吗？并发场景和"一次全量刷新把热点全顶掉"这类问题怎么处理？

**期望加分项：**
- 能实现 O(1) 的 LRU：哈希表（定位节点）+ 双向链表（维护访问序），get/put 都 O(1)
- 知道 Java `LinkedHashMap(accessOrder=true)` 就是 LRU，会重写 `removeEldestEntry`；Python `OrderedDict.move_to_end` 同理
- 能指出纯 LRU 在真实业务的三个坑：全量刷新冲掉热点、偶发访问污染的"缓存抖动"、扫描式访问把正常热点全部淘汰
- 能给出工程改造：LRU 加访问频次权重（LFU/ARC 思想）、给 key 分级或加"保护窗口"
- 处理并发：synchronized 锁粒度、ReadWriteLock、分片（Sharded LRU）、或直接用 Caffeine 等成熟组件

**减分项：**
- 只会背"双向链表 + 哈希表"，不演示具体 get/put 流程
- 不知道标准库已有实现，非要手写
- 不考虑"哪些数据值得进缓存"的策略，把淘汰策略当万能药
- 并发场景直接加一把大锁，说不出分片思路
- 不了解缓存击穿/雪崩与淘汰策略的关系

**解答：**
先给实现：LRU 需要"哈希表 O(1) 定位 + 链表 O(1) 增删"的组合。维护一个双向链表，头部是最近使用、尾部是最久未用；get 命中时把节点移到头部，put 新键时插到头部，若超容量则删尾部。哈希表存"key → 链表节点"，实现 O(1) 定位。工程上优先用成熟组件：Java 的 `LinkedHashMap`（构造参数 accessOrder=true + 重写 removeEldestEntry）几行就实现，Python 的 `OrderedDict` 同理；生产环境更推荐 Caffeine/Guava 这类带统计与自适应策略的组件，而不是自研。但"LRU 本身"不等于"缓存策略正确"，要主动指出三个坑：一是全量刷新——后台任务把整张表刷进缓存，会瞬间把原本的热点全部挤到尾部被淘汰，正确做法是"逐条刷新并保持原有访问序"或刷新前先判断是否已存在；二是扫描式访问——一次遍历千万条的分页查询会把所有正常热点淘汰，经典对策是"对超过阈值的批量访问只记一次 LRU 访问"，或混合 LFU 思想按频次加权；三是偶发抖动——周期性低频访问不断挤占窗口，可用"多级缓存/保护段"（如 Caffeine 的 W-TinyLFU 用频率布隆过滤器）。并发实现要点：Java 8 后可用 `ConcurrentHashMap + 手动同步链表段`，或干脆用 Caffeine（内部 W-TinyLFU，异步刷新、统计命中率）；不要一把大锁包所有操作。最后，被问"为什么缓存会失效"时，要能区分淘汰（容量策略）与过期（TTL 策略），两者要一起设计，否则会出现"缓存里全是旧数据"或"命中率很低"的割裂。

**延伸考点：** 热点 key 集中时，LRU 会不会把其他正常 key 全部淘汰，怎么用"频次 + 最近性"的折中解决（LFU/W-TinyLFU）？缓存过期策略里"惰性删除 + 定期清理"各解决什么问题？

### Q11. 关键词自动补全/联想，前缀搜要用什么结构？一亿词库怎么落？

**问题：** 搜索框要做"输入前缀即联想"（如输入 "app" 补全 "apple/apply/applet"），词库约一亿条。Trie（前缀树）的空间和内存问题怎么解决？查询"只返回 Top K 联想词"又怎么优化？

- 联想"Top K"用每个节点维护"子树最热 K 个"缓存，或先用前缀定位再按热度取
- 联系工程：Elasticsearch 的 prefix/edge_ngram、Redis ZSET 的 sorted set 前缀扫描、输入法词库

**减分项：**
- 只背"Trie 查前缀快"，答不出内存爆炸的现实
- 不知道"联想要按热度排序返回 Top K"，以为返回所有子树词
- 不考虑一亿词的存储形态（放内存还是磁盘、冷热分层）
- 不会权衡 Trie vs 哈希表（哈希只能查精确、不能查前缀）

**解答：**
前缀联想本质是"给定前缀，找所有/最热的关键词"，哈希表只能精确匹配、做不到前缀，所以第一个答案是 Trie。标准 Trie：根到叶子路径即单词，插入与查询长度均为 O(len)，查前缀时先走到前缀节点再遍历子树收集结果。但直接实现会踩内存坑：26 叉数组每个节点 26 个指针，英文词平均 8 字符、一亿词就是上亿节点，纯数组实现内存膨胀到数个 GB 甚至几十 GB，因为大量节点只有 1~2 个子节点。工程化手段按序给出：一是压缩——Radix Tree 把"没有分叉的连续边"合并成一个节点，大幅减少节点数；二是换子节点存储——用哈希 map 或有序数组按需分配子节点，稀疏节点不再白付 26 指针；三是改倒排——把词按前缀拆分索引（如 edge_ngram），查询时直接读倒排列表，这是搜索引擎（Elasticsearch）的常见做法；四是分层——热词放内存 Trie、冷词放磁盘倒排，用 LRU 换入。联想返回 Top K 的问题：朴素 Trie 查前缀要遍历整棵子树，若子树很大就慢，标准做法是每个节点缓存"该子树下最热的 K 个词"，插入时向上更新，查询 O(len + K)；或者前缀节点只负责定位，再走一个按热度排序的紧凑结构。实践中的坑：词库要支持增删（运营改词、下架敏感词），Trie 的删除要小心回收路径；中文按字做 Trie 会退化成"字→词"的图，通常改用前缀倒排 + 拼音/缩写别名；一亿词规模下先明确"补全的是热词子集（几十万）"而不是全量，绝大多数产品的联想词库远小于总词库。

**延伸考点：** 联想词还要支持"模糊前缀"（输错一两个字母也补全），怎么用编辑距离 + BK 树或 n-gram 做？输入法级联想（拼音→候选词）为什么用双向最大匹配或语言模型而不用纯 Trie？

- 不给"环具体是哪条路径"的定位，只说"有环"
- 忽略入度为 0 的初始节点可能不存在（全环）的边界
- 不考虑规模：几千节点用矩阵存边会浪费内存

**解答：**
任务依赖是典型 DAG（有向无环图）问题，判定与排序可以一次完成。最直观的 Kahn 算法：1) 统计每个节点入度；2) 入度为 0 的节点（没有前置依赖）入队列；3) 出队加入结果序，并把它指向的每个后继节点入度减一，减到 0 再入队；4) 循环直到队空。如果结果长度 < 节点总数，说明有节点永远减不到 0，即存在环——环上每个节点的入度至少为 1，谁也出不了队。用入度法还能精确圈出环：结束后入度仍 > 0 的节点集合就是环（或环的组成部分）。另一种写法是 DFS 三色标记：白=未访问、灰=在递归栈上、黑=已完成；遍历时若碰到灰色节点说明找到了环，且递归栈从该节点到栈顶的路径就是环路径，这常用于"要给出环的详细链路"的场景。大规模（几千任务）要注意存储：用邻接表而非邻接矩阵（矩阵要几千万格），空间 O(V+E)。工程上的延伸：一是在入度为 0 的多个节点间加优先级/依赖层级，让"先算底层、后算上层"更符合数仓/调度习惯；二是配置变更后要增量重算依赖关系而不是全量重建 DAG；三是给出环的完整路径（如 "A→B→C→A"）并提示哪条边是人工配置引入的，方便运维修复。实践中常被忽略的是"自环"（任务依赖自己）和"跨层间接环"，这两种都要靠算法兜底，而不是靠人工 review。

**延伸考点：** 如果任务图是"最终必须从 1 号任务开始执行"的约束，拓扑排序怎么调整？在 Airflow 这类系统里，调度周期（daily/hourly）与任务依赖叠加后，图的建模维度怎么处理？

### Q13. "矩阵从左上到右下的路径走法"这类计数问题，DP 的状态设计关键在哪？一维数组优化怎么做？

**问题：** 有一个 m×n 网格，从左上角走到右下角只能向右或向下，问不同路径数。这题很简单，但请把它升级：路径上带障碍物、要求"走完全部格子取最大得分"。状态设计、空间压缩、与记忆化递归的区别，请一并说清。

**期望加分项：**
- 能写出状态定义 dp[i][j] = 到 (i,j) 的路径数，转移 dp[i][j] = dp[i-1][j] + dp[i][j-1]，边界 i=0 或 j=0 全为 1
- 能扩展到带权/带障碍：dp[i][j] = max(dp[i-1][j], dp[i][j-1]) + grid[i][j]；有障碍则该点不可达
- 知道空间优化：按行滚动，dp 从二维压到一维，dp[j] = dp[j] + dp[j-1]（或 max），因为每格只依赖上一行同列和本行左列
- 能对比记忆化递归（自顶向下）与递推（自底向上）的区别及各自适用性
- 能指出 DP 适用前提：最优子结构 + 重叠子问题；"状态转移方向"（只能右下）决定了拓扑序
- 会检查溢出（路径数用 64 位）与障碍边界

**减分项：**
- 只会背公式，说不清"为什么可以这样转移"
- 不知道空间压缩的原理，直接给二维
- 障碍物场景不会处理"起点/终点本身是障碍"
- 说不清 DP 与回溯/DFS 的复杂度差异（O(mn) vs 指数）
- 不验证边界（m 或 n 为 1）

**解答：**
这类题的核心是"状态定义 + 转移方程 + 边界"，三个都要讲清。路径数版：dp[i][j] 表示到 (i,j) 的路径数，由于只能从上方或左方来，dp[i][j] = dp[i-1][j] + dp[i][j-1]；第一行、第一列只有一种走法，所以全为 1。带障碍：把障碍点 dp 设为 0，同时转移前检查。带权/取最大和：dp[i][j] = max(dp[i-1][j], dp[i][j-1]) + grid[i][j]，这就是"从左上角出发走格子的最大得分"标准解。空间压缩是考察重点：观察转移只依赖"上一行的同列 dp[i-1][j]"与"当前行的左列 dp[i][j-1]"，所以可以只保留一维数组 dp[j]，按行从左到右更新，`dp[j] = dp[j] + dp[j-1]`（路径数）或 `dp[j] = max(dp[j], dp[j-1]) + grid[i][j]`（最大和）——右边第一个 dp[j] 是上一行的值，更新完即当前行，完全正确。空间从 O(mn) 降到 O(n)。与记忆化递归的对比：递归自顶向下，代码直观但函数调用栈深、且要带 memo 数组（仍是 O(mn) 空间）；递推自底向上省去递归开销，还可做滚动优化，工程上一般用递推。适用前提要能说出来：问题有最优子结构（大问题最优由子问题最优构成）和重叠子问题（不同路径会重复计算同一子问题）才值得 DP；而"只能向右向下"这类约束保证了状态存在无环拓扑序，可直接按行序递推。坑：路径数是组合数级增长（20×20 就到几亿），int 会溢出，用 long；障碍网格要单独判起点/终点；m 或 n 为 1 时只有一条路径，别让数组越界。

**延伸考点：** "不同路径"用组合数 C(m+n-2, m-1) 直接算和 DP 的区别？如果网格是"环"（可以上下左右走），同样的状态设计还成立吗，为什么，这种情况该用什么算法？

### Q14. 10 亿个 URL 里判"是否见过"，内存只有 1GB，精确与近似分别怎么做？

**问题：** 爬虫系统每天产生约 10 亿条 URL 需要判重（防重复抓取），机器内存约 1GB。请分别给出"精确判重"和"可容忍小误判"两种方案的落地细节，并算内存账。

**期望加分项：**
- 能分两条线回答：精确方案与近似方案，而不是混在一起
- 近似：布隆过滤器，10 亿 × 9.6 bit/元素（1% 误判）≈ 1.2GB 略超，可把误判率放宽到 3%（约 7 bit/元素 → 0.9GB）或分片/磁盘布隆
- 精确：10 亿条存不下内存，用磁盘方案——对 URL 做哈希/排序后磁盘归并去重，或数据库唯一索引、或按 URL 哈希分片到多机（每机 1/N）
- 能讲"先哈希到定长指纹再判重"：把变长 URL 归一到固定长度指纹，既省内存又统一比较
- 讨论时效性：只判"今天见过"还是"历史全量"，可引入时间桶/滚动窗口
- 会指出"hash 本身不是判重依据"：不同 URL 可能同哈希（碰撞），精确场景需二次比对原文

**减分项：**
- 只说"用布隆"，不管 10 亿规模下参数是否放得下
- 精确方案答不出磁盘/分片，以为只能近似
- 混淆"URL 哈希去重"与"URL 判重"：前者取模分片，后者是全局判重
- 不考虑爬虫的时效性（重复抓取定义随窗口变化）
- 不算内存账，空谈方案

**解答：**
先把需求拆开：判重的语义是"这个 URL 是否处理过"，它决定了内存/磁盘/分布式的取舍。近似方案（可容忍 1% 级误判，即偶发跳过某个 URL 不抓，通常可接受）：布隆过滤器，公式 m ≈ -n×ln(p)/(ln2)²。n=10 亿，p=1% 时约需 9.6 bit/元素 = 1.2GB，超预算；把 p 放到 3% 约 7 bit/元素 = 0.9GB，可塞进 1GB；或者用分片布隆（拆成若干 100MB 段，按哈希高位路由）。精确方案：10 亿条原文存内存绝无可能（按平均 50 字节也要 50GB），要落到磁盘/分布式：做法一，哈希指纹 + 磁盘排序去重——把每条 URL 哈希成 8 字节指纹，写盘后外部排序（归并），相同指纹相邻，扫一遍判重；指纹碰撞率在 10 亿量级约 2^-64，可接受，若要 100% 则保留原文二次比对。做法二，按哈希取模分片到 N 台机器，每台处理 10 亿/N，单机内可再用布隆或精确集合——这是爬虫系统的经典横向扩展。时效性问题：爬虫通常只关心"近 N 天内是否抓过"，这时用时间窗口化的布隆/集合（每天一个，滚动淘汰），内存进一步下降。要讲清的坑：一是"取哈希去重"不等于"判重"，哈希取模只是路由分片，判重本身要落在每片的独立集合里；二是 URL 要规范化（去掉 fragment、排序 query 参数、统一大小写）再判重，否则同内容不同字符串会重复抓；三是分布式判重的一致性（跨节点看到不同步的集合）在最终一致性下可接受，但若要求强一致要用中心化存储如 Redis 的 SET 或数据库唯一索引。最后按面试官偏好给出"1GB 预算"的落地结论：近似用 3% 误判布隆约 0.9GB；精确则走磁盘指纹排序或分片多机。

**延伸考点：** 用 Redis SET 做全局判重，10 亿条要多少内存，什么时候值得上？布隆过滤器判重后"误判导致漏抓的 URL"怎么补偿（重试/抽样校验）？

### Q15. 微服务网关按请求特征路由，节点增删频繁，一致性哈希与哈希取模怎么选？

**问题：** 网关要根据 userId 把请求路由到 N 个后端节点。节点会扩容缩容（增删机器）。直接用 `hash(userId) % N` 会有什么问题？一致性哈希怎么改，环上的虚拟节点又解决什么？

**期望加分项：**
- 能指出取模法的问题：节点数 N 一变，绝大多数 key 的映射全部改变，缓存/会话大面积失效（雪崩式迁移）
- 能讲一致性哈希：把哈希值映射到 2^32 环上，节点哈希后放环上，key 顺时针找第一个节点；节点增删只影响环上相邻区间
- 知道虚拟节点作用：解决节点哈希不均导致的负载倾斜，并平滑扩容（每个物理节点复制 100~200 个虚拟点）
- 能指出"增删节点影响范围 ≈ 1/N 的 key"，并算例子
- 讨论分布式一致性：不同机器看到同一份环数据（配置中心下发或本地缓存 + 版本号）
- 联系实际：缓存分片、负载均衡、DHT 协议

**减分项：**
- 只会说"取模简单"，不知道 N 变化带来的连锁影响
- 把一致性哈希讲成"唯一正解"，说不出它也有数据倾斜和实现复杂度
- 不知道虚拟节点，负载倾斜答不出
- 不讨论环数据的同步与一致性问题
- 忽略 key 的哈希分布质量（直接 hash 字符串可能偏斜）

**解答：**
先算取模法的问题：`hash(userId) % N` 在节点数 N 变化时，重新哈希后几乎每个 key 的取模结果都变——比如 N=5 变 6，原本落在节点 3 的 key 大量跳到其他节点，若底层是会话状态或本地缓存，就是一次大面积的"缓存雪崩/会话失效"，线上扩容反而引发故障。一致性哈希正是为此设计：把哈希空间看成一个 2^32 的环，节点按自身哈希值落环，key 也哈希后沿环顺时针找第一个节点。节点增删时，只影响该节点环上"逆时针相邻区间"内的 key——期望只有 1/N 的 key 受影响，其余不受扰动，这是它相对取模的核心收益。但直接实现有缺陷：节点少且哈希位置分布不均时负载会严重倾斜（某节点环段特别大，承接过多 key）。解决方案就是虚拟节点：每个物理节点在环上复制出 K 个虚拟点（如 `node-1#0`、`node-1#1`…），key 路由到虚拟点再归并到物理节点，K 个点均匀铺开就让负载趋于均衡，扩容时新节点也复制 K 个虚拟点插入，迁移更平滑。工程落地要考虑的：一是环数据的一致性——每台网关必须看到同一份环拓扑，可用配置中心（ZooKeeper/etcd）推送节点列表 + 本地构建环，节点变更走版本号比对；二是迁移与双写——增删节点瞬间，环上被影响的 key 会短暂路由到旧/新节点，读路径要做"旧环回退查询"（先查新、miss 再查旧）避免丢数据；三是 key 的哈希函数质量——`String.hashCode` 这类分布一般，路由类场景建议用 MurmurHash/CRC32 并做分布测试。最后补一句：一致性哈希不是银弹，如果业务对"节点增删完全不迁移"有刚性需求（如强状态存储），要考虑 DHT 或重分片策略，而不是把所有压力转给一致性哈希。

**延伸考点：** 一致性哈希环上"只有 2 个节点、每个节点 100 个虚拟点"时，某一时刻新增 1 个节点，哪些 key 会迁移，占比怎么算？缓存场景用一致性哈希，节点扩缩后本地缓存怎么配合做渐进迁移？

### Q16. Redis 的 ZSET 为什么用跳表而不是红黑树？跳表的时间/空间复杂度怎么证明直觉？

**问题：** Redis 的有序集合（sorted set）用跳表（skiplist）实现范围查询和按分数排序。为什么不用红黑树或 B+ 树？跳表的查找/插入复杂度为什么是 O(log n)，它在工程上比平衡树好在哪？

**期望加分项：**
- 能讲清跳表结构：多层链表，每层是下层的"快速通道"，概率升层（如 1/2）
- 能直觉证明 O(log n)：期望层数 O(log n)，每层期望跳跃 2 个节点，总步数 O(log n)
- 能对比红黑树：两者 O(log n)，但跳表实现简单（无旋转/变色），并发改造容易（无锁或分段锁友好），范围遍历天然有序
- 能说出 Redis 选跳表的具体工程理由：范围查询（ZRANGEBYSCORE）不用回溯父节点、插入删除只改指针、内存友好（节点共享前向指针数组）
- 知道 B+ 树适合磁盘（扇出大、页内二分），跳表适合内存
- 能讨论空间：跳表期望 O(n)（每节点平均额外指针 2 个），红黑树每节点 2 指针 + 颜色位

**减分项：**
- 只会说"跳表简单"，说不出复杂度证明
- 分不清"随机化 vs 确定性"数据结构的取舍
- 不知道 B+ 树为什么是磁盘首选（扇出/顺序 IO）
- 不知道跳表也有退化风险（随机运气差时层数高，但概率指数级小）
- 不讨论 Redis 场景的具体 API 需求（范围查询、按排名取）

**解答：**
跳表本质是"多级有序链表"：底层链表存所有元素并有序，之上每层以一定概率（通常 1/2）保留部分节点作为"快车道"，顶层节点最稀疏。查找时从最高层开始，向右找到"不超过目标的最大节点"后下沉一层，逐层逼近，期望步数 O(log n)。为什么期望 O(log n)：每次向下跳，同层能跨过约 2 个底层节点，层高期望为 log₂n，每层常数次比较，所以总时间 O(log n)；插入同样先找插入点，再按概率随机生成层高并维护指针。对比红黑树，两者渐进复杂度一致，但工程差异很大：红黑树维护平衡靠旋转+变色，代码复杂、并发下难做无锁；跳表结构就是"多层链表+指针数组"，插入删除只动相邻指针，且天然有序——做范围查询（返回 [min, max] 的所有元素）只需在底层链表上连续走，不用像红黑树那样中序遍历回溯。这正是 Redis 场景需要的：ZSET 的核心操作是 ZRANGEBYSCORE（按分数范围取）和 ZRANK（按排名取），跳表在内存里实现这些既简单又高效。为什么不用 B+ 树：B+ 树节点（页）大、扇出高，是为了减少磁盘 IO 次数而设计，Redis 数据在内存，跳表按节点组织更贴近内存布局且无需页管理。空间上：跳表期望每节点 2 个前向指针（1/2+1/4+...=1，加底层本身），约 O(n)；红黑树每节点左右指针 + 颜色位，常数略小，但跳表的实现简洁度与并发友好性补回来了。实践中的坑：随机种子决定层高分布，生产环境别用质量差的随机数；跳表"最坏情况"是随机运气极差导致链表演化，但概率指数级小，工程上可接受；Redis 内部 ZSET 在元素少时用压缩列表/紧凑数组、元素多才转跳表，这个切换点也是考察点。

**延伸考点：** ZSET 里 score 相同怎么办（按成员字典序），跳表怎么处理？跳表做"按排名取第 k 名"（ZRANK）为什么还要在每个节点维护跨度（span）字段？

- 能给出流式方案：服务端分页拉取 + 应用层边取边写，或数据库游标（如 MySQL 的流式 ResultSet、PostgreSQL cursor）
- 讨论排序稳定性：只按一个字段排序时，重复值会导致翻页重复/漏页，必须"排序字段 + 主键"二元排序
- 会算性能账：游标分页每页都是索引定位 + 取 size 条，总成本 O(总条数) 而非 O(总条数 × 页号)
- 场景取舍：交互分页（用户跳页）用 offset 可接受；导出/遍历用游标或流式

**减分项：**
- 不知道深分页的成因，只背"别用 OFFSET"
- 游标分页不会处理排序字段有重复值的情况
- 分不清"用户交互翻页"和"全量遍历"两种需求的差异
- 忽略并发写入下数据变化导致的分页漂移（插入新行会推进 offset）
- 不讨论索引如何支撑排序字段的查询

**解答：**
先定义需求：这个接口是"用户翻页浏览"还是"全量导出"？前者页数浅（几十页内），`LIMIT offset, size` 配联合索引通常够用；后者页数深或数据量大，OFFSET 的代价开始失控——MySQL 等数据库对 OFFSET 的实现是"扫描并丢弃前 N 行"，第 10000 页要扫描 100 万行，速度呈线性劣化。所以导出类需求用游标分页（keyset pagination）：不记页码，而是记住上一页最后一条记录的位置，下页查询变成 `WHERE (sort_key, id) > ('上一页最后的值', 上一页最后 id) ORDER BY sort_key, id LIMIT size`。这样每页都从索引直接定位，复杂度稳定，第 N 页与第 2 页同代价，本质是把"分页"变成"连续取 next 段"。三个关键点：一是排序必须"字段 + 主键"二元组合，否则 sort_key 有重复值时同一条会被跨页重复取或漏掉（经典 bug）；二是 where 里的比较运算符要随排序方向一致（升序用 `>`, 降序用 `<`），别写反；三是游标从哪来——前端传"上一页最后一条的 (sort_key, id)"（可编码进 token），或服务端维护一个轻量游标。如果数据量巨大、又要导出到文件，直接用数据库级游标/流式拉取（JDBC setFetchSize 分批、MySQL 用 ResultSet 流式、PostgreSQL 用 CURSOR），应用层边读边写，避免一次性加载全量内存。取舍与坑：用户"能跳页"的需求（跳到第 100 页）游标分页做不到，此时要么接受 offset 的浅层代价、要么用快照/缓存中间结果；并发写入时插入新行会让 offset 分页出现"重复/遗漏"，游标分页则天然稳定（记录位置而非行号）；最终给出结论：交互浏览 → offset + 索引；遍历/导出 → 游标或流式。

**延伸考点：** "跳过中间 5 万条、直接看最后 100 条"（如最新 100 条公告）用什么方案最省？游标分页下"按多个字段排序"（如先按时间再按优先级）的 where 条件怎么写？

### Q18. 正则/敏感词过滤的"多模式匹配"为什么不能用逐条正则？Aho–Corasick 在做什么？

**问题：** 内容审核要用几千个敏感词做命中检测，文本几百万字。用 `for 每个词 { 正则匹配 }` 会有什么问题？请讲一种把"多个模式"一次性匹配完的算法思路（如 Aho–Corasick），以及它的构建与匹配复杂度。

**期望加分项：**
- 能点破朴素逐词匹配是 O(词数 × 文本长度 × 模式长度)，几千词 × 百万字文本不可接受
- 能讲 Aho–Corasick：把多模式建成 Trie，再加 fail 指针（失配回退边）构成 AC 自动机，一次扫描 O(文本长度 + 匹配数)
- 构建分三步：建 Trie → BFS 求 fail 指针 → 匹配时沿 Trie 走、失配走 fail
- 理解 fail 指针含义：当前匹配的最长后缀对应的另一模式前缀，用于不回溯主串
- 知道工程实现还能"只报告最长命中/首个命中/全部命中"来降配开销
- 联系场景：敏感词过滤、病毒特征码匹配、多关键字日志告警

**减分项：**
- 只会说"用 AC 自动机"，构建与匹配流程讲不清
- 不知道朴素方案为何慢（没意识到模式数 × 文本是瓶颈）
- fail 指针的语义说不清
- 不考虑中文分词/变体（谐音、插入符号）的现实难题
- 不讨论内存：AC 节点数与模式总长度成正比

**解答：**
朴素做法是 O(词数 × 文本长度 × 模式平均长度)：每个词都对全文跑一遍匹配，几千词 × 百万字文本就是几十亿次比较，显然不行。AC 自动机（Aho–Corasick）的思想是"把多个模式合并成一棵 Trie，一次扫描主串同时完成所有模式的匹配"。构建分三步：第一步，把所有敏感词插入 Trie，叶子标记"这里是某个词的结尾"；第二步，BFS 求 fail 指针——fail[u] 指向"u 节点代表字符串的最长真后缀，且该后缀也是某个模式的前缀"的节点；第三步，匹配：从根出发按主串字符沿 Trie 走，若当前节点没有该子节点，就沿 fail 跳到能继续的位置（这保证主串不回溯），每到一个节点还要沿 fail 链收集所有命中的模式（因为"词尾"可能藏在后缀里）。复杂度：构建 O(总模式长度)，匹配 O(主串长度 + 命中总数)，这才是它能扛住敏感词过滤的根本原因。工程化的几个点：一是"命中报告策略"——常见只需报告首个命中/最长命中，可剪掉部分 fail 链遍历；二是大词库时构建出的 Trie 可能占几十 MB，要关注内存，可用压缩边或双数组 Trie；三是中文场景的变体绕过（谐音、插入标点、拆字）AC 匹配不到，需配合预处理（归一化、去噪）或扩展到编辑距离容忍的近似匹配；四是匹配结果要能反查"命中哪个词、位置在哪"，便于审核系统展示。实践中的坑：词库更新频繁时全量重建 AC 代价大，用"主 AC + 增量词表"双通道或定期重建；AC 匹配的是子串级，要区分"敏感词出现在 URL 里"等上下文，可能还要接白名单或策略引擎。

**延伸考点：** 如果要求"命中时必须给出最长匹配词"（如 "敏感词系统"命中 "敏感" 和 "敏感词" 两个模式），AC 自动机匹配阶段怎么处理？AC 自动机 + 通配符（如 "a?c"）扩展成更复杂的多模匹配时，构建有什么变化？

### Q19. 接口要在"秒杀"瞬间扛住百万 QPS 的瞬时洪峰，设计层面和数据层面各怎么办？

**问题：** 秒杀/大促时流量会在几秒内从几千 QPS 冲到百万 QPS，但真正的"可成交"订单远少于请求数。请从系统设计角度讲清"削峰、限流、放行"三件事分别怎么做，再落到数据结构与算法层面说明每层怎么实现。

**期望加分项：**
- 能拆层次：网关限流（令牌桶/漏桶）→ 队列削峰（MQ）→ 缓存承接 → 数据最终一致性
- 令牌桶：匀速令牌注入，允许突发，适用于"希望平滑但容忍短突发"；漏桶：恒定速率输出，强制平滑
- 能讲清"漏斗模型"的层次：请求先到网关（限流放行）→ 写入 MQ（缓冲）→ 下游按库存能力消费；或 Redis 原子扣减库存 → MQ → DB 落账
- 关键算法点：Redis `DECR`/Lua 原子扣库存防超卖；MQ 保证不丢不重；数据库乐观锁 `UPDATE ... SET stock=stock-1 WHERE stock>0`
- 能给出"限流放行率"的量级估算：真正可成交订单/请求量可能是 1/1000
- 讨论降级：直接返回"已售罄/繁忙"给未放行请求，前端轮询或 WebSocket 通知
- 会算"秒杀单点写放大"：单个 SKU 的库存扣减并发必须串行化（Redis 单线程天然适合）

**减分项：**
- 只会说"上 MQ 削峰"，说不清削峰后库存怎么扣、超卖怎么防
- 限流算法只背名字，不知道令牌桶和漏桶的区别
- 不考虑"未放行请求"的用户体验（直接 404 还是排队提示）
- 库存扣减不加原子性，出现超卖
- 没有"最终一致性"的兜底（异步对账/补偿）

**解答：**
秒杀的本质是"瞬时洪峰 + 稀缺资源"，所以设计主线是"流量分层消化 + 库存原子扣减 + 最终一致性"。第一层网关/接入层：限流器先用令牌桶（Guava RateLimiter、Redis Lua 实现）把流量从百万压到后端能承受的水平——令牌桶按固定速率注入令牌、允许少量突发，漏桶则强制匀速，前者更适合"平滑但容忍突发"的秒杀；被限流的多余请求直接返回"排队中/已抢完"，不要放进来。第二层队列削峰：放行后的请求写入 MQ（如 Kafka/RabbitMQ），下游按消费能力取单处理，把"秒级洪峰"拉平为"分钟级匀速"，同时天然获得异步化。第三层库存：用 Redis 原子扣减——`DECR` 或 Lua 脚本一次完成"检查库存>0 且扣减"，Redis 单线程执行保证无超卖；扣减成功才发 MQ 落数据库，DB 层再上乐观锁（`UPDATE sku SET stock=stock-1 WHERE id=? AND stock>0`）做最终兜底。第四层对账：定时任务核对 Redis 扣减数 vs DB 落账数，出现差异补偿。要能回答"为什么扣库存放 Redis 不放 DB"：DB 单行更新要行锁、TPS 有限（几千~几万），Redis 单机轻松上十万；而"单 SKU 扣减"本质是串行资源，Redis 单线程模型正好把串行化做在引擎层。算法层面的细节：限流要按用户维度（同 uid 限 1 次）+ 全局维度双层；防止"脚本抢购"要靠风控与验证码，不在本题核心但可提；秒杀成功后的通知用轮询/WebSocket 返回结果，别让前端自己猜测。最后给出"设计检验标准"：任何一次请求都必须有明确去向——要么限流拒绝、要么排队、要么成功扣减，三选一，不能有请求丢失或库存超卖。

**延伸考点：** 同一个用户同时发起 100 个请求，Redis 扣库存怎么做到"每人限购 1 件"（需要 Lua 里加用户维度判重）？如果秒杀商品是"多 SKU 可选"（如颜色尺码），库存分布在不同 key，怎么避免事务性丢失？

### Q20. "缓存是系统里最难的事"——缓存一致性、击穿、穿透、雪崩的工程解法，你会怎么完整讲？

**问题：** 面试官让你完整讲一遍缓存体系：Cache-Aside 写策略下缓存与数据库的一致性怎么保证？缓存击穿、穿透、雪崩分别是什么、各自怎么防？请按"问题定义 → 解法 → 权衡"的结构讲，并给出量化依据。

**期望加分项：**
- 能先分类：缓存穿透（查不存在的数据）、击穿（热点 key 过期瞬间）、雪崩（大量 key 同时失效或缓存整体不可用）
- Cache-Aside 的正确顺序：先更新 DB 再删缓存（而非更新缓存），删失败用消息队列重试补偿
- 一致性程度分层：强一致/最终一致（允许短暂不一致窗口）、脏数据检测
- 穿透：布隆过滤器挡不存在 key + 空值缓存（TTL 短）；击穿：互斥锁/分布式锁重建 + 逻辑过期；雪崩：过期时间加随机值 + 缓存多级/降级
- 会量化：缓存命中率、重建成本（DB 压力）、不一致窗口的时长
- 主动提"缓存加不加锁的取舍"：锁保护重建，但锁本身也是热点
- 能说出"删缓存 vs 更新缓存"的经典坑：并发下更新缓存会引入旧值覆盖

**减分项：**
- 三种故障混为一谈，说不清各自场景
- Cache-Aside 写错了顺序（先更新缓存）还不自知
- 只说"加锁"，不知道锁的粒度、超时、重入问题
- 不给量化依据（命中率、重建成本）
- 不考虑缓存本身的可用性（缓存挂了怎么降级）

**解答：**
先按"故障三分法"定义清楚，防止概念混用。穿透：查询一个数据库中不存在的数据，每次都要打到 DB（攻击者可构造大量不存在的 key 打爆 DB）。防法：1) 布隆过滤器前置拦截"不可能存在的 key"；2) 对查无结果的 key 也缓存空值并设短 TTL（如 60s），把 DB 压力降到极低——两个方案按"key 空间是否可枚举/可预知"取舍。击穿：某个热点 key 过期瞬间，海量请求同时打到 DB 重建。防法：1) 互斥锁（分布式锁/进程内锁）：重建期间只允许一个请求回源，其余等待或读旧值，注意锁超时与热点线程被拖垮；2) 逻辑过期：value 里存"过期时间戳"，后台线程异步刷新，读请求永不阻塞但可能短暂读到旧值——权衡是"一致性 vs 重建延迟"。雪崩：大量 key 同一时间过期，或 Redis 整体不可用，导致 DB 被打爆。防法：1) 过期时间加随机抖动（base + rand(0,300)s），错开集中过期；2) 多级缓存（本地 Caffeine + Redis）与缓存高可用（主从/集群/哨兵）；3) 降级预案：缓存挂了直接降级到"限流 + 直查 DB 的简化查询"。然后是 Cache-Aside 的一致性顺序（最常考）：读先查缓存，miss 回源 DB 再写缓存；写操作"先更新 DB，再删除缓存"，而不是更新缓存——因为"更新缓存"存在并发窗口：两个请求 A/B，A 写库后更新缓存，B 更新后 A 又覆盖，或 B 的旧读先于 A 写导致缓存旧值覆盖新值；而"删缓存"配合"下一次读 miss 重建"天然避免旧值常驻。删缓存失败怎么兜底：用消息队列/订阅 binlog（如 Canal）异步删除并重试。最后要承认一致性有代价：Cache-Aside 是最终一致（DB 更新与缓存删除之间有不一致窗口），强一致场景要"读也走 DB"或"事务+缓存同步"或干脆别用缓存。给出衡量标准：命中率（>95% 说明缓存有效）、重建成本（回源 QPS 是否压垮 DB）、不一致窗口时长（业务可接受性），三者是设计缓存的核心三角。

**延伸考点：** 为什么"先删缓存再更新 DB"比"先更新 DB 再删缓存"更容易出问题，给出一个具体的时序反例？缓存 key 是"聚合结果"（如列表页全量数据）时，某个元素变化如何精确失效而不清掉整个缓存？
