# 通用 · 网络安全（面试题库）

本文件考察候选人面向 Web 业务的网络安全工程实践能力，不考八股文式的概念背诵。考察重点：Web 常见漏洞（SQL 注入、XSS、CSRF、SSRF、文件上传、命令注入、反序列化）的发现与修复、认证授权与越权防护、密码与密钥管理、传输与 API 安全、安全测试与 DevSecOps、日志检测与应急响应、合规治理与零信任/云安全架构。题目以真实事故与业务场景切入，考察候选人能否给出可落地的方案、说清取舍，并有线上实战佐证。

### Q1. 从源头封死 SQL 注入：搜索接口注入的定位与修复

**问题：** 安全测试报告线上一个搜索接口存在 SQL 注入。你如何确认注入点与注入类型？修复这一处之外，还需要做哪些工作避免同类问题再次出现？

**期望加分项：**
- 能讲清「参数化查询为什么能防注入」的本质（数据与代码分离），而非只背结论
- 能给出 MyBatis `#{}` vs `${}`、JDBC PreparedStatement 等具体落地对比
- 主动覆盖 ORDER BY、IN、LIKE、表名等「预编译失效」的角落，并给出白名单方案
- 提出纵深防御：最小权限数据库账号、WAF 兜底、扫描与 Code Review 常态化
- 能说明布尔盲注 / 时间盲注的确认方法，体现真实排查经验

**减分项：**
- 只会背「预编译防注入」，讲不出原理与适用边界
- 只修报告点出的接口，没有存量排查思路
- 把 WAF 当作唯一防线，或迷信「过滤关键字」
- 忽略二次注入、编码绕过等历史遗留场景

**解答：**
先确认注入点与类型：接口若把用户输入直接拼接进 SQL，通过报错回显可判断语法错误注入；无回显时用布尔盲注（如 `id=1 AND 1=1` 与 `AND 1=2` 对比响应）或时间盲注（`SLEEP(5)` 观察延迟）确认，再结合输入点判断是字符型还是数字型。修复的核心不是「过滤关键字」而是让数据与代码分离：Java 用 PreparedStatement / MyBatis 的 `#{}`，Node 用驱动占位符，Python 用参数绑定，业务代码中禁止 `+` 拼接 SQL。存量排查要扫全量 DAO 层代码，重点盯 `${}`、字符串拼接、动态排序与分页——ORDER BY、IN、LIKE 这类无法直接参数化的位置是常见漏网点，正确做法是白名单映射（如排序字段名与 DB 列名做映射表，非法值拒绝）。纵深防御兜底：数据库账号按最小权限分库分表、只授必要操作权限；WAF 仅作兜底（编码、注释、Unicode 变体可绕过）；上线前用 sqlmap 复测。实践中的坑：仅过滤单引号与 `--` 可被宽字节、二次编码绕过；二次注入（恶意数据先入库、再次拼接执行）需要特别注意从库中取出后仍要参数化。

**延伸考点：** 二次注入是怎么产生的，如何防御？动态排序与 IN 子句无法参数化，怎么安全实现？

### Q2. 存储型 XSS 的定位与富文本场景下的修复

**问题：** 用户反馈在个人中心输入内容并保存后，打开页面直接弹窗（alert），怀疑是存储型 XSS。如何定位根因并修复？如果该功能必须支持富文本，方案有什么不同？

**期望加分项：**
- 能区分存储型 / 反射型 / DOM XSS，并说清各自的修复侧重点
- 富文本场景知道用白名单净化（如 DOMPurify），并能说明为何黑名单必然被绕过
- 能讲清输出编码要按上下文区分（HTML 元素、属性、JS、URL 各自编码规则不同）
- 主动补 CSP、HttpOnly Cookie 等兜底，并说明前端的 `innerHTML`、`v-html` 风险点
- 能指出服务端与前端输出点都要覆盖，多端（Web/H5/App WebView）一致

**减分项：**
- 只会说「过滤 < >」或「转义引号」，讲不清上下文编码
- 不知道富文本为什么必须白名单，用黑名单凑合
- 忽略 DOM XSS 与前端框架默认转义的边界
- 混淆「输入过滤」与「输出编码」的作用

**解答：**
打开页面即执行，说明数据入库时未做策略性过滤、输出时未编码，属于典型的存储型 XSS。定位时先确认写入链路（输入接口、存储字段、渲染方式），再排查所有输出点：模板插值、`innerHTML`、`v-html`、`dangerouslySetInnerHTML`、URL 参数拼接、`eval`。修复原则是「输入侧策略性过滤，输出侧按上下文编码」：纯文本场景，输出时对 `<>&"'` 做实体编码即可，前端框架（Vue/React）的插值默认转义，但 `v-html` 类 API 会绕过默认保护，使用前必须净化。富文本场景必须用白名单净化库（前端 DOMPurify、服务端 OWASP Java HTML Sanitizer 等），配置允许的标签与属性，属性值里的 URL 只允许 http/https 协议，`javascript:` 一律拒绝——黑名单过滤（禁 script、onerror）必然被大小写、编码、事件属性组合绕过。兜底：加 CSP 限制脚本来源，会话 Cookie 加 HttpOnly+Secure，降低凭证被窃影响。实践中的坑：DOM XSS 不经过服务端，服务端编码与 CSP 都拦不住，前端同样要做编码与净化；多端场景要统一评审输出点，App 的 WebView 注入接口（addJavascriptInterface）要加协议白名单校验。

**延伸考点：** Vue/React 默认转义为什么还会中 XSS？必须用 v-html 渲染富文本时如何兜底？

### Q3. 「没点任何按钮钱被转走」：CSRF 的确认与修复

**问题：** 用户投诉「没点任何按钮，账户里的钱被转走了」，怀疑是 CSRF。你怎么确认？修复方案有哪些，各自的取舍是什么？它与 XSS 的本质区别在哪里？

**期望加分项：**
- 能讲清 CSRF 利用的是浏览器自动携带 Cookie 的机制，无需执行攻击者代码，与 XSS 是两类攻击
- 给出多层修复：SameSite Cookie、CSRF Token、Origin/Referer 校验、关键操作二次验证
- 能说清 SameSite=Lax 对跨站跳转、第三方登录回调的兼容性影响
- 能指出无 Cookie 认证（Authorization 头、双 Token）场景天然免疫 CSRF
- 了解 JSON 接口与老浏览器伪造 Content-Type 的历史绕过场景

**减分项：**
- 说不清 CSRF 与 XSS 的区别
- 只提 CSRF Token，不知道 SameSite 已是现代主流方案
- 不知道 Token 必须放请求体/头而非 Cookie
- 忽略 GET 请求被滥用为副作用操作的问题

**解答：**
判断思路：受害者在登录态下访问了恶意页面，恶意页面用表单或图片标签自动发起跨站请求，浏览器自动带上 Cookie，服务端无法区分请求是否用户本意——这就是 CSRF 的特征。确认方法：检查目标接口是否仅依赖 Cookie 认证、是否校验来源与 Token。与 XSS 的本质区别：XSS 是代码注入，攻击者可以在受害者页面里执行任意脚本；CSRF 是「诱导浏览器发请求」，攻击者拿不到也不需要在受害者页面执行代码（但 XSS 可以配合 CSRF 增加危害）。修复分三层：1) Cookie 层面：`SameSite=Lax`（默认放行顶层 GET 导航，拦掉跨站 POST），关键操作可上 `Strict`，需评估跨站跳转与第三方登录回调用例；2) 请求层面：CSRF Token 绑定会话，敏感请求必须携带，前后端分离场景放自定义 Header（自定义头不受表单自动提交影响）；3) 业务层面：转账、改密等关键操作加支付密码/短信二次验证。补充校验 Origin/Referer 要注意空 Origin（隐私模式、部分 App 内嵌）不能一律放行。实践中的坑：Token 存进 Cookie 等于没防；把写操作做成 GET 接口会放大攻击面；纯 JSON API 早期被认为天然免疫，实际老浏览器可用表单伪造 Content-Type，仍需校验。

**延伸考点：** 前后端分离 + JWT（Authorization 头）的项目为什么 CSRF 风险低？风险转移到了哪里？

### Q4. SSRF：URL 抓取功能被用来探测内网，如何封堵

**问题：** 系统有个「根据 URL 生成网页缩略图 / 抓取页面」的功能，被安全测试发现可以通过它探测内网、读取云元数据。如何发现与修复？需要防住哪些绕过手法？

**期望加分项：**
- 能说清 SSRF 的危害面：内网端口探测、读取云元数据（169.254.169.254）、横向攻击
- 修复思路完整：协议白名单 → DNS 解析后校验真实 IP → 防重定向绕过 → 网络层出网收敛
- 知道常见绕过：十六进制/八进制 IP、`[::1]`、短域名、DNS Rebinding、302 跳转
- 云上场景特别关注元数据接口与实例角色凭证泄露
- 能提业务可用性权衡：校验失败给明确错误而非静默失败

**减分项：**
- 只用正则做 URL 黑名单，忽略 DNS 解析与重定向
- 不知道云元数据接口的存在与危害
- 只堵应用层，不提网络层出网控制
- 修复时一刀切禁掉功能，不考虑业务损失

**解答：**
「服务端主动访问任意 URL」意味着攻击者能借服务器发起内网请求，危害是内网探测、端口扫描、读取云元数据接口（169.254.169.254，可拿到实例角色临时凭证）乃至横向攻击。修复分三层：第一层应用层：只允许 http/https 协议（禁止 file、gopher、dict 等），拿到 URL 后先解析 DNS 得到真实 IP，校验不在保留网段（10/8、172.16/12、192.168/16、127/8、169.254.169.254 等）——只对 URL 字符串做正则一定被绕过（十进制/十六进制 IP、`[::1]`、`0x7f000001`、短域名解析等），必须解析后比对 IP；第二层防绕过：跟随 302 重定向时对最终地址再做同样校验，DNS 解析结果在连接时再次校验防 DNS Rebinding；第三层网络兜底：服务端出网统一走代理/白名单网关，内网按零信任分段，即使应用层被绕过也访问不到敏感网段。实践中很多图片处理、网页快照功能为可用性默认全放开，修复时要同步做灰度：校验失败返回明确错误，同时在日志里记录被拦截的目标便于攻击溯源。云上实例用最小权限角色（IMDSv2 开启），并把元数据访问限制到必要进程。

**延伸考点：** 云上实例元数据接口 169.254.169.254 为什么危险？如何系统收敛服务端出网流量？

### Q5. 头像上传被传了 WebShell：止血、根因与修复

**问题：** 网站头像上传功能被安全事件监测发现有人上传了 WebShell（网页木马）。请给出止血步骤、根因分析思路，以及一劳永逸的修复方案。

**期望加分项：**
- 处置有序：先止血（删除文件、断外联、排查同目录与日志）再分析根因
- 能指出常见绕过：Content-Type 伪造、多后缀、图片马 + 文件包含、解析漏洞
- 修复要点完整：扩展名白名单 + 魔数校验 + 随机文件名 + 上传目录禁止脚本执行 + 存储与代码分离
- 云上方案：对象存储静态托管 + CDN，天然无脚本执行
- 知道要排查「隐式上传点」（CSV 导入、附件等），而非只修头像一处

**减分项：**
- 只会加扩展名黑名单（php、jsp 逐一枚举）
- 不处理上传目录可执行权限（Nginx/Apache 解析配置）
- 只删当前文件，不做存量扫描与全站上传点排查
- 不知道图片马 + 二次渲染的绕过原理

**解答：**
WebShell 说明两个事实：文件落进了可执行目录，且被当作脚本执行了。处置顺序：1) 止血——立即删除已确认的 WebShell 文件，杀掉异常进程，阻断可疑外联 IP，按日志时间线排查同目录近期写入的文件与访问路径；2) 根因分析——上传校验通常只看了 Content-Type 或扩展名黑名单：攻击者改包把 Content-Type 改成 image/jpeg、传 `a.php.jpg` 多后缀、利用 Nginx 对不存在的扩展名交给 PHP 解析的配置漏洞、或图片马配合文件包含执行。3) 修复要点——多重校验：扩展名白名单（jpg/png 等）+ Content-Type + 文件头魔数（可伪造，仅作辅助）+ 服务端对图片二次渲染/压缩丢弃冗余数据；存储重命名：用随机 UUID 重命名，丢弃用户可控后缀；执行隔离：上传目录禁止脚本执行（Nginx 配置该 location 不转发给 PHP），并加 `Content-Disposition: attachment` 防止浏览器把上传文件当 HTML 渲染（XSS）。云上直接落 OSS/S3 静态托管 + CDN，脚本无法执行，是最干净的方案。实践中的坑：只修头像上传点——CSV 导入、文件附件、富文本图片等「隐式上传」常被漏掉；历史存量文件要做一轮全量扫描。

**延伸考点：** 图片马 + 文件包含组合攻击怎么防？「上传目录禁止执行脚本」在 Nginx 上具体怎么写？

### Q6. 命令注入与反序列化：两类高危漏洞的处置

**问题：** 一个调用外部命令的运维工具（如 ping 检测）被报告存在命令注入；同时引入的 Java 组件被爆出反序列化漏洞。请分别给出定位、修复与止损方案。

**期望加分项：**
- 命令注入：不经过 shell（参数数组/ProcessBuilder），参数白名单校验，能用库替代就不用系统命令
- 反序列化：先评估可达性再处置，升级/禁用危险类/过滤类白名单等组合拳
- 临时止损：WAF 特征拦截、关闭受影响入口，但明确这只是临时措施
- 升级带来的兼容性回归风险有预案
- 两类漏洞的处置思路不混淆

**减分项：**
- 命令注入用正则黑名单过滤，说不清为什么必被绕过
- 反序列化只喊「升级版本」，不做可达性评估与回归
- 忽略 Java 反序列化黑名单类不完整的现实
- 紧急处置一刀切下线功能，无业务影响评估

**解答：**
两类漏洞的处置思路不同：命令注入的核心是「数据不再进 shell」。如果功能是 `ping $ip` 这类 shell 拼接，修复用参数数组形式调用——Python 用 `subprocess.run(["ping", ip], shell=False)`，Java 用 `ProcessBuilder`，绕开 `/bin/sh -c` 的解析环节；同时对参数做白名单校验（IP 用 ipaddress 模块解析、拒绝非法字符与分号管道等元字符）；更优解是功能层替换：ping 的目的通常是「探测连通性」，用平台 TCP 探测或 SDK 实现即可。反序列化处置顺序：1) 评估可达性——线上是否存在反序列化用户输入的真实路径（入口类、数据流），没有可达面的可以先降级风险等级；2) 修复——升级到官方修复版本，或换替代库；3) 无法立即升级的临时加固——全局禁用危险类（Fastjson safeMode、ObjectInputFilter 类白名单）、WAF 拦截已知 gadget 特征，但临时规则挡不住变体，必须尽快落到版本升级。两者的共同坑：为「安全」急升级导致线上兼容性故障是常见二次事故，升级必须带回归与灰度；安全修复要连同测试用例一起沉淀，防止回归。

**延伸考点：** Java 反序列化 gadget 链为什么难以靠黑名单彻底封堵？ObjectInputFilter 类白名单的正确用法？

### Q7. 认证方案选型：Session 还是 JWT，考虑哪些因素

**问题：** 新项目需要设计登录认证：一个是对内管理系统（需强管控），一个是对外 App（多端、跨域）。Session 还是 JWT？你怎么选，落地时各自要防哪些坑？

**期望加分项：**
- 先问场景再给结论：能谈 Session 的撤销能力、服务端可控；JWT 的无状态、跨域优势
- 说清 JWT 的硬伤：无法服务端吊销、密钥泄露全线失守、payload 可读非加密
- 知道算法混淆攻击（alg:none、RS256→HS256）并给出对策
- 落地细节：短时效 access + refresh 旋转、Token 存储位置（Cookie vs localStorage）与 XSS 的关系
- 能谈 Session 的分布式会话一致性、Session Fixation 问题

**减分项：**
- 无脑「JWT 更安全/更先进」选型，说不清场景差异
- 不知道 JWT 签发后服务端无法作废
- 把敏感数据放进 payload 当加密用
- 忽略 refresh token 的存储与轮换

**解答：**
先问场景：内部管理系统用户量小、部署在受控网络，需要「踢下线、改密即失效、会话审计」等强管控——Session + Redis 存储天然可撤销，配合 HttpOnly + Secure + SameSite Cookie 即可，这是首选。对外 App 跨域、多端、水平扩展压力大，JWT 无状态更合适，但要正视三个硬伤：1) 无法服务端吊销——用户改密或被踢后，旧 Token 在过期前仍有效，需引入黑名单/短时效缓解；2) 密钥泄露等于全线失守——密钥必须走密钥管理系统，算法要显式锁定并校验，防 `alg:none` 与 RS256→HS256 混淆（用公钥验签时攻击者用私钥伪造签名即可切换算法）；3) payload 只是 Base64 编码，可读不可信——只放 userId 等非敏感标识，业务数据服务端再查。落地要点：access token 设短时效（15 分钟级），配合 refresh token 旋转（每次刷新换新、可被服务端撤销），降低泄露窗口。存储位置：Web 端放 HttpOnly Cookie（防 XSS 窃取）优于 localStorage；移动端放系统安全存储。Session 方案注意点：分布式环境会话放 Redis 而非粘滞会话，登录成功要换 Session ID 防 Fixation。坑：很多「为微服务选 JWT」的团队把微服务间内部凭证与用户凭证混用一套密钥。

**延伸考点：** 用户改密码或被强制下线后，已签发的 JWT 如何作废？黑名单与短时效方案怎么取舍？

### Q8. 第三方 OAuth 登录与内部 SSO：最容易出问题的环节

**问题：** 公司要接入第三方 OAuth 登录（微信 / Google），同时给内部系统做统一 SSO。设计时哪些环节最容易出安全问题？请给出清单与对策。

**期望加分项：**
- OAuth 侧：state 防 CSRF、redirect_uri 严格校验、授权码一次性使用、scope 最小化
- 账号绑定侧：用第三方唯一标识（openid/sub）而非昵称/邮箱映射账号，合并前二次验证
- SSO 侧：SAML/OIDC 断言验签、校验 audience/issuer、防重放与全局登出
- 知道回调异常链路（用户拒绝授权）也要正确处理
- 能讲清「授权码换 token 后再取用户信息」的正确流程

**减分项：**
- 不知道 state 参数是干什么的
- 用昵称、邮箱当账号唯一标识
- 忽略授权码复用与 redirect_uri 前缀匹配问题
- 只测正常流程，不做异常链路测试

**解答：**
OAuth 登录的漏洞集中在「回调链路」与「账号绑定」两处。回调链路：1) state 参数必须加——授权码回调存在 CSRF（攻击者诱导受害者的浏览器完成授权流程），state 用随机值绑定本次登录会话，回调解码后比对；2) redirect_uri 必须严格白名单且精确匹配（不能用 contains，否则攻击者可把回调指到自己域名骗到授权码），同一客户端绑定固定回调地址；3) 授权码一次性使用，且换 token 时必须校验 code 对应的 client_id 与 redirect_uri，防止复用/串用；4) scope 最小化，只申请业务真正需要的权限（如只读基本资料，不要通讯录）。账号绑定：用第三方返回的唯一稳定标识（微信 openid、OIDC sub）去映射本地账号，绝不能拿昵称、邮箱当唯一键——攻击者注册同昵称/同邮箱即可撞号接管；涉及合并账号（本地密码账号与第三方账号关联）时必须二次验证（短信/密码）确认归属。SSO：SAML/OIDC 断言必须验签、校验 issuer 与 audience 是否指向本系统、通过 nonce/断言时效防重放；登出要实现全局单点登出，避免「登出一个入口，其他系统会话还在」。实践中的坑：回调接口要区分「用户拒绝授权」的错误返回与正常流程，否则会产生空引用/重复建号的线上问题。

**延伸考点：** OAuth 回调中 state 校验失败会导致什么？第三方账号与本地账号合并时如何防「账号接管」？

### Q9. 越权（IDOR）：改一下 id 就能看别人的订单

**问题：** 渗透测试发现修改请求中的 id 参数就能查看别人的订单、导出别人的数据。这类对象级越权如何系统排查与防范？为什么逐接口打补丁治不住？

**期望加分项：**
- 能区分水平越权与垂直越权，并说明各自根因
- 提出对象级授权基线：业务层统一校验资源归属（ownerId 比对）
- 数据层兜底：SQL 强制带 user_id 条件，list 接口尤其重要
- 知道在 CI/自动化中沉淀越权用例，或批量遍历 id 做检测
- 能点出导出、批量接口是越权重灾区

**减分项：**
- 只修当前接口，没有系统化方案
- 不知道「对象级授权」与「身份认证」是两件事
- 依赖前端隐藏按钮/菜单做安全控制
- 不知道 list 接口的越权面更大

**解答：**
改 id 能看到别人的数据，是典型的对象级越权（IDOR），根因是「只验证了你是谁，没验证这个资源是不是你的」。逐接口补判断治不住的原因：团队接口数量多、新接口持续产出，漏一个就崩。系统化方案：1) 建立对象级授权基线——在业务服务层统一校验资源归属（`order.getOwnerId().equals(currentUserId)`），把校验收敛到一个公共工具类或访问控制服务，各接口复用而不是各写各的，防止实现漂移；2) 数据层兜底——查询 SQL 强制带 `AND user_id = ?`，即使上层漏判，数据库层面也拉不出别人的数据，这条对 list 接口尤其关键（list 接口经常只按条件查询、缺少归属过滤，批量拉数据全靠它）；3) 网关/中间件统一做身份与权限（RBAC 管「你能调哪些接口」），对象级授权仍要落在业务层，两者是两层；4) 测试常态化——写越权用例（A 的 Token 请求 B 的资源）进入自动化回归，或用工具在 CI 中对 id 做遍历模糊测试。区分水平越权（同级互看）与垂直越权（低权限调高权限接口），后者靠接口权限清单 + 统一鉴权治理。坑：前端隐藏按钮、按钮置灰都是假安全，任何请求都能直接发到后端；导出、报表、批量同步类接口权限要单独收紧。

**延伸考点：** 如何在 CI 中自动化检测对象级越权？为什么 list 类通用接口的越权面更大？

### Q10. 密码存储：拖库之后，让密码库「无利可图」

**问题：** 登录功能上线后有人拖库，密码怎么存才安全？如果存量是明文或弱哈希（MD5/SHA1），怎么处置？

**期望加分项：**
- 能讲清加盐哈希与「加密」的区别，说明为何 MD5/SHA1 不可用（GPU 撞库、彩虹表）
- 知道选 BCrypt（cost 取值依据）或 Argon2id（内存型抗 GPU），盐随机且每用户独立
- 存量处置方案完整：检测撞库、强制重置、渐进式迁移（rehash on login）
- 密码策略「长度优先于复杂度」，配合防爆破（限流/锁定/验证码）
- 知道 BCrypt 72 字节截断等实现细节

**减分项：**
- 说「MD5 加盐就安全」
- 把哈希和加密混为一谈
- 没有存量数据迁移与用户通知方案
- 忽略撞库后的风控动作（异常登录检测）

**解答：**
判断思路：拖库已经发生，密码存储的目标是让「拖库无收益」。原则：密码绝不可逆存储。MD5/SHA1 及固定盐加盐 MD5 都被 GPU 撞库击穿（每秒数十亿次），必须用慢哈希：BCrypt（cost 依据服务器算力与登录 QPS 实测，一般 10-12，控制在百毫秒级）或 Argon2id（现代首选，内存型参数天然抗 GPU 并行）。盐必须随机、每用户独立，BCrypt/Argon2 内部已自动生成并随哈希存储，不需要自己拼盐。存量处置分三层：1) 立即——启动撞库监控（同 IP 批量尝试、异地高频登录告警），必要时强制全量重置密码；2) 中期——渐进式迁移：登录时检测到旧算法哈希则现场用新算法重算（rehash on login），配合「一段时间未登录强制改密」逐步清零弱哈希；3) 长效——测试环境必须用脱敏数据，禁止开发直连生产库，审计数据访问。密码策略上「长度优先于复杂度」（12 位以上随机组合）更有效，配合登录失败限流、锁定与验证码防爆破。实现细节的坑：BCrypt 只取前 72 字节（超长密码需先 SHA-256 预哈希再喂 BCrypt，或直接换 Argon2）；「先哈希再加密」的双层方案只适用于需要给密码做二次校验/审计的场景，多数业务不需要。

**延伸考点：** BCrypt 与 Argon2id 的差异与选型依据？拖库后如何检测并处置撞库攻击？

### Q11. 密钥管理：代码里的硬编码 SecretKey 怎么清理

**问题：** Code Review 发现代码里硬编码了数据库密码和云厂商 SecretKey。怎么立即处置？怎么建立长效机制，让密钥不再出现在代码里？

**期望加分项：**
- 处置顺序正确：先假设已泄露——轮换密钥、撤销 AK/SK、扫描 git 历史（gitleaks/trufflehog）
- 能说清环境变量只是「不在代码里」，不是密钥管理方案
- 知道密钥管理系统（Vault/KMS/Secrets Manager）的价值：动态凭据、权限、审计、自动轮换
- 落地配套：git hook/CI 扫描拦截、密钥与配置分离、镜像层泄露排查
- 最小权限 + 定期轮换的原则

**减分项：**
- 只删当前文件，不轮换不扫描历史
- 以为「放环境变量就安全了」
- 忽略 git 历史、CI 日志、镜像层里的密钥
- 不知道密钥管理系统解决什么问题

**解答：**
发现硬编码密钥的第一反应不是删代码，而是「假设已泄露」处置。立即动作：1) 轮换——改数据库密码、重新生成云 AK/SK（先发新后禁旧，避免服务中断，用云审计日志确认旧凭证是否被异常调用）；2) 全量排查——不止当前分支，git 历史里躺着更多（用 gitleaks/trufflehog 扫全历史），历史已推到远端的只能靠轮换兜底；3) 覆盖所有载体——CI 日志、镜像层（镜像构建时 COPY 进 secret 会永久留在镜像里，需重建镜像）、错误上报平台、日志聚合系统。长效机制要回答「密钥放哪」：环境变量只是「不在代码里」，拿到 shell 的人照样能读，且无法做权限细分、审计与自动轮换；正规做法是密钥管理系统——Vault（动态凭据、租约自动过期、审计）、云 KMS/Secrets Manager（加密存储 + IAM 权限 + 自动轮换），应用启动时拉取到内存，禁止写日志与 dump。配套：git 提交前 hook + CI 用模式/熵检测扫描拦截；本地开发用本地配置或 mock，生产密钥只在运行环境注入。实践中的坑：轮换要确认所有消费方都切到新密钥再禁用旧值；「Secret 扫不出来」不等于安全，要定期做全仓复查。

**延伸考点：** 云 AK/SK 泄露后攻击者能做什么？如何用云审计日志发现异常调用？

### Q12. 安全响应头：CSP、HSTS、X-Frame-Options、SameSite 怎么落地

**问题：** 安全报告建议加上 CSP、HSTS、X-Frame-Options、SameSite 四个安全头。逐一评估哪些该上、会带来什么线上影响，以及如何平滑落地不误伤业务？

**期望加分项：**
- CSP 用 report-only 灰度，先收集违规再 enforce，内联脚本用 nonce/hash 方案
- HSTS 先短后长，preload 不可逆要慎重
- 知道 X-Frame-Options 与 CSP frame-ancestors 的关系与优先级
- SameSite=Lax 对跨站跳转、第三方登录回调的影响评估
- 统一在网关/CDN 层加头，灰度期观察业务指标

**减分项：**
- 一股脑全开，不做影响评估
- 不知道 CSP report-only 模式
- 混淆 X-Frame-Options 与 frame-ancestors 的作用
- 加了头不验证效果，也不处理违规报告

**解答：**
四个头各有分工，落地顺序与灰度方式不同，最容易被误伤的是 CSP。CSP 的正确姿势：先上 `Content-Security-Policy-Report-Only`（只上报不拦截），配 report-uri/report-to 收集违规，跑一两个迭代清理完违规项再转 enforce；内联脚本、第三方统计、CDN 外链、iframe 都是常见拦截点——动态内联脚本用 nonce（每次响应随机值）或 hash 方案，配合构建工具（webpack 注入 nonce）落地，`'unsafe-inline'` 能不开就不开。HSTS：先 `max-age=300` 观察一段时间再逐步加到半年/一年；preload 一旦提交浏览器厂商清单就无法撤回，必须灰度充分后再上。点击劫持防护：`X-Frame-Options: DENY/SAMEORIGIN` 与 CSP `frame-ancestors` 作用重叠，后者更精细（可精确到具体域名），老浏览器两者同开取交集。SameSite：先上 `Lax`（默认放行顶层 GET 导航），重点观察跨站跳转、分享链接与第三方登录回调；敏感操作（改密、支付）再评估 `Strict`。落地载体：统一在网关/CDN 层配置，避免每个应用各配一套导致漂移；灰度期用违规报告与业务指标（跳转成功率、支付转化率）双向观察，上线后用 securityheaders 类工具复查。坑：只加头不消费违规报告等于没做；漏配 `frame-ancestors` 会让点击劫持仍然存在。

**延伸考点：** CSP 开启后如何排查被拦截的资源？nonce 方案与 webpack 动态注入怎么配合？

### Q13. 依赖与供应链安全：第三方库爆了高危 CVE

**问题：** 引入的第三方库被爆出高危 CVE。如何评估风险并处置？如何建立长效的依赖治理机制，把供应链风险挡在门外？

**期望加分项：**
- 先评估可达性再处置：库在业务里的实际调用路径、利用前置条件、缓解因素
- 处置分级：升级 / 临时缓解（WAF、关功能）/ 替换，能说清各自适用场景
- 长效机制：SCA 扫描接入 CI、锁文件提交、SBOM、版本策略
- 供应链源头：私有仓库代理、校验和验证、防投毒（typosquatting）与依赖混淆
- 升级必带回归测试与灰度，防二次事故

**减分项：**
- 见 CVE 就恐慌，不评估可达性
- 不知道锁文件（lockfile）的作用与提交要求
- 只扫直接依赖，忽略传递依赖
- 把供应链安全等同于「装个扫描工具」

**解答：**
处置顺序是「评估 → 处置 → 长效」。评估要回答三件事：这个库在线上代码里的实际可达路径（哪个模块调用了它、处理的是否是不可信输入）、CVE 的利用前置条件是否满足（是否需要本地权限/特殊配置）、有没有缓解因素。评估完再选处置：能升级就升级，大版本升级注意兼容性，必须带回归与灰度；不能立即升级的给临时缓解（WAF 规则拦截特征、禁用相关功能开关）；高危且无法缓解的才考虑替换库（替换本身的迁移成本也要评估）。长效治理：1) SCA（依赖扫描）接入 CI，合并前拦截新增高危依赖，扫描直依赖 + 传递依赖；2) 锁文件（package-lock.json、yarn.lock、go.sum、pom 依赖树）必须提交，保证构建可复现、漏洞排查有据；3) 维护 SBOM（软件物料清单），应对监管审计与「出了事能快速定位受影响组件」；4) 供应链源头管控：私有仓库代理 + 依赖包校验和验证，重点防两类投毒——typosquatting（拼写相似的名字，如 lodash 被仿冒 lodahs）和依赖混淆（内部包与公共仓库同名，攻击者在公共源上传同名包，CI 解析到恶意版本），对策是内部包统一私有源前缀并锁定源。坑：只扫不修等于没扫；把漏洞扫描结果直接当「安全已治理」交付，缺少 triage 与修复闭环。

**延伸考点：** SBOM 能解决什么问题？如何防止 npm/pip 依赖混淆与投毒？

### Q14. 数据泄露防护（DLP）：客服账号被钓，数据被导出

**问题：** 客服后台可以导出用户手机号，一个员工账号被钓鱼后数据外泄。作为安全负责人，如何从权限、存储、审计、人防四个维度做防护？

**期望加分项：**
- 最小权限落地：查看与导出权限拆分、按需申请 + 审批流
- 脱敏分层：显示脱敏、导出脱敏、水印溯源
- 存储侧：敏感字段加密、密钥独立管理，测试环境脱敏
- 审计告警：导出全量审计、异常批量导出/非工作时间导出告警、MFA 二次确认
- 人防：钓鱼演练、安全意识培训与考核闭环

**减分项：**
- 只加登录验证码/二次登录
- 不区分「查看」与「导出」的权限边界
- 忽略审计与告警，出了事无从溯源
- 测试环境用生产真实数据

**解答：**
员工被钓鱼是「人防」失守，数据能成规模导出是「权限与审计」失守，所以四个维度都要动。1) 权限最小化：客服默认只能「查看」，「导出」是独立权限点走申请 + 审批 + 理由填写；按角色拆分权限（查询 / 导出 / 批量导出分开授予），定期权限复核（员工离职、转岗即回收）。2) 脱敏：列表页与详情页显示脱敏（138****8000）；导出文件脱敏 + 水印（嵌入导出人标识、时间戳），高敏字段（完整手机号、身份证）导出时二次确认。3) 存储：敏感字段库内加密（字段级加密），密钥独立管理并与数据库权限分离，防止「拖库直接拿明文」；手机号加密后无法直接 LIKE 检索的取舍——方案是建哈希索引列（SHA256(手机号)）支持精确匹配，或用 ES 分词检索，但要在数据字典里明确「哪些字段加密、哪些仅脱敏」。4) 审计告警：导出操作全量审计（谁、什么时间、哪些字段、导出量），异常行为触发告警——非工作时间导出、单次导出量超阈值、同一账号高频导出；导出敏感数据强制 MFA。5) 人防：钓鱼演练常态化（模拟钓鱼邮件统计点击率并公示），员工处置流程培训（收到可疑邮件不点链接、及时上报），安全意识与绩效/晋升挂钩形成闭环。坑：测试环境用生产数据是常见二次泄露点，测试库必须脱敏；「最小权限」不能只做一次，要纳入权限季度复核。

**延伸考点：** 数据脱敏与加密各自适用什么场景？字段级加密后如何支持手机号等字段的检索？

### Q15. 上了 HTTPS 还被抓包：TLS 配置与证书生命周期

**问题：** 老系统已启用 HTTPS，但仍被安全测试抓包还原了明文。请排查可能的原因（协议、证书、客户端校验），并给出 TLS 配置基线；证书的签发、续期、吊销怎么管理才不出事故？

**期望加分项：**
- 能点出「上 HTTPS ≠ 安全」：协议版本、弱套件、证书链不完整、客户端关闭校验都是常见漏洞
- 给出现成基线：TLS 1.2+、禁用弱套件、Mozilla ssl-config 级别配置
- 证书生命周期管理：Let's Encrypt 自动续期 + 续期监控告警（证书过期是最常见事故）
- 知道 HSTS 防降级、OCSP stapling 提升性能、客户端必须校验证书链与主机名
- 自签证书只用于受控内网/测试，走信任库注入而非关闭校验

**减分项：**
- 认为「上 HTTPS 就安全了」
- 不检查客户端代码是否 verify=False / 忽略证书校验
- 忽略证书过期、续期失败的线上事故
- 分不清 TLS 加密与「中间人防护」的关系

**解答：**
抓包能还原明文，八成不是协议问题而是「客户端没校验证书」或「证书链不完整」。排查顺序：先用 `openssl s_client`/浏览器看证书链是否完整、协议与套件版本；再查客户端代码——`verify=False`、关闭 SSL 校验、App 内置忽略证书的配置，只要有这种代码，TLS 形同虚设（中间人换自己的证书就能解密）。修复基线：1) 协议与套件——禁 TLS 1.0/1.1 与 RC4、3DES 等弱套件，启用 TLS 1.2+，直接用 Mozilla 中间配置生成工具（ssl-config）产出，别手工拼；2) 证书——用受信任 CA 签发，私钥权限收紧且不进仓库；Let's Encrypt 自动续期任务必须加监控告警（证书过期导致的线上事故排在最常见故障前列，续期失败要能第一时间感知）；证书链要配完整（漏中间证书会导致移动端/老客户端握手失败）；3) 客户端——所有 HTTP 客户端必须校验证书链与主机名（hostname verification），把「禁 verify=False」写进代码规范与 SAST 规则；4) HSTS 强制浏览器走 HTTPS 防降级；5) 性能——会话复用与 OCSP stapling 减少握手开销。关于自签证书：内网/测试环境要用「自建 CA + 把 CA 证书注入客户端信任库」的方式，而不是在客户端关校验——关校验的习惯一旦带到生产就是灾难。坑：证书监控不能只盯到期日，还要盯私钥泄露与域名更换后的重新签发。

**延伸考点：** 如何验证客户端确实校验了证书（而不只是配置了 https 地址）？mTLS（双向认证）用在什么场景？

### Q16. 对外 OpenAPI 被刷量与参数绕过：API 安全基线设计

**问题：** 对外 OpenAPI 上线后被刷量、被拖数据，还有开发者发现能绕过参数校验。请设计一套 API 安全基线：认证签名、限流、参数校验、审计各怎么做？

**期望加分项：**
- 认证签名：API Key 按调用方分配 + 请求签名（timestamp + nonce + HMAC），能说清防什么
- 限流分级：全局限流 + 调用方级限流，分布式实现（Redis 滑动窗口/令牌桶），阈值怎么定（压测/监控 + 余量）
- 参数校验：类型/长度/枚举白名单、统一校验框架、拒绝未知字段
- 数据面：分页上限、批量接口限量、敏感字段按需返回
- 网关统一治理 + 全量请求审计（脱敏后留存）

**减分项：**
- 只做 IP 限流（代理池可绕过）
- 签名方案说不清防什么、防不住什么
- 把鉴权和参数校验混为一谈
- 忽略幂等与防重放的关系

**解答：**
API 被刷与参数绕过，说明缺统一基线。分层设计：1) 认证与签名——每个调用方分配独立 API Key，请求带 timestamp + nonce + HMAC 签名（密钥协商或公私钥），服务端校验时间窗（如 5 分钟内）且 nonce 在窗口内去重，防重放；签名必须覆盖请求体与关键头，否则攻击者可篡改参数后重签——签名防的是「参数被改」，nonce/timestamp 防的是「请求被重放」，两者配合才完整。2) 鉴权——每个 Key 只授最小 scope，对象级越权复用内部鉴权基线。3) 限流——全局限流（防整体被打垮）+ 调用方级限流（防单 Key 刷量），分布式限流用 Redis 滑动窗口或令牌桶在网关层统一做；阈值怎么定：基于线上监控 P99 调用量或压测结果，留 2-3 倍余量，超阈值返回 429 + Retry-After。4) 参数校验——类型、长度、枚举白名单，统一校验框架（Java Bean Validation / JSON Schema），默认拒绝未知字段。5) 数据面——分页上限、批量接口限量、响应只含必要字段（敏感字段默认不下发）。6) 审计——全量请求日志（脱敏）留存，供追责与风控建模。坑：限流只看 IP 会被代理池/肉鸡绕过，必须结合账号与 Key 维度；HTTP 明文传输时签名无意义，必须配合 HTTPS。

**延伸考点：** 签名机制中 timestamp 与 nonce 各防什么？接口幂等与防重放的区别与联系？

### Q17. 建立安全测试体系：SAST / DAST / 渗透 / 威胁建模的分工

**问题：** 团队要建立安全测试体系，预算有限。SAST、DAST、SCA、渗透测试、威胁建模各自解决什么问题？用最小成本怎么搭起来，怎么避免「买了工具没人用」？

**期望加分项：**
- 分层模型清晰：威胁建模（设计期）→ SAST（开发期）→ SCA（依赖）→ DAST（测试期）→ 渗透（上线前）→ 众测/红蓝（上线后）
- 知道各工具短板：SAST 误报高、DAST 覆盖有限、SAST 抓不到业务逻辑漏洞
- 落地节奏：先 SCA + SAST 接 CI（成本低见效快），再 DAST 定时跑，渗透按版本节奏做
- 治理误报：扫描结果走 triage 流程、误报率指标、规则与白名单沉淀，否则门禁会被绕过
- 威胁建模轻量化：只对高风险模块（登录、支付、数据导出）做 STRIDE/问答式评审

**减分项：**
- 以为买几个工具就等于建了体系
- 说不清各阶段工具的分工与短板
- 不处理误报，导致门禁形同虚设
- 把渗透测试当唯一手段

**解答：**
安全测试按「发现越早成本越低」分层，先想清楚每层解决什么：威胁建模在设计期回答「谁可能碰这个数据、失败路径是什么」，用 STRIDE 或轻量问答式评审，只针对高风险模块（登录、支付、数据导出）做，不要全量；SAST 在开发期扫代码（注入、硬编码密钥等），能集成到 IDE/CI，但误报高、对业务逻辑漏洞（越权）无能为力；SCA 扫依赖 CVE，见效最快；DAST 在测试期对运行中的应用发请求，抓配置与越权问题，覆盖依赖运行时上下文但受限于爬虫能力；渗透测试上线前做，人工为主，能发现逻辑漏洞与组合攻击；上线后众测/红蓝补充。最小成本落地顺序：先 SCA + SAST 接入 CI（工具成本最低、自动化程度最高），DAST 定时跑（周级），渗透测试按发布节奏外包或自建，威胁建模只在重大需求评审时做。体系能否活下来，关键在误报治理：扫描结果必须进 triage 流程（按天/周处理，沉淀误报白名单与规则优化），并统计漏报率/误报率指标，否则开发团队 3 个月后就绕过门禁。坑：买了工具没有「修复责任到人」的闭环，扫描结果躺在平台里就是白买。

**延伸考点：** SAST 误报率过高导致团队不信任，怎么治理？威胁建模如何轻量化融入快速迭代？

### Q18. 凌晨告警：疑似撞库与拖库，前 30 分钟怎么处置

**问题：** 凌晨收到告警：某账号出现大量异常登录、某数据接口请求量突增，疑似被撞库或拖库。作为安全负责人，前 30 分钟做什么？之后怎么取证、定级、复盘？

**期望加分项：**
- 处置顺序：先确认告警真实性 → 止血（封 IP、锁账号、冻结凭证、限流/下线接口）→ 并行取证
- 决策权与升级路径事先约定（值班主管、通知管理层/合规），不等「层层汇报」
- 取证：登录日志（IP/UA/设备指纹/行为序列）、请求日志、影响面评估，先落盘到隔离存储防日志被刷掉
- 定性：撞库（用泄露库试密码）vs 定向攻击，看密码正确率与目标账号集中度
- 复盘三项：检测规则完善、风控特征沉淀、演练与报告；按合规要求决定是否通报

**减分项：**
- 直接拔网线/重启机器，证据全丢
- 只封当前 IP 不做账号与凭证层面的处置
- 告警无分级，被噪音淹没后误判
- 事后不复盘不沉淀规则

**解答：**
前 30 分钟只做确定性动作，按「止血 → 取证 → 定性」并行推进。第一步确认告警真实性：看样本日志而非聚合数，确认存在真实异常（同一 IP 批量尝试、账号被异地登录、接口请求量超基线 N 倍）。第二步止血：批量失败的登录来源 IP 立即封禁、疑似失陷账号锁定并冻结凭证、必要时对受影响接口限流/下线、撤销相关 API Key——注意「先动账号层再动网络层」，别一上来断网。同时通知值班负责人（升级路径提前约定好，避免等批准耽误黄金时间）。第三步取证与止血并行：登录日志（IP、UA、设备指纹、行为序列）、请求日志、被访问的数据范围先复制到隔离存储，防止告警风暴刷掉日志；记时间线：首次异常时间、攻击手法、影响面（哪些用户/数据被碰过）。随后定性：撞库攻击的特征是「正确密码率低（用外部泄露库批量试）」，定向攻击是「目标账号集中、手法单一」；看数据接口突增是否有真实数据被拉走，决定影响等级。影响评估后按合规要求（等保 / 个保法 / 数据安全法）评估是否通报监管与用户。复盘三项必做：异常登录检测基线完善（异地 + 频率 + 时间窗组合）、撞库特征进风控规则、事件复盘报告 + 桌面演练。坑：告警不分级会造成「狼来了」；取证只截屏不落原始日志，复盘时无据可依。

**延伸考点：** 如何从日志区分「撞库成功」与「撞库失败」的特征？日志留存时长与合规要求怎么定？

### Q19. 出海 + 等保：GDPR、等保 2.0、数据安全法的技术落地

**问题：** 业务要出海欧洲，同时国内做等保测评。GDPR、等保 2.0、数据安全法/个保法分别要求什么？技术侧要动哪些，怎么排优先级？

**期望加分项：**
- 能分清三者的定位：GDPR 管欧洲用户个人数据、等保 2.0 是我国安全能力评级、个保法/数据安全法管国内个人信息与重要数据
- 技术落地：数据地图（数据在哪、谁处理、流向哪）是共同地基
- GDPR 落地：数据主体权利（访问/删除/更正/可携带）、删除要级联（含日志备份）、加密假名化、跨境合规（SCC/充分性认定）
- 等保 2.0 落地：定级备案测评整改，三级常见要求（身份鉴别、访问控制、审计、入侵防范、数据完整保密）
- 按「数据量 × 风险等级」排优先级，不搞一刀切

**减分项：**
- 把 GDPR、等保、个保法混为一谈
- 只谈合规文件与制度，不谈技术措施落地
- 忽略数据跨境合规
- 不知道个人信息与敏感个人信息的区别

**解答：**
先分清对象：GDPR 管「处理欧洲用户个人数据」的行为（包括行为发生在中国但处理欧盟数据）；等保 2.0 是我国对网络运营者安全能力的评级体系（定级、备案、测评、整改，三级最常见），要求落在技术与管理措施上——身份鉴别（双因素）、访问控制（最小权限）、安全审计、入侵防范、数据完整性与保密性；个保法/数据安全法管国内个人信息处理与重要数据。技术侧共同的地基是「数据地图」：盘点数据存在哪（数据库、日志、第三方）、谁处理、流向哪（含跨境），没有地图一切合规都是空谈。GDPR 技术要点：1) 数据主体权利——用户可访问/导出/删除自己的数据，删除要级联（订单、日志、备份副本都要删），涉及「被遗忘权」；2) 传输与存储——TLS、静态加密、个人敏感字段加密或假名化；3) 跨境——欧盟数据出境依据「充分性认定 / SCC 标准合同条款 / BCR」，国内重要数据出境走安全评估。等保落地要点：定级备案后按等级差距做整改，网络安全等级测评会逐项核查（身份鉴别、访问控制、审计、入侵防范、数据保密），安全区域划分与日志留存（≥6 个月）是硬指标。优先级：按「受影响数据量 × 风险等级」排序——先做数据地图与加密传输（成本低覆盖面大），再补删除/导出等用户权利接口，跨境合规尽早评估因为周期长。坑：只做文档不落技术措施，测评或监管检查时全部暴露。

**延伸考点：** 个人信息与敏感个人信息的区别（对技术方案的差异）？GDPR「被遗忘权」在业务上如何实现级联删除？

### Q20. 上云 + 远程办公 + 反薅羊毛：零信任与云安全整体设计（开放题）

**问题：** 公司上云、全员远程办公，同时业务面临薅羊毛/刷单。领导要求「零信任改造」。请给出整体安全架构设计：身份、网络、云资源、业务风控各怎么做，落地优先级怎么排？

**期望加分项：**
- 零信任原则落地：永不信任内网、持续验证；统一身份源 + MFA 强制 + 条件访问（设备合规）
- 网络：SDP/零信任接入替代 VPN、VPC 微隔离、应用不暴露公网
- 云安全：IAM 最小权限、对象存储（OSS/S3）权限审计（公开读写是最大泄露源）、IaC 配置扫描（CIS 基线）
- 业务风控：设备指纹 + 行为验证 + 多级频控 + 风控规则引擎，拦截率与误伤率要灰度权衡
- 分阶段落地与 ROI：先身份与云基线，再微隔离与风控
- 纵深防御 + 红蓝演练验证防线有效性

**减分项：**
- 把「零信任」当某个产品购买，只谈概念无落地路径
- 只讲网络层，忽略身份与数据
- 忽略对象存储权限这类高频泄露点
- 风控一刀切，不考虑误伤真实用户

**解答：**
三个诉求（上云、远程办公、反薅羊毛）本质是同一件事：信任边界消失，安全重心从「网络边界」转向「身份、数据与行为」。设计原则：永不信任、持续验证、最小权限、纵深防御。分层落地：1) 身份与访问（最高优先级）——统一身份源（IdP）+ MFA 强制（远程办公必上）、条件访问策略（设备合规、地理位置才放行）、特权账号管理（PAM，管理员账号另走一条审计链路）；2) 网络——零信任接入（SDP：先认证后连接，业务应用不暴露公网）替代传统 VPN，VPC 内按工作负载做微隔离（东西向流量最小策略）；3) 云安全——IAM 最小权限（服务角色、人账号分离，禁止长期密钥）、对象存储权限专项审计（OSS/S3 公开读写是最常见的数据泄露源）、用 IaC（Terraform）+ 云安全配置扫描（Checkov / CIS 基线）在代码层拦「配置漂移」；4) 业务风控——防刷单组合拳：设备指纹（识别设备级黑产）+ 行为验证（滑块/无感验证，区分人与脚本）+ 多级频控（账号/设备/IP/支付维度，超过阈值进风控队列）+ 风控规则引擎（规则 + 模型双轨，灰度放量，拦截率与误伤率按月复盘平衡），关键动作（领券、支付）走「风控决策」而非一刀切拒绝；5) 纵深防御与验证——分层设防 + 持续监控（SOAR 编排告警）+ 红蓝演练验证防线（打不穿的防线才算数）。落地节奏：先 IAM + MFA 与云安全基线（ROI 最高、改动小），再上零信任接入与微隔离，业务风控与数据安全并行推进。坑：零信任是架构演进不是买盒子，身份没统一之前上任何网络产品都是白搭。
