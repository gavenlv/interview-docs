# 通用 · 系统设计（面试题库）

本文件面向后端开发、架构师与资深工程师的系统设计面试。考察重点：面对模糊需求能否主动澄清边界并用数据说话完成容量估算，能否在一致性、可用性、成本之间做出有依据的取舍，是否有真实线上架构实践（踩坑、复盘、对账兜底）而非背诵标准答案。题目从实践基础到中高阶架构逐级递进，每题标注期望加分项与减分项，供面试官现场打分参考。本文件不考八股文，所有题目均以真实工程场景为背景，要求候选人给出判断依据与取舍逻辑。

### Q1. 面对模糊需求，怎么把系统设计的第一公里走对

**问题：** 面试官只丢给你一句话：「我们要做一个类似短链接的服务」，除此之外没有任何信息。你会如何开始这场设计？请把你问的问题、以及为什么要问这些问题讲清楚。

**期望加分项：**
- 能主动澄清 QPS、数据总量、读写比、一致性要求，而不是上来就画架构图
- 能把模糊业务量级转化为量化假设（峰值 QPS、单日新增量），并说明假设失效时方案如何调整
- 能区分核心路径与非核心路径，先定边界再谈技术选型
- 能识别需求中隐含的风险（防滥用、短链失效/过期策略）
- 能说明每个问题影响了后续哪些决策（存储选型、缓存、分片）

**减分项：**
- 需求没听完就直接画图、直接拍技术栈
- 只会问「高并发高可用」这类空洞问题，不会追问具体数字
- 拿不出任何量化假设，只会说「看情况」
- 忽略产品层面的约束（链接有效期、是否支持自定义短链、是否要统计）

**解答：**
思路：设计前先明确四个维度——量（QPS、总量）、性（读写比、延迟要求）、一致性要求、成本与运维约束；目的是把「一句话需求」翻译成可验证的假设，再决定后续每一步。关键方法：先问日活与请求量级，得到「日增 1000 万条、总量 10 亿、读 QPS 10 万、写 QPS 1000、读多写少」这类假设；再追问短链有效期（永久或 30 天）——这直接决定要不要 TTL、要不要过期清理与重建；接着问是否支持自定义短链、是否需要点击统计，这两点会分别引入「可用性冲突」与「旁路计数」设计。有了假设，容量估算、存储选型才有输入，而不是凭空选型。实践中的坑：最常见的是面试者跳过需求澄清直接给方案，导致后续所有假设悬空；其次是「敢不敢承认假设」——把预估说成一定，或者被追问「如果量级差 10 倍呢」时答不出来。好的回答会说清「基于 XX 假设，如果量级再大 10 倍，方案会变成 XX」，这比背一个标准架构更能体现真实设计能力。

**延伸考点：** 如果对方说日活只有 100 人，你还会用同一套方案吗？技术选型在什么量级下应该被推翻？

### Q2. 用数据说话：一张表算出你要多少台机器

**问题：** 给定输入：「1000 万 DAU、人均 20 次请求/天、单次请求返回 50KB 数据」。请现场推导峰值 QPS、所需带宽、存储与机器数，把每一步的假设和公式说清楚。

**期望加分项：**
- 能给出清晰推导链：DAU → 日均请求 → 峰值 QPS（乘峰值系数 3-10 倍）→ 单机吞吐 → 机器数
- 能区分读请求与写请求分别估算
- 能主动考虑带宽瓶颈（50KB × QPS）与内外网带宽差异
- 能用「量级」表达结论（万级 QPS 是分水岭），而不是精确到个位数
- 能说明估算结果如何影响选型（Redis 内存、MySQL 连接数、CDN 分流）

**减分项：**
- 公式对但数字拍脑袋，说不出假设来源
- 只算 QPS 不算存储与带宽
- 把估算当精确值，不会用量级表达
- 忽略缓存命中后实际打到数据库的 QPS

**解答：**
思路：容量估算的本质是把「业务假设」转成「资源需求」，目标是量级而非精确值。关键方法：峰值 QPS ≈ DAU × 人均请求 × 峰值系数 ÷ 86400，峰值系数按业务取 3-10——本例 1000 万 × 20 × 4 ÷ 86400 ≈ 9000+ QPS 量级；若缓存命中率 90%，实际打到 DB 的只有约 900 QPS（这是最容易漏算的一步）；带宽 = 峰值 QPS × 单次响应大小 ≈ 9000 × 50KB ≈ 450MB/s，外网出口已到千兆网卡上限，必须 CDN 分流或压缩；存储按单条记录大小 × 总量 × 冗余系数估算，如 1 亿条 × 1KB × 3 副本 ≈ 300GB，可判断单机 Redis 是否放得下；机器数用「峰值 QPS ÷ 单机压测吞吐」推导，如单机 2000 QPS 需要 5 台起步（另加冗余）。实践中的坑：一是只估 QPS 忽略带宽与存储，二是把 DAU 直接当并发数，三是忘了写放大（ES 索引、二级索引都会放大写入成本）。面试官要的不是精确值，而是「量级判断 + 假设可追溯」的能力。

**延伸考点：** 如果缓存全部失效（雪崩），按你算出的数据库规模能扛住吗？流量再翻 10 倍，你的扩容顺序是什么？

### Q3. 设计短链接服务：从需求澄清到落地

**问题：** 设计一个短链接服务：10 万 QPS 写入、亿级总量、短链可永久有效。请从需求澄清、容量估算、存储选型、发号策略到重定向链路完整走一遍。

**期望加分项：**
- 能澄清关键点：总量、写入 QPS、有效期、是否支持自定义短链、是否防滥用
- 能算出存储量级并据此选型（亿级数据 MySQL 需分表，或直接选 KV 存储）
- 发号策略能讲清取舍：DB 自增 + 进制转换、号段预取、雪花算法，以及各自的性能与可用性代价
- 重定向链路能说出 301/302 的选择与缓存层级（本地缓存 → Redis → DB）
- 能讨论短链冲突、过期策略与点击统计对架构的影响

**减分项：**
- 只会背「62 进制编码」，讲不出发号与存储的关系
- 不考虑 10 万 QPS 写入对单机 DB 的压力
- 忽略防滥用校验（开放短链服务会被刷爆，甚至被利用做跳板）
- 说不清 301 与 302 对统计的影响

**解答：**
思路：先定边界——10 万 QPS 是极高写入，意味着发号必须批量预取，不能每次打 DB；读链路则靠多层缓存扛。关键方法：存储选 KV（如 Redis + 落库 Cassandra/TiDB）或 MySQL 分 128 张表，主键为短码；发号用「发号机预取号段 + 本地自增 + 62 进制编码」，每台发号机一次取 1000 万号段，10 万 QPS 写入在内存内消化，号段用尽再申请；重定向链路：本地缓存（Caffeine）→ Redis → DB 三层，热点短链直接命中本地缓存可支撑百万级 QPS；重定向用 302 以记录点击统计，用 301 会被浏览器缓存导致统计失真。实践中的坑：一是 10 万 QPS 写入时 DB 自增必然成为瓶颈，必须号段化；二是「永久有效」意味着存储只增不减，要有容量告警与数据归档；三是未校验输入 URL 导致 SSRF 与恶意跳转。点击统计是隐藏需求，应走旁路异步计数（写 MQ 后聚合），不能同步写在重定向链路上。

**延伸考点：** 如果短链有效期改为 30 天而非永久，架构会怎么变？点击统计需要按小时维度聚合报表，你会把计数放在哪个环节、怎么保证不丢？

### Q4. 秒杀：「超卖」与「详情页被打爆」分别怎么设计

**问题：** 一场秒杀：10 万件商品、开抢瞬间百万级请求涌入。「库存扣减超卖」和「商品详情页被热点打爆」是两个经典问题，请分别给出设计，并说明二者在架构上如何隔离。

**期望加分项：**
- 超卖方案能讲清「Redis 预扣减 + DB 原子扣减兜底」的取舍，能解释为什么 DB 侧 `UPDATE stock=stock-1 WHERE id=? AND stock>0` 有效
- 详情页能讲清静态化 + CDN、Redis 缓存热点、入口限流的组合
- 能把读链路（详情页）与写链路（下单扣库存）在架构上拆开，互不拖垮
- 能主动提到防刷、黄牛、以及「只抢不买」导致库存虚占
- 能给出「放量」思路：在入口挡掉大部分流量，只放小部分进入下单

**减分项：**
- 只知道「Redis 预减库存」一个答案，讲不清扣多了/扣少了怎么兜底
- 把读和写耦合在一起设计
- 忽略恶意流量与秒杀器
- 答不出超卖的判定边界（扣减的原子性边界在哪一层）

**解答：**
思路：把秒杀拆成两个独立链路——读（详情页）与写（下单），并明确「Redis 是挡流量的，DB 才是对账依据」。关键方法——读链路：详情页静态化进 CDN，动态库存数由 Redis 缓存按秒级刷新，Redis 前再挂本地缓存 + 限流，入口先按用户维度限频挡掉大部分流量。写链路：下单请求过网关限流后，先到 Redis 用 Lua 脚本原子扣减（DECR 并判断结果大于 0，防超卖），扣减成功才投递 MQ 异步落库；DB 侧用 `UPDATE stock=stock-1 WHERE id=? AND stock>0` 做最终原子保证，两条链路各自的扣减数用对账任务核对。实践中的坑：只做 Redis 预减不做 DB 兜底，Redis 宕机或重启库存全乱；只做 DB 原子扣减，百万并发全打 DB 直接打爆；漏掉「N 分钟未支付回滚库存」的补偿；固定窗口限流挡不住多 IP 秒杀器，要叠加账号维度风控。面试加分点：主动讲「只抢不买」的库存虚占如何用预占 + 超时释放解决，以及为什么对账（Redis 扣减数 vs DB 订单数）是最后一道安全网。

**延伸考点：** 库存扣减成功但下单失败（支付超时），库存怎么回补？同一用户重复下单导致一单多扣，怎么拦截？

### Q5. 缓存三兄弟：穿透、击穿、雪崩一次讲透

**问题：** 线上出现缓存穿透、缓存击穿、缓存雪崩，请说明三者各自的成因、现象与应对手段，并解释为什么很多团队用同一个方案硬扛三种问题。

**期望加分项：**
- 能准确区分三者：穿透=查不存在的数据；击穿=单个热点 key 过期瞬间；雪崩=大量 key 同时过期或缓存整体宕机
- 穿透能给出参数校验、缓存空值、布隆过滤器的组合，并说明布隆误判率与不可删的代价
- 击穿能给出互斥锁重建或「逻辑过期 + 异步刷新」，能说出各自取舍
- 雪崩能给出过期时间加随机抖动、多级缓存、DB 侧限流兜底
- 能联系线上事故：大促缓存失效后 DB 被打挂的止损过程

**减分项：**
- 三种问题混为一谈，答不出区别
- 只会背「布隆过滤器」，不会评估误判与重建成本
- 不区分缓存层故障与数据过期故障
- 只给方案不给验证手段（如何证明方案有效）

**解答：**
思路：三者的共同点是「流量打到 DB」，但成因不同，应对必须不同——先定性再给方案。关键方法：穿透（key 根本不存在）：入口校验非法参数 + 缓存空值（TTL 设短）+ 布隆过滤器拦截，注意布隆有误判且删除困难，需要重建；击穿（热点 key 过期瞬间）：同一 key 高并发重建，用互斥锁只放一个线程回源，或「逻辑过期 + 永不过期 + 后台异步刷新」，后者无锁但读可能拿到稍旧数据；雪崩（批量过期或缓存宕机）：过期时间加随机抖动分散，缓存分级（本地缓存兜底），DB 侧限流 + 连接池保护。实践中的坑：团队常把三者统一处理成「加 Redis 集群」，但雪崩的根因是「DB 保护缺失」，加再多缓存节点也挡不住重建风暴；空值缓存要防「故意构造不存在 key 刷爆内存」；互斥锁要防死锁与超时释放导致锁失效；布隆过滤器在数据频繁删除更新的场景会持续误判。最高分回答是结合一次真实事故讲「怎么发现、怎么止血、怎么根治」。

**延伸考点：** 如果 DB 本身也扛不住（Redis 与 DB 同时抖动），你最后一道防线是什么？布隆过滤器在你这个业务里，误判的代价具体是什么？

### Q6. 缓存与数据库的一致性：更新顺序到底怎么定

**问题：** 你的服务缓存了商品价格，运营改价后「先更新 DB 还是先删缓存」？请讲清 Cache Aside 的删除策略、为什么「先删缓存再更新 DB」会有窗口期，以及延迟双删、订阅 binlog 等补偿手段的取舍。

**期望加分项：**
- 能讲清 Cache Aside 标准姿势：读 miss 回源；写先更新 DB、成功后删缓存
- 能指出「先删缓存再写 DB」的并发窗口：删除与写入之间，读请求会把旧值写回缓存
- 能给出补偿手段：延迟双删、binlog 订阅（Canal）异步删除、版本号比对
- 能区分「强一致」与「最终一致」该在什么场景选哪个，承认绝大多数业务只需最终一致
- 能联系实践：改价这种低频写 vs 高并发读场景，一致性代价的量化

**减分项：**
- 只会背「先更新 DB 再删缓存」，讲不出为什么
- 把「删缓存」说成「更新缓存」，忽略并发写-写竞争
- 不会评估一致性窗口的大小与业务影响
- 不提缓存删除失败的兜底（重试/MQ）

**解答：**
思路：先定业务要求——价格、库存这类业务「最终一致」即可，不必追求强一致，方案复杂度要跟业务要求匹配。关键方法：Cache Aside——读 miss 回源写缓存；写侧「先更新 DB，成功后删缓存」。为什么不先删缓存？因为先删后写在「删→写」窗口内，并发读会把旧值写回缓存，产生长期脏数据。删除失败的兜底：删除加入重试队列，或订阅 MySQL binlog（Canal）异步删除，保证「DB 一变，缓存必删」。更进一步：延迟双删（删 → 写 DB → 延迟 500ms 再删一次）可把窗口压缩到延迟时间以内，但增加复杂度；版本号/序号方案（缓存带 version，读时比对）更严谨但成本高，一般业务用不上。实践中的坑：把「更新缓存」当「删除缓存」，高并发下写-写竞争直接脏缓存；删除失败无补偿，脏数据一直存活到 TTL 到期；过度设计——为 99% 只需最终一致的业务上了分布式事务。面试要体现「我知道窗口在哪、业务能承受多久、用什么兜底」，而不是背结论。

**延伸考点：** 如果这个缓存是秒杀库存这类热点数据、一致性要求突然变高，你的方案怎么升级？binlog 订阅有延迟，窗口期内读到旧值，业务上怎么处理？

### Q7. 分布式锁：为什么「Redis SETNX + 过期时间」远远不够

**问题：** 团队用 Redis SETNX 实现了分布式锁，线上出现「锁提前过期导致并发执行」「主从切换后锁丢失」两类事故。请分析根因并给出你的方案，说明 Redis 锁与 ZooKeeper/etcd 锁的取舍。

**期望加分项：**
- 能指出 SETNX 与 expire 分两步的原子性问题，应使用 `SET key uuid NX PX 30000`
- 能给出 owner 标识（value 放唯一 ID）与「释放前校验归属 + Lua 原子释放」，防误删别人的锁
- 能给出看门狗续期（如 Redisson watchdog）解决执行超时问题
- 能讲清主从异步复制导致锁丢失，以及 Redlock 的提出与争议（GC 停顿、时钟漂移）
- 能讨论锁粒度：业务上是否真需要全局锁，能否用分段锁、乐观锁、幂等替代

**减分项：**
- 只会背「SETNX 加锁、DEL 解锁」，不知道释放时要校验 owner
- 说不清锁过期与业务执行时间的关系
- 把 Redlock 当银弹，讲不出它的争议与适用边界
- 不考虑锁的可重入、等待机制与超时行为

**解答：**
思路：分布式锁的正确性边界 =「锁的过期时间 > 业务执行时间 + 容差」，任何方案都在与这个不等式搏斗——业务执行不可控，过期时间必须可续期。关键方法：加锁用 `SET key uuid NX PX 30000`（原子设置 + 过期）；解锁用 Lua：GET 比对 uuid 一致才 DEL，防止误删别人的锁；执行超时用看门狗自动续期（Redisson watchdog 默认每 10 秒续期 30 秒）。主从切换锁丢失：Redis 异步复制下主节点挂了、锁未同步到从节点，Redlock 尝试多节点加锁，但存在争议——GC 停顿、时钟漂移都可能破坏互斥性，工程上更务实：锁内操作必须幂等 + 对账兜底，把「锁失效」当成可恢复故障而非绝对保证。实践中的坑：锁粒度过大（全局一把锁）导致性能雪崩，应先评估能否用分段锁、DB 乐观锁甚至业务幂等替代；锁内做远程调用/重 IO 会让持锁时间不可控；ZooKeeper/etcd 锁基于临时顺序节点 + 会话保活，不依赖过期时间，适合低频高可靠场景，但性能与运维成本更高。

**延伸考点：** 锁里执行了 60 秒的任务但锁只设了 30 秒，看门狗刚好断了怎么办？如果业务能接受偶尔并发，分布式锁是不是根本不该用？

### Q8. 支付回调重复、下单重试：幂等怎么设计才不脏数据

**问题：** 支付系统回调可能重复投递、客户端可能超时重试、MQ 消费可能重复。请设计一个「下单 + 支付回调」场景的幂等方案，讲清幂等键怎么选、状态机怎么防乱序。

**期望加分项：**
- 能区分幂等的三层：接口层（唯一请求号）、业务层（订单号 + 状态机）、存储层（唯一索引兜底）
- 幂等键能结合业务选：支付回调用「支付流水号」而非订单号（一单多付场景）
- 能讲清「先查后写」的竞态，用唯一索引/分布式锁兜底
- 能讲清状态机驱动：只有「待支付 → 已支付」合法，重复回调直接返回成功不重复入账
- 能给出对账兜底：T+1 对账发现重复/漏单

**减分项：**
- 只会说「用 Redis SETNX 做幂等」，讲不清幂等键的来源与有效期
- 忽略「重复回调但状态已变化」的乱序问题（退款回调先到、支付回调后到）
- 把幂等与防重混为一谈
- 不给兜底方案，相信「消息不会重复」

**解答：**
思路：幂等的本质是「让同一操作的重复执行等价于一次」，设计顺序：选对幂等键 → 状态机约束 → 存储兜底。关键方法——幂等键：回调场景用「外部流水号（第三方支付单号）+ 内部订单号」双查，注意一单多付/合并支付要用支付流水号；消费场景用「业务主键 + 事件类型」建唯一索引。写入依赖「唯一索引 insert 失败即重复」的原子性，比先查后写可靠（先查后写存在竞态窗口）。状态机：订单状态流转限定在合法边（待支付 → 已支付 → 部分退款 → 已退款），任何重复回调先查状态，已支付直接返回成功幂等响应；乱序回调（支付回调晚于退款回调到达）用「时间戳/版本号」拒绝旧事件。实践中的坑：幂等键选错（用时间戳）导致每次都当新请求；幂等只在接口层做、存储层没唯一索引兜底，并发下照样脏数据；重试队列无上限，回调用例把下游打挂。最后 T+1 对账是兜底安全网——纯靠逻辑幂等总有漏洞，对账才能发现和修复。

**延伸考点：** 幂等键的过期时间怎么定？多久之前的重复请求可以直接丢弃？订单系统与支付系统数据不一致（支付成功但订单未更新），怎么发现和修复？

### Q9. 用 MQ 削峰：订单「先收单后处理」的完整链路

**问题：** 订单系统瞬时写入量是常态的 50 倍，你决定引入消息队列削峰。请设计：哪些环节进队列、队列怎么选、消息怎么保证不丢不重不乱序，以及「队列消费不过来」时怎么办。

**期望加分项：**
- 能画清链路：入口限流 → 收单接口只写订单表 → 投递 MQ → 异步完成校验/库存/积分等下游
- 能区分「必须同步」（用户要立刻看到结果）与「可异步」（延迟几秒无感）的业务
- 能讲清 at-least-once 与幂等消费的关系，乱序问题（同一订单多条消息）用分区键 + 序号解决
- 能给出消费压测与积压告警，消费端按 partition 数横向扩容
- 能说明队列选型取舍：RocketMQ/Kafka 事务消息 vs 本地消息表的差异

**减分项：**
- 把 MQ 当万能药，说不清为什么要削峰、削哪个峰
- 只讲投递不讲消费端保护（消费速度跟不上还是会被打爆）
- 忽略「消息必达」：DB 提交成功但 MQ 发送失败的分布式问题
- 不会设计重试与死信队列

**解答：**
思路：削峰的目标是把「瞬时峰值」摊平为「持续可控的消费速率」，前提是想清楚哪些步骤能异步。关键方法：收单接口只做两件事——校验参数、写订单表（状态=待处理），然后投递 MQ；库存扣减、风控、积分、通知全部异步消费。可靠性：生产侧用「本地消息表 + 定时补偿投递」或 RocketMQ 事务消息，解决 DB 提交成功但消息丢失的问题；消费侧 at-least-once + 幂等消费（见幂等题），消费失败重试、重试耗尽进死信队列人工处理。乱序：同一订单消息用同一 partition（订单号哈希）保证有序，下游状态机再兜一层。消费能力：partition 数与消费并发成正比，容量按「可容忍的积压时间 × 单条消费耗时」评估，并设置积压量告警。实践中的坑：只削峰不护底——消费端仍直连 DB，积压恢复期照样打爆数据库，应先做批量写/并行度控制；无积压监控，出问题几小时后才发现；死信无人处理，消息静默丢失。面试加分点：说清「哪些必须同步、哪些能异步」的判断标准。

**延伸考点：** 消费积压 1 亿条，你怎么快速恢复？消息延迟从秒级涨到分钟级，怎么定位是生产慢还是消费慢？

### Q10. 分库分表：什么时候分、怎么分、主键怎么来

**问题：** 订单表单表数据到 2 亿，写入与查询都开始变慢。请给出你的判断：先做什么、什么时候才需要分库分表、按什么分（分片键怎么选）、分布式主键用什么方案。

**期望加分项：**
- 能先排除非分片手段：索引优化、冷热归档、读写分离、缓存，说明为什么先做这些
- 能给出量化判断依据：单表行数（如千万级）、写入吞吐（超过单库 TPS 上限）、慢查询占比
- 分片键能结合核心查询选：订单按买家 id 分，卖家维度查询怎么办（索引表/宽表/异构存储）
- 主键能讲清雪花算法/号段方案，以及趋势递增对索引与分页的意义
- 能说清「分库分表是最后手段，且要一次分够」——容量预留

**减分项：**
- 一上来就分库分表，跳过索引、归档、读写分离等低成本方案
- 分片键选错，导致核心查询全部跨片
- 主键用自增 ID 而不考虑跨库唯一与时间有序
- 不考虑迁移成本与双写方案

**解答：**
思路：分库分表是「高成本、不可逆」的重构，必须先用低成本手段榨干单库潜力。关键方法——前置手段：慢查询优化（索引、覆盖索引）、冷热分离（6 个月前订单归档）、读写分离（读多写少场景）、必要时缓存。量化触发条件（参考值）：单表行数到千万级且插入/查询明显退化，或单库写入 TPS 持续超阈值，或慢查询占比上升——出现其一才考虑分片。分片：分片键必须对齐「最高频查询」——订单按 buyer_id 分片，卖家查询必然跨片，方案是维护「卖家订单索引表」或离线同步到 ES/数仓，要能解释分片键不能轻易改（迁移成本极高）。主键：雪花算法（机器位 + 时间位）或「号段 + 本地缓存」，保证全局唯一、趋势递增（利于索引与分页）；不要用 UUID 字符串（索引膨胀、随机 IO）。实践中的坑：只分表不分库，单库连接数与 IO 仍是瓶颈；分 16 片发现 3 年后不够，再扩容要做数据迁移 + 双写，成本极高——所以「预留容量，一次分够」；分片后事务范围收窄，跨分片事务要另想办法（见分布式事务题）。

**延伸考点：** 分片后「按时间范围查订单」必然跨片，你怎么设计查询入口？如何做不停机的在线扩容？

### Q11. 设计 feed 流：1000 万用户的时间线

**问题：** 设计类微博/朋友圈产品：1000 万 DAU、关注关系亿级、每人每天刷 50 次时间线。请对比推模式、拉模式、推拉结合的取舍，并说明热点用户、缓存与存储的设计。

**期望加分项：**
- 能讲清三种模式：拉模式（读时聚合，存简单读贵）、推模式（写时扩散，读快写放大）、推拉结合（普通用户推、大 V 拉）
- 能量化写放大：百万粉丝博主一条动态推 100 万份的代价，从而得出大 V 走拉的必然性
- feed 缓存设计：Redis 存时间线 ID 列表（每用户截断到数百条），正文再批量回源
- 能讨论一致性：粉丝取 feed 的延迟容忍、删除/拉黑对 timeline 的影响
- 分页用游标（cursor）而非 offset，避免深分页与合并排序失效

**减分项：**
- 只会背「推拉结合」，说不清什么用户该推、什么用户该拉
- 忽略写放大量化，把推模式用到所有用户
- 时间线分页用 offset
- 不考虑内容被删除/可见性（拉黑）的过滤成本

**解答：**
思路：feed 流的核心矛盾是「读写放大」——推模式把一次写放大为 N 份推送，拉模式把一次读放大为 M 次拉取，量级决定策略。关键方法——推拉结合：普通用户（粉丝数低于阈值，如 1 万）发动态走推，写放大可接受；大 V（粉丝百万）走拉，粉丝读时把「关注列表中大 V 的动态」与「普通用户推送的 timeline」合并排序。量化：百万粉丝大 V 一条动态 = 100 万次缓存写，必须避免，所以大 V 必然走拉。存储：动态正文存 MySQL/对象存储，粉丝 timeline 存 Redis List（ID 列表，每人截断到 500 条防无界增长）。合并拉取：取推送 timeline + 各关注大 V 最新 N 条，归并排序取 top 100；分页用游标（上一页最后一条的时间戳/ID）而非 offset。实践中的坑：删动态/改可见性要在已推送的副本里剔除（渲染时二次校验动态状态）；offset 分页在合并排序下失效；新用户冷启动要预生成 timeline。面试亮点：主动给出「推拉阈值」的估算逻辑与动态调整策略（粉丝数会变，阈值要可配置）。

**延伸考点：** 一个 5000 万粉丝的超级大 V 发动态，你的合并拉取在峰值时每秒被调用多少次，扛得住吗？timeline 里的动态被删了，已推给 10 万用户的副本怎么处理？

### Q12. 跨库扣库存 + 下单 + 积分：分布式事务怎么选

**问题：** 一个操作涉及订单库、库存库、积分服务，需要保证一致性。请对比 2PC、TCC、SAGA、本地消息表/事务消息的适用场景，给出你的选型与理由。

**期望加分项：**
- 能说清各方案本质：2PC 同步强一致但阻塞；TCC 业务补偿（try-confirm-cancel）；SAGA 正向 + 补偿链；本地消息表/事务消息最终一致
- 能结合场景取舍：扣库存 + 下单 + 积分这类「可异步、可补偿、对延迟敏感」的场景，选最终一致 + 对账
- 能识别「强一致陷阱」：什么时候真需要强一致（如资金），什么时候不需要（积分延迟几分钟无感）
- 能设计补偿动作与 TCC 细节：空补偿、悬挂、重复 confirm 的幂等
- 能给出对账与人工介入的兜底

**减分项：**
- 只会背 2PC 的 prepare/commit 流程，讲不出适用边界
- 把所有场景都套 TCC 或 SAGA，不做业务取舍分析
- 忽略补偿失败时的处理（补偿也失败怎么办）
- 不理解「本地消息表」如何解决 DB 与 MQ 的分布式问题

**解答：**
思路：先问「这个一致性是强一致还是最终一致」——扣库存、积分这类业务，用户能接受「下单成功、积分几分钟后到账」，最终一致足够；资金类才需要强一致。关键方法——推荐组合：本地消息表（或事务消息）保证「订单落库与发消息」原子性，下游消费时各自保证幂等与补偿；扣库存用「预占/预留」（类似 TCC 的 try），支付失败时释放预占。对比：2PC 适合短事务、低并发，工程上常因全局锁与长事务阻塞被劝退；TCC 把业务拆三阶段，灵活但开发量大，要处理空补偿、悬挂、重复 confirm；SAGA 把长事务拆成小事务 + 补偿链，适合跨服务编排。实践中的坑：选了 2PC 导致全局锁在高峰期把链路拖死；TCC 没做幂等，补偿执行两次；最常被忽略的是「对账」——分布式系统没有银弹，最终靠 T+1 对账 + 告警兜底，这应当作为设计的一部分主动讲出来，而不是补一句「最后做个对账」。

**延伸考点：** 积分服务补偿一直重试不成功，你怎么保证不无限重试（重试上限与人工介入）？「库存要么扣减成功要么明确失败，不能出现扣了库存但订单失败」——这个语义用 TCC 的哪一步实现？

### Q13. 一个业务三种存储：MySQL、Redis、ES 各干各的

**问题：** 商品检索系统需要「精确查询（ID/状态）、模糊搜索（关键词/条件筛选）、高并发读」。请设计存储分工：哪些数据放 MySQL、哪些放 Redis、哪些进 ES，并说明各自的一致性边界与数据同步方式。

**期望加分项：**
- 能讲清职责划分：MySQL 主数据/事务、Redis 热数据/计数器/排行榜、ES 全文检索与复杂过滤
- 能说清同步方案：先写 MySQL，再通过 binlog 订阅（Canal）异步同步到 Redis 与 ES，而不是业务代码双写
- 能指出不同存储间的延迟窗口与一致性问题（刚写入搜不到），如何补偿（上架显式刷新索引/查询兜底 DB）
- 能评估成本：三套存储的运维与一致性成本，什么阶段不需要三套
- 对查询编排有清晰认识：ID 查 Redis → MySQL 兜底，搜索走 ES

**减分项：**
- 把所有需求塞进一个存储，或反过来为每个功能加一套存储
- 双写用业务代码，且不考虑失败补偿
- 说不清 Redis 与 MySQL 哪边是事实源（source of truth）
- 不考虑删除/更新如何在 ES 里同步（重建文档 vs 更新字段）

**解答：**
思路：存储分工的本质是「一份事实源（MySQL）+ 多个派生视图（Redis/ES）」，先定事实源再定同步链路，避免双写。关键方法：MySQL 存商品主数据（状态、价格、库存），保证事务与事实；Redis 缓存热商品、计数（销量、库存余量）、排行榜，读多写少且允许秒级延迟；ES 承担关键词搜索与多条件过滤，商品每次变更通过 Canal 订阅 MySQL binlog 增量同步到 ES（全量初始化用迁移任务）。查询编排：ID/详情类查 Redis → MySQL 兜底；搜索类走 ES；写路径只打 MySQL，派生数据异步刷新。实践中的坑：业务代码双写 MySQL 与 ES，ES 写失败不回滚导致两边不一致且无法追溯；把 Redis 当事实源（如库存只放 Redis 不做 DB 兜底），重启即丢数据；Canal 同步延迟导致「刚上架搜不到」，要接受或加补偿（上架时显式触发索引刷新）。面试加分点：能讲「什么量级才需要 ES」——几百商家、几千商品时 MySQL LIKE 就够了，多一套存储多一套事故。

**延伸考点：** Redis 和 ES 数据不一致时（比如价格），以谁为准？你怎么发现不一致？商品改价极其频繁时，Canal 同步的写入放大怎么控制？

### Q14. 稳定性三板斧：限流、熔断、降级怎么配合

**问题：** 线上依赖的下游服务开始超时，流量还在涨。请设计你的稳定性策略：限流在哪几层做、熔断的判定与恢复、降级哪些功能，以及三者的优先级。

- 能结合真实案例：大促时通过全局限量保住支付成功率

**减分项：**
- 三个概念混在一起，说不清谁保护谁
- 只会背「令牌桶算法」，不会配置参数（容量、恢复速率）也没依据
- 熔断打开后所有请求直接失败，没有降级兜底（缓存/默认值）
- 不考虑恢复机制与抖动（半开状态的意义）

**解答：**
思路：三者目标不同——限流「保护自己不被流量打死」，熔断「保护下游不被自己打死」，降级「保核心、舍边缘」，优先级永远是核心链路。关键方法：限流分层——接入层按 IP/用户维度令牌桶限频（防刷），应用层按接口维度 QPS 配额（阈值来自压测，如「该接口单机 2000 QPS」），网关做全局限量；熔断——Sentinel/Hystrix 用滑动窗口统计最近 10 秒错误率超过阈值（如 50%）打开熔断，5 秒后半开放少量流量探测恢复；降级——降级清单按功能分级：一级核心（下单、支付）绝不降，二级（搜索、推荐）可降为缓存结果，三级（消息通知、报表）直接跳过。实践中的坑：熔断打开后直接抛异常（没有兜底值），体验比降级还差；限流阈值拍脑袋、没有压测依据，误伤正常流量；半开期间流量过大把刚恢复的下游又打挂（恢复抖动），需要平滑放量；只做入口限流不做依赖限流，下游一挂全部线程阻塞在等待上（线程池耗尽）。面试亮点：给出「限流阈值来自容量压测」「熔断要配合降级兜底」的工程连接。

**延伸考点：** 熔断恢复时如何避免「惊群」（大量请求同时涌入刚恢复的服务）？限流误伤了正常用户，怎么申诉与放行？

### Q15. 高可用：从单机到多活的每一层冗余

**问题：** 你的系统要支撑「99.99% 可用性」，从单机部署开始，请逐步设计每层的冗余与故障转移：应用层、缓存层、数据库层，并说明 RPO/RTO 目标。

**期望加分项：**
- 能逐层给出：应用多实例 + 负载均衡（健康检查、自动摘除）、Redis 主从 + 哨兵/Cluster（自动故障转移）、MySQL 主从 + 半同步 + 自动切换（MHA/Orchestrator）
- 能定义并解释 RPO（丢失多少数据）与 RTO（多久恢复），结合主从同步方式给出量级
- 能列出「隐藏单点」清单：DNS、负载均衡器本身、消息队列、注册中心
- 能讲清故障转移的细节：脑裂、切换后旧主恢复的冲突处理（防双写）
- 能设计备份与恢复演练：定期全量备份 + binlog 增量，恢复演练不是纸上谈兵

**减分项：**
- 只会说「加机器、做主从」，说不清故障转移的具体机制
- 说不出 RPO/RTO，或目标与现实脱节
- 忽略负载均衡器/注册中心自身的单点
- 认为有主从就万事大吉，没有备份恢复演练意识

**解答：**
思路：高可用是「消除单点 + 故障转移 + 数据保护」三件事，前提是假设「任何组件都会挂」。关键方法——应用层：多实例 + Nginx/LB 健康检查自动摘除，无状态应用任意水平扩容；缓存层：Redis 主从 + Sentinel 哨兵自动故障转移（Cluster 模式自带分片与转移），哨兵自身要奇数个防脑裂；数据库层：MySQL 主从（半同步保证已提交事务不丢）+ 自动切换工具（MHA/Orchestrator），RPO≈0（半同步）、RTO 分钟级；定期全量备份 + binlog 增量备份，并做「真实恢复演练」——很多团队备份存在但没恢复过，真出事才发现备份不可用。RPO/RTO 目标要量化：如 RPO < 30 秒、RTO < 5 分钟，再反推技术选型。实践中的坑：只做主从不做自动切换，故障仍要人工介入；切换后旧主恢复上线造成双写冲突，要防脑裂（仲裁节点/隔离手段）；LB 与注册中心是隐藏单点。面试加分点：主动提出「混沌演练」（kill 一个节点验证自动恢复）与故障复盘机制——纸上架构没有说服力，演练过的才可信。

**延伸考点：** 主从切换的瞬间，读流量打到只读从库会读到什么？如何让读流量感知切换？备份恢复演练怎么设计，才能验证 RTO 目标？

### Q16. 异地多活：两机房怎么「活」起来而不是两套孤儿数据

**问题：** 你要做双机房（同城或异地）多活，两边的用户都能读写。请设计数据同步与冲突处理，并讲清「多活」与「灾备」的本质区别，以及为什么很多团队做的其实是「伪多活」。

**期望加分项：**
- 能区分灾备（主备、standby 不承接流量）与多活（两边都承接读写）
- 能设计同步层：机房间数据同步（MySQL 双向复制、消息同步、单元化路由），讲清延迟（同城 1-5ms，异地几十 ms）对写冲突的影响
- 能讲清单元化（set 化）思路：按用户维度路由到固定单元，避免同一用户数据跨机房强一致
- 冲突处理：双向同步的冲突策略（版本号/最后写入胜出/业务规则），以及哪些数据不能双向同步（全局唯一 ID、库存类）
- 能指出伪多活的常见形态：只有读多活、写只进主机房；或切换时才发现备机房数据没同步全

**减分项：**
- 把灾备当多活讲，分不清概念
- 设计「两边同时写同一行数据」却不处理冲突
- 忽略机房间延迟对写链路的影响（异地写放大到秒级不可接受）
- 不谈切换判定（怎么知道对端机房挂了）与回切（数据回灌与对账）

**解答：**
思路：多活的本质是「把流量和数据切成可独立运作的单元」，核心是单元化路由 + 机房间同步。关键方法——单元化：按 user_id 哈希把用户绑定到固定单元（机房），读写都在本单元内闭环，同城单元间数据同步做最终一致；故障切换时把整个单元流量切到对端，而不是逐请求分散。同步：MySQL 双向复制处理「不同用户写不同数据」没问题，冲突发生在「同一行被两边写」——通过单元化路由从架构上避免这种冲突，而不是靠同步层解决；全局维度数据（ID 发号、库存）必须单点或专门设计，不能依赖双向同步。延迟约束：异地（如上海-北京）单向延迟 30ms+，同步型写链路会变慢，所以异地多活通常配合「读就近、写回源」或单元化。实践中的坑：只做了「读多活」（两边可读、写全回主），切换后才发现备机房没有写入能力；切换判定用心跳超时，但网络分区时两边互相认为对方挂了（脑裂双活），需要仲裁机制；回切时数据回灌与对账缺失。面试亮点：主动讨论「哪些业务能做多活，哪些（如库存强一致）不能」——多活不是所有业务的银弹。

**延伸考点：** 网络分区时如何保证「只有一边对外提供写服务」（防双写）？单元化后，用户在 A 单元注册、在 B 单元登录的场景怎么路由？

### Q17. 线上出问题 3 分钟定位：可观测性怎么搭

**问题：** 大促时服务 P99 延迟从 50ms 涨到 5s，你需要 3 分钟内定位到「哪个服务、哪个接口、依赖了谁」。请设计你的可观测性体系：日志、指标、链路追踪分别负责什么，告警怎么定阈值才不狼来了。

**期望加分项：**
- 能讲清三支柱分工：日志（排错细节）、指标（趋势与告警）、链路追踪（调用链与瓶颈定位），以及如何配合
- 指标能给出关键清单：QPS/错误率/P99/P999、饱和度（线程池、连接池、GC）、依赖指标
- 链路追踪能讲清 trace/span、采样策略（固定采样 + 慢请求强制采样的取舍）
- 告警能说出「基于 SLO 与压测定阈值」「告警降噪（聚合、抑制、去重）」「告警必须有可执行动作」
- 能把「先看全局指标 → 顺 trace 下钻 → 看日志细节」的排查流程讲出来

**减分项：**
- 只会堆组件名（Prometheus/Grafana/ELK/Jaeger），讲不清各自解决什么问题
- 告警阈值拍脑袋，天天狼来了最后没人看
- trace 与日志没有关联（traceId 未贯穿），出问题串不起来
- 只监控应用不监控依赖（DB、缓存、MQ 指标缺失）

**解答：**
思路：可观测性的目标是「快速回答三个问题：哪里慢了、为什么慢、影响多大」，三支柱缺一不可。关键方法——指标先行：Prometheus 采集中间件与业务指标（QPS、错误率、P99、线程池/连接池使用率、GC、DB/Redis 慢查询数），告警规则基于 SLO 与压测结果设定（如「P99 连续 3 个周期超过 2s」），避免拍脑袋阈值；链路追踪：全链路 traceId 贯穿（网关生成、日志打印），采样权衡——固定采样率 1% 会漏掉慢请求上下文，常用「固定采样 + 慢请求强制采样」；日志：结构化 JSON 日志带 traceId、user_id、业务上下文，日志与 trace 靠 traceId 关联。排查流程：先看仪表盘确认故障范围 → 看 trace 定位慢在哪一跳 → 下钻日志看异常详情。实践中的坑：日志和 trace 各存各的、traceId 没打进日志，出问题对不上；指标只做了 RED 没做 USE（连接池、线程池等资源饱和度缺失），出现「QPS 不高但很慢」无从下手；告警风暴（同一故障 200 条告警）导致告警被静音。面试亮点：强调「告警要能触发动作，不能只是通知」。

**延伸考点：** P99 从 50ms 涨到 5s 但平均延迟只涨了 2 倍，这说明什么？（提示：长尾/热点）trace 采样率 1% 时恰好没采到那个慢请求，怎么定位？

### Q18. 安全设计：认证、鉴权、防刷、加密一个都不能少

**问题：** 你的开放平台要对外提供 API，同时内部系统有敏感数据（用户手机号、支付信息）。请设计：认证与鉴权方案（含 token 体系）、接口防刷、以及敏感数据存储与传输的加密方案。

**期望加分项：**
- 认证能讲清 token 体系（JWT 的适用与局限：无状态但难吊销；access token + refresh token 双 token 方案）、OAuth2 三方接入的基本流程
- 鉴权能说清 RBAC/ABAC 的选择，以及「网关做粗粒度、服务内做细粒度」
- 防刷能给出多维度：IP/设备/账号维度限频、验证码/滑块、行为风控，以及分布式限频的滑动窗口实现
- 加密能区分：传输层 TLS、存储层哈希（密码 bcrypt/argon2 加盐）、字段级加密（AES）、密钥管理（KMS），并点出「密码明文入库」是红线
- 能讨论日志脱敏、数据导出权限等合规细节

**减分项：**
- 只会说「用 JWT」，讲不清吊销问题与过期策略
- 密码用 MD5 甚至明文，或不加盐
- 防刷只做单机限频，或限频可被伪造 IP 头绕过
- 不谈密钥管理，密钥写死在代码/配置里

**解答：**
思路：安全设计要分层——认证（你是谁）→ 鉴权（你能干什么）→ 防护（恶意流量）→ 加密（数据泄露兜底）。关键方法——认证：内部服务用双 token（短期 access token + 长期 refresh token），JWT 适合无状态网关，但「吊销难」要用黑名单层弥补（Redis 存被吊销的 jti）；三方平台用 OAuth2 authorization code 流程。鉴权：RBAC 管角色权限，敏感操作（提现、改手机号）叠加动态校验（风控、二次验证）。防刷：网关层按 IP + 设备 + 账号三维度滑动窗口限频，验证码与行为验证兜底，注意「X-Forwarded-For 可伪造」，要从可信代理取真实 IP。加密：传输 TLS1.2+；存储——密码用 bcrypt/argon2 加盐哈希，绝不存可逆密文；手机号等字段级 AES 加密 + 展示脱敏；密钥集中 KMS 管理、定期轮换，禁止写死代码。实践中的坑：JWT 无法主动踢人，账号安全事件无法止血；只加密存储不脱敏日志，日志里还是明文；限频阈值过高形同虚设、过低误伤正常用户（要按用户行为分布定）。面试亮点：把「攻击面」讲全——不止接口，还有管理后台、导出、日志、备份文件这些泄露点。

**延伸考点：** 用户 token 被盗用，如何在不改密码的情况下让 token 立即失效？支付回调接口的防刷与签名校验你会怎么设计？（提示：来源校验、验签、幂等）

### Q19. 微服务拆分：什么时候拆、怎么拆、拆错怎么办

**问题：** 一个 30 万行代码的单体应用已经上线，团队想微服务化。请给出你的判断：该不该拆、按什么边界拆（业务域 vs 技术分层）、拆的先后顺序，以及「拆完反而更慢」这种反模式的识别。

**期望加分项：**
- 能先判断「是否值得拆」：团队规模、发布频率、独立扩容需求、模块耦合度，用「拆了带来什么具体收益」衡量
- 边界能讲清按业务域/聚合拆（用户、订单、库存），而不是按技术层拆（controller 服务、service 服务）
- 顺序能说清「先拆低耦合高价值」：如消息通知、报表先拆，跨服务事务的模块最后拆
- 能识别反模式：分布式单体（拆了但到处调）、服务间共享数据库、拆太碎（一个方法一个服务）、调用链过长
- 能讲清拆分配套：服务发现、配置中心、网关、链路追踪、契约测试，否则拆完是灾难

**减分项：**
- 无脑推崇微服务，讲不出单体阶段的具体问题
- 按技术分层拆服务（数据层/逻辑层各一个服务）
- 忽略拆分带来的网络调用、数据一致性、运维复杂度成本
- 说不清拆分的验收标准（发布频率、故障隔离能力）

**解答：**
思路：微服务是手段不是目的，判断标准是「收益/成本」——收益 = 独立发布、独立扩容、故障隔离、团队自治；成本 = 网络调用、分布式事务、运维与监控复杂度。关键方法：先评估——发布频率（每周多次 vs 每月一次）、模块间耦合（是否有大量共享可变状态）、团队规模（小于 15 人拆了反而低效）。边界：按业务能力/聚合拆，用限界上下文划分，「订单」与「支付」分开，而不是「controller 服务」「dao 服务」。顺序：从「边界清晰、依赖少、独立价值高」的模块开刀（消息通知、报表），核心交易链最后拆，拆一个验证一个——发布频率提升、故障影响面缩小才算成功。实践中的坑：拆了但共用数据库表，两个服务通过 DB 隐式耦合，比单体还难维护（分布式单体）；服务间同步调用链过长（A→B→C→D），一次故障全链路抖动，要先砍调用深度；拆太碎导致一次下单 20 次 RPC。面试亮点：主动提出「拆完的验收指标」（发布频率、故障恢复时间、单服务独立扩缩容），并承认「单体 + 模块化」在某些阶段是更好的选择。

**延伸考点：** 什么信号出现说明「该从微服务退回单体/模块单体」？拆完后订单服务与支付服务的数据一致性怎么处理？

- 选型说不出理由（「大家都用」不算理由）

**解答：**
思路：架构演进是「用最便宜的方式撑过当下，用最小的代价为未来留口子」，每个阶段的触发器是「现有架构出现具体痛点」，而不是跟风。关键方法——阶段一：单体 + 单机 MySQL + Redis，快糙猛上线，目标是验证业务；阶段二：访问量上来，加缓存（热点读）、应用多实例 + LB、MySQL 主从读写分离，触发条件是单机 CPU/DB 连接告警；阶段三：写入与数据量上来，MQ 异步化（削峰解耦）、冷热归档、分库分表（量化依据见 Q10）；阶段四：团队与业务复杂度上来，按业务域微服务化（见 Q19）、异地多活（见 Q16）。架构图表达：接入层（Nginx 集群）→ 网关（限流/鉴权）→ 应用服务（无状态、水平扩展）→ 数据层（Redis 集群、MQ、MySQL 分片、ES），图上标出「下单关键路径」与「异步链路径」，面试时按图讲清「为什么这样分层、每层的容量边界在哪」。实践中的坑：阶段三做早了（数据量没到就分库分表）白白背迁移复杂度；阶段四做晚了（单体发布互相踩）团队效率崩塌；架构图只画组件不画数据流，无法评估合理性。面试亮点：主动讲「当前架构最可能先挂的组件是什么、下一步怎么演进」——动态演进比静态画图更能体现架构能力。

**延伸考点：** 你当前架构里最可能先挂的组件是什么？明天流量涨 10 倍，你的扩容顺序是什么（先扩哪些层、哪些层要改架构才能扛）？
