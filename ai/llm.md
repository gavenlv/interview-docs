# AI · 大模型基础（面试题库）

本文件考察 AI 工程师/算法工程师在大模型应用与工程落地上的真实能力：从 LLM 原理对工程的影响（Transformer、注意力、KV cache、token 管理），到训练与微调实践（PEFT、显存优化、数据治理），再到推理服务化、评估体系、安全对齐与成本治理。题目均为场景化提问，不考八股文——重点看候选人能否给出量化依据、说清取舍、联系线上实践、主动考虑边界条件。

---

### Q1. 线上回答质量突然下降，怎么排查？

**问题：** 线上模型回答质量这几天明显变差，但期间没改任何代码。可能是哪些环节出了问题？你会怎么排查？

**期望加分项：**
- 先区分"下降"的定义：有量化指标（抽检分、拒答率）还是仅凭感觉，能说出自己线上的质量口径
- 有完整排查路径：时间线对齐 → 分层定位（输入层/推理层/模型层）→ 离线回放验证
- 能主动想到 prompt、检索内容、上游模型、路由/降级策略、参数配置等"没改代码"但会变化的环节
- 提到"没有基线样本集就无法回放"这一工程痛点，并给出建立 golden set 的做法
- 能区分急性劣化（版本/配置变更）与慢性漂移（数据分布渐变）

**减分项：**
- 只说"可能是模型出问题了，换个大模型"这类无方法论的猜测
- 只盯着模型权重，想不到检索库、prompt 模板、路由策略也在线上
- 没有时间线比对和离线回放意识，排查靠拍脑袋
- 答不出"如何量化质量下降"

**解答：**

先确认"质量下降"有没有量化依据——是人工抽检分掉了，还是用户反馈变多，还是代理指标（拒答率、无引用率、超时率）突变；没有指标就先补抽检和日志，否则后面无法判断"修好了没有"。确认后拉出变化时间点，与发布记录做时间线对齐：prompt 模板有没有被改（哪怕只改了个标点）、RAG 索引有没有重建或更新、检索到的内容来源变了没有、模型版本有没有被路由策略切走、服务端有没有触发降级（比如并发过高把请求路由到小模型或关闭了某些特性）、解码参数（temperature、max_tokens）有没有被别处覆盖。线上排查最有效的手段是"回放"：从日志里捞到质量下降前后的同一批真实输入，用当前链路和旧链路分别跑一遍做 diff，通常几轮就能定位。常见根因按概率排序：上游检索内容变化（文档更新、去重策略变动）、prompt 被某次"顺手优化"改坏、路由/降级触发、模型上游版本漂移（API 侧模型更新导致行为变化）。坑在于：很多团队没有留输入输出日志和版本快照，问题一发生就只能靠猜——所以日常就要把"基线样本集 + 全链路版本号落日志"当基础设施来做。

**延伸考点：** 慢性质量漂移（分布渐变）和急性劣化在排查手段上有什么区别？如果没有任何历史日志，如何快速建立可比基线？

### Q2. 超长文档怎么塞进上下文窗口？

**问题：** 业务要处理 10 万字以上的长文档（合同、研报、客服工单），但模型上下文窗口有限，全量塞进去既超限又贵。你会怎么设计文本处理方案？

**期望加分项：**
- 能说清"全量入文"与"检索入文"两条路线，并给出取舍依据
- 熟悉截断策略（保头保尾、中间摘要压缩）与分块策略（chunk 大小、重叠率、语义边界切分）
- 能给出量化参数：chunk 256~512 token、重叠 10%~20%、摘要压缩比等，并说明依据
- 主动考虑信息丢失、召回失败、成本（token 数）三个约束
- 结合 RAG：检索 Top-K 段落入文，并说明如何控制总 token

**减分项：**
- 只会说"分块"两个字，说不出 chunk 大小、重叠、切分方式怎么定
- 不考虑截断丢信息的代价，也不评估召回率
- 把"长上下文模型"当万能答案，不谈成本与效果衰减
- 不量化 token 成本变化

**解答：**

先想清楚任务类型：如果是"根据文档某几处作答"，走检索入文；如果是"全局理解、总结、跨章节比对"，检索容易漏，需要更完整的覆盖。对前者，经典做法是分块 + 检索：chunk 取 256~512 token（太小语义不完整，太大检索精度下降且浪费上下文），相邻块留 10%~20% 重叠防止关键句被切断，优先按标题/段落等语义边界切而不是硬按长度切，然后向量召回 Top-K 块，再按原文顺序拼回 prompt。对后者，用"层级摘要"或"滑动窗口 + MapReduce"：先把全文分成若干段，逐段让模型生成摘要/要点，再让模型基于摘要+关键段作答，注意摘要本身有信息损失，也会引入模型自己补充的内容。全量截断时优先保头保尾（首因/近因效应明显），中段必要时做压缩。工程上最大的坑是：chunk 切分不当导致同一句话被拆到两个块里，检索召回时两个块都"像但都不全"，模型拼不出正确答案——所以重叠率和语义边界切分要专门验证；另一个坑是检索失败时模型会凭印象自由发挥，需要兜底提示"未找到相关内容时明确说明"。

**延伸考点：** chunk 大小和重叠率对召回率的影响如何离线量化？长文档总结场景，如何避免摘要层层叠加导致的信息失真？

### Q3. 几千 token 的系统 prompt 每次请求都重复计算，怎么优化？

**问题：** 服务端固定带一段很长的系统 prompt（含指令、格式示例、安全约束），每次请求都要重复 prefill，时延和成本都很高。有什么优化手段？

**期望加分项：**
- 知道 KV cache 跨请求复用的原理：相同前缀的 K/V 可复用，前缀必须逐 token 完全一致
- 能说出具体工程做法：系统 prompt 固定并放在最前、动态内容放最后、prompt 模板做版本管理防止前缀漂移
- 知道 vLLM Automatic Prefix Caching / SGLang RadixAttention / 云 API 的 prompt caching（如缓存计费打折）这些具体设施
- 能给出量化收益：缓存命中率、TTFT 下降幅度、成本节省
- 主动提缓存失效场景（带时间戳/随机数的 prompt 会让缓存全部失效）

**减分项：**
- 只说"加个缓存"，说不清缓存的是什么、怎么命中
- 不知道前缀缓存要求逐 token 完全一致，把"语义相同"当"可命中"
- 不评估缓存占用的显存/内存成本
- 多租户不同系统 prompt 的场景答不出适配方案

**解答：**

核心原理是 KV cache 前缀复用：transformer 的 prefill 阶段会为每个 token 计算 K/V，如果新请求的前缀和之前某个请求完全相同，这部分 K/V 可以直接复用，省掉重复计算，TTFT 能显著下降。工程上有三个关键动作。第一，结构固定：把系统 prompt 做成模板放在最前，用户问题、检索内容等动态部分放最后，任何动态内容都不要插进系统 prompt 中间——前缀一旦在中间被打断，后面全部缓存失效。第二，设施选型：自建推理用 vLLM 的 Automatic Prefix Caching 或 SGLang 的 RadixAttention（后者对共享前缀的树形复用更激进）；走云 API 则用平台自带的 prompt caching，命中部分按更低价计费，长系统 prompt 场景收益很明显。第三，治理：prompt 模板要版本化，同一模板的任何改动都会让缓存整体失效，所以高频迭代期缓存命中率会掉，需要权衡；不要在 prompt 里塞时间戳、随机数这类每次都变的内容。实操中要监控缓存命中率、TTFT 和显存占用：prefix cache 也占显存，命中率低时反而挤占推理资源；多租户场景可把公共系统 prompt 统一收口，把租户差异放到 prompt 尾部的数据区。

**延伸考点：** 缓存命中率只有 20%，可能是哪些原因？如何在不改产品逻辑的前提下提升命中率？

### Q4. 开源模型和商业 API 怎么选？

**问题：** 新项目要接 LLM 能力，团队既有 API 预算也有 GPU 资源，开源模型和商业 API 各有利弊。你怎么做选型决策？参数量选多大合适？

**期望加分项：**
- 能给出多维度对比框架：效果天花板、成本（API 按 token 计费 vs GPU 折旧+运维）、时延、数据合规、可控性、迭代速度
- 会算账：用 QPS × 平均输入输出 token × 单价 估算 API 成本，用模型参数量 × 卡型估算自建成本
- 提到数据出境与私有化约束是硬性前提，不是可选项
- 能说出"先 API 验证业务 → 蒸馏/微调开源模型降本"的演进路径
- 对参数量有量级概念：7B/13B 通用任务够用，70B+ 需多卡+量化

**减分项：**
- 一刀切"闭源最强"或"开源免费"，不给依据
- 不考虑数据合规红线（敏感数据出境）
- 只算 API 账单，不算 GPU 折旧、人力运维、多卡调度成本
- 对参数量选择没有量级概念

**解答：**

选型先列约束再谈对比。第一道硬约束是数据合规：数据能否出境、是否涉及敏感信息、客户是否要求私有化——只要有一条不满足，闭源 API 直接出局，只能在开源里选。其余维度按优先级排：效果天花板（复杂推理、长程规划、创意写作场景，开源小模型与一线闭源差距明显，这个差距后期很难靠工程补）、成本（API 是"按用量计费、零运维、随用随涨"，自建是"固定投入、折旧+电费+人力运维"，一般用月度预估 QPS×token 量把两条曲线拉出来对比，交叉点在哪个量级一目了然）、时延（API 有网络 RTT，自建可控且可本地化）、可控性（开源可微调、可固化版本、可审计）。工程上比较稳的路径是：先用闭源 API 快速验证业务假设和效果天花板，跑通后把高频、成本敏感、效果要求明确的场景蒸馏或微调成开源小模型替换，闭源保留给疑难长尾。参数量选择：7B 能覆盖大多数指令/抽取/摘要任务，13B~32B 是性价比拐点，70B+ 需要 4 卡起步还要量化，只有复杂推理强需求才值得。最大的坑是低估自建运维成本（多卡并行、故障恢复、框架调优的人力投入远超买卡的钱），以及忽视合规导致上线前返工。

**延伸考点：** 用 5 个量化指标（效果、成本、时延、合规、可控性）给一个具体场景做个选型打分，权重怎么设？蒸馏替代闭源模型前怎么验证"效果下降可接受"？

### Q5. 同一个场景既要低延迟又要高吞吐，推理服务怎么配？

**问题：** 线上推理服务要同时满足交互场景的低时延（用户等待体验）和离线场景的高吞吐（批量处理），但这两个目标相互牵制。服务参数和架构怎么设计？

**期望加分项：**
- 能说清 throughput 与 latency 的本质矛盾：batch 越大吞吐越高、单请求排队与串行拖慢时延
- 知道 continuous batching（连续批处理）如何打破固定 batch 的等待浪费
- 能给出关键参数及含义：max_num_seqs、max_seq_len、gpu-memory-utilization、队列策略
- 按场景分别给配置：交互走小 batch + 短超时，离线走大 batch + 长队列
- 提到限流、熔断、优先级队列应对突发

**减分项：**
- 只会说"开 batching"，说不出参数和权衡
- 不区分交互/离线场景，一套参数打天下
- 把 p95 时延当平均值来设计
- 忽略高峰突发导致的排队雪崩

**解答：**

先明确两件事：一是把场景拆开——交互接口定 p95 时延 SLA，离线任务只关心吞吐和总耗时，两者可以走同一套服务但参数和资源池分开；二是理解生成式推理的瓶颈，prefill 阶段计算密集、decode 阶段访存密集，batch 越大 GPU 利用率越高但单请求被拖得越慢。工程上核心是 continuous batching：不再等整个 batch 跑完才接收新请求，而是序列级动态调度，某序列生成完立即让位给新请求，vLLM、TGI、TensorRT-LLM 都支持。关键参数：max_num_seqs 决定同时处理的序列数，交互场景取小值（如 8~16）控时延，离线取大值（64~256）榨吞吐；max_seq_len 和 gpu-memory-utilization 决定 KV cache 预留——显存利用率设太高会让长序列突发时 OOM，一般 0.85~0.95；队列要有上限和优先级，交互请求插队、批处理请求排队，超时就快速失败而不是无限堆积。最后的兜底是限流+降级：突发时优先保证 p95，超阈值把部分流量路由到小模型或走缓存。常见的坑：只统计平均时延导致 p95 超标没人发现；单条超长请求（如 32K）会卡住整个 batch 的 decode 节奏，需要把长序列隔离到单独队列。

**延伸考点：** p95 和平均时延在设计上的差异在哪里？prefill 与 decode 阶段分别用什么手段优化时延？

### Q6. 支持 128K 长上下文，显存被 KV cache 吃光怎么办？

**问题：** 业务要支持 128K 长上下文对话，80G 显存的卡上 KV cache 几乎占满，并发数趋近于 1。怎么从模型选择和工程两个层面解决？

**期望加分项：**
- 能写出 KV cache 显存估算公式：2 × L × H × d × S × B × 字节数（K、V 各一份），对 7B 有量级概念（约 0.5MB/token@FP16）
- 知道 GQA/MQA 是模型结构层面的优化（Llama 3、Qwen2 系列已内置），KV 头数减 8 倍
- 能说出工程手段：KV cache 量化（INT8/FP8）、chunked prefill、滑动窗口/稀疏注意力、KV offload
- 能计算"单请求峰值"与"并发"之间的取舍，不盲目追求全量并发
- 主动提示 KV cache 量化的精度损失需要评测验证

**减分项：**
- 说不出公式或量级，凭感觉"应该挺大"
- 只会说"换更大的显存"或"少并发"
- 不知道 GQA 是什么、与 MHA 的差别
- 忽略 decode 阶段 KV cache 持续增长，不做峰值预估

**解答：**

先算账再优化。KV cache 显存 ≈ 2 × 层数 L × KV 头数 × 每头维度 d × 序列长度 S × batch × 字节数（K、V 各一份，7B 规模约 0.5MB/token@FP16）——这意味着 128K 单请求就要约 64GB，物理上排除了高并发，所以目标改为"单请求跑得动 + 有限并发"。模型层面：优先选带 GQA/MQA 的架构（Qwen2 系列、Llama 3 系列普遍内置），KV 头从 32 降到 4~8，cache 直接缩 4~8 倍，这是结构红利，工程手段补不回来。工程层面按顺序做：KV cache 量化（FP16→INT8/FP8 显存减半，配合低精度推理框架；注意量化后精度损失在超长上下文场景会被放大，要用业务长文档评测集验证）；chunked prefill 把超长输入的 prefill 切块，避免瞬时显存尖峰；长上下文对话用滑动窗口或稀疏注意力限制 cache 增长；必要时把冷段的 KV offload 到 CPU 内存，只保留热段在显存。最后是容量规划：按"最长序列 × 目标并发 × 每 token 显存"算峰值，gpu-memory-utilization 留余量防 OOM。常见坑：只优化了权重显存没算 KV cache；线上出现单条超长请求直接 OOM 拖垮整卡——要在服务层按长度分流，超长走低并发专用池。

**延伸考点：** 128K 上下文场景，GQA 换成 MHA 会多占多少显存？KV cache 量化为什么在长序列下精度损失更明显？

### Q7. 想把 70B 模型塞进单卡 80G，量化怎么选？

**问题：** 预算只够单卡 80G，想部署 70B 模型。量化方案（GPTQ/AWQ/FP8/GGUF）怎么选？怎么评估量化带来的效果损失？

**期望加分项：**
- 能说清几类方案的区别：GPTQ/AWQ 是 W4A16 权重量化、FP8 是 W8A8 全量化、GGUF 是 CPU/边缘部署友好格式
- 能量化估算：FP16 70B 权重约 140GB，W4 约 35GB，配合 KV cache 才能进 80G 单卡
- 知道"量化后必须用业务评测集对比"而不是只看困惑度
- 能说出敏感层概念（norm、attention 输出对量化更敏感）和 AWQ 基于激活异常值选层的原理
- 提到量化+长上下文组合时损失放大、需要回归验证

**减分项：**
- 只知道"量化会变笨"，给不出评估方法
- 把 W4/W8、权重量化/激活量化混为一谈
- 只用一两条样本或困惑度下结论
- 不做量化后业务指标回归

**解答：**

先定目标：是省显存、加速、还是上边缘设备，决定选型。量级上要心里有数：FP16 的 70B 光权重就约 140GB，W4（GPTQ/AWQ）压到约 35GB，加 KV cache 和激活后才能落进 80G 单卡——所以 70B 单卡基本必走 4bit。方案对比：GPTQ 是经典 W4A16 权重量化，AWQ 基于激活值敏感度选层、对异常值更鲁棒，两者精度接近、AWQ 对激活敏感场景略优；FP8（W8A8）权重和激活都量化，在 H100 等卡上有原生加速、精度损失很小，是"H 卡 + 不想掉精度"的折中；GGUF 是 llama.cpp 生态格式，主打 CPU/小内存部署，速度上限低。评估方法论是关键：不要用困惑度或一两条样本判断，用业务评测集（指令跟随、抽取、代码、RAG 问答各一档）量化前后逐项对比，设一个"关键指标下降阈值"（比如抽取准确率掉 2 个点以内可接受），超了回退到更高精度档位。实操坑：AWQ/GPTQ 需要校准集，校准集分布要贴近线上输入，否则量化效果在真实流量上打折；4bit 量化后模型在长上下文、数学推理上掉点比短文本明显；INT4 推理在部分框架上有反量化开销，未必比 FP8 快——选型要同时看显存、速度、精度三个数。

**延伸考点：** 为什么"激活量化"比"权重量化"难做？AWQ 的激活异常值感知原理是什么？

### Q8. vLLM、TGI、TensorRT-LLM 推理框架怎么选？

**问题：** 团队要自建 LLM 推理服务，vLLM、TGI、TensorRT-LLM、SGLang 各有拥趸。你怎么选型？决策依据是什么？

**期望加分项：**
- 能从吞吐、功能（prefix caching、量化、LoRA serving、多模态）、生态成熟度、团队维护成本四个维度对比
- 知道各框架差异点：vLLM 生态最广、prefix caching 成熟；TensorRT-LLM 单机吞吐上限高但定制成本高；SGLang 的 RadixAttention 对共享前缀/多轮场景友好；TGI 功能全但长文吞吐略逊
- 结合具体场景给结论（如多轮对话选 SGLang、极致性能选 TRT-LLM、通用首选 vLLM）
- 提到框架间精度/行为有差异，切换需重新评测
- 考虑团队人力：小团队别选维护成本高的框架

**减分项：**
- 直接说"用 vLLM 就行"，不给对比依据
- 不了解各框架差异，把名字报一遍当答案
- 不考虑团队维护能力与卡型适配
- 不做框架间的 benchmark 验证

**解答：**

先明确约束再选：模型架构（是否 GQA、是否多模态）、部署卡型（A100/H 卡/消费卡）、需要的特性（prefix caching、量化、多 LoRA 并发、函数调用）、团队人力。横向看：vLLM 社区最大、迭代最快，PagedAttention 和 Automatic Prefix Caching 成熟，通用场景首选，坑少；TensorRT-LLM 单机吞吐上限最高、显存利用极致，但需要 C++/CUDA 背景做定制，框架升级慢，适合"极致性能 + 有工程沉淀"的团队；SGLang 的 RadixAttention 把共享前缀做成了树形复用，多轮对话、固定系统 prompt、Agent 多步调用这类"前缀高度复用"的场景收益最明显，但生态相对年轻；TGI 功能全（量化、LoRA adapter、embeddings 端点开箱即用），但长上下文吞吐上相比 vLLM 略逊。选型后一定要做自己的 benchmark：用真实流量分布（序列长度、并发、输入输出比）压测对比吞吐和 p95，因为各框架对长序列的调度策略不同，官方榜单测的是理想分布，不一定代表你的场景。实操坑：框架间 kernel 实现不同，同一个模型量化后精度可能有细微差异，切框架必须重跑业务评测集；多机部署（tensor parallel + pipeline）各框架支持度不一，跨节点带宽不足时 TP 反而变慢；小团队最容易掉进"选最快的框架然后被定制需求拖死"的坑。

**延伸考点：** 怎么设计一个能反映真实场景的推理框架 benchmark？多轮对话场景下 SGLang 相比 vLLM 的优势具体体现在哪？

### Q9. 业务风格适配，LoRA 还是全参微调？

**问题：** 想让开源模型在业务场景里说话风格、输出格式完全符合团队要求，手里只有几千条标注数据。LoRA 和全参微调怎么选？微调效果怎么验证？

**期望加分项：**
- 能说清 PEFT 原理：冻结基座、注入低秩可训练矩阵，训练参数占比极小
- 给出选型依据：数据量小（<1 万条）+ 只做风格/格式适配 → LoRA；要学新知识/新能力 → 全参或加大数据量
- 知道关键超参：rank 4~64（任务越复杂越大）、alpha 取 rank 的 1~2 倍、target_modules 的选择
- 验证方法：业务评测集 before/after 对比（风格命中率、格式正确率）+ 通用能力回归（防灾难性遗忘）
- 提到 QLoRA 用 4bit 基座进一步降本

**减分项：**
- 只会背"LoRA 是低秩适配"的定义，说不出 rank 怎么定
- 微调完不验证，或只用训练集 loss 判断
- 忽略灾难性遗忘，不跑通用能力回归
- 数据量、任务复杂度与方案完全不匹配

**解答：**

先判断任务性质：如果只是"输出风格/格式/语气"这类行为层适配，且数据量在几千到一万条，LoRA 是默认选择——训练参数少、显存和成本低、几分钟到几小时就能出结果，而且可以保留基座权重、按业务动态挂载不同 adapter；如果是要让模型"学会新的知识或新的推理能力"（比如行业专有推理链路），LoRA 数据量不够时学不进去，得考虑全参微调或更多数据。LoRA 关键超参：rank 一般 4~64，任务简单取小值、复杂取大值（如代码/结构化输出取 32~64）；alpha 通常取 rank 的 1~2 倍；target_modules 默认覆盖 q_proj/v_proj，也可以扩展到全部线性层；训练轮次 1~3 轮为主，数据重复率高时一轮都够。验证要双线并行：正向看业务指标——风格命中率、格式规范率、任务成功率，拿独立 holdout 集对比基座与微调后；反向看通用能力——在同一批通用指令/推理样本上跑基座与微调后的对比，发现掉点明显说明灾难性遗忘，需要混入通用数据或调低学习率。坑：LoRA 权重合并回基座时如果精度不一致（adapter 是 FP32、基座是 FP16）会导致结果漂移，要先量化验证；训练数据只有"理想输出"没有"坏样本"会让模型把错误也学进去；验证集和训练集同源会导致效果虚高。

**延伸考点：** LoRA 和 QLoRA 的差别与适用边界？多业务共用一个模型时，多 Adapter 怎么管理和切换？

### Q10. 微调后训练集很好、线上泛化差还复读，怎么办？

**问题：** 微调后的模型在训练集和测试集上指标都很好看，但上线后泛化差，还出现复读、模板化严重、幻觉变多。问题可能出在哪？怎么修？

**期望加分项：**
- 先怀疑数据再怀疑超参：重复数据、噪声样本、分布单一、坏样本被学进
- 能识别过拟合信号：训练/评估指标差距大、输出模板化、长句复读
- 给出具体手段：数据去重（exact/near-duplicate）、清洗坏样本、扩充多样性、构造负样本、加入"不知道就直说"样本
- 超参侧：降低 epochs、early stopping、调低学习率、混入通用数据
- 强调独立同分布的 holdout 评估集

**减分项：**
- 只调 learning rate / epochs，不检查数据
- 评估集与训练集重叠，指标虚高不自知
- 看不出"复读/模板化"是过拟合的典型症状
- 不做数据去重和坏样本清洗

**解答：**

微调效果虚高 + 线上崩，十有八九是数据问题而不是超参问题。第一步查数据：用精确去重 + 近似去重（SimHash/Embedding 相似度）看训练集重复率，很多场景重复率高达 30%+——重复样本会被模型当先验放大，直接导致复读和模板化；再抽检坏样本，特别是"输出里带幻觉/事实错误"的标注，模型会把坏习惯学进去；还要看多样性，如果 90% 的样本是同一个模板套出来的，模型就只会背模板。第二步再调超参：epochs 过高是复读的头号诱因，一般 1~3 轮，配合 early stopping；学习率过高会快速破坏预训练知识，建议比通用推荐值低一档。第三步补数据：加入分布多样的改写样本，构造"不知道就直说"的负样本（模型最怕被训练数据逼着硬答），必要时混入 10%~30% 通用指令数据防遗忘。评估的坑要先堵住：holdout 集必须和训练集无重叠、且从线上真实分布采样，否则 before/after 对比全是虚的；训练时盯 loss 曲线和指标曲线，出现"训练指标还在涨、验证指标开始掉"的剪刀差就是过拟合信号，不是等上线才发现。最后用线上灰度 + 抽检来兜底，因为离线分布和线上分布永远有 gap。

**延伸考点：** 复读问题除了数据去重还能用什么解码侧手段缓解？怎么自动检测训练集里的坏样本和重复样本？
