# AI · 机器学习基础（面试题库）

本文件考察算法工程师/数据科学家在经典机器学习工程落地上的真实能力：从模型选型与特征工程（缺失值、类别编码、特征泄漏），到评估与调优（指标选择、过拟合、偏差方差、时序切分），再到上线治理（批量/在线服务、漂移监控、版本灰度、AB 实验、离线在线一致性）与开放性架构思考（多目标、冷启动、可解释性、与规则系统协同）。题目均为场景化提问，不考八股文——重点看候选人能否给出量化依据、说清取舍、联系线上实践、主动考虑边界条件。

### Q1. 排序模型 LR / GBDT / 深度学习怎么选型？

**问题：** 你们要做推荐排序或 CTR 预估，特征几百到上千维，数据量几千万级。团队里有人主张 LR、有人主张 GBDT、有人主张直接上深度模型。你从哪些维度做选型判断？

**期望加分项：**
- 先定义业务约束（推理时延、吞吐、更新频率、可解释性要求）再谈模型
- 能说清三类模型的本质差异：线性可分性、特征交叉能力、对高基数稀疏特征与稠密统计特征的适配、训练/推理成本
- 给出量化依据：特征类型（稀疏 ID vs 稠密统计）、样本量、数据稀疏度决定模型复杂度
- 提到实践中常见路径：LR/GBDT 快速建基线 → 树模型见顶再上深度模型，并说明为什么
- 主动谈"上限 vs 迭代速度"的取舍，以及特征工程在其中扮演的角色

**减分项：**
- 张口就说"深度学习最好"，给不出适用边界
- 只背"GBDT 特征交叉好"这类结论，说不清什么时候失效
- 不考虑推理时延、模型体积、上线成本
- 不讨论数据量与特征工程投入对选型的约束

**解答：**

选型先看三件事：数据形态、业务约束、迭代速度。数据形态上，如果特征主要是高基数稀疏类别（用户 ID、商品 ID、词 ID），树模型很难直接吃进去，LR/深度模型配合 embedding 更合适；如果特征是稠密统计特征（CTR、点击次数、时长），GBDT 几乎不需要特征工程就能拿到强基线，且对缺失值、量纲、离群点天然鲁棒。业务约束上，在线排序链路往往要求毫秒级推理，深度模型要算 embedding 查表加几层 MLP，量大时还得蒸馏裁剪；树模型 leaf-wise 推理快，但叶子数上万时模型文件几十 MB，也要做量化。迭代速度上，LR 加特征就是调权重，好解释好排查；GBDT 一轮训练几十分钟，迭代快；深度模型训练久、调参空间大，一般留给"树模型效果见顶"之后。实践路径通常是：先用 LR 或 GBDT 建立基线并验证特征有效性，再用树模型的上限判断是否需要深度学习；真要上深度模型，也常用 GBDT 输出做交叉特征喂给 LR/FM（如 GBDT2NN）作为过渡，而不是一步到位。选型不是选"最好的模型"，而是选"当前阶段投入产出比最高的方案"。

**延伸考点：** GBDT 效果遇到瓶颈时，怎么判断瓶颈是特征不足还是模型容量不够？高基数稀疏特征场景，树模型按单特征切分的问题是什么？

### Q2. 特征缺失率 30% 的特征怎么处理？

**问题：** 训练集里一个业务特征缺失 30%，另一个重要特征缺失 5%。你怎么决定填什么、还是留空、还是加缺失标记？不同模型的处理方式一样吗？

**期望加分项：**
- 先区分缺失机制：随机缺失与"缺失本身有业务含义"（如用户没行为导致行为特征为空）
- 能给出量化决策：缺失率阈值、特征重要性、与 label 的相关性决定投入多少功夫
- 说清树模型天然处理缺失（分裂时按增益把缺失样本分到最优侧），线性/深度模型必须填充
- 给出具体填充策略：中位数、分位桶、业务规则值、model-based 填充，以及缺失指示位
- 主动考虑训练与在线推理填充口径必须一致，否则上线即掉点

**减分项：**
- 只背"用均值/中位数填充"，不区分模型类型和缺失机制
- 不知道树模型对缺失的天然处理
- 忽略"缺失本身可能是强信号"（缺失代表没有行为）
- 不考虑在线推理时填充口径一致性

**解答：**

先别急着填。第一步判断缺失机制：随机缺失填充即可；如果"缺失"本身有业务含义——比如用户近 30 天没活跃导致一批行为特征全空——那"空"就是强信号，要显式建模，而不是默默填掉。做法分模型：XGBoost/LightGBM 原生支持缺失，分裂时自动把缺失样本分到增益最大的一侧，可以直接不填；LR/FM/神经网络必须填充，否则矩阵运算做不了。填充策略从简到繁：连续特征用中位数（比均值抗离群点）或分位桶填充；业务特征按业务规则填（如"距上次购买天数"缺失填一个很大的数代表"很久没买"）；高价值特征可做 model-based 填充（用其他特征预测它）。两个坑：一是填充后要加"缺失指示位"或让填充值落入独立分桶，否则填充值被当正常值学习，线性模型尤其吃亏；二是训练和线上的填充口径必须完全一致——线上特征计算要复刻训练时的填充逻辑，否则离线 AUC 高、上线即掉。评估填充方案别只看 AUC，要对比填充前后特征分布，并做线上短期回测。

**延伸考点：** 缺失率 70% 的特征直接丢弃吗？怎么量化它的价值？线上实时特征缺失和离线训练缺失成因不同，怎么统一口径？

### Q3. 千万基数类别特征怎么编码？

**问题：** 商品 ID 有上千万个取值，用户 ID 也是，直接 one-hot 会爆维度。你会怎么做类别编码？树模型和线性/深度模型场景分别怎么选？

**期望加分项：**
- 分清树模型与线性/深度模型的差异：树模型直接 label encode + 派生统计特征，不需要 one-hot
- 线性/深度模型：embedding 或频次截断 + one-hot（低频归入"其他"）
- 能讲到 target encoding 的防泄漏做法：K-fold 内统计、平滑先验、限定时间窗口
- 主动提冷启动：新 ID 没有统计量，需要 prior 兜底
- 考虑编码统计的时效性（只统计过去 N 天，避免未来信息）

**减分项：**
- 只会说 one-hot，不考虑维度爆炸和长尾
- 不知道 target encoding 有泄漏风险，或不知道怎么做防泄漏
- 树模型场景还坚持 one-hot（无效且浪费）
- 不考虑新 ID 出现时在线侧怎么办

**解答：**

分场景：树模型里类别特征直接 label encode 数值化即可，树分裂本来就是按值分组，不需要 one-hot；真正有价值的是给每个类别派生统计特征——近 7 天点击率、次数、均值等，这些比原始 ID 更能帮树模型泛化。线性/深度模型里，高基数特征要么 embedding（低维隐式表示，靠数据量学语义相似），要么截断 + one-hot：按频次排序取 top N（如 1 万），低频归入"其他"，N 要和样本量匹配。最常用也最易踩坑的是 target encoding（用目标均值编码类别）：直接在整个训练集上算均值必然泄漏，正确做法是 K-fold 内统计（本折只用其他折算），并加平滑：enc = (count·mean + prior·m) / (count + m)，prior 取全局均值，m 控制平滑强度。三个坑：一是 target encoding 对噪声标签敏感，标签质量差时编码全是噪声；二是新 ID 在线侧没有统计量，需要用全局 prior 兜底（回退到整体均值）或直接归入"其他"桶，否则在线编码算不出来、特征缺失导致模型失准；三是统计口径的时效性，编码统计只应使用预测时刻之前的数据，且线上编码的统计窗口必须与训练完全一致，防止未来信息泄漏。

**延伸考点：** label encode 后树模型仍可能按无业务含义的中间值切分，怎么判断该类别特征是否真的有效？target encoding 的平滑参数 m 和 K 折数怎么调？

### Q4. 训练集效果很好、验证集效果差，怎么诊断是过拟合还是别的？

**问题：** 你训练的模型在训练集上 AUC 0.92，验证集上只有 0.78。你怎么判断这是过拟合、特征泄漏还是分布差异？排查顺序是什么？

**期望加分项：**
- 先做系统排查：区分过拟合、特征泄漏、训练/验证分布差异（time split vs random split）三种可能
- 能说清验证集按时间切分与随机切分对诊断结论的影响
- 过拟合的量化诊断：训练/验证 gap 随迭代轮数、特征数、模型复杂度的联动曲线
- 用学习曲线区分偏差与方差：偏差问题 vs 方差问题应对手段不同
- 给出过拟合缓解手段的优先级排序：早停、正则、降特征、加数据

**减分项：**
- 只看 gap 就断言"过拟合"，不排除泄漏和分布差异
- 不提验证集切分方式对诊断的影响
- 不知道学习曲线能区分偏差与方差
- 缓解手段只会"加正则"，说不出顺序和为什么

**解答：**

先别急着下"过拟合"的结论。第一步看验证集的切分方式：如果验证集是随机切分，训练样本和验证样本可能来自同一时间段甚至同一用户，模型可能"见过"验证分布，gap 大更可能是泄漏；如果验证集按时间切分、和训练集分布本来就不同，gap 大可能是 covariate shift，要对比两集的特征分布（PSI/KL 散度）确认。第二步看训练集自身的表现：训练集只有 0.85 左右说明是欠拟合或特征不足，逼近 0.95+ 才有过拟合嫌疑。第三步用学习曲线区分偏差和方差：随样本量增加，训练误差和验证误差都下降并收敛到一起，是偏差问题（加特征、加容量）；训练误差低、验证误差高、且加大样本量两者不收敛，是方差问题（加正则、减复杂度）。确认过拟合后按性价比排序缓解：先早停（监控验证集 loss）和加正则（树模型限 max_depth/min_child_weight），再减特征（按特征重要性、相关性筛选），数据层面加噪声或做增强，最后才换更简单的模型。铁律是：任何"训练好验证差"都要先排除泄漏，因为泄漏的修复成本最高，且修完模型往往根本不需要"抗过拟合"手段。

**延伸考点：** 如果验证集和线上效果接近、只有训练集好，说明什么？early stopping 应该在哪个数据集上决定停止点，为什么？

### Q5. 正负样本 1:99，用哪个评估指标？

**问题：** 你们做欺诈检测，正样本（欺诈）只有 1%，模型上线后老板盯着准确率说"模型没用，一直预测正常也有 99% 准确率"。你怎么说服他？用什么指标评估和调优？

**期望加分项：**
- 指出准确率在类别不平衡下失真，改用 AUC / PR-AUC / Recall@K
- 能说清 AUC 与 PR-AUC 的差异：AUC 对类别比例不敏感、PR-AUC 对正样本更敏感，欺诈场景更推荐 PR
- 分层看待：排序能力（AUC）与业务决策（precision/recall 权衡）分开
- 结合业务代价选阈值：FP 与 FN 成本不同，用收益/成本曲线定阈值而非默认 0.5
- 主动谈负采样/加权对指标和概率校准的影响

**减分项：**
- 只会背"不平衡用 F1"，说不清为什么和怎么权衡
- 不区分排序指标与决策指标
- 忽略 FP/FN 的业务代价差异
- 不谈阈值选择，把模型概率当最终决策

**解答：**

准确率在 1% 正样本场景完全失真——全预测"正常"准确率也有 99%，所以第一步是换评估视角：模型能力看排序指标，业务决策看代价。排序层面用 AUC 或 PR-AUC：AUC 衡量正负样本排序能力，对类别比例不敏感，适合粗筛；但 AUC 对"正样本内部排序"不敏感，而欺诈场景真正关心的是"把欺诈尽量捞出来"，PR-AUC 对正样本占比变化更敏感，能反映正样本极稀疏时的召回能力，欺诈/风控场景更推荐 PR-AUC 或直接看 PR 曲线。决策层面，模型概率要结合业务代价定阈值：假设漏掉一笔欺诈损失 1000 元、误拦一个正常用户损失 10 元，沿 PR 曲线滑动阈值、计算每个点上的期望收益 = TP·收益 - FP·成本 - FN·成本，取收益最大点，而不是默认 0.5。调优时注意：做负采样后 AUC 基本不变但概率整体漂移，若要拿概率做阈值决策，要么不做采样，要么对概率校准（isotonic regression 或按采样比例还原）。向老板汇报就讲这个逻辑：模型的价值不是"猜中正常用户"，而是"在同样召回 80% 欺诈的前提下把误拦率从 X 降到 Y"。

**延伸考点：** AUC 和 PR-AUC 什么情况下会给出相反结论？在线按 top-K 截断出警，应该优化什么指标？

### Q6. 特征泄漏的典型案例——你怎么发现？

**问题：** 你接手一个信贷风控模型，训练 AUC 0.93、验证 AUC 0.92，上线后坏账率却没有改善。你怀疑特征泄漏。有哪些典型泄漏场景？怎么系统性排查？

**期望加分项：**
- 列出典型泄漏源：时间窗口越界、目标渗透（label 相关字段入特征）、样本重叠（同一实体跨折）、统计口径穿越
- 给出系统性排查方法：单特征 AUC/相关性审查、特征时间戳与 label 时间对齐检查、时间切分 + 用户去重验证
- 能讲泄漏的根源在数据管线（join 时机、窗口过滤），修复要在管线层
- 主动提泄漏的线上表现特征：离线高、线上无增益
- 考虑泄漏对可解释性报告的误导

**减分项：**
- 只会举"把 label 当特征"一个例子
- 不知道时间窗口越界是工程上最常见的泄漏
- 没有系统排查方法，靠肉眼
- 不谈泄漏对后续特征工程的误导

**解答：**

特征泄漏按工程出现频率排四类：第一是时间窗口越界——特征用了预测时刻之后的信息，比如用"客户是否已还清贷款"的结果统计量喂给放贷决策时的模型，或特征统计窗口覆盖了 label 时点之后的数据，这是工程上最常见的泄漏；第二是目标渗透——label 或 label 的强相关衍生字段直接混进特征，比如用"逾期天数"的字段反推是否违约；第三是样本重叠——同一用户/同一商品的多条样本同时出现在训练和验证集，验证 AUC 虚高，尤其是按行为日志抽样时；第四是统计口径穿越——全量数据算均值/分位数后再切训练验证，统计量里已含验证集信息。排查方法：先算每个特征与 label 的独立 AUC 或相关系数，单特征 AUC 异常高（0.8+）的字段逐个审查；再看特征时间戳分布，确认特征计算窗口严格在 label 定义时刻之前；最后做"时间切分 + 实体去重"后的验证，若 AUC 大幅下跌基本坐实泄漏。修复必须落在数据管线层——特征与 label 的 join 必须是"按时间点回看"，而不是整表 join，并把这条规则写进特征开发规范。泄漏的典型上线表现是离线漂亮、线上毫无增益甚至恶化，因为线上拿不到未来信息，特征全部退化。

**延伸考点：** target encoding 在时间序列样本上应该怎么折？同一用户多行的"去重泄漏"怎么发现？

### Q7. 线上特征分布和训练集不一样（covariate shift），怎么办？

**问题：** 模型上线三个月后，线上请求的特征分布和训练集明显不同——用户群体、渠道都变了。你怎么检测、怎么应对？

**期望加分项：**
- 能说清 covariate shift 的定义与检测手段：PSI / KS / KL 散度，按特征分桶计算
- 区分单特征分布漂移与联合分布漂移（域判别器）
- 应对手段分层：加快重训、特征工程（比值/相对化）、importance weighting、增量学习
- 能区分"无害漂移"与"有害漂移"：用 SHAP 估算漂移特征的输出贡献
- 主动提监控要建在特征分布、预测分布、业务指标三层

**减分项：**
- 只说"重新训练"，不说检测
- 不知道 PSI/KS 等量化指标
- 不区分无害漂移和有害漂移，见漂移就重训
- 忽略漂移与业务周期（季节性）的关联

**解答：**

先检测再应对。检测分两层：单特征层面用 PSI（群体稳定性指数）或 KS 检验对比"线上滚动窗口分布 vs 训练集分布"。PSI 按特征分桶计算：PSI = Σ(实际占比 - 期望占比)·ln(实际占比/期望占比)，经验阈值 PSI < 0.1 稳定、0.1~0.25 需关注、>0.25 显著漂移。联合分布层面用域判别器：训练一个分类器区分"训练样本 vs 线上样本"，判别 AUC 越高说明两域差异越大。检测出漂移后先判断"有害还是无害"：有些特征漂移对模型输出影响很小（如低频 ID 特征），用 SHAP 估算漂移特征对输出方差的贡献，按贡献排序决定处理优先级。应对按成本从低到高：先加快重训频率；再做特征工程——把绝对值特征改成比值/相对量（"距上次行为的天数"比"绝对时间戳"抗漂移）；若漂移源于样本选择偏差，用 importance weighting：w = P_online(x)/P_train(x)，密度比可以用域判别器的输出 odds 估计；最后才是模型层面（分布鲁棒训练、增量学习）。工程上监控一定做三层：特征分布（PSI）、预测分布（预测值直方图）、业务指标（CTR/坏账率），三层对照才能定位漂移源头——比如预测分布没变但业务变了，是概念漂移不是数据漂移。

**延伸考点：** concept drift 和 covariate shift 的应对方式有何不同？重训后效果仍差，怎么判断是数据问题还是模型问题？

### Q8. 时序数据怎么切训练/验证集才不会"偷看未来"？

**问题：** 你们做预测模型，数据是每天的日志。组里有人直接随机切分了训练集和验证集，离线 AUC 0.87，上线后一塌糊涂。问题出在哪？时序场景该怎么切分？

**期望加分项：**
- 指出随机切分的"未来泄漏"：验证集含预测时刻之后的样本，模型见过未来
- 给出正确切分：按"预测时刻"定义样本归属、训练时间在验证之前、按实体去重
- 进阶评估：walk-forward / rolling origin，比单次切分更稳
- 主动提特征层的时间窗口：统计特征只回看不前瞻
- 说明时间切分牺牲的样本量与评估稳定性的权衡

**减分项：**
- 不知道随机切分对时序数据的致命问题
- 只切分样本，不注意特征统计窗口用了未来数据
- 不考虑实体（用户/商品）跨折重复
- 不知道 walk-forward 或 rolling origin

**解答：**

随机切分在时序场景必死，问题在两个层面。样本层面：验证集里混着时间靠后的样本，模型在训练时"见过"了这些样本对应时间的未来信息——AUC 高是"背答案"，上线后没有未来数据可看，自然崩塌。正确做法：**按"预测时刻"给每个样本打时间戳，训练集时间严格早于验证集**，例如用 1~30 天训练、31~37 天验证；预测的"标签"（如未来 7 天是否转化）也要在训练与验证里保持同样的滞后窗口。第二层是特征泄漏：统计特征（"用户近 7 天点击率"）如果在构造时用了验证期乃至全量的数据，即使样本按时间切对了，特征仍然在偷看未来——统计窗口必须截止到样本的预测时刻之前。进阶做法是 walk-forward（滚动前向验证）：用 [t0,t1) 训练预测 t1~t2，再滑动 origin 重复多次，最后对多段验证结果求平均，比单次切分更能反映"模型在任意时刻上线的表现"；rolling origin 则保持训练窗长度不变、只滚动验证窗。三个实践坑：一是实体（用户/商品）会跨折重复，同一用户的训练样本和验证样本会泄漏其行为模式，必要时按实体分折；二是时间切分牺牲了样本量与评估稳定性（数据越靠近今天越少），要在"评估可靠"与"样本量"间取平衡；三是线上推理的特征窗口与离线完全一致，否则离线没问题、上线仍然掉点。给出结论时带上量化：随机切分 AUC 0.87 vs 时间切分 AUC 0.76，后者才是真实水平。

**延伸考点：** walk-forward 里"origin"滑动的步长怎么选，与预测时效（日频/周频）的关系？特征统计窗口用"截止到样本日"和"截止到验证期固定某天"，评估结果差多少，哪个更接近线上？

### Q9. 离线 AUC 0.9、线上点击率预估却掉点，怎么排查"离线在线不一致"？

**问题：** 排序模型离线验证 AUC 0.90，AB 实验里线上 CTR 却不升反降。候选人要给出排查清单：特征层面、数据层面、训练/推理层面分别可能出什么问题？

**期望加分项：**
- 先列大类：特征不一致（线上拿不到离线用的特征/口径不同）、样本不一致（线上遇到训练没见过的分布）、训练推理不一致（特征值截断/归一化参数不共用）、时延差异（线上特征在请求时点之后才到）
- 能讲典型坑：离线特征用"回填"（未来信息），线上只能用"当时可得"；缓存命中与重算特征不同步
- 会给验证手段：抽样线上请求重放离线推理（离线在线一致性对比）、特征分布漂移检测（PSI）、构造"只包含线上可达特征"的离线验证集
- 能谈"离线好不代表线上好"的归因逻辑：AUC 评估的是排序正确率，CTR 绝对水平受校准/选择偏差影响
- 会提出治理方案：特征平台统一口径（同一天生成离线/在线特征）、监控特征覆盖率与取值分布、上线前回放测试

**减分项：**
- 只会说"模型过拟合了"，不做系统性排查
- 不知道 PSI/特征漂移这类量化手段
- 忽略"未来信息"在离线特征里的存在
- 不区分 AUC（相对序）与 CTR（绝对量）的评估差异
- 没有重放/回放验证的落地手段

**解答：**
离线在线不一致是最常见的"翻车"原因，按四层排查。第一层特征层：离线特征常用"回填"方式构造（比如标签是 7 天后转化，特征里却用到了当天之后的统计），线上推理时这些值根本拿不到——用默认值/旧值顶替，模型就"变形"了；还有口径差异：离线"近 7 天点击次数"按事件日志聚合，线上按缓存/近实时计算，统计窗口或去重口径不同。第二层样本层：线上真实流量的分布（新用户比例、商品上新比例）与离线训练集不同，模型对未见分布外推错误。第三层训练推理层：归一化参数（min/max、mean/std）、分箱边界、特征截断阈值是训练时算好的，推理服务如果没加载同一份参数就出现偏差；特征缺失时离线填充"均值"、线上填"0"，也会偏离。第四层时延层：线上特征计算有延迟（比如点击后 1 秒才算出来），排序时用的还是旧值。给出一套可落地的排查动作：① 抽样线上真实请求，用线上可得的特征重新离线推理，对比与线上打分一致率（一致性回放）；② 对每个特征做分布漂移检测（PSI > 0.2 视为显著漂移），重点盯高重要度特征；③ 构造"线上特征可行性约束"的离线训练集——只允许使用预测时刻之前可得的信息，重新评估；④ 区分评估维度：AUC 衡量序、与 CTR 绝对水平无关，线上掉点可能是校准问题（得分分布偏移）而非排序能力下降。治理的根本是特征平台统一：同一套特征定义同时产出离线与在线特征，带上版本号与生成时间，监控覆盖率与取值分布；上线前做回放测试，对比"离线评分 vs 线上评分"的一致性。

**延伸考点：** 怎么设计一个"回放测试"的具体流程（从线上日志抽样到重放打分）？特征 PSI 高了之后，是重训还是特征排查优先，判断依据是什么？

### Q10. 训练一个分类模型，正样本只有 0.1%，负采样比例怎么定？

**问题：** 广告点击率/支付转化类模型，正样本比例 0.1%（1000 个样本里 1 个正例）。直接训练有什么问题？负采样该采多少比例？采样后预测分数怎么校准回真实概率？

**期望加分项：**
- 能说清极端不平衡的问题：模型退化为"全预测负类"、AUC 虚高但实际召回极低、正类梯度被淹没
- 负采样思路：随机负采样把正负比调到 1:1 或 1:10 区间（视模型与数据），保证训练效率与梯度信号
- 校准公式：采样后预测概率 p'，真实概率 p = p' / (p' + (1-p')/w)，w 为采样率（或更严谨用 p = w·p'/(1-p'+w·p')）
- 能讲替代方案：不采样直接用全部负样本但加类权重（class_weight）、或 focal loss 聚焦难分正样本
- 会做验证：采样后 AUC 变化不大、但校准后的预测分数要贴合真实 CTR，用 logloss/校准曲线验证
- 联系线上：线上打分必须用校准后的概率，否则按阈值截断会错

**减分项：**
- 只会说"正负样本不平衡就采样"，说不清采样比例依据
- 不知道采样后概率要校准回去（直接拿采样模型的概率当真实概率用）
- 分不清 AUC（对采样不敏感）与概率校准（对采样敏感）的关系
- 不知道 class_weight / focal loss 等替代方案
- 不考虑采样对特征统计（如类别特征占比）的影响

**解答：**
正负比 1:1000 时直接训练有两个问题：一是梯度信号被淹没，模型倾向把所有样本判为负类（loss 里 99.9% 是负类贡献）；二是评估失真——模型"全部判负"也能拿 99.9% 准确率，AUC 可能很高但毫无业务价值。主流解法是负采样：把负样本按比例 w 随机采样（如 1:10），训练集变成正负均衡，模型能学到正类特征。采样比例的选择：不是越均衡越好——1:1 会让模型对正类过拟合、且丢失大量负类分布信息；工程经验常取正负比 1:5~1:20 之间，通过验证集 AUC/logloss 网格搜索确定。关键坑是**概率校准**：模型在采样后的数据上学到的输出 p' 是"采样空间"里的概率，要还原为真实空间概率 p，公式为 p = (w·p') / (1 - p' + w·p')（w 为负样本采样率）。不校准的后果：线上用原始阈值（如 0.5）切，预测分数整体偏高，判定结果全部错乱。替代方案要能提：不采样 + class_weight 给正类加权（等价于隐式采样，无需校准但要小心权重过大过拟合）；focal loss 让模型聚焦难分样本（正负极端不平衡时比加权更稳）。评估注意：AUC 对正负采样比例不敏感（序不变），所以用 AUC 看排序能力没问题；但 logloss/校准曲线对采样敏感，必须在校准后评估。实践中还有一个坑：负采样后特征统计（如类别特征的频率占比）变了，树模型的类别分裂会偏，重要特征统计类特征要保留采样前分布或在特征构造时按全量计算。

**延伸考点：** 正负比 1:1000 且正样本极少（只有几千条）时，采样、加权、focal loss 怎么选？校准公式的推导假设是什么，线上打分的最终概率和阈值怎么定？

### Q11. 模型上线后发现线上特征分布和训练时不一样（covariate shift），怎么办？

**问题：** 线上监测发现某个高权重特征的分布和训练集差很多（比如"商品价格"整体上移）。候选人要判断：这是数据漂移吗、会影响模型吗、怎么检测、怎么处理？

**期望加分项：**
- 能定义 covariate shift：输入特征分布 P(X) 变了，但条件分布 P(Y|X) 理论上不变——模型"没见过"这种输入分布
- 检测手段：特征分布对比（KS 检验/PSI）、监控特征均值/分位数/缺失率随时间变化
- 影响判断：高重要度特征漂移影响大；低重要度特征漂移可忽略；先看特征重要性排序再决定
- 处理手段：短期——监控告警、上线兜底（模型降级/用历史分布截断异常值）；长期——重训/增量更新模型、或做 domain adaptation
- 能讨论"漂移不等于模型失效"：如果漂移的方向与业务一致（涨价导致价格整体上移），模型的分位特征仍有效
- 会建立监控体系：离线检测特征 PSI，在线检测特征覆盖率、业务指标异常

**减分项：**
- 只检测分布不同，不判断"影响多大、要不要处理"
- 拿所有特征一刀切处理，不按重要性排序
- 只会说"重新训练"，没有短期止血手段
- 不区分数据漂移（特征）与概念漂移（P(Y|X) 变了）——后者重训也未必有用
- 没有监控告警体系，事后才发现

**解答：**
第一步先确认是哪种漂移：covariate shift 指输入特征 P(X) 变化、条件关系 P(Y|X) 不变——模型遇到没见过的输入分布，外推能力不足；概念漂移（concept drift）指 P(Y|X) 本身变了（比如用户行为习惯变了），后者更严重，重训需要新标签、甚至重新建模。检测手段用数据说话：对每个特征算训练集与线上近期分布的差异——连续特征用 KS 检验或 PSI（PSI > 0.2 显著），类别特征用卡方/频率差；同时监控均值、分位数、缺失率、极端值比例的时间曲线。第二步判断影响：不是所有漂移都要处理——**先看特征重要性排序**，高重要度特征（如价格、用户活跃度）漂移必须处理，低重要度或派生冗余特征漂移可降级处理；还要结合业务方向判断，如果漂移是业务策略调整导致（涨价 → 价格上移），模型里价格特征的分位编码仍能正常使用，可能无需干预。第三步处理分短期与长期：短期止血——监控告警（PSI 超阈值自动告警）、对异常分布做截断/标准化兜底、必要时灰度回退旧模型；长期——**重新训练**（用近期数据覆盖新分布）、增量更新（在线学习/每日重训）、特征工程适配（把绝对价格改为相对分位/价格带）；概念漂移则需要换标签、重构训练样本甚至换模型。最后要建立体系：离线侧定期计算特征 PSI、在线侧监控特征覆盖率与业务指标（CTR/转化率）联动告警，漂移检测不是一次性的，而是模型健康度的日常体检。

**延伸考点：** PSI 的计算方法（按分位分桶后算分布差异）与阈值 0.1/0.2 的依据？如果漂移来自"数据回流延迟"（线上特征暂时缺失用默认值填充），怎么和真实漂移区分？

### Q12. 一个新业务/新用户没有任何行为数据，模型怎么给"冷启动"用户做推荐或排序？

**问题：** 电商新用户没有点击/购买历史，模型特征几乎全为空或默认值，推荐却要给出结果。候选人要设计一套冷启动方案：特征层面、模型层面、产品层面分别做什么？

**期望加分项：**
- 特征层面：冷启动用户用"群体画像"填充（同设备/同地域/同注册来源用户的热门行为）、人口统计特征、非行为特征（注册时间、设备类型）；新商品同理用类目均值
- 模型层面：把"用户行为深度"作为特征显式建模（模型学习到行为少时置信度低）、用多臂老虎机/探索策略在线探索、或两阶段（热门兜底 + 个性化）
- 能讲探索-利用（exploration-exploitation）权衡：初期多探索、积累数据后收敛到利用；epsilon-greedy、UCB、汤普森采样
- 产品层面：冷启动期用热门/新品/编辑推荐兜底，做新人引导交互引导用户产生行为
- 会评估：冷启动期的指标（探索点击率 vs 老用户点击率）分开看，别用同一阈值
- 能讨论"冷启动填充的置信度"：填充特征要带可信度标记，避免把猜测当事实

**减分项：**
- 只会说"给热门推荐"，没有分层设计
- 不知道 exploration-exploitation 权衡或具体算法
- 填充特征不带置信度，模型把噪声当真
- 不分用户/商品冷启动两个维度
- 冷启动期用老用户同一套评估标准

**解答：**
冷启动的本质是"数据稀疏下的决策"，要分层解决。特征层面：没有个性化行为，就用**群体代理特征**——同地域/同设备/同注册渠道/同年龄段的用户群体行为（该群体点击率最高的商品）、商品类目均值、以及非行为特征（注册时间、设备型号、注册来源）；关键技巧是这些填充特征要带**置信度/深度标记**（如"行为深度=0"、"填充来源=群体"），让模型学到"这个用户的个性化信号不足"而非把填充值当真实行为，否则模型会对噪声过拟合。模型层面：显式建模"用户行为量"——把行为深度作为特征，模型自然学到行为少的用户应回归到群体偏好；更主动的方案是**在线探索（exploration）**：冷启动期用多臂老虎机（UCB/汤普森采样）在候选池里探索，按"当前收益 + 不确定性"选择，积累点击数据后不确定性下降、自动收敛到利用（exploitation），这比纯热门推荐更早地抓到用户真实偏好；实践中常做"热门兜底 + 分桶探索"的混合策略。产品层面：新用户落地页用热门/新品/编辑推荐 + 引导交互（兴趣标签选择、关注引导）加速数据积累。评估要分层：冷启动期（前 N 次曝光）看"探索有效性"（探索点击率、探索-利用收益差），不要用老用户的 CTR 阈值一刀切；老用户才看个性化提升率。还有一个容易忽略的点：冷启动不只用户侧，**商品冷启动**同样存在（新品无点击），对称地用类目/相似商品特征填充 + 探索曝光。完整回答的结构是：特征填充（带置信度）→ 模型自适应（深度特征/探索策略）→ 产品兜底（热门/引导）→ 分层评估。

**延伸考点：** epsilon-greedy、UCB、汤普森采样三者在"探索分配"上的差异和适用场景？给冷启动用户填充"同地域群体热门"特征时，怎么避免"推荐结果趋同"（所有人拿一样的列表）？

### Q13. 老板要求"模型可解释"，业务方还要"上线前给理由"，候选人怎么做可解释性与规则协同？

**问题：** 风控/审核场景，监管或业务要求每条拒绝/命中都要有可解释的理由；而模型是 GBDT 这类黑盒。候选人要设计：模型内解释（特征重要性）、模型外解释（局部可解释）、以及与规则系统协同的分层架构。

**期望加分项：**
- 分层解释框架：全局解释（特征重要性、SHAP 汇总图）回答"模型整体靠什么"；局部解释（SHAP 单样本、LIME）回答"这条样本为什么被拒"
- SHAP 原理直觉：每个特征对预测的贡献（Shapley 值的近似），可解释且满足一致性（加性可解释）
- 能谈"可解释性与准确率"的取舍：风控可用"规则锁定红线 + 模型辅助打分"分层，红线规则可解释、模型分数做微调
- 落地：拒绝原因给出"命中规则 X + 关键特征贡献"模板；解释要面向业务可读（自然语言），不是给特征名
- 能讲黑盒+解释的局限：SHAP 是近似、对相关特征会分摊贡献；局部解释不稳定
- 会设计解释的验证：业务专家抽查解释合理性、解释一致性（相似样本相似解释）

**减分项：**
- 只会说"用 SHAP"，不理解它是局部还是全局、口径是什么
- 把特征重要性（全局）当"这条样本为什么被拒"（局部）的答案
- 不讨论规则与模型的分层协同
- 解释输出面向机器不面向业务（只给特征名不给结论）
- 不知道可解释性方案的局限与验证

**解答：**
先分清两类解释需求：全局解释回答"模型整体依赖什么"，局部解释回答"这一条样本为什么是 1"。全局：特征重要性（permutation importance、gain importance）给出排序；SHAP 汇总图（beeswarm）能看每个特征在不同取值下的正负贡献方向，比单值重要性信息量大。局部：**SHAP 值**基于 Shapley 值近似——对单条样本，每个特征分到一个"对预测结果的贡献"（正值推动向 1、负值推向 0），全部特征贡献 + 基线值 = 预测概率，加性且满足一致性（贡献总和等于预测），这是它比 LIME 更受欢迎的原因（LIME 用局部线性近似，不稳定且依赖采样）。落地到"拒绝理由"：把解释翻译成业务语言——命中规则（如"该设备近 1 小时请求次数超阈值"）+ 关键特征贡献（如"负债率特征贡献 -0.3，是最强拒绝因素"），模板化输出，而不是丢特征名给业务。**规则与模型的协同架构**是工程重点：分层设计——第一层"红线规则"（监管硬性要求、确定性规则，如涉黑名单直接拒绝）全可解释、优先级最高；第二层模型打分（GBDT 抓复杂模式）给出风险分；两层综合（如"规则否决 + 模型分微调"）输出最终决定与理由。这样既保住准确率又保住可解释性。要说清局限：SHAP 对强相关特征会分摊贡献（解释可能误导）、小样本上局部解释不稳定、解释是"对模型的解释"而非"对真实因果的解释"；要有验证环节：业务专家抽样评审解释合理性、检查相似样本的解释一致性、监控解释稳定性（同一样本多次解释差异小）。

**延伸考点：** SHAP 里"特征 A 与 B 高度相关"时贡献如何被分摊，解释结论怎么避免误导？规则系统与模型的权重（规则优先还是模型优先）在风控场景怎么定，冲突时以谁为准？

### Q14. 模型要同时优化转化率和客单价，还有平台生态约束，多目标怎么建模？

**问题：** 电商排序要同时提升点击率、转化率、GMV，三个目标可能互相冲突（低价高转化但 GMV 低）。候选人要给出多目标建模方案：损失函数层面、评估层面、线上策略层面分别怎么处理？

**期望加分项：**
- 能说多目标三个层面：训练（多任务学习/加权损失）、评估（分层看单一指标 + 综合指标）、线上（权重/规则调节）
- 训练层面：多任务学习（shared-bottom/MMoE 共享底层、各任务独立输出头）、加权损失（不同目标不同权重）
- 评估层面：别只看综合分，分层看 CTR/转化/GMV 各自的增益；用"帕累托最优"思维——一个目标提升不以另一个大幅恶化为代价
- 线上策略：权重随业务阶段调节（拉新期重转化、大促期重 GMV）、约束型优化（在转化率不低于阈值的约束下最大化 GMV）
- 能讲业务冲突：低价商品转化高但 GMV 低，多目标本质是业务权衡，不是纯算法问题
- 会落地：MMoE/ple 这类结构的动机是任务间共享与门控分离，比简单加权损失更适合任务冲突大时

**减分项：**
- 只会"把损失加起来"，不理解权重含义与调参
- 不看分层指标，只盯一个综合分（掩盖目标间冲突）
- 不知道多任务学习的结构（shared-bottom/MMoE）与适用边界
- 不谈业务权衡，把多目标当纯数学问题
- 线上调节没有监控单个目标是否被牺牲

**解答：**
多目标排序要拆成三个层面处理，缺一不可。**训练层面**：最简单是加权损失（loss = w1·ctr + w2·cvr + w3·gmv_loss），但简单加权有两个问题——权重难调、任务相关性差时互相干扰。更工程化的是多任务学习结构：shared-bottom 共享底层特征表示、各任务独立输出头，适合任务相关性高的场景；任务冲突大时用 **MMoE**（多个专家网络 + 门控，每个任务学自己的专家组合权重）或 PLE（渐进分层专家），让不同任务选择性利用共享表示——这是推荐/广告工业界的标准解法。还要注意样本定义：点击、转化、GMV 三个任务的标签粒度不同（曝光→点击→下单→支付），样本复用时别把"未点击"样本硬算进转化任务。**评估层面**：不能只盯一个综合分——分层看 CTR、CVR、GMV 各自的提升/下降（如 A/B 里 CTR +5%、GMV -2%，综合分可能掩盖 GMV 的损失）；用帕累托视角：判断模型是否"一个目标提升且没有显著恶化另一个"，恶化超阈值要触发回归审查。**线上策略层面**：权重不是训练时定死就完，要随业务阶段调节——拉新期重转化率、大促期重 GMV，权重从配置中心下发可调；更精细的是约束型优化：在"转化率不低于当前水平"的约束下最大化 GMV（拉格朗日或阈值约束实现）。最后要点破本质：CTR/CVR/GMV 冲突（低价商品转化高、GMV 低）是**业务权衡**而非纯算法问题，多目标建模只是把权衡显式化；落地时要和业务对齐优先级与可牺牲幅度，设定每个目标的"底线监控"。

**延伸考点：** MMoE 的"门控"在训练时如何避免退化为单一任务（所有专家权重趋同）？多目标评估里"综合分"用什么公式（加权归一化/几何平均）比较合理？

### Q15. 训练数据里 5% 的标签是错的，模型会怎样？候选人怎么检测与治理噪声标签？

**问题：** 运营手工打标的数据里有约 5% 标签错误（比如把"不感兴趣"标成"感兴趣"）。候选人要说明：噪声标签对模型的影响路径、怎么检测、怎么在训练中缓解？

**期望加分项：**
- 影响路径：模型被迫拟合错误标签→过拟合噪声、正负边界被污染；样本量足够时模型对随机噪声有一定鲁棒性，但系统性噪声（某类样本总标错）危害大
- 检测方法：训练中看样本损失（高损失常是噪声/难例）、交叉验证中预测与标签不一致的样本、置信度阈值、Noisy Label 专用方法（置信学习 confidence learning）
- 缓解：删除/降权疑似噪声样本、标签修正（用模型预测替代）、对噪声鲁棒的损失（对称交叉熵、Truncated loss）、样本清洗后重训
- 区分"噪声样本"与"难样本"：难样本（边界附近）损失也高但不该删，删了伤信息
- 会评估：清洗前后模型在干净验证集上的表现差异，别用清洗后的训练集自评
- 预防：标注流程优化（多人标注一致性、质检抽查）、打标指南明确边界

**减分项：**
- 不知道噪声标签的系统性危害，以为模型自动免疫
- 把"高损失样本"一律当噪声删掉（误删难样本）
- 清洗后拿训练集验证（自欺欺人，应该用干净的外部验证集）
- 不区分随机噪声与系统性噪声的处理差异
- 不讨论预防（标注流程）

**解答：**
5% 随机噪声通常不会让模型崩掉（样本量大时梯度被平均），但有两个前提：噪声是随机的（错误方向对称）、样本量足够。真正的危险是**系统性噪声**——某类样本总是被标错（比如某个商品类目运营倾向标"感兴趣"），模型学到的是错误模式而非真实规律，且难以通过常规手段发现。检测思路分两类：**训练过程中**——高训练损失的样本最可能是噪声或难例（要区分：难例在边界附近、损失高但信息有价值；噪声则与大部分同类样本规律相悖）；用交叉验证或 bagging 预测样本，对比"模型预测 vs 人工标签"一致性，不一致的列入候选；**统计方法**——置信学习（confidence learning）用"预测分布 + 标签"构造噪声转移矩阵，估计每个标签被标错的概率，可以给出"某个样本标签为 X 的概率"。治理分三步：清洗（删除置信度低于阈值的疑似噪声、或修正标签）、重训、**在干净的外部验证集上对比前后效果**（这是最容易错的一步——用清洗后的训练集自评是作弊，必须用独立标注的验证集）。对噪声鲁棒的训练技巧：降权疑似噪声样本、或用鲁棒损失（对称交叉熵、广义交叉熵）让模型对错标不敏感；主动学习思路也可以：把不确定样本送人工二次审核。系统性噪声的识别技巧：按子群（类目/渠道）统计"模型预测与标签的一致率"，某子群异常低说明该子群的标签/特征分布有问题。最后一定要提预防：标注 SOP（打标指南明确边界案例）、多人标注 + 一致性校验（Kappa）、定期质检抽检——噪声治理的根子在标注流程，模型侧只是止损。

**延伸考点：** "高损失样本 = 噪声"与"高损失样本 = 难例"怎么用数据区分（如看同子群损失分布）？标签噪声是"系统性的"（某类总标错）时，置信学习为什么比简单阈值法有效？

### Q16. 模型推理太慢/太大，线上延迟不够，怎么压缩与加速？

**问题：** 排序模型上线后单次推理 30ms 超标（要求 <5ms），模型文件 500MB（GBDT 叶子太多）。候选人要给出推理加速手段：模型结构层、推理框架层、服务层分别做什么？

**期望加分项：**
- 结构层：模型剪枝（去掉低重要度特征/树叶子）、量化（float32→int8/float16，精度损失可控）、蒸馏（大模型→小模型）、特征裁剪（删低重要度特征重训）
- 推理层：用优化推理框架（ONNX Runtime/TensorRT/OpenVINO）、batch 推理、线程优化
- 服务层：缓存（特征/结果缓存）、特征提前计算（预计算 embedding 查表）、并行/异步、模型分片或层级缓存（粗筛→精排两阶段）
- 能讲量化细节：后训练量化 vs 量化感知训练（QAT）的精度差异；GBDT 用 int8 量化空间有限但叶子剪枝有效
- 会算账：延迟/吞吐/精度/内存的权衡，量化掉的精度换来的延迟收益要量化
- 能先定位瓶颈：profile 是特征计算慢还是模型计算慢还是序列化慢

**减分项：**
- 只会说"换更快的机器"
- 量化/蒸馏不讲精度损失评估
- 不知道先 profile 定位瓶颈（可能瓶颈在特征而非模型）
- 一刀切用最激进的压缩（精度崩了没兜底）
- 不做离线延迟回归测试

**解答：**
先 profile 再动手：30ms 里可能是特征计算（SQL/Redis/embedding 查表）占了 25ms，模型只占 5ms——那优化方向是特征缓存与并行拉取，而不是压缩模型。确认瓶颈在模型后，按三层优化。**模型结构层**：一是特征裁剪——用特征重要性把 Top 100 特征裁到 Top 30 重训，常常精度只掉 0.1%~0.3% 但叶子数大降，GBDT 场景性价比最高；二是剪枝——GBDT 去掉贡献小的子树/叶子（叶子合并）、DNN 剪掉低权重通道；三是量化——float32 → int8 模型体积缩小 4 倍、推理提速 2~4 倍；int8 量化精度损失通常在可接受范围（0.1~0.5% AUC），但要注意激活值的分布（用校准集定 scale），必要时用 QAT（量化感知训练）把量化误差纳入训练，把精度损失压到最低；四是蒸馏——大模型（老师）的 soft label 训练小模型（学生），学生能逼近老师精度但体积小一个量级，适合"离线大模型 → 线上小模型"。**推理框架层**：ONNX Runtime/TensorRT（GPU）/OpenVINO（CPU）做算子融合与图优化，通常比原始框架（XGBoost 原生/scikit）快 1.5~3 倍；batch 推理摊薄框架开销。**服务层**：结果缓存（相同请求特征命中直接返回）、特征预计算（把高频 embedding/统计特征提前算好放缓存）、两阶段排序（粗排用轻模型过滤到 Top 200、精排用全量模型）——这是推荐系统"粗排→精排"的标准架构，把精排调用量降一个量级。最后强调度量与兜底：每次优化都要做"离线延迟 + 精度回归"双测试，量化前后对比 AUC 与 p99 延迟，确保收益可量化；保留快速回退通道（配置开关切回原模型）。

**延伸考点：** GBDT 和 DNN 在量化/剪枝上的收益差异（哪个更吃量化红利，为什么）？"粗排→精排"两阶段里，粗排模型的精度和延迟怎么权衡，误杀优质候选的代价怎么控制？

### Q17. 超参调优在团队里怎么工程化？从网格搜索到贝叶斯再到线上验证。

**问题：** GBDT 模型有 max_depth、learning_rate、n_estimators、min_child_weight 等一堆超参。候选人要讲：网格搜索/随机搜索/贝叶斯优化的适用场景、调参的评估协议（防过拟合验证）、以及"调参收益 vs 特征/数据收益"的工程判断。

**期望加分项：**
- 能讲三种方法：网格搜索（低维穷举，高维爆炸）、随机搜索（高维更优，论文论证）、贝叶斯优化（用代理模型找下一点，样本效率高，适合单次训练贵的场景）
- 评估协议：调参要用验证集/交叉验证选超参，最终效果用独立测试集评估，避免"调参过拟合"
- 能讲 GBDT 关键参数敏感性：learning_rate（越小越稳但训练越久，与 n_estimators 联动）、max_depth 控制复杂度、min_child_weight 抗过拟合
- 工程化：早停（early stopping）用验证集控制迭代次数、参数组合用配置化+实验记录（MLflow）、多轮搜索锁定后再微调
- 判断：特征/数据质量带来的提升通常远大于调参；"先特征后调参"，调参只吃最后几个点的收益
- 会做时间预算：一次训练 1 小时，网格 100 组 = 100 小时，贝叶斯能省一个量级

**减分项：**
- 只会"写个循环网格搜索"，不懂高维代价
- 调参用同一份数据反复看结果（过拟合验证集）
- 不知道 early stopping 与 learning_rate 的联动
- 把大量时间花在调参上而忽略特征工程
- 没有实验记录（改了哪个参数、结果如何无从追溯）

**解答：**
先说工程判断：**调参是"最后几个点"的收益**——特征质量、数据量、模型结构的提升通常远大于超参微调，所以正确顺序是"特征 → 数据 → 模型结构 → 调参"，调参放在最后收尾，避免在错误基线上浪费时间。三种搜索方法的选型：网格搜索适合 1~2 个参数且取值离散（如 max_depth 3/5/7），超过 4 个维度组合爆炸；随机搜索在高维空间里比网格更高效（随机覆盖比均匀网格更快命中好区域，Bergstra 论文有证明）；**贝叶斯优化**用高斯过程/TPE 做代理模型，根据已评估点预测下一组值得试的参数，样本效率最高，适合"单次训练贵（分钟~小时级）"的场景（如深度模型），GBDT 训练快、随机搜索+早停通常就够。评估协议是防"调参过拟合"的关键：调参过程只碰训练/验证集（用验证集选最优组合、可配交叉验证提升稳健性），**最终效果必须用从未参与调参的独立测试集**评估；同时每次实验记录参数与指标（MLflow/WandB），否则无法追溯"哪个参数起了作用"。GBDT 参数联动要讲清：learning_rate 越小精度越高但需要更多 n_estimators，两者通常配对调（先固定一个）；early stopping 用验证集在验证损失不再下降时停止迭代，直接省掉"估 n_estimators"；max_depth 控制树复杂度、min_child_weight 控制叶子最小样本量，共同抗过拟合。实践流程：粗搜（随机搜索/贝叶斯先定数量级）→ 精调（在粗搜最优附近做局部网格/贝叶斯）→ 早停兜底 → 锁定参数用全量数据重训 → 独立测试集出最终报告。最后再次强调：调参结束的标准不是"验证集最好"，而是"与基线比有统计显著的提升"。

**延伸考点：** 贝叶斯优化的"探索 vs 利用"与前面冷启动的 exploration 有什么共通与不同？early stopping 在"验证集噪声大"时容易早停过早，怎么缓解（更平滑的停止准则）？

### Q18. 特征版本、模型版本、数据版本怎么对齐管理？模型上线回滚怎么保证可追溯？

**问题：** 线上模型出问题了要回滚，但回滚后特征和训练时对不上，问题依旧。候选人要设计一套"特征-模型-数据"的版本治理体系：版本怎么记录、怎么保证线上回滚一致性、怎么快速定位问题版本。

**期望加分项：**
- 能指出核心：回滚不是"换模型文件"，而是"特征版本 + 模型版本 + 数据版本 + 代码版本"四件套一起回滚，只回滚一个必然出问题
- 版本记录：特征库版本号（特征定义/计算逻辑 hash）、模型产物带元数据（训练数据版本、特征版本、超参、commit hash）、线上配置指向明确版本组合
- 实现：特征平台（特征注册 + 版本化）、模型注册表（MLflow/模型仓库）、配置中心下发版本组合
- 回滚流程：配置中心一键切换到旧版本组合；回滚后先小流量验证再放量
- 问题定位：异常指标按版本组合回溯（哪个版本引入）、模型线上/离线一致性格差监控
- 预防：上线前"版本组合"完整性校验、灰度发布、AB 对照

**减分项：**
- 只回滚模型文件，不知道特征版本也要回滚
- 版本号不关联（特征版本和模型版本各管各的，对不上）
- 没有配置中心/注册表，靠人肉记忆版本
- 回滚不经过灰度验证直接全量
- 版本记录里没有数据版本（训练数据变过导致模型退化说不清）

**解答：**
线上模型可追溯的本质是"**版本四件套**"：特征版本（特征定义与计算逻辑）、模型版本（产物与训练配置）、数据版本（训练样本集）、代码版本（训练/推理代码），任一单独回滚都会错位——比如只回滚模型到旧版，但特征平台已升级、新特征字段缺失，旧模型推理直接报错或静默填默认值。设计三层落地：**特征平台**——特征注册中心，每个特征带版本号与计算逻辑 hash，离线/在线特征同源生成，变更走版本升级而非覆盖；**模型注册表**（MLflow / 自建模型仓库）——每次训练记录：训练数据版本、特征版本、超参、代码 commit、评估指标，模型产物打标签；**配置中心**——线上服务加载"版本组合配置"（feature_version + model_version + data_version + code_version），切换即回滚四件套。回滚流程：配置中心一键切到上一个已验证的组合 → **先灰度小流量**（如 5%）观察业务指标无异常 → 逐步放量；回滚不是目的，定位才是——通过版本组合回溯：监控异常开始时间，对照"哪个版本组合在那时上线"，结合指标变化定位引入问题的环节（特征 bug / 数据坏 / 模型退化 / 代码改动）。预防与治理：上线前做版本组合完整性校验（配置里引用的版本必须在注册表存在）、灰度 + AB 对照是常态流程、建立"模型健康度监控"（线上特征覆盖、评分分布、业务指标基线偏离自动告警）。一句话总结：**可回滚 = 可追溯 = 每个线上模型都有一份完整的版本族谱**，回滚按钮按下时，切换的是整个族谱而不是一个文件。

**延伸考点：** 特征"计算逻辑变更但没升级版本号"会怎样（线上静默错误）？模型健康度监控里的"评分分布偏移"和特征 PSI 有什么关系，怎么联合判断该回滚还是该重训？

### Q19. 树模型（GBDT）和深度模型在"表格数据"场景怎么选？为什么表格数据 GBDT 常常更强？

**问题：** 团队要在点击率/风控这类表格数据（稠密统计特征 + 稀疏 ID 特征混合）上建模。有人主张 GBDT、有人主张 DNN。候选人要给出选型依据：什么情况下 GBDT 更强、什么情况下 DNN 更强、混合结构（GBDT+DNN）怎么设计？

**期望加分项：**
- 能说 GBDT 的优势场景：中等规模表格数据、特征大部分是数值/类别统计特征时，树模型对特征尺度/缺失/非线性天然鲁棒，且不需要特征工程
- DNN 的优势：高基数稀疏类别特征（用户/商品 ID）需要 embedding 学习语义相似；海量数据下 DNN 容量更大
- 能讲两者的本质差异：树模型按"值域切分"（可解释、特征交互是硬切分）；DNN 学习"分布式表示"（特征交互连续、可迁移）
- 混合结构：GBDT 输出叶子作为 DNN 的交叉特征输入（GBDT+LR 是经典过渡，GBDT+NN 同理）、或 DNN 学 embedding + GBDT 做最终排序（stacking）
- 数据量是分水岭：百万级数据 GBDT 足够，十亿级 + 高基数 ID 特征时 DNN 上限更高
- 会谈工程因素：训练/推理成本、可解释性要求、特征上线依赖

**减分项：**
- 只会说"表格数据就选 GBDT"，说不出边界
- 不知道 embedding 对高基数稀疏特征的价值
- 混合方案只会一种，讲不清为什么要混合
- 忽略数据量这个分水岭
- 不考虑可解释性与工程成本

**解答：**
表格数据场景两者都有强适用，分水岭是"数据量与特征形态"。**GBDT 占优的场景**：数据百万~千万级、特征以数值统计特征和类别统计特征为主（点击次数、均值、占比）、需要快速迭代与一定可解释性——树模型对特征尺度不敏感、天然处理缺失、自动做非线性切分与特征交互，几乎不需要特征工程就能拿到强基线，训练快、推理快，这就是大多数中小业务表格建模选 GBDT 的原因。**DNN 占优的场景**：数据量亿级以上、且存在大量**高基数稀疏类别特征**（用户 ID、商品 ID、广告 ID）——这些 ID 必须用 embedding 学"分布式表示"（相似用户/商品在向量空间距离近），树模型对高基数 ID 几乎无能为力（按单 ID 切分没有泛化）；数据足够多时 DNN 容量上限高于树模型，能挖掘更复杂的交互。**混合结构**是工业界主流：经典的是 GBDT+LR——GBDT 把样本落到叶子（叶子索引即"自动特征交叉"的结果）作为 LR 的离散特征，白赚树的交叉能力；升级版 GBDT+NN——GBDT 输出（叶子/预测值）作为 DNN 的输入特征，或 DNN 学 embedding 后把用户/商品向量喂给 GBDT 做排序。两阶段也更常见：召回用 DNN（embedding 语义相似检索），精排用 GBDT 或 DNN+GBDT 混合。选型决策树：数据小 + 统计特征多 → GBDT；数据大 + 高基数 ID 多 → DNN 或混合；要可解释 → GBDT（或用 SHAP 但解释力有限）；要 SOTA 且预算足 → 混合/大模型蒸馏。工程提醒：别一上来就上 DNN——先 GBDT 建基线，用"GBDT 效果 vs 需求差距"决定是否投入深度模型，投入前先确认数据量和 embedding 特征是否存在。

**延伸考点：** GBDT 的叶子作为特征喂给 NN，为什么能带来"自动交叉特征"收益（对比手写交叉特征）？DNN 的 embedding 在"相似用户"上为什么能泛化到未见用户（冷启动）？

### Q20. 候选人被要求设计一个"模型评估与上线治理"的完整体系，从离线评估到线上监控怎么闭环？

**问题：** 团队准备把模型从"训练一次上线一次"升级为规范的"模型生命周期管理"。候选人要设计完整体系：离线评估（数据集怎么分、指标怎么选）、上线前验证（回放/AB 实验）、线上监控（指标与漂移）、以及下线/更新机制。

**期望加分项：**
- 离线评估：固定且隔离的测试集（不被调参污染）、分层看指标（不止 AUC：考虑业务指标 CTR/转化/收入、校准度、分类阈值下的 precision/recall）、分群评估（新老用户/长尾）
- 上线前：离线在线一致性回放、小流量灰度、AB 实验（随机分组 + 显著性检验 + 最小样本量预估）
- 线上监控：业务指标（CTR/转化率/收入）基线监控、模型指标（评分分布、特征覆盖/PSI、预测-实际校准）监控、数据质量监控
- 更新机制：定期重训（按数据漂移/业务节奏）、新模型灰度替代、失败自动回滚（版本四件套）
- 治理：实验平台、模型注册表、上线审批与审计、告警与值班
- 闭环逻辑：线上监控发现问题 → 回滚或重训 → 新的评估 → 再上线，形成循环

**减分项：**
- 只讲离线评估，不讲线上监控与回滚
- 指标只看 AUC，不看业务指标与分群
- AB 实验没有显著性检验与样本量计算
- 没有自动回滚与版本管理
- 漂移监控与更新机制脱节（发现了不处理）

**解答：**
模型生命周期要闭环，缺一环都容易翻车。**离线评估**是基础：测试集固定且隔离（与训练/验证分开，调参永不触碰）、指标分三层看——排序能力（AUC/NDCG）、业务指标（CTR/转化率/收入的预期提升，用数据模拟或回放估算）、决策指标（给定阈值下的 precision/recall 与成本）；还要**分群评估**（新老用户、头部长尾、不同渠道），防止"整体指标好、某群体崩"。**上线前验证**：先做离线在线一致性回放（抽样线上真实请求对比新旧模型打分）、再小流量灰度（5%~10% 观察业务指标与延迟）、最后 AB 实验——随机分组、跑够最小样本量、做显著性检验（t 检验/AA 检验校准），确认提升统计显著再全量。**线上监控**是防止"上线即退化"的核心：四类监控——业务指标（CTR/转化/收入相对基线的偏离，告警阈值按波动定）、模型输出（评分分布均值/分位数偏移，用 PSI）、输入特征（覆盖率和分布漂移，特征 PSI）、数据质量（缺失率、新鲜度、字段异常）；告警要有可执行动作，不是只发消息。**更新与下线机制**：监控触发 → 评估是"数据漂移/概念漂移/模型退化"哪种 → 漂移则重训（重训需要新数据与评估闭环）、模型退化则回滚到上一稳定版本（配置中心一键切版本四件套）；定期重训节奏按业务（如每周）；新模型上线走同样的评估+灰度+AB 流程。**治理配套**：实验平台（统一 AB 能力）、模型注册表（版本与元数据）、上线审批与审计、值班告警 SOP。一句话收尾：**评估决定"能不能上"，监控决定"要不要下"，回滚/重训决定"怎么恢复"——三件事串成闭环，模型才是被治理的资产而非一次性脚本**。
