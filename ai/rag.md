# AI · RAG（面试题库）

本文件聚焦 RAG（检索增强生成）工程实践，考察重点为：文档解析与切分、embedding 与向量库选型、召回与重排、query 改写、效果评估、成本与缓存、安全权限、在线离线链路与全链路架构。题目全部来自真实工程场景，重点看候选人能否定位问题环节、给出量化依据、说清取舍与边界，而不是背诵概念。难度从实践基础逐步过渡到中阶调优与高阶开放性思考。

### Q1. 场景判断：内部知识库问答，用 RAG 还是微调
**问题：** 团队要做内部知识库问答，有同事说直接微调一个模型更快，也有同事说用 RAG。你接到这个任务，第一步会怎么判断该走哪条路线？

**期望加分项：**
- 能用「知识更新频率、知识规模与精确性要求、是否需要引用溯源、成本与合规」等维度给出判断框架
- 有量化依据：如知识每周更新时微调无法承受重训成本，RAG 更新只需替换文档
- 能说清 RAG 与微调的互补关系，而不是二选一（如长尾格式/话术知识用微调、事实知识用 RAG）
- 联系线上实践：如「客户要求答案必须可溯源，微调给不出引用，所以必须 RAG」
- 主动考虑边界：混合场景、冷启动阶段

**减分项：**
- 只会背「RAG 是外挂知识库」这类定义，说不出决策依据
- 认为 RAG 一定优于微调，或反之
- 答不出「事实正确率要求很高时 RAG 的兜底方案」
- 没有评估闭环——没建评测集就谈不上选型

**解答：**
思路：先别急着选技术，先回答三个问题——知识变不变、答错的代价多大、用户要不要看来源。判断框架：知识高频更新（制度、公告、价目）→ 用 RAG，更新成本只是替换文档；知识规模大且是长尾碎片（FAQ、合同）→ 用 RAG；对生成风格/领域表达有要求（财报措辞、客服话术、固定格式输出）→ 微调收益更直接；合规场景要求引用来源 → 必须 RAG，微调无法给引用。实践中多数系统是 RAG 兜事实、微调兜表达，甚至可以并用：检索命中走 RAG，检索失败降级用微调模型直接回答。量化方法：收集 100~200 条真实问题做成评测集，RAG 方案事实类命中率/正确率低于可接受线（如 90%）再考虑微调或两者结合。坑：最常见的是「先微调后补 RAG」，知识一更新就要重训，成本失控；另一个坑是用模型自带 QA 能力当 RAG 基线，二者回答风格与口径完全不同，评测指标要分开定义、分开对标。

**延伸考点：** 知识库里 80% 是流程类问题（怎么报销）、20% 是事实查询（本月制度改了哪条），你会怎么拆？如果 RAG 事实正确率 85%、微调 90%，但微调每季度多花 3 万，你怎么决策？

### Q2. 扫描件 PDF 的文档解析
**问题：** 用户问「我们合同里退款条款是什么」，但合同是扫描件 PDF，回答总是不准，怎么系统性优化？

**期望加分项：**
- 能从链路定位：是 OCR 出错、切分截断、召回不到，还是生成错误
- 能给出 OCR 方案选型（PaddleOCR/商用 OCR/OCR 后校正）与质量评估手段（字符/字段级准确率）
- 能处理表格、印章遮挡、倾斜扫描、页眉页脚、双栏排版等干扰
- 能给出「OCR 文本与原文对不上」时的引用溯源方案
- 有量化意识：先抽样本评估 OCR 准确率，再决定投入力度

**减分项：**
- 只答「用 OCR 识别一下」这种一句话方案
- 不区分扫描件 PDF 和文字版 PDF，不做类型分流
- 答不出 OCR 结果该怎么切分（版面分析优先于纯文本切分）
- 忽略「合同条款往往带条款编号、常落在表格里」这类检索难点

**解答：**
思路：这不是单一问题，是文档解析质量问题的典型。先定位：抽 20~50 份样本人工跑一遍全链路，统计「解析→召回→生成」每段失败率，大概率卡在解析。方法：第一步判断 PDF 类型——文字版直接抽文本，扫描版走 OCR，很多工程直接用 PDF 库抽文本抽出乱码/空，就是因为没做类型分流。第二步 OCR 选型：中文合同可用 PaddleOCR 或商用 OCR（百度/腾讯/阿里），注意合同常见难点——表格结构（退款比例表）、印章遮挡、扫描倾斜，先做图像预处理（纠偏、去噪、增强对比度）。第三步是重点：OCR 文本不要直接按字符流切分，先做版面分析（段落/表格还原），表格转成结构化描述或还原成 Markdown 表格，否则「退款条款」这类词经常被切散。第四步：OCR 结果做后校正（常见错字映射、字段抽取验证），并保留 OCR 页码/版面坐标，供生成答案时引用原文位置。量化做法：抽 30 份合同人工标注「退款条款」位置，评测切分后能否被召回，目标命中率 ≥90%。坑：OCR 字符准确率 99% 但条款级召回 60% 很常见——因为错字集中在条款编号、金额这类关键检索词上；以及 OCR 文本与原文对不上，用户追问「原文在哪一页」时答不上来。

**延伸考点：** OCR 错字导致向量召回不到怎么办（错字容错、混合检索、同义词扩展）？合同是几百页的多版本合集，怎么保证检索到的是「当前生效版本」？

### Q3. chunk 切分策略
**问题：** 一份文档 200 页，直接整段进模型超长，切成小段后回答经常只答一半，chunk 到底怎么切才合理？

**期望加分项：**
- 能说清 chunk 大小取决于「模型上下文窗口、召回粒度、回答粒度」三者的匹配
- 能给出调参方法：以「检索命中率/答案完整率」为指标做小规模实验，而不是拍脑袋定 512
- 能处理结构：标题层级、表格、代码块、列表不能硬切
- 能说清重叠（overlap）解决什么问题、带来什么代价（冗余、重复召回）
- 能联系实际：chunk 大小要与「答案所在单元」匹配，如合同按条款切、FAQ 按问答对切

**减分项：**
- 只背「固定 512 token」这类默认值
- 答不出「为什么要重叠」的量化解释
- 忽略切分对引用溯源（chunk→原文）的影响
- 没有评估手段，纯靠感觉调

**解答：**
思路：切分的本质是让「一个检索单元 ≈ 一个可独立回答问题的段落」。先想文档里「答案的天然粒度」是什么——合同按条款、制度按章节、FAQ 按问答对、产品文档按主题段落。方法：优先结构化切分，利用标题层级（H1/H2/H3）把文档切成语义完整块，块过大再按段落/句子拆，块间重叠 1~2 句（约 10%~15%）保证跨块上下文不断。块大小以 token 计（中文 512~1024 常见），但必须和 embedding 模型最大输入（如 512/8192）及重排模型输入上限对齐。实践节奏：先按约 800 token 粗切，用 50 条真实问题测命中率——命中但答案不完整，说明块太小需并入上下文；命中不了，说明切分把关键信息切散了，需要加大重叠或按语义块（标题）切。进阶方案：父文档检索（parent document）——小块召回、整块生成，或做两级索引。坑：① 表格和代码被按行切散是重灾区，要先识别代码块/表格再切；② 重叠写进索引后重复片段占满 top-k，融合前要去重；③ 中文按字符切会截断词语，尽量按中文词/句子切，而不是硬按字符数。

**延伸考点：** 切完发现召回的都是「半句话」，你会先调 chunk 还是先调 top-k？同一个知识点散落在文档三处，检索重复命中，怎么合并去重？

### Q4. embedding 模型选型与验证
**问题：** 向量召回效果一般，团队想换 embedding 模型，你怎么选型、怎么证明新模型确实更好？

**期望加分项：**
- 能给出选型维度：中文效果、最大输入长度、向量维度与存储成本、推理延迟与部署成本、许可证
- 能用「领域内真实问题评测集」对比新旧模型，而不是跑公共 benchmark
- 能说明 domain 特化：通用模型对专业术语/代码/行业黑话召回差，需要领域适配或换领域模型
- 能给出量化指标：hit@k、MRR 等检索指标
- 能权衡成本：换模型要全量重嵌所有文档，考虑重算成本与双跑期

**减分项：**
- 只答「用 OpenAI embedding」或「用 BGE」而无对比依据
- 拿公共数据集结果直接套用
- 忽略「索引与查询必须用同一模型」的一致性约束
- 不考虑维度、调用计费等成本

**解答：**
思路：换 embedding 前先确认问题在召回侧还是重排侧——很多「召回差」其实是切分问题或没做重排，换模型应是最后手段。选型维度：中文场景优先中文/中英双语模型（如 BGE 系列、text-embedding-3、通义/文心 embedding），重点看四点——最大输入长度（决定 chunk 上限）、向量维度（决定存储与检索成本）、推理延迟（在线链路 QPS）、许可证（商用合规）。验证方法：抽 100~200 条领域真实问题，人工标注答案所在文档，算 hit@k（k=5/10）与 MRR，新旧模型同口径对比，并检查历史 bad case 是否被修复。进阶：领域术语多（法律/医疗/代码）时，用领域语料做 embedding 的领域适配，收益往往大于换更大的通用模型。实践注意：① 索引与查询必须同一模型，换模型要全量重嵌，规划好灰度——先双索引并行跑一段时间对比线上指标，再切换；② 开源模型中文效果未必差，先量化对比再决定；③ 维度压缩可降成本但可能掉精度，需实测。

**延伸考点：** 你的领域是金融研报，通用 embedding 对「承兑汇票」「转贴现」这类词召回差，怎么系统性解决？新模型 hit@10 高 5 个点但线上 QPS 降 30%，你怎么权衡？

### Q5. 向量库选型
**问题：** 文档量从 10 万条涨到 1000 万条，检索变慢，向量库选型怎么考虑？

**期望加分项：**
- 能说出不同量级/需求下 Milvus、FAISS、ES、PGVector、Qdrant 的适用场景
- 有量化依据：数据量、在线 QPS、延迟、过滤需求、运维成本
- 能说清「向量检索 + 标量过滤」的组合使用（如按部门/时间过滤）
- 能考虑存量迁移成本与已有技术栈复用
- 能给出容量估算：维度 × 条数 × 4 字节推算内存占用

**减分项：**
- 只推荐一个库，说不出为什么
- 不区分「离线计算」与「在线服务」场景
- 忽略过滤、权限、混合检索（BM25）对选型的影响
- 不考虑高可用、扩容等运维成本

**解答：**
思路：向量库选型本质是「检索需求 + 工程成本」的权衡，先列约束再选型。判断维度：① 数据量与增长——百万级内 FAISS/PGVector 够用，千万级以上考虑 Milvus/Qdrant/ES；② 在线 QPS 与延迟——FAISS 做在线服务要自己解决并发、持久化、高可用，Milvus/Qdrant 原生支持分布式；③ 过滤需求——真实场景常是「部门 A 只看自己文档」，纯 ANN 无法高效过滤，需选支持过滤的库（Milvus 标量过滤、ES filter），否则只能检索后过滤，量大时浪费严重；④ 混合检索——需要 BM25+向量融合时，ES（dense_vector）与 Milvus 生态都支持，FAISS 需另配。容量估算：1000 万条 × 1024 维 × 4 字节 ≈ 40GB 原始向量，HNSW 图结构再加约 1.3~2 倍内存，先估算再定机器。实践建议：量小且不想多维护一套系统，先用 PGVector/ES 复用现有库；量级上来再迁 Milvus。坑：① 只看 ANN 性能不看过滤性能，上线后带过滤的请求延迟爆炸；② 忽略删除/更新场景，增量删除在 HNSW 上可能退化；③ FAISS 不持久化，进程挂了要重建索引。

**延伸考点：** 搜索日志显示 30% 请求带「部门过滤」，对向量库选型和索引设计有什么影响？只允许内网部署、无 GPU，向量库和 embedding 推理怎么规划？

### Q6. 召回策略：相似度阈值与 top-k
**问题：** 检索结果里经常混进「看起来像但完全无关」的内容，top-k 和相似度阈值怎么定才合理？

**期望加分项：**
- 能区分「余弦相似度绝对值」与「相对排序」的意义，说明阈值因模型/领域而异
- 能给出确定 top-k 与阈值的量化方法：评测集上算 precision@k、hit@k
- 能说清「阈值过滤 vs top-k 截断」的取舍
- 能处理「query 太短、检索词少」导致的召回稀疏
- 联系线上：低于阈值时的兜底策略（无答案、改写重试、放宽条件）

**减分项：**
- 说「阈值定 0.7」这类无依据数值
- 把相似度当概率理解
- 只讲向量召回，不讲混合检索与兜底
- 答不出「宁缺毋滥 vs 宁滥毋缺」的业务权衡

**解答：**
思路：相似度阈值不是可移植的常数——它取决于 embedding 模型（不同模型分数分布差异很大）、领域文本分布和业务对「答错 vs 不答」的容忍度。方法：① 先看分数分布：抽线上真实 query，统计命中的相关文档与不相关文档的相似度分布，找可分界点（如相关集中在 0.75~0.85、噪声集中在 0.5~0.65，可取 0.7 左右），而不是拍脑袋；② top-k 用评测集画 hit@k 曲线，观察 k 从 1 涨到 10 时命中率是否收敛，取拐点；③ 阈值过滤与 top-k 截断结合：先按阈值滤掉「肯定无关」，再从结果取 top-k，避免「阈值严到召回为空、松到噪声多」两个极端；④ 业务权衡：客服场景答错代价高，宁可「无法回答」也不硬答，阈值从严；营销/覆盖类场景放宽；⑤ 兜底：低于阈值时尝试 query 改写/同义词扩展再召回一次，仍为空则走「无答案」话术，不要硬凑。坑：① 拿公共模型的默认分数当通用阈值；② 只调阈值不查 embedding 与切分质量，阈值越调越畸形；③ 忽略 query 长度——长 query 相似度普遍偏高、短 query 偏低，要分桶统计再定。

**延伸考点：** 阈值 0.7 时「无法回答」率 25%，业务要求降到 10%，你先动阈值还是先动召回链路？为什么相似度分数不能和「置信度」画等号？

### Q7. 混合检索：BM25 + 向量
**问题：** 向量检索对专有名词、产品型号召回很好，但用户用口语问「咱家那个三天的假期是啥政策」，纯向量搜不到，怎么解决？

**期望加分项：**
- 能说出混合检索解决「字面匹配」与「语义匹配」互补问题
- 能给出融合方法：RRF（Reciprocal Rank Fusion）或加权分数归一化，并说明取舍
- 能说明参数如何调（RRF 的 k 值、权重）
- 能处理中文分词对 BM25 的影响（分词器选择、专有名词词典）
- 有线上验证手段（A/B、bad case 回归）

**减分项：**
- 只会说「两个都跑然后合并」，说不出融合细节
- 不知道 RRF 为什么比直接加权分数稳
- 忽略 BM25 需要分词与倒排索引的运维成本
- 没有评估：混合后指标怎么算、提升多少

**解答：**
思路：纯向量对「语义相同但字面不同」强，对「专有词/型号/口语缩写」弱；BM25 相反。混合检索的动机是互补，难点在融合。方法：① 双路召回：一路向量、一路 BM25——中文必须配好分词器（jieba / ES 的 ik 分词），专有名词加自定义词典，否则「三天的假期」被切碎；② 融合首选 RRF：score = Σ 1/(k + rank)，k 取 60 左右，它只依赖排名、不依赖分数尺度，比「归一化加权和」稳健得多——因为两路分数分布不可比，直接加权会偏向分数虚高的一路；③ 权重调整：需要偏向量时对向量路乘系数或用 RRF 变体，实践中无权重 RRF 已足够好，别过度调参；④ 验证：用 100 条混合问题（含口语、专有词、同义改写）算 hit@k，混合后应显著高于单路；⑤ 进阶：query 分析——含专有词/型号的 query 向量路优先，口语化 query 补 BM25，可动态加权。坑：① 两路结果重合度高，融合后 top-k 被同一批文档占满，要先跨路去重；② 中文不分词直接建 BM25 索引几乎无效；③ 两路延迟不同，要给慢路设超时兜底，别拖慢整体链路。

**延伸考点：** RRF 里 k 值变大变小分别有什么影响？双路召回总延迟从 80ms 涨到 200ms，你怎么优化（并行、缓存、降级）？

### Q8. 重排：rerank 的定位与落地
**问题：** 召回 top-20 里前几条经常不准，第 5 名之后才出现正确答案，加 rerank 能解决吗？怎么加？

**期望加分项：**
- 能说清 rerank 的定位：粗排召回 + 精排重排，解决「embedding 粗排序不准」问题
- 能给出选型：cross-encoder 类（如 BGE-Reranker）vs 向量库二次打分，说明为什么 cross-encoder 更强
- 能说明重排模型的输入上限（token）与成本（延迟、GPU）
- 有量化验证：rerank 后 hit@k、MRR 提升多少
- 能权衡「是否真的需要 rerank」（答案已在 top-1~2 时可跳过）

**减分项：**
- 只背「加个 rerank 模型」，不知道原理和代价
- 不知道 rerank 是 query+doc 联合编码（cross-attention）
- 忽略重排模型输入长度限制导致的截断
- 没有评估就上线

**解答：**
思路：先确认「答案在不在召回集里」——top-5 内没答案而 top-20 有，正是 rerank 的典型适用场景；如果 top-20 都没有，加 rerank 没用，问题在召回/切分/embedding。方法：① 架构：向量库取 top-20~50 粗排，过 cross-encoder 重排模型（query 与 doc 拼接后联合打分），取 top-3~5 进生成；② 选型：中文场景可用 BGE-Reranker 系列，注意输入上限（如 512 token），超长候选要先切到合理片段再重排；③ 成本：cross-encoder 逐对计算，20 条候选 ≈ 20 次前向，延迟约 20~100ms（视 GPU），QPS 高时要做批处理或控制并发；④ 量化：上线前用 100 条问题算 MRR@20 与 rerank 后 MRR@5 对比，命中率提升 5~15 个点是常见量级；⑤ 进阶：可加规则重排混合——业务字段加权（置顶公告、时效性字段），或两段式——先用便宜模型粗筛到 20，再 cross-encoder 精排到 5。坑：① rerank 只对「召回集内」有效，别指望它救召回；② rerank 分数不可跨 query 比较，别拿它当阈值；③ 全量文档过 rerank 的延迟不可接受，粗排必须先把候选收窄。

**延伸考点：** 你的重排模型英文效果好、中文差，怎么验证和替换？rerank 让 p95 延迟从 300ms 涨到 900ms，业务不答应，怎么降本？

### Q9. query 改写与多轮对话检索
**问题：** 多轮对话里，用户先问「去年销售额是多少」，再问「那今年呢？」，第二轮直接搜不到，怎么处理？

**期望加分项：**
- 能指出问题本质：第二轮 query 是省略句/指代句，需要结合会话历史改写
- 能给出改写方案：LLM 改写、规则/模板、指代消解，并对比成本
- 能说明改写失败的兜底，以及改写是否要回填会话上下文
- 能处理意图漂移：用户聊着聊着换话题，不能永远带上文
- 有边界意识：改写只影响检索 query，不改变生成内容

**减分项：**
- 只会说「用 LLM 改写一下」
- 忽略改写成本（多一次 LLM 调用）与延迟
- 不处理「新 query 与历史无关」的误改写
- 不知道改写会放大幻觉——改写错了检索就错

**解答：**
思路：多轮检索的核心是把「语义完整的当前问题」提取出来，让检索基于它执行。方法分三档，按成本与场景选：① 轻量：规则/模板 + 指代词典（「这个/那个/上述」替换为历史实体），零延迟，适合结构化场景；② 主流：LLM 改写——把最近 N 轮对话 + 当前问题喂给模型，输出可直接检索的完整 query，prompt 关键约束是「只补全指代与省略，不添加新信息、不扩写」；③ 进阶：维护对话上下文状态，判断当前问题是否需要上文（分类或让模型输出「独立问题」标记），按需触发改写。关键细节：改写要「不添加、不臆造」，否则引入幻觉污染检索；改写失败降级用原始 query 检索。意图漂移处理：设置窗口（最近 2~3 轮）+ 相关性判断，用户开新话题时丢弃历史。实践：改写上线前做「改写前后命中对比」评测，统计增益与负增益比例（改写可能把对的改错），负增益超阈值（如 10%）就回退规则方案。坑：① 把「改写」和「闲聊生成」混在一个 prompt，加了太多指令导致改写漂移；② 每轮都调 LLM 改写，延迟成本翻倍——可只在「短 query + 有历史」时触发；③ 改写结果不回流——应把最终命中的文档 id 记录进会话上下文，下一轮可直接参考。

**延伸考点：** 用户连续问 8 个问题后说「把刚才第 3 个问题的答案再说一遍」，检索系统怎么定位到那一轮？改写用的小模型效果不稳，怎么评测、怎么换？

### Q10. 知识库更新与增量索引
**问题：** 新增了一批文档，第二天检索结果却搜不到新内容，可能卡在哪个环节？怎么排查？

**期望加分项：**
- 能系统列出链路环节：文档入库、解析、切分、embedding、写入索引、检索过滤条件
- 能给出排查手段：查索引条数、按 id 直查、对比新旧索引、查入库日志
- 能指出常见根因：缓存未失效、多索引未切换、写入失败无告警、增量与全量不一致
- 能谈版本与一致性：文档更新后旧版本还在、双索引灰度
- 有可观测性意识：入库链路每环节的成功/失败/耗时监控

**减分项：**
- 只猜「缓存问题」一个点
- 答不出排查的验证手段
- 忽略「删改文档」场景的索引一致性
- 没有监控/告警意识

**解答：**
思路：这是「索引不一致」问题，要按「数据链路 → 索引 → 检索」逐段验证。排查顺序：① 确认文档真的入库成功——查入库任务日志与文档状态，解析失败（尤其是扫描件/特殊格式）被静默跳过很常见；② 确认向量写入成功——查向量库文档总数与 embedding 日志，对比预期条数；③ 确认检索实际访问的索引包含新文档——多索引/分片场景，新文档可能写到了检索不用的那一路；④ 检查缓存——有 Redis/内存缓存时，TTL 内必然搜不到新内容，这是最常被忽略的环节；⑤ 检查过滤条件——新文档缺元数据（部门/时间字段），被检索过滤条件挡掉，索引里有但召回时被 filter 排除。防御性设计：入库链路加可观测性——每环节记录「输入条数/成功/失败/耗时」，失败有告警与重试；文档带版本号和生效时间，「更新 = 软删除旧版 + 写入新版」保证一致性；对「刚更新要秒级可见」的需求，可做直查旁路与离线全量的权衡。坑：① 全量索引重建与增量写入混跑，增量被全量覆盖；② 写入失败无重试无告警，索引「看起来在更新」实际漏数据；③ 测试环境能搜到、线上搜不到——两边索引配置不一致。

**延伸考点：** 文档更新后旧内容还在，用户问新政策却召回旧政策，索引层怎么保证版本一致？需求是「文档修改后 5 分钟内可检索」，你会怎么设计写入链路？

### Q11. 文档去重与版本管理
**问题：** 知识库导入时同一个政策文件被上传了三份不同版本，检索经常把旧版和新版混在一起回答，怎么治理？

**期望加分项：**
- 能区分「去重（dedup）」与「版本管理（version）」是两个问题
- 能给出去重方法：标题指纹、正文相似度（SimHash/MinHash）、embedding 距离
- 能给出版本决策：生效时间、覆盖关系、默认取最新生效版本
- 能处理「局部更新」：同一文件只改了几行怎么识别
- 有量化：重复文档占比、版本过滤前后检索命中率对比

**减分项：**
- 只答「删掉重复的」
- 不区分「完全相同」和「高度相似」的去重手段
- 忽略业务版本语义（生效日期、修订号、归档需求）
- 不解决检索侧的多版本互相干扰

**解答：**
思路：先分清楚是「重复」还是「多版本」——重复是内容几乎一致，去重解决；多版本是内容有差异且都有存在价值（历史政策需归档审计），要版本化而不是删除。方法：① 去重：入库前算文档指纹——标题 + 正文的 SimHash/MinHash 相似度，相似度 >0.9 判定重复，人工确认后合并；跨文档重复段落（如新闻稿转载）在 chunk 层去重，用 chunk 的 embedding 距离判断，余弦 >0.95 保留一篇；② 版本管理：文档表加 version、effective_date、status（草稿/生效/过期）字段，检索默认只查 status=生效 且 effective_date ≤ 今天，按 effective_date 倒序取最新版；同一逻辑文档（doc_id 相同）多版本并存，但检索与生成只暴露当前版；③ 引用溯源：答案带上「版本 + 生效日期 + 来源」，让用户能发现并核对版本差异；④ 量化：统计去重后索引量下降比例（常见 10%~30%）、版本过滤后命中「当前生效版」的比例。坑：① 直接物理删除旧版，破坏历史审计与回滚需求，要软删除；② 只按标题去重，标题带日期（「政策2023版」「政策2024版」）被误判为不同文档；③ chunk 级去重误删「引用了旧版数字」的上下文。

**延伸考点：** 两份文档标题不同、内容 95% 相同，你的去重策略怎么处理？用户问「2022 年的政策是什么」这种历史查询，版本管理怎么支持？

### Q12. 回答拼接与引用溯源
**问题：** RAG 答得挺顺，但用户追问「这个结论依据是哪个文件、哪一页」，答不上来，怎么让回答可溯源、少幻觉？

**期望加分项：**
- 能区分「检索到的内容」与「模型生成的结论」，要求答案必须基于检索片段
- 能给出引用方案：生成时携带来源标注（[1][2]）、chunk → 文档/页码映射
- 能控制幻觉：约束生成（仅基于给定上下文）、后验校验（答案与证据一致性检查）
- 能处理「证据不足」时的拒答话术
- 有评估：引用准确率、忠实度（faithfulness）

**减分项：**
- 只答「让模型把来源加上」，不考虑来源是否真实存在
- 不知道引用要可点击可校验（追溯到原文，而非仅 chunk id）
- 不处理「模型自己脑补的证据」
- 没有忠实度评测机制

**解答：**
思路：溯源与少幻觉是一体两面——让模型「只能基于证据说」并「标注证据来源」。方法：① 生成约束：prompt 明确「仅基于给定文档回答，信息不足时回答『根据现有资料无法确认』，不要编造」；把每个检索片段标上 id（如 [doc_id-chunk_id]），要求答案中引用这些 id；② 溯源落地：chunk 保留「文档名 + 页码 + 段落位置」元数据，前端把引用 id 映射回可点击的原文链接并展示原文摘要，让用户能自行验证；③ 后验校验：答案生成后做「证据校验」——检查答案中的关键数字/事实能否在引用的片段中找到（NLI 式判断或实体/数字比对），不一致则降级或拒答；④ 拒答兜底：相关度低于阈值或证据不足时明确说「查不到」，而不是硬答；⑤ 量化评测：人工标注评测集，算「引用准确率（引用的内容真能支撑答案）」与「忠实度（答案没有编造）」，这两项比答案流畅度更重要。坑：① 只标注 chunk id，用户点开发现是 200 字碎片无法验证，要映射到整页/原文位置；② 模型把多个来源混编，观点 A 的来源标成观点 B 的——引用要做到「逐句归因」而非整段归因；③ 后验校验只比对「有没有这个词」，数字「1.5 万」写成「15000」就对不上，校验前要做数值规范化。

**延伸考点：** 答案里有一句是模型推断的（不在任何片段里），怎么自动识别并标记？用户要求「引用必须是原文原句」，与模型要概括答案的要求冲突，怎么设计？

### Q13. RAG 效果评估
**问题：** RAG 系统上线前要评估效果，光靠几个人试用说「还行」不行，评测集和指标体系怎么建？

**期望加分项：**
- 能区分检索评估（hit@k、MRR、NDCG）与生成评估（答案正确率、忠实度、引用准确率、拒答合理性）
- 能给出评测集构建方法：线上真实 query 采样 + 人工标注答案所在文档
- 能给出可复现流程：固定版本、评测脚本、回归机制
- 能处理「评测集污染」（用反复调优过的文档做评测导致虚高）
- 有分层定位能力：指标差能定位到检索层还是生成层

**减分项：**
- 只用「效果还行」这种主观判断
- 指标只有一个「准确率」，无法定位环节
- 评测集脱离线上真实问题分布
- 没有回归机制，改一个参数全凭感觉

**解答：**
思路：评估要分层——检索层和生成层分开测，否则指标不好无法归因。方法：① 评测集：从线上日志抽 200~500 条真实 query（覆盖高频、长尾、口语化），人工标注「标准答案 + 答案所在文档/chunk」，这是最有价值也最费人力的一步，可先用规则筛选再人工复核；② 检索指标：hit@k（答案是否在 top-k 中）、MRR（答案排多靠前）、NDCG（排序质量），只依赖标注文档，跑得快、可自动回归；③ 生成指标：人工或 LLM 评分「答案正确率、忠实度、引用准确率、拒答合理性」，LLM 评分要先抽一部分人工复核校准，避免和回答模型同源偏差；④ 回归机制：每次改动（切分、模型、阈值、prompt）跑同一套评测集对比，让改动可归因；⑤ 分层定位：检索差 → 查 embedding/切分/混合检索；检索好生成差 → 查 prompt/上下文组织/重排；都差 → 先修数据质量。坑：① 评测集用「开发时反复调优过的文档」，指标虚高、线上崩；② 只用 hit@k 不看 MRR，答案在 top-20 也算命中，但生成实际只用 top-5；③ 生成评估只看「答没答上来」不看忠实度，幻觉被误判为答对。

**延伸考点：** 业务方说「准确率 95%」但用户反馈差，可能是什么原因（评测集分布、指标口径、bad case 聚类）？LLM 自动评分怎么避免「打分模型和回答模型同源」的系统性偏差？

### Q14. 缓存与成本优化
**问题：** RAG 系统日均调用 10 万次，每次都检索 + LLM 生成，成本和延迟扛不住，怎么优化？

**期望加分项：**
- 能区分缓存层级：query 规范化 + 答案缓存、检索结果缓存、embedding 缓存
- 能给出缓存设计：key 设计、TTL、与知识库版本联动失效、命中率监控
- 能说明「哪些适合缓存」：高频重复问题、热点文档
- 能从成本结构优化：embedding 复用、向量降维/量化、分级路由（小模型兜底）
- 有量化：命中率、成本下降比例、延迟收益

**减分项：**
- 只答「加个 Redis」
- 忽略缓存一致性（知识库更新后旧缓存还在）
- 不做 query 规范化（同义句缓存不命中）
- 只降成本，不评估质量与延迟影响

**解答：**
思路：先算成本结构——LLM 生成通常占 80%+ 成本，其次才是 embedding 与向量检索。优化按收益排序：① 答案缓存：对高频重复 query 直接缓存生成结果，带 TTL 与知识库版本号（知识库更新时按版本失效），命中率通常能做到 20%~40%，这是最省成本的一层；key 要先做 query 规范化（去标点、大小写归一、同义词归一），否则同义句不命中；② 检索结果缓存：同一 query 短时间内的检索结果复用，省 embedding 与向量查询；③ embedding 复用：文档侧 embedding 入库时算一次并缓存，query 侧 embedding 对热词缓存；④ 向量库降本：1024 维降到 512 维或做 PQ/标量量化，内存和带宽减半，精度损失用评测集验证；⑤ 分级路由：简单问题走小模型或模板，复杂问题走大模型——先做问题分类，别一视同仁；⑥ 批处理：离线报表类 query 合并批跑，摊薄固定开销。坑：① 缓存不过期，知识库更新后用户仍拿旧答案——缓存 key 要带知识库版本或做失效广播；② 缓存放大权限问题：带部门/用户过滤的 query 不能共享缓存，key 要包含过滤条件，否则越权泄露；③ 只优化生成不优化检索，延迟大头反而在慢检索。

**延伸考点：** 缓存命中率到 40% 后上不去了，还有什么手段（语义缓存、相似 query 复用）？检索结果缓存 5 分钟，遇到「文档刚更新就要新答案」的冲突怎么处理？

### Q15. 长文档与多源异构数据
**问题：** 知识库里既有 500 页的研究报告，又有几百条 FAQ，还有图片和表格，怎么统一检索？

**期望加分项：**
- 能给出多源统一思路：先类型分治 + 元数据治理，再统一检索入口
- 能处理长文档：分层切分、章节摘要、父子结构，避免单 chunk 过长
- 能处理多模态：图片 OCR/图文描述、表格转结构化
- 能统一打分：不同来源的检索分数可比性处理（RRF 等）
- 有数据治理意识：噪音、过期、来源冲突内容的处理

**减分项：**
- 所有文档切一样大就算完事
- 忽略「长文档里答案分布不均」的定位问题
- 不处理来源冲突（FAQ 和报告说法不一）
- 不给来源设置可信度权重

**解答：**
思路：异构数据统一检索的关键是「类型分治 + 元数据治理」，再统一检索入口，而不是一把梭。方法：① 分类型处理：FAQ 按问答对入库（一个 Q 一个 chunk）；报告按「章 → 节 → 段落」分层，做两级索引（先召回章节再定位段落）；表格用表格识别还原为 Markdown 或结构化行，图片配 OCR/视觉模型描述后统一 embedding；② 统一元数据：所有文档进库前打 source_type、来源、时间、权限、可信度标签，检索时作为过滤与加权维度；③ 长文档特化：500 页报告在段落级切分后丢失章节语境，可用「章节摘要 + 段落」父子结构——章节摘要做粗召回、段落做精排与生成，或生成时带上父章节上下文；④ 来源冲突：同一知识点多渠道说法不一，用「可信度权重 + 生效时间」裁决，冲突难以裁决时在答案里并列给出并标注来源；⑤ 统一打分：不同来源的相似度分布不同，用 RRF 或多路归一化后再排序，别直接比较原始分数。坑：① 表格被硬切成碎片后「表格检索」基本失效，表格必须整表识别存储；② 图片只 OCR 不保留版式，图内结构信息丢失；③ 所有来源一个权重，权威文档和用户上传的零散笔记打架。

**延伸考点：** 500 页报告里答案在第 450 页，且表述与第 20 页冲突，怎么定位并裁决？多模态检索的效果怎么单独评测（图/表问答单列一类）？

### Q16. 结构化数据与 API 结合
**问题：** 用户问「我们公司上个月各区域的销售额和增长率」，这些数据在数据库里、不在文档里，RAG 怎么接？

**期望加分项：**
- 能区分「非结构化检索」与「结构化查询」，指出 RAG 的能力边界
- 能给出方案：Text-to-SQL、NL2API、先检索表结构/口径再生成查询
- 能说清安全与正确性：SQL 生成受控（只读、表白名单、行级权限）
- 能处理「口径定义在文档、数据在库里」的混合场景
- 有验证：查询结果正确性校验、schema 变更影响

**减分项：**
- 直接把数据库表 dump 成文本塞进知识库
- 让模型自由写 SQL 不校验
- 忽略「先确认口径/维度」再查询的流程
- 不处理查询失败与降级

**解答：**
思路：这类问题要拆成两件事——「怎么算」（口径）和「数据在哪」。正确架构是 RAG 与结构化查询混合：文档/知识库负责「口径、定义、术语」，数据库/API 负责「数据」。方法：① 方案一（NL2SQL）：让模型基于「表结构元数据 + 字段说明」生成 SQL，执行前做安全校验（只读、限定表、强制 LIMIT、拒绝 DDL），执行后把结果转成自然语言回答；② 方案二（NL2API）：系统已有报表 API 时，把 API 文档（参数、示例）作为检索语料，模型检索到正确 API 并填充参数调用；③ 混合场景（重点）：用户问「增长率」——先检索知识库确认口径（环比还是同比）再查数，答案里注明口径，这是最容易答错也最容易被忽略的一步；④ 正确性保障：SQL 生成后加「执行前校验 + 结果合理性检查」，结果为空或异常时改写重试或降级为人工模板；⑤ 评测：用「query → 期望 SQL/API 调用 → 期望结果」的评测集回归，重点覆盖时间范围、多表 join、聚合口径等复杂条件。坑：① 把整库 dump 进向量库是常见错误——表数据量大、无语义、更新频繁，又慢又错；② 模型生成的 SQL 在多表 join 与聚合上容易错，复杂查询宁可走预设模板/API；③ 忽略权限——模型生成 SQL 没带「当前用户可见范围」的过滤条件，存在越权查询风险。

**延伸考点：** 用户问「上个月销售额」时，「上个月」是自然月还是财务月？系统怎么处理这种口径歧义？Text-to-SQL 答错一次的成本比 RAG 编造还高，你怎么评测和兜底？

### Q17. 安全与权限：防越权检索
**问题：** 知识库里有 A 部门薪酬文档，B 部门用户问「A 部门工资多少」，RAG 却答出来了，越权了，怎么防？

**期望加分项：**
- 能识别越权风险点：文档级/chunk 级权限、检索时强制过滤、生成时二次校验
- 能给出方案：元数据权限标签 + 检索强制过滤 + 生成侧校验
- 能说明「查询时过滤」与「查询后过滤」的区别及为什么必须前者
- 能处理 ACL 复杂场景：部门、角色、文档密级混合
- 有审计：敏感文档的检索与访问日志

**减分项：**
- 只在 prompt 里写「不要回答敏感内容」
- 认为向量库天然隔离（不了解 filter 机制）
- 忽略 chunk 跨权限文档的泄露风险
- 不做越权用例测试与回归

**解答：**
思路：权限必须在数据链路里强制实施，不能依赖模型自觉。三层防线：① 索引层（主防线）：每篇文档/每个 chunk 打 ACL 标签（部门、角色、密级），检索时强制带用户上下文做标量过滤（Milvus filter、ES filter），查询条件里写死「权限交集」，这一步从机制上杜绝越权；② 生成层：把「当前用户可见范围」写入 prompt 或对生成答案做校验——即使检索有遗漏，模型也不该引用不可见内容；③ 审计层：敏感文档的检索、命中、生成全链路日志，用于事后追踪与越权检测。关键细节：① 过滤要在「查询时」而非「查询后」——先取 top-100 再过滤是泄露风险，且浪费检索能力；② 权限粒度提前定：文档跨部门可见时，chunk 级权限更细但成本高，文档级简单，按业务密级决定；③ 缓存要带权限维度——缓存 key 必须包含用户权限指纹，否则 A 用户的结果可能命中给 B 用户；④ 测试：越权用例必须进评测集回归（B 部门用户问 A 部门问题必须返回空）。坑：① 只加 prompt 约束，模型被套话（「假设你是 HR」）就能绕过；② 权限枚举没对齐（密级字符串拼写不一致），过滤条件形同虚设；③ 微调/蒸馏出的模型没有权限概念，权限只能在检索与生成链路管。

**延伸考点：** 一个 chunk 被多个部门的文档引用，ACL 应该取交集还是并集？模型通过「编造」泄露了知识库里没有的敏感信息，这算 RAG 权限问题吗？

### Q18. 检索失败兜底与 RAG + Agent
**问题：** 用户问题检索不到（知识库里没有或太模糊），系统却硬答或胡编；同时业务想扩展「查不到文档时自动去查外部 API」的能力，怎么设计？

**期望加分项：**
- 能设计「检索置信度 → 行为分级」的兜底策略（拒答、改写重试、放宽召回、转人工/转工具）
- 能说清 RAG 与 Agent 的边界：什么场景值得引入 Agent（多步、工具、规划）
- 能设计工具调用框架：检索失败触发外部工具、工具结果回流上下文、可校验
- 能控制 Agent 的幻觉与成本（步数限制、工具白名单、无结果时必须收尾）
- 有评测：兜底命中率、拒答合理性、工具调用成功率

**减分项：**
- 检索不到还硬答（没有置信度判断）
- 把 Agent 当万能药，所有场景都上 Agent
- 工具调用结果不校验直接进答案
- 无步数/成本控制，Agent 乱转圈

**解答：**
思路：先解决「不会答时怎么办」的确定性兜底，再谈 Agent 扩展。分级策略：① 检索置信度低（相关度低于阈值、召回为空）时，第一优先「拒答」——回答「知识库中没有相关资料」，这是 RAG 系统最重要的安全阀；② 拒答前可先自救：query 改写（口语化 → 规范）、同义词扩展、放宽过滤条件再试一次；③ 仍失败则降级：转人工、返回「可能相关问题」列表（检索旁路给 top 相关标题），或转外部工具。引入 Agent 的判断标准：任务是否「多步、需工具、需推理规划」——例如「文档查不到，但公司有 ERP 系统，能不能自动去查」，这种场景值得把「检索工具」和「API 工具」交给 Agent 编排。设计要点：① Agent 的检索工具 = 原 RAG 检索能力，失败返回「空结果」，Agent 据此决定换工具或放弃，不能虚构；② 工具调用结果必须「可校验」——答案引用工具返回原文并标注来源；③ 强约束：步数上限（如 5 步）、工具白名单、无可用结果时必须输出「无法完成」；④ 成本控制：Agent 每步都是一次 LLM 调用，先评估「只有 5% 的场景需要」再上。坑：① Agent 在检索失败时为了「完成任务」编造工具返回结果——要在工具层拦截（结果必须真实）并测评；② 把「该拒答的问题」交给 Agent，成本翻倍还绕回幻觉；③ 拒答率过高被业务投诉后盲目放宽阈值，引入更多错误回答——要量化「拒答」和「答错」哪个代价更高。

**延伸考点：** 检索置信度 0.6 的知识库问题，你会拒答、硬答还是转 Agent？怎么定这条线？Agent 执行 4 步仍无结果，如何优雅收尾（不给用户留白）？

### Q19. 在线离线链路与监控
**问题：** RAG 系统上线后，线上检索偶尔变慢、偶尔召回率波动，你怎么建立监控与诊断体系？

**期望加分项：**
- 能区分离线链路（文档入库、索引构建）与在线链路（查询、召回、重排、生成）的监控
- 能给出关键指标：延迟分位数（p50/p95/p99）、QPS、缓存命中率、检索质量、错误率
- 能给出诊断手段：端到端 tracing（各环节耗时占比）、指标波动归因
- 能给出质量监控：新文档上线后的命中率变化、embedding/模型升级的回归
- 有告警与容量规划意识

**减分项：**
- 只监控 CPU/内存
- 没有端到端 tracing，延迟高不知道卡在哪一段
- 忽略数据质量波动（索引更新失败、重复文档入库）
- 模型/参数变更不做回归

**解答：**
思路：RAG 是「数据链路 + 服务链路」双链路系统，监控要分开建。① 离线链路监控：文档入库数、解析成功率、切分成功数、embedding 成功数、索引更新延迟与失败率——每环节记「入参条数/成功/失败/耗时」，任何环节失败率上升都可能造成线上「搜不到新内容」；② 在线链路监控：分环节埋点——query 规范化、embedding、向量检索、BM25、重排、LLM 生成，统计各环节 p50/p95/p99 与耗时占比，才能定位「慢在检索还是慢在生成」；业务指标：QPS、延迟分位、缓存命中率、错误率、超时率；③ 质量监控（最容易被缺）：定期抽线上 query 算检索 hit@k（需标注）、无答案率、拒答率、用户点踩聚合，监控召回质量随知识库更新的漂移；④ 诊断：端到端 trace（query id 贯穿全链路），检索质量波动先查「索引是否更新、embedding 模型是否被换、数据是否被污染（重复/错误文档入库）」；⑤ 发布规范：模型/参数/切分策略变更走灰度 + 评测集回归 + 线上 A/B。坑：① 只监控「答没答出来」，不监控「检索命没命中」，质量问题发现滞后；② 索引构建失败无告警，静默降级到旧索引，用户搜到过期内容；③ 没有 trace，p99 从 300ms 涨到 1s 只能靠猜。

**延伸考点：** 线上检索命中率突然下降 20%，你的排查顺序是什么？p99 延迟暴涨但 p50 正常，大概率是什么问题（长尾 query、慢索引、限流）？

### Q20. RAG 系统全链路优化方法论
**问题：** 接手一个「效果一般、原因不明」的 RAG 系统，你会用什么方法系统性地把质量做上去？

**期望加分项：**
- 能给出「分层定位 → 数据质量 → 检索质量 → 生成质量 → 线上验证」的方法论
- 能区分「问题在哪一层」的诊断手段（评测集分层指标）
- 能按 ROI 排序优化项（先低成本高收益的）
- 有数据驱动意识：用评测集和线上指标说话，而不是凭感觉
- 能谈「什么时候该停下来」（优化到业务可接受线即可，避免过度工程）
- 有迭代闭环：坏例聚类 → 修复 → 回归

**减分项：**
- 一上来列一堆「可以优化的点」，没有优先级
- 只凭感觉调参数
- 不做归因就动手（比如先换模型）
- 没有停止条件，无限优化
- 忽略数据质量这一层（通常最容易见效）

**解答：**
思路：接手「效果一般」的系统，先别动手，先归因。第一步：建评测基线——抽 200 条线上真实问题做标注，跑检索指标（hit@k、MRR）与生成指标（正确率、忠实度），确认「差在哪一层」：检索差、生成差，还是数据本身就差。第二步：按 ROI 排序修复——通常优先级：① 数据质量（重复、过期、解析错、权限错——修数据往往立竿见影且最便宜）；② 检索质量（切分、混合检索、重排、阈值）；③ 生成质量（prompt、上下文组织、引用、拒答）；④ 模型升级（embedding/生成模型）放最后——最贵且边际收益未必最大。第三步：每改一项，跑同一套评测集 + 线上 bad case 回归，记录指标变化，用证据说话；同时做「坏例聚类」——把线上错误答案聚类（如「日期算错」「政策过期」「查不到」），针对性修复。第四步：定义停止条件——与业务对齐「可接受线」（如事实类正确率 ≥ 92%、拒答率 ≤ 5%），达到即停，避免为了刷指标过度工程。方法论要点：永远分层归因、永远有评测闭环、永远按 ROI 排序，优化节奏「先数据、后算法、再模型」。坑：① 不动数据质量直接上 rerank/换模型，白花钱；② 每改一个参数都全量重跑评测，成本高——只对「受影响环节」做定向回归；③ 评测集固定不变，模型过拟合评测集，要定期补充新样本。

**延伸考点：** 如果评测显示「检索 hit@5 只有 60%，但生成正确率有 80%」，矛盾吗？下一步先动哪里？知识库每天新增 100 份文档，你的「数据质量防线」怎么自动化？
