### Q1. SQL 明明建了索引却不走，候选人在线上怎么排查"索引失效"？

**问题：** 一个订单查询接口，`WHERE order_status = 1 AND created_at > '2026-01-01'` 配合 `order_status` 单列索引，线上却全表扫描。候选人被要求排查：先验证什么、再看什么，最终怎么定位"索引失效"或"索引没建对"？

**期望加分项：**
- 第一反应是用 `EXPLAIN` 看执行计划（type/key/rows/Extra），确认是否真的没走索引
- 能列举常见失效场景：`WHERE` 里对索引列做函数运算/隐式类型转换、LIKE 以 `%` 开头、OR 连接非索引列、索引列参与运算、联合索引不满足最左前缀
- 能区分"优化器放弃索引（如回表成本高于全表扫描）"与"索引真的失效"，前者常见于 `SELECT *` + 大范围查询
- 能主动用 `EXPLAIN ANALYZE`/`optimizer_trace` 或 `FORCE INDEX` 对比验证成本估算
- 会检查 `cardinality`/`SHOW INDEX` 判断索引统计是否过期（`ANALYZE TABLE` 刷新）

**减分项：**
- 不先跑 EXPLAIN 就凭经验猜
- 把所有不索引都归因"函数操作"，忽略优化器成本选择
- 不知道 `EXPLAIN` 各列含义（key、rows、type、Extra）
- 上来就说加索引，不分析数据分布与回表成本
- 忽略隐式类型转换（`phone` 是 varchar 却传数字）

**解答：**
正确顺序是"先验证再归因"。第一步跑 `EXPLAIN`，看三个关键字段：`type`（index/range/ref 是走索引，ALL 是全表）、`key`（实际用的索引）、`rows`（估算扫描行数）、`Extra`（Using where/Using index/Using filesort）。若 `type=ALL` 才进入归因环节，按概率从高到低排查：一是表达式/函数包裹索引列（`WHERE DATE(created_at)='2026-01-01'` 无法用索引，应改成范围条件）；二是隐式类型转换（字段是字符串，条件传数字，MySQL 会把列转成数字破坏索引序）；三是 `LIKE '%xx'` 前缀通配（左匹配性失效）；四是 OR 左右两侧只有一个列有索引；五是联合索引不满足最左前缀。特别注意"优化器主动弃用"这一类：当 `SELECT *` 且过滤条件选择率低（如 `order_status` 高度倾斜，90% 数据都是 status=1）时，走索引回表反而比全表扫描贵，优化器选择 ALL——这不是索引失效，而是"索引没有性价比"，对策是改覆盖索引（只查索引能覆盖的列）、或改造为"热点子集索引"。验证手段：`EXPLAIN ANALYZE`（8.0）直接给出实际耗时与执行计划对比，`optimizer_trace` 能看到成本估算过程，必要时用 `FORCE INDEX` 做对照实验证明是成本问题而非实现问题。最后检查索引统计是否过期：数据大量增删后 `cardinality` 失真会导致优化器误判，执行 `ANALYZE TABLE` 刷新。给出结论时一定带着数据说话：把"扫描行数对比"和"回表预估"讲出来，而不是只报一句"没走索引"。

**延伸考点：** 联合索引 `(a, b, c)` 下 `WHERE a=1 AND c=2` 能用到索引吗，能用到哪部分，为什么 b 断了就断后面？`order_status` 高度倾斜时，怎么设计一个能让优化器走索引的查询形态？

### Q2. 聚簇索引和二级索引的区别，为什么回表慢？怎么避免？

**问题：** 一张表有主键索引和 `(user_id)` 二级索引。候选人要讲清楚：两种索引的叶子节点分别存什么？为什么二级索引查询可能存在"回表"？什么查询能完全避免回表？

**期望加分项：**
- 能准确描述：聚簇索引（主键索引）叶子存整行数据；二级索引叶子存"索引列 + 主键值"
- 能画出查询路径：`SELECT * WHERE user_id=?` 先走二级索引定位主键，再回聚簇索引拿整行——两次 B+ 树搜索
- 能给出避免回表的方案：覆盖索引（只 SELECT 索引列，Extra 出现 Using index）、联合索引把要取的列带上
- 能讲"为什么二级索引叶子放主键而不是行指针"：避免主键变更时所有索引都要更新，保证物理地址稳定性
- 联系实际：`SELECT COUNT(*)`、`SELECT id` 这类查询天然覆盖；大字段（TEXT/BLOB）不能进索引要注意
- 能意识到主键选择影响聚簇索引形态：自增整型 vs UUID 对页分裂/插入顺序的影响

**减分项：**
- 分不清聚簇与二级索引的存储差异
- 以为所有查询都要回表
- 不知道覆盖索引要建联合索引才能覆盖多个列
- 说不出"为什么二级索引存主键值"的设计动机
- 忽略主键类型对聚簇索引写性能的影响

**解答：**
InnoDB 的表本身按 B+ 树组织，主键索引（聚簇索引）的叶子节点存放"完整行数据"，所以主键就是数据的物理组织方式，一张表只能有一个聚簇索引。二级索引（如 `(user_id)` 上的索引）叶子节点不存整行，只存"索引键 + 主键值"两个部分。查询路径分两种：`SELECT id FROM t WHERE user_id=?` 只要主键，在二级索引里就拿到了，无需回表；而 `SELECT * FROM t WHERE user_id=?` 需要 name/amount 等非索引列，必须拿着主键再去聚簇索引里搜一次——这就是"回表"，代价是两次 B+ 树搜索，若命中的行数多（几十上百行）就是成百上千次随机 IO。避免回表的经典手段是覆盖索引：让查询要的列全部出现在索引中。例如查询频繁取 `user_id, created_at, status`，就建联合索引 `(user_id, created_at, status)`，查询只 SELECT 这三列时 Extra 显示 `Using index`，全程无需回表。工程上选列有讲究：把等值条件列放前面、范围列放后面（最左前缀 + 范围后失效）；TEXT/BLOB 不能直接进索引；覆盖索引不是越宽越好——索引越宽占用空间越大、写入维护成本越高，只覆盖"高频查询需要的列"。为什么二级索引叶子放"主键值"而非"行物理指针"？因为聚簇索引下数据行随主键排序存放，若二级索引记物理地址，一旦页分裂/主键变更，所有二级索引都要同步改指针，代价极高；而主键值稳定不变，二级索引只需维护主键引用。由此引出主键设计：自增/单调整型让新行总是追加到聚簇索引末尾，避免随机插入导致的页分裂与碎片；UUID 主键则可能频繁触发页分裂，写性能显著劣化——这也是"主键尽量自增"的底层原因。

**延伸考点：** 二级索引里已含主键，为什么 InnoDB 还要用"主键 + 二级索引值"双重 B+ 树，直接存行地址不行吗（结合主键变更场景）？`SELECT COUNT(*) FROM t` 在有/无主键时分别怎么执行？

### Q3. 一条大表 JOIN 查询跑很久，候选人怎么用执行计划定位并优化？

**问题：** `SELECT * FROM orders o JOIN users u ON o.user_id = u.id WHERE o.created_at >= '2026-01-01'`，orders 表 2 亿行，跑了 20 秒。要求候选人先看执行计划的关键列，再给出具体优化手段，并说明每步的预期收益。

**期望加分项：**
- 先看 `EXPLAIN`：驱动表是谁、被驱动表是否走索引、扫描行数、是否 Using join buffer（BNL）、是否 Using temporary
- 能指出大表 JOIN 的核心矛盾：被驱动表没有合适索引时走 BNL（Block Nested-Loop），内存 join buffer 一次装不下驱动表关联行时会分批导致扫描放大
- 能给出分层优化：1) 先过滤（把 created_at 过滤条件做成驱动表/子查询缩量）；2) 被驱动表关联列建索引（走 NLJ + 索引，避免 BNL）；3) 只查必要列减少回表与传输
- 能提到更彻底的手段：查询拆分（先查 user_id 集合再 IN）、汇总表/宽表反范式、或者把大 JOIN 换到离线引擎
- 能意识到 SELECT * 在 JOIN 里的放大效应：一次 join 取出 20 个字段 vs 5 个字段的 IO 差异

**减分项：**
- 不看执行计划直接"加索引"
- 说不清 BNL 和 NLJ 的区别，不知道"Using join buffer"意味着什么
- 分不清驱动表与被驱动表，不知道应该让"小表驱动大表"
- 只做 SQL 层面的小改动，不评估数据量级与业务是否真的需要全量 JOIN
- 不考虑索引失效（如 created_at 上有函数）

**解答：**
先读执行计划定盘：重点关注 `id`（join 顺序/驱动表）、`type`、`key`（被驱动表关联列是否命中索引）、`rows`（估算行数）、`Extra` 里是否出现 `Using join buffer (Block Nested Loop)`。如果被驱动表 users 的关联列 `u.id`（主键）没被利用，或 orders 作为驱动表一次要扫描上亿行，20 秒的根因就清楚了。优化按性价比排序：第一步缩小驱动表——在 orders 上利用 `created_at` 索引或加联合索引 `(created_at, user_id)`，先只把"需要的订单"限定到最小集合，甚至可以先 `SELECT id, user_id FROM orders WHERE created_at>=...` 得到小结果集；第二步保证被驱动表走索引——users.id 是主键天然走 NLJ，若被驱动表是业务关联列（如 `o.user_id = u.id` 反过来），要给关联列建索引，让 join 从 BNL 降级为 NLJ + 索引查找，这是收益最大的动作；第三步压缩返回列——把 `SELECT *` 改成业务真正需要的 5 个列，减少回表和网络传输。如果 2 亿行、过滤后仍有几千万行参与 join，SQL 层已到极限，要往架构层想：一是查询拆分为"两段式"（先取订单的 user_id 集合，`WHERE user_id IN (...)` 去查用户，避免大 join 中间结果膨胀）；二是数据反范式化（订单表冗余 user_name 等常用字段，查询单表完成）；三是分析类报表移到离线数仓/OLAP 引擎（这是 2 亿行级 join 的正确归宿）。判断标准：优化后 `EXPLAIN` 里 BNL 消失、rows 数量级下降、返回列变小，实测耗时从 20s 降到秒级。实践中的坑：join 方向搞反（小表驱动大表原则）、对驱动表条件列加了函数、以及把 join 结果又接子查询导致临时表堆积——这些都要用 EXPLAIN 逐步验证。

**延伸考点：** MySQL 8.0 里 BNL 已被 hash join 取代，这两者的适用场景和参数（join_buffer_size）怎么理解？"先 join 再过滤"和"先过滤再 join"在什么情况下结果不同？

### Q4. 事务隔离级别到底解决什么问题？RR 下的幻读为什么还能发生？

**问题：** 候选人被要求用一句话+一个例子区分 READ COMMITTED 和 REPEATABLE READ，并解释：MySQL 默认 RR 下，两个事务之间"插入一条新记录"为什么会出现幻读，是怎么被锁解决的？

**期望加分项：**
- 能准确说出三种异常：脏读（读到未提交）、不可重复读（同一条数据前后不一致）、幻读（同一范围前后行数不一致）
- 能说出隔离级别对应：RC 解决脏读、RR 解决脏读+不可重复读、可串行化全部解决；幻读在 RR 下靠 MVCC 快照读消除、靠间隙锁/临键锁在加锁读下解决
- 能区分两种幻读：快照读（MVCC 看不到新行）与当前读（`SELECT ... FOR UPDATE`/UPDATE 需要加锁，防止新行插入到锁范围）
- 能讲 MySQL RR 的现状：RR 下有 Next-Key Lock 其实已经杜绝当前读下的幻读，但"快照建立后 insert 再 update"这类边界仍有讨论空间
- 能给出生产建议：大部分业务 RC 就够，MySQL 默认 RR 有历史原因（binlog 复制格式演进）；RC 下锁更少、并发更好
- 会设计验证实验：开两个会话，用 `BEGIN` 分别演示三类异常

**减分项：**
- 把不可重复读和幻读混为一谈
- 认为 RR 就彻底没有幻读，说不清锁的机制
- 不知道 MVCC 与锁是"快照读/当前读"两条路径
- 说不清 MySQL 为什么默认 RR（与 binlog 主从复制格式兼容性有关）
- 不结合具体 SQL 讲，只背定义

**解答：**
先讲清三类异常与级别对应：脏读——读到了未提交事务的修改（RC 已禁止，RU 才有）；不可重复读——同一事务内两次读同一条记录，值被其他已提交事务改掉（RC 无法避免，RR 通过 MVCC 快照解决）；幻读——同一事务内两次范围查询，第二次多了新插入的行（读一致性由 MVCC 快照保证，但"当前读"下需要间隙锁）。MySQL InnoDB 的 RR 里，普通的 `SELECT` 是快照读，走 MVCC 版本链，事务内读到的是一致快照，所以新增的行"看不见"，幻读在快照读层面不存在；但 `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是当前读，必须看到并锁住最新数据——如果只锁住已有行，新插入的行（"间隙"里的数据）会漏锁，导致两次加锁读结果不同，这才是真正的幻读来源。InnoDB 的解法是 Next-Key Lock：对命中的记录加行锁（Record Lock）+ 对记录前面的间隙加间隙锁（Gap Lock），两者合起来锁住"一个范围"，其他事务无法在该范围内插入新记录，从而杜绝当前读下的幻读。为什么 MySQL 默认用 RR 而不是 RC：早期 binlog 默认 statement 格式，RC 下"先 delete 后 insert"等操作在主从执行顺序不同会产生数据不一致，RR 下对加锁的宽容能保证 statement 复制安全（后来自动切换 row 格式后 RC 也安全，但默认值已固化）。生产上的取舍：RC 下间隙锁用得少、死锁概率低、并发度更高，很多高并发团队把隔离级别降为 RC 换取性能；代价是 binlog 必须是 row 格式、且业务要接受"同一事务两次读可能不同"。总结一句话：MVCC 解决"读一致"，锁解决"写隔离与幻读"，两者配合构成 InnoDB 的隔离语义。

**延伸考点：** RC 与 RR 在"UPDATE 未提交事务的行"上的阻塞行为差异（半一致性读）是什么？怎么用 `SELECT ... FOR UPDATE` + 间隙锁手工构造一个"串行化"场景？

### Q5. MVCC 是怎么做到"读不阻塞写、写不阻塞读"的？undo log 和版本链怎么工作？

**问题：** InnoDB 高并发下读与写互不阻塞，靠的是 MVCC。候选人要讲清楚：每条记录的版本链怎么组织？`READ COMMITTED` 和 `REPEATABLE READ` 的快照（ReadView）创建时机分别是什么？undo log 在其中的作用？

**期望加分项：**
- 能说出版本链结构：行数据里有隐藏列 `trx_id`（最后修改事务 ID）和 `roll_pointer`（指向 undo log 中旧版本），形成历史版本链
- 能讲 ReadView 的核心字段：`m_ids`（活跃事务列表）、`min_trx_id`、`max_trx_id`、`creator_trx_id`，判断"当前事务能否看到某个版本"的四条规则
- 能准确区分快照创建时机：RC 是**每次 SELECT 都生成新 ReadView**，所以能看到已提交的新值（不可重复读）；RR 是**第一个 SELECT 时生成一次 ReadView** 并复用，所以前后一致
- 能讲 undo log 的角色：旧版本快照靠 undo log 链保存，回滚也靠它；快照的清理靠 purge 线程
- 能讲清"快照读 vs 当前读"：MVCC 只服务快照读，加锁读/写操作走锁
- 联系生产：长事务会导致 undo log 膨胀、ReadView 失效慢、历史版本积累拖慢 purge

**减分项：**
- 把 MVCC 只理解成"每个事务一份拷贝"的错误模型
- 说不清 trx_id 与 roll_pointer 两个隐藏列
- ReadView 的创建时机说反（RC/RR 记混）
- 不知道 undo log 既要回滚又要支撑 MVCC 历史版本
- 不讨论长事务对 undo 和 purge 的影响

**解答：**
MVCC 的思想是"记录保留历史版本，读事务通过可见性判断选版本"，从而读不需要加锁、写只锁自己写的行。具体机制：InnoDB 每行数据带两个隐藏列——`trx_id` 记录最后修改这行的事务 ID，`roll_pointer` 指向 undo log 中该行的上一个版本；每次更新不是覆盖而是"在 undo log 里生成一个旧版本并链接"，行通过 roll_pointer 串成版本链。读数据时，事务要判断版本链上哪个版本"对自己可见"，依据是 ReadView：创建时记录此刻活跃事务列表 m_ids（min~max 区间 + 自己的 trx_id）。判断规则核心是——版本 trx_id 不在活跃列表里且已提交，则该版本可见；否则沿版本链往旧版本找。关键差异在快照创建时机：`READ COMMITTED` 每次 SELECT 都新建 ReadView，所以能读到其他事务刚提交的新版本，产生不可重复读；`REPEATABLE READ` 只在事务第一次 SELECT 时建 ReadView 并一直复用，之后其他事务的提交对它不可见，前后读一致——这是 RR 一致性快照的精确机制。undo log 在这个体系里承担两个职责：一是事务回滚时把数据恢复到原始版本（反向应用 undo）；二是为 MVCC 提供历史版本（正向保留版本链）。因此长事务是性能隐患：它持有的 ReadView 会让"老版本"一直被认定为"可能被需要"，purge 线程无法清理对应 undo 段，undo log 持续膨胀，表空间只增不减，且版本链过长会拖慢每次读的版本遍历。工程上的验证手段：`information_schema.innodb_trx` 查长事务、`SHOW ENGINE INNODB STATUS` 看 undo 与 purge 状态。总结：读快照由 ReadView + 版本链决定，写隔离由锁决定，undo log 是两者的公共基础设施。

**延伸考点：** 一个 RR 事务"先读后写再读"，第二次读到的值为什么可能比自己写的新（当前读与快照读的混合）？purge 线程和"回滚段"在版本回收上分别承担什么？

### Q6. 死锁发生了，候选人怎么快速定位：看什么视图、分析什么信息、给出什么解法？

**问题：** 线上日志频繁出现 `Deadlock found when trying to get lock; try restarting transaction`。要求候选人给出完整的排查流程：从日志/视图拿到什么证据 → 分析出两条 SQL 的锁依赖 → 给出至少三种落地解法。

**期望加分项：**
- 能说出查看手段：`SHOW ENGINE INNODB STATUS` 里的 `LATEST DETECTED DEADLOCK` 段，或 8.0 的 `performance_schema.data_lock_waits` / `sys.innodb_lock_waits`
- 能读死锁现场：两组事务各自的等待锁与持有锁（`WAITING FOR THIS LOCK TO BE GRANTED` 与 `HOLD OF THE LOCK`），还原锁等待图
- 能分析典型成因：两个事务以不同顺序加锁（A→B vs B→A）、间隙锁互相覆盖、二级索引与主键锁获取顺序不同
- 给出解法：统一加锁顺序；减少事务持锁时间（大事务拆小）；用 RC 隔离级别减少间隙锁；必要时 `SELECT ... FOR UPDATE` 加锁顺序用索引保证一致性
- 知道 MySQL 会自动检测死锁并回滚其中一个事务（代价更小的一方），应用层需要重试
- 会从索引设计角度排查：是否因某个查询走全表扫描而锁了过多行

**减分项：**
- 只会说"重试"或"加锁顺序"，给不出排查证据链
- 不读死锁现场信息，凭空猜测
- 不知道 MySQL 是"立即检测"而非"超时"
- 不区分死锁与锁等待（lock wait timeout）是两回事
- 不检查事务里是否夹了外部 RPC/慢 SQL 导致持锁过长

**解答：**
死锁 = 两个事务各自持有一把锁、又都在等对方手里的锁，形成环。排查第一步是拿现场：执行 `SHOW ENGINE INNODB STATUS`，读 `LATEST DETECTED DEADLOCK` 段——里面给出了**两个事务各自的 SQL**、每条持有的锁（HOLD OF THE LOCK）与正在等待的锁（WAITING FOR THIS LOCK TO BE GRANTED）、锁的物理位置（记录所在行的主键/索引值）。有了这张锁等待图，就能还原环：典型如事务 A `UPDATE t SET ... WHERE id=1` 再 `UPDATE t SET ... WHERE id=2`，事务 B 顺序相反，两者各持一锁互等另一锁；另一个高频成因是二级索引命中行后，先加二级索引锁再回主键加锁，两条 SQL 走不同索引/不同顺序就会交叉。定位到环后给解法，按成本从低到高：1) **统一加锁顺序**——所有相关事务按同一顺序（如按主键排序）更新，从源头消环；2) **缩小锁范围**——让 WHERE 走索引，避免全表/大范围扫描锁住大量行；3) **缩短持锁时间**——把大事务拆小、事务内不夹外部 RPC/慢查询，减少锁重叠窗口；4) **降低隔离级别**——RR 下的间隙锁是死锁高发源，业务可接受时降 RC；5) 实在无法避免的，**应用层捕获死锁异常做有限次重试**（MySQL 自动回滚死锁中代价更小的一个事务，抛 1213 错误，业务必须重试，这是底线保障）。还要能区分"死锁"与"锁等待超时"（lock wait timeout，单方等锁超 50 秒默认报错）——前者是环、后者是排他持锁太久，解法不同。最后，如果死锁只在高峰期出现，优先怀疑"批量任务与在线业务抢同一批行"，检查定时任务是否在同一事务里锁了过多行。

**延伸考点：** 一个 UPDATE 命中二级索引时，加锁的顺序为什么是"二级索引锁 → 聚簇索引锁"，这会导致什么交叉？`innodb_lock_wait_timeout` 与死锁检测在 8.0 里分别怎么配置和调优？

### Q7. 深分页 `LIMIT 1000000, 20` 为什么会慢，怎么优化到毫秒级？

**问题：** 一个列表接口用户翻到第 5 万页，SQL 是 `SELECT * FROM orders ORDER BY created_at LIMIT 500000, 20`，耗时 3 秒。要求候选人讲清"为什么这么慢"的机制，并给出 2~3 种可行的改造方案及取舍。

**期望加分项：**
- 能讲清机制：LIMIT offset 的实现是"扫描 offset+size 行再丢弃前 offset 行"，offset 越大扫描越多，且 SELECT * 还要回表，第 5 万页可能扫描几十万行
- 方案一：延迟关联/子查询——先 `SELECT id FROM orders ORDER BY created_at LIMIT 500000,20`（只走索引不回表），再用 `WHERE id IN (...)` 取完整行
- 方案二：游标分页（keyset）——用上一页最后一条的 `(created_at, id)` 做 `WHERE (created_at,id) > ('2026-01-01', 12345) LIMIT 20`，每页都是索引定位，复杂度与页数无关
- 方案三：结合业务限制——不允许跳页/最多翻 100 页（产品约束），或直接按时间/分片翻页
- 能指出游标分页的代价：无法跳页、排序字段需唯一（加主键兜底）
- 会说明 `ORDER BY created_at` 需要联合索引 `(created_at)` 或 `(created_at, id)` 支撑

**减分项：**
- 只会背"用游标分页"，讲不清 LIMIT 慢的底层机制
- 游标分页不知道加主键保证排序稳定性
- 不做产品/技术取舍，一律上"最优"方案
- 忽略 SELECT * 的回表放大
- 不知道深分页优化还要配合索引设计

**解答：**
先讲机制：MySQL 执行 `LIMIT offset, size` 时，需要扫描 offset+size 行，然后把前 offset 行丢弃。offset=500000 意味着要遍历 50 万行；如果 `SELECT *` 且走的是二级索引，这 50 万行每一行都要回聚簇索引取完整数据——这是双重放大（扫描行数 + 回表次数）。所以深分页慢的本质是"无条件读取前面所有行"，页号越深代价越高，复杂度 O(offset)。优化三板斧：第一板斧是**延迟关联**（成本最低、改动最小）：先只查主键，`SELECT id FROM orders ORDER BY created_at LIMIT 500000, 20`——这条语句可以完全走索引（Extra: Using index），避免 50 万次回表；拿到 20 个 id 后再 `WHERE id IN (...)` 一次性取完整行，回表只发生 20 次。第二板斧是**游标分页（keyset pagination）**：不再用 offset，而是记住上一页最后一条的排序值 `WHERE (created_at, id) > ('2026-01-01 12:00:00', 99999) ORDER BY created_at, id LIMIT 20`——每一页都是"索引直接定位 + 取 20 行"，复杂度恒定 O(20)，页号再深也快；前提是排序键要加唯一性（主键兜底）避免重复值导致漏页，且查询条件变成"下一页"语义（前端传 last_cursor，或服务端编码 token），因此**不能随机跳页**。第三板斧是**产品约束**：绝大多数业务根本不需要翻到第 5 万页，列表接口限制最大页码（如 100 页）、或改为按时间分段浏览、或改成"加载更多"配合游标——这往往是性价比最高的方案。取舍结论：跳页需求必须保留 → 延迟关联；只做"下一页/加载更多" → 游标分页；海量导出 → 流式/游标 + 服务端分批。实践中的坑：`ORDER BY created_at` 若无索引会触发 filesort 全表排序，必须先建 `(created_at, id)` 联合索引；游标分页对"并发下新数据插入"天然稳定（基于值而非行号），这是它优于 offset 的额外好处。

**延伸考点：** 游标分页在"排序字段是普通列（有重复值）"时怎么写 WHERE 才不漏不重？延迟关联如果排序字段上不是索引，第一板斧还成立吗，为什么？

### Q8. 候选人被要求设计用户订单表的索引：主键、查询模式、联合索引顺序怎么定？

**问题：** 一张订单表 `orders(id, user_id, status, created_at, amount)`，高频查询有三类：按用户查订单、按用户+状态查、按状态+时间查列表。要求候选人给出完整索引设计（建哪些索引、列顺序依据），并指出"多建索引的代价"。

**期望加分项：**
- 能按最左前缀原则设计联合索引：`(user_id, status, created_at)` 或 `(user_id, created_at)` 覆盖前两类查询
- 能识别第三条查询（status + created_at）与前面冲突：status 选择率低，需要 `(status, created_at)`，但要评估 status 倾斜导致优化器弃用索引
- 能讲"索引不是越多越好"：每个索引都增加写入 IO、占用空间、优化器选择变复杂
- 能考虑覆盖索引：高频查询 SELECT 的列尽量进索引减少回表
- 能说清范围条件与等值条件的列顺序：等值列放前面、范围列放最后
- 会结合数据量评估：几百万行和上亿行索引策略不同

**减分项：**
- 每个查询单独建一个索引（联合索引不会用）
- 不考虑 status 的选择率/倾斜度，盲目建 `(status, created_at)`
- 不知道联合索引列顺序对"范围后失效"的影响
- 不考虑写入放大：高写入表每个索引都是成本
- 不分析实际查询频率，平均用力

**解答：**
索引设计的输入是"查询模式 + 数据分布"，不是机械套公式。先分析三类查询：1) `WHERE user_id=?`（按用户查全部）→ 单列 `user_id` 或联合索引的最左列；2) `WHERE user_id=? AND status=?` → 联合索引 `(user_id, status)` 命中；3) `WHERE status=? AND created_at BETWEEN ...` → 需要 `status` 或 `(status, created_at)` 在前。合并观察：前两类可以共用一个联合索引 `(user_id, status, created_at)`——最左前缀使 `(user_id)`、`(user_id,status)` 都能用，created_at 放在最后用于排序或范围（注意范围条件放最后，因为范围后的列无法用于索引过滤）。第三条查询单独建 `(status, created_at)` 前要评估：`status` 若高度倾斜（比如 95% 是"已完成"），优化器会认为走这个索引回表不如全表扫描，索引形同虚设——此时要么改成 `(status, created_at, 需要返回的列)` 做成覆盖索引，要么调整查询形态（按时间分页配合游标）。第三，考虑覆盖索引优化高频路径：若查询只取 `id, user_id, status, created_at` 且表中还有 amount 等大字段，可让高频联合索引包含这些列，减少回表（Extra: Using index）。最后必须主动讲"索引的代价"：每个二级索引都意味着——插入/更新时额外维护索引树（写放大）、占用额外存储空间、优化器要评估更多索引组合。所以设计原则是"宁缺毋滥"：用 1~2 个联合索引覆盖 80% 查询，而不是 4~5 个单列索引。评估方式：用 EXPLAIN 验证每条高频 SQL 是否走预期索引（type/key/rows/Extra），用 `SHOW INDEX FROM orders` 检查重复索引，压测写入场景对比索引数量对 TPS 的影响。实践中的坑：不要给低基数列（status）单独建索引；线上加索引用 Online DDL 或 gh-ost 避免锁表；索引变更后要回归 EXPLAIN 防止优化器换路。

**延伸考点：** 如果把 created_at 放联合索引中间（`(user_id, created_at, status)`），`WHERE user_id=? AND status=?` 还能用到索引吗，为什么？覆盖索引方案下 amount 字段放不进索引（太大），怎么权衡？

### Q9. 主从复制延迟怎么量化？候选人给出从现象到根因到解决方案的完整链路。

**问题：** 业务反馈"写完主库立即从库读"经常读不到，DBA 确认从库 seconds_behind_master 波动大。要求候选人：说明延迟的量化指标怎么读、延迟的可能根因（至少 3 类）、以及一套有效的缓解方案。

**期望加分项：**
- 能说出量化指标：`SHOW SLAVE STATUS` 的 `Seconds_Behind_Master`（IO 线程与应用线程的差距，秒级粗粒度，且可能有偏差）、`SHOW MASTER STATUS` 的 binlog pos 对比、或用 `pt-heartbeat` 秒级精度监控
- 根因分类：1) 从库单线程应用 binlog（主库并行 8~16 线程写，从库串行 apply）——高频大事务/批量导入最致命；2) 大事务（一条 UPDATE 影响百万行，binlog 巨大）导致 apply 卡住；3) 从库被读流量打满（大量报表/备份查询抢占 IO/CPU）；4) 网络/磁盘、从库无索引（同一条 DML 在主从执行成本不同）
- 方案：并行复制（8.0 的 MTS，`slave_parallel_workers` + 按库/按表并行）、大事务拆分、从库专用（索引/配置调优）、读写分离的"写后读一致性"兜底（写后读主库/主库权重）
- 能谈架构层：半同步复制、或写后延迟可接受的场景降级
- 认识 `Seconds_Behind_Master` 的坑：从库无流量时该值可能不涨、大事务期间计算方式有偏差

**减分项：**
- 只会报"有延迟"，给不出指标与监控手段
- 不知道 MTS 并行复制参数
- 把所有原因归为"机器性能差"
- 不区分"延迟多久可接受"（业务读的还是历史数据）
- 不了解大事务对 binlog 与 apply 的放大

**解答：**
先建立"延迟 = 写入主库与从库应用完成的时间差"的定义，再讲量化。最常用指标是 `SHOW SLAVE STATUS` 的 `Seconds_Behind_Master`，它等于"主库当前 binlog 时间 - 从库 SQL 线程已应用位置的时间"，但这是**秒级粗粒度**且两个已知偏差：大事务期间该值计算基准是"事件开始时间"可能突然飙高又回落；从库处于空闲时不更新。要精确监控用 `pt-heartbeat`（从库每秒写心跳表，主从心跳差值即真实延迟，毫秒级）。根因分析按三类排查：一是**应用线程单点**——主库 8 核并行写（并行提交），从库历史上 SQL 线程单线程串行 apply，高写入时必然追不上；8.0 已支持 MTS（多线程复制），默认按库并行，参数 `slave_parallel_workers`、`slave_parallel_type` 调优。二是**大事务**——单条 UPDATE 命中百万行，生成的 binlog 可能是几十 MB，从库要连续应用完整个事务才算完成，期间延迟瞬时拉满；解法是拆事务（分批 LIMIT 更新）。三是**从库过载**——从库同时扛报表查询、备份、导入导出，IO/CPU 被抢，apply 变慢；解法是从库专职化、或再加只读从库分流。四是**从库缺索引**——主库的 DML 走索引很快，从库同样的 SQL 因为索引缺失做全表扫描，执行时间被放大（常见于从库重建后索引没同步）。缓解方案分三层：应用层——写后立刻读走主库或强制主库（"写后读一致性"），读历史数据接受短延迟；中间层——监控延迟阈值，超过阈值读流量切走（从库摘除）；架构层——开启半同步复制（主库等从库 ACK 才提交，损失写性能换强一致）、优化 binlog 格式（row 格式大事务更明显，考虑压缩/分区）。实践中的坑：MTS 并行度不是越高越好，跨库事务/DDL 会退化为串行；大事务不仅延迟还占主库 binlog 磁盘，应源头治理。

**延伸考点：** `Seconds_Behind_Master` 在"主库写入很慢但 binlog 在赶"时的语义，怎么理解它不等于"数据丢失"？并行复制在"跨库事务"和"单库多表"两种场景下并行度有什么不同？

### Q10. binlog 有 row / statement / mixed 三种格式，候选人怎么选并说明各自风险？

**问题：** 团队要配置 binlog 格式。候选人要讲清三种格式的存储差异、主从复制与数据恢复的影响，以及生产环境怎么选、有没有混合用的场景。

**期望加分项：**
- 能说出三种格式的本质：statement 记 SQL 语句；row 记"每行变更前后值"；mixed 让 MySQL 根据语句类型自动选
- 能讲 row 的优势：确定性高、主从结果一致、支持闪回/误删恢复（能反推旧值）、`on update`/函数/存储过程结果一致
- 能讲 row 的代价：大事务时 binlog 体积巨大（一条 UPDATE 100 万行 → 100 万条 before/after 行记录）
- 能讲 statement 的风险：非确定性函数（NOW/RAND/UUID）主从执行结果可能不一致、DDL 与数据混用问题
- 生产结论：8.0 默认 row；高并发大事务团队会评估体积，一般仍选 row（可用 binlog 压缩/事务拆分缓解）；statement 基本只用于兼容老环境
- 能联系其他功能依赖：Canal/Debezium 等 CDC、数据备份（xtrabackup 基于物理备份 + binlog）、闪回工具依赖 row

**减分项：**
- 只知道"row 更安全"说不出代价
- 不了解 row 格式对 binlog 体积的放大
- 不知道 mixed 的自动判定规则
- 说不清 CDC 为什么必须 row 格式
- 不考虑恢复场景对格式的依赖

**解答：**
三种格式的核心差异在"记录什么"：statement 记原始 SQL（`UPDATE t SET x=1 WHERE id>100`），体积小但**依赖执行环境的确定性**——如果 SQL 里有 NOW()、RAND()、UUID() 或依赖表数据顺序，主从执行结果可能不一致（比如一条语句在不同库的索引选择不同导致影响行不同）；row 格式记录"每一行变更前后的完整值"，完全确定、主从结果必然一致，代价是**体积放大**：`UPDATE t SET x=1 WHERE 1` 改 100 万行，row 格式就会在 binlog 里写 100 万条 before/after 行记录，大事务时 binlog 暴涨几 GB；mixed 是折中：MySQL 判断语句是否"确定"，确定用 statement、不确定（函数/多表）用 row，但引入"执行时才决定格式"的复杂性。生产选择：8.0 默认 row 且有充分理由——现代 MySQL 的生态（CDC 工具 Canal/Debezium 订阅 binlog 做增量同步、数据校验、误删恢复）**全部依赖 row 格式**，因为只有 row 能还原出"哪行的旧值是什么"；主从复制安全、在线 DDL 兼容性也都以 row 为基准。row 的体积问题用工程手段化解：大事务拆小（LIMIT 分批）、开启 binlog 压缩（`binlog_transaction_compression`，8.0.20+）、提高 `binlog_row_image` 到 minimal（只记 changed 列，牺牲一点排查便利）。statement 的适用场景基本只剩"极低写入量 + 无 CDC 需求 + 老版本兼容"。恢复与回滚：基于 xtrabackup 物理备份 + binlog 增量恢复时，row 格式还能配合 flashback 工具（把 before 值拼成反向 SQL）实现"误删恢复"，这是 row 在生产中不可替代的价值。实践中的坑：row 格式下大事务的 binlog 会让从库 apply 变慢（前面 Q9 的延迟问题）、主库 binlog 磁盘占用翻倍，所以要监控 binlog 增长并及时归档/清理。

**延伸考点：** `binlog_row_image=minimal` 只记 changed 列，它对闪回工具和主从一致性分别有什么影响？mixed 格式下一条"UPDATE 含子查询"的语句会被判定为哪种格式，为什么？

### Q11. 单表数据量过亿，候选人怎么论证"分库分表 vs 不拆"？拆了之后哪些问题必须考虑？

**问题：** 订单表 3 年积累 3 亿行，查询开始变慢。要求候选人：先给出"不拆也能优化"的评估清单，再讲分库分表带来的三大类新问题（查询、事务、运维），并给出分片键与路由方案的选型。

**期望加分项：**
- 先算账：3 亿行如果索引合理、查询都走主键/索引，未必需要分片；先评估归档/冷热分离/分区表/读写分离是否能解决
- 能讲分片键选择：按 user_id 分片（订单天然按用户聚合）、避免按时间分片导致热点（写入集中在今天）；范围分片 vs 哈希分片取舍
- 能讲拆后的查询问题：跨分片查询（多分片聚合、`GROUP BY` 汇总要中间层合并）、非分片键查询变全分片广播
- 事务问题：跨分片分布式事务（2PC 不可用、TCC/本地消息表/Saga 取舍）
- 运维问题：扩容要迁移数据（一致性哈希缓解）、分片间数据倾斜、备份与恢复复杂度
- 能给出"分库分表前必答"的三问：数据量真的到瓶颈了吗？只读场景能不能先解决？拆分收益是否大于复杂度？

**减分项：**
- 一上来就"分库分表"，不做可行性评估
- 分片键选错（按时间分片导致写入热点）
- 不知道跨分片 join/聚合要应用层合并
- 忽略分布式事务的代价
- 不考虑扩容与数据迁移方案
- 不区分"分库"与"分表"的目的差异（并发 vs 数据量）

**解答：**
正确的思考顺序是"先证明必须拆，再设计怎么拆"。第一步评估不拆方案：3 亿行在 InnoDB 里并不算天文数字——如果查询都走索引、数据能按时间归档（历史订单移到冷表/归档库）、热点只集中在最近几个月（可用 MySQL 分区表按月份分区，查询自动裁剪）、读多写少可加从库读写分离，很可能不需要分片。只有当这些手段都做尽、仍出现"索引扫描行数过大""写并发撞行锁""单库磁盘/TPS 到物理上限"时，才进入分片。第二步选分片键与路由：订单场景分片键首选 `user_id`（用户维度查询占绝大多数，天然避免跨片）；路由用**哈希分片**（`hash(user_id) % N`，分布均匀，但扩容要迁移）或**范围分片**（按用户 ID 段/按时间，扩容简单但容易数据倾斜与热点）；要特别警惕按时间分片的陷阱——写入永远集中在"今天"这一片，热点单点反而更严重。第三步接受并设计三大新问题：一是跨分片查询——分片键之外的条件（如按订单号查）必须全片广播，聚合/排序要在应用层做中间合并，所以非分片键查询要么建"全局索引表"（映射表：order_no → user_id → 分片），要么接受广播；二是跨分片事务——传统本地事务失效，选型上 TCC（强一致、实现复杂）/本地消息表+MQ（最终一致、实现简单）/Saga，绝大多数订单业务用"最终一致 + 对账"即可，不要为了强一致上 2PC；三是运维——扩容要在线迁移（一致性哈希 + 双写/后台搬数）、分片间数据倾斜要监控、备份/恢复要按片管理。最后记住一个判断标准：**分库分表解决的是"单机物理瓶颈"，不是"SQL 写得烂"**；如果 3 亿行只是查询慢，先优化索引与架构，拆分是最后手段，且拆分后的复杂度需要专门的中间件（如 ShardingSphere）和团队来扛。

**延伸考点：** 一致性哈希分片扩容时，数据怎么平滑迁移（虚拟节点 + 双写回放）？"全局订单号"用分布式 ID（雪花/UUID）与分片键的关系，为什么全局唯一不能替代分片路由？

### Q12. 候选人被问"怎么给一张 2 亿行的大表加索引不锁业务"，Online DDL 与 gh-ost 怎么选？

**问题：** 线上订单表 2 亿行，要新增一个联合索引。要求候选人说明 MySQL 原生 Online DDL（ALGORITHM=INPLACE）的限制，以及为什么大厂常用 gh-ost 等工具，并讲清 gh-ost 的核心机制。

**期望加分项：**
- 能说出 Online DDL 的分级：`ALGORITHM=COPY`（锁表重建，禁用于大表）、`INPLACE`（允许并发 DML，但分两步：prepare+commit 时短暂持有排他锁）、`INSTANT`（8.0 只加列）
- 能指出 INPLACE 的实际限制：要"重建表"的 DDL（如改列类型、加索引需要 rebuild）期间有短暂的 MDL（元数据锁）窗口、磁盘空间要双倍、长事务/复制延迟会影响
- 能讲 gh-ost 机制：影子表（ghost 表）——先建新表结构 → binlog 监听原表变更（row 格式）回放到影子表 → 分块拷贝（chunk-by-chunk，每块限流）→ 最后原子切换表名（RENAME）+ 清理
- 能说出 gh-ost 优势：不锁原表、限速可调（控制主库压力）、失败可回滚、兼容所有 DDL（只要 row binlog）
- 能指出前提：必须开 row 格式 binlog；表必须有主键/唯一键（用于分块定位）
- 会给出生产流程：低峰期执行、监控主从延迟与慢查询、预留磁盘、演练回滚

**减分项：**
- 只会说"用 gh-ost"，说不清机制与前提
- 不知道原生 INPLACE 仍有锁窗口与双倍磁盘问题
- 不知道 DDL 期间主从复制的放大问题
- 忽略前置条件（binlog 格式、主键）
- 不考虑执行窗口（白天大促还是低峰）

**解答：**
加索引这类 DDL 对 2 亿行表的冲击点是"重建期间锁与资源"。MySQL 原生支持分三档：COPY 算法直接拷贝重建、全程锁表，大表不可接受；INPLACE（默认，如 `ALTER TABLE ADD INDEX`）不拷贝数据、允许并发 DML，但**并非零影响**——它分三个阶段，prepare 与 commit 两个瞬间需要获取排他 MDL（元数据锁），且内部要扫描全表构建索引（期间占用 IO/CPU、产生大量 redo/undo），更关键的是**磁盘需要临时存储**、主从复制时从库也要同样执行一遍造成延迟。8.0 的 INSTANT 只适用于"加列"等原地操作，加索引不属于。所以大厂在超大规模表上普遍用第三方工具 gh-ost（GitHub 出品），核心机制是"影子表 + binlog 回放"：1) 先创建一个结构相同的新表（ghost 表，含目标索引）；2) 拷贝数据：按主键分批（chunk）把原表数据插到 ghost 表，每批之间 sleep 限速，可配置"最大复制延迟阈值"，超过就自动暂停——这是保护主库和从库的关键；3) 同时，gh-ost 伪装成一个从库连接读取原表的 binlog（**前提是 row 格式**），把拷贝期间的新增变更回放到 ghost 表，保证两表一致；4) 最后执行原子切换：`RENAME TABLE original TO _del, ghost TO original`（一次 RENAME 在事务内交换表名），业务无感知，原表随后清理。前提条件：binlog 必须 row 格式、原表必须有主键或唯一键（chunk 定位与去重要靠它）、从库连接权限足够。与原生 INPLACE 的取舍：原生适合中小表/允许短窗口；gh-ost 适合超大规模且要"完全无锁、可暂停、可回滚"。生产执行规范：低峰期、预留 1.5 倍表空间磁盘、监控主从延迟与慢查询、先在小表演练、备好 kill 回滚路径。实践中的坑：gh-ost 的 binlog 回放依赖从库拉取，若主库 binlog 过期时间太短或从库挂掉，切换会失败；切换瞬间仍有几毫秒的 MDL 竞争，需监控抖动。

**延伸考点：** gh-ost 的分块拷贝中"每一批怎么定位"（用主键范围游标），为什么每批之间要 sleep（限速与复制延迟的关系）？RENAME 切换为什么能做到"原子、业务无感"，MySQL 的 RENAME TABLE 在同一事务中的行为是什么？

### Q13. 候选人要排查一条"有时快有时慢"的查询：缓存、优化器统计、锁竞争，怎么逐层排除？

**问题：** 同一 SQL 白天 20ms、晚上高峰 2s，且不稳定。要求候选人给出完整排查清单：从查询缓存/缓冲池、到优化器统计、到锁与资源竞争、到主从差异，逐层怎么验证和排除？

**期望加分项：**
- 先排除"结果是否一致"（查询计划是否稳定）：用 `EXPLAIN` 对比两次，看是否走了不同索引/表扫描
- 能想到缓冲池因素：Buffer Pool 冷热——同一查询第一次冷读（读磁盘）慢，后续命中缓存快；`SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%'` 看读命中率
- 能想到优化器统计过期：数据分布变化导致 `cardinality` 失真、走错索引，用 `ANALYZE TABLE` 刷新后对比
- 能想到并发与锁：高峰期行锁/间隙锁竞争（`SHOW ENGINE INNODB STATUS` 看锁等待、`performance_schema` 看 wait）、redo/undo 压力、IO 队列
- 能想到系统资源：CPU/磁盘 IO 排队（`iostat`/`vmstat`）、`SHOW GLOBAL STATUS LIKE 'Threads_running'` 看连接堆积
- 给出"慢在读取还是慢在等待"的判断方法：`EXPLAIN ANALYZE` 分阶段耗时、`performance_schema` 的 wait 事件定位

**减分项：**
- 只怪"数据量涨了"，不做对照实验
- 不知道 Buffer Pool 冷热导致的"首次慢"
- 不用 `ANALYZE TABLE` 排除统计信息问题
- 把锁等待和慢查询混为一谈
- 不做时间维度对比（白天/高峰、峰值 vs 平峰）

**解答：**
"时快时慢"的排查原则是**做对照实验 + 分层定位**。第一步排除执行计划不稳定：同一 SQL 在高峰期和平峰各跑一次 `EXPLAIN`，若 key/type/rows 不同，说明优化器在两个时间选路不同——优先怀疑统计信息过期（数据分布被大事务改变），执行 `ANALYZE TABLE` 刷新统计再对比；也检查是否因 `index hint` 缺失去正确索引。第二步排除缓冲池因素：InnoDB 有 Buffer Pool 缓存数据页，冷数据第一次读走磁盘（慢）、热数据命中内存（快）——"第一次慢、第二次快"是冷热页的典型特征；用 `SHOW GLOBAL STATUS` 看 `Innodb_buffer_pool_read_requests`（逻辑读）与 `Innodb_buffer_pool_reads`（物理读）算命中率，低于 95% 说明池子不够或数据被频繁挤掉，结合 `show engine innodb status` 的 Buffer pool 段确认。第三步排除锁与并发：高峰期慢更多是"等锁"而非"执行慢"——`SHOW ENGINE INNODB STATUS` 的 `TRANSACTIONS` 段能看到当前锁等待；`performance_schema.events_waits_current` 能精确定位等待的是 IO 还是锁（wait/io、wait/lock）。注意区分：`Sending data` 状态表示在真正执行，`Waiting for table metadata lock` / `Lock wait` 表示在等别人。第四步排除资源竞争：`iostat` 看磁盘 util 是否接近 100%、`vmstat` 看 CPU 是否排队、`Threads_running` 长期 > 几十说明连接堆积排队执行——这些都是"宿主过载"而非 SQL 本身问题。第五步主从差异：如果是读从库，从库配置/负载与主库不同，同一 SQL 也可能快慢不一。给出结论模板：把"执行计划是否变、缓冲命中率、锁等待记录、系统资源曲线"四张证据放一起，就能定位是"SQL 本身（计划/索引）"还是"资源竞争（锁/IO）"。实践中的坑：分析期间要开 `performance_schema`（8.0 默认开），否则无法事后追溯；采样要覆盖"慢的时刻"，高峰慢查询日志（slow_query_log + `long_query_time` 调低）是最直接的数据源。

**延伸考点：** "第一次慢、后续快"是缓存命中还是统计信息变化，怎么设计对照实验区分？`EXPLAIN ANALYZE` 输出的实际耗时里，哪些阶段是等待锁、哪些是真正扫描，怎么读？

### Q14. 一个事务里既有 UPDATE 又有 INSERT，还有远程调用，候选人对"事务边界"怎么看？

**问题：** 下单接口的事务里：扣库存 UPDATE、插订单 INSERT、调外部支付服务（HTTP 远程调用）、然后 UPDATE 订单状态。候选人要指出这个设计的问题，并给出正确的事务边界与可靠性方案。

**期望加分项：**
- 能一针见血：事务里夹远程调用是典型反模式——外部 RPC 不可控（慢/超时），会长时间持有数据库锁，拖垮整个连接池
- 能讲清正确边界：数据库本地事务只包"库内操作"，远程调用放在事务之外
- 能给出"先本地事务写 + 异步最终一致"方案：本地事务扣库存+插单（提交）→ 发 MQ → 支付回调更新状态；或"事务发消息"（本地消息表，保证消息与业务同生共死）
- 能讨论分布式事务取舍：TCC/本地消息表/Saga 按业务一致性要求选，而不是一律 2PC
- 能讲幂等：外部调用失败重试要有幂等键（订单号）；支付回调要防重复
- 会评估"事务里能做的事"：锁被持有的时间 = 业务风险，事务里只做快的、确定的、库内操作

**减分项：**
- 看不出远程调用在事务里的危害（持锁时间）
- 把"扣库存+插订单+调支付+更新"全放一个事务，还认为没问题
- 没有幂等与补偿机制
- 一提分布式事务就上 2PC
- 不讨论消息丢失/重复的兜底

**解答：**
核心问题一句话：**事务的持锁时间 = 业务风险，远程调用是不可控变量，绝不允许放进数据库事务**。把这个下单流程拆开看：`UPDATE 库存`、`INSERT 订单` 是数据库内操作，可以也应该在一个本地事务里原子完成；但"调外部支付"是网络往返（几十毫秒到秒级），若它放在事务里，这期间行锁/间隙锁一直持有——支付服务慢 3 秒，整个连接池里的其他事务都要等，最终拖垮库与接口。正确设计分两个层次。第一层：本地事务只做"库内且必要原子"的操作——扣库存 + 插订单（此时订单状态"待支付"），提交；支付调用放事务外，发起后异步等回调。第二层：保证"支付结果"与"订单状态"的最终一致：方案 A 本地消息表（事务内把"待发送支付事件"写入同一库的消息表，提交后定时任务/事务轮询把消息投到 MQ，投递成功删除）——这保证"业务提交"与"消息产生"原子性；方案 B 直接发 MQ（接受小概率消息丢失，靠订单超时扫描兜底）。支付回调更新订单状态时，要有幂等控制（以支付流水号/订单号为幂等键，重复回调只更新一次）、以及超时未支付订单的自动关单补偿。分布式事务的选型要说清：这里最重的需求是"扣库存成功则订单必须存在"，它已经在本地事务里解决了；真正跨系统的"支付成功 ↔ 订单已支付"是最终一致即可（回调 + 幂等 + 超时关单 + 对账），不需要强一致，所以 TCC/Saga 都未必上，本地消息表 + 定时对账通常够用。教训总结：**事务里只放"快、确定、库内"的操作**；任何 IO 型、RPC 型、慢操作全部移出事务，用消息/回调/对账把一致性补齐。实践中的坑：本地消息表方案要防"消息重复投递"（消费端幂等）和"消息表膨胀"（定期清理已消费）；库存扣减建议用条件更新 `UPDATE stock SET stock=stock-1 WHERE id=? AND stock>0` 防超卖，并校验影响行数。

**延伸考点：** "先发消息再提交事务"（非本地消息表）会出现什么不一致，怎么用"事务消息"（RocketMQ 半消息）解决？扣库存加"乐观锁版本号"和"条件更新 stock>0"在并发下各有什么行为差异？

### Q15. 候选人被要求讲清 MySQL 的 Buffer Pool：页结构、LRU 链表、刷盘时机、怎么调优。

**问题：** InnoDB 的 Buffer Pool 是内存缓存的核心。要求候选人讲清：缓冲池缓存什么、LRU 链表与普通 LRU 有何区别、脏页什么时候刷盘、`innodb_buffer_pool_size` 与相关参数怎么调、`SHOW ENGINE INNODB STATUS` 里怎么读命中率。

**期望加分项：**
- 能说出缓冲池缓存"数据页+索引页+undo 页+锁信息"，是 InnoDB 读写的中转站
- 能讲 LRU 的改进：分 old/new 两个区域（默认 5/8~3/8 分界），新页先放 old 区，再次被访问才进 new 区——防止全表扫描/冷数据一次读把热数据挤出
- 能讲脏页刷盘时机：后台线程按水位刷（`innodb_max_dirty_pages_pct` 默认 75% 触发）、redo log 写满/checkpoint 强制、正常 shutdown；不是每笔提交立即刷
- 能讲调优：`innodb_buffer_pool_size` 建议物理内存 60%~80%（取决于整体预算）；8.0 可在线调；多实例用 `innodb_buffer_pool_instances` 分片减少锁竞争
- 能读 `SHOW ENGINE INNODB STATUS`：Buffer pool hit rate（命中率）、free buffers（空闲页数）、dirty pages（脏页比例）
- 能理解"读冷数据先入 old 区"的工程动机：避免扫描型负载污染热区

**减分项：**
- 以为 Buffer Pool 只缓存查询结果（那是 query cache）
- 不知道 LRU 分区/预读机制
- 脏页刷盘时机讲不清（以为提交就刷盘）
- 命中率算不出来或不知道在哪看
- 参数调优没有"先看现状再调"的意识

**解答：**
Buffer Pool 是 InnoDB 的"内存页池"：缓存数据页、索引页、undo 页，所有读（先查池、miss 再读盘并换入）和写（先改池内页、标记脏页、异步刷盘）都经它中转——它决定了读的命中率与写的吞吐。LRU 不是教科书版：InnoDB 把 LRU 分成 new 区（热区，默认 5/8）和 old 区（冷区，3/8）。**新读入的页先放 old 区头部**，只有被再次访问才会"晋升"到 new 区——这个设计的动机是防污染：一次 `SELECT *` 全表扫描会把上亿行页读进池，如果它们直接进热区，原本的热点页全被挤掉（命中率暴跌）；放 old 区后，扫描页没被二次访问很快被淘汰，热点不受影响。此外 InnoDB 有预读（read ahead），顺序扫描时提前把相邻页读入。脏页刷盘是异步的，触发时机有四类：后台刷脏线程按 `innodb_max_dirty_pages_pct`（脏页占比默认 75%）水位持续刷；redo log 空间不够触发强制 checkpoint（`innodb_log_file_size` 太小会频繁强制刷，写吞吐暴跌）；正常 shutdown 全量刷；以及 buffer pool 实例独立刷。注意：**事务提交只需把 redo log 落盘（保证 crash-safe），数据页可以晚点刷**，这是 WAL（Write-Ahead Logging）的核心思想——所以"提交快"不代表"数据已刷盘"。调优顺序：1) `innodb_buffer_pool_size` 是最大头——读取命中率低、物理读高（`Innodb_buffer_pool_reads` 大）就该加大，常见配置为物理内存 60%~80%；2) 实例数 `innodb_buffer_pool_instances`（池子 ≥1GB 才生效）减少并发访问互斥锁竞争；3) 脏页阈值与刷盘线程数（`innodb_io_capacity`）配合磁盘能力设，别设太高把磁盘打满。看现状：`SHOW ENGINE INNODB STATUS` 的 `Buffer pool hit rate`（应 >99%）、`Free buffers`（别长期为 0）、`Dirty pages` 比例；`SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%'` 算命中率。实践中的坑：查询缓存（Query Cache）在 8.0 已移除，别把两者混淆；大表 JOIN 若池内放不下工作集，靠调参救不回来，要优化 SQL 本身。

**延伸考点：** 为什么 InnoDB 要"预读"相邻页，这与机械硬盘/SSD 的随机读成本有什么关系？脏页刷盘不及时会导致什么（崩溃恢复时要依赖 redo log），checkpoint 与 redo log 的关系怎么理解？

### Q16. 候选人被要求设计"订单表误删数据后的恢复方案"，binlog + 备份怎么配合？

**问题：** 线上订单表被一条 `DELETE FROM orders WHERE created_at < '2025-01-01'`（本应加条件）误删了 200 万行，业务方要求尽量恢复。候选人要给出：恢复策略（基于什么）、binlog 起止位置怎么定位、恢复过程中的一致性与风险控制。

**期望加分项：**
- 能说出恢复前提：必须有物理备份（如 xtrabackup）+ 归档的 binlog，且 binlog 是 row 格式（能还原出每一行的 before 值）
- 能讲定位 binlog 位置的技巧：误删前取一个备份点，备份点之后到误删时刻之间的 binlog 都是恢复区间；用误删 SQL 的特征（时间、表）在 binlog 里找 `DELETE` 事件的 position
- 能讲两种恢复路线：1) 把备份恢复到临时实例，再**跳过误删事件**回放 binlog 到误删前一刻（追平）；2) row 格式下用 binlog 的反向 SQL（把 DELETE 的 before 值转成 INSERT）直接补回
- 能讲一致性：备份时刻到 binlog 追平之间的 binlog 要连续完整，恢复实例要 `stop-slave` 校验主从一致
- 能讲风险控制：恢复到临时实例验证（行数、关键订单）再导回；期间原库继续写、恢复完成后用"按主键 INSERT IGNORE"合并；全程只读恢复、评估影响面
- 会提预防手段：恢复演练、备份周期与 binlog 保留时长匹配、误操作防护（防删语句加 `LIMIT`/审计）

**减分项：**
- 不知道恢复依赖 row 格式 binlog 与备份的配合
- 说不清"跳过误删事件"的具体操作
- 恢复直接在生产库上做（没有临时实例验证）
- 不考虑恢复窗口内业务继续写入的合并问题
- 没有备份策略的预防性思考（保留时长、恢复演练）

**解答：**
误删恢复的完整链路是"物理备份 + binlog 时间点回放"，前提有三个：有最近一次完整备份（xtrabackup 物理备份）、备份点到误删时刻之间的 binlog 都已归档且连续、binlog 是 row 格式（能解析出每行的 before/after 值——这是精确恢复的基础，statement 格式无法可靠还原）。流程分四步：第一步冻结基线——以最近备份为恢复起点，备份文件本身是"某个一致性时间点 T0"的快照；第二步锁定恢复区间——T0 到误删时刻 T1 之间所有 binlog 就是回放区间，用 `mysqlbinlog --base64-output=DECODE-ROWS -v` 解析 binlog，找到那条误删 DELETE 的 `# at position`（文件编号 + pos 偏移）；第三步在临时实例上恢复——先 `xtrabackup --apply-log` 把备份恢复到可启动状态，再按 `--start-position` 回放到**误删事件之前一个位置**（`--stop-position` 设在 DELETE 之前），这样临时实例就是"误删前一刻的完整数据"；第四步验证并回灌——在临时实例上核对行数、抽查关键订单，确认无误后再把缺失的 200 万行以 `INSERT IGNORE`/`INSERT ... ON DUPLICATE KEY UPDATE` 合并回生产（生产在这期间已有新写入，按主键冲突跳过即可）。如果 binlog 是 row 格式，还有一个更精细的旁路：直接解析 DELETE 事件的 before 值，用脚本/工具（如 binlog2sql）自动生成反向 INSERT 语句，只补回被删的行而不动其他数据。风险控制要点：恢复全程在**隔离的临时实例**进行，不要在生产库上直接回放；恢复实例要与业务隔离（关端口/停服务），防止恢复数据被篡改；恢复期间评估原库持续写入的影响，合并阶段用幂等写入防止重复；恢复完成后做总量核对（备份+binlog 行数 vs 生产行数）。预防层面要答出来：备份周期与 binlog 保留时长要匹配（保证任何时刻都能回到误删点）、定期做恢复演练验证备份可用、高危 SQL（DELETE 无 WHERE/少 WHERE）加审核与工单流程、必要时候用"逻辑删除/软删"替代物理 DELETE。

**延伸考点：** 误删发生在两次备份之间且 binlog 中间有一段损坏/缺失，恢复怎么做（接受部分丢失 + 从旁路补数）？`DELETE` 和 `TRUNCATE` 都能用 binlog 恢复吗，为什么 TRUNCATE 恢复难度更大？

### Q17. 候选人被要求设计一套 MySQL 高可用方案，从主从、故障切换讲到脑裂防护。

**问题：** 订单库是核心库，要求 99.95% 可用。候选人要设计高可用方案：单主多从怎么搭、主库故障怎么切换、切换中"脑裂"（双主）怎么防、以及读流量怎么在切换后恢复。

**期望加分项：**
- 能讲基础：一主多从（半同步优先）、读写分离、从库异步/半同步复制；主从都是单写入口
- 能讲切换手段：MHA（经典，脚本化）、orchestrator（自动检测+切换）、或云厂商高可用；8.0 有 Group Replication/MySQL Router 也可提
- 能讲检测与选主：从库心跳/半同步 ACK 判断主库真实存活（网络分区 vs 真宕机要区分）；选"数据最新"的从库提升
- 脑裂防护：主库失联不等于宕机——用租约/仲裁（如半同步、外部协调器 etcd/zk 的 fenced 机制、或 keepalived VIP 绑定）确保老主在切换期间不能再写；老主恢复后以新主为准（STOP SLAVE + 重新指向新主）
- 能讲切换过程的一致性：半同步复制保证切换后从库已收最新 binlog，避免丢已提交事务
- 能讲读流量恢复：VIP/路由层把读流量从故障库摘除、写流量指向新主；应用层重连

**减分项：**
- 只会说"配个主从"没考虑故障切换
- 不知道半同步复制的价值（切换不丢已提交数据）
- 不考虑脑裂：老主失联后自己还能接受写入怎么办
- 选主不看数据延迟，随便挑一个从库
- 忽略切换后主从关系重建（老主回归要重新挂载）
- 不做切换演练

**解答：**
先搭基础架构：一主多从，主库单写、从库负责读（读写分离 + 业务按一致性需求路由）。复制方式选**半同步**：主库提交事务后必须等至少一个从库 ACK 收到 binlog 才返回成功——它让"主从切换"不丢已提交事务，这是高可用的基石（异步复制在切换时可能丢掉最后几百 ms 的数据）。故障切换的完整流程：1) 检测——协调器（orchestrator/MHA/云 RDS 高可用）通过心跳、半同步状态、TCP 探活综合判断主库"真宕机"还是"网络分区"（心跳丢失≠宕机，要避免误切换）；2) 选主——在所有存活从库中选"binlog 位置最新"（数据最接近主库）的提升，必要时先补 binlog 追平；3) 切换——从库提升为新主（`STOP SLAVE; RESET SLAVE;` 去掉从库身份）、通知应用写入口指向新主（VIP 漂移或路由表变更）、其他从库重新 `CHANGE MASTER TO` 挂到新主。最关键的是**脑裂防护**：主库只是与协调器失联（网络分区）而自己仍存活时，它可能继续接受写入，若同时新主也在写，就形成双主数据分叉。防护手段分层：协调器用**租约/fencing**——切换前通过"防呆"机制（如半同步要求所有候选 ACK 已收到心跳停摆信号、或让老主"自杀"（SSH 杀进程）、或存储层面的共享锁）确保老主在切换后无法再提交；应用侧写入口必须有单一 VIP/代理（keepalived + 脚本），VIP 只在当前主上，切换即 VIP 漂移，从物理上保证"只有一个写入口"。老主恢复后不能直接加回：要把它当"从库"重新指向新主（`CHANGE MASTER TO`），先从新主拉取追平再开放读流量，并校验数据是否一致（pt-table-checksum）。切换后的读流量恢复：路由层（Proxy/LVS）摘掉故障从库、把读请求平摊到剩余从库，VIP 绑定新主后写流量自动切换，应用侧做好连接池重建与超时重试。最后必须强调**演练**：高可用方案没演练过等于没有——定期做"主库 kill 演练"，验证切换时长（秒级）、数据零丢失（半同步）、脑裂未发生。

**延伸考点：** 半同步复制在"唯一从库也挂了"时会发生什么（退化异步还是阻塞写入），生产怎么权衡这两个参数？网络分区导致"双主都以为自己该写"的典型场景，fencing 具体怎么做（举一个 lease 或锁存储的例子）？

### Q18. 候选人被要求设计订单号/全局 ID 生成方案，为什么不能直接自增或 UUID？

**问题：** 订单表未来要分库分表，订单号要全局唯一且尽量有序。候选人要比较：自增 ID、UUID、雪花算法（Snowflake）各自的优劣，并设计一套落地细节（含时钟回拨处理）。

**期望加分项：**
- 能指出自增 ID 的问题：单库单表 OK，分库分表后每库自增会重复；且泄露业务量（可被爬取总量）
- 能指出 UUID 的问题：128 位、无序（作为主键索引时页分裂/随机 IO 严重）、存储大；但全局唯一无需协调
- 能讲雪花算法：64 位 = 1 bit 符号 + 41 bit 时间戳（毫秒，约 69 年）+ 10 bit 机器 ID + 12 bit 序列号；单机每秒可生成约 400 万个
- 能讲序列号与并发：同一毫秒内 12 bit 序列号递增，超了等下一毫秒；多进程/多机房用机器 ID 区分
- 能讲时钟回拨问题：机器 NTP 校时导致时间倒退，会生成重复 ID——解法：序列号/延迟等待/内存记录最后时间戳拒绝回拨、或备用时钟源
- 能讲有序性与 MySQL 主键的配合：雪花 ID 趋势递增，作为聚簇主键比 UUID 页分裂少
- 工程落地：ID 生成服务（独立部署）、或用 `auto_increment + 步长`、或用 Redis INCR 批取号段

**减分项：**
- 只说"用雪花算法"，时钟回拨、机器 ID 分配都答不出
- 不知道 UUID 作主键对 InnoDB 聚簇索引的伤害
- 不分场景：单库单表用自增其实最优
- 不考虑分库分表后 ID 与分片键的关系
- 没有落地方案（怎么分配机器 ID、怎么保证高可用）

**解答：**
先按场景定结论：**单库单表单机时，自增主键就是最优解**（索引连续、页分裂少、实现零成本），不要为用而用；只有"未来要分库分表/多机房/要隐藏业务量"时才需要全局 ID。全局 ID 三条路线对比：自增（每库步长法 `auto_increment_offset/increment` 可以做到分库不重复，但机器数受限、扩容要改步长、且暴露业务量）；UUID（全局唯一无需协调，但 16 字节、完全无序——作为 InnoDB 聚簇主键，插入时随机位置导致频繁页分裂与索引碎片，且查询缓存/范围查询全部失效，绝大多数场景不推荐做主键）；雪花算法（Snowflake）是主流答案：64 位组成——1 bit 符号位 + 41 bit 毫秒时间戳（可表示约 69 年）+ 10 bit 机器 ID（可区分 1024 个节点）+ 12 bit 每毫秒序列号（单机单毫秒 4096 个，超了就等下一毫秒），单机理论每秒生成约 400 万个 ID。它的核心优点是**趋势递增且全局唯一**：作为聚簇主键插入时基本顺序追加、页分裂远少于 UUID，同时能塞进 bigint。落地必须处理的坑：一是**时钟回拨**——机器 NTP 校时导致时间戳倒退，会生成重复 ID，常见方案：记录"上次生成时间戳"，发现回拨时抛错/重试等待追平/用备用时间源，回拨较大时直接拒绝服务或降级到"借用序列号空间"（如把序列号高位当临时时间差）；二是**机器 ID 分配**——用配置中心下发或注册时从 Redis/DB 取号，避免手动配错；三是**高可用**——ID 服务要无状态可水平扩展（每个实例分配独立机器 ID 段）。除雪花外还有两条务实路线：Redis `INCR`（取号段）适合中小规模；数据库发号表（`UPDATE` 抢占 + 步长）适合不想引入 Redis 的场景。最后补一句关系辨析：**全局唯一 ≠ 分片路由**，订单号全局唯一没问题，但分库分表路由仍然要按分片键（如 user_id）来算，不能拿订单号哈希去路由。

**延伸考点：** 雪花算法 41 bit 时间戳在 2038 年/69 年后怎么办（预留位/迁移方案）？"ID 趋势递增"暴露业务量，如果业务要求"完全不可猜测"，雪花和 UUID 之外还有什么（如随机 + 校验位）？

### Q19. 数据库连接池的参数怎么定？候选人被要求给出配置依据而不是背默认值。

**问题：** 团队给 MySQL 连接池配了 `maxPoolSize=200`、`connectionTimeout=30000ms`，高峰期经常报"连接获取超时"。候选人要诊断：连接池太小还是连接泄漏？参数怎么定才合理，HikariCP/Druid 相关的关键参数分别怎么配？

**期望加分项：**
- 先给理论基线：连接池大小的经验公式 `connections = (core_count * 2) + effective_spindle_count`（PostgreSQL 作者提出，MySQL 类似思路）——高并发 IO 密集应用通常几十个连接足够，200 往往偏大
- 能指出"获取超时"的可能根因：连接池耗尽（池太小或泄漏）vs 后端慢 SQL 占满连接 vs 事务长时间持锁
- 能定位连接泄漏：Druid 的 activeCount/等待线程数、HikariCP 的 pool 指标、`show processlist` 看长连接、连接归还超时（leakDetectionThreshold）
- 关键参数：maximumPoolSize（合理基线）、minimumIdle、connectionTimeout（获取连接超时）、idleTimeout（空闲回收）、maxLifetime（超过数据库 wait_timeout 的 70%）、validation 手段
- 能讲"池大小与数据库能力的匹配"：连接数 × 每连接资源（内存、线程）不能压垮数据库；观察 DB 侧 `Threads_connected` 与 CPU
- 能处理"连接慢获取"场景：优先排查 SQL/锁，而不是盲目加大池子

**减分项：**
- 背默认值不理解含义
- 出了问题只会"加大连接池"
- 不知道连接池饱和与慢 SQL/死锁的因果关系
- 不关注 maxLifetime 与 MySQL wait_timeout 的配合（连接被服务端踢掉）
- 不监控连接池指标（active、idle、pending）
- 不了解连接泄漏的检测手段

**解答：**
先纠正思路：**连接池大小不是越大越好**。每个连接在 MySQL 侧都要占用线程栈、缓存、Buffer Pool 相关资源，池子开 200 时若每连接背后都是活跃查询，数据库 CPU/线程数会被打满，反而变慢。经验基线是"核心数 ×2 + 磁盘数"量级（几十个），IO 密集应用通常 20~50 就够，具体通过压测找拐点。诊断"获取连接超时"要三步：第一步看监控指标——连接池的 `activeCount`（活跃）、`idleCount`（空闲）、`pending`（等待获取的线程数）；如果 active 一直满且 pending 上涨，说明池真被占满；第二步看数据库侧——`SHOW PROCESSLIST`/`Threads_connected`，若大量连接停在 `Sleep`（闲置）或 `Sending data`（执行中），区分是"连接没归还"还是"SQL 太慢占着连接"；第三步定位泄漏——HikariCP 设 `leakDetectionThreshold`（如 30000ms），超时未归还的连接会打印堆栈，Druid 用 `removeAbandoned` 系列参数；同时检查事务是否未提交（`SELECT trx.* FROM information_schema.innodb_trx`）导致连接被长事务占死。参数设计：`maximumPoolSize` 按压测和 DB 能力定（别拍脑袋 200）；`connectionTimeout` 是"获取连接的等待上限"，设为几百 ms 到 2s 即可，太长会让调用方排队等死；`maxLifetime` 必须小于 MySQL 的 `wait_timeout`（默认 8 小时）——连接超时被服务端静默回收后，池里还认为可用，下次使用报"connection reset"，所以 HikariCP 建议 maxLifetime 设为 wait_timeout 的 70%~80%；`idleTimeout`（空闲回收）与 minIdle 配合，避免高峰期连接反复建连。落地结论：先压测确定池大小 → 配 leakDetection 抓泄漏 → 观察 DB 侧资源占用 → 有慢 SQL 先优化 SQL，连接池只是最后一道闸。

**延伸考点：** 为什么"池大小 × 平均 SQL 耗时"超过 QPS 时就必然出现获取超时（排队论），怎么用这个公式预估需要的连接数？连接池预热（启动时预建连接）和高并发下突发建连（到 MySQL 的 max_connections 上限）分别怎么处理？

### Q20. 候选人被要求复盘一次"数据库 CPU 被打满"的事故：从现象、排查到根治，完整讲一遍。

**问题：** 线上订单库 CPU 100%，接口大面积超时，DBA 和研发一起排查。候选人被要求按"事故复盘"的方式完整讲述：第一步看什么、怎么缩小范围、典型根因有哪些、根治方案是什么、如何避免再犯。

**期望加分项：**
- 先看宏观：`show processlist`（一堆慢 SQL/等待锁？）、`SHOW GLOBAL STATUS`（Threads_running、Questions 曲线）、CPU/IO 监控（`top`/`iostat`）
- 能按比例区分三类根因：1) 慢 SQL/坏 SQL 突增（索引失效、深分页、大 join）——高峰陡增的元凶；2) 连接风暴（连接池过大 + 慢查询排队，线程堆积）；3) 锁等待/死锁链（DDL 卡住、长事务）
- 定位手法：慢查询日志（`long_query_time` 调低）抓坏 SQL → EXPLAIN 分析 → 锁等待用 `information_schema.innodb_trx`/`performance_schema` 看等待链
- 止血：kill 坏查询（`KILL`）、或连接限流（max_connections/连接池收缩）；紧急手段：对慢 SQL 来源限流
- 根治：索引/SQL 改写、参数（buffer/线程）调优、架构（读写分离/分库）分流
- 预防：慢查询监控告警（阈值+采样）、SQL 上线评审（explain 卡点）、容量规划、演练

**减分项：**
- 只会说"加机器"或"重启"
- 不按"现象→定位→止血→根治→预防"的结构讲
- 区分不出慢 SQL 与连接堆积谁先谁后（往往互为因果）
- 没有 kill 与限流的止血意识
- 复盘不提"下次怎么防"

**解答：**
按复盘结构讲。**现象与快速定性**：CPU 100% + 接口超时，第一步 `SHOW PROCESSLIST` 看是否有大量 `Sending data`（真正在执行的慢查询）还是大量 `Sleep`+堆积（连接过多）——同时看 `Threads_running`（真正并发执行的线程）远超正常值说明有查询风暴；再对照 `top` 确认 CPU 是用户态（计算）还是 `wa`（IO 等待），`SHOW GLOBAL STATUS` 的 `Questions/Threads_created` 看是不是连接风暴。**定位根因**：高 CPU 三大典型：一是**坏 SQL 突增**——新上线的功能带着 `SELECT *` + 深分页、或 `OR`/函数导致索引失效、或大 join；从慢查询日志（平时 `long_query_time=1s`，出事时临时调低抓全）把高耗时、高频次的 SQL 捞出来逐个 EXPLAIN；二是**连接堆积**——应用连接池配太大 + 有慢 SQL 占连接，新请求都排队等连接，线程数暴涨，CPU 空转在上下文切换；此时 `Threads_connected` 与 `Threads_running` 双高、`show processlist` 全是 `Sleep` 或等待锁；三是**锁等待/长事务**——某条 DDL 或大事务持有锁，后续所有同表查询都在 `Waiting for table metadata lock` / `Lock wait`，`performance_schema.data_lock_waits` 能看到等待链。**止血**：按风险从高到低——KILL 掉占资源最大的坏查询（`KILL <id>`，注意 kill 大事务会回滚，先评估）；若是连接风暴，临时收缩应用连接池、`max_connections` 限制、对来源限流；必要时摘掉异常流量的服务节点。**根治**：坏 SQL 改写/加正确索引（用 EXPLAIN 验证）、优化深分页（游标/延迟关联）；锁问题拆大事务、调整隔离级别；架构层面读写分离把查询分流、或把分析型查询移到只读从库/数仓。**预防与复盘产出**：慢查询监控与告警（超过阈值自动抓取 SQL 与执行计划）、SQL 上线必须有 EXPLAIN 评审、连接池参数按压测固化、容量规划（峰值 QPS × SQL 耗时估算线程需求）、定期做压测与故障演练。最后给出复盘模板的一句话：**一次 CPU 100% 事故 = 定位是"SQL 还是连接" → 止血 → 根治 → 把该事故的触发条件变成自动化告警与上线卡点**，让同类问题不可能再发生。

**延伸考点：** 高 CPU 事故里"慢 SQL 导致连接堆积"和"连接堆积导致 CPU 高"如何用数据区分（先有鸡还是先有蛋）？`innodb_thread_concurrency` 和连接池在限制数据库并发上各自的作用与配合？
