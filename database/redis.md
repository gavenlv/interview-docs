# 数据库 · Redis（面试题库）

本文件聚焦 Redis 后端工程实践考察，覆盖缓存三大问题与一致性、数据结构与内存优化、持久化与高可用、分布式锁与原子性、性能调优与故障排查等主题。所有题目均为线上或项目中可复现的场景化问题，重点考察候选人的方案取舍、排查思路与量化能力，而非概念背诵。难度自 Q1 至 Q20 循序渐进，从实践基础逐步过渡到架构级开放性思考题。

### Q1. 恶意请求打穿缓存，DB 压力骤增，怎么挡？

**问题：** 线上有个查询接口，有人用不存在的 ID（如 -1、随机 UUID）疯狂请求，缓存和 DB 都没有这条数据，每次请求都穿透到 DB，DB 压力骤增。你怎么处理？

**期望加分项：**
- 能先说清穿透的本质：查不到的数据没有缓存，缓存形同虚设
- 能给出空值缓存方案，并主动说明 TTL 必须短、空值 key 数量要可控（防内存被垃圾塞满）
- 能提到布隆过滤器，并说清误判率方向（宁可放行不可误杀）、删除困难的局限
- 有参数校验、限流、风控等前置拦截手段
- 结合线上真实数据说明选择依据（QPS、DB 承受能力、key 基数）

**减分项：**
- 只会背"布隆过滤器"三个字，说不出为什么、代价是什么
- 空值缓存方案不考虑 TTL 与内存爆炸
- 忽略"布隆过滤器删除困难、误判"这些边界
- 没有前置参数校验与限流意识

**解答：**
先做判断：穿透的核心是"查不到的数据没有缓存"，所以解决思路是让"不存在"也能被缓存挡住，再叠加前置拦截降低恶意流量成本。第一层：参数校验，ID 格式、范围、长度合法性校验，负 ID、超长 ID 直接拒绝，这能过滤掉大部分脚本流量。第二层：空值缓存，把不存在的 key 也写进缓存，值标记为 null 并给短 TTL（30-60s）。关键坑是：如果恶意 key 是随机的，空值缓存会无限膨胀吃光内存，所以要限制空值缓存规模（如独立的短 TTL、计数上限），随机 key 场景空值缓存效果有限。第三层：布隆过滤器，启动/定时把合法 ID 集合加载进 Bloom Filter，查询前先判断。要点是误判方向：宁可把不存在的 key 判为"可能存在"放行回源，也不能把存在的 key 误判为不存在（那样正常数据读不到）。布隆过滤器不支持删除，数据变更频繁时要么定时重建，要么用 Cuckoo Filter，Redis 也提供 BF module（RedisStack）。实践中的取舍：key 基数小（几百万内）直接空值缓存最简单；key 基数大且随机性强，布隆过滤器才是正解；无论哪种，DB 侧连接池保护和限流兜底不能省。

**延伸考点：** 布隆过滤器的误判率怎么算？你们布隆过滤器里的 ID 集合多久更新一次，更新期间新增的合法 ID 会不会被误杀？

### Q2. 热点 key 刚好过期，瞬间流量打垮 DB，怎么防？

**问题：** 大促时某个热点商品 key 在高峰期恰好过期，一瞬间所有请求都回源 DB，DB 被打垮。除了"把 TTL 调大"还能怎么做？

**期望加分项：**
- 能区分穿透/击穿/雪崩三个概念，并准确指出本题是击穿（单个热点 key 过期瞬间）
- 能给出互斥锁方案并说清"让回源只发生一次"
- 能给出逻辑过期（value 带逻辑过期时间 + 异步重建）方案，并说清脏读窗口的取舍
- 提到多级缓存、热点 key 永不过期 + 后台刷新
- 关注锁的粒度、超时、死锁等细节

**减分项：**
- 三个缓存问题混为一谈，方案张冠李戴
- 只会说"加锁"，说不出锁不住时其他线程怎么处理（等待重试还是返回旧值）
- 忽略互斥锁在分布式环境下的实现复杂度
- 逻辑过期方案答不出"窗口期读到旧数据"的代价

**解答：**
先明确场景：击穿是"单个热点 key 物理过期瞬间，并发回源打爆 DB"，与穿透（查不到）、雪崩（大面积 key 同时失效）成因不同，方案也不同。核心思路两条：要么"让回源只发生一次"，要么"让 key 永不物理过期"。方案一：互斥锁，回源前用 SET NX 抢锁，抢到锁的线程回源 DB 并重建缓存，其余线程短暂 sleep 后重试读缓存。要点：锁按 key 粒度而非全局，加锁失败要设置等待超时（比如 200ms 内重试几次）而不是无限自旋，锁要带过期时间防死锁。方案二：逻辑过期，value 里存业务数据 + 逻辑过期时间戳，读的时候发现逻辑过期，先返回旧值，再异步丢给后台线程回源重建。优点是不存在物理过期瞬间的冲击，代价是窗口期内读到旧数据，适用于对一致性不敏感的展示类数据。方案三：热点 key 永不过期 + 后台定时刷新缓存。工程上通常是组合拳：本地缓存（Caffeine/Guava）挡第一层读，Redis 扛共享热点，回源加互斥锁保护 DB。实践中的坑：互斥锁用的分布式锁必须可靠（见 Q13），锁过期导致并发回源，这时候要靠 DB 侧的限流兜底，而不是指望锁万无一失。

**延伸考点：** 逻辑过期方案里异步重建线程怎么保证不重复回源？如果回源本身要 500ms，锁的过期时间设多少合适？

### Q3. 缓存雪崩：大批 key 集中过期 / Redis 整体不可用，怎么办？

**问题：** 凌晨缓存 key 集中过期，或者 Redis 实例直接挂了，流量全部打到 DB，DB 扛不住。分别怎么处理？两者有什么本质区别？

**期望加分项：**
- 能区分"大量 key 同时过期"与"Redis 实例不可用"两类雪崩，方案不同
- 给过期时间加随机扰动，能说出扰动范围怎么定（基于真实 TTL 分布）
- 提到多级缓存、热点 key 永不过期、实例高可用（主从/哨兵/Cluster）
- 有 DB 侧保护意识：限流、熔断、降级、连接池隔离
- 主动谈降级预案要提前演练，而不是出事才想

**减分项：**
- 把两类雪崩混在一起，只会说"加随机时间"
- 只说"做高可用"却讲不清哨兵/Cluster 在故障转移期间流量怎么过渡
- 没有降级、限流、熔断等 DB 保护手段
- 忽略本地缓存这一层兜底

**解答：**
先拆开两类成因。第一类：大量 key 同时过期。多见于批量导入缓存时 TTL 设成同一个值。解法：TTL 加随机扰动（基准值 + random(0, 300s)）错峰失效；热点 key 单独设永不过期 + 后台刷新；多级缓存兜底，本地缓存命中后根本不触发回源。第二类：Redis 实例整体不可用。解法分两层：一是架构层做高可用，主从 + 哨兵或 Cluster，故障转移期间切换会有几十秒窗口，业务要扛得住；二是应用层必须有"Redis 挂了"的降级预案——本地缓存（注意本地缓存 TTL 要覆盖故障恢复时间，否则本地缓存也失效）、直连 DB（但必须限流 + 连接池保护，防止把 DB 打死）、返回兜底数据（如默认配置、上次成功的快照）。两类雪崩都要在 DB 侧做保护：读请求限流、熔断器（Redis 连续失败快速熔断，避免每个请求都试 Redis 又都回源 DB）。实践中的坑：很多团队只做了"Redis 高可用"，但哨兵切换期间主库短暂不可写、从库读可能读到旧数据，业务对写失败要有补偿；降级预案必须演练过，真出事时人慌最容易出乱子；限流阈值要按 DB 实测 QPS 能力定，而不是拍脑袋。

**延伸考点：** 本地缓存和 Redis 都挂了的"最坏情况"你们怎么兜底？降级开关怎么做灰度放量？

### Q4. 缓存和数据库的一致性，你们线上到底用哪种方案？

**问题：** 业务要求更新后缓存不能长期是旧值。你们用 Cache Aside？延迟双删？还是订阅 binlog？为什么这样选？先更新 DB 还是先更新缓存？

**期望加分项：**
- 能明确说出"工程上接受最终一致，强一致不该依赖缓存"，并说明取舍
- 能讲清 Cache Aside 标准流程：读 miss 回源写缓存；写时先更新 DB 再删缓存（写后删）
- 能解释为什么"删缓存"而不是"更新缓存"，为什么"先 DB 后缓存"
- 能指出双删/延迟双删解决的是哪个并发窗口，并承认它不彻底
- 能给出 binlog 订阅（Canal）+ MQ 重试的工程化方案，说明删除失败的兜底

**减分项：**
- 只会背"Cache Aside 模式"几个词，说不清流程与理由
- 说不清"先更新缓存"的问题在哪
- 双删方案说不出解决什么问题、还有什么残留窗口
- 删除缓存失败导致长期不一致，答不出重试/补偿机制
- 声称"完全一致"，没有一致性等级的意识

**解答：**
先定基调：缓存一致性没有银弹，工程上普遍接受最终一致，强一致（如余额）就别走缓存或走版本校验。标准方案是 Cache Aside：读 miss 时回源 DB 写缓存；更新时先写 DB，成功后删缓存（写后删）。为什么删而不是更新：删除是幂等的、懒加载，避免"缓存写成功 DB 写失败"的脏状态；为什么先 DB 后缓存：先删缓存后写 DB 会在写 DB 期间读到旧缓存（虽然很快重建，但有窗口）。写后删的问题在于一个并发窗口：线程 A 更新 DB 后正要删缓存，线程 B 此时 miss 回源读到旧数据写入缓存，A 的删除把 B 写入的新缓存删掉或没删掉形成不一致。缓解手段：延迟双删——更新 DB 后删一次，sleep 几百毫秒再删一次，把"旧值重建缓存"的窗口错过去；更工程化的是订阅 binlog（Canal 监听 MySQL binlog）删缓存，配合 MQ 重试，删失败的消息重投。实践中的坑：删缓存失败必须能重试（否则长期不一致），很多团队"双删"里的第二次删除并没有重试保障；延迟双删的 sleep 时长拍脑袋，实际应按"读回源写缓存的耗时分布"来定；对一致性要求高的写操作，缓存更新后加一个版本号比对兜底更稳。记住：一致性靠"补偿与校验"闭环，而不是指望一次操作写对。

**延伸考点：** 如果删缓存的消息重试了很多次都失败怎么办？你们怎么校验缓存和 DB 最终一致（比如定时抽样比对）？

### Q5. 商品详情、排行榜、粉丝列表、签到、UV，各用什么结构？

**问题：** 下面几个场景你们分别用 Redis 的什么结构：商品详情（字段多、部分字段常更新）、排行榜、粉丝/关注列表、签到打卡、UV 统计。各自注意什么？

**期望加分项：**
- 能逐个给结构并说出理由（复杂度、操作特性、内存开销）
- 商品详情给 Hash（局部字段更新不用整体反序列化）而非 String 一把梭
- 排行榜用 ZSet（zrevrange 取 TopN、zincrby 实时加分）
- 签到用 Bitmap 并算清内存（每人每年约 46 字节）
- UV 用 HyperLogLog 并说清 0.81% 误差与何时不能用（精确统计）
- 主动提大 key 风险与编码（ziplist/intset）对内存的影响

**减分项：**
- 所有场景都答 String + JSON
- 说不出 ZSet 排行榜的分数/成员设计
- 不知道 HyperLogLog 有误差，或不知道 Set 可以做精确 UV
- 忽略内存与编码细节（字段多转 hashtable）
- 不关心大 key 风险

**解答：**
选型的判断标准是"操作模式 + 内存开销 + 大 key 风险"。商品详情：字段多且部分字段频繁更新，用 Hash，hsetset 单字段、hgetall 全量读，避免 String+JSON 每次更新都要整包反序列化再序列化；但注意 Hash 字段数超过 hash-max-ziplist-entries（默认 128）会从 ziplist 转 hashtable，内存翻几倍（见 Q6）。排行榜：ZSet，member 存用户 ID，score 存分数，zadd/zincrby 更新，zrevrange 0-99 取 Top100，天然支持按名次区间分页；加 TTL 或用 ZREMRANGEBYSCORE 清理过期名次。粉丝/关注列表：关系类用 Set，sadd/srem/sinter 做共同关注；需要按时间倒序时用 List 或 ZSet（时间戳做 score）。签到：Bitmap，setbit user:sign:{uid}:{month} dayOfMonth 1，bitcount 统计，每用户每月约 4 字节（31 位），百万用户一年也才几百 MB，比 Set/List 省两个数量级。UV 统计：HyperLogLog，内存恒定约 12KB，误差约 0.81%，适合"量级估算"（活动 UV、DAU 趋势）；要精确数（比如对账）用 Set 或累加计数，别在精确场景硬上 HLL。消息/任务队列用 Stream（见 Q16）。实践中的坑：Set 做到几十万成员就是大 key（见 Q11），交集操作 O(N)；Bitmap 每个用户一个 key 会形成海量小 key，考虑按天合并；选型最后要过一遍内存估算，别只看功能顺手。

**延伸考点：** 排行榜分数实时变化很频繁，ZSet 的写放大怎么控制？HyperLogLog 多个 key 怎么合并统计总量（PFMERGE）？

### Q6. 内存快满了，让你优化 key 和数据结构省内存，从哪入手？

**问题：** 线上集群内存接近上限，运维让你通过优化 key 设计和数据结构省内存。你会从哪些方面入手？哪些优化收益最大、代价是什么？

**期望加分项：**
- 能按收益排序：key 命名、String→Hash 批量、编码参数、value 压缩
- 能讲清 String 存小对象 vs Hash 存多字段的内存差异（key 本身的开销 + 对象头）
- 知道 embstr（≤44 字节内联）、ziplist/intset 编码与阈值
- 能说出"省内存往往费 CPU"的权衡（压缩、序列化）
- 有量化意识：能估算优化前后内存差几个数量级

**减分项：**
- 只会说"key 短一点"，答不出结构层面的优化
- 不知道编码（ziplist/intset/embstr）是什么、阈值多少
- 只说"换更短的 key"却忽略可读性与排查成本
- 不考虑优化对 CPU 与延迟的影响
- 没有量化与验证闭环（改完不看内存曲线）

**解答：**
按收益从大到小排序。第一：结构替换。大量"一个业务对象一个 String key"的场景，比如 user:10001 存 JSON 字符串，改成 user:10001 一个 Hash 存 name/age/email 等字段，收益非常大——String 每条 key 有约 40-100 字节的对象头 + SDS 开销，100 万个小对象优化后内存可省一半以上，而且字段级更新不再整包序列化。第二：key 本身。缩短 key（去掉冗余前缀、用短命名空间如 u:10001）、避免把整个业务上下文拼进 key（如 user:10001:profile:detail:v3）；但别短到不可读，排查成本也是成本。第三：利用编码。小集合自动用 intset（整数集合）编码，小 Hash/List/ZSet 用 ziplist（3.2+ 内部 quicklist/listpack）编码，字符串 ≤44 字节走 embstr 内联存储；这些是自动的，但要注意一旦元素数/大小超阈值（hash-max-ziplist-entries 等）会转成 hashtable，内存瞬时翻数倍，优化时要按业务控制单 key 规模。第四：value 压缩。大 JSON 用压缩（gzip）或换紧凑序列化（Protobuf/Kryo）——注意这是用 CPU 换内存。第五：存量数据。清理无用 key、把无 TTL 数据梳理一遍，必要时调整过期策略。实践中的坑：结构重构会影响所有读写代码，属于"提前设计"而非"事后补救"；改编码阈值参数要压测，避免引发大 key；优化完要对比 used_memory 曲线验证，别改完就忘。

**延伸考点：** 一个存 200 万条用户信息的缓存，从 String 改成 Hash 后大概能省多少内存，你怎么估算？ziplist 转 hashtable 的阈值设多大合适？

### Q7. maxmemory 满了会发生什么？淘汰策略怎么选？

**问题：** 线上 Redis maxmemory 设了 8G，有一天内存满了。会发生什么？你们线上用哪种淘汰策略？不同策略对业务的影响有什么差别？

**期望加分项：**
- 能区分"过期删除"（有 TTL 的键被删）与"内存淘汰"（maxmemory 满了踢数据，可能踢掉无 TTL 的键）
- 能列出主要策略：noeviction、allkeys-lru/lfu、volatile-lru/lfu、random 系列
- 能说清缓存场景选 allkeys-*、当存储用时选 volatile-*/noeviction 的理由
- 知道 LRU 与 LFU 的差异（突发流量 vs 稳定冷热）
- 提到 evicted_keys、命中率监控与告警

**减分项：**
- 把"过期删除"和"内存淘汰"混为一谈，以为满了会自动删过期的
- 说不出 noeviction 是默认策略且写会报错
- 把 Redis 当存储用还配 allkeys-lru，不知道会丢业务数据
- 没有监控 evicted_keys/命中率的意识

**解答：**
先纠正最常见的误区：Redis 满了不会"自动清理过期 key"，过期删除（主动删除/惰性删除/定期删除）只针对有 TTL 的键，而且平时主要靠惰性删除和定期抽样，过期键可能堆积占用内存；内存淘汰是另一套机制——达到 maxmemory 时按策略踢数据，踢的可能是没有任何 TTL 的键。策略选择：缓存场景（数据丢了可以从 DB 重建）用 allkeys-lru 或 allkeys-lfu，谁冷谁先走；当存储用的数据（不可重建）配 volatile-lru/lfu（只淘汰设了 TTL 的键）或 noeviction（满了写报错 OOM command not allowed when used memory > maxmemory），配合监控告警尽早介入，而不是让 Redis 偷偷丢数据。LRU vs LFU：LRU 对"突发热点"不敏感——一个 key 刚被大量访问后闲置，会被当作冷数据淘汰；LFU 统计访问频率，适合冷热长期分明的场景（如大促商品页），Redis 4.0+ 支持。淘汰过程本身有 CPU 开销（近似 LRU 抽样比较），maxmemory-samples 默认 5，调大更精确但更费 CPU。实践中的坑：allkeys-lru 下"当存储用"的键被莫名淘汰是线上最常见的丢键事故；淘汰后缓存命中率下降、回源 DB 激增，所以 evicted_keys 必须监控告警；maxmemory 设了要留出 AOF/RDB 与内存碎片空间，别把实例逼到淘汰临界点。

**延伸考点：** 线上命中率从 98% 掉到 80%，你怎么判断是淘汰策略问题还是数据模型问题？LFU 的计数衰减机制（aging）了解吗？

### Q8. Redis 重启后数据丢了，RDB 和 AOF 到底怎么配？

**问题：** 线上 Redis 重启后缓存数据丢了，排查发现没开 AOF。你们 RDB 和 AOF 怎么配？能接受丢多少数据？为什么这么选？

**期望加分项：**
- 能讲清 RDB（快照）与 AOF（追加日志）各自的丢数据窗口：RDB 取决于 save 策略，AOF 取决于 fsync 策略
- 能说出 AOF 三种 fsync：always（每条）/ everysec（最多丢 1s）/ no
- 知道 Redis 4.0+ 混合持久化（aof-use-rdb-preamble）兼顾恢复速度与丢窗口
- 按"缓存 vs 存储"场景给出取舍，而不是无脑全开
- 提到 fork 阻塞、AOF rewrite、恢复慢等实践代价

**减分项：**
- 只会背"RDB 快照、AOF 日志"定义，说不出各自丢多少数据
- 不知道 AOF 需要 rewrite，不知道文件膨胀问题
- 忽略 fork 大实例的阻塞风险
- 不考虑业务场景，所有实例一刀切
- 以为开了持久化就万无一失，忽视主从复制兜底

**解答：**
先按数据性质定方案：Redis 当缓存用，数据可重建，可只开 RDB 甚至全关，靠主从复制兜底；Redis 当存储用（如会话、计数、任务状态），要开 AOF 并接受"最多丢 1 秒"的窗口。RDB：按 save 策略（默认 900s 内 1 次写 / 300s 内 10 次 / 60s 内 10000 次）fork 子进程全量快照。优点文件小、恢复快；缺点是两次快照之间的数据全丢，且 fork 大实例时有阻塞（页表复制 + COW，内存可能翻倍，fork 期间命令延迟飙升）。AOF：追加写，丢数据窗口取决于 appendfsync：always 每条都 fsync（最安全但吞吐掉很多）、everysec 每秒一次（最多丢 1s，工程标准配置）、no 交给操作系统（可能丢几十秒）。AOF 的坑：文件无限膨胀需要 bgrewriteaof 重写（把历史压缩成最终态），rewrite 也要 fork；纯 AOF 恢复要重放全部命令，大数据量恢复慢。混合持久化（Redis 4.0+）：AOF 文件头部是 RDB 快照 + 之后的增量命令，恢复时先加载 RDB 再补增量，兼顾速度和丢窗口，存储场景建议开启。实践中的坑：大实例（几十 G）fork 耗时可能达到秒级，要用 info stats 的 latest_fork_usec 监控，必要时低峰期做 bgsave 或用 RDB 子进程限速（rdb-save-incremental-fsync）；只依赖主从复制兜底时，主库挂了从库没跟上会丢数据，持久化 + 复制双保险才是正解；恢复大数据集要先评估 rdbchecksum 加载耗时，避免业务等不起。

**延伸考点：** AOF rewrite 和 RDB bgsave 同时触发会怎样？你们多久做一次全量备份，备份文件怎么验证可用？

### Q9. 主库挂了，哨兵怎么切换？会不会丢数据、脑裂怎么办？

**问题：** 主库宕机，哨兵完成故障转移，期间业务丢了写数据；主库恢复回来后，还出现过数据回滚。分别解释原因，怎么配置减少损失？

**期望加分项：**
- 能讲清哨兵流程：主观下线 → 客观下线 → leader 选举 → failover 选新主
- 能指出异步复制的天然丢数据窗口（从库落后于主库）
- 能说清脑裂（分区）场景：旧主继续写，切换后旧主回归被降级，期间写入全丢
- 给出 min-replicas-to-write / min-replicas-max-lag 配置降低脑裂损失
- 提到哨兵数量 ≥3、quorum 设置、客户端 failover 期间的连接重试

**减分项：**
- 只知道"哨兵会自动切换"，说不出主观/客观下线细节
- 不知道脑裂这个概念，更说不出 min-replicas 配置
- 以为主从复制是同步的，无丢数据概念
- 不知道客户端要在 failover 期间处理连接中断与重连
- 哨兵自身的高可用与数量要求说不清

**解答：**
先讲复制模型：主从是异步复制，从库通过 repl backlog 增量同步，落后窗口内主库的写还没同步，此时主库挂了，从库顶上必然丢这部分数据，这是架构级限制，只能缩小不能消除。哨兵流程：哨兵 ping 主库，超过 down-after-milliseconds 主观下线；多个哨兵都判定后达到 quorum 变为客观下线；之后哨兵间选 leader，leader 从从库中选一个做新主（按复制进度、优先级），其他从库切换主从指向新主。脑裂是另一类丢失：主库与哨兵网络分区但主库进程活着、还在接收写请求，哨兵判定主库不可用并完成切换，分区恢复后旧主被降级为从库，重新同步时它那段时间的写全部被丢弃。降低脑裂损失的标准配置：min-replicas-to-write 1 + min-replicas-max-lag 10——主库发现连不上一半从库（lag 超阈值）就拒绝写，宁可短暂拒绝写，也不让脑裂期产生"注定要丢"的数据。实践中的坑：哨兵至少 3 个（奇数、quorum=2），2 个哨兵挂 1 个就永远选不出 leader；down-after-milliseconds 与业务容忍度匹配（太短频繁切换，太长故障时间久）；客户端要在 failover 窗口处理连接中断（Jedis 的 SO_TIMEOUT、Lettuce 的重连），否则服务端切好了客户端还报错；min-replicas 配置要结合写可用性权衡，写多从少的环境别把阈值设太死。

**延伸考点：** 切换后新主写入的 key 与旧主数据发生冲突怎么办（比如库存）？你们 failover 后怎么校验数据完整性？

### Q10. 单机内存不够了，Cluster 怎么分片？迁移扩容影响业务吗？

**问题：** 你们把单机 Redis 迁到 Cluster，数据怎么分片？扩缩容（resharding）时对业务有什么影响？哪些命令在 Cluster 下会受限？

**期望加分项：**
- 能说清 16384 个哈希槽、CRC16(key) % 16384 的分配机制
- 能讲清 smart client（JedisCluster/Lettuce）本地缓存槽位映射 + MOVED/ASK 重定向
- 知道多 key 操作受限（跨槽 mget/事务/Lua 报错），会用 hash tag {} 固定相关 key
- 说清 resharding 的迁移过程与对业务的影响（阻塞批次、大 key 迁移慢、部分命令重定向）
- 提到槽位倾斜、热点集中在少数槽的风险

**减分项：**
- 只会说"一致性哈希"，不知道 Redis Cluster 用的是固定槽位
- 不知道 MOVED/ASK 的区别
- 不知道 hash tag，跨槽多 key 操作直接报错
- 说不出扩容迁移的阻塞窗口
- 忽略 hash tag 滥用导致的槽位倾斜

**解答：**
先讲分片模型：Redis Cluster 固定 16384 个槽位，key 归属 = CRC16(key) % 16384，槽位由各 master 节点分管（可分配不均，但推荐均匀）。客户端是 smart client：初次启动拉取 CLUSTER SLOTS 拿到槽位映射，本地缓存后直接路由到目标节点；槽位迁移期间，目标节点返回 ASK（正在迁移中，去源节点搬 key 后再执行），key 归属已变更则返回 MOVED（客户端要刷新本地缓存）。多 key 限制：mget、事务、Lua 只允许操作同一槽位的 key，跨槽直接报错 CROSSSLOT——解决办法是 hash tag，key 写成 {user:1001}:orders、{user:1001}:cart，花括号内的部分参与哈希计算，让相关 key 落到同一槽；但 hash tag 是双刃剑，滥用会导致大量 key 挤在少数槽上（热点槽）。扩缩容：redis-cli --cluster reshard 把一部分槽从源节点迁到目标节点，迁移是逐 key 进行的（MIGRATE），小 key 很快，大 key 迁移时源节点会阻塞在 MIGRATE 上，这就是为什么大 key 在 Cluster 里是灾难；迁移期间该槽上的读写可能被重定向，客户端要正确响应 ASK。实践中的坑：迁移最好在低峰进行、一次迁移的 key 数控制好；没有 hash tag 的存量 key 迁移后跨槽业务直接坏；每个节点都要连接（连接数 = 节点数 × 客户端数），集群规模大了连接与监控成本要纳入规划；单节点内存同样受 fork/恢复限制，别把"用了 Cluster"当成大 key 的挡箭牌。

**延伸考点：** 槽位迁移到一半节点挂了怎么办？你们怎么发现和处理热点槽？

### Q11. 大 key、热 key 怎么发现？怎么治理？

**问题：** 线上 Redis 突然 CPU 飙高、命令超时，查出来是某个几十 MB 的 key，还有一个 key 每秒被访问几万次。大 key 和热 key 分别怎么发现？各自怎么治理？

**期望加分项：**
- 能区分大 key（value 过大）与热 key（访问过高）两类问题，手段不同
- 大 key 发现：redis-cli --bigkeys（低峰）、memory usage、slowlog 定位 O(N) 命令
- 热 key 发现：redis-cli --hotkeys（需 allkeys-lfu）、monitor 采样（说明其代价）、客户端统计
- 大 key 治理：拆分（Hash 分片/按维度拆）、压缩、unlink 异步删除、禁止热路径 O(N) 操作
- 热 key 治理：本地缓存、读写分离、key 打散（多副本随机读）、限流
- 意识到 bigkeys/monitor 本身的开销，选择低峰执行

**减分项：**
- 大 key 热 key 混为一谈，答不出各自的排查手段
- 用 keys * 扫全库找大 key
- 不知道 del 大 key 会阻塞主线程（不知道 unlink）
- 热 key 治理只想到"加缓存"，没有打散/副本思路
- 高峰期跑 bigkeys/monitor 不考虑副作用

**解答：**
先分清两类问题：大 key 是"单个 key 太大"（Value 几百 MB、Hash 百万字段），拖慢 O(N) 操作、阻塞迁移、占内存；热 key 是"单个 key 访问量爆炸"，把单实例 CPU 打满、单节点流量打满。发现大 key：redis-cli --bigkeys 按类型扫描统计最大的 key（注意它是全库遍历，高峰期跑会放大延迟，选低峰）；memory usage <key> 精确测单个 key 内存；slowlog 里频繁出现的 hgetall/keys/scan 往往是命中了大 key。发现热 key：redis-cli --hotkeys 需要把 maxmemory-policy 设成 allkeys-lfu 才有热度数据；monitor 命令实时抓取可定位热 key 但本身拖慢性能（高 QPS 下慎用，短时间采样即可）；更优雅的是在客户端/代理层（如 twemproxy、自研 agent）统计访问频次。治理大 key：能拆则拆（一个 Hash 拆成多个、按业务维度切 key）、能压则压（大 JSON gzip/换紧凑序列化）、该删则删（用 unlink 异步删除，避免 del 阻塞主线程）；改造前先禁止热路径上的 O(N) 操作（hgetall 改 hscan 分页、lrange 只取需要的区间）。治理热 key：读多场景先上本地缓存（Caffeine）挡大部分；再不行做 key 打散——把 hotkey 复制 N 份（hotkey:1..N）分别缓存，读时随机取一个，牺牲一点一致性换吞吐；写多场景要看业务本身是否合理。实践中的坑：大 key 拆分会改动所有读写代码，要评估收益；unlink 只是异步回收内存，极端情况下内存不会立刻降下来；热 key 打散后更新副本要广播，否则读到旧值；先定位再动手，别一上来就 flushall。

**延伸考点：** 你们怎么自动发现新出现的大 key/热 key（而不是出事才查）？拆分大 key 后跨片读取怎么合并？

### Q12. 慢查询日志里没有，命令却超时，阻塞在哪？

**问题：** 线上 Redis 命令偶发超时，slowlog 里却没有超时的命令。为什么？阻塞主线程的操作有哪些？怎么排查？

**期望加分项：**
- 能指出 slowlog 只记录命令本身执行耗时，阻塞导致的排队与延迟不会出现在 slowlog
- 列出阻塞源：O(N) 命令、大 key 同步删除（del）、fork（bgsave/bgrewriteaof）、AOF fsync 磁盘慢、内存淘汰、连接数打满
- 排查手段：latency monitor、latest_fork_usec、iostat、slowlog get、blocked_clients
- 防御：unlink、避免 keys、scan 分页、AOF 放 SSD、监控磁盘 IO
- 有"客户端超时 ≠ Redis 慢"的意识（网络、客户端 GC 也会造成超时）

**减分项：**
- 只会在 slowlog 里找原因，不知道阻塞不记录
- 说不出 fork/fsync 这些"命令外"的阻塞源
- 不知道 del 大 key 会阻塞（没有 unlink 概念）
- 只会背"keys 命令慢"，举不出更多场景
- 分不清客户端超时与 Redis 自身慢

**解答：**
先纠正认知：slowlog 记录的是"命令从开始执行到执行完"的耗时，但阻塞有三种形式它都记录不到：一是命令执行前就排队等（前面有慢命令或主线程被卡住）；二是主线程被非命令操作卡住（fork、fsync、过期清理、淘汰扫描）；三是网络问题（客户端到 Redis 的 RTT 增大）。阻塞源逐一排查：1）O(N) 命令：keys、smembers、hgetall、lrange 全量取，扫描几百万元素就是秒级；2）大 key 删除：del 是同步回收内存，几十 MB 的 key 删除也会阻塞主线程，Redis 4.0+ 用 unlink；3）fork：bgsave、bgrewriteaof 都要 fork 子进程，大实例 fork 耗时可达秒级，看 info stats 的 latest_fork_usec；4）AOF fsync：appendfsync everysec 下磁盘 IO 慢，主线程写 AOF buffer 刷盘被拖慢，iostat 看磁盘 util 打满；5）内存淘汰：maxmemory 满了每次写都触发淘汰循环；6）连接数：maxclients 打满，新连接被拒绝。排查工具：redis-cli --latency / --latency-monitor 观察延迟；info stats 的 latest_fork_usec、rdb_last_bgsave_status；latency monitor 的 latency events（fork、fsync、eviction、command）；slowlog get 50 看慢命令。实践中的坑：客户端超时先别怪 Redis，Java 侧 Full GC 停顿、连接池耗尽、网络抖动都会表现为"命令超时"，用 redis-cli --latency 从旁路实测排除；bigkeys 扫描本身也是全库遍历，低峰跑；AOF 千万别放机械盘或网络盘（NAS），fsync 慢是延迟尖刺的头号来源。

**延伸考点：** latency monitor 里的 eviction 事件出现频繁说明什么？你们怎么验证"延迟是 Redis 的还是网络的"？

### Q13. 分布式锁：SETNX 就能用？锁过期了怎么办？RedLock 有必要吗？

**问题：** 你们用 Redis 做分布式锁吗？只 SETNX key value 加锁有什么坑？锁过期了业务还没执行完怎么办？RedLock 到底该不该用？

- 能客观评价 RedLock：理论价值与工程争议（时钟跳跃、网络分区、GC pause 下并不绝对安全），多数场景单主 + 哨兵/Cluster 够用

**减分项：**

- 不知道怎么续期，答不出看门狗
- 把 RedLock 吹成万无一失，或一口否定，说不出理由
- 忽略锁过期导致临界区并发的现实，无业务兜底
- 不知道 Redisson 的封装能力

**解答：**
先给标准实现：加锁用一条原子命令 SET key uuid NX PX 30000（value 必须是每次加锁唯一的标识，如 UUID，不能是固定字符串）；解锁必须用 Lua：先 GET 比对 value 相等再 DEL，两步分开做会在"比对后 DEL 前"误删别人刚加上的锁。坑点一：锁过期而业务未完成——锁被自动释放，另一个线程进来，临界区并发。解法：Redisson 看门狗机制，加锁默认 30s 过期，后台线程每 10s 检测锁还在且业务未完成就续期到 30s，业务结束主动释放时取消续期；不用 Redisson 就手动把锁 TTL 设成业务最大耗时的上限并接受续期复杂度。坑点二：误删——上面说的 value 校验。坑点三：可重入、阻塞等待、公平性，Redisson 都封装了（hash 计数实现可重入）。RedLock 的争议要客观讲：它在 N 个独立节点上分别加锁、过半成功才算拿锁，理论降低单点故障影响；但 Martin Kleppmann 的分析指出它仍有漏洞——节点时钟跳跃会让锁同时"未过期"，网络分区 + 长 GC 停顿下多个客户端仍可能同时持有锁。所以工程结论通常是：对绝大多数业务，单主 Redis（哨兵/Cluster 保障高可用）足够；真要求极端互斥（如重复扣款），要么上 etcd/zookeeper（有租约 + fencing），要么在业务侧加版本号（fencing token）校验，而不是依赖 RedLock 玄学。实践中的坑：锁 TTL 设得比业务耗时短是最常见事故；看门狗在进程被 kill -9 时锁会自然过期（OK），但进程假死（GC 停顿）期间锁过期，别的线程进来——极端场景业务必须容忍；分布式锁不是万能，锁保护下的资源操作要幂等。

**延伸考点：** 你们锁保护的关键操作怎么保证幂等？fencing token 和数据库乐观锁结合怎么做？

### Q14. 扣库存、限流为什么用 Lua？Lua 和 MULTI/EXEC 事务有什么区别？

**问题：** 扣库存要求"先查再减"原子完成，限流要做"计数 + 判断"的滑动窗口。为什么用 Lua 脚本？Lua 和 Redis 事务（MULTI/EXEC）有什么区别？Redis 为什么不做真正的回滚？

**期望加分项：**
- 能说清 Redis 单线程模型下单命令原子，但"读-改-写"复合操作必须脚本或事务包裹
- Lua（EVAL）整体原子执行，脚本内可做条件判断（先查库存够不够再决定减不减）
- MULTI/EXEC 只是批量排队执行，命令间无法根据前一条结果做决策，且无隔离语义（EXEC 期间其他客户端命令可穿插）
- 知道 Redis 事务不支持回滚的设计哲学（语法错误入队即拒，运行期错误不中断）
- 场景判断：需要"读后决定"的逻辑用 Lua；纯批量无逻辑用 Pipeline/事务
- 注意 Lua 脚本不能有长循环/大遍历，否则阻塞整个实例；不能使用随机/非确定性命令（TIME、random）

**减分项：**
- 分不清 Lua 与事务的差别，以为两者等价
- 以为事务能保证"读到的值不被别人改"（没有隔离性）
- 写 Lua 脚本不注意复杂度，写出秒级阻塞脚本
- 不知道 EVALSHA 脚本缓存、Redis 7 的 Function
- 扣库存只说"用 Lua"，说不清脚本内容和回补逻辑

**解答：**
先讲为什么：Redis 单线程执行保证"单条命令"原子，但扣库存是"GET 当前库存 → 判断 > 0 → DECR"三步，不包起来就可能在判断后被别人扣到负数。Lua 脚本通过 EVAL 提交，整个脚本作为一段原子执行，中间不会有其他命令插入，且脚本内能做 if 判断——这是它和事务最大的区别。对比 MULTI/EXEC：事务只是把命令入队后一次性执行，命令之间互相独立，你不能"根据第一条命令的返回决定第二条发不发"；而且 Redis 事务没有隔离性，EXEC 执行期间别的客户端命令可能穿插在中间执行（5.0+ 才保证 EXEC 期间 WATCH 键不变）。为什么不做回滚：Redis 设计哲学是简单高性能，事务中一条命令运行期失败不会中止后续命令（语法错误在入队时就被拒绝），失败的影响范围可控，官方态度是"用脚本规避错误，而不是靠回滚兜底"。扣库存的 Lua 伪代码：if tonumber(redis.call('GET', key)) >= n then redis.call('DECRBY', key, n) return 1 else return 0 end，客户端收到 0 就知道库存不足。限流可以用 Lua 维护滑动窗口计数（ZADD + ZREMRANGEBYSCORE + 判断 count < limit）。实践中的坑：Lua 脚本不要写循环遍历大集合，脚本执行期间整个 Redis 实例都被卡住，这是线上事故高发点；脚本内禁止 TIME、RANDOMKEY 等非确定性命令（复制到从库会不一致）；脚本提前用 SCRIPT LOAD + EVALSHA 减少传输；扣库存成功但后续下单失败，要幂等回补（返还库存要防重复还）。

**延伸考点：** 扣库存和下单不在一处、扣成功但下单失败怎么处理？Lua 脚本出现运行期错误时，已经执行的部分会回滚吗？

### Q15. 批量写缓存用 Pipeline 还是事务？两者到底啥区别？

**问题：** 你们批量写缓存时用 Pipeline 还是 MULTI/EXEC 事务？有人用 Pipeline 提速，有人用事务保证原子。两者本质区别是什么？Pipeline 有副作用吗？

**期望加分项：**
- 能指出 Pipeline 解决"网络 RTT"，事务解决"原子性"，两者维度不同、可以结合
- 说清 Pipeline 无原子性（命令间可插入其他客户端命令），事务每条命令仍是一次网络交互
- 场景判断：纯批量写入用 Pipeline；需要"整体成功或失败"语义才考虑事务，Redis 事务实际也不是真回滚
- 知道 Pipeline 大批量发送的副作用：服务端命令积压、内存放大、结果全量缓存、错误定位难
- 有实践数字：一批几千条、分片发送，而不是一次几万条

**减分项：**
- 把 Pipeline 和事务混为一谈，以为 Pipeline 也原子
- 不知道 Pipeline 大量命令积压导致的内存/延迟问题
- 事务里依赖前一条命令结果做判断（事务做不了，该用 Lua）
- 没有批量大小的实践感知

**解答：**
先分清两个维度的东西：Pipeline（管道）是客户端机制，把多条命令打包成一次网络发送，服务端逐条执行后一次性返回，解决的是 RTT（往返）开销——批量 100 条命令串行要 100 个 RTT，Pipeline 只要 1 个；MULTI/EXEC 是服务端机制，命令先入队，EXEC 时按序执行，解决的是"多条命令一起执行、中间不被其他客户端插入"的原子性。区别要点：Pipeline 不具备原子性，管道里的命令之间其他客户端可以插入；事务本身不省网络（每条命令入队还是逐个发，但可以套 Pipeline 把入队也打包省 RTT）；两者可以叠加（MULTI + EXEC 之间的命令走 Pipeline 发送）。场景选择：纯批量写入（比如批量初始化缓存、批量计数累加）用 Pipeline 就够，没必要上事务；需要"中间无插入"的场景（如先 SET 再 INCR）优先 Lua 脚本而不是事务——因为 Redis 事务不支持"根据前一条命令结果做决策"，运行期错误也不回滚，灵活性远不如 Lua。Pipeline 的副作用要说清：一次塞几万条命令，服务端命令积压导致内存上升、后续命令延迟放大；返回结果全部缓存在客户端内存，读回时如果客户端处理慢也会卡；管道中某条命令出错只能按顺序解析定位，排查费劲。实践建议：分批发送（每批几百到几千条），观察延迟与内存，配合连接池；写多读少场景 Pipeline 收益明显，读多写少收益小；如果命令之间有逻辑依赖，别用 Pipeline，用 Lua。

**延伸考点：** Pipeline 里一条命令执行报错，其他命令还会执行吗？事务里的一条命令报错呢？两者的差异说明了什么？

### Q16. 消息通知用 Pub/Sub 还是 Stream？消息丢了谁负责？

**问题：** 你们有业务要用 Redis 做消息通知（如事件广播、任务队列）。Pub/Sub 和 Stream 怎么选？"订阅方不在线消息就丢"这种事分别发生在哪个方案里？和 Kafka 这类专业 MQ 的边界在哪？

**期望加分项：**
- 能说清 Pub/Sub 即发即弃：无持久化、无 ACK、无消费者组，订阅方离线/断连即丢
- Stream（Redis 5.0+）类似 Kafka：XADD 追加、消费者组、XREADGROUP、pending 列表、XACK、MAXLEN 裁剪
- 场景判断：实时广播/弱可靠性用 Pub/Sub；需要可靠投递、失败重试、消费进度用 Stream
- 丢消息场景盘点：Pub/Sub 离线即丢、慢消费者积压被断连；Stream 消费者崩溃后 XCLAIM 重分配、消息被 MAXLEN 裁剪、Redis 重启依赖持久化
- 明确边界：复杂路由、事务、多分区、亿级吞吐交给 Kafka/RabbitMQ，Redis 只做轻量队列

**减分项：**
- 不知道 Stream 存在，只会说 Pub/Sub
- 以为 Pub/Sub 能"补发"离线消息
- 说不出消费者组、pending、XACK 这些 Stream 核心概念
- 高可靠性消息场景硬用 Redis Pub/Sub，答不出为什么不行
- 没有与专业 MQ 的边界意识

**解答：**
先定性：Pub/Sub 是"即发即弃"的广播——发布者把消息丢给 Redis，在线订阅者实时收到；消息不落盘、无 ACK、无消费进度，订阅者不在线（或网络抖动断连）就永久丢。所以 Pub/Sub 适合：在线状态广播、内部事件通知、直播弹幕这类"丢了无所谓"的场景。Stream 是 Redis 5.0+ 的可靠消息结构，能力对齐 Kafka 的子集：XADD 追加消息，XREAD/XREADGROUP 消费，消费者组内消息分发给组员，每个消费者有 pending（PEL）列表记录未确认消息，XACK 确认后移除，消费者崩溃后其他消费者用 XCLAIM 接管 pending 消息，消息保留用 MAXLEN 裁剪（~ 近似裁剪更省性能）。所以 Stream 适合：任务队列、需要失败重试与消费进度的业务消息。丢消息盘点：Pub/Sub 丢——订阅方离线、慢消费者（客户端读缓冲区满被强制断连，消息在服务端无法暂存）；Stream 丢——消费者组里消息 XACK 前消费者挂掉（可用 XCLAIM 恢复）、消息被 MAXLEN 裁剪掉（backlog 超限）、Redis 本身重启丢失（取决于持久化配置，AOF 关了照样丢）。与专业 MQ 的边界：需要事务消息、死信队列、消息路由、跨机房高可用、超大规模吞吐，交给 Kafka/RabbitMQ；Redis 当消息中间件是"轻量够用"，别把核心订单链路压在 Redis Stream 上——它单实例的可靠性天花板就是 Redis 的可靠性天花板。实践中的坑：Pub/Sub 在高 QPS 下慢消费者会被断连（client-output-buffer-limit pubsub 配置可调）；Stream 的 PEL 不消费也不清理会无限增长；Stream 里大消息会阻塞（避免）；消息要设计幂等消费。

**延伸考点：** Stream 消费者组里的消息被 XCLAIM 接管后重复消费，业务怎么幂等？Pub/Sub 的慢消费者被断连后，消息还能找回来吗？

### Q17. 内存涨到 90% 又不让清空，怎么定位根因？新业务怎么预估容量？

**问题：** 线上 Redis 内存涨到 90%，又不允许清空，怎么定位是大 key、过期 key 还是业务增长？给一个排查顺序。另外，一个新业务上线前，你怎么预估需要多大内存、分几个实例？

**期望加分项：**
- 排查顺序合理：info memory（used_memory vs RSS 碎片）→ key 数曲线 → --bigkeys/memory usage 定位大 key → expired_keys/惰性删除堆积 → 对照发布/活动时间点
- 能区分 used_memory、used_memory_rss、内存碎片率三个指标
- 知道 bigkeys 只统计"每类型最大"，可能漏掉大量中等 key（用 scan + memory usage 抽样）
- 容量预估有公式：单 key 平均大小 × key 数 × 副本 × 冗余（1.5-2 倍）+ 增长缓冲，考虑 AOF/fork 内存翻倍
- 有监控闭环意识：内存水位、命中率、evicted/expired 曲线

**减分项：**
- 一上来就说"清掉大 key"或"扩容"，没有定位过程
- 分不清 used_memory 与 RSS、不知道内存碎片
- bigkeys 当作万能工具，不知道它的局限
- 容量预估拍脑袋，没有采样与公式
- 不考虑 AOF/fork 的瞬时内存翻倍

**解答：**
定位按"先看宏观、再逐层下钻"的顺序：第一步 info memory 看 used_memory（逻辑使用）、used_memory_rss（进程占的物理内存）、mem_fragmentation_ratio（RSS/used，大于 1.5 说明碎片严重，可考虑 active defrag 或低峰重启）。第二步看增长曲线：info keyspace 的 key 数量、used_memory 的时间序列，对照最近的发布、活动、数据导入时间点，判断是"持续匀速增长"（业务增长）还是"某天突然跳变"（某类数据暴增）。第三步定位大 key：redis-cli --bigkeys 在低峰跑（它只输出每种类型最大的几个，可能漏掉大量中等大小的 key，所以再配合 SCAN 游标遍历 + memory usage 精确抽样）；结合 slowlog 看有没有 hgetall/lrange 大 key 操作。第四步排查过期 key：info stats 的 expired_keys 曲线，如果过期键堆积（TTL 设置了但删除不及时，惰性删除下过期键可能长时间占内存），可以主动 scan 清理或调 lazyfree。第五步对业务增长：DBA 或业务侧给 key 前缀命名规范的话，按前缀分组统计就能定位是哪个业务的 key 在涨。容量预估公式：采样 N 个典型 key（memory usage），得到平均大小 A；预估峰值 key 数 K；单实例内存 ≈ A × K × 副本数 × 冗余系数（1.5-2 倍，留出过期/淘汰缓冲与碎片）；再叠加 AOF/RDB 场景 fork 时内存可能瞬时翻倍的风险，单实例一般建议控制在 16-32G 以内；最后按"单实例可承载内存上限"反推分几个实例、要不要上 Cluster。实践中的坑：别在内存 90% 时跑 bigkeys（全库遍历加重压力）；先定位再扩容/清理，盲目 flushall 是最糟操作；容量预估别只按当前数据量，要乘 3-6 个月的增长预期。

**延伸考点：** used_memory 不高但 RSS 很高，说明什么？你们怎么做 key 前缀的规范化以便按业务统计内存？

### Q18. 命令都很简单，QPS 却上不去、延迟还高，从哪优化？

**问题：** 线上 Redis 单条命令都很简单（GET/SET 为主），QPS 却上不去、延迟还偏高。除了命令本身，还有哪些因素在拖后腿？你们一般从哪几个方向优化？

**期望加分项：**
- 能指出瓶颈往往在客户端/网络/连接管理，而不是 Redis 单命令
- 连接池：合理配置大小、避免频繁建连断连，讲清"Redis 单线程但连接池仍必要"的原因（并发吞吐）
- 网络 RTT：Pipeline、mget/mset/hmget 聚合命令
- 序列化：避免 JDK 默认序列化臃肿，用 Protobuf/Kryo/JSON 精简，注意省内存费 CPU 的平衡
- 服务器侧：慢查询、大 key、TCP_NODELAY、同机房部署
- 有量化意识：先压测定位是 CPU、网络还是连接瓶颈

**减分项：**
- 只会在 Redis 服务器侧找问题，想不到客户端与网络
- 不知道连接池与 Redis 单线程的关系（以为连接池没用或多连接能并行加速单命令）
- 不考虑 RTT，逐条小命令硬扛
- 序列化方案说不出权衡
- 优化没有压测与指标对比

**解答：**
先给判断：单命令延迟高，十有八九是"网络往返 + 客户端开销 + 连接管理"的问题，Redis 本身单命令微秒级。按收益排序：第一，网络 RTT：客户端与 Redis 同机房部署，延迟从跨机房 5-10ms 降到 0.2-0.5ms，这是最大头；批量场景用 Pipeline 或聚合命令（mget、mset、hmget、sadd 多成员），把 N 个 RTT 压成 1 个。第二，连接池：Redis 是单线程模型，多连接并不能并行加速单条命令，但连接池让并发请求复用连接、避免每请求建连断连（建连有 TCP 握手 + Redis 握手开销），maxTotal 按 QPS × 平均耗时估算，过大反而浪费客户端资源、打高 Redis 端连接数（maxclients 有上限）。第三，序列化与 value 设计：默认 JDK 序列化体积膨胀 3-5 倍，换 Protobuf/Kryo/紧凑 JSON，序列化本身从毫秒级降到微秒级；value 结构设计避免"读 100 字节只要 1 字节"（比如 hgetall 大 Hash 只取需要字段）。第四，客户端并发模型：Lettuce 基于 Netty 多路复用、Go/Node 天然异步，别用阻塞同步客户端在高 QPS 下打满线程。第五，服务器侧兜底：slowlog 查慢命令、排查大 key、TCP_NODELAY（禁 Nagle 算法，小包不延迟合并）、io-threads 默认别开（Redis 6.0+ 多线程只处理网络 IO，官方建议非必要不开启，单线程处理命令仍够快）。实践中的坑：先压测定位再优化（用 redis-benchmark 或客户端压测对比），别盲目调参；Pipeline 过大反而内存放大（见 Q15）；序列化省内存/省网络但费 CPU，要按业务权衡；连接池 maxTotal 过大会触发 maxclients，也要监控。

**延伸考点：** 客户端 QPS 到 10 万、Redis 单实例 CPU 已经 80%，是加实例还是上 Cluster？你怎么判断瓶颈在客户端还是服务端？

### Q19. 延迟从 1ms 涨到 50ms、还有 key 莫名消失，怎么排查？

**问题：** 业务反馈 Redis 延迟从 1ms 涨到 50ms、命令偶发超时，同时有人反应 key 莫名其妙消失。你作为负责人，按什么顺序排查？从哪些指标入手？"丢 key"可能有哪些根因？

**期望加分项：**
- 排查顺序结构化：基础指标（CPU/内存/网络/连接）→ 实例事件（fork/重启）→ 命令级（slowlog/bigkeys/latency）→ 客户端链路
- 能区分症状同源：延迟与丢键可能都指向同一根因（重启、淘汰、内存劣化）
- 丢 key 根因盘点：过期删除、内存淘汰（evicted_keys）、主从切换/脑裂回滚、误操作（flushall）、前缀错误
- 用 uptime 变化判断重启、用 latest_fork_usec 判断 fork 阻塞
- 有"客户端超时不等于 Redis 慢"的鉴别方法（旁路 redis-cli --latency）

**减分项：**
- 没有排查顺序，想到哪查哪
- 只盯着 slowlog，不知道重启/fork/淘汰这些事件
- 丢 key 只想到"被人删了"，漏掉过期、淘汰、脑裂等系统级根因
- 不知道看 uptime、evicted_keys、expired_keys 这些指标
- 客户端 GC 停顿导致的超时误判为 Redis 故障

**解答：**
按"由外到内、由宏观到微观"排：第一步，基础面：CPU（user 高是命令重，sys 高是网络/IO）、内存（used_memory、RSS、碎片率）、网络（带宽打满？重传？）、连接数（blocked_clients、是否触达 maxclients）。第二步，实例事件：info server 的 uptime 秒数突然变小 = 刚重启过（重启前的数据若没持久化就丢——直接解释"丢 key"）；info stats 的 latest_fork_usec（最近一次 fork 耗时）、rdb_last_bgsave_status（bgsave 是否成功）；AOF 开启的话看磁盘 IO（iostat 的 util 是否打满，fsync 慢会造成延迟尖刺）。第三步，命令级：slowlog get 50 看慢命令、redis-cli --bigkeys 找大 key、latency monitor 看 latency events（fork/fsync/eviction/command 事件即延迟根因）。第四步，客户端链路：用 redis-cli --latency 从旁路实测真实延迟，如果旁路正常而业务超时，问题在客户端（连接池耗尽、GC 停顿、网络到业务的链路），Java 侧 Full GC 停顿几秒会让所有命令"看起来超时"，但 Redis 其实是好的。丢 key 的根因按可能性排：过期删除（TTL 到期，看 expired_keys 曲线，key 本来就有 TTL 却被当作"莫名消失"）、内存淘汰（看 evicted_keys，allkeys-lru 下当存储用的 key 被踢）、主从切换脑裂（旧主写的数据在切换后丢失，看 uptime 与主从角色变化日志）、误操作（flushall/flushdb 审计）、客户端 bug（key 前缀/序列化错误）。实践中的坑：先看 uptime 和事件日志再下结论，别一上来怀疑"黑客删库"；延迟问题要区分 Redis 内部 vs 网络 vs 客户端三段；丢 key 与延迟同时出现时，优先怀疑重启或内存劣化这类同源根因。

**延伸考点：** 如果你发现是主从切换导致的丢 key，怎么确认？flushall 这种高危命令你们怎么做操作审计与防护？

### Q20. 全面引入 Redis，作为负责人你怎么设计整体方案？

**问题：** 假设你们业务要大规模引入 Redis：哪些数据进 Redis、哪些不进？缓存和存储怎么分？容量与分片怎么规划？Redis 挂了业务怎么办？从架构视角给出你的设计。

**期望加分项：**
- 有数据分级意识：按"可丢性/一致性要求/访问模式"给数据分级，而不是什么都塞 Redis
- 能划清边界：纯缓存（可重算）进 Redis；强一致状态（钱）不进；存储型数据慎重（内存贵，用 MySQL/专业存储）
- 分层设计：L1 本地缓存 → L2 Redis → L3 DB，明确各层职责与失效策略
- 一致性按业务分级：弱一致用 Cache Aside，强一致走 DB 事务 + 缓存只做加速，关键决策不依赖缓存
- 容量与高可用：预估公式、单实例上限、Cluster/分片策略、主从 + 哨兵，降级预案（Redis 挂 → 直读 DB + 限流熔断）并演练过
- 监控体系：命中率、延迟、内存、evicted/expired、大 key/热 key、故障演练

**减分项：**
- 把 Redis 当万能存储，什么数据都往里塞（最大反模式）
- 强一致业务依赖缓存结果做决策
- 没有降级预案，Redis 一挂业务全瘫
- 容量规划只看当前数据量，不看增长与副本
- 没有监控与演练闭环

**解答：**
开放题，考的是结构思维，参考框架如下。第一步，数据准入分级：按"可丢性 × 一致性要求 × 访问模式"分三类——A 类纯缓存数据（商品页、配置、会话），丢了可从 DB/上游重建，放心进 Redis；B 类状态型数据（库存、余额、订单状态），强一致要求，核心决策必须走 DB 事务，Redis 只做读加速与限流计数，并接受其最终一致；C 类存储型数据（用户资料、日志、明细），可丢性低，内存昂贵，放 MySQL/对象存储，Redis 只缓存热点。第二步，架构分层：L1 本地缓存（Caffeine，毫秒级、扛热点）→ L2 Redis（共享缓存、分布式锁、计数）→ L3 DB；L1 只放"变了无所谓"的高频只读数据，避免本地缓存一致性噩梦。第三步，一致性策略：弱一致（浏览类）Cache Aside + 写后删即可；强一致（库存）DB 事务 + binlog 同步到缓存 + 定期校验补偿，关键决策（扣款成功与否）以 DB 为准，缓存只加速不决策。第四步，容量与分片：按"单 key 平均大小 × 峰值 key 数 × 副本 × 冗余 1.5-2 倍 × 增长系数"预估，单实例控制在 16-32G（fork/恢复成本），超了按业务域拆分实例或用 Cluster，key 设计留业务前缀便于按域统计。第五步，高可用与降级：主从 + 哨兵/Cluster 保可用；降级预案三层——Redis 降级直读 DB（限流 + 连接池保护，防止打垮 DB）、本地缓存兜底、核心链路熔断降级（返回默认值）；预案必须演练，真出事才有肌肉记忆。第六步，治理与监控：命中率、P99 延迟、内存水位、evicted/expired、大 key/热 key 巡检、操作审计（flushall 防护），形成"发现→定位→治理→验证"闭环。最大的坑就一条：把 Redis 当万能存储、上线前没想清楚挂了怎么办。

**延伸考点：** 如果你们要求"库存扣减以 DB 为准、Redis 只是挡流量"，怎么设计才能既挡住流量又不超卖？降级预案里"返回旧数据"的旧数据从哪来？
