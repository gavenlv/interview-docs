# 前端 · 工程化与性能（面试题库）

本文件考察前端工程师在真实工程场景中的实践能力，覆盖构建优化（Webpack/Vite）、首屏与运行性能（Web Vitals、长任务）、监控与告警（性能指标、错误上报）、资源与缓存策略（CDN、HTTP 缓存、Service Worker）、工程质量治理（规范、CI/CD、组件库、Monorepo）以及安全与架构演进。题目均为场景化提问，重点衡量候选人能否给出量化依据、说清取舍，并以线上实践佐证结论，而非复述八股概念。

### Q1. 首页 LCP 从 2 秒涨到 6 秒，怎么系统性定位并优化？

**问题：** 线上首页 LCP 从 2 秒涨到 6 秒，用户开始投诉，但你不知道是网络、代码还是第三方服务导致的。请给出从定位到优化的完整思路。

**期望加分项：**
- 先用数据分层定位：把 LCP 拆成 TTFB、资源加载、渲染绘制几段分别排查，或借助 Performance 面板/Lighthouse/RUM 数据，而不是凭感觉猜
- 能区分环境差异：线上 vs 预发 vs 本地、弱网 vs 强网、不同地域 CDN 命中情况
- 会结合"涨到 6 秒"的时间点反查发布记录，判断是否为某次发版引入的回归
- 能给出可量化的优化手段：压缩、CDN、拆包、preload LCP 资源、SSR/预渲染等，并说明取舍
- 优化后用同一套指标回验，能证明"确实变快了"而非体感
- 主动考虑 LCP 元素判定、懒加载破坏 LCP、第三方脚本阻塞等边界

**减分项：**
- 上来就背"压缩、CDN、缓存"优化清单，跳过定位环节
- 只看本地 DevTools，忽略线上真实网络与设备差异
- 分不清 TTFB、FCP、LCP、INP 的含义和各自对应的优化手段
- 优化后无量化对比，答不出"怎么证明优化有效"
- 忽略第三方脚本（埋点、客服、AB 实验）对首屏的拖累

**解答：**
先别急着优化，第一步确认"涨"发生在哪一层：打开 DevTools Performance 复现，同时拉取 RUM 数据对比 2 秒与 6 秒两个时间点之间的发布记录，确认是否为某次发版引入的回归。LCP 定位要逐段拆：Network 面板看 TTFB（服务端、网关、CDN 问题）、主文档与关键资源下载耗时（体积、带宽、CDN 命中问题）、LCP 元素从开始解析到绘制完成的时间（渲染阻塞问题）。一个常见的坑是 LCP 元素被判定为一张懒加载图片——首屏图片加了 loading="lazy"，浏览器会推迟加载，直接把 LCP 拖垮，这种问题用任何"压缩"手段都救不回来，正确做法是给 LCP 资源加 fetchpriority="high" 并用 preload 提前拉取。其次排查第三方脚本：埋点 SDK、客服、AB 实验脚本若同步加载会阻塞解析，应改为 async/defer，或推迟到空闲时间加载。定位清楚后再动手：首屏资源拆包、CDN 预热、图片转 WebP/AVIF 并按目标尺寸输出，必要时对首屏做服务端渲染或静态化。最后回到 RUM 面板用同一指标验收，并设置性能预算告警，防止再次回归。

**延伸考点：** LCP 压下来了但 TTFB 反而更高，你如何判断优先级？Lighthouse 全绿但线上 LCP 仍超标，可能是什么原因？

### Q2. Webpack 构建从 1 分钟涨到 8 分钟，怎么定位与优化？

**问题：** 项目构建从 1 分钟涨到 8 分钟，构建机 CPU 100%，团队每次发版都要等很久。怎么定位瓶颈并优化？

**期望加分项：**
- 用 stats 文件或 speed-measure-webpack-plugin 量化各 loader/plugin 耗时，而不是盲目加缓存
- 能判断"突然变慢"多半来自依赖或代码量增长，并用 webpack-bundle-analyzer 佐证
- 会分层优化：先编译缓存，再缩小 loader 处理范围，再并行化，最后处理依赖体积
- 知道 Webpack 5 filesystem cache 与 babel-loader cacheDirectory 的区别和适用场景
- 能谈构建优化与产物大小、内存、CI 成本的取舍，知道每项优化的副作用
- 有迁移 Vite（esbuild）的考量，且能指出迁移的成本与风险

**减分项：**
- 只会背"用缓存"，给不出具体配置与收益量级
- 不分析 stats，凭感觉调配置
- 把优化堆满，却说不出每项的实际收益和副作用（如缓存命中率、内存占用）
- 不知道 webpack-bundle-analyzer 这类分析工具
- 以为构建慢只是配置问题，忽略依赖升级、代码量增长这些根因

**解答：**
第一步量化：构建时导出 stats.json，配合 speed-measure-webpack-plugin 或 Webpack 自带计时，找出最耗时的 loader/plugin。绝大多数"突然变慢"来自依赖或代码量增长而非配置退化，先用 bundle-analyzer 确认体积分布。优化按层推进：一是编译缓存，Webpack 5 直接开 cache: { type: 'filesystem' }，babel-loader 加 cacheDirectory，增量构建立竿见影；二是缩小处理范围，loader 加 include/exclude 只编译 src，babel 用 browserslist + useBuiltIns 按需 polyfill 而不是全量注入；三是并行化，thread-loader 或 terser-webpack-plugin 的 parallel，注意多进程带来的内存翻倍与 CI 机器核数限制；四是拆依赖，把不常变的三方库抽成独立 chunk 或用 DllPlugin 减少重编译范围，但 Dll 与 HMR 兼容问题多，新项目更推荐直接迁移 Vite。最后回头查根因：比如某个大依赖（含地图数据的库、全量引入的 UI 库）被意外打进 bundle，删依赖比加缓存有效得多。优化完用同一份 stats 对比，把构建耗时接进 CI 并设阈值防回归。若团队愿意冒迁移风险，Vite 的 esbuild 预构建能把冷启动从分钟级降到秒级，但要评估 loader 生态、CommonJS 依赖兼容与产物分包行为差异。

**延伸考点：** 构建慢与产物大是两件事，你分别用什么指标衡量？迁移 Vite 后发现某老依赖不兼容，你的处理路径是什么？

### Q3. 单页应用首屏 JS 太大，怎么做代码分割与按需加载？

**问题：** 首屏 JS bundle 有 3MB，移动端首屏 3 秒起。路由懒加载、组件按需加载、体积分析，请给出完整方案和取舍。

**期望加分项：**
- 先做体积分析（webpack-bundle-analyzer / Vite build 产物分析）找出大头再动手
- 能说清路由级懒加载与组件级 dynamic import 的区别与适用场景
- 知道 splitChunks cacheGroups 的关键配置（vendors、common、拆包粒度与 chunk 数量的权衡）
- 能照顾首屏关键路径：LCP 相关代码留在首屏 chunk，其余按需加载
- 对拆分粒度有判断：拆太细导致大量小请求，HTTP/1.1 下并发握手成本高，HTTP/2、HTTP/3 下更有利
- 有实践佐证：给出优化前后体积与 LCP/FCP 的具体数字

**减分项：**
- 只会说"用动态 import"，答不出配置细节与拆分边界
- 不考虑请求数、缓存命中率与拆包粒度的平衡
- 全量引入 UI 库却说"按需加载"，自相矛盾
- 不知道懒加载与 preload/prefetch 如何配合
- 拆包后没有用指标验证收益

**解答：**
先量化：用 webpack-bundle-analyzer 或 Vite 的产物分析找出 3MB 里的大头——大概率是 UI 库全量引入、图表库、或 moment/lodash 这类大依赖。第一步做"正确的按需加载"：antd/element 这类库用 babel-plugin-import 或按路径引入，moment 换 dayjs（注意裁剪时区数据），lodash 按函数引入，这一步往往能砍掉一半体积。第二步做路由级懒加载：每个路由页改为 () => import('xxx')，Webpack 自动按路由分包，Vite 同理。第三步用 splitChunks 的 cacheGroups 抽离 vendors（三方依赖）与 common（多路由复用），配合 contenthash 让频繁改动的业务代码不影响长缓存命中。粒度要权衡：拆太细，首屏请求数暴涨（HTTP/1.1 下浏览器并发上限约 6 个）；拆太粗，缓存失效面大。实操建议"路由 chunk + 单一 vendors chunk + 复用模块抽公共"，并用 html-webpack-plugin 给首屏关键 chunk 加 preload、非关键 chunk 加 prefetch，让后续页面切换时"几乎无感"。最后用 Lighthouse 或线上 RUM 对比拆分前后 FCP/LCP，把收益量化出来再收工——拆包不是目的，首屏指标才是。

**延伸考点：** 开启 HTTP/2 后拆包策略要如何调整？懒加载的路由在弱网下被快速切换，会出现什么体验问题，怎么处理？

### Q4. 页面滚动掉帧卡顿，怎么定位长任务并优化？

**问题：** 列表页滚动掉帧、点击按钮后界面卡死 2 秒。请基于浏览器渲染原理定位长任务并给出优化方案。

**期望加分项：**
- 能用 Performance 面板的 Long Tasks 与火焰图定位耗时函数，能区分脚本执行、样式计算、布局、绘制各阶段
- 能讲清渲染流水线（JS → Style → Layout → Paint → Composite）与 60fps 的 16.7ms 帧预算
- 会处理大数据列表：虚拟滚动、分页、时间分片（requestIdleCallback）、Web Worker 计算
- 能识别强制同步布局（layout thrashing），知道读写分离的做法
- 会从 DOM 与样式层面优化：减少节点数、避免大面积重绘属性、用 transform/opacity 走合成层
- 会用长任务时长、FPS 等量化指标验证优化效果

**减分项：**
- 只会说"少用 setState"，答不出火焰图怎么读
- 分不清掉帧是 JS 长任务、布局抖动还是合成层问题
- 不知道 requestAnimationFrame 与 requestIdleCallback 的区别与用途
- 大列表直接全量渲染，答不出虚拟滚动原理
- 优化后无前后量化对比

**解答：**
先用 Performance 面板录一段滚动，看 Main 火焰图：若出现大片超过 50ms 的长任务，说明主线程被 JS 或样式计算占满；再判断任务颜色与耗时分布——脚本执行（黄色）说明是 JS 计算，紫色/绿色说明是布局与绘制开销。JS 长任务再分两类：渲染型开销（频繁改 DOM）用 requestAnimationFrame 合并写入，并避免强制同步布局——比如在循环里先读 offsetWidth 再改样式会不断触发 layout thrashing，正确做法是读操作与写操作分成两个阶段执行。计算型开销则看能否下放：耗时的数据处理放进 Web Worker，或拆成多个小于 50ms 的时间片用 requestIdleCallback 执行。列表页掉帧十有八九是大列表：几万条 DOM 一次渲染，滚动时浏览器反复布局，解法是虚拟滚动（只渲染可视区 + 缓冲区行数）或分页限制节点总量。还要检查 CSS：避免大面积 box-shadow、filter 等触发重绘的属性，用 transform/opacity 走合成层；同时审视框架层，React 的 memo、列表 key、Vue 的响应式粒度是否让更新最小化。最后别忽视"每帧都在跑"的第三方监听器与滚动事件里的重活。优化后用同一录制对比长任务数量与耗时，或用 PerformanceObserver 采集 FPS 佐证效果。

**延伸考点：** 上万行表格，虚拟滚动与 Web Worker 如何配合分工？长任务来自无法改造的第三方 SDK，怎么隔离它的影响？

### Q5. 怎么搭建一套可落地的性能监控体系？

**问题：** 团队没有性能监控，只有用户吐槽"卡"。你负责搭一套 Web Vitals 监控体系，从采集、上报到告警怎么设计？

**期望加分项：**
- 用 PerformanceObserver 采集 LCP、INP、CLS 等核心指标，能说明 performance.timing 已废弃、不准确的现状
- 区分实验室数据（Lighthouse）与真实用户数据（RUM），说明各自用途与局限
- 能设计上报策略：采样率、pagehide/visibilitychange 兜底上报避免丢数据、批量上报、URL 脱敏
- 能按维度聚合：路由、版本、网络、机型、地域，用 p75/p95 分位数而非只看平均值
- 能处理 SPA 路由切换时指标划分、首屏会话重置等实际问题
- 有告警设计：分位数阈值、分级告警、关联发布事件，避免告警风暴

**减分项：**
- 只会背"LCP、FID、CLS 是什么"，答不出怎么采集与上报
- 拿平均值当结论，掩盖长尾用户问题
- 不懂 p75/p95 分位数的意义
- 上报不分路由、不分版本，出问题无法定位到版本与页面
- 只做数据展示，没有告警与回归发现机制

**解答：**
监控体系要能回答"线上性能是否健康、是否比上次发版更差"，采集、上报、聚合、告警四环缺一不可。采集用 PerformanceObserver 订阅 LCP、INP、CLS、FCP 以及资源与长任务条目；页面级加载指标与 SPA 路由切换指标分开统计（监听 history 变化重置会话并标记路由）。上报时机很关键：用 pagehide/visibilitychange 兜底发送，避免用户直接关页丢数据；数据带路由、版本号、UA、网络类型、地域，便于后续维度拆解。上报本身要克制：按比例采样（如 10%）、聚合后批量上报、用 sendBeacon 或 fetch keepalive，避免监控拖慢业务。展示与告警不要只看平均值——2 秒的平均值可能掩盖 30% 用户 5 秒的问题，看 p75/p95 分位数并按路由、网络维度钻取。告警设计成两级：核心指标 p95 超预算触发警告，持续恶化（连续 N 个周期）才真正告警，并把最近发布版本关联进来，产出"某版本上线后某路由 LCP p95 上升 40%"这类可行动信息，而不是裸指标。最后把性能预算接进 CI，让回归在合入前被发现，监控体系才算闭环——监控的终点是自动拦截回归，而不是事后背锅。

**延伸考点：** INP 与 FID 的差异是什么，为什么 Google 用 INP 取代 FID？监控显示 LCP 长期超预算但找不到优化抓手，你怀疑数据本身有问题，会怎么排查？

### Q6. 首屏大图加载慢，图片资源优化有哪些手段？

**问题：** 电商首页顶部一张 3MB 的 JPEG 横幅，移动端加载要 4 秒。从图片格式、尺寸、懒加载、CDN、渐进加载等角度，怎么系统性优化？

**期望加分项：**
- 会先算账：目标尺寸下的合理体积（如 750px 宽、约 100-200KB），而不是"能小则小"
- 知道格式取舍：WebP/AVIF 的压缩率与兼容性、降级策略、响应式图片 srcset/sizes
- 会用 CDN 的图片处理能力（按参数裁剪、压缩、转格式），而不是本地手动维护多套图
- 能说清懒加载边界：首屏 LCP 图不能 lazy，要 preload + fetchpriority；非首屏用 loading="lazy" + 占位
- 谈渐进加载/模糊占位（LQIP）、预连接等进阶手段
- 会验证收益：图片体积、CDN 命中率、LCP 指标对比

**减分项：**
- 只会说"把图片压缩"，不知道格式、尺寸、加载时机哪个影响最大
- 所有图一律 lazy，把 LCP 图也懒加载了
- 不考虑 Retina 屏，答不出 srcset 的密度描述
- 不知道 CDN 图片处理参数怎么用
- 不验证效果，说不出收益数字

**解答：**
先明确这张图真正需要的尺寸：3MB 的原图在移动端最多显示 750px 宽，多出来的像素全是浪费。优化按"格式、尺寸、加载时机、传输"四层做。格式上，WebP 通常比 JPEG 小 30% 左右，AVIF 更小但要处理兼容降级；如果接入云厂商 CDN（OSS、COS、Cloudflare 等），直接用 URL 参数做实时裁剪压缩转格式（如 ?x-oss-process=image/resize,w_750/format,webp），比本地维护多套图省事得多。尺寸上用 srcset + sizes 按视口提供多档图，同时照顾 2x/3x 屏。加载时机最关键：首屏 LCP 横幅绝不能加 loading="lazy"——浏览器会推迟它的下载，直接用 <link rel="preload" as="image"> 或 fetchpriority="high" 让浏览器尽早开始；非首屏图用 loading="lazy" 配合模糊占位（LQIP）或骨架图。传输层再考虑 HTTP/2、HTTP/3 与 CDN 边缘节点，把 TTFB 压下来。还有一个常被忽略的收益：图片转格式后页面体积可能从 3MB 降到 300KB，首屏 LCP 与 CDN 流量成本同时改善。优化后务必用对比数据（LCP 降幅、单图体积、流量成本）向团队说明收益，而不是一句"改好了"。

**延伸考点：** 如果图片是用户上传的、尺寸格式千奇百怪，怎么在上传链路就避免后续的加载问题？CDN 缓存了旧图，更新后用户仍看到旧图，怎么处理？

### Q7. 线上资源更新后用户仍加载旧版本（缓存失效），怎么治理？

**问题：** 修复了一个线上 bug 并重新发布，但不少用户刷新后还是旧页面、旧 JS，问题依旧。请从 HTTP 缓存与版本管理角度给出完整治理方案。

**期望加分项：**
- 能说清强缓存（Cache-Control）与协商缓存（ETag/Last-Modified）的区别，以及各资源该用哪种
- 懂"文件名带 contenthash → 静态资源长缓存；HTML 不缓存或短缓存"的黄金组合
- 能排查 CDN 层缓存：回源缓存时间、缓存键是否忽略 query 参数、CDN 刷新机制
- 能处理 Service Worker 预缓存导致"永远旧版"的坑及其更新策略
- 有发布流程配合：资源先行、HTML 后切，灰度与回滚时缓存如何联动
- 会设计验证手段：抓包看响应头、对比发布前后资源 URL、定位是哪一层缓存命中

**减分项：**
- 分不清强缓存与协商缓存，说不出响应头字段
- 只知道"加版本号 ?v=2"，不懂 contenthash 与长缓存的配合
- 忽略 CDN 这一层的缓存机制
- 不知道 SPA 的 index.html 该不该缓存、该怎么缓存
- 只解决一次，答不出体系化治理（发布、回滚、灰度如何与缓存联动）

**解答：**
核心是"缓存策略与发布策略没有配合好"。标准解法是内容寻址：静态资源文件名带 contenthash（内容变了文件名就变），配合 Cache-Control: max-age=31536000, immutable 长缓存；HTML 入口不缓存或 Cache-Control: no-cache + ETag 协商。这样发新版时新 HTML 引用新 hash 资源，旧用户刷新一次即拿到新版本，没动过的资源继续命中旧缓存。排查时抓包看响应头，分三层定位：浏览器层（Cache-Control/Expires 是否异常）、CDN 层（是否缓存了旧资源、缓存键是否含 query——很多 CDN 默认忽略 query，?v=2 会命中旧缓存）、应用层（HTML 是否被网关或中间件强缓存）。最大的坑在 Service Worker：SW 预缓存了旧资源且更新策略不健全时，用户永远拿到旧版，需要设计 SW 更新流程（检测新版本、skipWaiting 时机、提示刷新、缓存版本清理）。治理要体系化：静态资源一律带 hash + 长缓存；HTML 走协商缓存；CDN 缓存时间与回源策略明确；发布时"资源先行、HTML 后切"，回滚时配合 CDN 刷新旧 HTML 的缓存。最后立一条团队纪律：任何涉及资源引用的改动都走这套缓存规范，而不是临时"清缓存"救火。

**延伸考点：** 资源带 hash 但用户断网或弱网时 HTML 加载失败，怎么兜底？灰度发布期间新旧资源并存，缓存策略如何配合？

### Q9. 按需引入了 lodash 的一个函数，bundle 里却出现了整个 lodash，怎么排查？

**问题：** 代码里写了 `import { debounce } from 'lodash'`，构建后分析产物却发现整个 lodash 都被打进来了。请定位 Tree Shaking 失效的原因并给出修复方案。

**期望加分项：**
- 讲清 Tree Shaking 原理：ESM 静态分析 + sideEffects 标记 + usedExports 剔除，三者缺一不可
- 知道 ESM 与 CommonJS 的本质区别：静态导入才能摇树，require 之后静态分析失效
- 理解 sideEffects 字段的作用与误配 false 的风险（会误删有副作用的模块）
- 能按链路排查：babel 转译成 CommonJS、TS 编译产物、库没有 ESM 入口、副作用代码
- 有具体优化手段：按路径引入、lodash-es、babel-plugin-import、升级库版本
- 优化后用体积分析工具复看产物，用数据确认"真的摇掉了"

**减分项：**
- 把 Tree Shaking 当成"自动魔法"，说不清生效的前提条件
- 不知道 sideEffects 字段，或为了省事统一配 false
- 分不清 ESM 静态导入与 CommonJS 动态引入
- 只调 Webpack 配置，不理解 babel/TS 编译链路对 ESM 的破坏
- 优化后不看产物验证，说"应该好了"

**解答：**
Tree Shaking 不是黑魔法，它建立在一个前提上：模块必须是 ESM（静态 import/export，编译器能在编译期确定导出关系），且模块被标记为无副作用。Webpack 侧是两步：module.usedExports 分析哪些导出被用到，配合 sideEffects: false 直接跳过整个模块的打包。失效排查从编译链路入手：第一环是 babel——@babel/preset-env 默认把 ESM 转成 CommonJS，除非指定 modules: false 或交给 Webpack 处理，转成 require 后静态分析失效，代码全部保留；第二环是 TypeScript，tsconfig 的 module 配置要保证产物仍是 ESM（或交给 esbuild/babel 转译）；第三环是库本身——lodash 是 CommonJS 包，整个无法摇树，要么按路径引入（import debounce from 'lodash/debounce'），要么换 lodash-es 这类 ESM 版本，要么用 babel-plugin-import 做按需转换。第四环是副作用误判：sideEffects 配 false 但模块里有全局补丁、原型扩展这类副作用代码时，线上会出现"神秘消失"的 bug，所以配 false 前要确认模块真的干净，或改用数组精确声明有副作用的文件。实践里还有两个易错点：纯 CSS 引入、polyfill 导入这类"只有副作用"的模块很容易被误伤，需要显式声明。最后，优化完必须用 bundle-analyzer 复看产物，按需引入是否成功一目了然——"我用了 import 所以自动摇了"是最常见的错觉。

**延伸考点：** sideEffects 配 false 后某个全局样式或注册代码被删了，怎么定位并修复？为什么 Rollup 的摇树通常比 Webpack 更彻底？

### Q10. 只改了一行代码，发版后用户的 JS/CSS 缓存几乎全部失效，回源量暴增，为什么？

**问题：** 线上只改了一行业务代码，发版后却发现大部分静态资源的 URL 都变了，CDN 回源量暴增。请检查构建产物命名与分包策略，找出缓存失效面失控的根因。

**期望加分项：**
- 讲清 hash / chunkhash / contenthash 三者的区别与适用场景
- 知道 contenthash 失效的常见根因：业务 chunk 与 vendor chunk 共享 runtime，业务改动带动 vendor hash 联动
- 会用 runtimeChunk 抽离运行时 + splitChunks 固定 vendor 分包，保证业务改动不影响 vendor 缓存
- 理解 moduleIds/chunkIds 的稳定性（deterministic）对缓存命中率的影响
- 能处理 CSS 与 JS 同 chunk 时的 hash 联动问题、CSS 独立提取
- 有实践数据：改动前后 URL 变化集合、缓存命中率、回源量的对比

**减分项：**
- 分不清三种 hash，只会说"用 hash"
- 不知道 runtimeChunk 是干什么的
- 业务改动导致 vendor chunk hash 全变，答不出原因
- 只背配置项，不理解 chunk 依赖图与模块 id 变化机制
- 优化完不验证缓存命中效果

**解答：**
命名策略的目标是"内容没变，URL 不变；内容变了，URL 才变"。先分清三种 hash：hash 基于整次构建，任何文件变化全部失效；chunkhash 基于 chunk，同 chunk 内文件联动；contenthash 基于文件内容，最精准，生产资源命名应该用它。本题的典型场景是：只改一行业务代码，vendors 的 hash 却跟着变了——根因是业务 chunk 与 vendor chunk 共享同一个 runtime（webpack 的模块加载器与模块映射表），业务文件内容一变，runtime 里的映射就变，vendor 的 hash 被连带改动。解法是 runtimeChunk: 'single' 把 runtime 抽成独立小 chunk，同时确认 vendor chunk 里只放真正不变的依赖（别把业务里也在变的代码塞进 vendors）。第二个坑是模块 id：不配置时 webpack 用自增数字 id，业务代码里插入一个模块就会让后续所有模块 id 位移，导致无关 chunk 的缓存全废；生产环境要配 optimization.moduleIds: 'deterministic'（Webpack 5 默认）与 chunkIds: 'deterministic'，让 id 由模块内容决定，内容不变 id 不变。第三个坑在 CSS：用 mini-css-extract-plugin 提取后，CSS 与 JS 若仍在同一 chunk，JS 内容变化会带动 CSS hash 变化（反之亦然），确认提取逻辑按内容独立计算，或拆分独立 chunk。拆包粒度也要克制：vendor 拆得太碎、更新太频繁都会侵蚀缓存收益，理想状态是"稳定依赖一个 chunk、低频升级"。上线后用"变更前后 URL 集合的差集大小、CDN 回源量、缓存命中率"做对比验收，证明改动最小化了缓存失效面。

**延伸考点：** 业务代码与依赖同一次发版升级时，缓存策略怎么联动设计？immutable 长缓存与灰度发布同时存在时，如何保证新旧资源都可用？

### Q11. 静态资源上 CDN 后，部分区域加载慢、偶尔 404、回源行为异常，怎么治理？

**问题：** 静态资源接入 CDN 后，海外用户加载很慢，偶尔出现 404，运维说是回源问题。请给出静态资源部署与 CDN 接入的完整方案。

**期望加分项：**
- 讲清 CDN 工作原理：边缘节点、回源、缓存命中、TTL 过期
- 能设计"内容寻址 + 版本目录"：先传新资源再切 HTML，目录结构天然支持回滚
- 规划静态资源独立域名，与主域分离，避免 cookie 拖累与缓存失效
- 处理回源策略：回源超时、重试、失败降级
- 知道内容寻址下资源无需手动刷新 CDN，需要刷新的是 HTML
- 有排查多地域慢的方法论：节点调度、回源链路、HTTP/2/3、运营商劫持

**减分项：**
- 不了解 CDN 缓存原理，以为资源传上去就是"全世界最新"
- 同名覆盖上传，导致新老用户拿到的资源不一致
- 静态资源与接口共用域名，或同域携带 cookie 导致无法缓存
- 不懂 CDN 刷新与内容寻址之间的关系
- 不设计版本保留策略，回滚时找不到旧资源

**解答：**
静态资源上 CDN 要解决三件事：一致性、可用性、成本。一致性靠内容寻址：文件名带 contenthash，发布时"先传新资源、再切 HTML 引用"，任何时刻用户刷新都能拿到完整可用的版本；绝对不要同名覆盖上传，否则会存在"HTML 已引用新资源但 CDN 还在回源旧文件"的窗口期。目录结构建议 /assets/{版本或日期}/{hash}.js，版本目录天然支持回滚——把 HTML 指回旧版本目录即可，几秒生效。域名规划：静态资源用独立 CDN 域名（如 static.example.com），与主域分离——同域会带上业务 cookie，请求头变大且 CDN 难以稳定缓存，跨域还能避免登录态泄露到 CDN 日志；注意配置跨域响应头（CORS）供字体、Worker 等资源使用。回源要兜底：回源超时设短（避免边缘节点排队堆积）、失败重试策略明确、回源失败时降级到上一版本或源站；海外慢先按链路排查——边缘节点覆盖与调度（对比多区域 DNS 解析结果）、回源是否跨海（源站在国内、海外用户每次回源都要跨海）、TLS/HTTP2 协商，以及被运营商劫持注入（HTTPS + HSTS 防护）。缓存策略：带 hash 的资源 Cache-Control 一年 + immutable，HTML 不缓存或极短 TTL；HTML 若由网关或边缘函数动态输出，就无需手动刷新 CDN 缓存，否则每次发版要自动刷新 HTML 缓存。最后立一条团队纪律：内容寻址的资源永远不需要"刷新 CDN"，真正要刷新的是 HTML 与少数未带 hash 的资源，把刷新动作固化进发版脚本，杜绝人工操作漏刷。

**延伸考点：** 源站在国内、目标用户主要在海外的静态资源，架构上如何规划才能降低延迟？CDN 出现大面积 5xx 时，前端侧能做什么兜底？

### Q12. 团队靠手工构建上传发布，出过几次"本地能跑线上挂了"，怎么搭 CI/CD 流水线？

**问题：** 前端发版一直是"本地 build 完压缩包上传"，最近两次都是"本地能跑、线上挂了"。你负责搭建从代码提交到上线的完整流水线，请给出设计。

**期望加分项：**

- 环境与密钥管理：按环境注入配置、secret 不进仓库与产物
- 知道回滚有两层：资源侧（内容寻址回指旧版本）与发布侧（产物与记录保留）

**减分项：**

- 流水线本身不可观测，失败无人负责

**解答：**
流水线设计的核心目标是把"环境差异"与"人为操作"从发布链路里彻底去掉。典型流程：MR 触发 → 静态检查（lint + 类型检查 + 格式）→ 单元测试 → 生产构建（在流水线内执行，产物作为 artifact 在阶段间传递，保证"构建机上是什么，线上就是什么"）→ 产物校验（体积预算、sourcemap 上传、依赖漏洞扫描）→ 部署阶段先传静态资源到 CDN/OSS、再切换 HTML 引用（避免资源与页面不一致的窗口期）→ 冒烟测试（关键路径请求断言、主资源可访问性检查）→ 灰度发布（先 10% 流量观察错误率与 LCP/INP）→ 全量。质量门禁要够硬：任何一步失败即阻断合并；灰度期间核心指标跌破阈值（错误率上升、LCP p95 恶化）要自动暂停放量而非继续。环境问题重点防两处：一是配置注入——环境变量走 CI 平台的 secret 管理，按环境区分配置，构建产物内不得出现任何密钥；二是可复现构建——lockfile 入库、固定 Node 版本、必要时固定构建镜像，保证任何时间重建得到一致产物。回滚必须是一键而非"找备份"：资源侧内容寻址天然支持——把 HTML 指回上一个版本的资源目录即可秒级生效；发布侧保留最近 N 个版本的产物与部署记录，回滚时自动联动 CDN 刷新与缓存策略。最后把流水线本身做成可观测的：各阶段耗时、失败率、失败原因统计，用"MR 到上线的 Lead Time"与"变更失败率"两个黄金指标衡量流水线健康度，持续优化。

**延伸考点：** 流水线构建一次要 10 分钟，怎么在不牺牲质量的前提下把周期压下来？灰度发现严重 bug，自动回滚的触发条件你会怎么设，避免误回滚伤到正常用户？

- 不懂 husky/lint-staged 的用途与局限（git 钩子可被跳过）
- 只管新代码，老代码与存量项目没有治理路径

**解答：**
规范落地有三层：工具配置、执行机制、演进治理。工具层先划清边界：Prettier 负责格式（缩进、引号、分号、换行），ESLint 负责质量（未使用变量、空值安全、hooks 依赖），再用 eslint-config-prettier 关掉 ESLint 里所有与格式重复的规则，从源头避免"Prettier 改完 ESLint 又报错"的撕扯。执行机制要双保险：开发时用 husky + lint-staged 在 pre-commit 只检查暂存文件（速度快，不会被存量代码的报错卡住提交），CI 里对全量或 diff 文件跑 eslint 并作为合并门禁——git 钩子能用 --no-verify 跳过，CI 才是兜底底线。规则演进要有节奏：不要一次性开全量规则，第一轮只启用无争议的（正确性相关的 error 级规则），存量代码用忽略文件列表或降级为 warn，新代码严格执行；之后每轮迭代把 warn 转 error、缩小 ignore 范围，并按模块排期做"存量清零"任务，逐步消灭历史债。TS 项目配 @typescript-eslint 的 recommended 与 React 的 hooks 规则（依赖数组）和 refresh 规则（组件热更新约束），这些规则抓的是真实 bug 不是风格，团队接受度最高。可观测性决定可持续性：把 lint 通过率、新增 error 数接进 CI 看板与 PR 评论，让规范执行有数据可见；定期复盘规则命中情况，删除常年不触发的死规则、补齐团队踩过的坑。落地的标志不是配置文件存在，而是每个开发者"想不规范都难、提交前自动被拦、出问题有据可查"，规范才会被团队当作工具而不是枷锁。

**延伸考点：** 存量代码几千条 lint error，怎么排期清零而不拖垮正常迭代？团队对某条规则有分歧，如何裁决而不是简单关掉？

### Q14. 中后台首屏 3MB、切换页面要白屏 1 秒，代码分割与按需加载怎么设计到极致？

**问题：** 中后台项目首屏 JS 有 3MB，路由切换加载新页面时白屏明显。路由懒加载已经做了，请从按需加载、拆包粒度、预加载策略与骨架屏配合的角度给出完整方案。

**期望加分项：**
- 先做体积分析（bundle-analyzer / Vite 产物分析）找大头，按"首屏必须的 / 进页面才需要的 / 永远用不到的"三层归类
- 说清路由级懒加载与组件级 dynamic import 的分工：页面级切包，弹窗/图表/编辑器等重型组件在真正打开时才加载
- 拆包粒度有量化依据：HTTP/2 下 chunk 数量与体积的权衡、vendors 与 common 的边界，避免"拆太碎"或"vendor 一个 chunk 3MB"
- 预加载策略成体系：首屏关键资源 preload，用户 hover/即将进入的页面 prefetch，配合 performance hints
- 骨架屏与懒加载衔接：路由切换时有骨架屏兜底，消除"点击后长时间空白"的感知问题
- 有前后对比数据：首屏体积、路由切换耗时、白屏时长

**减分项：**
- 只会"加懒加载"，说不出拆包边界与粒度权衡
- 把所有代码都懒加载，首屏关键代码也被拆走，反而更慢
- 不考虑 HTTP/2 下并行加载与 chunk 数量的关系，拆包无量化依据
- 懒加载页面没有任何加载态，白屏体验更差
- 不分析产物，凭感觉拆包

**解答：**
先量化再动手：用 bundle-analyzer 看 3MB 里到底有什么，常见是"全量引入的 UI 库 + 图表库 + 体积巨大的依赖"。把代码分成三类：首屏必需的（路由框架、登录态、布局）、进入页面才需要的（各路由页面、图表、编辑器）、极少触发的（管理后台里一年用几次的导出功能）。路由级懒加载已经做了，接下来补两层：一是组件级动态 import，比如表格的导入弹窗、报表的图表组件，`() => import('xxx')` 且不要提前执行，配合 Suspense 或自定义 loading；二是拆包粒度——用 splitChunks 把"所有路由共用的依赖"抽成一个或少数几个 chunk，但要克制：HTTP/2 下多几个请求无所谓，但 chunk 拆到几十个会让首屏请求数失控，量化标准是"首屏关键链路上的请求尽量少而小，非关键路径尽量晚加载"。预加载要成体系：首屏真正用到的关键 chunk 用 preload 提前拉，用户 hover 到某个菜单项时用 prefetch 预取对应路由 chunk（webpack 的 magic comment `/* webpackPrefetch: true */` 或 Vite 的 import.meta.glob 配合），让"点击后秒开"。最后是骨架屏：路由懒加载的页面切换时，先渲染与目标页面结构一致的骨架占位，配合 chunk 加载完成后的真实渲染，把"白屏 1 秒"变成"骨架 1 秒"——感知体验完全不同。收尾用数据验收：首屏体积从 3MB 降到多少、路由切换耗时、白屏时长，缺一个都说明没闭环。

**延伸考点：** 首屏某个 500KB 的依赖只有两个路由用，放 vendors 还是跟路由走，判断依据是什么？prefetch 预取过多导致带宽浪费或弱网下反而拖慢首屏，怎么控制？

### Q15. 全站性能只有用户吐槽"卡"，Web Vitals 采集、治理与防回归怎么搭？

**问题：** 团队没有性能监控，只有用户吐槽"卡"。你来负责从零搭建 Web Vitals（FCP/LCP/CLS/INP）的采集、治理与防回归体系，并跑通"发现问题 → 定位 → 修复 → 验证"的完整链路。

**期望加分项：**
- 用 PerformanceObserver 采集 FCP/LCP/CLS/INP 等指标，能说明 performance.timing 的局限与替换理由
- 区分实验室数据（Lighthouse）与真实用户数据（RUM），说明各自用途与局限，RUM 按 p75/p95 分位数聚合
- 上报链路完整：pagehide/visibilitychange 兜底、sendBeacon、采样率、URL 脱敏、带版本号与路由
- SPA 处理细节：路由切换重置会话、指标归属页面、避免跨路由统计错误
- 治理闭环：指标恶化 → 用瀑布图/长任务定位 → 专项优化 → 同指标回验，且能关联发布定位回归
- 防回归：性能预算接进 CI，超预算构建失败，而不是等线上出事

**减分项：**
- 只会背"LCP、CLS 是什么"，答不出怎么采集、怎么上报
- 拿平均值掩盖长尾，不懂 p75/p95 的意义
- 采集数据不带版本、路由、网络类型，出问题无法定位到具体发布与页面
- 只做采集展示，没有告警、没有治理、没有防回归
- 不知道 SPA 下指标会串路由、会话不重置等实际问题

**解答：**
先明确目标：监控体系要能回答"这次发版性能是变好还是变坏"。采集用 PerformanceObserver 订阅 FCP、LCP、CLS、INP（旧的 performance.timing 已废弃且不准确），用 bfcache、字段化指标的 `navigationEntry` 等补充上下文；SPA 下要监听路由变化重置会话——很多团队踩过"LCP 一直记在首页上"的坑，路由切换后要把新页面的 LCP/CLS 归到新路由。上报要可靠：用 pagehide/visibilitychange 兜底（用户直接关页也能发出）、sendBeacon 或 fetch keepalive、按比例采样（如 10%）、带上版本号、路由、网络类型、机型，URL 做脱敏（去掉 query 里的用户参数）。数据侧必须区分实验室与 RUM：Lighthouse 是受控环境、可复现但不能代表真实用户；RUM 覆盖真实长尾但要处理噪声，聚合用 p75/p95 分位数而不是平均值——平均 2 秒可能掩盖 30% 用户 5 秒的糟糕体验。治理闭环分四步：监控面板看趋势 → 指标恶化时用 WebPageTest/瀑布图/长任务火焰图定位瓶颈（是 TTFB、资源体积、还是 JS 执行）→ 针对性优化（拆包、图片、预加载、SSR 等）→ 用同一指标口径回验并同步给团队。防回归比救火更重要：把 LCP/INP/CLS 预算写进 CI，超预算直接失败，并接告警（如 LCP p95 连续 N 个周期超阈值），关联发布记录定位是哪次上线引入的。整套体系跑通后，"卡"这种模糊吐槽就变成了"哪个路由、哪个版本、什么网络下、哪个指标超标"的精确问题。

**延伸考点：** INP 与 FID 的区别是什么，为什么 Google 用 INP 取代 FID？RUM 显示某路由 LCP 长期超标但实验室测不出来，可能是什么原因？

### Q16. 测试金字塔怎么落：单元、组件、E2E 分别测什么、投入多少？

**问题：** 团队没有测试习惯，bug 频繁漏到线上。你被要求引入测试，但时间和人力都有限。请给出单元测试、组件测试、端到端测试的分层策略、优先级与取舍。

**期望加分项：**
- 讲清测试金字塔：底层单元测试多而快，顶层 E2E 少而贵，按 ROI 分配而不是"每层都堆"
- 明确三层分工：单测覆盖纯逻辑/工具函数/状态管理，组件测试覆盖交互与渲染行为，E2E 覆盖关键用户链路
- 有优先级意识：先给核心业务逻辑与高危模块补测试，E2E 只保登录、下单、支付这类黄金路径
- 知道各类测试的成本：E2E 慢、脆、依赖环境，全量 E2E 会拖垮 CI，单测/组件测试要能毫秒级跑完
- 会处理测试稳定性：选择器用 data-testid、mock 外部依赖、避免测试间相互依赖
- 能谈与 CI 的结合：单测组件测进门禁，E2E 冒烟或定时跑，避免阻塞日常提交

**减分项：**
- 一上来就"全链路 E2E"，慢且脆，最终被团队弃用
- 不知道三层各自测什么，或把 UI 快照当组件测试主力（改一点挂一片，价值极低）
- 测试互相依赖、依赖真实环境，跑起来不稳定
- 只为覆盖率数字写测试，不覆盖真实风险点
- 测试没接进 CI，只在本地偶尔跑

**解答：**
先接受现实：资源有限，测试必须按 ROI 分配，这就是测试金字塔的意义。底层是单元测试：测纯函数、工具库、状态管理（reducer/store）、hooks 逻辑——不依赖 DOM 和网络，毫秒级跑完，覆盖的是"最容易写错也最容易回归"的业务逻辑；中层是组件测试（React Testing Library / Vue Test Utils）：从用户视角断言渲染结果与交互行为（点击按钮出现什么、输入后列表怎么变），避免直接断言内部实现细节；顶层是端到端测试（Playwright/Cypress）：用无头浏览器模拟真实用户操作，覆盖登录、下单、支付这类"挂一次就是事故"的黄金链路。三层成本差异巨大：单测毫秒级、可跑几千条；E2E 一条就要几秒到几十秒，还要处理选择器稳定、环境依赖、并发执行，所以 E2E 必须控制在几十条以内，且只保关键链路——把全站几百条页面都写成 E2E 是常见死法。落地优先级：先给当前事故频发的模块补单测与组件测试（比如权限计算、金额计算、表单校验），E2E 从登录和最高频的核心流程起步。稳定性工程要前置：测试选择器统一用 data-testid（避免类名改了测试挂）、mock 掉第三方 SDK 和网络请求、每个测试独立造数互不影响、失败自动重试并截图。CI 集成分档：单测与组件测试进 merge 门禁（快，必跑），E2E 放部署后冒烟或 nightly 定时跑，避免拖慢合入速度。最后记住：测试是"防回归的网"，覆盖率是手段不是目标，把网撒在事故高发区才是最优解。

**延伸考点：** 某条 E2E 在 CI 上偶发失败但本地必过，怎么排查？快照测试的适用场景是什么，为什么不能当组件测试主力？

### Q17. 多团队要合一个平台，微前端怎么选：qiankun 还是模块联邦？

**问题：** 公司想把多个独立业务团队的前端聚合到一个平台（统一登录、导航、权限），且各团队技术栈不完全一致。请比较 qiankun 与模块联邦两种方案的原理、隔离能力与适用场景，给出选型建议。

**期望加分项：**
- 讲清两者本质：qiankun 是运行时应用隔离（子应用独立构建部署、主应用按需加载、JS 沙箱 + 样式隔离），模块联邦是构建时模块共享（跨应用直接 import 远端模块、依赖共享）
- 能说 qiankun 的 JS 沙箱原理（Proxy 劫持 window）与样式隔离方案（shadow DOM / scoped），以及各自的边界与坑
- 能说模块联邦的 shared 依赖机制（单一实例、版本冲突处理）与 remote/host 关系
- 有选型判断：依赖共享需求强、技术栈统一 → 联邦；多团队独立发版、技术栈异构、要应用级隔离 → qiankun
- 知道微前端的通用坑：公共依赖双实例（React 两份导致 hooks 崩）、样式污染、通信与状态同步
- 有落地意识：主应用壳、子应用注册、权限与路由、灰度与回滚、监控怎么统一

**减分项：**
- 把两者混为一谈，说不清运行时隔离与构建时共享的区别
- 只会说"qiankun 是微前端框架"，讲不出沙箱原理与隔离边界
- 不知道公共依赖双实例是最大的坑，或不知道怎么强制 single
- 不考虑各团队技术栈与发版节奏，无脑选一个
- 忽略微前端的运维成本：监控、灰度、性能都要重新设计

**解答：**
先分清两种方案的底层模型。qiankun 是"运行时应用隔离"：每个子应用独立构建、独立部署，主应用运行时通过 import-html-entry 加载子应用资源，并用 JS 沙箱（Proxy 拦截 window 属性的读写，应用切换时还原）和样式隔离（默认 scoped CSS 或 shadow DOM）把子应用隔离在独立环境里，适合"多团队独立发版、技术栈异构、需要应用级隔离"的场景——这正是题述场景。模块联邦（Module Federation）是"构建时模块共享"：host 应用在构建时声明要加载的 remote 模块，运行时从远端拉取，配合 shared 配置让公共依赖（如 React）只加载一份、强制 single 版本，适合"技术栈统一、希望跨应用共享组件与依赖"的场景，比如统一组件库、公共 utils 的复用。选型看三点：一是隔离需求——要应用级沙箱隔离选 qiankun，只要模块级共享选联邦；二是团队发版节奏——各团队独立发版、互不等待选 qiankun，统一发布节奏选联邦更简单；三是技术栈——异构选 qiankun，统一选联邦。落地时最常踩的坑是公共依赖双实例：子应用和主应用各自打包一份 React，页面出现 hooks 报错、事件系统异常，qiankun 下要用 externals 把公共依赖指向主应用版本；联邦下用 shared 加 `singleton: true` 并设置版本范围。样式污染靠 scoped 或约定前缀兜底，通信用主应用提供的全局事件或状态仓库，避免子应用之间直接耦合。还要提前设计统一能力：主应用壳负责登录与权限、子应用注册表管理版本与灰度、错误上报与性能监控在主应用侧统一采集。最后评估成本：微前端带来独立发版的灵活性，也带来加载性能、联调与运维复杂度，规模没到多团队并行瓶颈前，未必值得上。

**延伸考点：** qiankun 的沙箱为什么拦不住子应用通过 document 直接操作 DOM 或挂事件？模块联邦 shared 版本冲突时，构建会怎样表现，如何避免"两个 React"？

### Q18. 线上报错只有压缩代码，sourcemap 怎么既还原堆栈又不泄露源码？

**问题：** 线上 JS 报错，错误监控里全是压缩混淆后的代码，排障靠猜。你要接入错误上报并把堆栈通过 sourcemap 还原成可读的源码位置，同时不能把源码暴露给用户。方案怎么设计？

**减分项：**
- 只做 `window.onerror = alert`，没有完整的采集与还原链路
- 直接把 sourcemap 放线上公开目录，等于把源码开源
- 不知道 "Script error." 是跨域报错的统一占位，拿到手也没法定位
- 还原时不知道要拿"压缩产物对应行"去映射，把原始源码行号当产物行号用
- 错误上报不带版本号，发布关联与排查无从谈起

**解答：**
完整链路是"采集 → 上报 → 还原 → 聚合告警"。采集端：window.onerror 捕获运行时错误、unhandledrejection 捕获 Promise 拒绝、React 用 ErrorBoundary 捕获组件树错误，所有事件统一带上版本号、路由、UA、发生时间，这是后续一切排查的基础。跨域脚本（CDN 上的 JS）默认报错只有 "Script error."，必须在 script 标签加 crossorigin="anonymous" 且 CDN 响应带 CORS 头，才能拿到真实堆栈。上报后到平台端做还原：sourcemap 是压缩产物行列到原始源码行列的映射（VLQ 编码），用 source-map 库把报错信息里的"压缩产物文件名 + 行 + 列"喂进去，就能还原出源码文件、行列与函数名，配合 sourcesContent 还能直接展示源码片段。关键安全姿势是"map 文件不下发"：生产构建用 hidden-source-map（产物里不留 //# sourceMappingURL 注释，用户访问不到 .map 文件），构建产物打包时把 .map 单独提取上传到监控平台或内部对象存储，浏览器侧永远拿不到——否则任何人打开 DevTools 就能看到完整源码。精度与速度取舍：source-map（完整、构建慢）适合生产兜底，cheap-source-map 更快的代价是列信息不准；eval-source-map 只用于开发。还原后的错误按"错误签名"聚合（message + 堆栈指纹去参数化，避免时间戳、ID 之类造成误拆分），按影响用户数/次数分级，并关联发布记录——"这个错误是 v1.2.3 引入的"能大幅缩短排查路径。告警要防噪音：只对新增错误签名或影响面突增的告警，存量噪音分级降权。

**延伸考点：** sourcemap 还原出的行列和真实代码对不上（比如压缩器重排了语句），可能的原因是什么？移动端 H5 上脚本报错经常拿不到完整堆栈，怎么提高捕获率？

### Q19. 发布上线总出事，灰度发布与 A/B 能力怎么设计？

**问题：** 团队发布是"一把梭"全量上线，出过几次线上事故。你要引入灰度发布降低风险，同时产品想用 A/B 实验验证功能效果。灰度与 A/B 在实现上有什么异同，方案怎么设计？

**期望加分项：**
- 讲清灰度与 A/B 的关系与区别：灰度是降低风险的发布手段，A/B 是验证假设的实验方法，两者可共用流量分层但目的不同
- 前端灰度的实现手段：构建层（多版本产物并存）、部署层（网关/入口按比例分流）、代码层（feature flag 开关）
- 关键设计：按用户维度分流保证同一用户实验期间稳定在一组（避免体验抖动与数据污染）、分桶规则（user id 哈希）、流量分层避免多个实验互相污染
- 回滚能力：灰度比例可调、发现异常秒级回退（切回旧版本或关 feature flag），而不是重新发版
- 数据评估：A/B 要预先定主指标与显著性检验、样本量计算，避免"看了两天涨了 0.5% 就上线"
- 与监控联动：灰度期间 RUM/错误率按分组对比，异常自动暂停放量

**减分项：**
- 分不清灰度与 A/B，混为一谈
- 分流用随机数而不是用户维度，用户刷新就换组，数据全废
- 灰度就是"后端按比例放量"，不知道前端也要做版本并存与 feature flag
- 没有回滚预案，出问题只能全量回滚或紧急发版
- 数据评估拍脑袋，不看显著性、不算样本量

**解答：**
先厘清概念：灰度发布是"把新版本逐步放量给更多用户"的风险控制手段，核心是"随时能退"；A/B 实验是"对比两个方案哪个指标更好"的验证方法，核心是"结论可信"。两者可以共用一套流量系统，但目的不同。前端灰度的落地分三层：第一层部署与产物——新版旧版产物同时在线（内容寻址天然支持），入口按比例分流（如网关按 user_id 尾号或权重把 5% 流量切到新版本 HTML/接口）；第二层代码开关——feature flag 配置文件或远端配置中心控制功能开闭，同一份产物里新老逻辑共存，运营可随时调比例或直接关闭；第三层与发布流程结合——小流量观察（如 1% → 5% → 20% → 100%），每档观察窗口内对比核心指标与错误率，异常即暂停或回退。A/B 的关键在实验设计：分流必须按用户维度（user_id 哈希取模），保证同一用户整个实验期间固定在同一组，否则用户来回横跳、数据无法归因；分桶时不同实验要用不同的盐（salt）打散，避免多个实验组用户重合互相污染；实验前定好主指标（如转化率、LCP）与预期提升幅度，估算样本量与时长（避免样本不足时"看着涨了其实不显著"），结束后做显著性检验再决定上线或回滚。灰度与 A/B 要联动监控：放量期间按分组分别统计错误率、Web Vitals、接口失败率，任一指标异常自动暂停放量并告警。最后回滚设计是底线：任何时刻"切回旧版本"或"关闭 feature flag"都应是分钟级动作，且回滚本身也要有验证——确认回滚后指标恢复，而不是"回滚了但没生效"。

**延伸考点：** 灰度期间新版接口数据结构变了，怎么保证老页面不崩（前后端兼容策略）？A/B 实验里用户换设备或清 cookie 后分组变了吗，对结论有什么影响？

### Q20. 依赖装不上、CI 和本地不一致、包越来越大：npm/yarn/pnpm 与 Monorepo 怎么选？

**问题：** 团队项目依赖管理混乱：不同人装出的依赖树不一致导致"本地能跑 CI 挂"、node_modules 巨大、多个相关项目要共享代码。请对比 npm/yarn/pnpm 的核心差异，说明 lockfile 的作用，并给出是否上 Monorepo 的建议。

**期望加分项：**
- 讲清 lockfile 的意义：锁定整棵依赖树（不只是顶层版本）保证可复现安装，lockfile 必须提交进仓库，CI 用 --frozen-lockfile
- 说清三者差异的本质：npm/yarn v1 的扁平化 node_modules（hoisting）与幽灵依赖问题，pnpm 的符号链接 + 内容寻址存储，以及 yarn v2/v3 的 PnP 方案
- 知道幽灵依赖的危害：package.json 没声明的包能 import，一旦传递依赖升级就崩
- 能说 pnpm 的原理：全局 store + 硬链接 + 符号链接，省磁盘、安装快、严格依赖隔离
- 有 Monorepo 的判断：多项目共享内部库、统一构建与发布、依赖提升 → pnpm workspace；单项目则没必要
- 知道 workspace 的坑：版本提升与发布（changesets）、内部包版本引用、依赖循环

**减分项：**
- 不知道 lockfile 为什么要提交、CI 装依赖为什么必须锁版本
- 分不清 hoisting 和幽灵依赖，说不清 pnpm 和 npm 的 node_modules 结构差异
- 只会说"pnpm 快"，讲不出原理与代价
- 一上来就推 Monorepo，讲不出收益与成本，或不知道 workspace 里依赖怎么解析
- 忽略 npm audit / 依赖漏洞扫描这类安全治理

**解答：**
先讲透 lockfile：package.json 只声明顶层依赖的版本范围，真正决定装出来什么的是 lockfile——它锁定整棵依赖树（每个包的精确版本与依赖关系）。所以 lockfile 必须提交进仓库，CI 上安装要用 `--frozen-lockfile`（npm ci / pnpm install --frozen-lockfile），否则"本地好的 CI 挂"会一直发生。三者的本质区别在 node_modules 的组织方式：npm 和 yarn v1 做"扁平化 hoisting"——把依赖尽可能提到顶层 node_modules，优点是简单，代价是会出现幽灵依赖（代码能 import 一个 package.json 里没声明的包，因为它在提升后的某层"恰好存在"），一旦某个传递依赖升级或移除就崩；pnpm 用"符号链接 + 全局内容寻址 store"：node_modules 里只有直接依赖的符号链接，真实文件在全局 store 里按内容寻址存储，同一版本全局只存一份，跨项目共享，省磁盘且安装快，更重要的是依赖隔离——包只能访问自己声明的依赖，幽灵依赖从根上消失，代价是少数不兼容"严格 node_modules"的工具链需要适配。yarn v2/v3 的 PnP 更进一步（连 node_modules 都没有，靠 .pnp 文件解析），但生态兼容问题更多。选择建议：单项目直接 pnpm（隔离 + 快 + 磁盘省）；多项目共享内部库、需要统一发布与联调时上 Monorepo，且几乎必然配 pnpm workspace——用 workspace 协议引用内部包、changesets 管理版本发布、turbo/nx 做增量构建缓存。Monorepo 的收益是依赖与构建统一、原子提交跨包改动；成本是包边界治理、发布编排、CI 策略复杂化，规模小的团队要掂量。最后补一层安全治理：依赖漏洞扫描（npm audit/pnpm audit、Snyk、Dependabot）应接进 CI，高危漏洞阻止合并。

**延伸考点：** pnpm 为什么偶尔会遇到符号链接相关的奇怪问题（比如某些工具扫描 node_modules 递归死循环）？Monorepo 里内部包改了但没发版，其他项目引用的是旧版本，怎么用 changesets 管住？
