# 后端 · Java（面试题库）

本文件聚焦 Java 后端工程师的真实工程能力考察，覆盖 JVM 内存与 GC、并发编程、Spring 生态、数据库与缓存、微服务与分布式等关键领域。题目均为线上或项目中可复现的场景化问题，重点考察候选人的排查思路、调优方法、取舍判断与系统设计能力，而非概念背诵。难度自 Q1 至 Q20 循序渐进，从实践基础逐步过渡到架构级开放性思考题。

### Q1. 新服务上线，JVM 堆内存和 GC 参数你是怎么定的？

**问题：** 你们新服务首次上线时，JVM 的堆大小、新生代比例、GC 收集器这些参数是怎么确定的？上线后又靠什么验证？

**期望加分项：**
- 能说明参数不是拍脑袋定的，而是基于对业务对象大小、QPS、单请求分配量的预估，最好有压测数据支撑
- 能讲清 -Xms/-Xmx 相等、堆与容器内存（k8s limit）的关系、-XX:MaxRAMPercentage 等容器化适配
- 能说出 G1 的 MaxGCPauseMillis 与吞吐量之间的取舍，以及小堆（4G 以下）场景 G1 优势不明显的认知
- 上线后通过 GC 日志、堆水位、GC 频率监控做闭环调整
- 主动预留堆外内存（线程栈、Metaspace、DirectBuffer、JIT 代码缓存）空间

**减分项：**
- 只会背参数名，说不出每项参数为什么这么设
- 忽略容器环境（Cgroup）导致 JVM 不识别内存上限的问题
- 上线后从不回看 GC 指标，没有验证闭环
- 认为堆设得越大越好，答不出大堆带来的 Full GC 停顿风险

**解答：**
先明确原则：JVM 参数服务于业务特征，而不是反过来。第一步估算对象生命周期：如果服务以短请求为主、对象大多快速死亡，新生代要留足；如果以长生命周期缓存/连接为主，老年代要宽松。首次上线建议先压测，观察 GC 日志和对象分配速率，而不是凭经验猜。基线配置通常为：-Xms 与 -Xmx 设为相同值（避免扩容抖动），堆大小取容器内存的 50%-70%（如 4C8G 容器给 4-6G 堆），剩余留给堆外（线程栈、DirectBuffer、Metaspace、JIT 代码缓存）。用 G1 时通过 -XX:MaxGCPauseMillis 控制停顿目标（常见 100-200ms），新生代不手动设比例，交给 G1 自适应；用 Parallel GC 时新生代一般占堆 1/3。容器化务必保证 JDK 支持 -XX:+UseContainerSupport（JDK8u191+ 默认开启）并用 -XX:MaxRAMPercentage=75 这类比例参数，避免 JVM 读到宿主机内存。线上要开 GC 日志（JDK9+ 用 -Xlog:gc*，老版本 -verbose:gc -XX:+PrintGCDetails）滚动输出，配合监控（堆使用率曲线、GC 频率、停顿时间）做闭环调整。实践中的坑：堆设得过大反而加剧 Full GC 停顿；G1 在 4G 以下小堆上优势不明显；只盯堆使用率不看 GC 频率，会漏掉对象分配过快的问题。

**延伸考点：** 压测时你们关注哪些 GC 指标，判断依据是什么？堆外内存泄漏怎么排查？

### Q2. 你们线程池的核心线程数、最大线程数、队列是怎么定的？

**问题：** 你们线程池的核心线程数、最大线程数、队列长度具体是多少？依据是什么？如果任务高峰期队列被打满会怎样？

**期望加分项：**
- 能区分 IO 密集与 CPU 密集，并给出公式（CPU 密集 = CPU 核数±1，IO 密集 ≈ CPU 核数 ×（1 + 等待时间/计算时间）），且有压测校准
- 结合真实业务数据：QPS、单任务耗时、可接受的排队延迟，反推出线程数与队列大小
- 能说明拒绝策略的选择与降级方案（本地落盘/MQ 兜底、CallerRunsPolicy）
- 提到动态调参与监控告警（队列积压、活跃线程、拒绝次数）
- 主动考虑线程池隔离：业务池与中间件池分离，避免相互拖累

**减分项：**
- 只会背公式，说不出自己项目里的实际数字和推导过程
- 对"核心线程数 → 队列 → 最大线程数 → 拒绝"的触发顺序说不清
- 不知道 RejectedExecutionHandler 有哪几种，也不做降级
- 没有监控，不知道线程池实际利用率与队列积压情况

**解答：**
核心思路是"先测量，再设定"，线程数不是纯算出来的，而是从业务指标反推。先明确参数行为：提交任务时核心线程数内直接执行；超过则进队列；队列满才扩容到最大线程数；再满触发拒绝策略。基于这个模型：CPU 密集（加解密、压缩）线程数取 CPU 核数±1；IO 密集（大量 RPC/DB 调用）用公式 核心线程数 = CPU 核数 ×（1 + W/C），W 是等待时间、C 是计算时间，实际用压测校准。队列与最大线程数是"削峰缓冲"的取舍：队列越大越平滑但延迟越高，越小越快触发扩容与拒绝。一个可落地的推导：目标 TPS=2000、单任务平均耗时 50ms，需要的线程数 ≈ TPS × 单任务耗时 = 2000 × 0.05 = 100；排队延迟 ≈ 队列长度 / 每秒消费能力，据此定队列大小。实践中：所有线程池要有名字（自定义 ThreadFactory）、拒绝策略不能静默丢弃（默认 AbortException 会让上游抖动），通常配 CallerRunsPolicy 或降级到 MQ/本地落盘，队列必须设容量上限（无界队列会吃光内存且永不扩容）。最后加监控：队列积压数、活跃线程数、拒绝次数、任务耗时并配置告警，必要时支持运行时动态调整核心/最大线程数。

**延伸考点：** 线程池提交任务时，队列满但线程数未到最大线程数会发生什么？一个线程池阻塞怎么避免连累整个应用？

### Q3. 库存扣减用 synchronized 还是 CAS？你们怎么保证不超卖？

**问题：** 秒杀场景下扣减库存，有人用 synchronized 锁方法，有人用 update ... where stock > 0，有人用 Redis Lua。你们线上怎么做的？各自有什么问题？

**期望加分项：**
- 能指出 synchronized 只对单机 JVM 生效，多实例部署必然超卖
- 能理解数据库 update stock = stock - 1 where stock > 0 的原子性与受影响行数判断
- 能说出 Redis Lua 原子扣减的边界：扣减前置、下单失败后的回补
- 能讨论并发粒度与热点问题：分段库存、热点 key
- 联系实际：库存预扣、超卖回补、订单取消释放库存的一致性

**减分项：**
- 只会背"乐观锁/悲观锁"概念，不知道 synchronized 跨 JVM 失效
- 说不清 CAS 的 ABA 与自旋开销在扣库存场景的适用性
- 忽略库存扣减与订单创建的分布式一致性
- 不知道 Lua 脚本原子执行的边界和超时处理

**解答：**
先分清场景：扣库存是"单写多读、数值原子减"，核心诉求是原子性 + 不超卖。synchronized 只锁住本 JVM，线上多实例部署必然超卖，第一步就排除它。数据库方案是底线保障：`UPDATE t_stock SET stock = stock - 1 WHERE sku_id = ? AND stock > 0`，由数据库行锁保证原子性，影响行数 = 0 即库存不足，这是"最终一致"的正确性兜底，缺点是行锁在高并发下成瓶颈。Redis 方案把扣减前移到缓存：用 Lua 脚本原子执行 `if tonumber(redis.call('GET', key)) > 0 then return redis.call('DECR', key) else return -1 end`，可抗更高 QPS；但缓存与数据库之间要做"回补"对账（Redis 扣减成功但下单失败时回补），否则会少卖。工程上的成熟做法是分层：Redis Lua 做前置预扣，数据库 update 做最终校验，异步对账兜底；热点 SKU 可做分段库存（拆多个 key）摊薄热点。实践中的坑：直接把 DECR 当扣减、不判断正负会超卖；预扣后不释放造成"库存假死"；对账任务延迟导致不一致窗口拉长。

**延伸考点：** Redis 扣减成功但数据库事务回滚了，怎么补偿？分段库存如何避免某个分片先耗尽导致过早限流？

### Q4. 你们遇到过 @Transactional 失效吗？怎么排查？

**问题：** 线上有个方法加了 @Transactional，但异常后数据没回滚。你们是怎么排查和修复的？

**期望加分项：**
- 能列举典型失效场景：同类自调用、private 方法、异常被 catch、受检异常、类未被 Spring 管理
- 能讲清 Spring 事务基于 AOP 动态代理，自调用 this.method() 不经过代理对象
- 能说清 rollbackFor 默认只回滚 RuntimeException 和 Error，受检异常默认不回滚
- 有实际排查手段：确认代理对象、观察事务是否开启、分析异常抛出位置
- 能联系"大事务"实践：事务里做 RPC、循环查库、发 MQ 的危害与拆解

**减分项：**
- 只知道"加注解就行"，说不出代理机制
- 答不出受检异常默认不回滚
- 不知道事务传播行为（REQUIRED/REQUIRES_NEW）对边界控制的意义
- 没有把"事务范围过大"作为实践问题考虑

**解答：**
先明确 Spring 声明式事务的本质：@Transactional 靠 AOP 动态代理，调用方拿到的是代理对象，方法执行前开启事务、正常返回提交、异常回滚。因此所有"代理失效"都会让事务失效。排查顺序：先确认方法所在类是否被 Spring 管理（是不是 @Service/@Component）；再看是不是同类内部调用——this.method() 不会经过代理，必须注入自身代理或拆到别的 Bean；再看方法修饰符，private 方法无法被代理增强；再看异常处理——异常被 catch 掉，事务自然感知不到；最后看异常类型，受检异常（如 Exception）默认不回滚，需要 rollbackFor 显式声明。工程上更常见的坑是"大事务"：一个事务里做远程调用、循环查库、发 MQ，导致长事务持锁、连接占用、主从延迟。修复方向：缩小事务范围（事务只包住必要的写操作）、用 REQUIRES_NEW 或编程式事务（TransactionTemplate）控制边界、查询走从库。排查手段：看日志确认事务开启/提交记录，或临时打印 AopUtils.isAopProxy(this) 验证是否代理对象；更直接的是看数据库连接是否被事务长时间占用。

**延伸考点：** 事务方法里发 MQ，事务回滚了消息却已发出怎么办？REQUIRES_NEW 在什么场景下用？

### Q5. 两个事务并发更新同一行数据，你们怎么处理？

**问题：** 两个用户同时操作同一笔订单余额，你们遇到过更新丢失吗？事务隔离级别和锁是怎么配合的？

**期望加分项：**
- 能说清 MySQL 默认隔离级别 RR（可重复读）与脏读/不可重复读/幻读的定义边界
- 能区分"更新丢失"的真正解法：行锁原子 update 或乐观锁版本号
- 能讲 update 的 where 条件是否命中索引决定锁行还是锁表
- 知道 RR 下当前读会加 Next-Key Lock（记录锁+间隙锁），也是死锁常见来源
- 谈取舍：隔离级别升级的代价、乐观锁重试的代价、事务内不要做 RPC

**减分项：**
- 三个隔离级别问题概念混淆，或认为 RR 完全消除一切并发问题
- 不知道 update 语句本身加排他锁，select 才可能读到旧快照
- 忽略"先 select 再 update"中间被别的连接修改的窗口
- 只会说"加锁"，说不出锁的类型与索引的关系

**解答：**
先定位问题类型：两个事务并发写同一行，最直接的是"更新丢失"。MySQL 的 RR 隔离级别下，update 走"当前读"并加排他锁，两个 update 并发时后一个会阻塞等待前一个提交——前提是 where 条件命中索引（否则退化为锁表，正确但性能差）。真正的坑在"先 select（快照读）后 update"模式：比如先查余额再在 Java 里算新余额再 update，两个请求都读到旧余额，各自加 10，结果只加了 10 而不是 20。解法两种：一是把读改写包进事务并让 select 走当前读（SELECT ... FOR UPDATE），或直接 `UPDATE ... SET balance = balance - 10 WHERE id = ? AND balance >= 10` 让数据库完成原子计算；二是乐观锁，表加 version 字段，`UPDATE ... SET amount = ?, version = version + 1 WHERE id = ? AND version = ?`，影响行数为 0 就重试或报错。关于幻读：RR 下普通 select 是快照读，不受并发插入影响，但 SELECT FOR UPDATE/update 会加 Next-Key Lock 阻止幻影插入，这也是 RR 下死锁常见来源。工程取舍：读多写少的对账类场景用乐观锁+重试；写冲突高、强一致场景用悲观锁；严禁在事务里做 RPC 调用拉长持锁时间。

**延伸考点：** RR 和 RC 下 update 加锁有什么差异？为什么 RR 下更容易死锁？你们生产上用哪个隔离级别，为什么？

### Q6. MyBatis 查出 1 万条数据再逐条 update，你们怎么优化？

**问题：** 有个批量任务要从数据库查出几万条数据逐条处理后更新，跑得很慢。你们怎么改？

**期望加分项：**
- 能识别循环单条 update 的多次网络往返与多次事务提交开销
- 能给出批量方案：ExecutorType.BATCH、foreach 批量 update（注意 SQL 包大小限制）、按批 500-1000 条拆分
- 能讲 JDBC URL 上 rewriteBatchedStatements=true 的作用
- 能考虑分批分页处理避免大事务与内存压力，深分页用 id > lastId 游标
- 有实际性能数据对比（如从 10 分钟降到 30 秒）

**减分项：**
- 直接回答"改成 foreach 就行"，忽略 SQL 长度限制与索引
- 不知道 MyBatis ExecutorType.BATCH 与普通 executor 的区别
- 一次性加载全量数据到内存再处理
- 不做分批，也不考虑事务边界与重跑幂等

**解答：**
先诊断慢在哪：通常不是数据库执行慢，而是"网络往返 × 条数"。逐条 update 一万条 = 一万次 TCP 往返 + 一万次事务提交，耗时主要在客户端与 DB 之间。优化分三层：第一层减少往返，MyBatis 用 ExecutorType.BATCH（或 Spring 的 SqlSessionTemplate batch）把多条 update 攒批发送，配合 JDBC 的 rewriteBatchedStatements=true 才能真正合并执行；或者用 foreach 构造批量 update，但注意一条 SQL 的包大小（max_allowed_packet）限制，拆成每批 500-1000 条。第二层减少事务开销：不要每条一个事务，用一个事务包住一个批次（如 1000 条），失败时整批回滚或记录失败清单继续下一批。第三层减少扫描与锁定：处理时带上过滤条件（如状态字段）建立索引，避免全表扫描；分页用 `WHERE id > lastId ORDER BY id LIMIT 1000` 的游标方式代替 limit offset，避免深分页。实践中的坑：foreach 批量 update 的 SQL 过大时 MySQL 会因 max_allowed_packet 直接报错；BATCH executor 在 MyBatis-Plus 里要注意 flush 时机，未 flush 前查询结果可能为空；批量任务务必加失败重试与幂等设计（update 的 where 条件带状态字段，如 status = 0），保证重跑安全。

**延伸考点：** 批量 insert 用什么方式最快（多值 insert vs 批量 executor）？大数据量导出时你们怎么避免 OOM？

### Q7. 服务内存一直涨但没 OOM，你们怎么定位是不是内存泄漏？

**问题：** 一个服务运行几天后内存占用持续上涨、GC 频率变高，但还没 OOM。你们如何定位？

**期望加分项：**
- 排查思路清晰：先确认是堆内还是堆外（Metaspace、DirectBuffer、线程栈）
- 会用 jmap -histo / jmap -dump + MAT 分析堆转储，定位大对象与持有链
- 能识别典型泄漏源：静态集合、ThreadLocal 未清理（线程池复用）、缓存无淘汰、连接未释放
- 能区分"泄漏"（GC 后水位逐次抬高）与"正常波动"（GC 后回落）
- 有线上实践：先看 GC 日志与水位曲线，再抓 dump，最后修复验证

**减分项：**
- 一上来就 dump，抓不到问题时刻的快照
- 只会看堆使用率，分不清泄漏与正常水位上涨
- 不关注 GC 后堆是否回落这一关键信号
- 不知道堆外内存（NMT）排查手段

**解答：**
先判断"是不是真泄漏"：如果 GC 后堆使用率能回落到稳定水位，那是正常波动；如果 GC 后水位一次比一次高，才是泄漏。所以第一步看 GC 日志（或监控）里每次 Full GC 后的堆占用趋势，这是最便宜且最快的判断。第二步定位对象：用 jmap -dump:format=b 抓堆转储，先用 jmap -histo:live 看哪些类实例数异常多（如 HashMap$Node、byte[]、某个业务对象），再用 MAT 的 Leak Suspects 或支配树找持有链，重点检查：static 容器不断 put 不清理、ThreadLocal 在业务线程池里 set 后不 remove、ConcurrentHashMap 做缓存无淘汰、连接池/线程池的队列积压、Metaspace 类加载器泄漏（频繁热部署）。第三步处理：缓存类泄漏加容量上限+LRU 淘汰或过期清理；ThreadLocal 在 finally 里 remove；静态集合确认生命周期。堆外内存排查是进阶：Metaspace 看 GC 日志区域使用，DirectBuffer 用 NMT（-XX:NativeMemoryTracking=summary）看内存分类。实践中的坑：dump 时机不对（泄漏对象已被 GC），要连续抓两个时间点对比；大堆 dump 文件几个 G，先看 histo 再看 MAT；修复后要跑足够长时间验证水位不再上涨。

**延伸考点：** ThreadLocal 为什么在使用了线程池的环境里更容易泄漏？NMT 怎么看堆外内存？

### Q8. 线上突然 OOM，服务重启后恢复，你怎么查？

**问题：** 线上服务凌晨突然 OOM 宕机，重启后恢复。你如何处理？先做什么后做什么？

**期望加分项：**
- 先保住服务：快速重启/摘流量，同时想尽办法保留现场
- 有预案：启动参数预先配置 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath，否则事后无法定位
- 能结合 OOM 类型分析：Java heap space / Metaspace / Direct buffer / unable to create new native thread
- 分析步骤：看 GC 日志、堆转储、监控（QPS、响应时间、调用链）、关联发布变更记录
- 有复盘意识：dump 开关、OOM 告警、内存监控常态化

**减分项：**
- 只说"重启就好了"，没有保留现场和定位手段
- 不知道 HeapDumpOnOutOfMemoryError 这个关键开关
- OOM 类型分不清，拿"堆溢出"的方案去处理"线程数耗尽"
- 不结合发布变更（新版本/新流量/促销活动）做关联分析

**解答：**
处理 OOM 的核心是"先恢复、再保留现场、最后定位根因"，顺序不能反。第一步止血：服务已宕则快速重启或从注册中心摘除，把流量切到健康节点，业务恢复优先。第二步保留现场：如果启动参数里预先配了 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/logs，JVM 会在 OOM 时自动 dump，这是能否定位的关键，没配就只能靠事后监控数据。第三步分析：打开堆转储用 MAT 看 Leak Suspects 与支配树，判断是大对象（一次性加载大量数据）还是泄漏对象堆积；同时看 GC 日志里 OOM 前的 Full GC 频率、堆水位；再看监控大盘：OOM 前 QPS 是否有尖峰、是否有慢查询/大结果集、某类接口调用量是否暴涨；最后查发布记录与变更（当天是否上新版本、新上线了批量任务/报表接口）。不同 OOM 类型手段不同："Java heap space" 查堆转储；"Metaspace" 查热部署/动态生成类（CGLIB、反射、字符串 intern）；"Direct buffer memory" 查 NIO/Netty 未释放的 ByteBuffer；"unable to create new native thread" 查线程数上限（ulimit）与线程泄漏（线程池无限创建、死循环 new Thread）。复盘层面：把 dump 开关、内存使用率超 80% 即告警（而非等宕机）、内存曲线监控做成常态化，并压测模拟峰值验证。

**延伸考点：** OOM 前服务通常会先表现出什么征兆，怎么提前拦截？如果 dump 文件太大分析不动怎么办？

### Q9. 频繁 Full GC 但堆没满，怎么回事？

**问题：** 监控显示服务频繁 Full GC，每次停顿几百毫秒，但堆内存远没到上限。你怎么排查？

**期望加分项：**
- 能想到"堆没满却 Full GC"的多种原因：Metaspace 扩容、G1 大对象（humongous）直接进老年代、显式 System.gc()、晋升过快
- 会看 GC 日志确认 Full GC 触发原因（cause 字段）
- 能检查 Metaspace 使用量与扩容情况
- 会用 jstat -gcutil 观察各代使用率与 GC 次数
- 能区分 G1 的 Mixed GC / Full GC / 并发周期

**减分项：**
- 只说"内存泄漏导致"，未考虑 GC 触发机制
- 不知道 G1 里超过 Region 大小一半的对象直接进老年代（humongous）
- 不关注 GC 日志里的 cause 字段
- 忽略代码里的 System.gc()、RMI 触发 Full GC 的可能

**解答：**
堆没满却 Full GC，说明触发条件不是"老年代满"，要按 Full GC 的 cause 逐一排查，第一动作是打开 GC 日志看原因（JDK9+ 用 -Xlog:gc*，老版本 -XX:+PrintGCDetails），日志里会带 cause。常见原因：一是 Metaspace 不足——动态生成类（反射、CGLIB 代理、脚本引擎）或大量字符串 intern 把 Metaspace 顶满，每次扩容都触发 Full GC，看日志中 Metaspace 行与 -XX:MaxMetaspaceSize 设置；二是大对象——G1 里超过 Region 大小（默认 1M-32M）一半的对象叫 humongous，直接进老年代且 GC 处理开销大，典型是超大的 byte[]/String 批量缓存，用 jmap -histo 或 MAT 验证；三是代码里显式调 System.gc()（部分框架/监控组件会调，RMI 也会周期性触发），可用 -XX:+DisableExplicitGC 验证是否缓解；四是晋升过快——新生代太小或 Survivor 放不下，对象过早晋升老年代并造成碎片化，加 -XX:+PrintTenuringDistribution 看年龄分布。排查命令：jstat -gcutil <pid> 1000 看各代使用率与 Full GC 次数，配合 GC 日志确认 cause。实践中的坑：只看堆总量忽略 Metaspace；G1 下没测大对象分布就用默认 Region 大小；修好一个 cause 后要观察是否还有别的触发源。

**延伸考点：** G1 的 Mixed GC 和 Full GC 触发条件分别是什么？为什么要避免把大批量数据一次性读入内存？

### Q10. AQS 加锁和 synchronized 你们怎么选？什么场景用 ReentrantLock？

**问题：** 项目里既有 synchronized 也有 ReentrantLock，你们各自用在什么场景？为什么？

**期望加分项：**
- 能说出 synchronized 在 JDK6+ 有偏向锁/轻量级锁/锁膨胀优化，常规互斥够用且代码简洁
- ReentrantLock 的优势：可中断（lockInterruptibly）、超时（tryLock）、公平锁、多个 Condition 条件队列
- 能讲 Condition 的实际用途：生产者消费者、有界队列、按条件唤醒
- 能说 AQS 的核心：volatile state + CLH 变种队列 + 模板方法（tryAcquire/tryRelease），共享/独占两种模式
- 有工程选择依据：并发量、等待策略（要不要限时等待）、可读性与维护成本

**减分项：**
- 只会背"AQS 用 CAS + 队列"，说不清实际应用
- 不知道 Condition 与 wait/notify 的对应关系和优势
- 说不出 synchronized 锁膨胀的过程
- 无法举出自己项目中使用场景（如缓存重建锁、批量任务并发控制）

**解答：**
选择标准是"场景需要什么能力"：如果只是保护一段临界区，synchronized 就够——JDK6 之后有偏向锁、轻量级锁到重量级锁的膨胀路径，无竞争时开销极小，代码也简洁，不用手动释放。ReentrantLock 的价值在 synchronized 给不了的三个能力：一是限时等待与可中断，如缓存重建 `tryLock(200, TimeUnit.MILLISECONDS)`，抢不到就返回旧值或直接查库，避免锁竞争拖垮接口；二是公平性，按需用 fair 参数（默认非公平，吞吐更高）；三是 Condition 条件队列，相比 wait/notify 可以按条件分组唤醒，比如实现有界阻塞队列或"库存充足才扣减"的逻辑，await/signal 比 wait/notify 更精确、无 lost wakeup 隐患。AQS 是这些锁的基石：volatile int state 加 CLH 变种等待队列，acquire 流程是 CAS 更新 state 成功即拿到锁，失败则入队阻塞，唤醒时按 FIFO 传递；ReentrantLock 只是重写了 tryAcquire/tryRelease（state 累加支持重入）。工程实践：本地限流或批量任务并发控制可以用 Semaphore（AQS 共享模式）；缓存防击穿用 tryLock 而不是把整个方法 synchronized；读多写少可评估 ReentrantReadWriteLock 或 StampedLock，但要警惕写饥饿。实践中的坑：ReentrantLock 忘在 finally 里 unlock；tryLock 拿到锁后 catch 了 InterruptedException 却没恢复中断标志；滥用公平锁导致吞吐下降。

**延伸考点：** Semaphore 和 CountDownLatch 分别解决什么问题，内部都是 AQS 的什么模式？可重入是怎么实现的？

### Q11. 一个接口从 2 秒优化到 200ms，你们是怎么做的？

**问题：** 线上有个接口 P99 延迟 2 秒，你们是怎么定位瓶颈并优化的？讲讲完整过程。

**期望加分项：**
- 有系统化定位思路：先确认瓶颈在应用还是下游（链路追踪、耗时拆解、火焰图）
- 会用工具：arthas trace/watch、async-profiler、APM 链路、慢 SQL 日志
- 能区分耗时组成：串行 RPC 转并行（CompletableFuture/虚拟线程）、DB 慢查询加索引、大对象序列化、GC 停顿
- 有前后性能对比数据，验证优化有效性
- 关注 P99 而非均值，理解长尾效应（GC、锁竞争、网络抖动）

**减分项：**
- 直接猜"加缓存"，没有先定位
- 只优化均值，不解释 P99 高的长尾原因
- 不会用 arthas 等工具，纸上谈兵
- 优化后不回归验证，或把问题推给下游不做根因分析

**解答：**
正确姿势是"先测量再优化"，禁止凭感觉下手。第一步链路定位：用 APM（如 SkyWalking/Pinpoint）或 arthas trace 看接口整体耗时分布，把 2 秒拆到具体环节——瓶颈通常集中在几类：多次串行 RPC、慢 SQL、大量序列化/大对象、GC 停顿或锁竞争。第二步逐项处理：如果发现 5 次串行 RPC 各 300ms，用 CompletableFuture 并行化（或 JDK21 虚拟线程）把总耗时压到单次最长；如果 SQL 慢，用 EXPLAIN 看执行计划，加索引或改写（避免深分页、隐式类型转换、函数包列导致索引失效）；如果对象大，检查是否整表查回再内存过滤（改分页/只查必要列），以及 JSON 序列化是否字段过多；如果 GC 停顿明显，回到 Q9 的排查思路。第三步验证与观测长尾：P99 高通常不是平均慢，而是少数请求撞上 GC、锁、网络重传，优化后要看 P99/P999 曲线而不是只看平均值。常用工具：arthas trace 接口方法耗时、async-profiler 出火焰图找 CPU 热点、慢查询日志、链路追踪看下游耗时。实践中的坑：只优化了热点接口的 80% 路径但 20% 异常分支拖垮 P99；缓存优化引入了缓存穿透/一致性新问题；并行化后线程数暴涨压垮下游——并行度要有上限（信号量/固定线程池）。

**延伸考点：** P99 从 2s 降到 200ms 后，P999 可能仍然很高，怎么继续挖长尾？并行调用多个下游时怎么控制线程资源上限？

### Q12. 缓存雪崩/穿透/击穿你们怎么防护？

**问题：** 某大促活动开始后数据库瞬间被打挂，查询全走了数据库没有走缓存。你们当时怎么处理的？平时有哪些预防措施？

**期望加分项：**
- 能清晰区分穿透（查不存在的数据）、击穿（单个热点 key 过期瞬间）、雪崩（大量 key 同时过期/Redis 宕机）
- 有对应措施：穿透用布隆过滤器或缓存空值；击穿用互斥锁重建或逻辑过期；雪崩用过期时间随机抖动、多级缓存、Redis 高可用
- 能讲缓存一致性：先更新 DB 还是先删缓存、延迟双删、binlog 订阅等方案与取舍
- 有降级预案：本地缓存兜底、限流、数据库连接池保护
- 结合真实案例讲取舍（比如宁可短暂不一致也要保可用）

**减分项：**
- 三种问题概念混淆，措施张冠李戴
- 只知道"加缓存"没有降级方案
- 答不出缓存与数据库一致性问题（读到旧数据怎么办）
- 不了解布隆过滤器的误判率与不可删除特性

**解答：**
先区分三个问题：穿透是"查了根本不存在的数据"，每次都会打到 DB，防线是布隆过滤器（拦截不存在 key）或缓存空值（TTL 短一点防堆积）；击穿是"单个热点 key 在过期瞬间有大量并发去重建"，防线是互斥锁——重建时加锁（如 Redis setnx 或分布式锁），只让一个线程查库回填，其余线程等锁后直接读缓存，或用"逻辑过期"（value 里带过期时间，异步重建）；雪崩是"大量 key 同一时间过期"或 Redis 集群整体不可用，前者给 TTL 加随机抖动（如 300s ± 60s），后者靠多级缓存（本地 Caffeine + Redis）与降级预案。一致性问题必须一并回答：常见策略是"先更新数据库，再删缓存"，删除失败会短暂不一致，可加延迟双删（删、等 100ms 再删一次）或订阅 binlog 异步删除；读多写少场景也可用"先删缓存再更新 DB"，接受短暂 miss。真实案例中的坑：大促前一次性批量加载缓存导致同时过期（解决：分片加载+抖动 TTL）；热点 key 用单机 synchronized 做互斥锁导致多实例各自重建（要用分布式锁）；布隆过滤器重启后数据丢失（需持久化或重建）；Redis 宕机时没有本地缓存兜底，DB 被击穿——预案要提前演练。

**延伸考点：** 缓存和数据库最终一致，你们接受多长时间的窗口？热点 key 的互斥锁你们用什么实现，单机锁在多实例下有什么问题？

### Q13. 一条慢 SQL 把数据库 CPU 打满了，你们怎么处理？

**问题：** 监控显示某条 SQL 每次执行 3 秒，调用量一上来数据库 CPU 就 100%，你怎么排查和优化？

**期望加分项：**
- 排查步骤：慢查询日志定位 SQL → EXPLAIN 看执行计划 → 分析 type/rows/possible_keys → 确认是否索引失效
- 能识别常见索引失效：隐式类型转换、函数包裹列、like '%xx'、联合索引最左前缀、order by 未用索引
- 优化手段：加/改索引、SQL 改写（子查询改 join、深分页改游标）、必要时反范式化或加汇总表
- 有容量评估与治理意识：SQL 治理规范、慢 SQL 告警、索引评审
- 分清是 SQL 问题还是数据量问题，给出量化依据（rows 扫描数 vs 返回行数）

**减分项：**
- 只会说"加索引"，说不清为什么这条 SQL 没走索引
- 不看执行计划，凭经验猜
- 不区分"扫描行数大"与"返回行数大"两种慢的本质
- 优化后不做压测验证，也不关心是否引入新问题

**解答：**
第一步用慢日志抓到语句：MySQL 开启 slow_query_log 并设 long_query_time=1，配合 pt-query-digest 或自研工具聚合 TOP N。第二步 EXPLAIN 看执行计划，重点看 type（ALL 全表扫描是最大嫌疑）、key（实际用的索引）、rows（预估扫描行数）、Extra（Using filesort/Using temporary 都要警惕）。常见根因：隐式类型转换（字段是 varchar 但传数字，或反之）导致索引失效；函数包裹列如 `WHERE to_char(create_time)='2024-01-01'` 索引用不上；like '%xxx' 前缀模糊无法走索引；联合索引没遵守最左前缀；深分页 `LIMIT 1000000, 10` 扫描 100 万行后丢弃。对症下药：函数包裹列改写成范围条件（`create_time >= '2024-01-01' AND create_time < '2024-01-02'`）；深分页改 `WHERE id > last_id ORDER BY id LIMIT 10` 的游标方式；子查询改 join 并确认 join 字段有索引；确实要模糊搜索就上 ES 或全文索引。治理层面：慢 SQL 告警常态化（阈值 500ms），新 SQL 上线前做 EXPLAIN 评审，索引变更走审批+灰度。实践中的坑：加索引不是万能——选择性低的列（如 status 只有 2 个值）加索引 MySQL 优化器也不走；在备库验证索引效果要注意数据量差异；优化后要关注写放大（索引多会拖慢写入）与磁盘占用。

**延伸考点：** 为什么 status 这种低基数字段加索引可能没用？order by 排序慢一般怎么解决？

### Q14. JDK 新特性你们在工程里实际用了哪些？

**问题：** 除了 forEach、lambda，你们项目里用了哪些 JDK 8 之后的特性？具体解决什么问题？

**期望加分项：**

- 能讲清选型理由与坑：如 record 替代 Lombok 的 @Data（不可变、equals/hashCode 语义）、CompletableFuture 的异常处理与线程池选择

**解答：**
好的回答是"每个特性都有对应解决的问题"。工程里常见落地：record 用于定义 DTO 与不可变值对象，相比 Lombok @Data 更简洁且 equals/hashCode 基于组件自动生成，还支持模式匹配解构；switch 表达式 + 模式匹配（JDK17+）替代 if-else 链式判断与 instanceof 强制转换，代码意图更清晰；文本块（JDK15+）解决 SQL/JSON 字符串转义地狱；CompletableFuture 解决并行调用与编排，如 Q11 提到的并行 RPC——但要点是必须传自定义线程池（默认 ForkJoinPool 是公共池，业务任务会互相影响，且阻塞任务会耗尽池线程）；虚拟线程（JDK21）在高 IO 并发场景可以替代大量阻塞线程，显著降低内存占用，但要留意 pinning 问题（synchronized 块内阻塞会钉住载体线程）。选型上：团队要统一 JDK 版本（建议 LTS：8 或 17/21），升级前评估框架兼容性（Spring Boot 3.x 要求 JDK17、MyBatis 等中间件版本、Lombok 需要 1.18.20+）、字节码增强类工具（CGLIB/ByteBuddy）对高版本 JDK 的支持。实践中的坑：Optional 用在字段和集合里（Optional 本身不可序列化，也不建议做字段类型）；并行流 parallelStream 滥用导致线程与顺序问题；record 与 Jackson/MyBatis 的序列化兼容性需要较新版本支持；CompletableFuture 里业务代码抛异常若不显式 get/join 会被吞掉，要用 exceptionally/whenComplete 兜底。

**延伸考点：** 你们从 JDK8 升到 17/21 遇到的最大兼容性问题是什么？虚拟线程在什么场景收益最大？

- 有实际案例：重复支付回调怎么过滤、重复消息怎么去重

**减分项：**
- 只会说"用 Redis setnx"，答不出 setnx 的过期、删除时机和单点问题
- 不知道唯一索引冲突后要捕获 DuplicateKeyException 并优雅处理
- 忽略幂等键的生成规则（幂等键必须由客户端生成且唯一）
- 不区分接口幂等与消息去重

**解答：**
核心思路是"给每次业务操作定义一个唯一的幂等键，并用存储层约束保证只生效一次"。分场景：①下单/表单提交类，客户端生成唯一幂等 token（或用业务单号），服务端把 token 写入 Redis（setnx + 过期时间）作为第一道防线，同时业务表上建唯一索引（如 user_id + 幂等号）做最终兜底，插入时捕获 DuplicateKeyException 返回"已处理"；②支付回调类，用支付渠道的流水号（如 out_trade_no、transaction_id）做唯一索引，入库前先查订单状态机——只有待支付才能改为已支付，已支付直接返回成功；③MQ 消费去重，消费端维护去重表（业务主键唯一）或 Redis setnx（key 带业务主键，过期时间要覆盖消息重试窗口，通常 ≥ 24h），并在事务内插入去重记录，保证"去重和业务写入同事务"；④状态流转类，用乐观锁 `UPDATE t_order SET status = 'PAID' WHERE id = ? AND status = 'PAYING'`，影响行数为 0 说明已被处理。关键设计点是幂等键的生成：必须由调用方生成且全局唯一（UUID/雪花 ID），服务端不能自己造，否则重复请求带着不同 key 就无法识别。实践中的坑：Redis 幂等 key 没设过期时间导致 key 无限增长；setnx 成功但业务失败回滚，key 要用 Lua 保证原子删除；先查后插的竞态窗口必须靠唯一索引收口；幂等判断与业务写入不在同一事务里，出现"去重成功但业务没落库"的脏数据。

**延伸考点：** 幂等 key 的过期时间怎么定？为什么去重记录和业务写入必须同事务？

### Q16. 你们分布式锁是怎么实现的？遇到过什么问题？

**问题：** 定时任务在多个实例上都跑导致重复执行；或库存操作需要跨实例互斥。你们的分布式锁怎么做的？

**期望加分项：**
- 能对比 Redis setnx/Redisson、ZooKeeper、数据库锁的适用场景与可靠性差异
- 能讲 Redisson 的实现：看门狗续期、可重入、原子释放（Lua）
- 能讨论锁过期时间与业务执行时间不匹配的问题（锁过期导致并发进入临界区）
- 能说出 Redis 主从切换丢锁的风险与应对（RedLock/MultiLock、或换 ZK 强一致）
- 有实际踩坑：锁没释放、误删别人锁、时钟跳跃、GC 停顿导致锁过期

**减分项：**
- 只会写 setnx + expire 两步，不知道要原子设置（SET NX EX）
- 不讨论锁过期与业务耗时的矛盾
- 不知道看门狗机制或主从切换丢锁
- 把"分布式锁"和"本地锁"混为一谈，或不知道单点 Redis 的局限

**解答：**
先明确需求边界：分布式锁要解决"跨实例互斥"。Redis 实现：`SET key value NX PX 30000` 原子设锁，value 用唯一随机值（防误删别人锁，释放时 Lua 比较再删），这是最基础的方案；工程上直接用 Redisson 的 RLock，自带看门狗（默认 30s 续期，业务没结束自动续期）、支持可重入、自动释放。核心难点是"锁过期时间 vs 业务执行时间"：锁太短，业务没跑完锁就过期，另一个实例进来并发执行；Redisson 看门狗解决续期，但极端情况下 GC 停顿可能让续期也来不及。第二个问题是可用性与一致性权衡：Redis 主从异步复制，主节点宕机时锁可能丢失（客户端 A 加锁成功，主节点没复制就宕机，从节点顶上后 B 也能加锁成功），严格一致性场景要 RedLock（多节点多数派）或改用 ZooKeeper/etcd（强一致、临时节点 + watch 会话机制），但 ZK 方案有性能与运维成本。实践取舍：一般业务（定时任务幂等、缓存重建）用 Redisson 足够，配合"拿到锁后二次校验状态再执行"降低并发风险；对账、资金类强一致场景用 ZK/etcd 或数据库悲观锁兜底。实践中的坑：释放锁时用 del 而不是 Lua 比较删除会误删别人的锁；锁的粒度太粗（整表锁）导致并发退化；忘记在 finally 里解锁；Redis 单点故障时锁服务本身不可用，需要降级策略（DB 锁兜底或快速失败）。

**延伸考点：** RedLock 在什么场景下是必要的，它自己有什么争议？业务执行时间超过锁的续期上限怎么办？

### Q17. 跨服务的数据一致性你们怎么保证？分布式事务怎么做的？

**问题：** 下单要扣库存、扣优惠券、写订单，分布在多个服务里，任何一个失败都会造成数据不一致。你们怎么保证最终一致？

**期望加分项：**
- 能给出方案选型：本地消息表、事务消息（RocketMQ）、TCC、SAGA、最大努力通知，说明适用场景与取舍
- 能讲清 2PC 的问题（同步阻塞、协调者单点）与为什么不用它做高并发业务
- 能说 TCC 的 try/confirm/cancel 三阶段落地细节与空回滚、悬挂问题
- 结合具体业务：如扣库存用事务消息 + 对账兜底
- 强调"先定业务边界"：哪些可以异步、哪些必须强一致

**减分项：**
- 只会背名词（TCC/SAGA），说不出自己项目的具体实现
- 认为分布式事务一定能做到"强一致"，不承认最终一致 + 对账兜底是常态
- 不知道本地消息表与事务消息的区别
- 忽略幂等与补偿机制

**解答：**
先给结论：跨服务强一致（2PC/XA）在高并发业务里基本不可用——同步阻塞、协调者单点、长事务锁资源，业界主流是"最终一致 + 对账兜底"。方案选型按场景：①消息驱动型（下单后异步扣积分、发通知），用本地消息表（业务事务里同时写消息表，定时任务轮询投递 MQ）或 RocketMQ 事务消息（half 消息 + 本地事务确认 + 回查），核心是"本地事务与消息投递的原子性"；②多资源强一致性要求高且并发低（如账户间转账），用 TCC：try 阶段冻结资源，confirm 提交，cancel 释放，注意幂等、空回滚（try 未执行就收到 cancel）与悬挂（cancel 先于 try 到达）三个经典坑，也可用 Seata 的 AT 模式（自动生成 undo_log）；③补偿式（SAGA），把长流程拆成带补偿操作的正向步骤，任一失败沿反方向执行补偿，适合编排复杂但各步骤可补偿的场景。无论哪种方案，三个必备要素：每个参与者操作要幂等（重试安全）、要有对账任务兜底（定期比对订单/库存/资金流水，发现不一致自动冲正或告警）、要记录操作流水表便于排查。工程实践中的误区：把不需要强一致的操作硬做成分布式事务（如发短信、发通知），白白增加复杂度；把 TCC 的 cancel 写成交互式调服务而不是幂等补偿；没有对账，出问题只能靠人工。实践原则：能异步就异步、能本地事务就不引入分布式事务、必须有兜底对账。

**延伸考点：** 本地消息表和事务消息的差别？TCC 的空回滚和悬挂怎么处理？你们对账任务怎么设计？

### Q18. 你们限流熔断怎么做的？Sentinel 还是自研？

**问题：** 大促或上游故障时，你们的服务靠什么机制保护自己？限流、熔断、降级分别怎么做？

**期望加分项：**
- 能分层讲：网关层限流（Nginx/API 网关、按 IP/用户/接口）+ 应用层限流（令牌桶/漏桶/计数器）+ 依赖隔离（线程池隔离/信号量隔离）
- 能讲清限流算法与取舍：固定窗口临界问题、滑动窗口、令牌桶允许突发、漏桶平滑
- 熔断三态（关闭/打开/半开）与恢复逻辑：基于错误率/慢调用比例的阈值、探测请求
- 降级策略：返回兜底数据、默认值、本地缓存、快速失败
- 能联系实际：Sentinel/Hystrix/Resilience4j 选型，或自研的落地方案与监控

**减分项：**
- 限流熔断降级三个概念混着说，说不清各自触发时机
- 只会用框架，说不清熔断器状态机与恢复策略
- 不知道限流与"削峰填谷"（MQ 缓冲）的组合用法
- 没有兜底/降级方案，只说"限了就行"

**解答：**
三个机制职责不同：限流是"自己扛不住时主动拒绝"，熔断是"下游扛不住时快速失败不拖死自己"，降级是"功能不可用时给用户兜底体验"，要分层设计。限流：网关层（Nginx limit_req 或 API 网关）按 IP/用户/接口维度限流挡住大部分恶意与超量流量；应用层用令牌桶/滑动窗口做精细限流，令牌桶允许一定突发（Guava RateLimiter 是单机限流，分布式要 Redis+Lua 或 Sentinel 集群流控）；高并发写入场景配合 MQ 削峰填谷，让下游按自己的节奏消费。熔断：以 Sentinel 为例，配置接口的错误比例或慢调用比例阈值（如错误率 > 30%）、最小请求数、熔断时长，熔断打开后进入快速失败，半开状态放少量探测请求验证下游恢复，成功则关闭。降级：熔断后返回本地缓存/默认值/错误提示，而不是让请求堆积；降级要分级（核心链路强依赖、非核心链路可降级）。工程取舍：Sentinel 相比 Hystrix 更贴近国内实践（实时监控、流控规则可动态推送、资源粒度细），相比自研省大量开发量；但任何限流组件都要关注其自身可用性——Sentinel 控制台挂掉不影响规则生效（规则已推送到客户端），配置数据源（Nacos）挂了用本地规则兜底。实践中的坑：限流阈值拍脑袋（要基于压测得到的容量定，且按比例留 buffer）；只对入口限流不保护内部依赖；熔断阈值设得太敏感导致误伤；降级了但返回的错误码没有标记，监控看不出降级占比。

**延伸考点：** 你们限流阈值怎么定的，压测出容量后留多少 buffer？熔断打开期间流量都打到哪去了，怎么观测？

### Q19. MQ 消息丢失和重复消费，你们怎么处理的？

**问题：** 有人反映订单消息偶尔丢失，且消费者偶发重复处理。你们从生产端到消费端是怎么保障的？

**期望加分项：**
- 能按三段分析：生产端（confirm/ack 回调 + 重试）、Broker 端（持久化、多副本）、消费端（手动 ack、重试、幂等）
- 能讲 Kafka/RocketMQ 各自的关键配置：acks=all、min.insync.replicas、enable.auto.commit=false、事务消息/半消息
- 重复消费的解法：消费幂等（业务主键去重表/唯一索引/状态机），与接口幂等呼应
- 能说顺序消息的难点（分区有序、重试乱序、补偿）
- 有监控与告警：消费积压、消费失败重试次数、死信队列

**减分项：**
- 只答"加 try-catch 重试"，不知道 ack 机制
- 不知道手动 ack 与自动 ack 的语义差异（at-most-once/at-least-once）
- 说不清"先更新业务再发消息"与"先发消息"的原子性问题（回滚后消息已发）
- 没有积压监控与处理预案

**解答：**
消息可靠性要逐段分析：①生产端：确认机制——RocketMQ 用事务消息或同步发送 + sendResult 判断；Kafka 用 producer 的 acks=all 并处理回调重试；关键是"业务与发消息的原子性"：先更新 DB 再发消息，DB 回滚了消息可能已发，工程上用本地消息表（同事务写业务 + 消息表，轮询投递）或 RocketMQ 事务消息解决。②Broker 端：Kafka 配 replication.factor ≥ 3、min.insync.replicas ≥ 2、acks=all 保证写多副本才返回；RocketMQ 刷盘策略至少用 ASYNC_FLUSH + 主从同步复制。③消费端：关闭自动提交（enable.auto.commit=false），业务处理成功才手动 commit，失败则重试；重试要有上限并进死信队列人工处理。重复消费是常态（网络抖动导致 ack 丢失、重试机制天然会产生重复），所以消费逻辑必须幂等——用业务主键唯一索引/去重表/状态机（如订单已支付状态直接跳过），这和接口幂等是同一套方法论。顺序消息：分区维度有序（同一订单号路由到同一分区），但重试会打乱顺序，需要业务层用版本号校验。监控：消费积压量（Lag）、重试次数、死信队列告警是必须项，大促前要确认消费者吞吐与扩容预案。实践中的坑：消费端 try-catch 吞掉异常导致消息"丢了"（其实没 commit 会重复）；重试逻辑写成循环里 sleep 导致消费线程阻塞、积压加剧；消息体过大超出 MQ 限制（走附件存储）；把顺序性寄托在全局，影响吞吐。

**延伸考点：** 消息积压怎么快速处理（扩容消费者/临时新建 topic 分流）？事务消息回查失败会怎样？

### Q20. 开放性思考题：如果让你重构这个老系统，你怎么入手？

**问题：** 一个运行 5 年的老系统，代码 50 万行，没有自动化测试，核心服务耦合严重，QPS 峰值偶尔打满。让你负责重构/架构演进，第一步做什么？你会怎么推进？

**期望加分项：**
- 有工程方法论：不推倒重来，先治理风险再演进；灰度、可回滚、双跑对账
- 先做可观测性建设（日志、监控、链路追踪）作为改造基础
- 用"绞杀者模式"（strangler fig）逐步替换：新功能走新架构，老功能逐步迁移
- 优先级判断：按业务价值与风险矩阵排序，先解决容量与稳定性问题
- 有团队协作与推进意识：接口契约先行、自动化测试补建、文档沉淀

**减分项：**
- 张口就是"重写"，没有评估业务风险与成本
- 不先建可观测性，盲目动手
- 没有灰度与回滚方案
- 只谈技术不谈业务优先级与团队协作

**解答：**
第一原则：老系统重构最怕"推倒重来"，正确姿势是"渐进式演进 + 风险控制"。第一步不是写代码，而是建立可观测性——全链路日志（traceId）、指标监控（QPS、延迟、错误率、资源）、告警体系，先能"看见"系统，才能知道瓶颈在哪、改造后怎么验证。第二步做容量与稳定性治理：针对"QPS 峰值打满"这个最痛的问题，先解决当前容量瓶颈（如慢 SQL、热点接口、资源水位），这往往比架构改造收益更快、风险更低。第三步用绞杀者模式演进：识别核心链路，把新需求的实现放新架构（新服务/新表），老功能通过适配层逐步迁移，每次迁移都做"双跑"（新旧并行，结果对账）再切换，切换前必须想好回滚方案。优先级用"业务价值 × 风险"矩阵：先动影响面小、收益明确的模块（如日志/配置/非核心服务），核心资金链路放最后且要最谨慎。工程配套：给核心模块补最小可用自动化测试（不追求全覆盖，先锁住关键逻辑）、接口契约先行（OpenAPI 定义再实现）、按接口/表梳理依赖图作为改造依据。常见失败模式：只做技术炫技不做业务对齐；一次性大规模迁移没有回滚点；不沉淀文档导致知识断层。考核点在于候选人有没有"重构是长期工程"的认知：分阶段、可验证、可回滚、持续交付价值。

**延伸考点：** 你会先拆哪个服务，依据是什么？如何说服业务方支持一次看不到短期收益的重构？
